## Event loop

<details>
  <summary>Event loop overview</summary>

### Event loop

**Definition:** Цикл событий — это планировщик, который наблюдает за стеком вызовов и очередями задач. Когда стек пуст, он берет следующую задачу из очереди и помещает ее в стек для выполнения.

**How it works:**

- JavaScript выполняется **синхронно** в **одном потоке** — одновременно выполняется только один кадр стека вызовов.
- Длительная работа (таймеры, ввод-вывод, сеть) делегируется хосту (веб-API браузера или Node libuv).
- Когда асинхронная работа завершается, ее обратный вызов помещается в **очередь задач** (микрозадача или макрозадача).- Цикл событий повторяется: слив кода синхронизации → слив всех микрозадач → запуск одной макрозадачи → (браузер: возможно, рендеринг) → повтор.
- Стек должен быть пуст перед запуском любого обратного вызова в очереди.

| Часть                | Роль                                       |
| -------------------- | ------------------------------------------ |
| **Стек вызовов**     | Выполняет синхронные вызовы функций (LIFO) |
| **Веб-API/API узла** | Таймеры, ввод-вывод, события DOM, `fetch`  |
| **Очереди задач**    | Держите обратные вызовы готовыми к запуску |

**When to use:**

| Ситуация                               | Что проверить                                                                            |
| -------------------------------------- | ---------------------------------------------------------------------------------------- |
| `setTimeout(fn, 0)` не немедленно      | Обратный вызов ожидает стека + микрозадачи                                               |
| Заморозка пользовательского интерфейса | Длинный цикл синхронизации в основном потоке                                             |
| Порядок обещания и таймера             | Микрозадачи всегда перед следующей макрозадачой                                          |
| Отладка асинхронного потока            | Используйте [JSV9000](https://www.jsv9000.app/) или [Лупу](http://latentflip.com/loupe/) |

#### Common pitfalls

- Предполагая `setTimeout(fn, 0)` запускается сразу после текущей строки — микрозадачи запускаются первыми.
- Планирование неограниченное `Promise.resolve().then(...)` цепочки — блоки рендеринга и таймеры.
- Непонятный цикл событий браузера с фазами узла — см. [8_nodejs.md](./8_nodejs.md).

**Pluses and minuses:**

| +                                                          | −                                                        |
| ---------------------------------------------------------- | -------------------------------------------------------- |
| Простая модель параллелизма — никаких блокировок в куче JS | Код синхронизации, нагружающий процессор, блокирует все  |
| Микрозадачи дают предсказуемый порядок обещаний            | Бесконечные микрозадачи истощают макрозадачи и рендеринг |
| Работает одинаково в браузере и Node (в основном)          | Узел имеет доп. `process.nextTick` приоритет             |

**Examples:**

```js
console.log("sync");
setTimeout(() => console.log("macrotask"), 0);
Promise.resolve().then(() => console.log("microtask"));
// sync → microtask → macrotask
```

**Sources:** [javascript.info/event-loop](https://javascript.info/event-loop) · [Визуализатор JSV9000](https://www.jsv9000.app/) · [Лупа](http://latentflip.com/loupe/)

  <summary>Call stack</summary>

### Call stack

**Definition:** Структура данных LIFO, которая отслеживает активные вызовы функций и контексты их выполнения. Весь код приложения JavaScript проходит через стек вызовов.

**How it works:**

- Каждый вызов функции **помещает** новый контекст выполнения в стек.
- Когда функция **возвращается**, ее контекст **выскакивает**.
- Вложенные вызовы создают стек: `main()` → `foo()` → `bar()`.
- Каждый контекст имеет: переменную среду, цепочку областей действия, `this` привязка и (для генераторов) состояние.
- Переполнение стека (`Maximum call stack size exceeded`) происходит, когда рекурсия никогда не возвращается или глубина превышает предел движка (~ 10–50 тыс. кадров). Модель памяти ОС/процесса (виртуальные страницы, куча или стек): [Память: стек и куча](./3_js_variables.md#memory-stack-heap).

| Этап           | Что происходит                                                         |
| -------------- | ---------------------------------------------------------------------- |
| **Создание**   | Выделить память, построить цепочку областей действия, привязать `this` |
| **Исполнение** | Запустить тело функции; вложенные вызовы помещаются в стек             |
| **Снос**       | Вытащить контекст, когда функция возвращает                            |

**When to use:**

| Ситуация                 | Значение                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| Чтение трассировки стека | Вверху = текущая функция, внизу = точка входа                                                    |
| Рекурсия                 | Должен быть базовый случай или использовать батут/итерацию                                       |
| `async` функции          | `await` приостанавливает функцию, но не блокирует стек — продолжение выполняется как микрозадача |
| Обработчики событий      | Каждый вызов получает новый кадр стека                                                           |

#### Common pitfalls

- Ожидая `async`/`await` чтобы заблокировать поток — приостанавливается только эта функция; другой код продолжает работать.
- Бесконечная рекурсия без оптимизации хвостовых вызовов в JS (не гарантировано) — переполнение стека.

**Pluses and minuses:**

| +                                                                 | −                                                                       |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Простая ментальная модель потока синхронизации                    | Глубокая рекурсия может переполниться                                   |
| Сопоставление трассировок стека непосредственно для заказа вызова | Никакого параллельного выполнения JS в одном потоке                     |
| Быстрое нажатие/выталкивание для вызовов функций                  | Асинхронные обратные вызовы выполняются позже — не в том же кадре стека |

**Examples:**

```js
function greet(name) {
  console.log("Hello, " + name + "!");
}

function main() {
  greet("Alice");
  greet("Bob");
}

main();
// Stack: main → greet('Alice') → pop → greet('Bob') → pop → pop
```

**Sources:** [javascript.info/call-stack](https://javascript.info/call-stack)

### Microtasks vs macrotasks

**Definition:** Асинхронная работа запланирована в двух типах очередей. **Микрозадачи** выполняются после текущего кода синхронизации и перед следующей макрозадачой. **Макрозадачи** выполняются по одной за один оборот цикла событий.

**How it works:**

- После завершения кода синхронизации и опустошения стека движок очищает **всю очередь микрозадач**.
- Каждая микрозадача может включать в очередь дополнительные микрозадачи — все они выполняются в один и тот же ход перед любой макрозадачой.
- Затем запускается **одна** макрозадача (таймер, обратный вызов ввода-вывода, событие пользовательского интерфейса).
- Браузер может рисовать между макрозадачами; микрозадачи могут задерживать покраску.
- Узел добавляет `process.nextTick` — выполняется раньше других микрозадач (более высокий приоритет).

| Тип             | Примеры                                                                                          | Приоритет                                     |
| --------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| **Микрозадача** | `Promise.then/catch/finally`, `queueMicrotask`, `MutationObserver`, `async/await` продолжения    | Выше — слить все перед следующей макрозадачой |
| **Макрозадача** | `setTimeout`, `setInterval`, ввод-вывод, события пользовательского интерфейса, `message` событие | Нижний — по одному на итерацию цикла          |

**When to use:**

| Используйте микрозадачи | Используйте макрозадачи |

|--------------------------------|
| Обещание реакции, `queueMicrotask` | Таймеры, пользовательские события, завершение ввода-вывода |
| Наблюдение DOM (`MutationObserver`) | Отмененные обновления пользовательского интерфейса (часто `setTimeout`) |
| Прерывание синхронизации без блокировки рисования | Кадры анимации (`requestAnimationFrame` — отдельная очередь) |

#### Common pitfalls

- `requestAnimationFrame` **не** микрозадача — выполняется перед отрисовкой, отдельно от обеих очередей.
- Рекурсивный `queueMicrotask` или цепочки обещаний — могут заморозить страницу.
- Предполагая `setInterval` срабатывает точно в интервале — задерживается, если основной поток занят.

**Pluses and minuses:**

| +                                                | −                                                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Пакетные микрозадачи обещают эффективные реакции | Длинные цепочки микрозадач блокируют таймеры и пользовательский интерфейс                |
| Макрозадачи поддаются рендерингу (браузер)       | Сложнее рассуждать о смешанном коде таймера и обещания                                   |
| Явный приоритет: обещания раньше `setTimeout`    | Узел `nextTick` может привести к прекращению ввода-вывода при неправильном использовании |

**Examples:**

```js
Promise.resolve().then(() => console.log("micro 1"));
Promise.resolve().then(() => console.log("micro 2"));
setTimeout(() => console.log("macro"), 0);
// micro 1, micro 2, macro
```

**Sources:** [MDN QueueMicrotask](https://developer.mozilla.org/en-US/docs/Web/API/Window/queueMicrotask) · [MDN MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver)

</details>

### Execution order

**Definition:** Одна итерация цикла событий следует фиксированному порядку: запускать код синхронизации до тех пор, пока стек не станет пустым, очистить **все** микрозадачи, запустить **одну** макрозадачу, а затем, при необходимости, отрисовать кадр (браузер).

**How it works:**

- Код синхронизации всегда выполняется первым — сверху вниз, пока стек не станет пустым.
- Запускаются все ожидающие микрозадачи, включая те, которые были запланированы более ранними микрозадачами в том же ходу.
- На каждой итерации выполняется ровно **одна** макрозадача (кроме пакетов браузера).
- Браузер: после макрозадачи может выполняться **этапы рендеринга** (стиль, макет, рисование), если прошло достаточно времени (~ 16 мс для 60 кадров в секунду).
- Цикл повторяется до тех пор, пока все очереди не опустеют и не поступит новая работа.- Код синхронизации всегда запускается первым.
- Все ожидающие микрозадачи выполняются до следующей макрозадачи.
- Микрозадача, планирующая другую микрозадачу — новая тоже выполняется в том же ходу.
- Браузер может иметь отдельные очереди рендеринга между макрозадачами.

**When to use:**

| Ситуация                           | Ожидаемое поведение                                                      |
| ---------------------------------- | ------------------------------------------------------------------------ |
| Загадки с асинхронным выводом      | Трассировка: синхронизация → микрозадачи → один макрос                   |
| Пакетное чтение/запись DOM         | Читайте синхронно, пишите после микрозадач или в `requestAnimationFrame` |
| `Promise.then` внутри `setTimeout` | Сначала запускается макрос, затем его микрозадачи                        |
| Настройка производительности       | Делайте очереди микрозадач короткими                                     |

#### Common pitfalls

- Забыв об этом `setTimeout` внутри микрозадачи по-прежнему планируется **будущая** макрозадача (4 запуска после 2 и 6).
- `new Promise(executor)` запускает исполнителя **синхронно** — только `.then` является асинхронным.

**Pluses and minuses:**

| +                                                      | −                                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| Детерминированный порядок головоломок для интервью     | Реальные приложения смешивают множество источников — их трудно отследить |
| Микрозадачи выполняют цепочки обещаний атомарно за ход | Рендеринг может быть задержан из-за шторма микрозадач                    |
| Одна макрозадача за ход позволяет рисовать             | Порядок немного отличается в Node и браузере                             |

**Examples:**

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
Promise.resolve().then(() => setTimeout(() => console.log(4)));
Promise.resolve().then(() => console.log(5));
setTimeout(() => console.log(6), 0);
console.log(7);
// 1, 7, 3, 5, 2, 6, 4
```

**Sources:** [javascript.info/event-loop](https://javascript.info/event-loop)

## queueMicrotask & process.nextTick

<details>
  <summary>queueMicrotask & process.nextTick (Node)</summary>

### queueMicrotask & process.nextTick

**Definition:** `queueMicrotask(fn)` планирует микрозадачу в браузере и Node. узла `process.nextTick(fn)` планирует обратный вызов с **более высоким приоритетом**, чем у других микрозадач.

**How it works:**

- `queueMicrotask(callback)` — запускается после текущего кода синхронизации, в очереди микрозадач, перед следующей макрозадачой.
- То же семейство очередей, что и `Promise.then` реакции.
- Узел `process.nextTick(callback)` — отдельная очередь очищается **перед** микрозадачами обещаний и перед вводом/выводом.
- Предназначен для отсрочки работы без задержки ввода/вывода; злоупотребление `nextTick` может истощить цикл событий.
- Браузер: `queueMicrotask` on `globalThis` or `window`.

| API                | Окружающая среда | Приоритет                 |
| ------------------ | ---------------- | ------------------------- |
| `queueMicrotask`   | Браузер, Узел    | Стандартная микрозадача   |
| `Promise.then`     | Оба              | Стандартная микрозадача   |
| `process.nextTick` | Только узел      | Над другими микрозадачами |

**When to use:**

| Использование                                      | Избегайте                                                   |
| -------------------------------------------------- | ----------------------------------------------------------- |
| Запускать после обновления DOM, перед отрисовкой   | Длительные циклы в микрозадачах                             |
| Узел: отложить обратный вызов до фазы ввода-вывода | `nextTick` рекурсия вместо `setImmediate` для тяжелых работ |
| Polyfill обещает время реакции                     | Замена `Promise.then` для удобства чтения                   |

#### Common pitfalls

- Бесконечный `process.nextTick` цепочка в узле — блокирует ввод-вывод на неопределенный срок.
- Предполагая `queueMicrotask` бежит раньше `Promise.then` — та же очередь, порядок записи имеет значение.
- С использованием `setTimeout(0)` когда микрозадачи достаточно — добавляет ненужную задержку макрозадачи.

**Pluses and minuses:**

| +                                                          | −                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------- |
| Явное планирование микрозадач                              | Легко заморозить макрозадачи, если они рекурсивны       |
| `nextTick` выполняется перед обработчиками обещаний в Node | `nextTick` недоступно в браузере                        |
| Прервите работу синхронизации без `setTimeout(0)`          | Чрезмерное использование блоков ввода-вывода и таймеров |
| Предсказуемый порядок на уровне микрозадач                 | Различия между узлом и браузером                        |

**Examples:**

```js
console.log("sync");

queueMicrotask(() => console.log("microtask"));

Promise.resolve().then(() => console.log("promise microtask"));

// Node only:
// process.nextTick(() => console.log('nextTick')); // runs before promise microtask

setTimeout(() => console.log("macrotask"), 0);

// sync → nextTick (Node) → microtask → promise microtask → macrotask
```

**Sources:** [MDN QueueMicrotask](https://developer.mozilla.org/en-US/docs/Web/API/Window/queueMicrotask) · [javascript.info/microtask-queue](https://javascript.info/microtask-queue) · [Node process.nextTick](https://nodejs.org/api/process.html#processnexttickcallback-args) · [8_nodejs.md](./8_nodejs.md)

</details>
