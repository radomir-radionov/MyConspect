### From URL to pixels
**Definition:**

Ввод URL-адреса запускает цепочку от разрешения DNS через HTTP до анализа HTML и полного конвейера рендеринга браузера.

| Шаг | Действие |
|------|--------|
| Разобрать URL | Схема, хост, путь, запрос, фрагмент |
| Разрешить IP | HTTP-кэш HTML, затем DNS-кеши → IP |
| TCP | Трехстороннее рукопожатие (SYN → SYN-ACK → ACK) |
| ТЛС | Дополнительное рукопожатие + шифрование, если `https:` |
| HTTP | Запрос HTML; ответ потока |
| Разобрать | HTML → DOM; CSS → CSSOM |
| Рендеринг | Дерево рендеринга → макет → рисование → **композитинг графического процессора** |

**How it works:**

1. **Разобрать URL** — схема (`http`/`https`), хост, порт, путь, запрос, хэш. Хэш не отправляется на сервер.
2. **Повторное использование или выборка** — HTTP-кеш браузера может возвращать сохраненный HTML-документ (`Cache-Control` / `ETag`). Если нет, разрешите хост IP-адресу.
3. **Найдите IP** — файл хостов → кеш DNS браузера → кеш DNS ОС → рекурсивный преобразователь (часто интернет-провайдер) → корень → TLD → авторитетный. Первое попадание побеждает.
4. **Квитирование TCP** — SYN, SYN-ACK, ACK, чтобы обе стороны согласовали соединение.
5. **HTTPS** — подтверждение TLS (сертификат + ключи сеанса), после чего все байты HTTP шифруются. HTTP пропускает этот шаг.
6. **HTTP(S)-запрос** — обычно `GET /path` с `Host`, печенье, `Accept`. Сервер (часто Nginx) сопоставляет URI с файлом или восходящим потоком.
7. **HTML-поток** — парсер строит **DOM**; связанный CSS создает **CSSOM**. JS с блокировкой парсера без `defer`/`async`/`type="module"` приостанавливает анализ HTML.
8. **Дерево рендеринга** — объединить DOM + CSSOM; пропускать `display: none`.
9. **Макет** — геометрия (где/насколько большая). **Paint** — пиксели (цвет, текст, тени). **Композитинг** — графический процессор объединяет слои в кадр (`transform` / `opacity` оставайтесь на композиторе — именно он делает дешевую анимацию).

**When to use:**

Полная загрузка страницы · Навигация по SPA-клиенту (History API пропускает полную перезагрузку) · Подсказки по предварительной выборке/пререндерингу.

#### Common pitfalls

- Предполагается, что DNS работает мгновенно (TTL, промахи в кеше).
- Игнорирование стоимости установления связи TLS при первом посещении.
- Измерение только TTFB, а не LCP/CLS.
- Анимация `top`/`left`/`width` (макет) вместо `transform`/`opacity` (композитор/графический процессор).

**Pluses and minuses:**

| + | − |
|------|------|
| Предсказуемый критический путь | Много сетевых прыжков при холодном запуске |
| Кэшируется на каждом уровне | Трудно отлаживать без DevTools |

**Examples:**

```html
<!DOCTYPE html>
<html lang="en">
  <head><title>Products</title></head>
  <body><h1>Catalog</h1></body>
</html>
```

**Thoughts:**

*URL → кэши/DNS → TCP → TLS, если HTTPS → HTTP HTML → DOM+CSSOM → дерево рендеринга → макет → рисование → композитный графический процессор.*

CSSOM и этапы рисования → [2_css.md](./2_css.md). DOM API после анализа → [3_js_browser.md](./3_js_browser.md). HTTP/TLS/кэш → [6_web_api.md](./6_web_api.md).

**Sources:** [MDN — Как работают браузеры](https://developer.mozilla.org/en-US/docs/Web/Performance/How_browsers_work)

### DNS
**Definition:**

DNS (система доменных имен) сопоставляет удобочитаемые доменные имена с IP-адресами, чтобы браузер мог открыть сетевое соединение.

| Порядок поиска | Уровень кэша |
|--------------|-------------|
| 0 | `/etc/hosts` (или Windows `hosts`) — локальные переопределения |
| 1 | DNS-кеш браузера |
| 2 | DNS-кэш ОС |
| 3 | Рекурсивный преобразователь (часто ISP) |
| 4 | Корневой → TLD → авторитетный сервер имен |

**How it works:**

- Проверьте **файл хостов**, затем **кэш браузера**, затем **кэш ОС**, а затем **рекурсивный преобразователь**. Промахи идут root → TLD → авторитетный.
- Возвращает записи A/AAAA (IP); Цепочки CNAME увеличивают задержку.
- `dns-prefetch` / `preconnect` теплый DNS и TCP/TLS заранее.

**When to use:**

Первое посещение · CDN CNAME · внутренний DNS с разделенным горизонтом.

#### Common pitfalls

- Жесткое кодирование IP-адресов вместо имен хостов.
- Забывчивость `preconnect` для стороннего происхождения.
- Длинные цепочки CNAME без мониторинга.

**Pluses and minuses:**

| + | − |
|------|------|
| Удобочитаемые имена хостов | Дополнительная задержка поиска |
| Распределенный, кэшируемый | Неправильно настроенный TTL приводит к устаревшим IP-адресам |

**Examples:**

```html
<!-- Browser resolves example.com → 93.184.216.34 before fetching -->
```

**Sources:** [MDN — DNS](https://developer.mozilla.org/en-US/docs/Glossary/DNS)

  <summary>Fetching HTML</summary>

### Fetching HTML
**Definition:**

После разрешения DNS браузер открывает соединение TCP/TLS, отправляет HTTP-запрос и получает поток HTML-документов для анализа.

| Фаза | Что происходит |
|-------|--------------|
| Подключиться | TCP + TLS-квитирование (HTTPS) |
| Запрос | `GET /` с `Host` заголовок |
| Ответ | `200 OK`, `Content-Type: text/html` |
| Разобрать | Токенизировать HTML-поток в DOM |

**How it works:**

- После подключения браузер отправляет `GET` с `Host`, `Accept`, печенье.
- Сервер отвечает статусом, заголовками и потоком тела.
- Парсер потребляет HTML постепенно (потоковая передача).
- Сканер предварительной загрузки обнаруживает связанные ресурсы параллельно.
- Связанные активы — это дополнительные запросы: `<link rel="stylesheet">`, `<img src>`, `<script src>`, шрифты и т. д. Изображения обычно неблокируются; классические сценарии блокируют парсер.

**When to use:**

HTML того же происхождения · Попадание в пограничный кеш CDN · `304 Not Modified` повторная валидация.

#### Common pitfalls

- Гигантский встроенный JSON в HTML, раздувающий TTFB.
- Отсутствующий `Content-Type: text/html; charset=utf-8`.
- Без сжатия (gzip/Brotli) HTML.

**Pluses and minuses:**

| + | − |
|------|------|
| Потоковый анализ начинается раньше | Большой HTML по-прежнему блокирует первую отрисовку |
| Мультиплексирование HTTP/2 | Блокировка начала строки на HTTP/1.1 |

**Examples:**

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <link href="/style.css" rel="stylesheet" />
    <title>Document</title>
  </head>
  <body>
    <img src="/hello.jpg" alt="Hello" width="400" height="300" />
    <script src="/index.js" defer></script>
  </body>
</html>
```

Ответ HTML также запускает выборку `style.css`, `hello.jpg`, и `index.js`.

**Sources:** [MDN — HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP) · [MDN — Как работают браузеры](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/how_browsers_work)

</details>

### DOM
**Definition:**

DOM (объектная модель документа) — это интерактивное древовидное представление HTML-документа в памяти браузера. HTML является источником; анализ строит DOM.

| Концепция | Описание |
|---------|-------------|
| HTML | Статическая разметка в ответе |
| ДОМ | Граф объектов времени выполнения |
| Мутация | JS меняет DOM → браузер перерисовывает |

**How it works:**

- Парсер разбивает HTML на узлы: `document` → `html` → `head`/`body` → элементы/текст.
- DOM **живой** — мутации JS вызывают обновления стиля/макета.
- Исходный код HTML ≠ DOM после изменений JS.
- Классический `<script src>` в середине документа: синтаксический анализатор построил только узлы **над** тегом. `getElementById` на потом `<img>` is `null` если вы не используете `defer`/`async`/`module` или переместите скрипт после разметки.

**When to use:**

Статические страницы · SPA, отображаемые клиентом · `innerHTML` обновления.

#### Common pitfalls

- Путаница HTML-файла с DOM во время выполнения.
- `innerHTML` с ненадежным вводом (XSS).
- Предполагается, что текстовые узлы с пробелами не существуют.

**Pluses and minuses:**

| + | − |
|------|------|
| Стандартный API для всех браузеров | Многословие против фреймворков |
| Постоянные обновления | Частая запись приводит к сбою макета |

**Examples:**

```html
<!-- image is null: parser stopped at the script -->
<script src="script.js"></script>
<img id="image" src="/hello.jpg" alt="Hello" />

<!-- image is found -->
<img id="image" src="/hello.jpg" alt="Hello" />
<script src="script.js"></script>

<!-- also found: defer runs after HTML parse -->
<script src="script.js" defer></script>
<img id="image" src="/hello.jpg" alt="Hello" />
```

**Thoughts:** Манипулирование DOM → [3_js_browser.md](./3_js_browser.md). События → [3_js_events.md](./3_js_events.md).

**Sources:** [MDN — DOM](https://developer.mozilla.org/en-US/docs/Web/API/Document_Object_Model) · [MDN — скрипт](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/script)

</details>

### HTML parsing
**Definition:**

Браузер анализирует HTML сверху вниз: токенизация преобразует байты в токены, затем построение дерева создает узлы DOM. Классические скрипты без `async`/`defer`/`type="module"` разбор блоков.

| Шаг | Действие |
|------|--------|
| Токенизация | Байты → начальные/конечные теги, текст, комментарии |
| Деревянное строительство | Токены → DOM-узлы |
| Обработка скриптов | Блокирующие скрипты приостанавливают парсер |
| Сканер предварительной загрузки | Раннее обнаружение ресурсов |

**How it works:**

- Токенизатор читает байты → теги, атрибуты, текст, комментарии.
- Построитель деревьев вставляет узлы; исправляет дополнительные теги для каждой спецификации.
- **Блокировка парсера** `<script>` без `async`/`defer`/`module` приостанавливает построение дерева.
- Сканер предварительной загрузки заранее извлекает CSS/изображения/скрипты.

**When to use:**

Документ с отложенными скриптами · встроенный скрипт в середине тела · неверный HTML (восстановление ошибок).

#### Common pitfalls

- `<script>` in `<head>` без `defer` блокирует весь анализ.
- `document.write` во время синтаксического анализа (устаревший анти-шаблон).
- Использование неявных необязательных тегов для макета.

**Pluses and minuses:**

| + | − |
|------|------|
| Прощающее восстановление ошибок | Неверный HTML-код может отличаться в разных системах |
| Инкрементная сборка | Блокирующие скрипты задержки DOMContentLoaded |

**Examples:**

```html
<html><body><h1>Hello</h1><p>Text</p></body></html>
```

**Thoughts:** `async`/`defer` поведение скрипта → [3_js_browser.md](./3_js_browser.md).

**Sources:** [WHATWG — Синтаксический анализ](https://html.spec.whatwg.org/multipage/parsing.html)

</details>

### CSSOM
**Definition:**

CSSOM (объектная модель CSS) — это объектное представление анализируемых правил CSS в браузере. DOM содержит структуру; CSSOM содержит вычисленную информацию о стиле.

| Модель | держит |
|-------|-------|
| ДОМ | Структура документа |
| CSSOM | Правила стиля для каждого селектора |
| Рендеринг дерева | DOM + CSSOM объединены |

**How it works:**

- Каждая таблица стилей разобрана на объекты правил (селектор → объявления).
- Cascade вычисляет выигрышные стили для каждого элемента.
- CSSOM отделен от DOM до тех пор, пока не произойдет объединение дерева рендеринга.
- Блокировка рендеринга: CSS в `<head>` задерживает первую покраску (избегает FOUC). В первую очередь отдавайте предпочтение **критическому CSS** (общий + специфичный для страницы в верхней части страницы).
- Ожидание CSS не требует остановки анализа HTML (сканер предварительной загрузки), но **блокирует JS**: сценарии часто запрашивают вычисленные стили/селекторы.

**When to use:**

Внешняя таблица стилей · встроенная `<style>` · `@import` цепи (медленнее).

#### Common pitfalls

- `@import` внутри CSS (последовательная загрузка).
- Отсутствующий `<link rel="stylesheet">` in `<head>`.
- Предполагается, что порядок отрисовки определяется только порядком DOM.

**Pluses and minuses:**

| + | − |
|------|------|
| Отделяет структуру от презентации | `@import` блокирует параллельную выборку |
| Кэшируемые файлы CSS | Большой CSS задерживает первую отрисовку |

**Examples:**

```html
<head><link rel="stylesheet" href="/styles.css" /></head>
<body><h1>Hello</h1></body>
```

**Thoughts:** Каскадность и специфика CSS → [2_css.md](./2_css.md).

**Sources:** [MDN — CSSOM](https://developer.mozilla.org/en-US/docs/Web/API/CSS_Object_Model) · [MDN — Как работают браузеры](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/how_browsers_work)

</details>

### Render tree
**Definition:**

Дерево рендеринга объединяет DOM и CSSOM в дерево блоков, готовых к макетированию и рисованию. Элементы с `display: none` исключены. WebKit/Blink называют это деревом рендеринга; Gecko использует **дерево рамок**.

| Ввод | Выход |
|-------|--------|
| ДОМ | Узлы структуры |
| CSSOM | Стиль для каждого узла |
| Рендеринг дерева | Видимые поля с вычисленными стилями |

**How it works:**

- Прогулка ДОМ; прикрепите вычисленные стили из CSSOM.
- Исключать `display: none` поддеревья целиком.
- `visibility: hidden` остается на дереве (невидимый, все еще занимает место).
- Выход: коробки готовы к раскладке.

**When to use:**

Скрытые модальные окна (`display:none`) · внеэкранные меню · `content-visibility: auto`.

#### Common pitfalls

- `visibility:hidden` по-прежнему влияет на макет/CLS.
- `aria-hidden` не удаляет из дерева рендеринга.
- `display:none` дети все еще находятся в DOM (можно запросить).

**Pluses and minuses:**

| + | − |
|------|------|
| Выложены только видимые работы | Легко спутать `hidden` vs `display:none` |
| Объединяет стили DOM + | Псевдоэлементы добавляют дополнительные поля |

**Examples:**

```html
<body>
  <h1>Hello</h1>
  <p hidden>Not in render tree</p>
</body>
```

**Thoughts:** `display: none` vs `visibility: hidden` → [2_css.md](./2_css.md).

**Sources:** [web.dev — Дерево рендеринга](https://web.dev/articles/critical-rendering-path/constructing-the-object-model)

</details>

### Layout (Reflow)

**Definition:**

Макет (перекомпоновка) вычисляет геометрию каждого видимого элемента — ширину, высоту, положение и поля — на странице.

| Изменение недвижимости | Перекомпоновка триггеров? |
|-----------------|-----------------|
| `width`, `height`, `padding` | Да |
| DOM вставка/удаление | Да |
| `transform`, `opacity` | Нет (композитор) |

**How it works:**

- Вычисляет x/y/ширину/высоту для каждого поля дерева рендеринга рекурсивно от корня (размера области просмотра).
- **Нормальный поток:** блоки, которые не влияют на одноуровневые элементы, можно изменить за один проход. Оставайтесь в потоке, чтобы движок выполнял меньше работы.
- **Глобальный макет** — целое дерево (изменение размера окна). **Инкрементная компоновка** — только **грязные** узлы: мутировавший элемент и его потомки (дочерние элементы могут зависеть от родителя).- Триггеры: изменение размера, загрузка шрифта, вставка/удаление DOM, чтение макета после записи.
- Здесь запускаются алгоритмы Flexbox/Grid/table.

**When to use:**

Первоначальный макет страницы · Адаптивное изменение размера · Динамическое внедрение контента.

#### Common pitfalls

- Анимация `width`/`height`/`top`/`left` (запускает макет каждого кадра).
- Чтение `offsetHeight` затем написание стиля в цикле.
- Изображения без размеров, вызывающие перекомпоновку при загрузке.

**Pluses and minuses:**

| + | − |
|------|------|
| Точная геометрия | Самый дорогой этап рендеринга |
| Требуется для читаемости текста | Разбивка макета при чередовании чтения и записи |

**Examples:**

```html
<div>One</div>
<div>Two</div>
```

**Thoughts:** Боксовая модель и режимы макета → [2_css.md](./2_css.md).

**Sources:** [MDN — Reflow](https://developer.mozilla.org/en-US/docs/Glossary/Reflow)

</details>

### Paint

**Definition:**

Paint растрирует внешний вид каждого блока — текст, фон, границы и тени — в растровые слои.

| Этап | Ответы |
|-------|---------|
| Макет | Где и насколько большой? |
| Краска | Как это выглядит? |
| Композитный | Как укладываются слои? |

**How it works:**

- Растеризует визуальные части: текст, фон, границы, тени.
- Разделить записи краски на слой; область просмотра разбита на прямоугольники — перерисовываются только грязные плитки.
- Рисование обычно является самым ресурсоемким этапом ЦП среди этапов синтаксического анализа → макета → рисования.
- Упрощенный порядок (сзади → спереди, в контексте штабелирования): `background-color` → `background-image` → `border` → потомки → `outline`. Полный порядок → [2_css.md — контекст стекирования](./2_css.md).
- `overflow:hidden` а контексты наложения создают границы клипа.

**When to use:**

Отрисовка текста · тени от прямоугольников · `border-radius` · большой `box-shadow` перекрашивает.

#### Common pitfalls

- Огромный `box-shadow` на прокручиваемых контейнерах.
- Частый `background` изменения на крупных элементах.
- Предполагая `opacity` всегда избегает краски (зависит от слоя).

**Pluses and minuses:**

| + | − |
|------|------|
| Необходимо для визуальной точности | Большие площади окраски обходятся дорого |
| Разделение слоев помогает | `will-change` чрезмерное использование приводит к потере памяти |

**Examples:**

```html
<p class="hero">Styled text</p>
```

**Thoughts:** Стоимость краски и `will-change` → [2_css.md](./2_css.md).

**Sources:** [MDN — Repaint](https://developer.mozilla.org/en-US/docs/Glossary/Repaint)

</details>

<details>
  <summary>Compositing</summary>

### Compositing

**Definition:**

Композиция объединяет нарисованные слои в финальный кадр на графическом процессоре. Элементы с `transform`, `opacity`, or `will-change` могут быть повышены до отдельного слоя.

| Изменить тип | Типичная стоимость |
|-------------|--------------|
| Макет | Самый высокий |
| Краска | Средний |
| Только композитный | Самый низкий |

**How it works:**

- Макетирование и рисование выполняются на **ЦП**; анимация, удобная для композитора, использует **GPU**.
- Графический процессор объединяет окрашенные слои в окончательный буфер кадра. Слои независимы — изменение одного не требует перерисовки другого.
- Продвигаемые слои: `transform`, `opacity`, `will-change`, `<video>`, `<canvas>`.
- Только композитор меняет макет пропуска и часто пропускает отрисовку.
- Проверьте, какие свойства CSS активируют макет/рисование/композит: [CSS Triggers](https://csstriggers.com/).

**When to use:**

`transform` анимации · фиксированные заголовки · наложения видео.

#### Common pitfalls

- Анимация `margin` вместо `transform`.
- `will-change: transform` на всем.
- Игнорирование ограничений памяти мобильного графического процессора.

**Pluses and minuses:**

| + | − |
|------|------|
| Плавная анимация со скоростью 60 кадров в секунду | Дополнительные слои используют память графического процессора |
| Пропускает макет для преобразований | Чрезмерное продвижение приводит к взрыву слоя |

**Examples:**

```html
<div class="animated-card">Compositor-friendly</div>
```

**Thoughts:** Анимация, оптимизированная для графического процессора → [2_css.md](./2_css.md).

**Sources:** [MDN — Композитный](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Composite)

</details>

<details>
  <summary>Layout vs Paint vs Compositing</summary>

### Layout vs Paint vs Compositing

**Definition:**

Эти три этапа рендеринга отвечают на разные вопросы. Понимание того, какие свойства CSS запускают какой этап, помогает оптимизировать анимацию и избежать зависаний.

| Этап | Ответы | Типичные триггеры |
|-------|---------|------------------|
| **Макет** | Где? Насколько большой? | `width`, `height`, `padding`, вставка ДОМ |
| **Краска** | Как это выглядит? | `color`, `background`, `box-shadow` |
| **Композитный** | Как укладываются слои? | `transform`, `opacity` |

**How it works:**

- **Макет** — геометрия. **Краска** — пиксели. **Композитный** — набор слоев.
- Панель DevTools Performance показывает, на каком этапе было запущено каждое изменение.
- Отдавайте предпочтение композитным свойствам для анимации.

| Этап | Стоимость | Типичные объекты недвижимости |
|-------|------|--------------------|
| Макет | Самый высокий | `width`, `height`, `padding` |
| Краска | Средний | `color`, `background`, `box-shadow` |
| Композитный | Самый низкий | `transform`, `opacity` |

**When to use:**

Изменение цвета при наведении (раскраска) · высота гармошки (макет) · выдвижная панель (`transform`, составной).

#### Common pitfalls

- С использованием `top`/`left` для анимации вместо `transform`.
- Одно изменение свойства запускает все три этапа.
- Не проводить профилирование перед микрооптимизацией.

**Examples:**

```html
<div id="box">Content</div>
```

**Thoughts:** Полное руководство по производительности CSS → [2_css.md](./2_css.md).

**Sources:** [web.dev — Производительность рендеринга](https://web.dev/articles/rendering- Performance)

</details>

<details>
  <summary>Global vs incremental layout (dirty nodes)</summary>

### Global vs incremental layout (dirty nodes)

**Definition:** Layout может пересчитывать все дерево рендеринга (**глобальное**) или только **грязное** поддерево (**инкрементное**) — измененный элемент и его потомков.

**How it works:**

- **Глобальный** — например. изменение размера области просмотра: каждый блок должен соответствовать новой ширине. Дорогой.
- **Incremental** — изменение стиля/DOM загрязняет этот узел; дети загрязнены, потому что их размер/положение может зависеть от родителя.
- По возможности оставайтесь в **нормальном потоке**, чтобы братья и сестры не требовали дополнительных передач.

**When to use:**

Изменение размера окна (глобальное) · переключение ширины боковой панели (грязное поддерево) · вставка элемента списка.

#### Common pitfalls

Чтение `offsetHeight` после записи вызывает синхронную (часто глобальную) перекомпоновку.

**Pluses and minuses:**

| + | − |
|---|---|
| Инкрементальный метод позволяет избежать работы с полным деревом | Грязный родитель до сих пор выгуливает всех детей |
| Схема потока однопроходная для независимых коробок | Размеры вне потока/процентов могут привести к каскадному загрязнению |

**Examples:** Смена одной карты `padding` ретранслирует эту карточку и ее вложенное содержимое, а не обязательно всю страницу.

**Thoughts:**

*Dirty = измененный узел + потомки; изменение размера окна является глобальным.*

Таблица стоимости свойств CSS → [2_css.md — Перекомпоновка, перерисовка, композиция](./2_css.md).

**Sources:** [MDN — Как работают браузеры](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/how_browsers_work) · [Doka — Как браузер отображает страницы](https://doka.guide/js/how-the-browser-renders-pages/)

</details>

<details>
  <summary>Reflow, repaint, and animation frames</summary>

### Reflow, repaint, and animation frames

**Definition:** Конвейер рендеринга является циклическим. Изменения DOM/стиля перестраивают (части) дерево рендеринга, затем **перекомпоновывают** (макет) и/или **перерисовывают** один раз для **кадра анимации**.

**How it works:**

- Новый узел, изменение текста или геометрии CSS → новое/обновленное дерево рендеринга → макет → рисование.
- Цвет/`background` часто только **перекрашивать**; `width`/`margin`/`top` → **перекомпонуйте**, затем раскрасьте.
- Целевое значение ~60 кадров в секунду (~16 мс/кадр). `requestAnimationFrame(cb)` бежит `cb` **перед следующей покраской**, в соответствии с дисплеем.
- `setInterval(fn, 1000/60)` не синхронизируется с конвейером: кадры могут быть неравномерными, а скрытая вкладка может **догнать**, запуская множество обратных вызовов одновременно.

**When to use:**

Циклы анимации Canvas/JS · измерение макета, а затем его изменение в rAF · избежание искажений макета.

| + РАФ | − `setInterval` для визуальных эффектов |
|--------|-----------------------------|
| Перед рисованием, паузы на заднем плане | Не имеет отношения к этапу покраски |
| Близко к частоте обновления | Догоняющие всплески после неактивной вкладки |

#### Common pitfalls

Анимация `left`/`top`/`margin`/`background` каждый кадр (макет/покраска). Предпочитать `transform` и `opacity`.

**Examples:**

```js
function animate(ts) {
  box.style.transform = `translateX(${Math.min(ts / 10, 400)}px)`;
  requestAnimationFrame(animate);
}
requestAnimationFrame(animate);
```

**Thoughts:**

*Один цикл = один кадр анимации; сообщите браузеру с помощью `requestAnimationFrame`, а не интервал 16 мс.*

Подробности API → [3_js_browser.md — requestAnimationFrame](./3_js_browser_extra.md#request-animation-frame).

**Sources:** [MDN — requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/window/requestAnimationFrame) · [MDN — производительность анимации CSS и JS](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/CSS_JavaScript_animation_ Performance)

</details>

<details>
  <summary>Progressive rendering</summary>

### Progressive rendering

**Definition:** Прогрессивный рендеринг показывает полезные пиксели заранее, вместо того, чтобы ждать полного пакета HTML/CSS/JS — рисуйте постепенно по мере поступления ресурсов.

**How it works:**

- HTML представляет собой **поток**: парсер создает DOM по мере поступления байтов; первая отрисовка по-прежнему ожидает **CSS-блокировки рендеринга** для CSSOM.
- Сначала выпустите **критический CSS**; остальное отложить. `defer`/`async`/`type="module"` держите сценарии подальше от критического для парсера пути.
- Ниже: `loading="lazy"`, `content-visibility: auto`, скелеты при загрузке данных.

**When to use:**

Длинные статьи · Маркетинговый герой LCP · SSR HTML, который позже разводится.

#### Common pitfalls

Один гигантский файл CSS в `<head>`; Пакет блокировки парсера перед содержимым.

**Pluses and minuses:**

| + | − |
|---|---|
| Более быстрое восприятие FCP/LCP | Дополнительная сложность CSS/JS |
| Потоковая передача HTML начинает анализ раньше | Неполный CSS по-прежнему задерживает первое оформление стилей |

**Examples:** Встроенный CSS над сгибом в `<head>`; `<script defer>` для приложения; `loading="lazy"` на изображениях ниже.

**Thoughts:**

*Нарисуйте что-нибудь полезное как можно скорее — критический CSS + неблокирующий JS + ленивый нижний сгиб.*

Техники CSS → [2_css.md — прогрессивный рендеринг](./2_css.md). Загрузка скрипта → [3_js_browser.md](./3_js_browser.md).

**Sources:** [MDN — критический путь рендеринга](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Critical_rendering_path) · [web.dev — критический путь рендеринга](https://web.dev/articles/critical-rendering-path)

</details>

<details>
  <summary>First render — full pipeline</summary>

### First render — full pipeline

**Definition:**

Критический путь рендеринга — это последовательность от получения HTML/CSS/JS до первого нарисованного кадра. Ресурсы, блокирующие парсер, задерживают время первой отрисовки.

| # | Шаг |
|---|------|
| 1 | DNS-поиск |
| 2 | TCP/TLS-соединение |
| 3 | HTTP-запрос/ответ |
| 4 | HTML → DOM |
| 5 | CSS → CSSOM |
| 6 | Рендеринг дерева |
| 7 | Макет → Краска → Композит |

**How it works:**

- Критический путь рендеринга: HTML → DOM + CSS → CSSOM → дерево рендеринга → макет → рисование → композит.
- First Contentful Paint (FCP) / LCP отмечает видимые пользователем вехи. Полный FCP: [6_web_api.md](./6_web_api_security.md#first-contentful-paint-fcp).
- Блокировка парсера CSS в `<head>` задерживает первую отрисовку (браузер ожидает CSSOM). JS с блокировкой парсера без `defer` приостанавливает анализ HTML.

**When to use:**

Маркетинговый лендинг (оптимизировать LCP-героя) · Дашборд (отложить некритичный JS) · SSR + гидратация.

#### Common pitfalls

- Скрипты блокировки рендеринга в `<head>` без `defer`.
- Изображение героя без `width`/`height` or `fetchpriority`.
- CSS загружен внизу `<body>` вызывая FOUC.

**Pluses and minuses:**

| + | − |
|------|------|
| Четкие цели оптимизации (CRP) | Множество движущихся частей в HTML/CSS/JS |
| Измеримо с помощью веб-показателей | Чрезмерное встраивание раздувает HTML |

**Examples:**

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <link rel="stylesheet" href="/critical.css" />
    <script src="/app.js" defer></script>
  </head>
  <body><main><h1>First paint</h1></main></body>
</html>
```

**Thoughts:** Загрузка скрипта → [3_js_browser.md](./3_js_browser.md). Блокировка CSS → [2_css.md](./2_css.md).

**Sources:** [web.dev — критический путь рендеринга](https://web.dev/articles/critical-rendering-path)

</details>
