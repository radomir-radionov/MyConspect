### Что такое WebSocket protocol and how does it differ from HTTP?

**Definition:**

### WebSocket vs. HTTP: 2026 Technical Audit

**WebSocket** (RFC 6455) и **HTTP/3** (RFC 9114) представляют собой разные парадигмы связи на транспортном и прикладном уровне. В то время как HTTP/3 поверх QUIC сократил разрыв в задержке для циклов запрос-ответ, WebSocket остается стандартом для постоянных, полнодуплексных потоков с отслеживанием состояния.

**How it works:**

### Core Differences

* **Модель связи**: HTTP по своей сути представляет собой **запрос-ответ**. Даже при мультиплексировании HTTP/2 и HTTP/3 обмен данными диктуется клиентом. WebSockets реализует **полнодуплексную** связь через одно соединение TCP/TLS, позволяя любой стороне передавать данные асинхронно.
* **Жизненный цикл соединения**: HTTP преимущественно **без сохранения состояния**. Хотя HTTP/3 поддерживает постоянство соединения (0-RTT), он остается транзакционным. WebSockets подвергаются рукопожатию **HTTP 101 Switching Protocols**, преобразуя соединение в постоянный двоичный поток, который остается открытым до тех пор, пока он не будет явно разорван.
* **Накладные расходы протокола**: HTTP/1.1 требует повторяющейся передачи заголовков. HTTP/2+ сжимает их через **HPACK/QPACK**, но WebSocket всё равно выгоднее на частых коротких сообщениях: после рукопожатия кадр добавляет только **от 2 до 14 байт**.
* **Кадрирование**: у WebSocket свой формат кадра. Управляющие кадры (ping/pong) и кадры данных (текст/бинарные) идут вперемешку, без нового цикла запрос-ответ.

### Operation Mechanism

* **HTTP**: работает на основе транзакций. Клиент отправляет запрос; сервер обрабатывает состояние и возвращает ответ. Современный HTTP/3 использует **QUIC** (на основе UDP) для решения проблемы блокировки начала строки на транспортном уровне, что значительно повышает производительность традиционного веб-контента.
* **WebSockets**: использует долгоживущее TCP-соединение. Поддерживая канал, сервер избегает накладных расходов на повторные подтверждения TLS для каждого сообщения. Это уменьшает задержку доставки сообщений до `O(1)` после рукопожатия, что делает его детерминированным по сравнению с джиттером, присущим последовательным HTTP-запросам.

### Protocol Stack Integration

* **HTTP**: находится на **прикладном уровне** (уровень 7). HTTP/3 использует QUIC, который интегрирует функции транспортного уровня в стек протоколов.
* **WebSockets**: запускается через **заголовок обновления HTTP/1.1**, затем происходит переход к реализации специального протокола. В 2026 году **WebTransport** (построенный на основе HTTP/3) все чаще будет использоваться в случаях, требующих ненадежных или неупорядоченных потоков данных, хотя WebSocket остается повсеместным выбором для надежной упорядоченной связи.

### Best-Candidate Use Cases

* **HTTP/3**: оптимален для выборки документов, RESTful API и идемпотентного извлечения данных, когда накладные расходы на поддержание состояния не нужны.
* **WebSockets**: обязательно для сред с малой задержкой и состоянием:
 * **Механизмы совместной работы в реальном времени**: многопользовательское редактирование (например, синхронизация на основе CRDT).
 * **Данные финансового рынка**: тикеры обновляются с высокой частотой, при этом каждая миллисекунда сокращения задержки имеет решающее значение.
 * **Интерактивные игры**: управление синхронизированными обновлениями состояния игры в клиентских сеансах с высоким уровнем параллелизма.

### 2026 Modernization Note: WebSocket vs. WebTransport
Хотя WebSockets остаются стандартом для надежных потоков, **WebTransport API** теперь предпочтительнее для потоковой передачи мультимедиа с низкой задержкой и продвинутых игр, поскольку он позволяет разработчикам выбирать между надежной и ненадежной доставкой данных через HTTP/3, смягчая проблемы «блокировки начала строки», присущие протоколу WebSocket на основе TCP.

### Объясните how the WebSocket handSHAke works.

**Definition:**

### WebSocket Handshake Architecture (2026 Update)

**Квитирование WebSocket** преобразует стандартный запрос HTTP/1.1 в постоянный **полнодуплексный** протокол двоичного кадрирования (RFC 6455). Этот механизм обеспечивает связь с малой задержкой, минуя накладные расходы на повторяющиеся циклы HTTP-запрос-ответ.

**How it works:**

#### 1. Client Initiation
Клиент инициирует обновление с помощью HTTP-запроса GET. В 2026 году в число клиентов должны войти `Sec-WebSocket-Version: 13` заголовок, который остается окончательной версией для глобальной совместимости.

#### 2. Server Response and Protocol Switching
Сервер проверяет запрос. После проверки он возвращает статус **HTTP 101 Switching Protocols**. Соединение остается открытым, в результате чего базовый сокет переходит от текстового анализа HTTP к **Протоколу WebSocket Frame**.

#### 3. Cryptographic Handshake Integrity
Чтобы предотвратить неправильную идентификацию соединения кэширующими прокси-серверами и подтвердить, что сервер поддерживает протокол, сервер обрабатывает `Sec-WebSocket-Key` используя **GUID** `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`.

**Modernized Node.js (v22+) Implementation:**

*Примечание:* Хотя SHA-1 криптографически слаб для цифровых подписей, здесь он используется исключительно для **обфускации рукопожатия** и проверки протокола; он остается стандартом RFC 6455.

#### 4. Post-Handshake Full-Duplex Framing
После завершения рукопожатия обмен данными осуществляется посредством **кадров**. Эти кадры имеют минимальный заголовок (2–14 байт), что значительно снижает накладные расходы по сравнению со стандартными заголовками HTTP/2 или HTTP/3.

* **Сложность:** Сложность анализа кадра составляет `O(1)` относительно размера полезной нагрузки, поскольку структура заголовка имеет фиксированную длину после определения длины полезной нагрузки.
* **Постоянное состояние:** TCP-соединение остается активным до тех пор, пока `Close` кадр управления (код операции `0x8`) получен или происходит тайм-аут сети.
* **Безопасность (лучшая практика 2026 г.):** Всегда используйте **WSS (WebSocket Secure)** с использованием **TLS 1.3** для обеспечения целостности и конфиденциальности данных. Не используйте незашифрованные `ws://` в производственных средах.

**Examples:**

```http
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <base64-encoded-nonce>
Sec-WebSocket-Version: 13
Origin: https://example.com
```

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: <computed-hash>
```

```javascript
import { createHash } from 'node:crypto';

const MAGIC_STRING = '258EAFA5-E914-47DA-95CA-C5AB0DC85B11';

/**
 * Computes the Sec-WebSocket-Accept header value.
 * @param {string} clientKey - Provided via Sec-WebSocket-Key header
 */
function computeAcceptHeader(clientKey) {
    return createHash('sha1')
        .update(clientKey + MAGIC_STRING)
        .digest('base64');
}
```

### Что такое some common use cases for WebSockets?

**Definition:**

### WebSockets (RFC 6455) Modernized Audit

**WebSockets** обеспечивают постоянный полнодуплексный канал связи через одно TCP-соединение. В 2026 году они останутся стандартом для связи с низкой задержкой и отслеживанием состояния, хотя в конкретных корпоративных архитектурах их часто абстрагируют протоколами более высокого уровня, такими как **WebTransport** или **gRPC-Web**.

**How it works:**

### High-Frequency Use Cases

* **Производительность совместной работы (на основе CRDT)**: разрешение конфликтов в реальном времени с использованием **бесконфликтных реплицируемых типов данных (CRDT)** для многопользовательских сред редактирования (например, децентрализованных текстовых редакторов, движков холста, подобных Figma).
* **Телеметрия Интернета вещей на периферийных вычислениях**: двунаправленная потоковая передача для циклов управления и контроля с малой задержкой в ​​робототехнике и промышленном Интернете вещей, обычно с использованием сериализации **MessagePack** или **Protobuf** для минимизации накладных расходов на полезную нагрузку.
* **Интерфейсы высокочастотной торговли (HFT)**: синхронизация книги ордеров в реальном времени. WebSockets по-прежнему предпочтительнее **Событий, отправленных сервером (SSE)**, когда требуется двунаправленная сигнализация (например, отмена заказа).
* **Многопользовательские игры в реальном времени**: синхронизация состояний игровых серверов. Хотя **WebRTC** предпочтительнее для одноранговых каналов передачи данных, WebSockets обрабатывают широковещательную рассылку состояния сервера для массовых одновременных сеансов.* ** Оркестрация AI-агента **: потоковая передача ответов по токенам от серверных частей LLM к внешним интерфейсам, минимизируя время получения первого токена (TTFT).

### Technical Limitations & 2026 Alternatives
* **WebTransport (HTTP/3)**: для сценариев, требующих **ненадежной** доставки (дейтаграмм), WebTransport теперь является предпочтительным преемником WebSockets, поскольку он позволяет избежать блокировки заголовка линии (HOL), присущей TCP.
* **Масштабируемость**: соединения WebSocket сохраняют состояние и потребляют память для каждого сокета (`O(n)` где `n = connected clients`). Современные реализации используют **Redis Pub/Sub** или **NATS** в качестве брокера сообщений для отделения серверов шлюза WebSocket от логики приложения.

### 2026 Implementation Standard (Modernized)

Современные реализации используют **TypeScript** для обеспечения безопасности типов при передаче данных, часто используя **Zod** для проверки схемы входящих полезных данных JSON, чтобы предотвратить атаки путем внедрения или ошибки неправильного состояния данных.

### Performance Metrics
* **Задержка**: типичное время прохождения сигнала туда и обратно (RTT) для WebSockets значительно ниже, чем при опросе (`O(RTT)` vs `O(RTT + polling interval)`).
* **Объем памяти**: каждый открытый сокет потребляет примерно 10–50 КБ ОЗУ на стороне сервера, что требует эффективной **балансировки нагрузки** (например, NGINX, HAProxy) с использованием закрепленных сеансов, если состояние поддерживается на уровне приложения.

**Examples:**

```typescript
// Modernized WebSocket implementation with Type Safety
interface MarketUpdate {
  symbol: string;
  price: number;
  timestamp: number;
}

const socket = new WebSocket('wss://api.exchange.com/v2/stream');

socket.addEventListener('open', () => {
  const subscribeMsg = JSON.stringify({ action: 'subscribe', pair: 'BTC-USD' });
  socket.send(subscribeMsg);
});

socket.addEventListener('message', (event: MessageEvent<string>) => {
  try {
    const data: MarketUpdate = JSON.parse(event.data);
    // UI thread processing using requestAnimationFrame for 60/120fps smoothness
    requestAnimationFrame(() => updateDashboard(data));
  } catch (err) {
    console.error('Schema validation failed:', err);
  }
});

function updateDashboard(data: MarketUpdate): void {
  const el = document.getElementById(`price-${data.symbol}`);
  if (el) el.textContent = data.price.toFixed(2);
}
```

### Что такое the limitations of WebSockets?

**Definition:**

### Limitations of WebSockets in 2026

**WebSockets (RFC 6455)** остаются отраслевым стандартом полнодуплексной связи. Однако переход к **HTTP/3 (QUIC)** и бессерверным парадигмам требует переоценки их роли в современных архитектурах.

**How it works:**

#### Connection Lifecycle & Resource Management
* **Постоянное потребление ресурсов**. В отличие от модели запрос-ответ HTTP/1.1 или мультиплексированных потоков HTTP/2 и HTTP/3, WebSockets поддерживает TCP-соединения с отслеживанием состояния. Каждое соединение использует дескриптор файла сокета и память на сервере. В масштабе это приводит к `O(N)` сложность памяти, где `N` — это количество одновременно работающих пользователей, что усложняет горизонтальное масштабирование без внешнего брокера сообщений (например, Redis Pub/Sub, NATS).
* **Сохранение состояния и бессерверность**. Сохраняемость WebSocket принципиально несовместима с эфемерной природой **Бессерверных функций (FaaS)**. Такие решения, как *API-интерфейсы AWS API Gateway WebSocket* или *Azure Web PubSub*, эффективно абстрагируют это, но они вводят привязку к поставщику и дополнительные затраты на задержку для процесса установления связи/обновления.

#### Infrastructure & Network Constraints
* **Вмешательство промежуточного блока**: хотя HTTP/3 через QUIC обходит блокировку начала строки TCP, WebSockets привязаны к TCP. Старые брандмауэры, прокси-серверы Deep Packet Inspection (DPI) и ограничительные корпоративные шлюзы часто разрывают или разрывают долгоживущие соединения WebSocket, что требует агрессивных стратегий подтверждения/поддержания активности.
* **Сложность балансировки нагрузки**. Обычные балансировщики нагрузки уровня 7 требуют «закрепленных сеансов» или маршрутизации с поддержкой WebSocket для поддержания канала с отслеживанием состояния. Напротив, современные **Service Mesh (Istio/Linkerd)** справляются с этой задачей, но неправильная настройка часто приводит к отключению соединения во время развертывания чередующихся обновлений.

#### Protocol Efficiency vs. Alternatives
* **HTTP/3 и WebTransport**: **WebTransport (RFC 9218)** — это преемник WebSockets 2026 года, обеспечивающий высокую пропускную способность и низкую задержку. Он обеспечивает ненадежную (на основе дейтаграмм) и надежную потоковую связь через HTTP/3, смягчая проблемы блокировки начала строки, присутствующие в основе TCP WebSocket.
* **Избыток для простых обновлений**: для однонаправленных потоков «сервер-клиент» **События, отправленные сервером (SSE)** остаются более эффективными. SSE легче, работает со стандартными потоками HTTP/2 и имеет встроенную функцию автоматического переподключения, что сокращает количество шаблонного кода, необходимого для WebSockets.

#### Security & Compliance
* **Хрупкость аутентификации**: WebSockets не поддерживают стандартные заголовки HTTP (например, `Authorization: Bearer `) во время `101 Switching Protocols` рукопожатие в среде браузера. Разработчикам часто приходится передавать токены в качестве параметров запроса, которые могут привести к утечке в журналах сервера и истории браузера. **Согласование подпротокола** или аутентификация на основе файлов cookie предпочтительнее, но требует тщательного устранения CSRF.
* **Положение о конфиденциальности (GDPR/CCPA)**: постоянные соединения усложняют запросы «Право на забвение». Потоки данных в реальном времени должны активно отслеживаться в памяти, чтобы обеспечить немедленное завершение по запросу пользователя или по истечении сеанса для обеспечения соответствия требованиям.

#### Mobile & Connectivity
* **Состояние батареи и радио**: поддержание постоянного TCP-соединения дольше сохраняет мобильную радиосвязь в состоянии высокой мощности. В регионах с нестабильным сигналом 5G/6G частые циклы переподключения (проблема «громового стада») могут значительно сократить срок службы батареи мобильного устройства по сравнению с опросом на основе HTTP или push-уведомлениями (APN/FCM).

#### Summary Table: 2026 Protocol Comparison

| Особенность | Вебсокеты | HTTP/3 (Веб-транспорт) | ССЕ |
| :--- | :--- | :--- | :--- |
| **Транспорт** | TCP | QUIC | HTTP/2+ |
| **Полнодуплексный режим** | Да | Да | Нет |
| **Сложность** | Умеренный | Высокий | Низкий |
| **Случай использования** | Игры в реальном времени/Чат | Высокопроизводительная потоковая передача | Панели мониторинга в реальном времени |

#### Recommendation
Для новых проектов с нуля в 2026 году:
1. Используйте **SSE** для однонаправленных обновлений между сервером и клиентом.
2. Используйте **WebTransport** для обеспечения двунаправленной передачи данных с высокой производительностью и малой задержкой.
3. Используйте **WebSockets** только в том случае, если совместимость устаревших браузеров (среды до 2023 года) или широкая поддержка экосистемных библиотек является критическим бизнес-ограничением.

### Можете ли вы describe the WebSocket API provided by HTML5?

**Definition:**

### Technical Audit: WebSocket API (2026 Standards)

**WebSocket** — это **полнодуплексный** протокол связи с отслеживанием состояния, стандартизованный в **RFC 6455**. Он работает через одно постоянное TCP-соединение, минуя накладные расходы на циклы запрос-ответ HTTP/1.1. Первоначально представленный как часть пакета HTML5, теперь он является независимым стандартом IETF.

**How it works:**

### Key Aspects of WebSockets

- **Обновление протокола**: инициируется посредством **HTTP/1.1 GET-запроса**, содержащего определенные `Upgrade: websocket` и `Sec-WebSocket-Key` заголовки. После установления связи соединение переходит на уровень двоичного кадрирования.
- **Двунаправленное кадрирование**: данные разделяются на **кадры** (текстовые, двоичные, пинг, понг, закрытие). Фреймирование позволяет осуществлять фрагментированную доставку сообщений, сохраняя `O(1)` накладные расходы на заголовок кадра по сравнению с накладными расходами HTTP.
- **Встроенный стек браузера**: полностью интегрирован в **Веб-API** (WHATWG Living Standard). Современная архитектура предпочитает `wss://` (WebSocket Secure) для обеспечения шифрования TLS, обязательного для производственного развертывания.

### WebSocket Lifecycle

1. **Рукопожатие**: Клиент отправляет HTTP-запрос GET с `Upgrade` заголовки. Сервер проверяет через `Sec-WebSocket-Accept` (хеширование SHA-1 ключа клиента).
2. **Постоянное состояние**. В отличие от HTTP/3 (на основе QUIC), который оптимизирует потоки, WebSocket предоставляет необработанный, долгоживущий канал. Для балансировки нагрузки для горизонтального масштабирования требуются объединительные платы **прикрепленные сеансы** или **на базе Redis pub/sub**.
3. **Передача данных**: сообщения отправляются в виде непрерывных кадров. Двоичные данные (например, `ArrayBuffer`, `Blob`) поддерживается изначально, что делает его превосходным по сравнению с HTTP для высокочастотных двоичных данных (например, сигнализации WebRTC, двоичной сериализации, такой как Protobuf).
4. **Завершение**: управляемое отключение через `CloseFrame` (код операции `0x8`). Внезапный сбой сети вызывает `onerror` событие, за которым последовало `onclose`.

### 2026 Modern Considerations

- **WebSocket против WebTransport**: для потребностей высокой производительности эпохи 2026 года **WebTransport** (построенный на HTTP/3) предпочтительнее WebSockets для сценариев, требующих ненадежной доставки или многопотоковой передачи без блокировки начала строки.
- **Управление ресурсами**: соединения WebSocket потребляют память сервера для каждого сокета. Проверяйте реализации на предмет поддержки **противодавления**, чтобы предотвратить переполнение буфера во время пакетов с высокой пропускной способностью.

### Объясните the WebSocket frame format.

**Definition:**

### WebSocket Frame Architecture (RFC 6455 Refined)

Протокол **WebSocketframe** обеспечивает полнодуплексную связь через одно TCP-соединение. Современные реализации (2026+) отдают приоритет высокопроизводительному кадрированию данных и строгой гигиене безопасности, особенно в отношении маскировки и фрагментации кадров.

**How it works:**

#### Initial Header and Control Bits

Каждый кадр начинается с фиксированной 2-байтовой последовательности. Первый байт идентифицирует состояние фрагмента и код операции, а второй байт определяет бит **Маски** и начальную длину полезных данных.

* **FIN (1 бит):** Указывает последний фрагмент сообщения.
* **RSV1-3 (3 бита):** Зарезервировано для расширений протокола (например, для каждого сообщения). `deflate` сжатие). Должно быть `0` если продление не оговорено.
* **КОД операции (4 бита):**
 * `0x0`: Продолжение
 * `0x1`: Текст (UTF-8)
 * `0x2`: Двоичный
 * `0x8`: Закрытие соединения
 * `0x9`: Пинг
 * `0xA`: Понг
* **МАСКА (1 бит):** Если установлено значение `1`, a `32`Далее следует -битный ключ маскировки. Согласно RFC 6455, клиенты **должны** маскировать все кадры, отправляемые на серверы. Серверы **не должны** маскировать кадры, отправляемые клиентам.

#### Extended Header Logic

Поле длины полезной нагрузки (7 бит) определяет необходимость байтов расширенной длины:
* **0–125:** Значение представляет собой длину полезных данных.
* **126:** Следующее `16` биты (`2` байты) представляют длину полезной нагрузки (беззнаковый обратный порядок).
* **127:** Следующее `64` биты (`8` байты) представляют длину полезной нагрузки.

#### Payload and Masking

Полезные данные состоят из **Данных расширения** (если таковые имеются), за которыми следуют **Данные приложения**. 

**Masking Mechanics:**
Если бит маски установлен, полезная нагрузка подвергается операции XOR с `32`-битовый ключ маскировки (`masking_key`). Преобразование для `i`-ый байт данных (`transformed_octet_i`) is:

`transformed_octet_i = original_octet_i XOR masking_key[i mod 4]`

Этот механизм не обеспечивает криптографической безопасности; он существует исключительно для предотвращения межпротокольных атак на промежуточные прокси, которые в противном случае могли бы интерпретировать вредоносные двоичные данные как законные HTTP-запросы.

#### Example Interpretation (2026 Context)

Рассмотрим двоичный кадр: **FIN=1, код операции=0x2 (двоичный), маска=0, полезная нагрузка=75 байт 'A' (0x41).**

1. **Байт 0:** `10000010` (`0x82`). (набор FIN, двоичный код операции).
2. **Байт 1:** `01001011` (`0x4B`). (Бит маски 0, длина 75).
3. **Полезная нагрузка:** `75` байты `0x41`.

**Modern Implementation Note:** В 2026 году в производственных средах (например, при использовании Node.js `ws` или Питон `websockets` библиотеки), разработчики редко взаимодействуют с необработанными кадрами. Абстракции высокого уровня внутренне обрабатывают фрагментацию и маскирование. Аудиты должны быть сосредоточены на использовании **бита RSV1**, поскольку современные приложения, критичные к производительности, активно используют бит RSV1. `permessage-deflate` расширение (`RSV1=1`), чтобы уменьшить пропускную способность на `O(n)` относительно степени сжатия.

### Как WebSockets handle communication through proxies and firewalls?

**Definition:**

### WebSockets and Network Intermediaries (2026 Standards)

**WebSockets** (RFC 6455) обеспечивают постоянные полнодуплексные каналы связи через одно TCP-соединение. В 2026 году архитектурные проекты должны учитывать преобладание **HTTP/3 (QUIC)** и сложных межсетевых экранов **уровня 7 (L7)**.

**How it works:**

### Proxies and Intermediaries

* **Механизм обновления HTTP/1.1**: WebSocket начинается с HTTP-запроса `GET` с заголовками `Upgrade: websocket` и `Connection: Upgrade`. Старые прокси, которые не понимают WebSocket, часто не пропускают эти заголовки и отвечают `400 Bad Request` или `502 Bad Gateway`. 
* **Согласование протокола**: современные прокси действуют как **шлюзы с поддержкой WebSocket**. Они участвуют в HTTP-квитировании для поддержания состояния. Если посредник явно не поддерживает `Upgrade` механизм, он разорвет соединение.
* **Мультиплексирование соединений и HTTP/2+**. В то время как прокси-серверы HTTP/1.1 борются с долгоживущими потоками WebSocket (вызывая закрытия, вызванные тайм-аутом), прокси-серверы **HTTP/2 и HTTP/3 (QUIC)** справляются с мультиплексированием более эффективно. Однако WebSocket-over-HTTP/2 (RFC 8441) является обязательным стандартом современной инфраструктуры для предотвращения блокировки заголовка на уровне прокси-сервера.

### Firewalls and Content Inspection

* **Использование порта**: отраслевые стандарты требуют, чтобы трафик WebSocket проходил через **WSS (WebSocket Secure)** с использованием порта **443**. Брандмауэры, настроенные для трафика HTTPS, обычно разрешают трафик WSS, поскольку подтверждение связи и последующее формирование кадров непрозрачны для механизмов проверки с отслеживанием состояния после установки туннеля TLS.
* **Глубокая проверка пакетов (DPI)**: сложные межсетевые экраны уровня 7 выполняют **завершение TLS**. Расшифровывая трафик, эти брандмауэры могут проверять отдельные фреймы WebSocket. Если полезная нагрузка WebSocket нарушает политику безопасности (например, несанкционированное туннелирование протокола), брандмауэр отправит сообщение `TCP RST` чтобы прекратить соединение.
* **Политика таймаута простоя**: брандмауэры часто завершают TCP-соединения, которые кажутся простаивающими. Современные реализации WebSocket должны использовать **управляющие кадры Ping/Pong** (каждые 30–60 секунд) для поддержания состояния и предотвращения молчаливого разрыва сеанса промежуточными устройствами.

### Addressing Challenges: 2026 Best Practices

* **Инкапсуляция через TLS**: TLS 1.3 является обязательным транспортным уровнем. Он обеспечивает **прямую секретность**, значительно усложняя проверку контента для брандмауэров, если только они не выполняют прокси-сервер «человек посередине» (MITM) с доверенными корпоративными корневыми сертификатами.
* **Резервные стратегии**. В средах с высокими ограничениями **WebSockets-over-HTTPS** действует как базовый вариант. В случае сбоя подключения из-за блокировки, зависящей от протокола, приложения должны вернуться к использованию **WebTransport** (через HTTP/3), который обеспечивает связь с малой задержкой и изначально совместим с современной сетевой инфраструктурой на основе QUIC.

### Modern Implementation (Python 3.14+)

In 2026, `websockets` (asyncio-native) является предпочтительной библиотекой. Он автоматически управляет механизмами управления на уровне кадра и контрольного сигнала (пинг/понг), что имеет решающее значение для поддержания прозрачности прокси.

### Technical Audit Summary
* **Предупреждение об устаревании**: избегайте использования ручного управления. `websocket-client` (на основе потоков) в средах с высоким уровнем параллелизма; использовать `asyncio` для эффективности работы.
* **Соответствие стандартам**: убедитесь, что все рабочие конечные точки поддерживают **RFC 8441** для беспрепятственного прохождения через прокси-серверы с поддержкой HTTP/2.
* **Сложность**: установление соединения WebSocket включает в себя `O(1)` переход к установлению связи, но для поддержания состояния в средах NAT требуется `O(n)` сердцебиений в течение срока службы соединения.

**Definition:**

### Security Considerations for WebSocket Architecture (2026)

Постоянные соединения смещают границы безопасности от проверки на основе запросов к проверке состояния сеанса. Современные реализации должны учитывать долгоживущие транспортные уровни и смягчение асимметричного потребления ресурсов.

**How it works:**

#### Key Security Concerns

* **Межсайтовый перехват WebSocket (CSWSH)**. В отличие от стандартного CORS, подтверждение WebSocket не приводит к автоматическому обеспечению соблюдения политик одного и того же происхождения. `Origin` заголовок должен быть строго проверен на соответствие белому списку доверенных схем и имен хостов. Неспособность подтвердить `Origin` позволяет межсайтовым сценариям инициировать несанкционированные постоянные соединения.
* **Очистка ввода (уровень протокола)**: WebSockets транспортируют необработанные двоичные или текстовые кадры. Поскольку постоянный характер позволяет осуществлять высокочастотную потоковую передачу, выполняйте **проверку схемы** (например, с использованием буферов протокола или схемы JSON) на уровне приложения, чтобы предотвратить атаки путем внедрения (SQLi, внедрение команд), которые обходят традиционное промежуточное программное обеспечение HTTP.
* **Исчерпание ресурсов и ограничение скорости**: постоянные соединения обходят стандартные правила брандмауэра для каждого запроса. Внедрите **управление противодавлением** и ограничения параллелизма на IP-адрес для смягчения последствий. `O(n)` DDoS-атаки с исчерпанием соединения. Установите тайм-ауты простоя, чтобы предотвратить использование файловых дескрипторов соединениями-зомби.
* **Безопасность транспортного уровня (TLS)**: всегда используйте `wss://` (WebSocket Secure). Стандартный `ws://` соединения подвержены атакам типа «человек посередине» (MitM) и перехвату пакетов. TLS 1.3 является обязательным базовым уровнем в 2026 году.
* **Аутентификация и управление сеансами**: Аутентификация должна происходить во время первоначального HTTP-квитирования (например, с помощью файлов cookie Secure/HttpOnly или кратковременных токенов на предъявителя). После установки сервер должен сопоставить постоянное соединение с аутентифицированным идентификатором, гарантируя, что последующие сообщения в потоке строго проверяются на соответствие разрешениям владельца сеанса.
* **Атаки на размер сообщения и кадрирование**: установите строгие ограничения на размер кадра. Вредоносный клиент может передавать массивные полезные данные, вызывая исчерпание кучи. Внедрить `maxPayloadLength` порог на уровне обработчика WebSocket сервера.

**Definition:**

### Connection Monitoring

1. **Встроенные Heartbeats**: используйте встроенную версию браузера. `WebSocket.ping()` и `pong` события (если это поддерживается конкретной реализацией протокола) или реализовывать контрольные кадры уровня приложения. Стандартизировать на интервале `I` (обычно 30 секунд) и тайм-аут. `T < I`.

3. **Отслеживание на стороне клиента**. Используйте `onclose` и `onerror` слушатели событий. Для сред React 19+ оберните логику сокета в `useSyncExternalStore` или специальные перехватчики для обеспечения согласованности состояний в дереве компонентов.

**How it works:**

### Identifying Disconnection Causes

1. **Изящное закрытие**: обозначается кодом закрытия. `1000` (Нормальное закрытие).
2. **Аномальное отключение**: обозначается кодом закрытия. `1006` (Близкий кадр не получен). Обычно это означает тайм-аут уровня TCP, истечение срока действия таблицы NAT или физический сбой сети.
3. **Ошибки протокола**: обозначаются кодами. `1002` (ошибка протокола) или `1009` (Сообщение слишком большое). Для этого требуются обновления логики на стороне клиента, а не повторное подключение.

### Reconnection Strategies

1. **Дрожащая экспоненциальная задержка**. Предотвратите синдром «Громового стада», добавив к отсрочке случайный фактор. 
 Задержка `D` рассчитывается как: `D = min(base × 2^n, max_delay) + jitter`, где `n` это количество попыток и `jitter in [0, base]`.
2. **Синхронизация состояния**. При повторном подключении клиент должен выполнить подтверждение синхронизации состояния, чтобы получить пропущенные события во время автономного окна (например, запросить дельта-полезную нагрузку на основе идентификатора последней обработанной последовательности).
3. **Интеграция API видимости**: используйте `document.visibilityState`. Приостановите или уменьшите частоту пульса, когда страница скрыта, чтобы сэкономить энергию и снизить нагрузку на сервер.

### Modernized Code Example (TypeScript/React 19)

### 2026 Auditor Notes
* **Производительность**: избегайте частых опросов; полагаться на настройки TCP Keep-Alive, настроенные в балансировщике нагрузки (например, NGINX `proxy_read_timeout` / тайм-ауты простоя AWS NLB) для разрыва соединений.

* **Сложность**: логика повторного подключения сохраняется. `O(1)` пространственная сложность, но управление состоянием соединения на стороне сервера во время широко распространенных событий повторного подключения `O(N)` где `N` количество одновременных клиентов. Обеспечьте ограничение скорости на стороне сервера `/ws` конечная точка рукопожатия.

```typescript
  }, [connect]);
```

### Объясните the role of ping/pong frames in WebSockets.

**Definition:**

### Role of Ping/Pong Frames in WebSockets (RFC 6455)

**Пинг** (код операции `0x9`) и **Понг** (код операции `0xA`) — это **Кадры управления** в протоколе WebSocket, предназначенные для **Мониторинг активности** и **Обслуживание пути**. Они работают независимо от потока данных, гарантируя, что базовое TCP-соединение остается жизнеспособным при наличии промежуточных устройств (NAT, балансировщиков нагрузки и межсетевых экранов).

**How it works:**

#### Purpose and Operational Necessity

1. **Поддержание соединения (живучесть):** Межсетевые экраны с отслеживанием состояния часто отключают простаивающие TCP-соединения после заранее определенного времени жизни (TTL). Периодические кадры Ping сбрасывают эти таймеры, предотвращая внезапное завершение соединения.
2. **Обнаружение мертвого узла:** Если сетевой путь выходит из строя или клиент автоматически отключается (например, при переходе в режим сна мобильного радио), отсутствие ответа Pong позволяет серверу идентифицировать «зомби-соединения». Затем сервер может инициировать `Close` кадры для освобождения файловых дескрипторов и памяти.
3. **Измерение задержки.** Включив временную метку в полезные данные приложения, конечные точки могут измерять время приема-передачи (RTT) для оценки работоспособности сети и настройки параметров контроля перегрузки.

#### Frame Architecture (RFC 6455 Specification)

Длина полезной нагрузки управляющего кадра не больше `≤ 125` байт, и такой кадр нельзя фрагментировать. 

| Тип рамы | Код операции (шестнадцатеричный) | Описание |
| :--- | :--- | :--- |
| **Пинг** | `0x9` | Запрос на коллегиальную проверку. |
| **Понг** | `0xA` | Незапрошенный или запрошенный ответ на пинг. |

**Hexadecimal Structure:**
Кадр Ping без полезной нагрузки представлен как:
`89 00` (Установлен бит FIN, код операции 9, бит маски 0, длина полезной нагрузки 0).

*Примечание:* Согласно разделу 5.5.3 RFC 6455, кадр Pong **должен** быть отправлен в ответ на кадр Ping как можно скорее, отражая полезную нагрузку «Данные приложения» полученного Ping.

#### Modern Security Considerations

* **Исчерпание ресурсов.** Быстрые и частые пинги являются вектором **DDoS (распределенный отказ в обслуживании)**. Внедрите ограничение скорости на уровне приложения или через входящий контроллер (например, NGINX/Envoy), чтобы отбрасывать соединения, превышающие предопределенный порог скорости пинга.
* **Зеркалирование полезной нагрузки.** Поскольку кадры Pong повторяют полезную нагрузку Ping, они не подходят для токенов аутентификации или конфиденциальных данных. Не рассматривайте ответы Pong как подтверждение личности; они только проверяют возможность подключения пути.

#### Modern Implementation (Python 3.14+ / `websockets` 15.0+)

В современных асинхронных парадигмах `websockets` библиотека автоматически обрабатывает сигналы Ping/Pong через `ping_interval` и `ping_timeout` параметры конфигурации. Ручной вызов обычно не нужен.

#### Complexity Analysis
* **Затраты памяти:** `O(1)` на каждое соединение, поскольку кадры ping являются временными и небуферизуются.
* **Сетевые издержки:** `O(k)` где `k` частота пингов. Протокол гарантирует, что это минимальное количество, поскольку управляющие кадры совместно используют существующий сокет TCP, а не устанавливают новые рукопожатия.

**Examples:**

```python

    # Automatically manages keep-alive pings every 20 seconds
    # Closes connection if Pong is not received within 10 seconds
    async with websockets.connect(
        "wss://api.example.com",
        ping_interval=20,
        ping_timeout=10
    ) as ws:
        async for message in ws:
            print(f"Data received: {message}")

if __name__ == "__main__":
    asyncio.run(connection_manager())
```

### Как WebSocket ensure ordered delivery of messages?

**Definition:**

### WebSocket Ordered Delivery Mechanisms

**WebSocket** обеспечивает упорядоченную доставку, используя встроенные потоковые гарантии **TCP** (протокол управления передачей) и **протокол кадрирования WebSocket** (RFC 6455).

**How it works:**

#### The Role of TCP Layering
WebSockets работают через одно долгоживущее TCP-соединение. **TCP** обеспечивает основную гарантию заказанной доставки с помощью следующих механизмов:

* **Порядковые номера**: каждому передаваемому байту присваивается уникальный порядковый номер.
* **Подтверждение (ACK)**: получатель подтверждает получение сегментов; если обнаружен пробел в порядковых номерах, получатель буферизует пакеты, не соответствующие порядку, и запрашивает повторную передачу недостающих сегментов.
* **Доставка по порядку**: стек TCP гарантирует, что сегменты доставляются на уровень приложения (реализация WebSocket) только после того, как все предыдущие сегменты были успешно получены и повторно собраны.

#### Full-Duplex Communication
В отличие от цикла запрос-ответ HTTP/1.1, протокол WebSocket поддерживает постоянный **полнодуплексный** канал. Это предотвращает «блокировку начала строки» на уровне приложения HTTP, разрешая асинхронный поток трафика, в то время как базовое TCP-соединение поддерживает строгую последовательную целостность для этого конкретного двунаправленного потока.

#### WebSocket Framing and Message Integrity
Когда сообщение WebSocket превышает размер буфера кадров или фрагментируется, **Протокол кадрирования WebSocket** обеспечивает реконструкцию с помощью бита **FIN (Final)**:

1. **Фрагментация**. Если сообщение слишком велико или требует потоковой передачи, отправитель разбивает полезную нагрузку на несколько кадров.
2. **Отслеживание кода операции**. В первом кадре используется определенный **код операции** (например, `0x1` для текста, `0x2` для двоичного кода), а последующие фрагменты используют **код операции продолжения** (`0x0`).
3. **Бит FIN**: `FIN` бит установлен на `0` для всех нефинальных фрагментов и `1` для последнего фрагмента. 
4. **Реконструкция**: конечная точка буферизует полезные данные кадров с помощью `FIN=0` до кадра с `FIN=1` получено, и в этот момент сообщение обрабатывается как дискретная единица.

#### Modern Implementation (2026 Standards)
В современных средах используются **Streams API** и **Web Workers** для эффективной реконструкции кадров, избегая объединения строк с интенсивным использованием памяти, которое наблюдалось в старых реализациях.

### Complexity Analysis
Реконструкция фреймов WebSocket эффективно `O(n)` относительно общего размера полезной нагрузки, где `n` — сумма байтов во всех фрагментах. Поскольку TCP гарантирует поступление сегментов по порядку (`i, i+1, dots, n`), реконструкция на уровне приложения привязана к памяти, а не к вычислениям. 

`T(n) = sum_i=1^k copy(frame_i) approx O(n)`

*Примечание: использование `ArrayBuffer` и `TypedArrays` в средах 2026 года гарантирует сохранение сложности пространства `O(n)`, что минимизирует нагрузку на сбор мусора по сравнению с устаревшей конкатенацией строк.*

**Definition:**

**WebSockets** поддерживают настоящую **двустороннюю полнодуплексную связь**. Хотя протокол определяет соединения «точка-точка» между клиентом и сервером, широковещательная рассылка достигается за счет ведения реестра активных соединений на уровне приложения и их перебора.

**How it works:**

### Modern Broadcasting Mechanism
- **Реестр соединений**: сервер управляет набором дескрипторов активных сокетов.
- **Сложность**: передача сообщения `N` подключенных клиентов несет `O(N)` накладные расходы на одно сообщение.
- **Горизонтальное масштабирование**: в производственных средах 2026 простые резидентные наборы (как показано в предыдущем коде) не работают в кластерах с балансировкой нагрузки. **Брокеры Pub/Sub** (например, Redis, NATS или RabbitMQ) теперь являются стандартом для синхронизации состояния между несколькими серверными узлами.

### Optimized Code Example (Python 3.14+)
Используя современные `asyncio` шаблоны и управление типизированными соединениями.

### Architectural Best Practices (2026)

* **Надежность вещания**: простой цикл `O(N)` подвержен блокировке начала строки медленного клиента. использовать `asyncio.gather` с `return_exceptions=True` чтобы предотвратить сбой цикла широковещательной передачи из-за одного отключенного клиента.
* **Развязка Pub/Sub**: для распределенных систем замените локальную `set()` с внешней шиной событий. Когда узел сервера получает событие, он публикует его в канале Redis; все экземпляры сервера подписываются на этот канал и передают информацию своим локально подключенным клиентам.
* **Жизненный цикл соединения**: всегда реализуйте механизмы **Heartbeat/Ping-Pong** (которые изначально обрабатываются `websockets` библиотека) для обрезки устаревших соединений (`O(1)` очистка) и предотвратить утечки памяти.
* **Аспекты протокола**. Для сценариев, требующих однонаправленной широковещательной рассылки (только от сервера к клиенту), оцените **События, отправленные сервером (SSE)** через HTTP/2, который обеспечивает автоматическое повторное подключение и снижает нагрузку на заголовок по сравнению с рукопожатием WebSocket.

**Examples:**

```python
import asyncio
from typing import Set
from websockets.server import serve, WebSocketServerProtocol

# Type-hinted connection tracking
active_clients: Set[WebSocketServerProtocol] = set()

async def handler(websocket: WebSocketServerProtocol):
    active_clients.add(websocket)
    try:
        async for message in websocket:
            # Broadcast pattern: Concurrently propagate to all clients
            if active_clients:
                tasks = [client.send(message) for client in active_clients]
                await asyncio.gather(*tasks, return_exceptions=True)
    finally:
        active_clients.remove(websocket)

async def main():
    async with serve(handler, "localhost", 8765):
        await asyncio.get_running_loop().create_future()  # Run forever

if __name__ == "__main__":
    asyncio.run(main())
```

### Что такое the difference between WebSockets and Server-Sent Events (SSE)?

**Definition:**

### Comparative Audit: WebSockets vs. Server-Sent Events (SSE)

**WebSockets** и **События, отправленные сервером** (SSE) представляют собой отдельные архитектурные шаблоны для потоковой передачи данных. По состоянию на 2026 год SSE повсеместно поддерживается во всех современных браузерах (включая полную реализацию в WebKit/Safari), что делает предыдущую «нишевую» классификацию устаревшей.

**How it works:**

### Key Distinctions

#### WebSockets
- **Характеристики**: **Полнодуплексный**, двунаправленная связь через одно долговечное TCP-соединение. Обеспечивает взаимодействие с низкой задержкой и отслеживанием состояния, при котором и клиент, и сервер действуют как одноранговые.
- **Протокол**: работает на основе специального протокола формирования кадров (RFC 6455), инициируемого посредством запроса на обновление HTTP 1.1/2/3.
- **Сложность**: требуется **управление состоянием** на обоих концах. Разработчикам приходится вручную реализовывать механизмы подтверждения (пинг/понг) для обнаружения молчаливых обрывов соединения.
- **Сценарий использования**: высокочастотные интерактивные приложения, требующие задержки в доли миллисекунды, такие как **совместное редактирование (CRDT)**, многопользовательские игры и высокочастотные торговые панели.

#### Server-Sent Events (SSE)
- **Характеристики**: **Однонаправленный** (сервер-клиент). Работает через стандартный HTTP. Как только соединение установлено, сервер передает клиенту текстовые потоки событий.
- **Протокол**: собственный **HTTP**. Он использует стандартные транспортные уровни, то есть использует мультиплексирование HTTP/2 и функции уровня потока HTTP/3 (QUIC) без необходимости установления связи по специальному протоколу.
- **Функции**: встроенная поддержка **автоматического повторного подключения**, отслеживание идентификаторов событий для восстановления сообщений и упрощенное использование через `EventSource` API. 
- **Сценарий использования**: потоковая передача обновлений данных с низкими затратами, например **генерация ответов LLM** (потоковая передача токенов вывода), потоки уведомлений в реальном времени и мониторинг телеметрии.

### Technical Comparison Summary

| Особенность | Вебсокеты | События, отправленные сервером (SSE) |
| :--- | :--- | :--- |
| **Общение** | Полнодуплексный (двунаправленный) | Однонаправленный (Сервер -> Клиент) |
| **Транспорт** | Пользовательское обновление TCP/HTTP | Собственный HTTP (1.1, 2, 3) |
| **Накладные расходы на соединение** | Высокий (с состоянием) | Низкий (HTTP без сохранения состояния) |
| **Формат данных** | Двоичный или текстовый (пользовательский) | Текст UTF-8 (EventStream) |
| **Поддержка браузера** | Универсальный | Универсальный (включая Safari/iOS) |
| **Сложность** | `O(n)` логика синхронизации состояния | `O(1)` потребление потока |

#### 2026 Architectural Guidance
* **Предпочитайте SSE** для приложений с большим объемом чтения или обновлений (например, мониторинг в реальном времени, потоковая передача токенов AI) из-за снижения затрат ресурсов по сравнению со стандартным HTTP и собственным автоматическим переподключением. 
* **Предпочитайте WebSockets** только в том случае, если приложению требуется настоящий одноранговый обмен сообщениями (например, VoIP, игры). Избегайте использования WebSockets для простых обновлений «сервер-клиент», чтобы избежать ненужных издержек TCP-квитирования и сложности управления состоянием.

### Объясните how a WebSocket connection is closed.

**Definition:**

### WebSocket Connection Termination (2026 Standard)

**Соединение WebSocket** (RFC 6455) — это постоянный полнодуплексный канал связи. Завершение происходит в соответствии с определенной процедурой **Закрытие соединения** для обеспечения целостности данных.

**How it works:**

### Closure Scenarios

#### The Close Control Frame
Завершение регулируется обменом **Закрытыми кадрами** (код операции `0x8`). Когда одна конечная точка инициирует закрытие, она отправляет кадр закрытия, содержащий необязательный код состояния и причину. Узел должен подтвердить это соответствующим кадром закрытия, прежде чем базовое **TCP-соединение** будет разорвано.

#### The CloseEvent Interface
По завершении браузер запускает `CloseEvent` на `WebSocket` объект:

* **`code`**: An `unsigned short` с указанием статуса закрытия (например, `1000` для нормального закрытия).
* **`reason`**: A `USVString` предоставление понятного человеку объяснения.
* **`wasClean`**: A `boolean` (Истина, если соединение корректно закрывается посредством рукопожатия).

### Closing via Client API

1. **Изящное закрытие**: клиент вызывает `socket.close(code, reason)`. Браузер инициирует рукопожатие и ждет подтверждения от сервера.
2. **Резкое прекращение**: вызвано потерей сетевого интерфейса или `AbortController` интеграция сигналов, что приводит к `wasClean = false`.

### Closing via Server-Side

1. **Изящное закрытие**: сервер отправляет кадр закрытия. Клиент при получении должен ответить своим собственным кадром Close.
2. **Ошибка протокола**: если сервер обнаруживает нарушение протокола WebSocket (например, неверные кадры), он немедленно разрывает соединение со статусом `1002`.

### 2026 Lifecycle Management

Современные приложения используют **Streams API** или **WebTransport** для обеспечения высокой производительности, но для стандартных WebSockets стабильность соединения контролируется с помощью `keepalive` механизмы на транспортном уровне для предотвращения полуоткрытых состояний TCP.

### Как бы вы implement a chat application using WebSockets?

**Definition:**

Чат держит один WebSocket на браузер. Сервер запоминает эти сокеты и пишет каждое сообщение остальным открытым сокетам. В протоколе нет комнат: приложение само решает, кому уходит кадр.

**How it works:**

- **Соединение**: Страница вызывает `new WebSocket("wss://example.com/chat")`. Браузер шлёт HTTP/1.1 upgrade (`Upgrade: websocket`, `Sec-WebSocket-Key`). Сервер отвечает `101 Switching Protocols`, после этого обе стороны шлют кадры.
- **Кто в комнате**: После рукопожатия сервер хранит сокет. В руководстве MDN для сервера сказано вести таблицу клиентов, чтобы не делать рукопожатие с тем же сокетом повторно. Комната — эта таблица, отфильтрованная по id комнаты, который прислал клиент.
- **Сообщение**: Текстовые кадры — UTF-8. Достаточно небольшого JSON (`{ "room", "text" }`). `send()` ставит данные в очередь; `bufferedAmount` растёт, пока байты не ушли из браузера.
- **Рассылка**: У сервера `ws` набор сокетов — `wss.clients`. Пишите только в сокеты с `readyState` равным `OPEN` и пропускайте отправителя, если интерфейс не должен слышать эхо.
- **Выход**: `close()` начинает закрывающее рукопожатие. На `close` уберите сокет из таблицы, чтобы следующие сообщения не писались в мёртвое соединение.

**When to use:**

- WebSocket нужен, когда обе стороны должны слать данные без нового HTTP-запроса: комната, где люди печатают одновременно.
- Историю, вход и «загрузить старые сообщения» оставьте на обычном HTTP. Сокет несёт живой хвост, а не весь архив.

**Examples:**

```js

const wss = new WebSocketServer({ port: 8080 });

wss.on("connection", (socket) => {
  socket.on("message", (data, isBinary) => {
    for (const client of wss.clients) {
      if (client !== socket && client.readyState === WebSocket.OPEN) {
        client.send(data, { binary: isBinary });
      }
    }
  });
});
```

### Объясните how Pub/Sub messaging can be achieved with WebSockets.

**Definition:**

Публикация и подписка — это схема приложения поверх кадров WebSocket. Издатель шлёт сообщение, сервер копирует его сокетам, подписанным на тему. RFC 6455 темы не задаёт.

**How it works:**

- **Подписка**: После `open` клиент шлёт текстовый кадр вроде `{"op":"sub","topic":"orders"}`. Сервер записывает сокет в эту тему.
- **Публикация**: Кадр издателя называет ту же тему. Сервер обходит сокеты темы и вызывает `send` только если `readyState` равен `OPEN`.
- **Один сокет, много тем**: У браузера по-прежнему одно соединение. Темы — имена в вашем JSON, а не отдельные TCP-соединения.
- **Несколько процессов**: Сокет живёт на одном процессе. Чтобы публиковать между машинами, процесс передаёт нагрузку в общую шину, и каждый процесс пишет в свои сокеты.

**When to use:**

- Карта тем нужна, когда одно событие должны услышать много клиентов и вы контролируете оба конца.
- Комнаты Socket.IO берите, когда нужна эта карта плюс собственный формат пакетов и запасной long-polling. Обычный клиент WebSocket этот формат не говорит.

**Examples:**

```js
const topics = new Map();

function publish(topic, payload) {
  for (const socket of topics.get(topic) ?? []) {
    if (socket.readyState === WebSocket.OPEN) socket.send(payload);
  }
}
```

Конструктор в браузере — `new WebSocket(url, protocols)`. Он не принимает произвольную карту заголовков. Заголовки рукопожатия, включая `Origin`, выставляет браузер.

**How it works:**

- **Что можно передать**: `protocols` — одна строка подпротокола или список. Они уходят как `Sec-WebSocket-Protocol`. Повтор или недопустимый токен даёт `SyntaxError`.

- **Вне браузера**: Клиент Node вроде `ws` может задать заголовки, потому что сам собирает HTTP-запрос. Это не браузерный `WebSocket`.

### Можно ли WebSockets be used together with other web technologies like WebRTC?

**Definition:**

Да. WebRTC нужен канал сигнализации, чтобы две стороны обменялись описаниями сессии и кандидатами ICE. В руководстве MDN по сигнализации сказано, что каналом может быть WebSocket или любой двусторонний путь.

**How it works:**

- **Разные задачи**: WebSocket несёт небольшие JSON-сообщения сигнализации через ваш сервер. Медиа и data channel идут между узлами или через TURN, а не через этот WebSocket.

**When to use:**

- Сокет используйте для «кто кому звонит» и текста SDP/ICE.
- Сами аудиосэмплы не гоните через WebSocket, если доступен WebRTC. Иначе медиа окажется на вашем сервере и на TCP.

### Что определяет a WebSocket message?

**Definition:**

Сообщение — это последовательность кадров, которые относятся друг к другу. Оно начинается с текстового или двоичного кода операции и заканчивается кадром, у которого бит FIN равен 1. У сообщения из одного кадра FIN равен 1 уже на первом кадре.

**How it works:**

- **Коды операций**: `0x1` начинает текст (UTF-8). `0x2` начинает двоичные данные. `0x0` продолжает то же сообщение. Управляющие коды не входят в это сообщение с данными.
- **FIN**: FIN 0 значит, что кадры ещё будут. FIN 1 значит, что накопленная нагрузка — полное сообщение. Событие браузера `message` приходит на собранное сообщение, а не на каждый фрагмент.
- **Чередование**: Управляющие кадры (ping, pong, close) могут прийти между фрагментами. Они не заканчивают сообщение с данными.

**Sources:**

<summary>Как WebSocket extensions used?</summary>

### Как WebSocket extensions used?

**Definition:**

Расширение меняет то, как переносятся кадры или нагрузка. Оно не задаёт смысл сообщения приложения. Обычный пример — сжатие `permessage-deflate`.

**How it works:**

- **Согласование**: Клиент перечисляет расширения в `Sec-WebSocket-Extensions`. Сервер возвращает принятые в ответе 101. Биты RSV в кадре зарезервированы под расширения.
- **Не подпротокол**: MDN: расширения необязательны и общие (сжатие). Подпротоколы — это структура нагрузки (чат против игры) и кадр они не меняют.
- **Цена**: Сервер `ws` оставляет permessage-deflate выключенным по умолчанию: zlib под нагрузкой может стоить памяти и CPU. Включайте его, только когда нагрузка достаточно велика, чтобы это окупилось.

**When to use:**

- Включайте `permessage-deflate` для болтливого JSON с повторяющимися ключами.
- Оставляйте выключенным для маленьких двоичных игровых пакетов и для серверов, которые уже упираются в CPU.

**Examples:**

```js
import { WebSocketServer } from "ws";

const wss = new WebSocketServer({
  port: 8080,
  perMessageDeflate: {
    threshold: 1024,
    concurrencyLimit: 10,
  },
});
```

### Объясните WebSocket's support for text and binary frames.

**Definition:**

**How it works:**

- **Зарезервированные коды**: Коды `0x3`–`0x7` и `0xB`–`0xF` в этой версии ничего не значат. Управляющие коды: `0x8` close, `0x9` ping, `0xA` pong.

<summary>Как message fragmentation handled in WebSockets?</summary>

### Как message fragmentation handled in WebSockets?

**Definition:**

Фрагментация режет одно сообщение на несколько кадров данных. У первого кадра код `0x1` или `0x2` и FIN 0. Следующие кадры используют код `0x0`. Последний кадр ставит FIN в 1.

**How it works:**

- **Где применяется**: В MDN фрагментация только для кодов `0x0`–`0x2`. Управляющие кадры так не режутся, и их нагрузка не больше 125 байт.
- **Сборка**: Получатель склеивает нагрузки, пока FIN не станет 1, и тогда считает результат одним текстовым или двоичным сообщением. Браузер делает это до события `message`.
- **Пример из MDN**: Один кадр `FIN=1, opcode=0x1` — целое сообщение. Следующее может быть `FIN=0, opcode=0x1`, затем `FIN=0, opcode=0x0`, затем `FIN=1, opcode=0x0`.

<summary>Что такое the standard status codes for indicating connection closure in WebSockets and what do they mean?</summary>

### Что такое the standard status codes for indicating connection closure in WebSockets and what do they mean?

**Definition:**

Кадр Close может нести код статуса и короткую причину. RFC 6455 задаёт 1000–1015 и резервирует диапазоны для следующих спецификаций, библиотек и частного использования. Метод браузера `close()` может задать только `1000` или код от 3000 до 4999.

**How it works:**

- **На проводе**: 1000 нормальное закрытие. 1001 сторона уходит. 1002 ошибка протокола. 1003 неподдерживаемые данные. 1007 плохой UTF-8. 1008 политика. 1009 сообщение слишком большое. 1010 клиент требовал расширение, которое сервер не выбрал. 1011 неожиданное состояние сервера.
- **Не ставятся в кадр**: 1005 значит, что статуса не было. 1006 значит, что соединение закрылось без кадра Close. 1015 значит, что рукопожатие TLS не удалось. Конечные точки не должны ставить их в кадр Close. 1004 зарезервирован.
- **Диапазоны**: 0–999 не используются. 1000–2999 — для протокола и публичных расширений. 3000–3999 — для библиотек, зарегистрированных в IANA. 4000–4999 — частные договорённости.
- **close() в браузере**: Строка причины — не больше 123 байт UTF-8. Код вне `1000` и `3000`–`4999` бросает `InvalidAccessError`.

**Sources:**

- [RFC 6455 — Status Codes](https://www.rfc-editor.org/rfc/rfc6455#section-7.4)
- [MDN — WebSocket.close()](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/close)
</details>

<summary>Как WebSocket mask data from the client to the server?</summary>

### Как WebSocket mask data from the client to the server?

**Definition:**

Каждый кадр от клиента к серверу ставит бит MASK и содержит 4-байтовый ключ маски. Каждый байт нагрузки XOR-ится с `key[i % 4]`. Кадры от сервера к клиенту не маскируются.

**How it works:**

- **Обязательно**: В MDN сказано, что сервер должен отключить клиента, который прислал немаскированный кадр (RFC 6455, раздел 5.1). Маскирование обязательно даже на защищённом сокете.
- **Ключ**: Клиент выбирает новый ключ маски на каждый кадр. MDN описывает это как меру, чтобы посредники не предсказывали байты на проводе.
- **Снятие маски**: Прочитайте 4 октета после длины, затем XOR. Браузер делает это сам. Сервер, который пишете вы, или библиотека вроде `ws` делает это до того, как обработчик `message` увидит нагрузку.

**Examples:**

```js
function unmask(encoded, mask) {
  return encoded.map((byte, i) => byte ^ mask[i % 4]);
}
```

**Sources:**

- [MDN — Writing WebSocket servers](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers)
- [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)
</details>

### Опишите error handling with WebSocket connections in JavaScript.

**Definition:**

### Как бы вы implement a WebSocket server in Node.js?

**Definition:**

**Examples:**

```js
import { WebSocketServer } from "ws";

const wss = new WebSocketServer({ port: 8080 });
wss.on("connection", (socket) => {
  socket.on("message", (data) => socket.send(data));
});
```

### Что такое the role of WebSocket server libraries, such as ws or Socket.IO?

**Definition:**

`ws` реализует протокол WebSocket для Node: upgrade, маскирование, фрагментацию, ping/pong и необязательный permessage-deflate. Socket.IO — другой протокол, который может взять WebSocket как транспорт.

**How it works:**

- **ws**: Браузерный `WebSocket` может подключиться к серверу `ws`. В readme сказано, что `ws` проходит набор тестов Autobahn и в браузере не работает.
- **Socket.IO**: В документации Socket.IO сказано, что это не реализация WebSocket. Сырой клиент не подключится к серверу Socket.IO, потому что каждый пакет добавляет кадрирование Engine.IO и Socket.IO.
- **Что не пишете сами**: Вы не XOR-ите маски и не собираете биты FIN. Аутентификацию, комнаты и смысл текстовой нагрузки вы всё равно задаёте сами.

**When to use:**

- Берите `ws`, когда другая сторона — браузерный `WebSocket` или другой стек RFC 6455.
- Берите Socket.IO, когда каждый клиент будет клиентом Socket.IO и вам нужны его запасной транспорт, подтверждения и комнаты.

**Sources:**

- [Socket.IO](https://socket.io/docs/v4/)

### Как servers handle WebSocket connection upgrades?

**Definition:**

<summary>Как бы вы authenticate WebSocket connections on the server side?</summary>

### Как бы вы authenticate WebSocket connections on the server side?

**Definition:**

Аутентифицируйте во время HTTP upgrade, до того как считать сокет участником чата. В readme `ws` слушатель `upgrade` вызывает вашу функцию `authenticate` и отвечает `401`, если она не прошла.

**How it works:**

- **Что есть в запросе**: В MDN сказано, что рукопожатие может включать `Cookie` и другие HTTP-заголовки. Браузеры также шлют `Origin`. Конструктор браузера не может задать заголовок `Authorization`.
- **Отказ по умолчанию**: В примере `ws` неудачный `authenticate` пишет `HTTP/1.1 401 Unauthorized` и уничтожает сокет. Только потом выполняется `handleUpgrade`.
- **После open**: Если токен не едет на cookie, потребуйте его в первом сообщении приложения и игнорируйте остальные кадры, пока проверка не пройдёт. Если не прошла — закройте частным кодом.

**Examples:**

```js
server.on("upgrade", (request, socket, head) => {
  authenticate(request, (err, client) => {
    if (err || !client) {
      socket.write("HTTP/1.1 401 Unauthorized\r\n\r\n");
      socket.destroy();
      return;
    }
    wss.handleUpgrade(request, socket, head, (ws) => {
      wss.emit("connection", ws, request, client);
    });
  });
});
```

### Что такое WebSocket Secure (WSS), and when should you use it?

**Definition:**

`wss` — это рукопожатие WebSocket поверх TLS. `ws` — то же кадрирование без TLS. В MDN сказано, что браузеры обычно требуют защищённое соединение, с возможным исключением для локальных устройств.

**How it works:**

- **URL**: Конструктор принимает схемы `wss` и `https`. Страница, загруженная по HTTPS, не откроет `ws://` на другой хост: браузер считает это смешанным содержимым.
- **Маска всё равно есть**: В MDN кадры клиента маскируются даже на защищённом сокете. TLS не заменяет бит MASK.
- **Сервер**: В примере `ws` для HTTPS в `https.createServer` передают `cert` и `key`, затем к этому серверу крепят `WebSocketServer`.

**When to use:**

- Используйте `wss` для любого соединения, которое уходит с машины.
- `ws://localhost` — обычное исключение на время разработки.

### Какие measures можно предпринять для secure WebSocket transmissions?

**Definition:**

Используйте `wss`, проверяйте `Origin`, аутентифицируйте upgrade и ограничивайте, сколько сокетов может держать один клиент. Маска кадра обязательна от клиента к серверу и не заменяет TLS.

**How it works:**

- **TLS**: Предпочитайте порт 443 и `wss`. MDN предупреждает, что другие порты чаще упираются в файрволы и что браузеры обычно хотят защищённое соединение.
- **Origin**: Браузеры шлют `Origin`. В MDN сказано, что несовпадение можно отклонить с `403`. Клиенты не из браузера могут подделать этот заголовок, поэтому ещё нужна сессия или токен.
- **Пределы**: Отказывайте клиентам, которые открывают слишком много соединений. Ограничьте размер сообщения и закрывайте с `1009`, когда сообщение слишком велико для обработки.
- **Нагрузка**: Считайте текст данными, а не HTML для вставки на страницу. Проверяйте UTF-8; некорректный текст — код закрытия `1007`.

### Как Cross-Site WebSocket Hijacking (CSWSH) be prevented?

**Definition:**

CSWSH — это страница с другого origin, которая открывает WebSocket к вашему серверу и едет на cookie пользователя. В MDN сказано, что проверка заголовка `Origin` и ответ `403` против этого эффективны для браузеров.

**How it works:**

- **Origin**: Браузеры шлют `Origin` в рукопожатии. Разрешайте только origin вашего сайта. Отсутствие `Origin` — повод отклонить клиент из браузера.
- **Подделка**: MDN предупреждает, что агент не из браузера может прислать поддельный `Origin`. Сочетайте проверку с политикой cookie `SameSite` и сессией, которой самой по себе мало для опасного действия.
- **Не доверяйте только первому кадру**: Вредоносная страница может слать кадры после upgrade, прошедшего по cookie. Отклоняйте upgrade при неверном `Origin`, чтобы эти кадры не начались.

### Можете ли вы use OAuth or tokens with WebSocket connections?

**Definition:**

Да, но конструктор браузера `WebSocket` не может задать `Authorization`. Токен должен приехать cookie на рукопожатии или значением, которое вы проверяете сами, прежде чем доверять сокету.

**How it works:**

- **Сессия в cookie**: Если поток OAuth уже поставил сессионную cookie `HttpOnly`, рукопожатие её отправит. Проверьте эту сессию в слушателе `upgrade`, как в примере `ws` с `401`.
- **Bearer-токен**: Клиент не из браузера может задать заголовок. Страница — нет. Обычные схемы для страницы: короткоживущий билет в query или токен в первом сообщении после `open`.
- **Срок**: Долго живущий сокет не повторяет рукопожатие OAuth. Когда токен истекает, закройте сокет и дайте клиенту переподключиться с новым.

### Как WebSockets be used in distributed systems?

**Definition:**

WebSocket остаётся на процессе, который принял TCP-соединение. Другие сервисы узнают о нём, только если этот процесс публикует нагрузку туда, откуда они могут читать.

**How it works:**

- **Край системы**: Браузеры подключаются к шлюзу, который говорит на RFC 6455. За ним сервисы остаются на HTTP или очереди. MDN уже описывает прокси перед выделенным сервером WebSocket.
- **Рассылка**: Шлюз публикует каждое входящее сообщение в шину. Каждый экземпляр шлюза читает сообщения для пользователей, чьи сокеты он держит.
- **Общего сокета нет**: Нельзя перенести открытое TCP-соединение на другой процесс, скопировав id. Переподключение создаёт новый сокет на том экземпляре, который его принял.

### Объясните the role of WebSockets in IoT (Internet of Things).

**Definition:**

<summary>Как WebSocket protocol handle backpressure or throttling?</summary>

### Как WebSocket protocol handle backpressure or throttling?

**Definition:**

Протокол опирается на TCP для противодавления транспорта. Браузер показывает результат как `bufferedAmount`: байты, которые принял `send()` и которые ещё не записаны в сеть.

**How it works:**

- **Нет окна приложения**: RFC 6455 не задаёт окно приёма WebSocket. Если сторона читает медленно, TCP сжимает окно отправителя, и `bufferedAmount` растёт.
- **Что его не сбрасывает**: MDN: значение падает до нуля, когда очередь отправлена. Закрытие его не обнуляет. Следующие вызовы `send()` всё равно его увеличивают.
- **Ограничение в приложении**: Перестаньте вызывать `send`, пока `bufferedAmount` выше выбранного предела, или закройте с `1009`, когда одно сообщение больше, чем вы готовы обработать.

- [MDN — bufferedAmount](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/bufferedAmount)

<summary>Как you handle reconnection and state sync after a WebSocket reconnects?</summary>

### Как you handle reconnection and state sync after a WebSocket reconnects?

**Definition:**

Упавший сокет не продолжается. Клиент открывает новый `WebSocket`, снова аутентифицируется и спрашивает то, что пропустил. `1006` значит, что старое соединение умерло без кадра Close.

**How it works:**

- **Обнаружение**: Слушайте `close`. Если `code` равен `1000`, сторона закончила нарочно. Иначе запланируйте новый вызов конструктора.
- **Пауза**: Ждите дольше после каждой неудачи, чтобы мёртвый сервер не получили все клиенты сразу. Socket.IO описывает это как экспоненциальную паузу, которую он делает сам; с сырым WebSocket таймер пишете вы.
- **Синхронизация**: Дайте каждому сообщению приложения id. На `open` пошлите последний id, который вы применили. Сервер отвечает пропуском или снимком, если пропуск слишком велик. Снимок может отдать HTTP.

**Examples:**

```js
socket.addEventListener("close", (event) => {
  if (event.code === 1000) return;
  setTimeout(connect, 1000);
});
```

```python
async def main():
    server = await serve(handler, "", 8001)
    await server.serve_forever()

asyncio.run(main())
```

### Что такое CORS (Cross-Origin Resource SHAring) and how does it relate to WebSockets?

### Как handle cross-origin WebSocket connections in Node.js?

**Definition:**

**How it works:**

- **Заголовок**: Node отдаёт сырой HTTP-запрос. `origin` — обычный заголовок этого запроса, тот самый, который MDN велит проверять.
- **Отказ**: Следуйте примеру аутентификации `ws`: напишите ошибку HTTP и `socket.destroy()` вместо вызова `handleUpgrade`.
- **Затем аутентификация**: Разрешённый origin — это не пользователь. На том же запросе всё равно проверьте сессию или токен.

**Examples:**

```js
    socket.write("HTTP/1.1 403 Forbidden\r\n\r\n");
    socket.destroy();
    return;
  }
  wss.handleUpgrade(request, socket, head, (ws) => {
    wss.emit("connection", ws, request);
  });
});
```

### WebSockets and Full-Duplex Communication

<details>
<summary>Что означает full-duplex communication mean in the context of WebSockets?</summary>

### Что означает full-duplex communication mean in the context of WebSockets?

**Definition:**

Полный дуплекс значит, что любая сторона может послать кадр в любой момент по тому же соединению, не дожидаясь запроса другой стороны. MDN описывает это как причину выйти из HTTP после рукопожатия.

**How it works:**

- **После 101**: Клиент не шлёт новый HTTP-запрос на каждое сообщение. У кадров сервера бит MASK снят. Кадры клиента маскированы.
- **Независимо**: Ping сервера (код `0x9`) можно записать, пока клиент ещё шлёт текстовое сообщение. Управляющие кадры могут стоять между фрагментами.
- **Всё ещё одна труба TCP**: Байты остаются упорядоченными. Полный дуплекс не значит, что медленная отправка перестаёт задерживать поздние байты на этом соединении.

**Sources:**

- [MDN — Writing WebSocket servers](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers)
- [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)
</details>

**Definition:**

**Definition:**

- **Предел**: Сертификат — не подпись каждого сообщения. После рукопожатия используйте привязанную личность и обычные кадры.

### Что такое the RFCs (Request for Comments) that define the WebSocket protocol?

**Definition:**

RFC 6455 — это протокол WebSocket: рукопожатие, кадры, маскирование и коды закрытия. Поздние RFC добавляют расширения и другие транспорты. GUID рукопожатия в RFC 6455 — `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`.

**How it works:**

- **RFC 6455**: MDN просит авторов серверов читать его, особенно разделы 1 и 4–7 и раздел 10 про безопасность. Версия 13 — это `Sec-WebSocket-Version`, которую шлют браузеры.
- **Сжатие**: Readme `ws` согласует расширение permessage-deflate из RFC 7692. Оно необязательное и отдельно от базовых кадров.
- **HTTP/2**: ASP.NET описывает WebSockets поверх HTTP/2 как RFC 8441. Эти рукопожатия используют `CONNECT`, а не исходный `GET` upgrade.

### Как compliance with WebSocket standards affect interoperability and future-proofing your application?

**Definition:**

Если вы реализуете рукопожатие, маскирование и коды закрытия из RFC 6455, браузерный `WebSocket` и другой совместимый сервер смогут говорить. Частная схема кадров — нет.

**How it works:**

- **Совместимость**: Autobahn, который проходит `ws`, ловит незаконный UTF-8, плохие длины и ошибки фрагментации, которые один браузер мог бы простить.
- **Расширения**: Согласуйте `permessage-deflate` заголовком. Не выдумывайте значения битов RSV, которых сторона не знает. Неизвестные коды `0x3`–`0x7` и `0xB`–`0xF` в этой версии ничего не значат.
- **Ваша версия**: Версии приложения кладите в имя подпротокола. `Sec-WebSocket-Version` оставьте 13, чтобы будущие браузеры всё ещё завершали рукопожатие.
