### OSI & TCP/IP models

**Definition:** **Модель сети** – это многоуровневая спецификация того, как хосты обмениваются цифровыми данными. **OSI** (Взаимосвязь открытых систем, ISO/IEC 7498-1/ITU-T X.200) — это семиуровневая _эталонная_ модель для обучения, обсуждения стандартов и устранения неполадок. В Интернете используется стек **TCP/IP** (DoD/набор интернет-протоколов), описанный в RFC 1122/RFC 1123 — четыре широких уровня, а не семь.

**How it works:**

Каждый уровень OSI взаимодействует с нижним уровнем и предлагает услуги вышестоящему уровню. При отправке данные **инкапсулируются** (добавляется верхний/нижний колонтитул); при получении заголовки удаляются. Уровни 1–3 — это **медиа** (биты → кадры → пакеты между каналами и маршрутизаторами); 4–7 — это **основные** слои.

| ОСИ | ПДУ | Работа | Типичные примеры |
| --- | --- | --- | --- |
|7 Приложение | данные | Протоколы приложений, которые видит пользователь/программа | HTTP, SMTP, FTP, DNS, SIP, [SSH](./15_devops.md#ssh) |
| 6 Презентация | данные | Синтаксис: кодирование, сжатие, шифрование (учебник) | TLS/MIME/ASN.1; JPEG/TIFF как _форматы_, а не проводной протокол |
| 5 сессия | данные | Настройка/контрольная точка/снос диалога | Сеансы в стиле RPC, туннели PPTP; сокеты в TCP/IP |
|4 Транспорт | сегмент (TCP)/дейтаграмма (UDP) | Сквозная доставка, порты, дополнительная надежность | TCP, UDP, QUIC |
| 3 Сеть | пакет | Адресация и **маршрутизация** между сетями | IP, ICMP, OSPF. IP **не** гарантирует порядок, доставку или уникальность |
| 2 Канал передачи данных | рамка | Доставка соседям по одной ссылке; МАК; обнаружение ошибок | Ethernet, Wi-Fi (IEEE 802.11), PPP. IEEE 802 разделяет **MAC** + **LLC** |
|1 Физический | бит/символ | Сигналы в среде | Медь, оптоволокно, радио; 802.15 Bluetooth PHY, DSL, GSM-радио |

интервью и операторы по-прежнему говорят о **балансировщике нагрузки L4** (IP+порт) и **L7** (пути/заголовки HTTP). Имена являются OSI, даже если стек TCP/IP. Он также отображает вопрос «где это сломалось?» (кабель, коммутатор, маршрутизация, TCP, TLS или HTTP).

| TCP/IP | Карты для OSI | Примеры |
| ------ | ----------- | -------- |
|Приложение | 5 + 6 + 7 | HTTP, DNS, TLS, WebSocket |
| Транспорт | 4 (плюс корректное закрытие TCP, которое OSI запускает сеанс) | TCP, UDP |
| Интернет | 3 | IP, маршрутизация |
| Ссылка/доступ к сети | 1 + 2 | Ethernet, Wi-Fi |

RFC 3439 («Многослойность считается вредной») объясняет, почему настоящие стеки негерметичны: TLS находится между HTTP и TCP; HTTP/3 использует **QUIC через UDP**. Не помещайте каждый протокол в один блок OSI.- **DoD/TCP/IP** — тот, кто победил; разработан для распределенной пакетной сети, которую трудно уничтожить (каждый пакет маршрутизируется независимо).

- **IPX/SPX** (Novell NetWare) — маршрутизация IPX + транспорт SPX; распространенный в локальных сетях DOS в 1990-х годах, слабый в глобальных глобальных сетях, почти исчез.
- **AppleTalk** — пакет другого поставщика; та же идея (уровни), разные протоколы.

- **Wireshark** — графический интерфейс: список пакетов, декодированное дерево, шестнадцатеричный/байтовый формат.**Фильтры захвата** (libpcap, во время анализа) и **фильтры отображения** (после захвата). Запуск/остановка захвата на интерфейсе.
- **tcpdump** — CLI; часто требуется root/admin. Остановитесь, нажав **SIGINT** (Ctrl+C). Запись/чтение pcap:

```bash
tcpdump -n 'tcp port 80 or udp port 80'
tcpdump -w out.pcap
tcpdump -r out.pcap
tcpdump -n 'port 8080'
```

**When to use:**

Интервью: «HTTP — это приложение, TCP-транспорт, IP-интернет». Отладка: Wireshark/tcpdump. Проект: L4 против L7 LB ([балансировка нагрузки](./0_system_design_data.md#load-balancing)).

#### Common pitfalls

Рассматривать OSI как реализацию браузеров. Называя GraphQL/gRPC «сеансовым уровнем», они являются **прикладными** протоколами (RPC – это лишь _учебный_ пример сеанса). Предполагая, что IP надежен. Приравниваем UDP к «отсутствию целостности» — UDP все еще имеет контрольную сумму; он просто не выполняет повторную передачу или изменение порядка.

**Pluses and minuses:**

| +                                         | −                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------- |
| Общий словарь (L2/L3/L4/L7)               | _Протоколы_ OSI никогда не заменяли TCP/IP                                            |
| Чистая ментальная модель для инкапсуляции | Строгое семиуровневое сопоставление TLS/QUIC/RPC принудительно                        |
| Отделяет «средство» от «приложения»       | Дополнительные уровни сеанса/представления часто являются просто приложением в TCP/IP |

**Examples:**

```
Browser GET https://example.com
  L7  HTTP request
  L4  TCP segments (ports; order + retransmission)  — or QUIC/UDP for HTTP/3
  L3  IP packets (src/dst addresses; routers pick a path per packet)
  L2  Ethernet/Wi-Fi frames (MAC; FCS/CRC on the frame)
  L1  bits on wire / radio
```

Полезная нагрузка Ethernet **MTU** обычно составляет **1500** байт, а не фиксированный «кадр в 1446 байт». TCP MSS в IPv4 Ethernet часто равен **1460** (1500–20 IP–20 TCP); PPPoE и другие заголовки еще больше сжимают его.

**Thoughts:** _OSI — семиуровневый словарь; TCP/IP — это четырехуровневый стек, на котором работает Интернет: HTTP через TCP (или QUIC) через IP через ссылку._

**Sources:**

[Doka — OSI](https://doka.guide/tools/osi/) · [ISO/IEC 7498-1](https://www.iso.org/standard/20269.html) · [RFC 1122](https://www.rfc-editor.org/rfc/rfc1122) · [MDN — Как Интернет работает](https://developer.mozilla.org/en-US/docs/Learn_web_development/Howto/Web_mechanics/How_does_the_Internet_work) · [tcpdump(1)](https://www.tcpdump.org/manpages/tcpdump.1.html) · [фильтры захвата Wireshark](https://www.wireshark.org/docs/wsug_html_chunked/ChCapCaptureFilterSection.html) · TCP/UDP: [TCP vs UDP](#tcp-vs-udp) · Стек HTTP: [HTTP и TCP/IP](./6_web_api_http.md#http--tcpip) · Сокеты: [Порты, сокеты и сеть службы](#ports-sockets--network-services)

### IPv4 & IPv6

**Definition:** IPv6 (Интернет-протокол версии 6) является 128-битным преемником IPv4: он маршрутизирует пакеты между хостами и нацелен на сквозное соединение (меньше «серых» NAT по сравнению с публичными адресами).

**How it works:**

- Адрес имеет размер **128 бит** и записывается как **восемь шестнадцатеричных цифр** (четыре шестнадцатеричные цифры). Пример: `2001:0db8:4ac7:fddd:8da3:981f:fbda:1e43`.
- Типичное разделение `/64`: первые 64 бита = **префикс сети** (провайдер/сайт); последние 64 бита = **идентификатор интерфейса** (устройство в этой подсети — представьте, что это UUID, а не гарантия стабильного MAC).
- **Сжатие (RFC 5952):** исключать ведущие нули в шестистетах; заменить **одну** самую длинную серию нулевых гекстетов на `::`. `2001:0db8:0000:0000:0000:0000:0000:0000` → `2001:db8::`. Вы можете оставить лишние нули для обучения (`2001:db8:0:0:0:0:0:0`); каноническая форма — сжатая + строчная.
- **Литералы URL-адреса (RFC 3986):** двоеточия конфликтуют с `host:port`, поэтому заверните адрес в `[]`. Такие инструменты, как `telnet host port` возьми голый адрес.
- **Префиксы** используют CIDR (`address/length`), а не точечные маски IPv4. `/64` это обычная подсеть LAN (SLAAC). Большие префиксы от интернет-провайдера представляют собой наборы `/64`с.
- **DNS:** `A` → IPv4, `AAAA` → IPv6. Двойной стек **Happy Eyeballs** (RFC 8305) запрашивает оба соединения и обеспечивает гоночные соединения (сначала IPv6, резервный IPv4), поэтому сломанный AAAA не останавливает работу сайта.
- **Конфиденциальность:** операционные системы используют **временные адреса конфиденциальности** (RFC 8981). Не рассматривайте полный 128-битный адрес клиента как постоянный идентификатор человека; коррелировать в **`/64` или шире**, если необходимо сгруппировать сеть.

| Префикс | Размер         | Типичное использование                                                      |
| ------- | -------------- | --------------------------------------------------------------------------- |
| `/64`   | 1 подсеть      | Домашняя/LAN-подсеть (грубый IPv4) `/24` аналог для «одной локальной сети») |
| `/60`   | 16 × `/64`     | Часто интернет-провайдер клиенту                                            |
| `/56`   | 256 × `/64`    | Часто интернет-провайдер клиенту                                            |
| `/48`   | 65 536 × `/64` | Сайт/организация                                                            |
| `/32`   | 65 536 × `/48` | Распределение ISP/LIR                                                       |

| Префикс                      | Цель                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| `::1/128`                    | Шлейф (`127.0.0.1`)                                                                  |
| `2001:db8::/32`, `3fff::/20` | Только документация (RFC 3849, RFC 9637) — не для производства                       |
| `fe80::/10`                  | Локальный канал (один канал; не глобальная маршрутизация)                            |
| `::ffff:0:0/96`              | IPv6, отображаемый на IPv4 (часто в базах данных/сокетах с двойным стеком)           |
| `2000::/3`                   | В настоящее время выделена **глобальная одноадресная рассылка** (публичный Интернет) |
| `fc00::/7`                   | Уникальный локальный (ULA, «частный»)                                                |

**When to use:**

Общедоступные сайты с двумя стеками (мобильные / в некоторых регионах много IPv6). WebRTC/VoIP: реальные публичные адреса уменьшают NAT/TURN. Локальная отладка без ngrok, когда у вас глобальный IPv6. Слушай дальше `[::]` плюс IPv4; опубликуйте **статическую** AAAA.

#### Common pitfalls

Публикация AAAA, который не отвечает (черная дыра) — пользователи с двойным стеком все равно могут работать через Happy Eyeballs; Клиенты **только IPv6** выходят из строя. С использованием `2001:db8::` or `3fff::` на реальных хостах. Лечение `fe80::` в качестве публичного выступления. Размещение IPv6 в URL-адресе без `[]`. Идентификация пользователей по полному адресу вместо `/64`. Если предположить, что «никто не использует IPv6» — доля мобильных устройств велика ([Google](https://www.google.com/intl/en/ipv6/statistics.html), [Cloudflare](https://www.cloudflare.com/ipv6/)).

**Pluses and minuses:**

| +                                                                         | −                                                                                       |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Огромное пространство; один адрес на хост — это нормально                 | URL-адреса и журналы выглядят зашумленными; `:` против порта                            |
| Меньше CGNAT: P2P, WebRTC, входящий трафик на устройство                  | Сломанный AAAA без счастливых глаз = тайм-ауты                                          |
| Уникальный хост против общего хостинга IPv4/блоков CGNAT                  | Конфиденциальность: не регистрируйте 128-битный ключ как надежный пользовательский ключ |
| Сети только с протоколом IPv6 (некоторые мобильные/развивающиеся регионы) | Нужен глобальный одноадресный адрес + работающий DNS                                    |

**Examples:**

```
# URL (brackets required)
https://[2001:db8:4ac7:fddd:8da3:981f:fbda:1e43]:8080/

# CLI (no brackets)
telnet 2001:db8:4ac7:fddd:8da3:981f:fbda:1e43 8080

# Short forms
::1          # loopback
2001:db8::   # documentation prefix, compressed
```

Отправьте IPv6 на сайт: (1) адрес сервера в **`2000::/3`**, (2) веб-сервер прослушивает IPv6, (3) стабильный (статический) адрес, (4) **AAAA** в DNS. Нгинкс: `listen [::]:443 ssl;` плюс IPv4 `listen`.

**Thoughts:** IPv6 — это 128-битная сквозная адресация; для веба вам нужен прослушивание + статический GUA + `AAAA`, и клиенты уже предпочитают его через Happy Eyeballs.

**Sources:**

[Doka — IPv6 для веб-разработчиков](https://doka.guide/tools/ipv6-for-webdevs/) · [MDN — IPv6](https://developer.mozilla.org/en-US/docs/Glossary/IPv6) · [IPv6 специального назначения IANA](https://www.iana.org/assignments/iana-ipv6-special-registry) · [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html) · [RFC 5952](https://www.rfc-editor.org/rfc/rfc5952.html) · [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html) · [RFC 9637](чhttps://www.rfc-editor.org/rfc/rfc9637.html)

### SSL/TLS

**Definition:**

TLS (преемник SSL) шифрует сетевой трафик и аутентифицирует одноранговые узлы с помощью сертификатов и согласованных наборов шифров.

**Examples:**

```
Browser → supports TLS 1.3
Server  → presents cert signed by Let's Encrypt
Both    → agree cipher suite, exchange keys
```

### TCP vs UDP

**Definition:** TCP и UDP — это протоколы **транспортного уровня** (уровень 4 OSI / транспорт TCP/IP). Они перемещают байты приложения между клиентом (браузером) и сервером в виде пакетов; они различаются надежностью, порядком и настройкой подключения.

**How it works:**

- Данные в сети представляют собой пакеты ограниченного размера. **TCP** создает **поток байтов** после соединения; **UDP** отправляет независимые **дейтаграммы** без сеанса.
- **TCP (Протокол управления передачей)** — ориентирован на соединение. Повторно передает потерянные сегменты, удаляет дубликаты, доставляет по порядку, подтверждает отправителю и запускает **контроль перегрузки** (начинайте с малого, увеличивайте по мере доступной пропускной способности).- **UDP (Протокол пользовательских дейтаграмм)** — без установления соединения. Никакого рукопожатия, никаких гарантий доставки/заказа/дубликата. Заголовок имеет длину **8 байт** (порт источника, порт назначения, длина, контрольная сумма). Контрольная сумма необязательна в IPv4 и обязательна в IPv6. Приложения, которым необходима надежность, реализуют ее самостоятельно (или используют TCP/QUIC).

SYN означает **синхронизировать**. Каждая сторона выбирает случайный **начальный порядковый номер** (ISN).

1. Клиент → `SYN` с продолжением `x`.
2. Сервер → `SYN-ACK` с продолжением `y`, ок `x + 1`.
3. Клиент → `ACK` с подтверждением `y + 1` (его продолжение `x + 1`). Соединение **УСТАНОВЛЕНО**.

Клиент может отправлять данные с окончательным подтверждением или после него; сервер ждет подтверждения, прежде чем рассматривать соединение как открытое. Закрытие — это **четырёхсторонний** обмен FIN/ACK (каждая сторона закрывается независимо). Рукопожатие происходит **после DNS** и **перед TLS** на HTTPS.

Много источников на странице = много рукопожатий = дополнительные RTT. Меры по снижению риска: повторное использование соединений (поддержание активности HTTP, мультиплексирование HTTP/2), `<link rel="preconnect">` (DNS + TCP + TLS; нет `dns-prefetch`, то есть только DNS), меньше хостов.

- **TFO (RFC 7413)** — после предыдущего посещения файл cookie быстрого открытия** позволяет клиенту помещать **данные приложения в SYN**. Данные сервера в SYN-ACK не являются обязательными. Полезная нагрузка SYN ограничена примерно **одним MSS\*\* (а не 10 сегментами). Требуется поддержка ОС + стека на обоих концах; промежуточные ящики иногда ломают его. Сегодня HTTP/3/QUIC — это обычный путь 0-RTT в Интернете.
- **Первоначальное окно перегрузки (`initcwnd`, RFC 6928)** — после рукопожатия отправитель может взорваться до `min(10 * MSS, max(2 * MSS, 14600))` байт в первом RTT (~10 × 1460 в Ethernet). Это **не** предел TFO SYN.

Критический путь рендеринга — это **общий** конвейер браузера (анализ HTML/CSS, сначала рисование перед всеми ресурсами), а не функция только Chromium.

DNS (часто), игры, живое аудио/видео, **WebRTC**, **QUIC/HTTP/3**. Отбрасывание позднего кадра лучше, чем остановка для повторной передачи.NAT (один общедоступный IP-адрес, множество частных хостов) плюс брандмауэры затрудняют входящий UDP: **STUN** изучает общедоступный IP-адрес:порт; **TURN** ретранслирует, когда симметричный NAT блокирует одноранговые узлы; **ICE** пытается STUN, а затем TURN ([Протоколы MDN WebRTC](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols)). Датаграммы UDP можно отбрасывать, дублировать или переупорядочивать в сетях; приложения должны справиться с этим.Общие буферы/привязки NAT могут плохо взаимодействовать с TCP на одном и том же пути — проверьте настоящий NAT, не предполагайте, что это LAN.

**When to use:**

TCP — HTML/CSS/JS, файлы, HTTP/1.1 и HTTP/2, электронная почта, все, что должно быть полным и в порядке. UDP — DNS, потоковая передача, WebRTC, HTTP/3 (QUIC повышает надежность **по UDP**).


| TCP                               | UDP                           |
|  -------------------  |  ---------------------------------  |
| Подключение         | Рукопожатие, затем трансляция     | Нет                           |
| Доставка            | Надежно, упорядоченно, без обмана | Лучшее из возможного          |
| Контроль перегрузок | Да                                | Нет (приложение или QUIC)     |
| Накладные расходы   | Высшее (состояние, ACK)           | Низкий (8-байтовый заголовок) |
| Интернет | HTTP/1.1, HTTP/2, TLS через TCP | DNS, WebRTC, HTTP/3/QUIC |

#### Common pitfalls

- С использованием `dns-prefetch` когда ты имел в виду `preconnect`.
- Вызов TFO «10×1460 байт» — т.е. `initcwnd`, а не данные SYN.
- Если UDP «не имеет контрольной суммы» — включите его; требуется для IPv6.
- Рассматривать HTTP/3 как «ненадежный HTTP» — QUIC восстанавливает надежность UDP.

**Pluses and minuses:**

| + (TCP)             | − (TCP)                                                                      |
| ------------------- | ---------------------------------------------------------------------------- |
| Честность и порядок | Рукопожатие + подтверждения добавляют RTT                                    |
| Контроль перегрузок | Блокировка начала строки для каждого соединения (HTTP/2 по-прежнему TCP HOL) |

| + (UDP)                                               | − (УДП)                               |
| ----------------------------------------------------- | ------------------------------------- |
| Низкая задержка, небольшой заголовок                  | Потеря, повторный заказ, дубликаты    |
| Подходит для работы в режиме реального времени / QUIC | Проблемы с NAT/брандмауэром; нет cwnd |

**Examples:**


```

HTTP/3             → QUIC over UDP (crypto + 0-RTT in the transport)
WebRTC media       → UDP + ICE/STUN/TURN
```

**Thoughts:**

_TCP обменивает RTT и ACK на надежный упорядоченный поток; UDP — это тонкая датаграмма. Используйте ее, когда задержка превосходит полноту или когда QUIC обеспечивает надежность на высоте._

### Ports, sockets & network services

**Definition:** **Порт** — это 16-битное число (1–65535) на хосте, который мультиплексирует соединения, чтобы ядро ​​могло передавать пакеты нужному процессу. **Сокет** — это конечная точка ОС (`IP + port + protocol`). **Сетевой стек** (ядро) создает сокеты; **сетевая служба** — это приложение (nginx, `sshd`, Node), привязанный к одному.

**How it works:**

- HTTPS браузера по умолчанию — порт **443** (`https://example.com` ≡ `https://example.com:443`). HTTP — **80**. IANA назначает общеизвестные порты; локальные приложения часто используют **8080**/**8000**.
- Другие протоколы приложения: почта **IMAP/POP3/SMTP**; чат исторически XMPP. Протокол приложения определяет только **формат сообщения**; TCP/UDP по-прежнему переносят байты.
- Соединение из четырех кортежей (IP-адрес источника, порт источника, IP-адрес dst, порт порта) плюс протокол идентифицирует соединение. **Статические маршруты** настроены;**динамические** маршруты берутся из протоколов маршрутизации. Хосты обычно имеют шлюз по умолчанию, а не полную карту Интернета.
- **Осмотр:** `ping` (эхо ICMP — доступность, а не «HTTP включен»). Адреса: `ip addr` (Линукс) / `ifconfig` (BSD/macOS) / `ipconfig /all` (Окна). Связи: предпочитаю **`ss`** в Linux (`net-tools` `netstat` является наследием). Байты пакета: [tcpdump / Wireshark](#osi--tcpip-models). Фильтр: [брандмауэр](./15_devops.md#firewall--packet-filter).

**When to use:**

«Почему мой Node на 3000 не открывается в браузере?» (неправильная привязка/брандмауэр). «Кто слушает 443?» Проверка безопасности прослушивающих сокетов.

#### Common pitfalls

`netstat -L` / `-p tcp` со страницы руководства macOS в Linux. `https://host:443` против пропуска порта. Лечение `ping` успех, поскольку «сайт работает».

**Pluses and minuses:**

| +                                                             | −                                                               |
| ------------------------------------------------------------- | --------------------------------------------------------------- |
| Один порт → одна служба прослушивания                         | Эфемерный беспорядок в клиентских портах `ss` вывод             |
| Значения по умолчанию IANA скрыть `:80` / `:443` в URL-адресе | Названия флагов различаются (`netstat -p` PID против протокола) |

**Examples:**

```bash
ping 8.8.8.8                 # ICMP; Google DNS — not HTTP
ip addr                      # Linux addresses (prefer over ifconfig)
ifconfig                     # macOS / older Unix
ipconfig /all                # Windows

ss -tulpn                    # Linux: TCP/UDP, listening, numeric, processes
ss -s                        # protocol stats
netstat -an                  # numeric sockets (most OS)
netstat -p tcp               # macOS/BSD: filter TCP — NOT Linux (-p = PID/program)
```

**Thoughts:** _IP находит хост; порт находит процесс; `ss`/`netstat` показать сокеты, которые в данный момент есть в стеке._

[Реестр портов IANA](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml) · [ss(8)](https://man7.org/linux/man-pages/man8/ss.8.html) · [ip(8)](https://man7.org/linux/man-pages/man8/ip.8.html) · [Doka — Работа с сетью](https://doka.guide/tools/network/) · [Как работает Интернет](./6_web_api_core.md#internet)

### GraphQL

**Definition:**

GraphQL — это язык запросов и среда выполнения, в которой клиенты запрашивают именно те поля, которые им нужны, из типизированной схемы.

| ОТДЫХ                      | ГрафQL                             |
| -------------------------- | ---------------------------------- |
| Несколько конечных точек   | Одинокий `/graphql` конечная точка |
| Фиксированная форма ответа | Клиент выбирает поля               |
| Чрезмерная выборка общего  | Точная выборка данных              |

**How it works:** Клиент отправляет документ запроса по схеме (`type Query { book(id: ID!): Book }`). Сервер разрешает каждое поле. Мутации меняют данные; подписки отправляют обновления (часто через WebSocket). Используйте постоянные запросы и ограничения сложности в рабочей среде.

**When to use:** Многим клиентам нужны разные формы одного и того же графика (мобильные и веб-версии). Неофициальный **средний вариант**: обрезать избыточную выборку REST без клонирования конечных точек — та же идея, что и [BFF](./7_special_architecture.md#bff-backend-for-frontend). Избегайте недружественной к кешу замены простого CRUD REST API.

**Pluses and minuses:**

| +                                                        | −                                              |
|  --------------------------------------------------------  |  ----------------------------------------------  |
| Клиент выбирает поля; один обход для вложенных данных    | Кэширование и семантика HTTP сложнее, чем REST |
| Сильная схема/кодогенератор (похож на orval для GraphQL) | Резолверы N+1 без DataLoader |
| Самоанализ и игровая площадка DX | Аутентификация на уровне поля — дополнительная работа |

**Examples:**

```graphql
query GetBook($id: ID!) {
  book(id: $id) {
    title
    author {
      name
    }
  }
}
```

**Sources:**

[GraphQL — Введение](https://graphql.org/learn/)

### WebSocket

**Definition:**

WebSocket обновляет HTTP-соединение до постоянного полнодуплексного канала для двунаправленного обмена сообщениями в реальном времени.

| HTTP-опрос             | Вебсокет                          |
| ---------------------- | --------------------------------- |
| Повторные запросы      | Одиночное долгоживущее соединение |
| Более высокая задержка | Нажатие с низкой задержкой        |
| Простой                | Требуется управление подключением |

**How it works:** Браузер отправляет `Upgrade: websocket` (+ `Sec-WebSocket-*`). Сервер отвечает `101 Switching Protocols`. После этого кадры идут в обе стороны (текстовые или двоичные). Предпочитать `wss://` (TLS; прокси менее склонны разрывать туннель). Heartbeats обнаруживает мертвых одноранговых узлов. Масштабируйте с помощью закрепленных сеансов или шины публикации/подписки (Redis) за несколькими процессами Node.

- События: `open`, `message`, `error`, `close`. Отправлять: `socket.send(data)` (строка/Blob/ArrayBuffer).
- `binaryType`: `'blob'` (по умолчанию) или `'arraybuffer'`.
- Противодавление: проверьте `socket.bufferedAmount` перед затоплением `send`.
- Закрывать: `socket.close(code, reason)` — `1000` нормальный; `1006` означает нечистый (нет тесной рамки). `readyState`: 0 ПОДКЛЮЧЕНИЕ → 1 ОТКРЫТО → 2 ЗАКРЫТИЕ → 3 ЗАКРЫТО.
- Нет встроенного переподключения/аутентификации — библиотеки или повторная попытка вручную.

**When to use:** Чат, живые информационные панели, совместные курсоры. Предпочитайте SSE, когда серверу нужно только **push** (уведомления). Предпочитайте HTTP для запроса/ответа CRUD.

**Pluses and minuses:**

| +                                        | −                                                                                        |
|  ----------------------------------------  |  ----------------------------------------------------------------------------------------  |
| Двунаправленная связь с низкой задержкой | Прокси, балансировщики нагрузки и бессерверные таймауты борются с долгоживущими сокетами |
| Меньше накладных расходов, чем при опросе | Должен обрабатывать переподключение, противодавление, аутентификацию на сокете |

**Examples:**

```js
const ws = new WebSocket("wss://chat.example.com");
ws.binaryType = "arraybuffer";
ws.onopen = () => ws.send(JSON.stringify({ type: "join", room: "general" }));
ws.onmessage = (e) => console.log(e.data);
ws.onclose = (e) => console.log(e.code, e.wasClean);
```

**Thoughts:** Обновите HTTP один раз, а затем говорите о кадрах — это не замена REST CRUD.

### Polling, long polling, SSE & WebSocket

**Definition:**

Эти шаблоны доставляют обновления сервера клиентам с различными компромиссами между простотой, задержкой и направленностью.

| Техника        | Направление     | Подключение                             |
|  --------------  |  ---------------  |  ---------------------------------------  |
| Короткий опрос | Клиент тянет    | Повторный HTTP                          |
| Длинный опрос  | Клиент тянет    | Удерживает HTTP до тех пор, пока данные |
| SSE (Источник событий) | Сервер → клиент | Постоянный HTTP |
| Вебсокет       | Двунаправленный | Модернизированный TCP                   |


| Вебсокет           | Источник событий (SSE) |
|  -----------------------  |  ------------------  |
| Направление             | В обе стороны      | Сервер → только клиент |
| Данные                  | Двоичный + текст   | Только текст           |
| Протокол                | `ws://` / `wss://` | HTTP                   |
| Восстановить соединение | Руководство        | Встроенный             |

**How it works:**

- **Короткий опрос:** клиент задает вопросы через определенные промежутки времени — простой, с задержкой, шумный в режиме ожидания.
- **Длительный опрос:** сервер удерживает запрос до тех пор, пока не придет сообщение (или не истечет время ожидания).`502`); клиент немедленно переподключается. Сервер должен обрабатывать множество ожидающих соединений.
- **ССЕ:** `Content-Type: text/event-stream`. Поля: `data:`, необязательный `id:` (→ `Last-Event-ID` при повторном подключении), `retry:` (ms), `event:` (произвольное имя → `addEventListener`). Автоматическое повторное подключение, если `close()` или фатальный статус. Для перекрестного происхождения требуется CORS; учетные данные через `{ withCredentials: true }`.
- **WebSocket:** см. [WebSocket](#websocket) выше.

**When to use:** Редкие пуши → длинный опрос или SSE. Высокочастотная двунаправленная связь → WebSocket. CRUD по-прежнему HTTP.

**Examples:**

```js
// Server-Sent Events
const es = new EventSource("/api/events");
es.onmessage = (e) => console.log(e.data);
es.addEventListener("bye", (e) => console.log(e.data));
// es.close();
```

```js
// Long polling sketch
async function subscribe() {
  const res = await fetch("/subscribe");
  if (res.status === 502) return subscribe(); // timeout — reconnect
  if (!res.ok) {
    await new Promise((r) => setTimeout(r, 1000));
    return subscribe();
  }
  console.log(await res.text());
  return subscribe();
}
```

### MPA — dynamic HTML

**Definition:** При каждом запросе сервер запускает скрипт (PHP, Python, Ruby,…), читает БД, заполняет шаблон и возвращает HTML.

**How it works:** Пользователь открывает «друзей»: (1) запрос попадает на сервер (2) запрашивает БД (3) собирает HTML из частей (4) отправляет HTML. Следующий визит к новым друзьям → другой HTML. Статические фрагменты по-прежнему можно кэшировать. Клиентский JS остается небольшим.

**When to use:** Классические форумы и магазины. Крупные продукты исторически использовали это (страницы, генерируемые сервером) до оболочек SPA.

**Pluses and minuses:**

| +                                          | −                                                               |
| ------------------------------------------ | --------------------------------------------------------------- |
| Логика остается на сервере; меньший клиент | Полная перезагрузка — никакого мгновенного UX «приложения»      |
| Свежие данные из БД                        | Позиция прокрутки потеряна; некэшированные страницы ждут в сети |

**Thoughts:** HTML собирается **по запросу** на сервере, а не в виде готового файла.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/)

---

</details>

<details>
  <summary>SPA (Single Page Application)</summary>

### SPA (Single Page Application)

**Definition:** Один HTML-документ. JavaScript создает контент, переключает экраны и загружает данные (обычно через API). Навигация не перезагружает всю страницу.

**How it works:** Мгновенная смена экрана; может показывать загрузчики, пока `fetch` бежит. Богатая экосистема (библиотеки пользовательского интерфейса, шаблоны). Разделить по **где создается первая отрисовка**: браузер (**CSR**) или сервер (**SSR**). Часто нужны фреймворки.

**When to use:** Сложная клиентская логика, UX, подобный приложению. Кэшированный SPA JS все равно может менять экраны в плохой сети; MPA ожидает следующего HTML.

**Pluses and minuses:**

| +                                     | −                                                                                                              |
|  -------------------------------------  |  --------------------------------------------------------------------------------------------------------------  |
| Мгновенные переходы внутри приложения | Harder: инструменты, пакеты, производительность |
| Визуальная обратная связь при загрузке данных | Требуется JS — отключен JS = пусто |

| Краулеры предпочитают статический HTML (сейчас они _могут_ запускать JS, но статический по-прежнему побеждает) |

**Thoughts:** Страница останется; JS рисует следующий экран.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/) · [MDN — SPA](https://developer.mozilla.org/en-US/docs/Glossary/SPA)

---

</details>

<details>
  <summary>CSR (Client-Side Rendering)</summary>

### CSR (Client-Side Rendering)

**Definition:** **Браузер** создает каждое представление, включая первое. Пользователь ждет JS; до тех пор страница пуста или статический загрузчик.

**How it works:** Загрузите JS → выполните → визуализируйте. Простейшее СПА. Хорошо, когда комплект небольшой. Слабые устройства/медленные сети могут отскакивать. Поисковые системы сегодня используют JS, но статический HTML по-прежнему индексируется более надежно.

**When to use:** Небольшие SPA, панели авторизации с низкой потребностью в SEO.

**Pluses and minuses:**

| +                                        | −                                                   |
| ---------------------------------------- | --------------------------------------------------- |
| Простая настройка СПА                    | Первая краска заблокирована на JS                   |
| Быстрый старт, если приложение маленькое | Нет JS → ничего                                     |

| Большие приложения: медленный TTI, более слабое SEO |

**Thoughts:** Первый HTML — это оболочка; Пользовательский интерфейс появляется после JS.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/) · [рендеринг Next.js](./4_nextjs_rendering.md#1-rendering-strategies)

---

</details>

<details>
  <summary>SSR (Server-Side Rendering)</summary>

### SSR (Server-Side Rendering)

**Definition:** **Сервер** отправляет уже обработанный HTML для первого просмотра, чтобы пользователь мог читать, пока SPA JS загружается и гидратируется.

**How it works:** Узел (типичный) использует тот же пользовательский интерфейс на сервере. Next.js (React) / Nuxt (Vue) — обычные стартеры — см. [4_react_server.md §8](./4_react_server.md#8-server-rendering--rsc), [4_vue_ssr.md §8](./4_vue_ssr.md#8-ssr--hydration), [4_nextjs_rendering.md §1](./4_nextjs_rendering.md#1-rendering-strategies), [4_nuxt_core.md §4](./4_nuxt_core.md#4-rendering-strategies). Пользовательский SSR — это сложно (загрузка данных, правильный рендеринг, инфра). Дополнительный сервер = дополнительные операции.

**When to use:** SEO + первая краска, которая не должна ждать в связке. Персонализированные страницы (сессия) — см. Next.js. `cookies()` / `force-dynamic`.

**Pluses and minuses:**

| +                                            | −                         |
| -------------------------------------------- | ------------------------- |
| HTML немедленно; лучший UX и поиск           | Сервер + инфраструктура   |
| То же приложение может превращать воду в СПА | DIY SSR подвержен ошибкам |

**Examples:**

```ts
export const dynamic = "force-dynamic";
```

**Thoughts:** Первые байты — это реальный контент, а не пустая оболочка.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/) · [Next.js — рендеринг](https://nextjs.org/docs/app/getting-started/caching)

---

</details>

<details>
  <summary>SSG (Static Site Generation)</summary>

### SSG (Static Site Generation)

**Definition:** На этапе сборки данные и шаблоны превращаются в **статические HTML-файлы** (MPA на диске). Инструменты SSG часто оборачивают структуру SPA, поэтому вы получаете статические файлы _и_ интерактивность клиента.

**How it works:** Сообщения в блоге → HTML-страницы при сборке. Сама Doka — это SSG. **Jamstack** = JavaScript + API + разметка (Doka: Markdown как типичный источник контента). Реагировать/и т.д. «разбудить» страницу; API извлекают дополнительные данные.

**When to use:** Блоги, документы, маркетинг. Следующий.js: `generateStaticParams` предварительно отображает динамические маршруты при сборке.

**Pluses and minuses:**

| +                     | −                                         |
| --------------------- | ----------------------------------------- |
| Статический + SPA UX  | Заморожено до следующей сборки (или ISR)  |
| Кэш CDN, отличное SEO | Не для индивидуальных панелей мониторинга |

**Examples:**

```ts
export async function generateStaticParams() {
  const posts = await fetch("https://example.com/posts").then((r) => r.json());
  return posts.map((post: { slug: string }) => ({ slug: post.slug }));
}
```

**Thoughts:** HTML существует **до** запроса (время сборки), в отличие от классического PHP-запроса MPA.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/) · [Next.js —generateStaticParams](https://nextjs.org/docs/app/api-reference/functions/generate-static-params)

<details>
  <summary>PWA (Progressive Web App)</summary>

### PWA (Progressive Web App)

**Definition (three angles):**

| Вид             | Значение                                                                                                                                                                                                           |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Каждый день** | Сайт, который можно закрепить в виде значка;запускается в **автономном режиме** (без браузера Chrome), может работать в автономном режиме, получать push-уведомления и т. д. — выглядит как нативное приложение.   |
| **Официально**  | Веб-приложение, использующее **прогрессивное улучшение**: распознает функции веб-API и, если они есть, использует их для создания пользовательского интерфейса собственного класса. Вот почему они _прогрессивны_. |
| **Технический** | Сайт, соответствующий **критериям установки для конкретного браузера** (они меняются).Ни одного глобального контрольного списка спецификаций.                                                                      |

**How it works — Chromium install (Chrome/Edge/…):** HTTPS или `localhost` + **манифест веб-приложения**. Chromium **раньше** также требовал Service Worker; это больше **не** требуется для приглашения на установку. Программное обеспечение по-прежнему позволяет вам отключаться от сети, отправлять сообщения, фоновую синхронизацию и перехватывать сообщения. `fetch`. Safari/Firefox обычно **не** отображают пользовательский интерфейс Chromium «Установить приложение». Apple называет их **Веб-приложениями для домашнего экрана**, а не «PWA».

Хром `beforeinstallprompt` ([web.dev](https://web.dev/articles/install-criteria)): еще не установлен; HTTPS; вовлечение пользователя (~30 секунд + нажатие); проявляться с `name` or `short_name`, `start_url`, `icons` (192 + 512), `display` in `fullscreen` / `standalone` / `minimal-ui` / `window-controls-overlay`; `prefer_related_applications` отсутствует или `false`.

**History (short):** Термин придуман в **2015** Алексом Расселом и Фрэнсис Берриман (_Прогрессивные веб-приложения: экранирование вкладок без потери души_). Идея старше: Palm webOS, Firefox OS, ChromeOS; Джобс (2007) описал приложения, доставляемые через Интернет, до появления App Store. Логотип сообщества PWA: Диего Гонсалес (конкурс 2017 г.).

**When to use:** Нанесите слой на любой MPA/SPA. Постепенно: сначала добавьте манифест, затем ПО для автономного режима. Необязательно: обернуть тонкой родной оболочкой для Play/App Store.

**Notes (Doka):** Установка и работа в автономном режиме **не** обязательны для «считания PWA». Сайт только с вкладками и сенсорами push/сенсоров по-прежнему прогрессивен. Приложениям для видеозвонков нужна сеть. PWA — это совокупность практик + дополнительные правила установки, а не строгий тип продукта.

| Плюсы | Минусы |
|---------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Одна кодовая база; любой форм-фактор с браузером | Та же «децентрализованная» сеть: **нет большого магазина PWA** для оценок/скриншотов |
|Нативное: значок на главном экране, обработчики ОС, автономный режим, push-уведомления, датчики (при наличии API) | **Неравномерная поддержка веб-API** в разных браузерах, версиях и ОС |
| Кэш = офлайн + более быстрые повторы; Фоновая синхронизация при подключении к сети | iOS: все браузеры используют **WebKit**; API-интерфейсы работают с задержкой или отсутствуют до обновления ОС |
| Посетите URL-адрес — магазина нет;кэш может обновляться в фоновом режиме | «Настоящая кроссплатформенность» ограничена самым слабым браузером |
| Меньше, чем нативный: вызывайте API **браузера**, загружайте только то, что вам нужно |
|URL-адреса с возможностью поиска, обмен ссылками, копирование/перевод/масштабирование/печать/расширение | |
| Песочница браузера + HTTPS; **запросы разрешений** (push, NFC, …) | |
| HTML/CSS/JS — нет собственного SDK;отладка в DevTools | |
| Интернет остается обратно совместимым | |

**Examples:**

```html
<link rel="manifest" href="/manifest.json" />
```

```json
{
  "name": "My App",
  "short_name": "App",
  "start_url": "/",
  "display": "standalone",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

```js
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js");
}
```

**Common pitfalls:** Обработка ПО, как требуется для _установки_ (устарело). Ожидается баннер установки Chrome в Safari. Кэширование навсегда без этапа активации версионного ПО.

**Thoughts:** PWA = веб-сайт + дополнительные встроенные возможности. Установить ≠ офлайн.

**Sources:** [Doka — PWA](https://doka.guide/tools/pwa/) · [web.dev — критерии установки](https://web.dev/articles/install-criteria) · [MDN — Progressive Web Apps](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps)

<details>
  <summary>Compare: MPA, SPA, CSR, SSR, SSG, PWA</summary>

### Compare: MPA, SPA, CSR, SSR, SSG, PWA

**Definition:**

Выберите **перезагрузку или маршрутизацию JS** (MPA/SPA) и **при построении HTML** (CSR/SSR/SSG). PWA — это усовершенствование, а не пятая архитектура.


| Первый просмотр | Навигация | SEO | Оффлайн |
| --------------- | -------------------- | ---------------------- | --------- |
|**MPA статический** | Файлы на диске | Полная перезагрузка | Отлично | CDN/ПО |
| **Динамический MPA** | Шаблон сервера + БД | Полная перезагрузка | Хорошо | сложнее |
| **СПА + КСО** | После JS | Мгновенный | Слабее | Ограниченная |
| **СПА + ССР** | HTML, затем гидратировать | Мгновенно после загрузки | Сильный | Ограниченная |
|**ССГ** | HTML во время сборки | Перезагрузка или увлажненное СПА | Отлично | Статический кеш |
| **ПВА** | Зависит от базы | Зависит от базы | Варьируется | Сервисный работник |

**When to use:** Плохая сеть: SPA все еще может менять экраны из кэшированного JS; MPA ожидает следующего HTML. SPA все равно может работать медленно, если пакет огромен.

**Thoughts:** MPA vs SPA — это навигация. CSR/SSR/SSG — это _когда_ HTML существует.

**Sources:**

[Doka — Типы веб-приложений](https://doka.guide/tools/web-app-types/)

</details>
