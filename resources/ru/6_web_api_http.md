## 7. HTTP

<details>
  <summary>HTTP protocol</summary>

### HTTP protocol

**Definition:** HTTP — это протокол запросов/ответов прикладного уровня: **клиент** (пользовательский агент, обычно браузер) отправляет сообщения; отвечает **сервер**. Он содержит API-интерфейсы HTML, CSS, JS, JSON, изображения, мультимедиа, данные форм и многое другое.

**How it works:**

- Три роли HTTP-уровня: **клиент** (отправляет запросы, обрабатывает ответы), **исходный сервер** (обрабатывает их), **прокси** (реле, которое может кэшировать, фильтровать, распределять нагрузку, проверять подлинность или вести журнал). Маршрутизаторы и TCP располагаются ниже HTTP.
- Клиент **всегда инициирует**. Сервер не отправляет классические HTTP-ответы до тех пор, пока не поступит запрос (SSE/WebSocket — это дополнительные механизмы).- Порядок действий: открыть или повторно использовать соединение **TCP** (HTTP/3 использует **QUIC/UDP**) → отправить запрос → прочитать ответ → сохранить или закрыть соединение. постоянные соединения HTTP/1.1; HTTP/2 мультиплексирует потоки по одному соединению.
- **Без сохранения состояния, а не без сеанса:** каждый запрос независим. Файлы cookie (и другие токены) воссоздают **сессию**, поэтому состояние входа/корзины может охватывать запросы.
- Сообщения HTTP/1.x являются текстовыми.HTTP/2/3 сохраняет ту же **семантику** (методы, статус, заголовки) внутри двоичных кадров. Текущие спецификации: [RFC 9110](https://httpwg.org/specs/rfc9110.html) (семантика), RFC 9112 (HTTP/1.1), RFC 9113 (HTTP/2), RFC 9114 (HTTP/3) — а не устаревший RFC 2616.

начальная строка → заголовки → пустая строка → необязательное **тело**. Тело сигнализирует о `Content-Length` or `Transfer-Encoding` (e.g. `chunked`). Ответы HEAD не имеют тела; многие запросы GET не имеют ни одного.

| Стартовая линия | Формат | Пример |
| ---------- | ------ | ------- |
| Строка запроса | `METHOD target HTTP/version` | `GET / HTTP/1.1` |
| Статус-строка | `HTTP/version code reason` | `HTTP/1.1 200 OK` |

| Метод | Намерение |
| ------ | ------ |
| `GET` | Получить представление (безопасно; не должно иметь тела запроса) |
| `HEAD` | То же, что и GET, **нет тела ответа** |
| `POST` | Отправить данные / запустить обработку |
| `PUT` | Заменить ресурс по URI |
| `PATCH` | Частичное обновление |
| `DELETE` | Удалить ресурс |
| `OPTIONS` | Варианты связи с целью (`*` = весь сервер); CORS предполетная подготовка |
| `TRACE` | Закольцовка запроса по пути (часто отключена) |
| `CONNECT` | Открыть TCP-туннель (HTTPS через прокси) |

| Класс | Значение | Общие коды |
| ----- | ------- | ------------ |
| 1хх | Информационно, запрос продолжается | `100 Continue`, `103 Early Hints` |
| 2хх | Успех | `200 OK` |
| 3хх | Перенаправление/повторная проверка кэша | `301 Moved Permanently`, `307 Temporary Redirect` (метод сохранен), `304 Not Modified` |
| 4хх | Ошибка клиента | `400 Bad Request`, `403 Forbidden` (личность известна, доступа нет), `404 Not Found` |
| 5хх | Ошибка сервера | `500 Internal Server Error` |

Заголовки — это метаданные (`Name: value`). Неформальные группы: **общие** (любая сторона), **запрос**, **ответ**, **представительство/организация** (`Content-Type`, `Content-Length`). Допускаются пользовательские заголовки. Сжатие: клиент `Accept-Encoding: gzip, br, deflate`; сервер `Content-Encoding: gzip` — [HTTP-сжатие](#http-compression-content-encoding).

Типичные типы телесных сред: `text/html`, `application/json`, `multipart/form-data` (формы/файлы).

**Прокси** (переходы на уровне приложений): кэш; фильтр (антивирус, родительский контроль); балансировка нагрузки; аутентифицировать; бревно; иногда обнаруживают оскорбительный трафик. Детали обратного прокси/LB: [0_system_design.md — Обратный прокси](./0_system_design_data.md#reverse-proxy).

**When to use:**

Каждая загрузка страницы и `fetch`; REST API; статические активы. Не для длинных двунаправленных потоков — [WebSocket](./6_web_api_apps.md#websocket). Проверьте с помощью сети DevTools или `curl -v`.

#### Common pitfalls

Рассматривать HTTP как «с сохранением состояния» без файлов cookie. Вызов OPTIONS «преобразование данных». С использованием `302` когда тебе нужно `307` (сохраняйте ПОСТ). Включение `TRACE` в производстве (межсайтовое отслеживание). Предполагая, что HTTP/2 имеет текстовый `GET / HTTP/2.0` на проводе.

**Pluses and minuses:**

| + | − |
| - | - |
| Универсальный, кэшируемый, удобочитаемый (HTTP/1.1) | Обычный HTTP не зашифрован — используйте [HTTPS](#https) |
| Расширяемый через заголовки | Нет встроенного сеанса — файлы cookie/токены |
| Одни и те же команды/статусы в HTTP/1.1, 2, 3 | Фрейминг HTTP/2+ является двоичным; DevTools по-прежнему отображает линии в стиле 1.1 |

**Examples:**

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.0
Accept: */*

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256

<!doctype html>…
```

```bash
curl -v http://example.com
# *  TCP / connection
# >  request (client)
# <  response (server)
```

**Thoughts:**

*Браузер запускает каждый HTTP-обмен; методы и коды состояния являются контрактом; файлы cookie добавляют сеансы по протоколу без сохранения состояния.*Структура: [Структура HTTP-запроса](#http-request-structure) · Заголовки: [HTTP-заголовки](#http-headers) · Методы/статус: [HTTP-методы и коды состояния](#http-methods--status-codes) · Файлы cookie: [HTTP cookie](#http-cookies) · JS: [HTTP в JavaScript](#http-in-javascript) · Серверный процесс: [Веб-сервер](#веб-сервер) · Пакеты/DNS/LAN: [Как работает Интернет](./6_web_api_core.md#internet).

**Sources:**

[MDN — обзор HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview) · [MDN — HTTP-сообщения](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages) · [MDN — Методы](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods) · [MDN — Статус](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status) · [Doka — HTTP](https://doka.guide/tools/http-protocol/)

### Web server

**Definition:** Программа, которая принимает HTTP-запросы от клиентов (обычно браузеров), обрабатывает их (файл, кэш, прокси-сервер или приложение) и отправляет HTTP-ответы.

**How it works:**

- Клиент-сервер: один сервер, много клиентов. Веб-сервер — это процесс HTTP на этом компьютере (или за балансировщиком нагрузки). Первые такие программы появились примерно в 1991 году.
- Типичный путь: TCP (или QUIC для HTTP/3) → необязательный TLS → HTTP-сообщение. Сервер читает стартовую строку + заголовки, затем тело, если оно есть, и записывает ответ.
- **Статический:** сопоставляет путь запроса с файлом (HTML/CSS/JS/изображениями) и возвращает его с помощью `Content-Type`.
- **Динамический:** **прокси** запрос к приложению (Node, PHP-FPM, Python, …). Приложение строит тело; веб-сервер по-прежнему владеет HTTP-соединением с клиентом.
- Дополнительная работа обычно выполняется **модулями**: сжатие, сертификаты TLS, аутентификация, кеш, обратный прокси. Nginx, Apache httpd, Caddy и Node `http` все это веб-серверы; в производственных стеках Nginx/Caddy часто ставятся перед приложением.

Форма сообщения (текст HTTP/1.1; HTTP/2+ использует ту же семантику в двоичных кадрах/псевдозаголовках):

| Часть | Запрос | Ответ |
| ---- | ------- | -------- |
| Стартовая линия | `METHOD target HTTP/1.1` | `HTTP/1.1 code reason` |
| Заголовки | `Name: value` за строку | то же самое |
| Пустая строка | конец головы | конец головы |
| Тело | опционально (POST/PUT/PATCH) | опционально (не для 204/некоторых 1xx) |

**When to use:**

Локальный предварительный просмотр построенного сайта; СПА `dist/` + `/api/` прокси; прекращение TLS; gzip/brotli для HTML/CSS/JS.

#### Common pitfalls

Лечение `GET /path HTTP/2.0` как сетевой HTTP/2 — HTTP/2 не имеет текстовой строки запроса; DevTools по-прежнему *показывает* метод + путь. Использование шифрования с открытым ключом для всей полезной нагрузки. TLS использует асимметричное шифрование при рукопожатии, а затем **симметричные** ключи сеанса ([SSL/TLS-рукопожатие](#ssltls--https-handshake)). Снова сжимаем файлы JPEG/ZIP ([HTTP-сжатие](#http-compression-content-encoding)).

**Pluses and minuses:**

| + | − |
| - | - |
| Одно место для TLS, сжатия и статических файлов | Неправильно настроенный прокси-сервер скрывает реальную ошибку приложения |
| Модули охватывают кеш, аутентификацию, обратный прокси | Дев `http-server` не является производственным сервером |

**Examples:**

```js
import { createServer } from 'node:http';

createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/plain; charset=utf-8' });
  res.end('ok');
}).listen(8080);
```

Локальный статический предварительный просмотр (не для производственной загрузки): `npx serve` or `npx http-server` в папке сайта → `http://127.0.0.1:8080` (петлевая обратная связь). URL-адрес локальной сети использует IP-адрес локальной сети устройства (например, `http://192.168.1.56:8080`). `browser-sync` может зеркально отображать прокрутку/навигацию между устройствами в одной сети.

**Thoughts:**

*Веб-сервер поддерживает HTTP; приложения, кэши и TLS — это функции этого процесса или обратного прокси-сервера перед ним.*

Протокол (клиент, прокси, сообщения): [Протокол HTTP](#http-протокол). Слушать порт / `8080`: [Порты, сокеты и сетевые службы](./6_web_api_apps.md#ports-sockets--network-services).

**Sources:**

[MDN — HTTP-сообщения](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages) · [Doka — веб-сервер](https://doka.guide/tools/web-server/) · [Node.js http](https://nodejs.org/api/http.html) · Прокси: [Обратный прокси](./0_system_design_data.md#reverse-proxy) · [Nginx](./10_build_infra.md#nginx) · [Node `http`](./8_nodejs_modules.md#http)

### HTTP & TCP/IP

**Definition:**

TCP/IP — это сетевой стек; HTTP — это прикладной протокол, работающий поверх TCP и использующий надежный поток байтов для сообщений запросов и ответов.

Имена слоев и почему OSI все еще появляется в интервью: [Модели OSI и TCP/IP](./6_web_api_apps.md#osi--tcpip-models).

| Протокол | Слой | Роль |
| -------- | ----------- | -------------------------- |
|ИП | Интернет | Адресация и маршрутизация ([IPv4 и IPv6](./6_web_api_apps.md#ipv4--ipv6)) |
| TCP | Транспорт | Надежная заказная доставка |
| ТЛС | Выше TCP | Шифрование + аутентификация сервера — не замена TCP ([HTTPS](#https)) |
| HTTP | Приложение | Семантика запроса/ответа |Порты и сокеты прослушивания: [Порты, сокеты и сетевые службы](./6_web_api_apps.md#ports-sockets--network-services). Сквозной путь: [Как работает Интернет](./6_web_api_core.md#internet). |

**Examples:**

```
Client                    Server
  |---- TCP SYN ----------->|
  |<--- SYN-ACK ------------|
  |---- ACK --------------->|
  |---- HTTP GET / -------->|
  |<--- HTTP 200 OK --------|
```

**Thoughts:** Рукопожатие, UDP, TFO vs `initcwnd`, STUN/TURN → [TCP против UDP](./6_web_api_interview.md#tcp-vs-udp). HTTP/3 пропускает TCP и использует QUIC для UDP.

### HTTPS

**Definition:**

HTTPS — это протокол HTTP, зашифрованный с помощью TLS, обеспечивающий конфиденциальность, целостность и аутентификацию сервера с помощью сертификатов.

| HTTP | HTTPS |
| ----------------- | ------------------------ |
| Порт 80 (по умолчанию) | Порт 443 (по умолчанию) |
| Открытый текст | Зашифровано |
| Нет сертификата | Требуется сертификат TLS |

**How it works:**

- HTTPS — это **HTTP через TLS** на порту **443** (HTTP — это обычный текст на **80**).
- Дополнительная работа по сравнению с HTTP: **квитирование TLS** (аутентификация сервера с помощью сертификата, согласование сеансовых ключей), затем **шифрование** байтов запроса/ответа в сети.
- Конфиденциальность (перехватчики не могут прочитать), целостность (обнаружение несанкционированного доступа), подлинность (цепочка сертификатов до доверенного центра сертификации).Современные браузеры рассматривают многие API только как **безопасный контекст** (HTTPS).
- После подключения TCP TLS запускается **перед** любыми заголовками/телом HTTP. HTTP/2 и HTTP/3 по-прежнему используются на этом зашифрованном канале (HTTP/3 использует QUIC/UDP, а не TCP).

**When to use:** Все производственные сайты; печенье с `Secure`; смешанный контент блокируется, если страница использует HTTPS, а подресурс — HTTP.

**Pluses and minuses:**

| + | − |
| ------------------------------------ | -------------------------------------------------- |
| Останавливает чтение/изменение трафика MiTM | Первое посещение оплачивает задержку рукопожатия TLS |
| Требуется для современных функций браузера | Неправильная конфигурация сертификата или истечение срока действия приводит к отключению сайта |

**Examples:**

```
https://example.com
  → TCP handshake
  → TLS handshake (cert + session keys)
  → Encrypted HTTP GET / HTTP response
```

**Thoughts:**

*HTTPS = HTTP + TLS-квитирование + шифрование; HTTP-глаголы и заголовки одинаковы, провод — нет.*

В общедоступных сетях Wi-Fi HTTP представляет собой риск **MITM** (чтение/изменение). Сертификаты TLS от доверенного центра сертификации не позволяют злоумышленнику кафе подменить ключи. Пользователи, просматривающие предупреждения о сертификатах, отменяют это. HSTS снижает понижение версии HTTP. Симметричный, открытый ключ и хэши: [Special — Encryption](./7_special_security.md#encryption).Что содержит сертификат и кто его подписывает: [TLS-сертификаты](#tls-certificates-x509--pki). См. [Специальное — MITM](./7_special_security.md#man-in-the-middle-mitm).

**Sources:**

[howhttps.works](https://howhttps.works/) · [MDN — TLS](https://developer.mozilla.org/en-US/docs/Glossary/TLS)

### HTTP method characteristics

**Definition:**

Методы HTTP имеют семантические свойства — безопасные (только для чтения), идемпотентные (повторяемые без побочных эффектов) и кэшируемые.

| Недвижимость | Значение | Методы |
| ---------- | ------------------------- | -------------------------------------------- |
| Сейф | Никакого изменения состояния сервера | GET, HEAD, ОПЦИИ, СЛЕД |
|Идемпотент | Тот же эффект при повторении | GET, HEAD, OPTIONS, TRACE, PUT, DELETE |
| Кэшируемый | Ответ может быть сохранен | GET, HEAD (обычно); ПОСТ/ПАТЧ если свежесть + `Content-Location` |
| Ни | Туннель / побочные эффекты | CONNECT (небезопасно, не идемпотентно, не кэшируемо) |

**Examples:**

```http
GET /api/counter HTTP/1.1     ← safe, idempotent
POST /api/counter/increment   ← not safe, not idempotent
PUT /api/settings/theme       ← idempotent replace
```

**Thoughts:** CONNECT/TRACE и классы состояния: [Протокол HTTP](#http-protocol). Полная таблица методов: [HTTP-методы и коды состояния](#http-methods--status-codes).

**Sources:**

### SSL/TLS & HTTPS handshake

**Definition:**

TLS согласовывает ключи шифрования и аутентифицирует сервер перед передачей данных HTTP по защищенному каналу.

| Тип ключа | Цель |
| ------------------------------ | ------------------------------------ |
| Асимметричный (государственный/частный) | Обмен ключами во время рукопожатия |
| Симметричный (общий сеансовый ключ) | Быстрое массовое шифрование после рукопожатия |

**How it works:**

1. **Сначала TCP** — SYN/SYN-ACK/ACK (HTTP пока нет).
2. **ClientHello** — версия TLS, наборы шифров, общий ключ (TLS 1.3, часто 1-RTT).
3. **ServerHello + сертификат** — аутентификация сервера; браузер проверяет цепочку сертификатов на соответствие доверенным центрам сертификации (совпадение имени хоста, срок действия). См. [сертификаты TLS](#tls-certificates-x509--pki).
4.**Завершено** — обе стороны получают **симметричные** сеансовые ключи (асимметричное шифрование только для рукопожатия). Современный TLS использует **соглашение об эфемерных ключах** (например, ECDHE), а не «шифрование сеансового ключа с помощью RSA» (этот старый обмен ключами RSA устарел).
5. **Данные приложения** — HTTP-запрос/ответ, зашифрованный с помощью этих ключей. Билеты сеанса / 0-RTT могут пропускать работу при последующих посещениях.

ХСТС (`Strict-Transport-Security`) сообщает браузеру использовать HTTPS при будущих посещениях без перехода по HTTP.

1. TCP-соединение
2. ClientHello/ServerHello + сертификат
3. Браузер проверяется с помощью CA
4. Симметричные сеансовые ключи
5. Начинается зашифрованный HTTP

**When to use:** Каждый `https://` навигация; `preconnect` разогреть TCP+TLS; Завершение TLS в Nginx или балансировщике нагрузки.

**Pluses and minuses:**

| + | − |
| ------------------------------------------------ | ----------------------------------------------------- |
| Быстрое массовое шифрование после рукопожатия | Дополнительные RTT при холодном соединении |
|Сертификат подтверждает, что вы разговариваете с предполагаемым хостом | Неправильные часы/отсутствует промежуточный центр сертификации, не удается установить соединение |

**Examples:**

```js
// Node.js — enforce HTTPS in production
if (process.env.NODE_ENV === 'production' && !req.secure) {
  return res.redirect(301, `https://${req.headers.host}${req.url}`);
}
```

**Thoughts:** *TLS аутентифицирует сервер и устанавливает ключи; Затем HTTP запускается внутри этого туннеля.*

### TLS certificates (X.509 / PKI)

**Definition:** Сертификат TLS (исторически «SSL») — это документ **X.509**, который связывает **открытый ключ** с **субъектом** (доменом, иногда организацией) и **подписан** **центром сертификации (CA)**, которому уже доверяет браузер.

**How it works:**

- В проводном режиме используется протокол **TLS** (SSL — старое название). HTTPS = HTTP внутри туннеля TLS. Сервер хранит **закрытый ключ**; сертификат является общедоступным.
- Содержание (веб-PKI, RFC 5280/X.509 v3): открытый ключ, субъект (имена хостов SAN), эмитент, окно действия, использование ключа/EKU, подпись CA. Браузеры поставляются с **корневым хранилищем**; лист должен **связать** через промежуточные соединения с доверенным корнем.- Модель доверия: сайт A подтверждает личность посетителя B, поскольку оба доверяют CA T. T подписывает сертификат A закрытым ключом T. B хэширует поля сертификата и сверяет их с подписью T, используя **открытый** ключ T из корневого/промежуточного ключа. Соответствие → открытый ключ в сертификате принадлежит этому субъекту (если отмечен T).
- После установления связи для массового трафика используется **симметричный** сеансовый ключ.Асимметричная криптография аутентифицирует сервер и помогает согласовать этот ключ — она не шифрует каждый байт HTTP.
- Получение сертификата: (1) общедоступного центра сертификации (Let’s Encrypt ACME/платного центра сертификации) после подтверждения **контроля над доменом**; (2) **самозаверяющий** (эмитент = субъект) для local/dev/intranet — браузеры предупреждают, если вы не установите эмитент; (3) одноразовые/фальшивые имена только для лаборатории.
- Chrome (2014+) поддерживает HTTPS;**Июль 2018 г.** Версия Chrome 68 с пометкой HTTP **Небезопасно**. Браузеры обычно *блокируют* все HTTP-сайты. Замок — это подсказка пользовательского интерфейса, а не дополнительная криптовалюта.

Организации, которые подписывают сертификаты после проверок. Доверие — это продукт: дискредитированный центр сертификации удаляется из корневых хранилищ. Выбирайте по включению в магазины браузеров/ОС, автоматизации ACME, юрисдикции, цене. **Let’s Encrypt** выдает бесплатные **DV** сертификаты через ACME (хостинг часто делает это;в противном случае Certbot или другой клиент ACME).

| Вид | Что на самом деле проверил центр сертификации | Типичное использование |
| ---- | ---------------------------- | ----------- |
| **ДВ** | Контроль домена (вызов DNS/HTTP) | Почти все публичные сайты Let’s Encrypt |
| **ОВ** | Домен + идентификатор организации | Некоторые предприятия |
| **ЭВ** | Более строгие организационные проверки (CA/Форум браузеров) | Банки исторически;**без дополнительного шифрования**, в браузерах удалена зеленая полоса пользовательского интерфейса |
| **Подстановочный знак** | `*.example.com` (обычно не вершина `example.com` если они также не указаны) | Множество поддоменов, один сертификат |
| **SAN/многодоменный** | Несколько имен хостов в одном сертификате | `www` + вершина + дополнительные возможности |

DV/OV/EV различаются **проверкой личности**, а не надежностью шифрования. Исторические каталоги «Класс 1–5» (VeriSign) и РУ «физлицо/бизнес/EV» являются вендорской упаковкой; Ответ на собеседовании: **DV / OV / EV + подстановочный знак/SAN**.

**When to use:**

Рабочий HTTPS (подписанный CA); локальный HTTPS (`mkcert` / самоподписанный); внутренняя PKI с корнем компании на управляемых устройствах.

#### Common pitfalls

Лечение `openssl req -new` вывод в виде сертификата (это **CSR**). История рукопожатия RSA с обменом ключами («браузер шифрует сеансовый ключ открытым ключом сайта») — устаревшее; TLS 1.3 использует (EC)DHE. Предполагая, что EV — это «более сильный HTTPS». Просматривая предупреждения о сертификатах. Подстановочный знак не распространяется автоматически на регистрируемый домен, если он не включен в SAN.

**Pluses and minuses:**

| + | − |
| - | - |
| Останавливает случайный MITM; разблокирует API безопасного контекста | Истечение срока действия/отсутствие промежуточного звена приводит к закрытию сайта |
| Let’s Encrypt + ACME бесплатен и автоматизирован | Самоподписанным не доверяют в общедоступной сети |
| Та же криптография TLS для дешевого DV, что и для EV | Скомпрометированный ЦС — это провал отраслевого уровня |

**Examples:**

```bash
# Private key (add -aes256 to passphrase-protect it)
openssl genrsa -out example.com.key 2048

# CSR for a public CA — not a certificate; do not install this as the server cert
openssl req -new -key example.com.key -out example.com.csr
openssl req -noout -text -in example.com.csr

# Self-signed leaf for localhost / labs (issuer = subject)
openssl req -newkey rsa:2048 -x509 -sha256 -days 365 -nodes \
  -out cert.pem -keyout key.pem
```

**Thoughts:**

*Подпись CA в сертификате X.509 позволяет браузеру доверять открытому ключу имени хоста; Затем TLS использует это для аутентификации сервера и установки симметричных ключей.*

Шаги установления связи → [Рукопожатие SSL/TLS](#ssltls--https-handshake). MITM → [7_special.md](./7_special_security.md#man-in-the-middle-mitm). Завершение TLS в Nginx → [10_build.md — Nginx](./10_build_infra.md#nginx).

**Sources:**

[MDN — Центр сертификации](https://developer.mozilla.org/en-US/docs/Glossary/Certificate_authority) · [MDN — TLS](https://developer.mozilla.org/en-US/docs/Glossary/TLS) · [Давайте зашифруем — Начало работы](https://letsencrypt.org/getting-started/) · [OpenSSL HOWTO сертификаты](https://github.com/openssl/openssl/blob/master/doc/HOWTO/certificates.txt) · [Doka — SSL-сертификаты](https://doka.guide/tools/ssl/) (довериемодель; подробности о рукопожатии/CSR, приведенные выше, заменяют статью 2022 года)

### HTTP request structure

**Definition:** Сообщения HTTP/1.x представляют собой **начальную строку**, необязательные **заголовки**, пустую строку и необязательное **тело**. Запросы используют строку запроса; ответы используют строку состояния.

**How it works:**

- Строка запроса: `<method> <request-target> <protocol>` — e.g. `GET / HTTP/1.1`. Заказ фиксированный. Целью обычно является исходная форма (путь + запрос); `Host` держит авторитет. Другие формы: абсолютный URL (прокси-GET), `host:port` (`CONNECT`), `*` (`OPTIONS`).
- Статус-строка: `<protocol> <status-code> <reason-phrase>` — e.g. `HTTP/1.1 200 OK`. Фраза причины предназначена для людей. Классы: [Протокол HTTP](#http-протокол).
- Заголовки: `Name: value` (имя не чувствительно к регистру). Наличие тела обозначается `Content-Length` or `Transfer-Encoding` (часто `chunked`). `Content-Type` называет тип носителя (`text/html`, `application/json`, `multipart/form-data`).
- HTTP/2+ сохраняет те же поля, что и **псевдозаголовки** (`:method`, `:path`, `:authority`, `:scheme`, `:status`) внутри двоичных кадров; версия не повторяется в каждом сообщении.

**When to use:**

Отладка с помощью DevTools/ `curl -v`. GET не должен отправлять тело запроса; HEAD не имеет тела **ответа**; POST/PUT/PATCH обычно имеют тело запроса.

#### Common pitfalls

Забывчивость `Host` по HTTP/1.1. Предполагая, что HTTP/2 выглядит так `HTTP/2.0` на проводе. Сбивает с толку шаг за шагом `Transfer-Encoding` со сквозным `Content-Encoding`.

**Examples:**

```http
POST /api/login HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbG…

{"email":"user@example.com","password":"***"}
```

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /users/123

{"id":123}
```

```bash
curl -v http://example.com
# * connection  > request  < response
```

**Thoughts:** *Изучите текст HTTP/1.1; HTTP/2/3 меняет кадр, а не методы, коды состояния или значение заголовка.*

**Sources:**

[MDN — HTTP-сообщения](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages)

  <summary>HTTP headers</summary>

### HTTP headers

**Definition:** Заголовки HTTP — это строки метаданных «ключ-значение», которые описывают запрос, ответ или представление (тело). Новые функции часто представляют собой просто новые заголовки, с которыми согласны обе стороны.

**How it works:**

Сначала отправляйте **общие** заголовки, затем только запросы или ответы, а затем **заголовки представления/сущностей** (`Content-Type`, `Content-Length`, `Content-Encoding`). Имена не чувствительны к регистру. Допускаются пользовательские заголовки. Типичные вакансии: `Host`, `Authorization`, кэш (`Cache-Control`, `ETag`), язык (`Accept-Language`), последняя модификация.

| Категория | Роль | Примеры |
| -------- | ---- | -------- |
| Общие | Обе стороны | `Cache-Control`, `Date`, `Connection` |
| Запрос | Только клиент | `Authorization`, `Accept`, `Origin`, `Host`, `User-Agent` |
| Ответ | Только сервер | `Set-Cookie`, `ETag`, `Location`, `WWW-Authenticate` |
| Представительство (юридическое лицо) | Метаданные тела | `Content-Type`, `Content-Length`, `Content-Encoding` |

**When to use:** Согласовать кодировку (`Accept-Encoding` / `Content-Encoding`) — [HTTP-сжатие](#http-compression-content-encoding). Аутентификация, файлы cookie, CORS — все находится в заголовках.

**Examples:**

```http
GET /api/data HTTP/1.1
Accept: application/json
Accept-Language: en-US
Accept-Encoding: gzip, deflate, br
User-Agent: MyApp/1.0
Origin: https://app.example.com
```

**Thoughts:** *Стартовая линия — это глагол/статус; заголовки — это плоскость управления.*

**Sources:**

[MDN — HTTP-заголовки](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers)

### HTTP compression (Content-Encoding)

**Definition:** Сервер может сжимать **тело сообщения**; `Content-Encoding` называет алгоритм, чтобы клиент мог декодировать обратно в `Content-Type` ресурс.

**How it works:**

1. Реклама клиента `Accept-Encoding: gzip, deflate, br` (и часто `zstd`).
2. Сервер выбирает один, сжимает тело и отвечает `Content-Encoding: br` (or `gzip`) и должен отправить `Vary: Accept-Encoding` поэтому в кешах хранятся отдельные варианты.
3. `Content-Length` относится к **закодированным** байтам.

| Токен | Алгоритм |
| ----- | --------- |
| `gzip` | LZ77+CRC — универсальный |
| `deflate` | оболочка zlib вокруг deflate |
| `br` | Brotli — для текста обычно меньше, чем gzip |
| `zstd` | Zstandard — растущая поддержка |

**When to use:**

HTML, CSS, JS, JSON, SVG. Пропускайте уже сжатые типы (JPEG, PNG, WebP, ZIP, большинство видео). Изображения требуют работы с форматом/размером/качеством, а не с помощью gzip-на-пикселях.

#### Common pitfalls

Двойное сжатие (приложение + прокси и gzip). Рассматривая Zopfli как отдельную HTTP-кодировку, Zopfli генерирует **gzip-совместимые** байты. Шаг за шагом `Transfer-Encoding` (e.g. `chunked`) не то же самое, что сквозной `Content-Encoding`.

**Pluses and minuses:**

| + | − |
| - | - |
| Меньшие текстовые данные, более быстрая загрузка | ЦП на сервере; крошечные тела могут вырасти |
| Бротли часто превосходит gzip в HTML/CSS/JS | Отсутствующий `Vary` отравляет общие кэши |

**Examples:**

```http
GET /app.js HTTP/1.1
Host: example.com
Accept-Encoding: gzip, deflate, br

HTTP/1.1 200 OK
Content-Type: text/javascript; charset=utf-8
Content-Encoding: br
Vary: Accept-Encoding
```

**Thoughts:** *Переговоры с `Accept-Encoding`; пометить тело значком `Content-Encoding`; не сжимайте файлы JPEG.*

**Sources:**

[MDN — кодирование контента](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Encoding) · [MDN — сжатие в HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Compression)

### PUT vs POST

**Definition:**

| | УРИ | Коллекция (`/books`) | Специфический (`/books/3`) |

**Examples:**

```http
POST /books        → creates new book, returns 201 + Location
PUT  /books/3      → replaces book 3 entirely (same result if repeated)
```

<details>
  <summary>HTTP caching</summary>

### HTTP caching

**Definition:** Кэширование HTTP сохраняет ответы, поэтому повторные запросы могут обслуживаться из кеша без обращения к источнику.

**How it works:**

1. Сервер отправляет `Cache-Control: max-age=3600` и/или `ETag: "abc"`. Исходные серверы и обратные прокси-серверы также могут кэшировать идентичные запросы и пропускать повторный запуск приложения (TTL/стратегия — это конфигурация сервера).
2. Браузер (и, при необходимости, CDN) сохраняет ответ до тех пор, пока он не перестанет быть **свежим**. `Cache-Control: public, max-age=31536000` сообщает клиенту, что статический актив может оставаться в течение года (`max-age` это секунды).
3. По истечении срока действия браузер может отправить **условный** запрос: `If-None-Match: "abc"` (or `If-Modified-Since`).
4. Сервер возвращает **304 Not Modified** (нет тела), если оно не изменилось — экономит полосу пропускания.

| Директива | Эффект |
| -------------- | ------------------------------------------------------ |
| `max-age=3600` | Свежий 3600 секунд |
| `no-cache`     | Сохранить, но **перепроверить** с использованием источника перед повторным использованием |
| `no-store`     | Не хранить (конфиденциально/зависит от пользователя) |
| `private`      | Только браузер, без общего CDN |
| `public`       | Общие кэши/CDN могут хранить |
| `immutable`    | Никогда не выполняйте повторную проверку (хешированные имена файлов, длинные `max-age`) |

| Слой | Кто | Пример |
| ------------ | ------------------------------------- | -------------------------------------------------------------------------------------- |
| HTTP/CDN | Дисковый кеш браузера, Nginx, Cloudflare | `Cache-Control`, `ETag`, `304`                                                         |
| Приложение (клиент) | JS в памяти / Redux | **RTK-запрос**, TanStack Query — с ключом по конечной точке + аргументы, повторная выборка, `keepUnusedDataFor` |

Заголовки HTTP **не** заменяют клиентский кеш: два `fetch` вызовы в React по-прежнему попадают в сеть, если вы не используете библиотеку (или кэш-хранилище). По умолчанию RTK-запрос: данные остаются, пока подписывается крючок; после размонтирования происходит сбор мусора через **60 с** (`keepUnusedDataFor`), независимо от `Cache-Control`.

Кэшированные **изображения** не попадают в сеть. Кэшированный **JS/CSS** по-прежнему требует анализа (и выполнения JS) — именно поэтому существует разделение кода ([10_build.md](./10_build_bundlers.md#code-splitting)).

**When to use:** Хешированные имена файлов ресурсов → `public, max-age=31536000, immutable`. Пользовательский API → `private, no-store`. Повторите чтение пользовательского интерфейса одного и того же запроса GET → RTK / TanStack Query.

**Pluses and minuses:**

| + | − |
| ------------------------------------- | ------------------------------------ |
| Более быстрые повторные загрузки, меньшая нагрузка на сервер | Устаревшие данные, если TTL слишком длинный |
| 304 экономит пропускную способность | Инвалидация для динамического API сложна |

**Examples:**

```http
Cache-Control: public, max-age=3600
ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"

GET /style.css
If-None-Match: "33a64df…"
→ 304 Not Modified
```

**Thoughts:**

`Cache-Control` *это уровень HTTP/CDN; RTK Query — это клиентский кеш JSON в памяти. Они складываются, но не совпадают.*

| Стратегия | Поведение |
| ---------------------- | ---------------------------------- |
| Только кэш | Обслуживать статические ресурсы из кэша |
| Только сеть | Всегда получать (аналитика) |
|Кэш → сеть | Откат в режиме оффлайн |
| Сеть → кэш | Свежие данные, кэш в случае успеха |
| Устарело при повторной проверке | Подавать устаревшие, обновлять в фоновом режиме |

**Sources:**

[MDN — HTTP-кэширование](https://developer.mozilla.org/en-US/docs/Web/HTTP/Caching)

### HTTP in JavaScript

**Definition:**

Браузеры предоставляют несколько API для асинхронного HTTP без полной перезагрузки страницы (шаблон AJAX). `fetch` это современное значение по умолчанию; `XMLHttpRequest` остается для прогресса загрузки и некоторых устаревших путей.

| API | Статус |
| ---------------- | -------------------- |
| `fetch`          | Современный стандарт |
| `XMLHttpRequest` | Наследие + прогресс загрузки |
| HTML `<form>`    | Полная навигация по страницам |
| Аксиос/jQuery | Сторонние оболочки |

**How it works:** `fetch(url, init)` возвращает `Promise<Response>`. Набор `method` к HTTP-глаголу (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, …). Тела JSON нужны `JSON.stringify` и обычно `Content-Type: application/json`. Сбои сети отклоняются; HTTP 4xx/5xx делать **нет** — проверьте `res.ok`. Тело однажды: только один из `res.json()` / `text()` / `blob()` / `arrayBuffer()`.

**Download progress:** читать `response.body.getReader()` куски; сумма `value.length` vs `Content-Length` когда присутствует. **Ход загрузки:** недоступен на `fetch` - использовать `xhr.upload.onprogress`.

**XHR sketch:** `open` → `send` → `onload` / `onerror` / `onprogress`. `xhr.responseType = 'json'` | `'blob'` | `'arraybuffer'`. Файлы cookie перекрестного происхождения: `xhr.withCredentials = true` (та же идея, что и `fetch` `credentials: 'include'`).

**Resumable upload idea:** спросить сервер, сколько у него байтов (`X-File-Id`), затем `file.slice(startByte)` + `X-Start-Byte` через XHR (сервер должен добавить).

**Examples:**

```js
const res = await fetch('/api/save-text', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(state),
});
if (!res.ok) throw new Error(`HTTP ${res.status}`);
```

```js
// download progress (fetch)
const res = await fetch(url);
const total = +res.headers.get('Content-Length') || 0;
const reader = res.body.getReader();
let received = 0;
const chunks = [];
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  chunks.push(value);
  received += value.length;
  console.log(received, total);
}
```

[javascript.info/fetch](https://javascript.info/fetch) · [javascript.info/fetch-progress](https://javascript.info/fetch-progress) · [javascript.info/xmlhttprequest](https://javascript.info/xmlhttprequest) · [javascript.info/resume-upload](https://javascript.info/resume-upload) · [MDN — использование Fetch API](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) · [MDN — методы HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods)

### Fetch API — AbortController & FormData

**Definition:** `fetch` это современный API браузера для HTTP. `AbortController` отменяет запросы в полете; `FormData` строит `multipart/form-data` тела для загрузки файлов и смешанные поля.

**How it works:**

- `fetch(url, options)` возвращает `Promise<Response>` - проверять `res.ok` (`status 200–299`); сетевые ошибки отклоняются, HTTP 4xx/5xx — нет.
- `AbortController` — `const ac = new AbortController(); fetch(url, { signal: ac.signal })`; вызов `ac.abort()` → обещание отклоняется с `AbortError`. Один контроллер может прервать совместное использование нескольких выборок. `signal`.
- `FormData` — `fd.append('file', fileInput.files[0])`; проходить `body: fd` — наборы браузеров `Content-Type` с границей автоматически (не задается вручную). Файловый: `append(name, blob, fileName)`.
- Таймауты — объединить `AbortController` с `setTimeout(() => ac.abort(), 5000)`.
- Редкие варианты: `keepalive: true` (в стиле маяка, например `unload`, тело ≤ 64 КБ всего); `credentials` / `mode` / `cache` / `integrity` — см. [javascript.info/fetch-api](https://javascript.info/fetch-api). Подробности CORS: [CORS](./6_web_api_security.md#cors).

**When to use:**

- Исправлен поиск — прерывание предыдущего запроса, когда пользователь снова вводит текст.
- Реагировать `useEffect` очистка — прерывание выборки при размонтировании.
- Загрузка файла — `FormData` + `POST`; для использования JSON `JSON.stringify` + `Content-Type: application/json`.
- Аналитика в отпуске — `keepalive` ПОСТ (или `navigator.sendBeacon`).

**Pluses and minuses:**

| Особенность | + | − |
| ----------------- | ------------------------------------------- | ------------------------------------------- |
| `AbortController` | Отменяет устаревшие запросы (поиск, навигация) | Должен справиться `AbortError` в улове |
| `FormData`        | Собственные многочастные загрузки | Меньше контроля, чем ручная граница |
| `fetch`           | На основе обещаний, потоки через `res.body`       | Нет прогресса загрузки без `XMLHttpRequest` |

**Examples:**

```js
const ac = new AbortController();
const timeout = setTimeout(() => ac.abort(), 8000);

try {
  const res = await fetch('/api/upload', {
    method: 'POST',
    signal: ac.signal,
    body: (() => {
      const fd = new FormData();
      fd.append('title', 'Report');
      fd.append('file', file);
      return fd;
    })(),
  });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return await res.json();
} catch (e) {
  if (e.name === 'AbortError') return; // cancelled — ignore
  throw e;
} finally {
  clearTimeout(timeout);
}
```

**Thoughts:** `credentials: 'include'` отправляет файлы cookie из разных источников только в том случае, если CORS разрешает учетные данные. Предпочитать `res.json()` только после проверки статуса.

**Sources:**

[javascript.info/fetch](https://javascript.info/fetch) · [javascript.info/formdata](https://javascript.info/formdata) · [javascript.info/fetch-abort](https://javascript.info/fetch-abort) · [javascript.info/fetch-api](https://javascript.info/fetch-api) · [MDN — AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController) · [MDN — FormData](https://developer.mozilla.org/en-US/docs/Web/API/FormData))

### Rate limiting (429)

**Definition:** Ограничение скорости ограничивает количество запросов, которые клиент может сделать за определенный период времени. При превышении сервер отвечает **429 Too Many Requests**.

**How it works:**

- Сервер отслеживает счетчики для каждого ключа — IP, ключа API, идентификатора пользователя или их комбинации.
- Алгоритмы: **фиксированное окно** (100 запросов в минуту), **скользящее окно** (более плавный), **корзина токенов** (пакетный режим + постоянная скорость).
- Ответ включает в себя `**Retry-After**` заголовок (секунды или HTTP-дата), сообщающий клиенту, когда следует повторить попытку.
- Edge/CDN (Cloudflare, API Gateway) или промежуточное ПО приложения (Redis `INCR` + TTL) обеспечивают соблюдение ограничений.

**When to use:**

- Публичные API — многоуровневые ограничения (бесплатные или платные).
- Конечные точки входа — строгие ограничения на грубую силу.
- Клиент — уважение `429` + `Retry-After`; экспоненциальная задержка с джиттером.

**Pluses and minuses:**

| Подход | + | − |
| -------------- | ------------------- | --------------------- |
| на базе IP | Простой | Общая несправедливость NAT |
| API-ключ/пользователь | Ярмарка на арендатора | Требуется авторизация |
| Ведро токенов | Позволяет короткие очереди | Более сложный |
| Счетчик Redis | Распределенное, быстрое | Дополнительная инфраструктура |

**Examples:**

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{ "error": "rate_limit_exceeded", "limit": 100, "window": "1m" }
```

```js
// Client retry with backoff
async function fetchWithRetry(url, opts, retries = 3) {
  const res = await fetch(url, opts);
  if (res.status !== 429 || retries === 0) return res;
  const wait = Number(res.headers.get('Retry-After') ?? 1) * 1000;
  await new Promise((r) => setTimeout(r, wait));
  return fetchWithRetry(url, opts, retries - 1);
}
```

**Thoughts:** Возвращайте **429**, а не **403** — 403 означает, что вход запрещен независимо от скорости. Ограничения на документы в документации API (`X-RateLimit-Limit`, `X-RateLimit-Remaining` являются общими соглашениями). Ограничения IP помогают перебору и Slowloris с одного хоста; они **не** останавливают крупные DDoS-атаки — для этого необходимы периферийные мощности. Для неполных медленных запросов требуются **таймауты чтения**, а также 429. См. [Special — DoS / Slowloris](./7_special_security.md#denial-of-service-dos--ddos).

**Sources:**

[MDN — 429 слишком много запросов] (https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/429) · [IETF — Retry-After] (https://datatracker.ietf.org/doc/html/rfc7231#section-7.1.3)
