## Event loop

<details>
  <summary>Event loop overview</summary>

### Event loop

**Definition:** Цикл событий — это планировщик, который наблюдает за стеком вызовов и очередями задач. Когда стек пуст, он берет следующую задачу из очереди и помещает ее в стек для выполнения.

**How it works:**

- JavaScript выполняется **синхронно** в **одном потоке** — одновременно выполняется только один кадр стека вызовов.
- Длительная работа (таймеры, ввод-вывод, сеть) делегируется хосту (веб-API браузера или Node libuv).
- Когда асинхронная работа завершается, ее обратный вызов помещается в **очередь задач** (микрозадача или макрозадача).- Цикл событий повторяется: слив кода синхронизации → слив всех микрозадач → запуск одной макрозадачи → (браузер: возможно, рендеринг) → повтор.
- Стек должен быть пуст перед запуском любого обратного вызова в очереди.

| Часть                | Роль                                       |
| -------------------- | ------------------------------------------ |
| **Стек вызовов**     | Выполняет синхронные вызовы функций (LIFO) |
| **Веб-API/API узла** | Таймеры, ввод-вывод, события DOM, `fetch`  |
| **Очереди задач**    | Держите обратные вызовы готовыми к запуску |

**When to use:**

| Ситуация                               | Что проверить                                                                            |
| -------------------------------------- | ---------------------------------------------------------------------------------------- |
| `setTimeout(fn, 0)` не немедленно      | Обратный вызов ожидает стека + микрозадачи                                               |
| Заморозка пользовательского интерфейса | Длинный цикл синхронизации в основном потоке                                             |
| Порядок обещания и таймера             | Микрозадачи всегда перед следующей макрозадачой                                          |
| Отладка асинхронного потока            | Используйте [JSV9000](https://www.jsv9000.app/) или [Лупу](http://latentflip.com/loupe/) |

#### Common pitfalls

- Предполагая `setTimeout(fn, 0)` запускается сразу после текущей строки — микрозадачи запускаются первыми.
- Планирование неограниченное `Promise.resolve().then(...)` цепочки — блоки рендеринга и таймеры.
- Непонятный цикл событий браузера с фазами узла — см. [8_nodejs.md](./8_nodejs.md).

**Pluses and minuses:**

| +                                                          | −                                                        |
| ---------------------------------------------------------- | -------------------------------------------------------- |
| Простая модель параллелизма — никаких блокировок в куче JS | Код синхронизации, нагружающий процессор, блокирует все  |
| Микрозадачи дают предсказуемый порядок обещаний            | Бесконечные микрозадачи истощают макрозадачи и рендеринг |
| Работает одинаково в браузере и Node (в основном)          | Узел имеет доп. `process.nextTick` приоритет             |

**Examples:**

```js
console.log("sync");
setTimeout(() => console.log("macrotask"), 0);
Promise.resolve().then(() => console.log("microtask"));
// sync → microtask → macrotask
```

**Sources:** [javascript.info/event-loop](https://javascript.info/event-loop) · [Визуализатор JSV9000](https://www.jsv9000.app/) · [Лупа](http://latentflip.com/loupe/)

<details>
  <summary>Call stack</summary>

### Call stack

**Definition:** Структура данных LIFO, которая отслеживает активные вызовы функций и контексты их выполнения. Весь код приложения JavaScript проходит через стек вызовов.

**How it works:**

- Каждый вызов функции **помещает** новый контекст выполнения в стек.
- Когда функция **возвращается**, ее контекст **выскакивает**.
- Вложенные вызовы создают стек: `main()` → `foo()` → `bar()`.
- Каждый контекст имеет: переменную среду, цепочку областей действия, `this` привязка и (для генераторов) состояние.
- Переполнение стека (`Maximum call stack size exceeded`) происходит, когда рекурсия никогда не возвращается или глубина превышает предел движка (~ 10–50 тыс. кадров). Модель памяти ОС/процесса (виртуальные страницы, куча или стек): [Память: стек и куча](./3_js_variables.md#memory-stack-heap).

| Этап           | Что происходит                                                         |
| -------------- | ---------------------------------------------------------------------- |
| **Создание**   | Выделить память, построить цепочку областей действия, привязать `this` |
| **Исполнение** | Запустить тело функции; вложенные вызовы помещаются в стек             |
| **Снос**       | Вытащить контекст, когда функция возвращает                            |

**When to use:**

| Ситуация                 | Значение                                                                                         |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| Чтение трассировки стека | Вверху = текущая функция, внизу = точка входа                                                    |
| Рекурсия                 | Должен быть базовый случай или использовать батут/итерацию                                       |
| `async` функции          | `await` приостанавливает функцию, но не блокирует стек — продолжение выполняется как микрозадача |
| Обработчики событий      | Каждый вызов получает новый кадр стека                                                           |

#### Common pitfalls

- Ожидая `async`/`await` чтобы заблокировать поток — приостанавливается только эта функция; другой код продолжает работать.
- Бесконечная рекурсия без оптимизации хвостовых вызовов в JS (не гарантировано) — переполнение стека.

**Pluses and minuses:**

| +                                                                 | −                                                                       |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Простая ментальная модель потока синхронизации                    | Глубокая рекурсия может переполниться                                   |
| Сопоставление трассировок стека непосредственно для заказа вызова | Никакого параллельного выполнения JS в одном потоке                     |
| Быстрое нажатие/выталкивание для вызовов функций                  | Асинхронные обратные вызовы выполняются позже — не в том же кадре стека |

**Examples:**

```js
function greet(name) {
  console.log("Hello, " + name + "!");
}

function main() {
  greet("Alice");
  greet("Bob");
}

main();
// Stack: main → greet('Alice') → pop → greet('Bob') → pop → pop
```

**Sources:** [javascript.info/call-stack](https://javascript.info/call-stack)

</details>

<details>
  <summary>Microtasks vs macrotasks</summary>

### Microtasks vs macrotasks

**Definition:** Асинхронная работа запланирована в двух типах очередей. **Микрозадачи** выполняются после текущего кода синхронизации и перед следующей макрозадачой. **Макрозадачи** выполняются по одной за один оборот цикла событий.

**How it works:**

- После завершения кода синхронизации и опустошения стека движок очищает **всю очередь микрозадач**.
- Каждая микрозадача может включать в очередь дополнительные микрозадачи — все они выполняются в один и тот же ход перед любой макрозадачой.
- Затем запускается **одна** макрозадача (таймер, обратный вызов ввода-вывода, событие пользовательского интерфейса).
- Браузер может рисовать между макрозадачами; микрозадачи могут задерживать покраску.
- Узел добавляет `process.nextTick` — выполняется раньше других микрозадач (более высокий приоритет).

| Тип             | Примеры                                                                                          | Приоритет                                     |
| --------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| **Микрозадача** | `Promise.then/catch/finally`, `queueMicrotask`, `MutationObserver`, `async/await` продолжения    | Выше — слить все перед следующей макрозадачой |
| **Макрозадача** | `setTimeout`, `setInterval`, ввод-вывод, события пользовательского интерфейса, `message` событие | Нижний — по одному на итерацию цикла          |

**When to use:**

| Используйте микрозадачи | Используйте макрозадачи |

|--------------------------------|
| Обещание реакции, `queueMicrotask` | Таймеры, пользовательские события, завершение ввода-вывода |
| Наблюдение DOM (`MutationObserver`) | Отмененные обновления пользовательского интерфейса (часто `setTimeout`) |
| Прерывание синхронизации без блокировки рисования | Кадры анимации (`requestAnimationFrame` — отдельная очередь) |

#### Common pitfalls

- `requestAnimationFrame` **не** микрозадача — выполняется перед отрисовкой, отдельно от обеих очередей.
- Рекурсивный `queueMicrotask` или цепочки обещаний — могут заморозить страницу.
- Предполагая `setInterval` срабатывает точно в интервале — задерживается, если основной поток занят.

**Pluses and minuses:**

| +                                                | −                                                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Пакетные микрозадачи обещают эффективные реакции | Длинные цепочки микрозадач блокируют таймеры и пользовательский интерфейс                |
| Макрозадачи поддаются рендерингу (браузер)       | Сложнее рассуждать о смешанном коде таймера и обещания                                   |
| Явный приоритет: обещания раньше `setTimeout`    | Узел `nextTick` может привести к прекращению ввода-вывода при неправильном использовании |

**Examples:**

```js
Promise.resolve().then(() => console.log("micro 1"));
Promise.resolve().then(() => console.log("micro 2"));
setTimeout(() => console.log("macro"), 0);
// micro 1, micro 2, macro
```

**Sources:** [MDN QueueMicrotask](https://developer.mozilla.org/en-US/docs/Web/API/Window/queueMicrotask) · [MDN MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver)

</details>

### Execution order

**Definition:** Одна итерация цикла событий следует фиксированному порядку: запускать код синхронизации до тех пор, пока стек не станет пустым, очистить **все** микрозадачи, запустить **одну** макрозадачу, а затем, при необходимости, отрисовать кадр (браузер).

**How it works:**

- Код синхронизации всегда выполняется первым — сверху вниз, пока стек не станет пустым.
- Запускаются все ожидающие микрозадачи, включая те, которые были запланированы более ранними микрозадачами в том же ходу.
- На каждой итерации выполняется ровно **одна** макрозадача (кроме пакетов браузера).
- Браузер: после макрозадачи может выполняться **этапы рендеринга** (стиль, макет, рисование), если прошло достаточно времени (~ 16 мс для 60 кадров в секунду).
- Цикл повторяется до тех пор, пока все очереди не опустеют и не поступит новая работа.- Код синхронизации всегда запускается первым.
- Все ожидающие микрозадачи выполняются до следующей макрозадачи.
- Микрозадача, планирующая другую микрозадачу — новая тоже выполняется в том же ходу.
- Браузер может иметь отдельные очереди рендеринга между макрозадачами.

**When to use:**

| Ситуация                           | Ожидаемое поведение                                                      |
| ---------------------------------- | ------------------------------------------------------------------------ |
| Загадки с асинхронным выводом      | Трассировка: синхронизация → микрозадачи → один макрос                   |
| Пакетное чтение/запись DOM         | Читайте синхронно, пишите после микрозадач или в `requestAnimationFrame` |
| `Promise.then` внутри `setTimeout` | Сначала запускается макрос, затем его микрозадачи                        |
| Настройка производительности       | Делайте очереди микрозадач короткими                                     |

#### Common pitfalls

- Забыв об этом `setTimeout` внутри микрозадачи по-прежнему планируется **будущая** макрозадача (4 запуска после 2 и 6).
- `new Promise(executor)` запускает исполнителя **синхронно** — только `.then` является асинхронным.

**Pluses and minuses:**

| +                                                      | −                                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| Детерминированный порядок головоломок для интервью     | Реальные приложения смешивают множество источников — их трудно отследить |
| Микрозадачи выполняют цепочки обещаний атомарно за ход | Рендеринг может быть задержан из-за шторма микрозадач                    |
| Одна макрозадача за ход позволяет рисовать             | Порядок немного отличается в Node и браузере                             |

**Examples:**

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
Promise.resolve().then(() => setTimeout(() => console.log(4)));
Promise.resolve().then(() => console.log(5));
setTimeout(() => console.log(6), 0);
console.log(7);
// 1, 7, 3, 5, 2, 6, 4
```

**Sources:** [javascript.info/event-loop](https://javascript.info/event-loop)

## Callbacks & async patterns

<details>
  <summary>Sync vs async execution</summary>

### Sync vs async execution

**Definition:** **Синхронный** код выполняется в основном потоке шаг за шагом — следующая строка ожидает завершения предыдущей. **Асинхронные** расписания кода выполняются позже, не блокируя основной поток.

**How it works:**

- Синхронизация: стек вызовов запускает каждый оператор; вызовы функций блокируются до возврата.
- Асинхронность: API хоста начинает работать; JS продолжает; обратный вызов/обещание выполняется позже через очереди.
- `async/await` является синтаксическим сахаром — по-прежнему однопоточным, по-прежнему основанным на очередях.
- Порядок завершения асинхронных задач **не** гарантированно соответствует порядку запуска (за исключением одной цепочки).


| Синхронизировать          | Асинхронный                                     |
|  ---------------------  |  -------------------------  |
| **Блокировка**        | Да — держит нить          | Нет — обратный вызов/обещание выполняется позже |
| **Примеры**           | `console.log`, арифметика | `setTimeout`, `fetch`, `fs.readFile`            |
| **Оформление заказа** | Строгий сверху вниз       | Порядок выполнения зависит от очередей          |

**When to use:**

| Используйте синхронизацию                          | Используйте асинхронный                                    |
| -------------------------------------------------- | ---------------------------------------------------------- |
| Чистые вычисления, преобразование локальных данных | Сеть, файловая система, таймеры                            |
| Короткие чтения DOM в обработчике событий          | Длительные операции, многошаговый ввод-вывод               |
| Проверка перед асинхронным вызовом                 | Все, что не должно замораживать пользовательский интерфейс |

#### Common pitfalls

- Лечение `fetch` как синхронизация — немедленно возвращает обещание; тело асинхронно.
- `fs.readFileSync` в узле в основном потоке — блокирует весь процесс.

**Pluses and minuses:**

| +                                                                              | −                                                                                                |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Синхронизация: простые рассуждения, немедленные результаты                     | Синхронизация ввода-вывода блокирует пользовательский интерфейс и пропускную способность сервера |
| Асинхронность: адаптивный пользовательский интерфейс, одновременный ввод-вывод | Более сложная отладка, сложность обратного вызова/промиса                                        |
| Смешайте оба в одном приложении                                                | Легко случайно заблокировать при работе синхронизации                                            |

**Examples:**

```js
console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");
// A, C, B
```

**Sources:** [javascript.info/intro](https://javascript.info/intro)

</details>

### Callbacks

**Definition:** Функция, передаваемая в качестве аргумента, которая будет вызываться после завершения асинхронной операции — исходный асинхронный шаблон JavaScript.

**How it works:**

- Проходит звонящий `callback(err, result)` or `onSuccess` / `onError` к API.
- Когда асинхронная работа завершается, хост вызывает обратный вызов через цикл событий.
- Вложенные обратные вызовы создают пирамиды («ад обратных вызовов»), когда шаги зависят друг от друга.
- Соглашение об ошибках в узле: `(err, data) => { if (err) ... }`.
- Отсутствие встроенной композиции — ручная разводка для последовательных и параллельных потоков.

**When to use:**

| Используйте обратные вызовы                      | Предпочитаю обещания/`async`             |
| ------------------------------------------------ | ---------------------------------------- |
| Слушатели событий (`on('click', fn)`)            | Многоэтапные конвейеры запросов          |
| API устаревших узлов                             | Новый код приложения                     |
| Простой `setTimeout` задержки                    | Параллельная выборка с агрегацией ошибок |
| Библиотеки, предоставляющие API обратного вызова | Нуждаться `try/catch` ошибки стиля       |

#### Common pitfalls

- Забывание обрабатывать ошибки — молчаливые сбои.
- Обратный вызов вызывается дважды — охрана с флажком или обещание.
- `forEach` с асинхронными обратными вызовами — не ждет; использовать `for...of` or `Promise.all`.

**Pluses and minuses:**

| +                            | −                                                                 |
| ---------------------------- | ----------------------------------------------------------------- |
| Простой, универсальный       | Ад обратного вызова с вложенной логикой                           |
| Никаких дополнительных типов | Трудно создавать и обрабатывать ошибки                            |
| Работает во всех средах      | Инверсия управления — вызывающий теряет поток                     |
| Штраф за разовые мероприятия | Параллельная обработка + обработка ошибок становится многословной |

**Examples:**

```js
function loadData(url, onSuccess, onError) {
  fetch(url)
    .then((r) => r.json())
    .then(onSuccess)
    .catch(onError);
}

// Error-first (Node style)
fs.readFile("file.txt", (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});
```

### Side effects

**Definition:** Операции, которые взаимодействуют с внешним миром — сетью, файловой системой, DOM, таймерами или журналированием — в отличие от чистых вычислений на локальных данных.

**How it works:**

- Чистые функции: тот же вход → тот же выход, никаких внешних операций чтения/записи.
- Побочные эффекты: изменение глобального состояния, касание DOM, вызов API, запись файлов, `console.log`.
- Побочные эффекты асинхронности завершаются позже — их необходимо дождаться или обработать в `.then`.
- В React побочные эффекты относятся к `useEffect` или обработчики событий, а не рендеринг.
- Тесты имитируют побочные эффекты (выборка, таймеры), чтобы обеспечить изоляцию модулей. Шутка: заглушка `global.fetch` к `{ json }` Ответ — [Первые тесты Jest](./7_special_testing_tooling.md#jest--first-tests-node-vs-jsdom). Заглушка против макета против шпиона: [Тестовые дубли](./7_special_testing_practices.md#test-doubles-stubs-mocks-spies).

| Операция        | Пример                        |
| --------------- | ----------------------------- |
| вызов API       | `fetch('/api')`               |
| Мутация DOM     | `element.textContent = '...'` |
| Таймер          | `Date.now()`, `setTimeout`    |
| Ведение журнала | `console.log`                 |

**When to use:**

| Ситуация                | Подход                                                                                                                                                                 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Определите, что `await` | Сеть, БД, файловый ввод-вывод                                                                                                                                          |
| Модульные тесты         | Насмехаться `fetch` (`jest.fn` / Витест `vi.fn`), поддельные таймеры (`vi.useFakeTimers`) — [Тестовые двойники](./7_special_testing_practices.md#test-doubles-stubs-mocks-spies) |
| Загрузка данных React   | `useEffect` + уборка(`AbortController`)                                                                                                                                |
| Redux/редукторы         | Сохраняйте редюсеры чистыми — эффекты в thunks/saga                                                                                                                    |

#### Common pitfalls

- Выстрелил и забыл `fetch` без обработки ошибок.
- Устаревшее замыкание, считывающее старое состояние после асинхронного разрыва — частое явление в React. `useEffect`.
- Несколько одновременных эффектов, обновляющих один и тот же DOM — побеждает гонка за последней записью.

**Pluses and minuses:**

| +                                                                          | −                                       |
| -------------------------------------------------------------------------- | --------------------------------------- |
| Побочные эффекты — это то, как приложения работают на самом деле           | Сложнее тестировать и рассуждать        |
| Асинхронные эффекты обеспечивают отзывчивость пользовательского интерфейса | Условия гонки, если заказ не выполнен   |
| Четкое разделение в хорошо структурированном коде                          | Легко распределять эффекты по базе кода |

**Examples:**

```js
async function refreshUI() {
  const data = await fetch("/api/user").then((r) => r.json()); // side effect: network
  document.title = data.name; // side effect: DOM
}
```

**Sources:** [javascript.info/intro](https://javascript.info/intro)

### AJAX

**Definition:** **Асинхронный JavaScript и XML** — шаблон запроса данных с сервера без полной перезагрузки страницы. Современный код использует `fetch` or `XMLHttpRequest`.

**How it works:**

- Браузер отправляет HTTP в фоновом режиме (`XMLHttpRequest` or `fetch`).
- Сервер **Ранний AJAX:** часто возвращал **фрагмент HTML**; JS вставил его — без полной перезагрузки, API по-прежнему привязан к разметке.
- **Сегодня:** полезная нагрузка обычно представляет собой **JSON**; клиент рендерит. `fetch` возвращает обещание; XHR использует `onload` / `onerror`.
- Применяются CORS, файлы cookie и заголовки аутентификации — см. [Веб-API — CORS](./6_web_api_security.md#cors).

**When to use:**

| Используйте AJAX/`fetch`        | Рассмотрите альтернативы                                  |
| ------------------------------- | --------------------------------------------------------- |
| Динамическая загрузка данных    | Статический контент — SSR/SSG                             |
| Отправка формы без перезагрузки | WebSockets для push-потоков                               |
| Автозаполнение поиска           | События, отправленные сервером для односторонней отправки |
| Опрос на приборной панели       | WebSocket или SSE для работы в режиме реального времени   |

#### Common pitfalls

- Забывчивость `res.ok` проверять - `fetch` не отклоняет на 404/500.
- По умолчанию тайм-аут отсутствует — перенос с помощью `AbortController`.
- Анализ JSON перед проверкой статуса.

**Pluses and minuses:**

| +                                               | −                                                  |
| ----------------------------------------------- | -------------------------------------------------- |
| Адаптивные СПА                                  | Обработка ошибок и сложность кэширования           |
| Частичные обновления                            | CORS и проблемы авторизации                        |
| Лучший UX, чем полная перезагрузка страницы     | Проблемы SEO/гидратации без SSR                    |
| Стандартный `fetch` API в современных браузерах | Устаревшие API XHR все еще находятся в старом коде |

**Examples:**

```js
const res = await fetch("/api/items");
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const items = await res.json();
```

### Callback vs Promise vs async/await

**Definition:** Три уровня асинхронной абстракции — от обратных вызовов вручную до компонуемых обещаний и синхронного вида. `async/await` синтаксис.

**How it works:**

- **Обратные вызовы:** передают функции; вызываемый вызывается, когда все готово. Распространение ошибок вручную.
- **Обещания:** объект с `.then`/`.catch`; цепной; пузырь ошибок до ближайшего `.catch`.
- **асинхронность/ожидание:** `async` функция возвращает обещание; `await` разворачивает его; `try/catch` за ошибки.
- Все три компилируются в одни и те же очереди цикла событий — синтаксический сахар, а не новый параллелизм.
- Обещания и `async/await` взаимодействовать — `await` работает на любом тобле.

**When to use:**

| Узор                 | Лучшее для                                            |
| -------------------- | ----------------------------------------------------- |
| Обратные звонки      | События DOM, устаревшие API, `EventEmitter`           |
| Обещания             | Параллельные партии (`Promise.all`), библиотечные API |
| асинхронный/ожидание | По умолчанию для последовательной логики приложения   |

#### Common pitfalls

- Смешивание обратных вызовов и обещаний без обещаний — двойные пути ошибок.
- `async` функционировать без `await` все равно возвращает Promise — легко забыть `await` на сайте вызова.
- Последовательный `await` в цикле, когда `Promise.all` будет работать.

**Pluses and minuses:**

| Узор                 | +                        | −                                                                           |
| -------------------- | ------------------------ | --------------------------------------------------------------------------- |
| Обратный звонок      | Простой, универсальный   | Ад обратного вызова, слабая обработка ошибок                                |
| Обещание             | Сборный, цепной          | Подробный для последовательной логики                                       |
| асинхронный/ожидание | Читабельный, `try/catch` | Легкая последовательная ловушка; потребности `Promise.all` для параллелизма |

**Examples:**

```js
// Promise chain
getUser(id)
  .then((user) => getPosts(user.id))
  .then((posts) => render(posts))
  .catch(console.error);

// async/await equivalent
try {
  const user = await getUser(id);
  const posts = await getPosts(user.id);
  render(posts);
} catch (err) {
  console.error(err);
}
```

**Sources:** [javascript.info/async](https://javascript.info/async)

## Promises

<details>
  <summary>Promise basics</summary>

### Promise

**Definition:** Обещание — это объект, представляющий конечный результат асинхронной операции. Он всегда находится в одном из трех состояний: `pending`, `fulfilled`, or `rejected`. Однажды заселенное государство не может измениться.

**How it works:**

- Создано с `new Promise((resolve, reject) => { ... })` или статические помощники (`Promise.resolve`, и т. д.).
- Исполнитель работает **синхронно**; `resolve`/`reject` выполнить обещание один раз (игнорируется при повторном вызове).
- `.then(onFulfilled, onRejected)` планирует обработчики как **микрозадачи**, когда обещание выполняется.
- `.catch(fn)` is `.then(undefined, fn)` — ловит отказы и вбрасывает предварительные `.then`.
- `.finally(fn)` работает при расчете независимо от результата; не получает значения; возвращает новое обещание.
- `await` и `.then` возвращать связанные обещания.

| Метод                            | Цель                                       |
| -------------------------------- | ------------------------------------------ |
| `.then(onFulfilled, onRejected)` | Обрабатывать успех или неудачу             |
| `.catch(onRejected)`             | Обработка отказа                           |
| `.finally(onFinally)`            | Запустить очистку независимо от результата |

**When to use:**

| Используйте обещания              | Использовать `async/await` вместо этого |
| --------------------------------- | --------------------------------------- |
| Обертывание API обратного вызова  | Последовательная бизнес-логика          |
| Публичные API библиотеки          | `try/catch` блоки ошибок                |
| Параллельно `Promise.all` партии  | Читабельный поток управления            |
| Когда вам нужно `.finally` уборка | Циклы с условными операторами           |

#### Common pitfalls

- Не возвращая обещание от `.then` - следующий `.then` получает `undefined`.
- Использование второго аргумента `.then` вместо `.catch` — пропускает броски в обработчике выполнения.
- `new Promise` антишаблон, когда значение уже существует — используйте `Promise.resolve(x)`.

**Pluses and minuses:**

| +                                         | −                                                                                   |
| ----------------------------------------- | ----------------------------------------------------------------------------------- |
| Сборные цепочки                           | Подробный против `async/await`                                                      |
| Ясно устоявшаяся государственная машина   | Ошибки исполнителя требуют внешнего `try/catch` or `.catch` о возвращенном обещании |
| `Promise.all` для параллелизма            | Забывчивость `return` in `.then` разрывает цепь                                     |
| Универсальное взаимодействие (`thenable`) | `.then` второй аргумент используется редко — предпочитаю `.catch`                   |

**Examples:**

```js
const promise = new Promise((resolve, reject) => {
  setTimeout(() => resolve("I'm a Promise!"), 500);
});

promise
  .then((value) => console.log(value))
  .catch((err) => console.error(err))
  .finally(() => console.log("done"));
```

**Sources:** [Обещание MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise) · [javascript.info/promise-basics](https://javascript.info/promise-basics)

</details>

### Promise states & chaining

**Definition:** Обещание подчиняется строгим правилам: оно должно раскрывать `.then` метод; оно начинается `pending` и однажды соглашается `fulfilled` or `rejected`; установленное значение является неизменным.

**How it works:**

- **ожидание** → операция выполняется; обработчики стоят в очереди до урегулирования.
- **выполнено** → `resolve(value)` называется; `.then` обработчики получают `value`.
- **отклонено** → `reject(reason)` или добавьте исполнителя; `.catch` обработчики получают `reason`.
- Каждый `.then`/`.catch`/`.finally` возвращает **новое** обещание — включает цепочку.
- Возвращаемое значение обработчика становится выполнением следующего обещания; выброшенная ошибка становится отклонением.
- Возврат промиса из обработчика **сглаживает** — его ждет следующий промис.

| Государство | Значение                        |
| ----------- | ------------------------------- |
| `pending`   | Исходный; операция продолжается |
| `fulfilled` | Завершено успешно               |
| `rejected`  | Ошибка по причине               |

**When to use:**

| Ситуация                       | Узор                                                                |
| ------------------------------ | ------------------------------------------------------------------- |
| Многошаговые зависимые запросы | `.then` цепной или последовательный `await`                         |
| Преобразовать результат за шаг | `return` сопоставленное значение из каждого `.then`                 |
| Восстановление после ошибки    | `.catch(() => fallback)` затем продолжить цепочку                   |
| Остановить цепочку при ошибке  | Пусть отторжение распространяется – никакого выздоровления `.catch` |

#### Common pitfalls

- Вбрасывание `.then` без `.catch` — необработанный отказ.
- `async` обработчик в `.then` возвращает Promise — должен возвращать его явно, если он вложен.
- Предполагая `.then` запускается немедленно — всегда микрозадача после текущего кода синхронизации.

**Pluses and minuses:**

| +                                                                  | −                                                                  |
| ------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Неизменная установленная стоимость — ее можно безопасно передавать | Невозможно отменить встроенный Promise (используйте `AbortSignal`) |
| Цепочка четко кодирует конвейер                                    | Длинные цепочки сложно отладить без меток                          |
| Ошибки распространяются на ближайшие `.catch`                      | Проглотил ошибки, если `.catch` отсутствует в конце                |

**Examples:**

```js
Promise.resolve(1)
  .then((x) => x + 1)
  .then((x) => {
    throw new Error("fail");
  })
  .catch(() => 42)
  .then(console.log);
// 42
```

**Sources:** [javascript.info/promise-chaining](https://javascript.info/promise-chaining)

</details>

<details>

### Promise static methods

**Definition:** Методы класса для выполнения нескольких обещаний с различной семантикой завершения.

**How it works:**

- `Promise.all(iterable)` — ждет всех; отклоняет при первом отказе; результаты в порядке.
- `Promise.allSettled(iterable)` — ждет всех; никогда не отвергает; `{ status, value|reason }[]`.
- `Promise.race(iterable)` — рассчитывается, когда **первое** обещание выполнено (выполнено или отклонено).
- `Promise.any(iterable)` — выполняется при первом успехе; отвергает `AggregateError` если все потерпит неудачу.
- Неперспективные элементы, обернутые `Promise.resolve`.
- Пустая итерация: `all` → `[]`, `race` → ожидание навсегда, `any` → `AggregateError`.

| Метод                | Решается, когда    | Отклоняет, когда  |
| -------------------- | ------------------ | ----------------- |
| `Promise.all`        | все выполнить      | сначала отклонить |
| `Promise.race`       | сначала поселиться | сначала отклонить |
| `Promise.allSettled` | все улажено        | никогда           |
| `Promise.any`        | сначала выполнить  | все отвергают     |

**When to use:**

| Метод                | Используйте, когда                                                    |
| -------------------- | --------------------------------------------------------------------- |
| `Promise.all`        | Требуются все результаты (например, пользователь + сообщения)         |
| `Promise.allSettled` | Пакет, в котором некоторые могут дать сбой (статус массовой загрузки) |
| `Promise.race`       | Обертка тайм-аута, побеждает самый быстрый CDN                        |
| `Promise.any`        | Первое успешное зеркало; резервный пул                                |

#### Common pitfalls

- `Promise.all` с последовательным `await` внутри цикла — используйте `map` + `all` вместо.
- `race` по таймауту — проигрышный запрос все еще выполняется; отменить с помощью `AbortController`.
- `allSettled` Порядок результатов соответствует порядку ввода, а не порядку завершения.

**Pluses and minuses:**

| +                                                | −                                                           |
| ------------------------------------------------ | ----------------------------------------------------------- |
| `all` — быстрый провал, упорядоченные результаты | Одна ошибка приводит к потере всех результатов              |
| `allSettled` — проверять каждый результат        | Более подробный анализ результатов                          |
| `race` — тайм-ауты, первый ответчик              | Победа первого отказа — не всегда желательно                |
| `any` — резервные зеркала/CDN                    | Все отказоустойчивые потребности `AggregateError` обработка |

**Examples:**

```js
var p1 = new Promise((resolve) => setTimeout(() => resolve("one"), 500));
var p2 = new Promise((resolve) => setTimeout(() => resolve("two"), 100));

Promise.race([p1, p2]).then(console.log); // "two"

// Timeout pattern
const timeout = (ms) =>
  new Promise((_, reject) =>
    setTimeout(() => reject(new Error("timeout")), ms),
  );
await Promise.race([fetch("/api"), timeout(5000)]);
```

**Sources:** [javascript.info/promise-api](https://javascript.info/promise-api)

### Promisification

**Definition:** Обертывание API в стиле обратного вызова (`fn(arg, (err, result) => ...)`) в функцию, возвращающую обещание.

**How it works:**

- Обернуть оригинальную функцию; возвращаться `new Promise((resolve, reject) => ...)`.
- Вызов оригинала с аргументами + обратный вызов; при обратном вызове с ошибкой: `err ? reject(err) : resolve(result)`.
- Узел обеспечивает `util.promisify(fn)` для стандартных функций, ориентированных на ошибку.
- Теряет семантику множественного обратного вызова (например. `progress` обратные вызовы), если не расширены.
- Результат можно скомпоновать с `await` и `Promise.all`.

**When to use:**

| Ситуация                                          | Подход                                          |
| ------------------------------------------------- | ----------------------------------------------- |
| Устаревший узел `fs.*`                            | `util.promisify` or `fs.promises`               |
| Старый API браузера                               | Ручная упаковка обещаний                        |
| Библиотека с обратным вызовом и версиями обещаний | Используйте обещанную версию, если она доступна |
| Завершение пользовательского события              | `new Promise` + `once` слушатель                |

#### Common pitfalls

- Многообещающая функция, которая вызывает обратный вызов несколько раз — подсчитывается только первый раз.
- Неправильная подпись обратного вызова (только успех или сначала ошибка).
- Не является обязательным `this` для методов — используйте `promisify(fs.readFile.bind(fs))` or `fs.promises`.

**Pluses and minuses:**

| +                                                     | −                                                          |
| ----------------------------------------------------- | ---------------------------------------------------------- |
| Единый асинхронный стиль                              | Теряет семантику множественного обратного вызова           |
| Компонуется с `await`                                 | Необходимо правильно обрабатывать соглашение об ошибках    |
| Одноразовая упаковка, повторное использование повсюду | Некоторые API используют обратные вызовы только для успеха |

**Examples:**

```js
function promisify(fn) {
  return function (...args) {
    return new Promise((resolve, reject) => {
      fn(...args, (err, result) => {
        if (err) reject(err);
        else resolve(result);
      });
    });
  };
}

// Node: util.promisify(fs.readFile)
const readFile = promisify(fs.readFile);
const data = await readFile("file.txt", "utf8");
```

**Sources:** [javascript.info/promisify](https://javascript.info/promisify)

</details>

<details>
  <summary>try...catch with promises</summary>

### try...catch with promises

**Definition:** `try...catch` выполняет синхронные броски; с `async/await` он также перехватывает отклоненные обещания. С сырыми обещаниями используйте `.catch()` или конечный `.catch` на цепи.

**How it works:**

- `try/catch` вокруг `await` уловы обещают отказы, как если бы это были броски.
- Синхронизация внутри `async` функция → отклоненное обещание возвращается вызывающему абоненту.
- `.catch` по цепочке обрабатывает отказы от любых предыдущих `.then`.
- `.finally` запускается после успеха или неудачи — хорошо для очистки (закрытия соединений).
- Необработанный отказ: отклоненное обещание без `.catch` и нет `await` в попытке/пойме.

| Подход                | Лучшее для                                       |
| --------------------- | ------------------------------------------------ |
| `.catch()` на цепочке | Обещание трубопроводов                           |
| `try/catch` + `await` | `async` функции                                  |
| `.finally()`          | Очистка как на пути успеха, так и на пути неудач |

**When to use:**

| Ситуация                               | Узор                                  |
| -------------------------------------- | ------------------------------------- |
| Одна асинхронная функция               | `try { await ... } catch (e) { ... }` |
| Обещание трубопровода                  | тянущийся `.catch(console.error)`     |
| Всегда закрывать ресурс                | `try { ... } finally { cleanup() }`   |
| Повторный бросок после входа в систему | `catch (e) { log(e); throw e; }`      |

#### Common pitfalls

- `try/catch` без `await` — `fetch()` возвраты в ожидании обещания; ошибки не пойманы.
- Пустой `catch` проглатывание ошибок — скрывает ошибки.
- `return` in `catch` без повторного броска — вызывающий абонент видит успех с `undefined`.

**Pluses and minuses:**

| +                                          | −                                                       |
| ------------------------------------------ | ------------------------------------------------------- |
| `try/catch` читается как код синхронизации | `try/catch` за `await` многословен                      |
| `.catch` в конце цепочки — один обработчик | Легко забыть обработчик по принципу «выстрелил и забыл» |
| `.finally` для общей уборки                | `.finally` не подавляет неприятие                       |

**Examples:**

```js
const processData = async () => {
  try {
    const data = await fetchData();
    console.log("Processed:", data);
  } catch (error) {
    console.error("Error:", error);
  }
};

// Promise chain equivalent
fetchData()
  .then((data) => console.log("Processed:", data))
  .catch((error) => console.error("Error:", error));
```

**Sources:** [javascript.info/try-catch](https://javascript.info/try-catch)

</details>

<a name="async-await"></a>

## Async / await

<details>
  <summary>async/await basics</summary>

### async/await

**Definition:** `async` отмечает функцию, которая всегда возвращает обещание. `await` приостанавливает выполнение внутри этой функции до тех пор, пока не будет выполнено обещание, а затем возобновляется со значением.

**How it works:**

- `async function f() { ... }` — всегда возвращается `Promise`; `return x` → `Promise.resolve(x)`; `throw` → отказ.
- `await promise` — приостанавливает **только** эту асинхронную функцию; другой код в потоке продолжается.
- После завершения ожидания выполнение возобновляется как **микрозадача**.
- `await` работает с thenables, а не только с собственными обещаниями.
- Высший уровень `await` разрешено в модулях ES — см. [Await верхнего уровня](#top-level-await).

**When to use:**

| Используйте async/await            | Используйте необработанные обещания     |
| ---------------------------------- | --------------------------------------- |
| По умолчанию для логики приложения | Библиотека возвращает имущество         |
| Последовательные шаги с ветвями    | `Promise.race` остроты                  |
| `try/catch` обработка ошибок       | Взаимодействие в стиле обратного вызова |

#### Common pitfalls

- Отсутствующий `await` — `const x = fetch()` это обещание, а не данные.
- `async` IIFE забыли — await верхнего уровня только в модулях.
- `forEach` с `async` обратный вызов — не ожидает итераций.

**Pluses and minuses:**

| +                                       | −                                                                          |
| --------------------------------------- | -------------------------------------------------------------------------- |
| Читаемый последовательный код           | Забывчивость `await` молча ломает логику                                   |
| Родной `try/catch`                      | Последовательные циклы выполняются медленно без пакетной обработки         |
| Знакомый поток управления (`if`, `for`) | Отладка асинхронных стеков может оказаться сложнее                         |
| Взаимодействие с обещаниями             | Невозможно использовать `await` в не-`async` функции (кроме TLA в модулях) |

**Examples:**

```js
async function load() {
  const res = await fetch("/api/data");
  if (!res.ok) throw new Error(res.statusText);
  return res.json();
}

load().then((data) => console.log(data));
```

**Sources:** [javascript.info/async-await](https://javascript.info/async-await)

</details>

<details>
  <summary>Parallel vs sequential</summary>

### Parallel vs sequential

**Definition:** Последовательный `await` запускает задачи одну за другой; параллельное выполнение сначала запускает все задачи, а затем ожидает их вместе.

**How it works:**

- `const a = await fetchA(); const b = await fetchB();` — Б начинается только после завершения А.
- `const [a, b] = await Promise.all([fetchA(), fetchB()]);` — оба запускаются сразу; подожди обоих.
- Ключ: вызов функций **before** `await` приступить к работе — `const p = fetchA(); await p` является параллельным.
- `for await` и последовательный `await` в цикле — по одному за раз.
- Использовать `Promise.all` для независимого ввода/вывода; последовательный, когда каждый шаг требует предыдущего результата.

**When to use:**

| Узор                     | Когда                                            |
| ------------------------ | ------------------------------------------------ |
| Последовательный `await` | Шагу Б нужен результат шага А                    |
| `Promise.all`            | Независимые выборки, все необходимое             |
| `Promise.allSettled`     | Независимо, хорошо, если что-то потерпит неудачу |
| `map` + `all`            | N параллельных товаров с сохранением порядка     |

#### Common pitfalls

- `await` внутри `for` цикл — N × задержка; партия с `Promise.all`.
- Запуск обещаний, но ожидание одно за другим — по-прежнему последовательно, если второе ожидание ожидает завершения первого только после того, как первое началось поздно.
- `Promise.all` когда один сбой не должен отменять другие — используйте `allSettled`.

**Pluses and minuses:**

| +                                                            | −                                                                      |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Последовательный: простые зависимости                        | Последовательный: сумма задержек                                       |
| Параллельно: минимальная задержка для самостоятельной работы | Параллельно: все потерпит неудачу, если `Promise.all` и один отвергает |
| `allSettled` для частичного успеха                           | Больше памяти — все запросы в работе                                   |

**Examples:**

```js
// Sequential — B waits for A
const a = await fetchA();
const b = await fetchB();

// Parallel — start both, await together
const [a, b] = await Promise.all([fetchA(), fetchB()]);

// Parallel in loop
const results = await Promise.all(ids.map((id) => fetchItem(id)));
```

**Sources:** [javascript.info/promise-api](https://javascript.info/promise-api)

</details>

<details>
  <summary>Async iterators and for await...of</summary>

### Async iterators and for await...of

**Definition:** Объекты с `[Symbol.asyncIterator]` давать обещания; `for await...of` потребляет их последовательно.

**How it works:**

- Асинхронные итеративные разоблачения `asyncIterator()` возвращение `{ next() → Promise<{ value, done }> }`.
- `for await (const x of asyncIterable)` — ждет каждого `next()` прежде чем продолжить.
- Асинхронные генераторы: `async function* gen() { yield await fetch(...); }`.
- Работает с потоками (читаемыми узлами), API с разбивкой на страницы, веб-потоками. `ReadableStream`.
- Должно быть внутри `async` функция или модуль верхнего уровня (с TLA).

**When to use:**

| Использовать `for await...of`                             | Использовать `Promise.all`                     |
| --------------------------------------------------------- | ---------------------------------------------- |
| Файловые/сетевые потоки                                   | Независимые параллельные запросы               |
| API с разбивкой на страницы (страница зависит от курсора) | Исправлен список известных URL-адресов         |
| Поток сообщений WebSocket                                 | Пакетная обработка с ограничением параллелизма |

#### Common pitfalls

- С использованием `for await` на неасинхронной итерации — ошибка времени выполнения.
- Не прерывание цикла при ошибке — весь поток завершается сбоем, если не обрабатываться за итерацию.
- Параллельно с `for await` — неправильный инструмент; используйте одновременных рабочих + очередь.

**Pluses and minuses:**

| +                                                | −                                                       |
| ------------------------------------------------ | ------------------------------------------------------- |
| Потоковая передача больших асинхронных данных    | Последовательный — медленнее параллельного              |
| Чистый синтаксис против руководства `.then` цепи | Требуется контекст асинхронной функции                  |
| Противодавление с потоками (Узел)                | Необходимость обработки ошибок `try/catch` вокруг петли |
| Пагинация с эффективным использованием памяти    | Не для несвязанных параллельных выборок                 |

**Examples:**

```js
async function* generateIds() {
  for (let i = 0; i < 3; i++) {
    await new Promise((r) => setTimeout(r, 100));
    yield i;
  }
}

(async () => {
  for await (const id of generateIds()) {
    console.log(id);
  }
})();
```

**Sources:** [javascript.info/async-iterators-generators](https://javascript.info/async-iterators-generators)

</details>

<details>
  <summary>AbortController</summary>

### AbortController

**Definition:** `AbortController` обеспечивает `signal` отменить `fetch` и другие асинхронные операции.

**How it works:**

- `const ac = new AbortController();` — `ac.signal` это `AbortSignal`.
- Проходить `{ signal: ac.signal }` to `fetch` (и другие API, которые его поддерживают).
- `ac.abort()` — прерывает связанные операции; `fetch` отвергает с `AbortError`.
- `signal.aborted` и `signal.reason` проверить состояние.
- `AbortSignal.timeout(ms)` — сокращение для прерывания по тайм-ауту (современные браузеры/Node).
- Составление: один сигнал может прервать несколько выборок; Реагировать на вызовы очистки `abort()` при размонтировании.

**When to use:**

| Ситуация            | Узор                                                 |
| ------------------- | ---------------------------------------------------- |
| Пользователь уходит | `abort()` in `useEffect` уборка                      |
| Отказ от поиска     | Отменить предыдущий запрос при новом нажатии клавиши |
| Запросить тайм-аут  | `AbortSignal.timeout(5000)` или ручной таймер        |
| Победитель гонки    | Прервать проигравших после `Promise.race`            |

#### Common pitfalls

- Лечение `AbortError` как настоящая неудача — часто ожидаемая в навигации.
- Не прерывать размонтирование компонента — setState выдает предупреждение о размонтированном компоненте.
- Контроллер одноразового использования — создайте новый по запросу.

**Pluses and minuses:**

| +                                                                        | −                                                                    |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Отменяет запросы в полете                                                | Не все API поддерживают `AbortSignal`                                |
| Компонуемый с таймаутами                                                 | Необходимо подключить сигнал к каждому вызову                        |
| Предотвращает обновление пользовательского интерфейса устаревших ответов | Прерванная выборка по-прежнему отклоняется — дескриптор `AbortError` |
| Стандарт в экосистеме выборки                                            | Старые библиотеки требуют отмены вручную                             |

**Examples:**

```js
const controller = new AbortController();
const timeout = setTimeout(() => controller.abort(), 5000);

try {
  const res = await fetch("/api/data", { signal: controller.signal });
  clearTimeout(timeout);
  const data = await res.json();
} catch (err) {
  if (err.name === "AbortError") console.log("Request aborted");
  else throw err;
}
```

**Thoughts:** Прерывание устаревшего поиска `fetch` уменьшает работу основного потока и гонки — помогает **INP**. [6_web_api.md — INP](./6_web_api_security.md#inp-interaction-to-next-paint).

**Sources:** [javascript.info/fetch-abort](https://javascript.info/fetch-abort) — полные сведения о выборке в [HTTP — AbortController & FormData](./6_web_api_http.md#fetch-api-abortcontroller-and-formdata)

</details>

## Related APIs

<details>
  <summary>Timers</summary>

### Timers

**Definition:** `setTimeout` выполняет обратный вызов один раз после задержки; `setInterval` повторяется через фиксированный интервал. Оба планируют **макрозадачи**. `clearTimeout` / `clearInterval` отменить ожидающие обратные вызовы.

**How it works:**

- `setTimeout(fn, ms)` — минимальная задержка `ms`; фактическая задержка ≥ `ms` (ограничено до ~4 мс в браузерах при глубине вложенности ≥5).
- `setInterval(fn, ms)` — повторяется до тех пор, пока `clearInterval`; интервал включает в себя время обратного вызова — реальный разрыв между запусками может сокращаться или суммироваться.
- **Вложенный `setTimeout`** — запланируйте следующий запуск в **конце** текущего: гарантирует минимальную паузу между финишами; можно регулировать задержку (отсрочку) на итерацию.
- Возвращаемое значение – числовой идентификатор (браузер) или `Timeout` объект (Узел) — перейти к `clear*`.
- Обратный вызов выполняется как макрозадача — после текущего кода синхронизации и всех микрозадач.
- `setTimeout(fn, 0)` переходит к следующему ходу макрозадачи — не немедленно.
- Планировщик удерживает ссылку на обратный вызов до тех пор, пока он не запустится/не будет очищен — отмените неиспользуемые таймеры, чтобы освободить закрытую память.

| API                    | Поведение                                                 |
| ---------------------- | --------------------------------------------------------- |
| `setTimeout(fn, ms)`   | Запустить один раз после `ms` (минимум ~4 мс в браузерах) |
| `setInterval(fn, ms)`  | Повторяйте каждые `ms` пока не будет очищено              |
| Вложенный `setTimeout` | Следующий тик запланирован после предыдущего завершения   |
| `clearTimeout(id)`     | Отменить `setTimeout`                                     |
| `clearInterval(id)`    | Отменить `setInterval`                                    |

**When to use:**

| Использование                                      | Вместо этого предпочитаю                          |
| -------------------------------------------------- | ------------------------------------------------- |
| Устранение дребезга/дроссель                       | `requestAnimationFrame` для визуальных обновлений |
| Отложенное обновление пользовательского интерфейса | `queueMicrotask` для макроса перед следующим      |
| Опрос                                              | WebSocket/SSE для отправки с сервера              |
| `sleep` в асинхронном коде                         | `await new Promise(r => setTimeout(r, ms))`       |

#### Common pitfalls

- `this` в обратном вызове таймера — используйте функцию стрелки или `.bind`.
- Забывчивость `clearInterval` об изменении маршрута SPA — утечки и устаревшие обновления.
- Предполагая точное время — нагрузка цикла событий добавляет дрожание.
- Остаток `setInterval` (опрос, автосохранение) регулярно крадет основной поток — хуже для **INP**, чем одноразовый `setTimeout`. [6_web_api.md — INP](./6_web_api_security.md#inp-interaction-to-next-paint).

**Pluses and minuses:**

| +                                                | −                                                             |
| ------------------------------------------------ | ------------------------------------------------------------- |
| Простая отсрочка и планирование                  | Неточно для анимации (используйте `rAF`)                      |
| Работает везде                                   | `setInterval` складывается, если обработчик работает медленно |
| Хорошо подходит для устранения дребезга/дросселя | Фиксация минимальной задержки удивляет вложенными таймерами   |
| Макрозадача — позволяет рисовать между           | В середине периода отмены обратного вызова в полете не будет  |

**Examples:**

```js
const id = setTimeout(() => console.log("later"), 1000);
clearTimeout(id);

const interval = setInterval(() => tick(), 500);
clearInterval(interval);

// Nested setTimeout — delay between *ends*, optional backoff
let delay = 1000;
let timerId = setTimeout(function tick() {
  // work...
  delay = overloaded ? delay * 2 : 1000;
  timerId = setTimeout(tick, delay);
}, delay);

// Async sleep helper
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
await sleep(1000);
```

**Sources:** [javascript.info/settimeout-setinterval](https://javascript.info/settimeout-setinterval)

</details>

<details>
  <summary>requestIdleCallback</summary>

### requestIdleCallback

**Definition:** API браузера, который запускает обратный вызов во время **периода простоя** (после работы с макетом/рисованием, когда у цикла событий есть свободное время). Это **не** микрозадача Promise и **не** `requestAnimationFrame`.

**How it works:**

- `requestIdleCallback(cb, { timeout })` — `cb` получает `IdleDeadline`: `timeRemaining()` (мс осталось в этом незанятом фрагменте) и `didTimeout`.
- Уступайте, когда `timeRemaining()` достигает ~0, чтобы браузер мог рисовать. Если ты пройдешь `timeout`, обратный вызов по-прежнему выполняется по истечении крайнего срока (`didTimeout === true`) даже если вкладка была занята — `timeRemaining()` тогда ~0.
- Без `timeout`, занятая страница **возможно, никогда** не позвонит вам.
- Недоступно в Node. Предпочитать `scheduler.yield()` / работа по частям, если вам нужна более широкая поддержка; РАФ для визуальных рамок.

**When to use:** Отложить некритичный JS; контрастирует с rAF (должен выполняться перед покраской) и микрозадачами (выполняется перед следующей макрозадачой **и** может задерживать покраску, если она никогда не истощается).

**Pluses and minuses:**

| +                                                             | −                                                                                               |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Низкоприоритетная работа (аналитика, предварительная выборка) | Можно голодать без `timeout`                                                                    |
| Сотрудничает с рендерингом                                    | Не является заменой веб-работников при выполнении задач с интенсивным использованием процессора |

**Examples:**

```js
requestIdleCallback(
  (deadline) => {
    while (deadline.timeRemaining() > 0 && queue.length) {
      work(queue.pop());
    }
  },
  { timeout: 2000 },
);
```

**Thoughts:** _В режиме ожидания работа выполняется, когда браузер не рисует; бесконечная очередь микрозадач никогда не достигает состояния простоя или отрисовки._

**Sources:** [MDN — requestIdleCallback](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback) · [IdleDeadline](https://developer.mozilla.org/en-US/docs/Web/API/IdleDeadline)

</details>

<a name="queuemicrotask-processnexttick"></a>

## queueMicrotask & process.nextTick

<details>
  <summary>queueMicrotask & process.nextTick (Node)</summary>

### queueMicrotask & process.nextTick

**Definition:** `queueMicrotask(fn)` планирует микрозадачу в браузере и Node. узла `process.nextTick(fn)` планирует обратный вызов с **более высоким приоритетом**, чем у других микрозадач.

**How it works:**

- `queueMicrotask(callback)` — запускается после текущего кода синхронизации, в очереди микрозадач, перед следующей макрозадачой.
- То же семейство очередей, что и `Promise.then` реакции.
- Узел `process.nextTick(callback)` — отдельная очередь очищается **перед** микрозадачами обещаний и перед вводом/выводом.
- Предназначен для отсрочки работы без задержки ввода/вывода; злоупотребление `nextTick` может истощить цикл событий.
- Браузер: `queueMicrotask` on `globalThis` or `window`.

| API                | Окружающая среда | Приоритет                 |
| ------------------ | ---------------- | ------------------------- |
| `queueMicrotask`   | Браузер, Узел    | Стандартная микрозадача   |
| `Promise.then`     | Оба              | Стандартная микрозадача   |
| `process.nextTick` | Только узел      | Над другими микрозадачами |

**When to use:**

| Использование                                      | Избегайте                                                   |
| -------------------------------------------------- | ----------------------------------------------------------- |
| Запускать после обновления DOM, перед отрисовкой   | Длительные циклы в микрозадачах                             |
| Узел: отложить обратный вызов до фазы ввода-вывода | `nextTick` рекурсия вместо `setImmediate` для тяжелых работ |
| Polyfill обещает время реакции                     | Замена `Promise.then` для удобства чтения                   |

#### Common pitfalls

- Бесконечный `process.nextTick` цепочка в узле — блокирует ввод-вывод на неопределенный срок.
- Предполагая `queueMicrotask` бежит раньше `Promise.then` — та же очередь, порядок записи имеет значение.
- С использованием `setTimeout(0)` когда микрозадачи достаточно — добавляет ненужную задержку макрозадачи.

**Pluses and minuses:**

| +                                                          | −                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------- |
| Явное планирование микрозадач                              | Легко заморозить макрозадачи, если они рекурсивны       |
| `nextTick` выполняется перед обработчиками обещаний в Node | `nextTick` недоступно в браузере                        |
| Прервите работу синхронизации без `setTimeout(0)`          | Чрезмерное использование блоков ввода-вывода и таймеров |
| Предсказуемый порядок на уровне микрозадач                 | Различия между узлом и браузером                        |

**Examples:**

```js
console.log("sync");

queueMicrotask(() => console.log("microtask"));

Promise.resolve().then(() => console.log("promise microtask"));

// Node only:
// process.nextTick(() => console.log('nextTick')); // runs before promise microtask

setTimeout(() => console.log("macrotask"), 0);

// sync → nextTick (Node) → microtask → promise microtask → macrotask
```

**Sources:** [MDN QueueMicrotask](https://developer.mozilla.org/en-US/docs/Web/API/Window/queueMicrotask) · [javascript.info/microtask-queue](https://javascript.info/microtask-queue) · [Node process.nextTick](https://nodejs.org/api/process.html#processnexttickcallback-args) · [8_nodejs.md](./8_nodejs.md)

</details>

<a name="unhandled-promise-rejections"></a>

## Unhandled promise rejections

<details>
  <summary>Unhandled promise rejections</summary>

### Unhandled promise rejections

**Definition:** Отклоненное обещание без `.catch` обработчик и нет `await` внутри `try/catch` **необработанный**. Среды выполнения создают события и могут завершить процесс (узел) или войти в консоль (браузер).

**How it works:**

- Отклонение отслеживается, когда обещание отклонено, а обработчик еще не прикреплен.
- Если обработчик прикреплен позже (тот же тик или поворот микрозадачи в некоторых движках), все равно может считаться обработанным.
- Браузер: `window` событие `unhandledrejection`; `event.promise`, `event.reason`.
- `event.preventDefault()` — отключить ведение журнала по умолчанию (браузер).
- Узел: `process.on('unhandledRejection', (reason, promise) => ...)`.
- Узел 15+: необработанный отказ по умолчанию может привести к сбою процесса.
- `rejectionhandled` / `handled` события, когда обработчик добавлен поздно.

| Окружающая среда          | Поведение по умолчанию                         |
| ------------------------- | ---------------------------------------------- |
| Браузер                   | `console.error` + `unhandledrejection` событие |
| Узел (современный)        | Предупреждение или выход из процесса           |
| `async` главный без улова | Необработанный отказ по возвращенному обещанию |

**When to use:**

| Ситуация                       | Исправить                                                               |
| ------------------------------ | ----------------------------------------------------------------------- |
| `fetch()` без улова            | Добавлять `.catch` or `try/catch` с `await`                             |
| `async` IIFE                   | `.catch` по обещанию: `(async () => {})().catch(...)`                   |
| Экспресс-обработчики маршрутов | Обертывание в промежуточное программное обеспечение try/catch или error |
| Глобальный мониторинг          | `unhandledrejection` слушатель → сообщить Sentry                        |

#### Common pitfalls

- `async` Возвращаемое значение функции игнорируется — отказ не обрабатывается на месте вызова.
- `.then(fn)` без `.catch` — отказ в `fn` распространяется, но внешнему обещанию нужен обработчик.
- Проглатывание глобального обработчика без устранения основной причины.

**Pluses and minuses:**

| +                                                     | −                                                       |
| ----------------------------------------------------- | ------------------------------------------------------- |
| Поверхности забыли пути ошибок                        | Может привести к сбою производства, если его не поймать |
| Глобальные обработчики для журналирования/мониторинга | Легко пропустить обещания «выстрелил и забыл»           |
| Вызывает явную стратегию ошибок                       | Трассировки асинхронного стека могут быть нечеткими     |

**Examples:**

```js
// Unhandled — logs error / may crash Node
Promise.reject(new Error("oops"));

// Handled
Promise.reject(new Error("oops")).catch(console.error);

// async without catch
async function main() {
  throw new Error("fail");
}
main(); // unhandled
main().catch(console.error); // handled

// Browser global handler
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled:", event.reason);
  event.preventDefault();
});
```

**Sources:** [MDN unhandledrejection](https://developer.mozilla.org/en-US/docs/Web/API/Window/unhandledrejection_event) · [javascript.info/promise-error-handling](https://javascript.info/promise-error-handling) · [javascript.info/microtask-queue](https://javascript.info/microtask-queue) · [Узел unhandledRejection](https://nodejs.org/api/process.html#event-unhandledrejection)

</details>

<a name="top-level-await"></a>

## Top-level await

<details>
  <summary>Top-level await (brief)</summary>

### Top-level await

**Definition:** `await` на верхнем уровне модуля (не внутри `async` функция) — приостанавливает **вычисление модуля** до тех пор, пока не будет выполнено обещание. Функция ES2022 только для модулей ES.

**How it works:**

- Только в `.mjs` файлы или `<script type="module">` — не CommonJS, не классические скрипты.
- Граф модуля ожидает — импортеры этого модуля блокируются до завершения TLA.
- Используется для: загрузки конфигурации, инициализации WASM, условного импорта.
- Недостаток: сериализует цепочку загрузки модуля — может замедлить запуск приложения.

**When to use:**

| Хорошее применение                                    | Избегайте                                                  |
| ----------------------------------------------------- | ---------------------------------------------------------- |
| `const config = await loadConfig()` во входном модуле | Тяжелый ввод-вывод в широко импортируемом служебном модуле |
| Динамический `await import()` на основе окружения     | Замена всей отложенной загрузки на TLA                     |
| ВАСМ `await init()`                                   | ЗАО `require` контексты                                    |

#### Common pitfalls

- TLA в дереве глубоких зависимостей — непредвиденная задержка запуска.
- Использование в общем модуле, импортированном многими — узкое место.
- Классический скрипт или CJS — `SyntaxError`; используйте асинхронный IIFE или динамический импорт.

**Pluses and minuses:**

| +                              | −                                                     |
| ------------------------------ | ----------------------------------------------------- |
| Нет асинхронной оболочки IIFE  | Блокирует импорт зависимых модулей                    |
| Очистить конфигурацию/загрузку | Не в CJS без динамики `import()`                      |
| Естественно для модуля init    | Чрезмерное использование вредит параллельной загрузке |

**Examples:**

```js
// config.mjs
const res = await fetch("/api/config");
export const config = await res.json();

// app.mjs — waits for config.mjs to finish
import { config } from "./config.mjs";
console.log(config.apiUrl);
```

**Sources:** [Ожидание верхнего уровня MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/await#top_level_await) · [javascript.info/modules](https://javascript.info/modules-intro)

</details>

<a name="promisewithresolvers"></a>

## Promise.withResolvers

<details>
  <summary>Promise.withResolvers (brief)</summary>

### Promise.withResolvers

**Definition:** Возврат статического метода ES2024 `{ promise, resolve, reject }` — отделяет создание обещания от исполнителя, что полезно, когда решение/отклонение необходимо вызывать извне конструктора.

**How it works:**

- `const { promise, resolve, reject } = Promise.withResolvers();`
- Эквивалентно ручному `let resolve, reject; const promise = new Promise((res, rej) => { resolve = res; reject = rej; });`
- `resolve`/`reject` вызывается несколько раз — учитывается только первый раз (стандартные правила обещаний).
- Очистка отложенных шаблонов, мостов от событий к обещаниям, тестов.

**When to use:**

| Использование                                             | Пример                               |
| --------------------------------------------------------- | ------------------------------------ |
| Отложенный — предоставить разрешение вызывающему абоненту | Ручной контроль обещаний             |
| Событие → пообещай один раз                               | `once(emitter, 'data')` помощник     |
| Испытательные приспособления                              | Решите обещание извне тестового тела |
| Очередь с противодавлением                                | Решите, когда слот будет доступен    |

#### Common pitfalls

- Забыл позвонить `resolve` or `reject` — обещание висит навсегда.
- Вызов обоих — побеждает первый; второй проигнорирован.
- Нет встроенной поддержки в более старых версиях Node — используйте полифилл или шаблон вручную.

**Pluses and minuses:**

| +                                                        | −                                                 |
| -------------------------------------------------------- | ------------------------------------------------- |
| Избегает неуклюжего шаблона исполнителя                  | ES2024 — проверьте поддержку целевой среды        |
| Более понятные API отложенных событий/отложенных событий | Все еще нужно `.catch` для необработанных отказов |
| Та же семантика, что и `new Promise`                     | Polyfill необходим для старых сред выполнения     |

**Examples:**

```js
const { promise, resolve, reject } = Promise.withResolvers();

setTimeout(() => resolve("done"), 1000);

const result = await promise; // 'done'

// Event bridge
function once(emitter, event) {
  const { promise, resolve } = Promise.withResolvers();
  emitter.once(event, resolve);
  return promise;
}
```

**Sources:** [MDN Promise.withResolvers](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/withResolvers)

</details>

<a name="asyncawait-tasks-and-concurrency-model"></a>

<details>
  <summary>Async/await, tasks, and concurrency model</summary>

### Async/await, tasks, and concurrency model

**Definition:** В JavaScript **`async/await`** — синтаксический сахар над Promise на **одном main thread**. **Tasks** — работа в очередях: **microtasks** (promises, продолжения `async/await`) и **macrotasks** (таймеры, I/O, UI events). **Многопоточность** для JS-кода — **Web Workers** (браузер) или **`worker_threads` / `cluster`** (Node), а не параллельный `await` на main thread.

**How it works:**

| Концепт              | JS / браузер                                                          | Node.js                                          |
| -------------------- | --------------------------------------------------------------------- | ------------------------------------------------ |
| **async/await**      | `async` возвращает Promise; `await` ставит функцию на паузу, не поток | То же; продолжения — microtasks                  |
| **Task queues**      | Sync → microtasks → одна macrotask → (paint)                          | Sync → `nextTick` → microtasks → фаза event loop |
| **Параллельный I/O** | Запускать promises до `await`; `Promise.all`                          | То же + libuv thread pool для fs/crypto          |
| **Параллельный CPU** | `new Worker('worker.js')` — без DOM                                   | `worker_threads` или `cluster` для multi-core    |

Маппинг JD **«async/await, Task, многопоточность»**:

- **async/await** → async с видом sync; ошибки через `try/catch`; параллель — `Promise.all`, не цикл с `await`.
- **Task** → **microtask/macrotask**, не C# `Task` (та же идея: единица async-работы). На .NET — `Task`/`Task.Run`; в JS — очереди event loop.
- **Многопоточность** → main thread JS один; CPU — workers; I/O — async + thread pool под капотом.

**When to use:** JD про async, event-loop задачи, «почему Node однопоточный, но держит много соединений».

**Pluses and minuses:**

| Модель                   | Плюс                          | Минус                                    |
| ------------------------ | ----------------------------- | ---------------------------------------- |
| async/await              | Читаемый поток                | Легко написать случайно sequential код   |
| Microtasks               | Упорядоченные promise-реакции | Длинные цепочки блокируют timers и paint |
| Workers / worker_threads | Настоящий parallel CPU        | Нет общего DOM; overhead message passing |

**Thoughts:** Профилируйте до workers — чаще узкое место I/O или main thread, не «мало потоков». CPU loop в Node → `worker_threads`; parse/sort в браузере → Web Worker. Процессы/потоки ОС → [Processes & multitasking](./0_system_design_core.md#processes-multitasking).

**Sources:** [javascript.info/event-loop](https://javascript.info/event-loop) · [MDN async function](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function) · [MDN Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API) · [Node worker_threads](https://nodejs.org/api/worker_threads.html)

</details>
