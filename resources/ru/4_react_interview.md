### What is React and why is it used?

**Definition:**

- **React**: Современное определение (2026)

React — это декларативная компонентная библиотека для создания пользовательских интерфейсов. С 2026 года он регулируется парадигмой React 19+, в которой упор делается на параллельный рендеринг, Server Components и действия.

**How it works:**

#### Основные архитектурные концепции

#### Параллельный рендеринг & Virtual DOM

Хотя React по-прежнему использует Virtual DOM для согласования, в стандарте 2026 года особое внимание уделяется Concurrent React. Это позволяет React одновременно готовить несколько версий пользовательского интерфейса, не блокируя основной поток. Отдавая приоритет обновлениям (например, вводу ввода, а не извлечению данных), React достигает лучшего реагирования. Алгоритм сравнения поддерживает сложность O(n) за счет эвристических предположений, оптимизированных для современных браузерных движков.

#### Функциональные компоненты и крючки (стандарт)

Компоненты класса фактически являются устаревшими. В современной разработке используются исключительно функциональные компоненты.

- **Хуки**: стандартный механизм состояния (useState), побочных эффектов (useEffect) и мемоизации (useMemo, useCallback).

- **React 19 Особенности**: Введение функции использования и автоматических переходов заменило большую часть шаблонного шаблона, ранее необходимого для выборки данных.

#### Server Components (RSC)

Архитектурный разрыв между Client Components и Server Components является фундаментальным. Server Components выполняется исключительно на сервере, отправляя визуализированный пользовательский интерфейс клиенту. Это значительно уменьшает размер пакета, поскольку логика и зависимости уровня компонентов остаются на сервере, передавая браузеру нулевой килобайт JavaScript для статических частей пользовательского интерфейса.

#### Однонаправленный поток данных & Server ActionsДанные остаются строго односторонними (от родителя к ребенку). Однако Server Actions заменили традиционный шаблон получения данных через useEffect + useState. Действия позволяют вызывать серверные функции непосредственно из элементов пользовательского интерфейса (например, форм), интегрируя логику мутаций непосредственно в жизненный цикл компонента.

#### JSX: Транспиляция в React элементы

JSX остается расширением синтаксиса JavaScript. В современных инструментах сборки (например, Vite, Rspack) JSX преобразуется в вызовы среды выполнения _jsx, оптимизированные для конкретной цели рендеринга (клиент или сервер).

**When to use:**

#### Зачем использовать React в 2026 году?

- **Сначала на стороне сервера**: современные платформы (например, Next.js, Remix), построенные на React, используют React Server Components (RSC) для превосходных показателей SEO и производительности.

- **Декларативный пользовательский интерфейс**: определяя пользовательский интерфейс как функцию состояния ($UI = f(state)$), React упрощает переходы между состояниями и обеспечивает предсказуемый рендеринг.

- **Экосистема**: 2026 React является частью огромной экосистемы, включающей TanStack (запрос/маршрутизатор), Zustand (состояние) и Tailwind CSS, обеспечивающей стандартизированный путь масштабируемости корпоративного уровня.

- **Типовая безопасность**: первоклассная поддержка TypeScript теперь является базовой. Определения свойств и типы состояний строго соблюдаются в процессе сборки, что сводит к минимуму ошибки во время выполнения.

**Examples:**

#### Пример современного кода (React 19+)

Следующий фрагмент демонстрирует переход к useActionState и современным функциональным шаблонам, заменяющим устаревшее управление состоянием на основе классов.

```tsx
'use client'; // Required for interactivity in RSC environments

import { useActionState } from 'react';

// Modern approach: Server Actions integration
async function incrementCounter(previousState, formData) {
  return previousState + 1;
}

export default function Counter() {
  const [state, action, isPending] = useActionState(incrementCounter, 0);

  return (
    <form action={action}>
      <button type="submit" disabled={isPending}>
        Clicked {state} times
      </button>
    </form>
  );
}
```

- **Примечание для проверки**: пример компонента на основе классов в исходном контенте теперь считается антишаблоном. Новые проекты должны использовать функциональные шаблоны для использования возможностей Suspense и потокового SSR, присущих современному конвейеру React.

### How is React different from Angular or Vue?

**Definition:**

#### Архитектурная парадигма

- **React (19)**: библиотека для создания пользовательских интерфейсов с использованием концептуальной модели, предназначенной только для причинного декодера, для рендеринга. В нем особое внимание уделяется парадигмам функционального программирования с помощью хуков и компилятора React (автоматическое запоминание).

- **Angular (v19+)**: платформа, использующая систему реагирования на основе сигналов (заменяющую устаревшее обнаружение изменений Zone.js). Он требует строгой архитектуры внедрения зависимостей.

- **Vue.js (3.x/4)**: прогрессивная структура, использующая систему реактивности на основе прокси. Он устраняет разрыв между возможностью компоновки React и DX, основанным на шаблонах, Angular.

**How it works:**

#### Кривая обучения

- **React**: усиление в 2026 году в связи с необходимостью владения Server Components (RSC), Suspense и переходом на собственные асинхронные шаблоны.

- **Angular**: Сведено с помощью автономных компонентов, что устраняет необходимость в NgModules, которые ранее обременяли новичков.

- **Vue.js**: остается наиболее доступным благодаря Composition API и его сходству со стандартными веб-компонентами.

#### Производительность и рендеринг

- **React**: переход к рендерингу на стороне сервера (SSR) и частичной гидратации. Сложность повторных рендерингов: O(n) где n — количество узлов компонента; оптимизирован с помощью компилятора React, чтобы свести к минимуму ненужные различия.

- **Angular**: API Signals позволяет выполнять детальные обновления (O(1) обновлений компонентов), напрямую отслеживая зависимости состояний, а не анализируя все дерево компонентов.

- **Vue.js**: высокая производительность благодаря Virtual DOM в сочетании со статическим подъемом и флагами исправлений, что позволяет компилятору оптимизировать динамическое исправление контента в O(m), где m — количество динамических узлов.

#### Управление состоянием

- **React**: Канонический подход — Server Actions и React Query (TanStack) о состоянии сервера; Zustand или Контекст для состояния клиента. setState эффективно заменяется хуками useActionState и useOptimistic.

- **Angular**: RxJS теперь является необязательным в пользу сигналов, которые обеспечивают более эргономичный, императивный синтаксис для реактивного состояния без сложности потоков.

- **Vue.js**: Pinia — официальный стандарт, заменяющий Vuex. Он создан специально для TypeScript и обеспечивает модульную и легкую архитектуру магазина.

#### Шаблоны и композиция

- **React**: JSX остается отраслевым стандартом. Тенденция движется к Server Components, где логика и пользовательский интерфейс унифицированы для уменьшения размера пакета на стороне клиента.

- **Angular**: использует синтаксис шаблона со структурными директивами. Недавнее введение потока управления (@if, @for) заменило *ngIf и *ngFor для большей безопасности типов и производительности.

- **Vue.js**: однофайловые компоненты (SFC), использующие синтаксис <script setup>, являются лучшими отраслевыми практиками, предлагающими самую тесную интеграцию между логикой шаблона и реактивным состоянием.

#### Инструменты и языковая поддержка

- **React**: TypeScript встречается повсеместно. Инструментарий сильно зависит от метафреймворка (например, Next.js или Remix), который управляет LSP и конвейером сборки.

- **Angular**: Angular Language Service остается золотым стандартом поддержки IDE корпоративного уровня, обеспечивая глубокую проверку типов в шаблонах и контроллерах.

- **Vue.js**: Volar (Vue Language Tools) обеспечивает лучшую в своем классе поддержку вывода TypeScript в SFC, часто превосходя инструменты на основе JSX в точности проверки типов шаблонов.

### What is a React component?

**Definition:**

#### Определение компонента React (стандарт 2026 г.)

Компонент React — это фундаментальный строительный блок современных приложений React, инкапсулирующий логику и структуру пользовательского интерфейса. В текущей экосистеме (React 19+) компоненты определяются как функциональные компоненты. Хотя компоненты классов продолжают технически поддерживаться для совместимости с устаревшими версиями, они считаются устаревшими архитектурными шаблонами в пользу функциональных парадигм.

**How it works:**

#### Функциональные компоненты и компоненты устаревших классов

- **Функциональные компоненты**: отраслевой стандарт. Это функции JavaScript, которые принимают реквизиты в качестве аргумента и возвращают элементы пользовательского интерфейса. Они используют хуки для управления состоянием, контекстом и побочными эффектами.

- **Компоненты класса**: устаревшие структуры, использующие классы ES6, расширяющие React.Component. В настоящее время это не рекомендуется из-за увеличения размеров пакетов и сложностей, связанных с привязкой this и фрагментацией жизненного цикла.

#### JSX и современный рендеринг

- **JSX**: расширение синтаксиса JavaScript, позволяющее писать разметку пользовательского интерфейса внутри кода. Начиная с версии React 19, преобразование React.createElement в значительной степени оптимизировано современными компиляторами (такими как SWC или Babel), транслируя JSX непосредственно в высокопроизводительные виртуальные узлы DOM.

- **Server Components (RSC)**: стандарт 2026 требует, чтобы компоненты теперь различались по среде выполнения. Server Components запускаются исключительно на сервере, что позволяет уменьшить размер пакета на стороне клиента, а Client Components обеспечивает интерактивность с помощью перехватчиков.

#### Структурная согласованность

Приложения React поддерживают иерархическую древовидную структуру. Точка входа (например, createRoot) инициирует дерево, которое распространяет обновления посредством параллельного рендеринга. Это позволяет React отдавать приоритет срочным обновлениям (например, пользовательскому вводу) над промежуточными фоновыми задачами, улучшая воспринимаемую производительность.

#### Поток данных и управление состоянием

React обеспечивает однонаправленный поток данных. Данные (реквизит) передаются строго от родителя к дочернему элементу.

- **Props**: неизменяемые данные, передаваемые по дереву компонентов.

- **Состояние**: реактивные данные, управляемые через useState или useReducer. В современном React обновления состояния запускают цикл повторного рендеринга, в котором React вычисляет «разницу» между предыдущим и текущим Virtual DOM, применяя только необходимые исправления сложности (O(n)).

- **Синхронизация состояний**. Современное управление состоянием часто выходит за рамки простого детализации реквизитов и использует useContext или внешние реактивные хранилища (например, Zustand, TanStack Query) для облегчения доступа к данным между деревьями без узких мест в производительности.

#### Операции жизненного цикла: парадигма крючка

Методы жизненного цикла (comComponentDidMount и т. д.) были заменены перехватчиком useEffect и более широким API эффектов.

- **Декларативная синхронизация**: вместо императивных перехватчиков жизненного цикла современные компоненты синхронизируются с внешними системами с использованием декларативных зависимостей.

- **Suspense и переходы**: React 19+ обрабатывает состояния «загрузки» и сложную выборку данных через границы <Suspense>. Вместо того, чтобы вручную управлять статусом «монтирования», компоненты определяют свое состояние загрузки декларативно, что обеспечивает более плавную работу пользователя в приложениях с интенсивным использованием данных.

- **Примечание по архитектуре**: с 2026 года акцент сместился с «управления жизненным циклом» на «синхронизацию с внешним состоянием», при этом композиция стала приоритетнее моделей наследования, используемых в старых проектах на основе классов.

### How do you create a component in React?

**Definition:**

#### Архитектура компонентов в React (стандарты 2026 г.)

Современная разработка React строго отдает приоритет функциональным компонентам с использованием хуков. Хотя компоненты на основе классов продолжают поддерживаться для совместимости с устаревшими версиями, они считаются антишаблоном при разработке новых функций из-за более высоких затрат памяти и сложного поведения привязки this.

**How it works:**

#### Современная реализация

Функциональные компоненты используют перехватчики (например, useState, useEffect) для управления состоянием и побочными эффектами, заменяя устаревшие методы жизненного цикла (comComponentDidMount,ComponentWillUnmount).

#### Пример функционального компонента (React 19+)

- **Примечание**. Использование TypeScript является отраслевым стандартом 2026 года, обеспечивающим статическую проверку типов реквизитов и возвращаемых типов.

#### Современное управление состоянием и жизненным циклом

В 2026 году отрасль перешла от ручного управления жизненным циклом к декларативной синхронизации.

- **Хуки**: логика инкапсулируется в специальные хуки, что повышает возможность повторного использования и тестирования по сравнению с методами класса.

- **Server Components**: в целях оптимизации производительности компоненты теперь могут выполняться на сервере, что уменьшает размер пакета JavaScript на стороне клиента.

- **Параллелизм**: React 19 функций, таких как useTransition и useActionState, обеспечивают неблокирующие переходы пользовательского интерфейса и плавное управление состоянием формы.

#### Стандарты разработки: линтинг и форматирование

Современные экосистемы полагаются на ESLint (плоская конфигурация) и Biome или Prettier для обеспечения качества кода.

- **TypeScript Интеграция**: строгий режим необходим для обеспечения безопасности типов и уменьшения ошибок во время выполнения.

- **Композиция компонентов**: в архитектурных шаблонах предпочтение отдается композиции, а не наследованию. Сложное поведение абстрагируется в повторно используемые хуки, а не в компоненты высокого порядка (HOC) или реквизиты рендеринга.

- **Современное форматирование**. Руководство по стилю Airbnb в значительной степени заменено стандартами сообщества, которые подчеркивают удобочитаемость и отсутствие настроек (например, экосистемы Vite/Turbopack).

#### Резюме технического аудита

| Особенность | Унаследованный статус | Стандарт 2026 г. |
| --- | --- | --- |
| Тип компонента | На основе классов | Функциональные (Hooks) |
| Проверка типов | PropTypes | TypeScript (Interface/Types) |
| Получение данных | componentDidMount | use API / TanStack Query |
| Рендеринг | Клиентская сторона (CSR) | Server Components (RSC) / Потоковая передача |
#### Ключевые выводы

Функциональные компоненты являются стандартными; избегайте занятий по новой архитектуре.
TypeScript необходим для поддержки крупномасштабных баз кода.
Композиция — это основной механизм повторного использования логики; отдайте приоритет пользовательским хукам.
Производительность оптимизируется с помощью Server Components и функций параллельного рендеринга.

### What is JSX and why do we use it in React?

**Definition:**

#### JSX в React 19+

JSX (JavaScript XML) — это синтаксическое расширение JavaScript, которое обеспечивает декларативный способ описания структуры пользовательского интерфейса. Хотя он напоминает HTML, он представляет собой синтаксический сахар для вызовов функций, которые компилируются в дерево элементов React.

**How it works:**

#### Технические основы

- **Синтаксический сахар**: JSX не является HTML; это абстракция React.createElement (или нового преобразования jsx(), представленного в React 17+).

- **Внедрение выражений**: разработчики могут вставлять произвольные выражения JavaScript в фигурные скобки {}. Среда выполнения React обрабатывает вычисление и внедрение этих выражений в VDOM.

- **Транспиляция**: современные инструменты сборки (Vite, SWC или Babel) преобразуют JSX в стандартный JavaScript на этапе сборки. SWC, написанный на Rust, является стандартом 2026 года для высокопроизводительной транспиляции JSX.

#### Ключевые особенности

- **Декларативный пользовательский интерфейс**: согласовывая структуру кода с иерархией DOM, JSX снижает когнитивную нагрузку, сопоставляя логику компонента непосредственно с отображаемым выводом.

- **Элементы безопасности типов**: в сочетании с TypeScript JSX обеспечивает полный вывод типов для свойств компонента, гарантируя, что контракты интерфейса выполняются на этапе компиляции (O(n), сложность для проверки типа по сигнатуре компонента).

- **Композиция компонентов**: JSX упрощает композицию сложных пользовательских интерфейсов, позволяя вкладывать пользовательские компоненты так же, как стандартные встроенные элементы.

#### Преимущества современного JSX

- **Оптимизация производительности**: компилятор React 19 может выполнять расширенное запоминание и оптимизацию hoisting непосредственно в структурах JSX, сокращая накладные расходы на повторный рендеринг.

- **Опыт разработчика (DX)**: IDE (VS Code/Cursor) используют структуру JSX для обеспечения надежного IntelliSense, возможностей рефакторинга и анализа в реальном времени.

- **Уменьшенный шаблон**: JSX устраняет многословие ручных функциональных вызовов, заменяя глубоко вложенные цепочки React.createElement читаемыми декларативными деревьями.

**When to use:**

#### Зачем использовать JSX в 2026 году?

- **Согласование экосистемы**: вся экосистема React (Server Components, Suspense, Hooks) построена на JSX. Отклонение от JSX ограничивает доступ к новейшим функциям платформы и библиотекам пользовательского интерфейса, поддерживаемым сообществом.

- **Проверка во время компиляции**: JSX позволяет инструментам сборки обнаруживать отсутствующие реквизиты или недопустимые структуры тегов еще до того, как код достигнет браузера, что значительно снижает количество ошибок во время выполнения.

- **Декларативная согласованность**: JSX предоставляет единый язык для Client Components и React Server Components (RSC), обеспечивая плавный переход между рендерингом на стороне сервера и интерактивностью на стороне клиента.

- **Оптимизация инструментов**: стек сборки 2026 оптимизирован специально для JSX. Использование JSX позволяет таким инструментам, как компилятор React, статически анализировать граф компонентов, что приводит к значительному увеличению производительности во время выполнения по сравнению с подходами, не использующими JSX.

### Can you explain the virtual DOM in React?

**Definition:**

- **Virtual DOM**: 2026 Технический аудит

Virtual DOM (VDOM) остается фундаментальным архитектурным шаблоном в React, хотя его реализация значительно изменилась с появлением React Fiber и примитивов параллельного рендеринга. Он служит декларативной моделью пользовательского интерфейса, позволяя React отделить состояние пользовательского интерфейса от дорогостоящих императивных манипуляций с DOM браузера.

**How it works:**

#### Усовершенствованный механизм

- **Первоначальный рендеринг**: React создает дерево Fiber, внутреннюю структуру данных, представляющую дерево компонентов. Каждый узел Fiber соответствует компоненту React или элементу DOM, состоянию удержания, реквизитам и побочным эффектам.

- **Сверка (Алгоритм различий)**: при обновлении состояния React запускает повторный рендеринг. Он выполняет сравнение дерева между текущим деревом Fiber и новой структурой. React использует эвристический алгоритм O(n), предполагающий, что компоненты одного типа создают схожие деревья, чтобы минимизировать вычислительные затраты.

- **Оптиковолоконная архитектура**: в отличие от предыдущих версий, процесс согласования 2026 года является поэтапным и прерываемым. React может приостанавливать, прерывать или повторно использовать работу над деревом компонентов, чтобы отдать приоритет срочным обновлениям (например, пользовательскому вводу) над фоновыми задачами (например, получением данных), поддерживая высокую частоту кадров.

- **Пакетные переходы**: React 19+ использует useTransition и useDeferredValue для категоризации обновлений. Изменения состояния группируются в переходы, гарантируя, что обновления с более низким приоритетом не блокируют основной поток, эффективно отделяя логику от рендеринга.

- **Фаза фиксации**: после завершения согласования React переходит в «Фазу фиксации». Здесь он применяет изменения к фактическому DOM за один проход. Пакетируя эти операции, React сводит к минимуму перестановку макета и принудительную синхронную перекомпоновку.

- **Параллельная отрисовка**: Modern React визуализирует компоненты «одновременно», то есть в памяти можно одновременно подготовить несколько версий пользовательского интерфейса. VDOM действует как блокнот, где React экспериментирует с изменениями, прежде чем «вынести» их на экран, обеспечивая плавный переход между состояниями.

- **Декларативная абстракция DOM**: прямые манипуляции с DOM (например, document.getElementById) считаются антишаблоном. React предоставляет useRef для необходимых императивных переходов, но VDOM гарантирует, что источник истины остается в пределах жизненного цикла компонента React, предотвращая рассинхронизацию.

- **Универсальное согласование**: VDOM не зависит от платформы. В то время как React-dom обрабатывает обновления, специфичные для браузера, логика согласования повторно используется в React-native (через собственный мост) и React-three-fiber (через пользовательские средства рендеринга), обеспечивая согласованный декларативный API на всех платформах.

#### Сложность производительности

Эффективность VDOM основана на:

- **Эвристическое различие**: сокращает сравнение деревьев с O(n^3) до O(n) за счет использования ключевых свойств в списках и сравнения типов компонентов.

- **Пакетная обработка**: уменьшает постоянный коэффициент записи DOM (обычно O(DOM nodes changed)), группируя их в один цикл перекомпоновки браузера.

### How do you handle events in React?

**Definition:**

#### Обработка событий в React (стандарты 2026 г.)

React обрабатывает события через SyntheticBaseEvent, кросс-браузерную оболочку собственного события браузера. Эта абстракция обеспечивает согласованное поведение интерфейса в различных средах (DOM, React Native) и обеспечивает оптимизацию производительности.

**How it works:**

#### Синтетические события

React нормализует события, чтобы они имели одинаковые свойства во всех браузерах. Начиная с React 19, синтетические события не объединяются, что устраняет необходимость вызывать event.persist() для асинхронного доступа к свойствам событий.

#### Подписка на события

- **Соглашения об именах**: React использует CamelCase для обработчиков событий (например, onClick, onKeyDown) вместо встроенного нижнего регистра HTML (например, onclick).

- **Ссылки на функции**: в качестве обработчика событий вы передаете функцию, а не строку.

- **Современный синтаксис**: компоненты класса являются устаревшими. В современной разработке используются функциональные компоненты с крючками.

#### Современная обработка событий: функциональные компоненты

В 2026 году состояние управляется через useState. Привязка в конструкторах не требуется, а использование useCallback рекомендуется для предотвращения ненужной повторной визуализации дочерних компонентов, получающих обработчики событий.

#### Ключевые архитектурные обновления (2026 г.)

- **Делегирование событий**: React 19 продолжает прикреплять прослушиватели событий к корневому контейнеру, а не к отдельным узлам DOM, сокращая накладные расходы памяти до O(1) по сравнению с общим числом интерактивных элементов.

- **TypeScript Интеграция**: строго типизированные объекты ChangeEvent и FormEvent заменяют общий тип событий, обеспечивая безопасность типов в конвейере событий.

- **API перехода**: для несрочных обновлений (например, фильтрации большого списка) следует использовать useTransition, чтобы обработчики событий не блокировали основной поток, поддерживая сложность реагирования пользовательского интерфейса O(1) для задержки ввода.

**Examples:**

#### Пример кода: шаблон функционального компонента (React 19)

```tsx
import { useState, useCallback, FormEvent, ChangeEvent } from 'react';

export default function Form() {
  const [value, setValue] = useState<string>('');

  // useCallback optimizes performance by memoizing the handler reference
  const handleChange = useCallback((e: ChangeEvent<HTMLInputElement>) => {
    setValue(e.target.value);
  }, []);

  const handleSubmit = useCallback((e: FormEvent<HTMLFormElement>) => {
    e.preventDefault();
    console.log('Submitted:', value);
  }, [value]);

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="name-input">Name:</label>
      <input 
        id="name-input"
        type="text" 
        value={value} 
        onChange={handleChange} 
      />
      <button type="submit">Submit</button>
    </form>
  );
}
```

<summary>What are state and props in React?</summary>

### What are state and props in React?

**Definition:**

#### Управление данными в React (стандарты 2026 г.)

В современном React (v19+) реквизиты и состояние остаются фундаментальными примитивами для распространения данных и синхронизации пользовательского интерфейса. Архитектура React следует однонаправленному потоку данных, где данные обычно перемещаются от родительского элемента к дочернему через реквизиты, в то время как состояние остается локализованным в компоненте или передается общим предкам.

**How it works:**

#### Роль и жизненный цикл

- **Props (свойства)**: неизменяемые объекты данных, передаваемые от родительского компонента дочернему компоненту. Они служат конфигурацией компонента. Компонент должен быть чистым по отношению к своим свойствам; он никогда не должен изменять свои собственные реквизиты, поскольку ими управляет родительский элемент.

- **Состояние**: локальное изменяемое хранилище данных внутри компонента. Обновление состояния с помощью функции установки (например, диспетчеризация useState) планирует повторную визуализацию дерева компонентов для отражения нового состояния.

#### Стратегический выбор

- **Реквизит**: используется для передачи данных, настройки и обратных вызовов событий. Реквизит действует как «API» компонента.

- **Состояние**: используйте для данных, которые изменяются в течение жизненного цикла компонента, например, вводимые пользователем данные, буферы ответов на стороне сервера или временные переключатели пользовательского интерфейса. С появлением Server Components в React 19 состояние сведено к минимуму в пользу потоковой передачи данных непосредственно с сервера.

#### Управление и производительность

- **Повторный рендеринг**: React использует алгоритм согласования Fiber. Обновление состояния запускает рендеринг поддерева. В 2026 году мы избегаем ручной оптимизации, такой как mustComponentUpdate (не рекомендуется для функциональных компонентов). Вместо этого мы используем useMemo, useCallback и компонент высшего порядка memo, чтобы предотвратить ненужные повторные вычисления.

- **Подъем состояния**: если несколько компонентов имеют общее состояние, «поднимите» состояние до ближайшего общего предка.

- **Композиция**: вместо глубокого детализации используйте React Context или Server Components для ввода данных в поддеревья.

#### Объединение с помощью хуков и Server Components

- **Функциональные компоненты**: отраслевой стандарт. Компоненты класса являются устаревшими и не должны использоваться в новых проектах.

- **React 19 Контекст**: хук использования модернизировал способ использования обещаний и контекста, позволяя более четкое разрешение асинхронного состояния внутри компонентов.

- **Server Components**: по умолчанию компоненты архитектуры App Router являются серверными компонентами. Они не поддерживают такие хуки, как useState. Состояние отнесено к Client Components, явно отмеченному директивой «use client».

#### Анализ сложности

- **Сложность рендеринга**: учитывая n узлов в поддереве компонента, обновление состояния имеет временную сложность O(n) в худшем случае, поскольку React должен выполнить согласование (различение) для определения исправлений DOM.

В 2026 году Redux Toolkit (RTK) станет обязательным интерфейсом. Устаревшая версия Connect HOC устарела; хуки useSelector и useDispatch являются стандартными для всех функциональных компонентов.

- **Высокочастотное состояние**: оптимизировано для состояния, которое меняется несколько раз в секунду (например, тикеры в реальном времени, сложные буферы перетаскивания).

- **Предсказуемые переходы состояний**: обеспечивает однонаправленный поток данных через Immer-интегрированные редукторы, обеспечивая неизменность состояний с концептуальной сложностью O(1) для разработчиков.

- **Экосистема промежуточного программного обеспечения**: надежная поддержка управления побочными эффектами с помощью RTK Query, который изначально управляет кэшированием, опросом и оптимистичными обновлениями, сокращая количество шаблонов по сравнению с ручными реализациями useEffect.

- **DevTools & Observability**: обеспечивает централизованное ведение журнала и отладку с перемещением во времени, что остается отраслевым стандартом для аудита сложных траекторий состояния в распределенных командах.

#### React Context API

Context API — это механизм внедрения зависимостей, а не решение для управления состоянием. Он предназначен для распространения значений по дереву без сверления опор.

- **Легкая интеграция**: отсутствие накладных расходов, поскольку это основная функция React. Идеально подходит для предотвращения раздувания сторонних зависимостей в легких компонентах.

- **Ограничения производительности**: контекст передает обновления всем потребителям при каждом изменении значения. Без мемоизации (useMemo, memo) это вызывает повторные рендеры всего дерева провайдера и даёт сложность повторного рендеринга O(n), где n — количество дочерних узлов.

- **Инкапсуляция**: упрощает распространение статических или полустатических данных (например, локализации, темы, сеанса аутентификации).

#### Сводка технического сравнения

| Особенность | Redux Toolkit | Context API |
| --- | --- | --- |
| Основное использование | Сложное, высокочастотное состояние | Конфигурация, внедрение зависимостей |
| Производительность | Выборочный рендеринг (селекторы) | Полный повторный рендеринг поддерева (по умолчанию) |
| Шаблон | Умеренный (стандартизован через RTK) | Минимальный |
| Инструменты разработчика | Родное путешествие во времени | Ограничено (React только для DevTools) |
| Сложность | Масштабирование от O(1) до O(log n) | O(n) поведение рендеринга |
- **Заключение аудита**: отдайте предпочтение Context API для глобальных конфигураций пользовательского интерфейса и Redux Toolkit для бизнес-логики приложения, состояния формы и синхронизации кэша сервера. Откажитесь от использования устаревших шаблонов подключения на основе классов в пользу текущего API на основе перехватчиков.

**When to use:**

#### Когда выбирать Redux

- **Сложные зависимости состояний**: используйте, когда срезы состояния совместно используют данные или требует реляционной логики.

- **Крупномасштабные требования к производительности**: используйте, когда требуются детальные обновления компонентов, чтобы предотвратить повторную визуализацию всего дерева компонентов.

- **Расширенное кэширование**: используйте, когда приложению требуются сложные стратегии извлечения данных и аннулирования кэша, предоставляемые RTK Query.

#### Когда выбирать Context API

- **Статические или низкочастотные данные**: идеально подходят для данных конфигурации, которые редко меняются (например, темы пользовательского интерфейса, текущий языковой стандарт пользователя).

- **Простое внедрение зависимостей**: используйте, когда вам нужно передать сервисы или одноэлементные экземпляры без явного детализации свойств.

- **Библиотеки компонентов**: необходимы для создания шаблонов составных компонентов, в которых подкомпоненты должны неявно обращаться к родительскому состоянию.

### Explain the lifecycle methods of a React class component.

**Definition:**

Эти методы относятся к устаревшему классовому API на `Component`. React вызывает их при монтировании, обновлении и размонтировании экземпляра класса. Новые компоненты пишут функциями и хуками; эти методы оставляют, когда поддерживают уже существующий класс.

**How it works:**

#### До render

- `static getDerivedStateFromProps(props, state)` выполняется перед каждым `render`, включая первое монтирование. Верните частичный объект состояния или `null`, если менять ничего не нужно. У метода нет `this`.
- `render` должен оставаться чистым. Он возвращает UI для текущих props и state.

#### После коммита

- `componentDidMount` выполняется после того, как экземпляр появился на экране. Здесь запускают подписку или сетевой запрос. В разработке со Strict Mode React вызывает `componentDidMount`, затем `componentWillUnmount`, затем снова `componentDidMount`.
- `componentDidUpdate(prevProps, prevState, snapshot)` выполняется после обновления DOM. Сравните предыдущие props и state, прежде чем начинать новую работу.
- `componentWillUnmount` выполняется перед удалением. Отключите то, что подключил `componentDidMount`.

#### Пропуск обновления и снимок

- `shouldComponentUpdate(nextProps, nextState, nextContext)` выполняется перед отрисовкой. Верните `false`, чтобы пропустить обновление. По умолчанию метод возвращает `true`.
- `getSnapshotBeforeUpdate(prevProps, prevState)` выполняется после `render` и до обновления DOM. Его возвращаемое значение приходит в `componentDidUpdate` как `snapshot`. React пропускает метод, если `shouldComponentUpdate` вернул `false`.

**Examples:**

```jsx
class ChatRoom extends Component {
  componentDidMount() {
    this.setupConnection();
  }

  componentDidUpdate(prevProps) {
    if (this.props.roomId !== prevProps.roomId) {
      this.destroyConnection();
      this.setupConnection();
    }
  }

  componentWillUnmount() {
    this.destroyConnection();
  }

  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

### How do hooks work in React?

**Definition:**

Хуки — это функции, имена которых начинаются с `use`. Они дают функциональному компоненту состояние и связь с системами вне React. React вызывает их во время рендера и сопоставляет каждый вызов с тем же вызовом прошлого рендера по порядку.

**How it works:**

#### Где вызов допустим

- Хук вызывают на верхнем уровне функционального компонента или на верхнем уровне своего хука, до любого раннего `return`.
- React хранит состояние хуков в порядке вызовов. Вызов внутри условия, цикла или вложенной функции сдвинет слоты на следующем рендере.

#### Что делают частые хуки

- `useState` хранит значение между рендерами и возвращает функцию обновления.
- `useEffect` связывает компонент с внешней системой после коммита. Эффект — запасной выход: если вы не общаетесь с чем-то вне React, он часто не нужен.
- `useContext` читает ближайшее подходящее значение контекста выше по дереву.

**Examples:**

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount((c) => c + 1)}>
      Clicked: {count} times
    </button>
  );
}
```

### Can you describe the useEffect hook and its purpose?

**Definition:**

`useEffect` связывает компонент с внешней системой после того, как React закоммитил UI. Функция настройки может вернуть функцию очистки. Это не место для данных, которые можно вычислить прямо во время рендера.

**How it works:**

#### Настройка и очистка

- React запускает эффект после отрисовки браузером. `useLayoutEffect` — вариант до отрисовки; `useInsertionEffect` выполняется до изменений DOM и предназначен для библиотек CSS-in-JS.
- Верните из эффекта функцию, чтобы отключиться, снять слушатель или проигнорировать устаревший результат. React вызывает очистку перед повторным эффектом и при размонтировании.
- В разработке со Strict Mode React выполняет настройку, очистку и снова настройку, чтобы пропущенная очистка стала видна.

#### Зависимости

- Второй аргумент перечисляет реактивные значения, которые читает эффект. Когда одно из них меняется, React сначала очищает эффект, затем запускает его снова.
- Пропущенное прочитанное значение даёт устаревшее замыкание. Линт `exhaustive-deps` об этом сообщает.
- `useEffectEvent` оборачивает функцию, которую нужно вызвать из эффекта, не добавляя её в зависимости.

**Examples:**

```jsx
function ChatRoom({ roomId }) {
  const [serverUrl, setServerUrl] = useState("https://localhost:1234");

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [serverUrl, roomId]);
}
```

### How do you fetch data with hooks in React?

**Definition:**

На клиенте запрос начинают в `useEffect`, результат пишут через `useState` и игнорируют ответ, который пришёл после очистки. В React 19 клиентский компонент также может прочитать Promise через `use`, пока родительский `Suspense` показывает запасной UI.

**How it works:**

#### Запрос в эффекте

- Не передавайте `async`-функцию в `useEffect`. Объявите async-функцию внутри эффекта и вызовите её.
- Держите флаг `ignore`. Очистка ставит его в `true`, чтобы более старый медленный ответ не вызвал setter после старта нового запроса.
- Значения, от которых зависит запрос, кладут в массив зависимостей, чтобы смена значения запустила запрос снова.

#### Чтение Promise через use

- `use(promise)` читает разрешённое значение во время рендера. В отличие от других хуков, `use` можно вызывать условно.
- Клиентский компонент не может сделать `await` во время рендера. Читающий компонент оборачивают в `<Suspense fallback={...}>`.
- Эффекты остаются запасным выходом для подписки, которая живёт только в браузере. Ими плохо дирижировать потоком данных, который уже закрывает фреймворк или `use`.

**Examples:**

```jsx
useEffect(() => {
  let ignore = false;
  setBio(null);
  fetchBio(person).then((result) => {
    if (!ignore) {
      setBio(result);
    }
  });
  return () => {
    ignore = true;
  };
}, [person]);
```

### What rules do you have to follow when using hooks?

**Definition:**

Хуки вызывают только пока React рендерит функциональный компонент или свой хук, и только на верхнем уровне, в одном и том же порядке каждый раз. Исключение — `use`: его можно вызывать условно.

**How it works:**

#### Только верхний уровень

- Не вызывайте хуки внутри условий, циклов, вложенных функций или `try` / `catch` / `finally`.
- Не вызывайте их после условного `return`, в обработчике события, в классе и внутри функции, которую передают в `useMemo`, `useReducer` или `useEffect`.
- Свой хук может вызывать другие хуки, потому что его самого вызывают во время рендера.

#### Почему важен порядок

- React сопоставляет n-й вызов хука на этом рендере с n-м вызовом на прошлом. Пропущенный вызов привяжет состояние не к тому хуку.
- `eslint-plugin-react-hooks` ловит эти ошибки, включая пропущенные зависимости эффекта.

**Examples:**

```jsx
function FeedbackForm() {
  const [isSent, setIsSent] = useState(false);
  const [message, setMessage] = useState("");

  if (isSent) {
    return <h1>Thank you!</h1>;
  }

  return <textarea value={message} onChange={(e) => setMessage(e.target.value)} />;
}
```

### How do props work in React?

**Definition:**

Props — это входные данные, которые родитель передаёт компоненту. Потомок читает их как аргумент функции (или `this.props` в классе) и сам их не меняет.

**How it works:**

#### Что можно передать

- Prop может быть строкой, числом, объектом, массивом или функцией. Атрибуты JSX становятся этими полями.
- Вложенный JSX между открывающим и закрывающим тегами приходит как prop `children`.
- Рендер читает `props` этого прохода. Следующий рендер родителя даёт следующие значения.

#### Данные в одну сторону

- Потомок рисует UI из полученных props. Чтобы изменить то, что хранит родитель, родитель передаёт функцию, и потомок её вызывает.
- Прокидывание одного и того же prop через много слоёв, которые его не используют, — это prop drilling. Контекст или композиция убирают эту цепочку.

**Examples:**

```jsx
function Avatar({ person, size }) {
  return (
    <img
      src={getImageUrl(person)}
      alt={person.name}
      width={size}
      height={size}
    />
  );
}

<Avatar size={100} person={{ name: "Katsuko Saruhashi", imageId: "YfeOqp2" }} />
```

### What is prop drilling and how can you avoid it?

**Definition:**

Prop drilling — это передача prop через компоненты, которые его не используют, только чтобы его прочитал глубокий потомок. Так бывает, когда владелец данных далеко от компонентов, которые их читают.

**How it works:**

#### Почему это появляется

- Props явные. Каждый слой называет prop, который ему не нужен, и переименование задевает каждый файл в цепочке.
- Подъём состояния к общему предку делает цепочку длиннее.

#### Как пройти сквозь неё

- Контекст даёт родителю опубликовать значение. Любой потомок вызывает `useContext` и пропускает средние компоненты. В текущем React провайдер — это `<LevelContext value={level}>`, а не отдельный элемент `.Provider`.
- Композиция оставляет родителя, который владеет данными, тем, кто рендерит потомка, и передаёт готовый элемент как `children`, так что средний компонент prop не видит.
- Функция-prop вроде `renderItem` — ещё один способ, которым родитель решает UI потомка. Контекст подходит данным, которые делят много далёких компонентов, например теме или уровню заголовка.

**Examples:**

```jsx
function Section({ level, children }) {
  return (
    <section>
      <LevelContext value={level}>{children}</LevelContext>
    </section>
  );
}
```

### Explain the Context API and its use cases.

**Definition:**

Контекст публикует значение от компонента любому потомку, который вызывает `useContext`, без прокидывания этого значения через props. Значение по умолчанию из `createContext` используется только когда над читателем нет провайдера.

**How it works:**

#### Настройка

- `createContext(defaultValue)` возвращает объект контекста.
- `<SomeContext value={value}>` оборачивает поддерево, которое должно видеть `value`. Читатель ниже подписывается через `const value = useContext(SomeContext)`.
- Когда `value` меняется, каждый компонент, прочитавший этот контекст, рендерится снова, включая потомка в `memo`.

#### Когда уместен

- Тема, локаль, текущий пользователь или уровень заголовка: данные, которые нужны многим компонентам и которые меняются редко.
- Список задач и функция `dispatch`, разнесённые по двум контекстам, чтобы компонент, который только диспатчит, не рендерился на каждое изменение списка.
- Контекст плохо подходит для состояния с высокой частотой обновлений. Новый объект или функция в `value` на каждом рендере уведомляет каждого читателя.

**Examples:**

```jsx
const theme = useContext(ThemeContext);

return (
  <ThemeContext value={theme}>
    <Button />
  </ThemeContext>
);
```

### How do you use render props?

**Definition:**

Render prop — это prop, значение которого является функцией, возвращающей JSX. Компонент вызывает эту функцию с данными, которыми владеет, а родитель решает, что рисовать.

**How it works:**

#### Вызов функции во время рендера

- Родитель передаёт `renderItem` или `renderContent`. Потомок вызывает её с текущим элементом, id или флагом подсветки.
- Потомок хранит состояние (какая вкладка выбрана, какая строка подсвечена). Разметку определяет родитель.
- `children` тоже может быть такой функцией. Именованный prop яснее, когда компонент ещё и оборачивает другие элементы.

#### Обычный потомок, когда функции не нужно

- Если родитель уже знает UI, передайте элементы как `children`, а не функцию.
- В документации `renderItem` показан как замена клонированию детей и перезаписи их props через `cloneElement`.

**Examples:**

```jsx
<List
  items={products}
  renderItem={(product, isHighlighted) => (
    <Row key={product.id} title={product.title} isHighlighted={isHighlighted} />
  )}
/>
```

### What is the children prop?

**Definition:**

`children` — это prop, который React заполняет тем, что вложено между открывающим и закрывающим тегами компонента. Компонент сам выбирает, где этот контент появится.

#### Откуда он берётся

- `<Card><Avatar /></Card>` передаёт `<Avatar />` как `children`. Текст и несколько элементов приходят так же.

```jsx
function Card({ children }) {

</Card>
```

### Why is performance optimization important in React?

**Definition:**

Повторный рендер родителя заново рендерит детей. Эта работа впустую, когда медленный потомок получает те же props, и она видна как тормозящий список или заблокированное действие.

#### Что реально стоит времени

- Рендер выполняет функции компонентов. Список с тяжёлой работой на каждое обновление родителя повторяет её, даже если элементы не менялись.
- Обновления состояния привязаны к компоненту, который им владеет. Состояние рядом с UI держит повторный рендер в маленьком поддереве.
- `memo` — инструмент производительности. Если UI неверен без него, сначала чинят ошибку. В документации список искусственно замедлен, чтобы пропущенный рендер был заметен.

#### К чему тянуться

- `memo` пропускает функциональный компонент, когда его props поверхностно равны прошлому рендеру.
- `useMemo` держит объект или отфильтрованный массив той же ссылкой, чтобы потомок в `memo` увидел тот же prop.
- `useCallback` делает то же для функции-prop.

**Examples:**

```jsx
const List = memo(function List({ items }) {
  return (
    <ul>
      {items.map((item) => (

    </ul>
  );
});
```

### What is React.memo and when would you use it?

### How does PureComponent differ from Component in React?

**Definition:**

`PureComponent` — классовая форма поверхностной проверки props и state. `Component` всегда рендерится снова, когда рендерится родитель или обновляется его собственное состояние. `PureComponent` может этот рендер пропустить. Оба относятся к устаревшему классовому API; функциональный компонент вместо этого использует `memo`.

**How it works:**

#### Разница

- Подкласс `Component` вызывает `render` на каждый рендер родителя, если вы сами не написали `shouldComponentUpdate`.
- `PureComponent` реализует этот метод поверхностным сравнением `props` и `state`. Если все поля равны, React пропускает повторный рендер.
- Новый объект в prop всё равно считается изменением, как и для `memo`. Мутация существующего объекта или массива с той же ссылкой прячет изменение от поверхностного сравнения.

**When to use:**

- Уже существующий класс рендерится снова, потому что родитель обновил постороннее состояние, а его props и state — плоские данные.
- Новый UI пишут функциональным компонентом и оборачивают в `memo`, только когда пропуск рендера действительно нужен.

**Examples:**

```jsx

  render() {
    return <h3>Hello{this.props.name && ", "}{this.props.name}!</h3>;
  }
}
```

### Can you explain the concept of reconciliation in React?

**Definition:**

- Смена `key` говорит React, что в этой позиции другой компонент, поэтому состояние сбрасывается. Так устроена кнопка сброса: `<Form key={version} />`.

- Middleware выполняется по порядку до loader и action этого перехода. `next()` продолжает цепочку.
- Если идентификатора пользователя нет, `throw redirect("/login")` отменяет защищённый переход и отправляет на вход.
- Middleware вешают на layout-маршрут, чтобы проверка досталась каждому дочернему маршруту.
- На этот layout добавляют `loader`, даже если он возвращает `null`: тогда middleware выполняется и при клиентских переходах.

**Examples:**

```tsx
import { redirect } from "react-router";

async function authMiddleware({ request }) {
  const session = await getSession(request);
  if (!session.get("userId")) {
    throw redirect("/login");
  }
}

export const middleware = [authMiddleware];

export async function loader() {
  return null;
}
```

### What are higher-order components (HOCs)?

**Definition:**

Higher-order component — это функция, которая принимает компонент и возвращает компонент. В текущей документации React такую логику выносят в свой хук, а линт `component-hook-factories` отклоняет фабрику, которая объявляет вложенный компонент или хук.

**How it works:**

#### Что говорят текущие документы

- Имя своего хука начинается с `use` и заглавной буквы. Он делит логику состояния, а не само значение состояния.
- Компоненты и хуки объявляют на уровне модуля. Функция, которая возвращает новый компонент, или компонент, объявленный внутри другого, — это как раз то, что отмечает линт.
- Родитель по-прежнему передаёт данные через props или context. Обёртке не нужно прятать эти данные в сгенерированный тип компонента.

**Examples:**

```js
import { useState } from "react";

export function useFormInput(initialValue) {
  const [value, setValue] = useState(initialValue);
  function handleChange(e) {
    setValue(e.target.value);
  }
  return { value, onChange: handleChange };
}
```

<summary>Explain the container/presenter (smart/dumb) component pattern.</summary>

### Explain the container/presenter (smart/dumb) component pattern.

**Definition:**

Container читает состояние и передаёт обычные данные в presenter. Presenter возвращает JSX из props и не владеет этим состоянием.

**How it works:**

#### Разделение

- Container вызывает `useState`, `useReducer` или `useContext`, затем рендерит presenter со значениями и обработчиками.
- Presenter — функция этих props. Один и тот же presenter может нарисовать строку задачи, превью или пример и не знать, откуда данные.
- В руководстве по масштабированию общее состояние кладут в provider, а каждый ребёнок читает то, что ему нужно. Разделение то же: один модуль владеет обновлениями, компонент строки только рисует.

**When to use:**

- Presenter нужен, когда разметку переиспользуют с разными данными.
- Состояние оставляют в родителе, если обновлять его должен только он. Данные передают props, а не прячут за сгенерированной обёрткой.

**Examples:**

```jsx
function TaskRow({ task, onToggle }) {
  return (
    <label>
      <input
        type="checkbox"
        checked={task.done}
        onChange={(e) => onToggle(task.id, e.target.checked)}
      />
      {task.text}
    </label>
  );
}
```

### Explain the use of custom hooks in React.

**Definition:**

Свой хук — это функция, имя которой начинается с `use` и которая вызывает другие хуки. Он делит логику состояния между компонентами. У каждого вызова своё состояние.

**How it works:**

#### Правила из документации

- Имя — это `use` и заглавная буква, например `useOnlineStatus` или `useFormInput`.
- Хуки выполняются на каждом рендере компонента, который их вызвал. Их вызывают на верхнем уровне функции, не внутри условия.
- Хук возвращает данные и функции. Он не делит значение состояния с другим компонентом, который вызвал тот же хук.
- Назначение хука должно быть конкретным. В документации не советуют заводить хук вроде `useMount`, чья единственная работа — подпись к жизненному циклу.

**Examples:**

```js
function StatusBar() {
  const isOnline = useOnlineStatus();
  return <h1>{isOnline ? "Online" : "Disconnected"}</h1>;
}
```

### What is a render prop pattern?

**Definition:**

Render prop — это обычный prop-функция, который говорит компоненту, что рендерить. Компонент вызывает эту функцию и может передать ей данные, например индекс или id.

#### Вызов функции

- В имени prop нет ничего особенного. Функцией могут быть и `renderRow`, и `children`.
- Родитель решает разметку. Ребёнок решает, когда вызвать функцию и какие аргументы передать.
- Это сотрудничество через props. Ребёнок не переписывает элементы родителя.

**Examples:**

```jsx
function RowList({ items, renderRow }) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={item.id}>{renderRow(item, index)}</li>
      ))}
    </ul>
  );
}
```

<summary>How do you handle forms in React?</summary>

### How do you handle forms in React?

**Definition:**

Форму ведут, храня значения полей в state, или читая `FormData` из события отправки. Action в React 19 может принять этот `FormData` и вернуть сообщение об ошибке через `useActionState`.

**How it works:**

#### State или событие отправки

- Управляемое поле хранит строку в `useState` и записывает её из `onChange`. Кнопка сброса возвращает state в `""`.
- На отправке вызывают `event.preventDefault()`, чтобы браузер не перезагрузил страницу. `new FormData(event.target)` включает каждый элемент с `name`.
- Этот `FormData` можно сразу передать в `fetch(url, { method: form.method, body: formData })`.
- `useActionState(action, null)` возвращает последнее сообщение и action для `<form action={...}>`. Action получает предыдущее состояние и `FormData`.

**Examples:**

```jsx
export default function MyForm() {
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.target);
    fetch("/some-api", { method: e.target.method, body: formData });
  }

  return (
    <form method="post" onSubmit={handleSubmit}>
      <input name="myInput" defaultValue="Some initial value" />
      <button type="submit">Submit</button>
    </form>
  );
}
```

<summary>What is controlled and uncontrolled components?</summary>

### What is controlled and uncontrolled components?

**Definition:**

Управляемый input показывает значение из state React: вы передаёте `value` и `onChange` либо `checked` и `onChange`. Неуправляемый input хранит значение в DOM; вы передаёте `defaultValue` или `defaultChecked` и читаете его позже из формы.

**How it works:**

#### Какие props

- `value` без `onChange` замораживает текстовое поле. Обработчик должен вызвать setter с `event.target.value`.
- `checked` делает то же для checkbox или radio. `value` у radio называет вариант, который попадёт в данные формы.
- `defaultValue` и `defaultChecked` задают только начальное значение DOM. Это props неуправляемого поля.
- На отправке неуправляемую форму всё равно можно прочитать через `new FormData(event.target)`, если у каждого элемента есть `name`.

**When to use:**

- Управляемый input нужен, когда рендер зависит от текста: заголовок повторяет имя или кнопка выключена, пока ответ пуст.
- Неуправляемый input нужен, когда значение требуется только на отправке и экран не повторяет каждое нажатие.

**Examples:**

```jsx
const [firstName, setFirstName] = useState("");

<input
  value={firstName}
  onChange={(e) => setFirstName(e.target.value)}
/>
```

### How do you validate forms in React?

**Definition:**

Форму в React проверяют до отправки и показывают ошибку в state. Проверка может выключить кнопку, отклонить отправку в обработчике или вернуть сообщение из action.

**How it works:**

#### Где выполняется проверка

- Управляемая форма может выключить кнопку, пока `answer.length === 0` или `status === "submitting"`.
- Обработчик отправки ставит статус вроде `"typing"`, `"submitting"` или `"success"` и сохраняет пойманную ошибку, чтобы следующий рендер показал `error.message`.
- Action вместе с `useActionState` может сделать `return err.toString()` после неудачного запроса. Компонент рендерит это сообщение. Пример с `<form>` работает ещё до загрузки клиентского JavaScript, если action — Server Function.
- Браузерные ограничения тоже действуют. В примерах context на обязательные поля ставят `required`.

**Examples:**

```jsx
<button
  disabled={answer.length === 0 || status === "submitting"}
>
  Submit
</button>
{error !== null && <p className="Error">{error.message}</p>}
```

<summary>What is Formik and how is it used in React forms?</summary>

### What is Formik and how is it used in React forms?

**Definition:**

Formik сам хранит значения формы, ошибки и состояние отправки. Ему передают `initialValues`, функцию `validate` или `validationSchema` и `onSubmit`.

**How it works:**

#### Хук или компоненты

- `useFormik({ initialValues, validate, onSubmit })` возвращает `values`, `errors`, `handleChange` и `handleSubmit`. `handleSubmit` ставят на `<form onSubmit>`, а каждый input связывают через `name`, `value` и `onChange`.
- `validate` возвращает объект с ключами как у `initialValues`. Она выполняется на change, blur и submit.
- `<Formik>`, `<Form>`, `<Field name="email" />` и `<ErrorMessage name="email" />` закрывают тот же поток. `<ErrorMessage>` рисует сообщение только если поле тронуто и в нём есть ошибка.

**Examples:**

```jsx
const formik = useFormik({
  initialValues: { email: "" },
  validate: (values) => {
    const errors = {};
    if (!values.email) errors.email = "Required";
    return errors;
  },
  onSubmit: (values) => {
    alert(JSON.stringify(values, null, 2));
  },
});
```

### How do you handle file uploads in React?

**Definition:**

Загрузка файла — это `<input type="file" name="..." />` внутри формы. На отправке читают объект `FormData` и передают его телом `fetch`. Файл не копируют в state React только ради отправки.

**How it works:**

#### Поле файла

- `accept` ограничивает типы в диалоге выбора, например `image/*`.
- Элементу нужен `name`, чтобы `FormData` включил файл.
- `event.preventDefault()` не даёт странице перейти. `fetch("/upload", { method: "post", body: formData })` отправляет файл вместе с остальными именованными полями.
- `capture` может запросить микрофон, видео или камеру для этого поля.

```jsx
function UploadForm() {
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.target);
    fetch("/upload", { method: "post", body: formData });
  }

  return (
    <form method="post" onSubmit={handleSubmit}>
      <input type="file" name="attachment" accept="image/*" />
      <button type="submit">Upload</button>
    </form>
  );
}
```
