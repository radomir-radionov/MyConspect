### What is Go and why was it created?

**Definition:**

Go, также называемый Golang, — это язык программирования с открытым исходным кодом, разработанный командой Google и представленный публике в 2009 году. На дизайн Go повлияли его известные создатели: Роб Пайк, Кен Томпсон и Роберт Гриземер.

Этот язык был направлен на решение конкретных проблем, с которыми столкнулись разработчики Google, а также на объединение лучших функций разных языков.

**How it works:**

#### Ключевые цели дизайна Go

- **Простота**: Go был разработан с минималистичным подходом для минимизации сложности. Его дизайн избегает чрезмерных абстракций и программной «магии».

- **Эффективность**: для Go было крайне важно быть эффективным и выразительным как во времени, так и в пространстве.

- **Безопасность**: создатели стремились сделать Go безопасным статически типизированным языком.

- **Параллельное программирование**: дизайн Go призван сделать параллельное программирование прагматичным и простым.

Во многом это было достигнуто благодаря таким функциям, как goroutines и каналы.

- **Язык системы**: Go задумывался как язык, подходящий для программирования на уровне системы. Это означает, что Go можно использовать для создания операционных систем, написания драйверов устройств или управления системными операциями.

#### Ключевые особенности

- **Открытый исходный код**: Go имеет открытый исходный код, что означает, что его исходный код находится в открытом доступе. Вы можете просматривать, изменять и распространять его в соответствии с условиями лицензии.

- **Статически типизированный**: как и Java и C++, Go требует явного указания типов переменных и возвращаемых значений функций. Эти типы проверяются во время компиляции на безопасность и точность.

- **Управление памятью**: разработчикам Go не приходится иметь дело с низкоуровневыми операциями с памятью, как в C/C++. Вместо этого Go использует сборщик мусора для освобождения памяти от неиспользуемых объектов.

- **Параллельное программирование**: Go напрямую поддерживает параллельные операции за счет использования goroutines и каналов.

- **Встроенный набор инструментов**: Go поставляется с многочисленными инструментами, такими как инструмент командной строки go, который автоматизирует многие задачи разработки. Например, вы можете использовать go build для компиляции программы и go test для запуска тестов.

- **Портативность**: Go был разработан с учетом совместимости с множеством систем и архитектур.

- **Поддержка Unicode**: Go полностью совместим с Unicode.

- **Поддержка сети**: Go поставляется с библиотеками для эффективного управления сетевыми операциями, что делает его оптимальным языком для разработки сетевых систем.

**When to use:**

#### Кто использует Go?

Несколько известных компаний широко используют Go в критически важных системах, ориентированных на производительность, таких как:

- **Google**: Go часто используется во внутренних системах, и многие облачные сервисы, такие как YouTube, Google Search и другие, в значительной степени полагаются на Go для своих серверных задач.

- **Dropbox**: Dropbox использовал Go для повышения производительности программных компонентов, требующих синхронизации и других задач.

- **Docker**: Go играет ключевую роль в обеспечении Docker достижения межплатформенной совместимости и эффективности использования ресурсов.

- **SoundCloud**: SoundCloud использовал Go для развертывания и управления своей инфраструктурой.

- **BBC Worldwide**: Go позволяет обрабатывать данные в реальном времени для BBC Worldwide, гарантируя, что зрители получат самый актуальный контент.

Помимо этого, Go все чаще предпочитают использовать для облачных приложений и микросервисов благодаря своей производительности, эффективности управления ресурсами и надежной стандартной библиотеке. По прогнозам, эта популярность будет расти по мере того, как все больше компаний признают преимущества Go.

### Explain the workspace architecture in Go.

**Definition:**

Язык Go использует упрощенную архитектуру рабочей области, которая отличает его от многих других языков программирования.

**How it works:**

#### Golang Архитектура рабочего пространства

Рабочая область по существу состоит из трех каталогов:

- **src**: Здесь находится исходный код.

- **pkg**: в каталоге pkg хранятся объекты пакета, созданные в процессе сборки. Такое разделение помогает установить четкое различие между кодом и результатами сборки.

- **bin**: каталог, в котором будет расположено скомпилированное приложение после его сборки.

Лидер Go Дистрибутива "Golang", Google уточняет, что это не просто предложения, а соблюдаемые стандартом Go инструменты.

#### GOPATH

Переменная среды GOPATH играет ключевую роль. Это отправная точка для поиска кода Go, и все упомянутые каталоги находятся внутри него.

В каталоге $GOPATH/src инструмент Go ожидает увидеть пакеты исходного кода вашего приложения.

Утилита "go get"
Эта команда является важным инструментом для разработчиков Golang. Вы можете использовать его для получения зависимостей и управления ими из удаленных репозиториев, таких как GitHub. Например, если вы запустите go get github.com/gorilla/mux, он получит пакет mux из GitHub и сохранит его в вашем $GOPATH.

Следуя рекомендациям сообщества Go, убедитесь, что в корне вашего проекта есть файлы «go.mod» и «go.sum». Файл "go.mod" содержит требования к регистрации модулей и зависимостям, а файл "go.sum" записывает версии зависимостей.

#### Для местного развития

Предположим, ваш GOPATH — ~/go. Для личного проекта с URL-адресом bob.com/project исходный код можно найти по адресу ~/go/src/bob.com/project.

#### Развитие в команде

Если, скажем, в репозитории Git находится проект с URL-адресом импорта gitlab.com/team/project, код будет расположен по адресу ~/go/src/gitlab.com/team/project.

#### Потенциал GOPATH Лучшие практики

- **Изоляция**: наличие одного GOPATH для каждого проекта обеспечивает чистоту и позволяет избежать конфликтов, возникающих из-за различных зависимостей проекта.

- **Свободная конфигурация**: избегайте установки GOPATH в профиле конфигурации оболочки, это может привести к нежелательному вмешательству в другие проекты.

- **Несколько рабочих областей**. Для разных языковых версий или разных сред рассмотрите возможность создания отдельных рабочих областей и сопровождающих их GOPATH. Такое разделение предотвращает обновление проектов, созданных в старых версиях, до новых инструментов.

#### Для систем контроля версий

- **GitHub & Co**: путь импорта часто связан с URL-адресом репозитория.

- **Локальные репозитории**: если ваш репозиторий является локальным и не подключен к удаленной службе VCS, вы можете использовать любую структуру пути импорта.

#### Лучшие практики

Объедините все свои кодовые базы в системе контроля версий для упрощения управления и развертывания.
Храните внешние зависимости за пределами $GOPATH, возможно, используя менеджер пакетов.

**Examples:**

#### Примеры путей

Инструмент будет ожидать ваш код в соответствующей папке в src. Если ваша система контроля версий — Git, папка может соответствовать соглашениям Git: например, github.com/username/project. Без Git вы можете думать об этом так: весь код должен находиться в каталоге, на который в некоторой степени влияет его URL-адрес импорта.

#### Пример go get: получение пакета mux

```bash
$ go get github.com/gorilla/mux
```

Эта команда будет контролировать загрузку репозитория GitHub для пакета "mux" и сохранять его локально для вас по мере необходимости.

#### go get с подробным флагом

```bash
$ go get -v github.com/gorilla/mux
```

Добавление здесь подробного параметра делает команду более информативной, предоставляя подробную информацию о предпринимаемых действиях.

#### Структура каталогов после получения с помощью Go Get

После выполнения команды go get будет получен пакет mux из репозитория gorilla, который должен находиться по следующему пути:

```text
~/go/src/github.com/gorilla/mux
```

### How is the GOPATH environment variable used?

**Definition:**

В Go переменная среды GOPATH имеет решающее значение, она служит корнем как для управления пакетами, так и для вашего репозитория кода, а также отделяет область разработки от установленных пакетов.

**How it works:**

#### Рабочий процесс без модулей (Go 1.10 и ранее)

#### Местоположение исходных файлов

Исходные файлы Go, скорее всего, находятся в каталогах bin, pkg и src внутри вашего каталога GOPATH.
Внутри каталога src вы обычно организуете свой код, используя путь к модулю.

#### Установка пакетов

Команда go get отвечает за выборку и установку пакетов. Например, запуск go get <имя-пакета> из любого места вашего рабочего пространства устанавливает пакет в глобальный кэш пакетов.

#### Создание и запуск кода

Когда вы создаете или запускаете свои программы, Go сначала ищет импортированные пакеты в вашем рабочем пространстве (в GOPATH/src), а затем проверяет глобальный кэш пакетов. Исходные файлы команд и инструментов Go ожидаются непосредственно в GOPATH/src.

#### Разрозненность кода

Использование GOPATH привело к созданию специфической структуры и рабочего процесса, которые иногда изолировали ваши проекты и рабочее пространство.

Теперь let сосредоточился на улучшении рабочих процессов с модулями.

#### Ключи к рабочему процессу модуля Go

- **Поддержка модулей**: начиная с Go 1.11, Go имеет более модульную конструкцию. Если ваш код находится в каталоге с файлом go.mod, это модуль. Нет необходимости в GOPATH.

- **Центральный кеш модулей**: в режиме с поддержкой модулей все зависимости хранятся в центральном кеше, что исключает необходимость повторных загрузок.

- **Контроль версий**: модули Go обеспечивают четкое управление версиями зависимостей проекта, обеспечивая повышенную надежность разработки, воспроизводимость и переносимость.

- **Чистая независимость**: каждый модуль получает свое изолированное пространство, обеспечивая четкую границу между зависимостями.

- **Совместное использование кода**: в отличие от предыдущей настройки, где все коды находились в одном каталоге, над модулями Go let вы работаете и отслеживаете свои модули в любом подходящем месте.

- **Глобальная видимость**: ваши модули, определенные в файле go.mod, доступны во всех системах, что упрощает совместное использование и совместную работу.

- **Интеграция VCS**: Go позволяет напрямую взаимодействовать с различными системами контроля версий, такими как Git, путем распознавания URL-адресов модулей.

- **Отчет о зависимостях**: Go теперь обеспечивает видимость зависимостей вашего проекта путем добавления файла go.mod, что позволяет избежать потенциально перегруженной структуры каталогов в GOPATH.

- **Мягкий переход**: Go поддерживает постепенный переход к новому режиму с учетом модулей, позволяя пользователям выбирать темп перехода.

Давайте рассмотрим новый рабочий процесс go mod в Go.

#### Как упрощается рабочий процесс go mod

- **Автономность**: код может находиться в любом месте вашей системы, что делает его независимым от центрального хранилища, такого как GOPATH.

- **Контроль версий**: версии библиотек устанавливаются точно, обеспечивая согласованную и стабильную среду сборки.

- **Кэш модуля**: этот эффективный центральный кеш устраняет головную боль при повторяющихся загрузках.

- **Уменьшение ошибок**: нет необходимости управлять общесистемными изменениями и глобальными кэшами — каждый модуль находится в надежном отдельном состоянии.

- **Механизм изоляции**: Go не ограничивается своей обычной структурой пакета; вы по-прежнему получаете автономный модуль, что позволяет сохранять предсказуемость и управляемость вашей среды.

- **Простая установка**: новые пользователи или участники могут быстро настроить рабочее пространство, не беспокоясь о правильности GOPATH.

**Examples:**

#### Пример кода: включение модулей

Вы можете вызывать модули, инициализируя файл go.mod в корне вашего проекта:

```bash
# Initialize a go.mod file
go mod init <module-path>
```

Это действие автоматически активирует режим с учетом модулей, делая GOPATH неактуальным.

**How it works:**

- **Автоматическое управление памятью**: сборщик мусора Go эффективно управляет памятью, освобождая разработчиков от бремени выделения/освобождения памяти.

- **Встроенная компиляция**: программы Go компилируются непосредственно в машинный код, обеспечивая переносимость между оборудованием без каких-либо внешних зависимостей во время выполнения.

- **Структурная типизация и интерфейсы**: Go предлагает особый подход к объектно-ориентированному программированию посредством интерфейсов и структурной типизации.

- **Статически связанные двоичные файлы**: двоичные файлы Go объединяют необходимые библиотеки, упрощая развертывание и снижая риск конфликтов библиотек по сравнению с такими языками, как C.

- **Стабильность языка**: Go придерживается политики «минимального управления версиями» для своей стандартной библиотеки, обеспечивая стабильность кода и обратную совместимость. Это также приводит к меньшему количеству сюрпризов во время обновлений.

- **Неявная реализация интерфейса**: типы могут реализовывать интерфейсы неявно, что снижает потребность в шаблонном коде.

- **Управление пакетами с помощью go mod**: начиная с Go 1.11, go mod обеспечивает управление зависимостями на уровне пакета, одновременно предлагая контроль версий и инкапсуляцию модулей.

- **Краткая обработка ошибок**: возвращаемое значение единичной ошибки Go, дополненное пакетом ошибок, делает обработку ошибок компактной и простой.

- **Эффективность генерации кода**: компилятор Go генерирует оптимизированный машинный код, что приводит к ускорению исполняемых файлов.

- **Веб-серверы со стандартной библиотекой**: стандартная библиотека Go включает пакет HTTP, упрощающий разработку веб-серверов без использования сторонних платформ.

- **GoDoc для документации**: GoDoc автоматизирует документацию кода, повышая удобство сопровождения кода и расширяя возможности сотрудничества с разработчиками.

- **Goroutines и примитивы параллелизма**: оператор 'select' Go и пакет 'context' предоставляют мощные механизмы координации и тайм-аутов в параллельных приложениях.

- **Полная поддержка Unicode**: Go по умолчанию обрабатывает текст как Unicode, обеспечивая плавность интернационализации и обработки текста.

- **Разрешение цикла**: цикл for Go поддерживает различные стили, что способствует адаптивности кода.

<summary>Describe how packages are structured in a Go program.</summary>

### Describe how packages are structured in a Go program.

**Definition:**

В Go весь код находится в пакетах. Каждому пакету отведена определенная роль с четкими спецификациями относительно наглядности, доступности и его места в более широкой программе.

**How it works:**

#### Ключевые понятия

- **Видимость**: элементы, начинающиеся со строчной буквы, видимы только внутри своего пакета (на других языках — только для пакета). Экспортированные элементы, начинающиеся с заглавной буквы, доступны вне пакета (аналогично public на других языках).

- **Организация**: код организован на трех уровнях: основная программа, пакеты и отдельные файлы.

- **Именование пакетов**: большинство разработчиков Go используют имена пакетов, состоящие из одного слова, строчными буквами.

### How does Go handle memory management?

**Definition:**

Go обеспечивает автоматическое управление памятью через сборщик мусора. Это гарантирует, что разработчикам не придется явно управлять выделением или освобождением памяти.

**How it works:**

#### Ключевые понятия

- **Сборка мусора (GC)**: Go использует GC для идентификации и освобождения памяти, которая больше не используется, предотвращая утечки памяти.

- **Поддержка параллельного выполнения**: GC Go предназначен для эффективной работы в параллельных средах, влияя на производственные приложения реального времени.

- **Плюсы**: Сборщик мусора Go упрощает управление памятью, снижая вероятность возникновения распространенных проблем, таких как зависшие указатели или утечки памяти.

- **Минусы**: Хотя обычно процесс сборки мусора оказывает минимальное влияние, он может вызвать небольшие колебания производительности, которые необходимо учитывать приложениям реального времени.

- **Настройка политики**: Go позволяет разработчикам влиять на поведение сборщика мусора, используя переменные среды и функции времени выполнения. Некоторые командуют всем программистам настроить GOGC на эффективность использования памяти. Тем не менее, это не гарантии, а эвристика для GC.

**Examples:**

#### Пример кода: сбор мусора в памяти

Вот код Go:

```go
package main

import "fmt"
import "runtime"

func main() {
    // Create lots of memory-consuming objects
    for i := 0; i < 100000000; i++ {
        _ = make([]byte, 100)
        if i%10000000 == 0 {
            fmt.Printf("Allocated %d bytes\n", i*100)
        }
    }

    // Request garbage collection
    runtime.GC()
    var ms runtime.MemStats
    runtime.ReadMemStats(&ms)
    fmt.Println("Memory allocated, not yet garbage collected:", ms.Alloc)

    // It would be a rare use case to invoke manual GC in production
}
```

### What is a channel in Go, and when would you use one?

**Definition:**

В Go channel — это способ безопасно и эффективно обмениваться данными между горутинами. Его основная цель разработки — оптимизировать одновременную связь и передачу данных.

- **Тип безопасности**: каналы зависят от типа, чтобы обеспечить четкую передачу данных.

- **Блокировка синхронизации**: при отправке или получении данных отправка или получение Goroutine блокируется до завершения операции, что способствует синхронизации.

**When to use:**

#### Распространенные случаи использования

- **Goroutine Координация**: установите связь и синхронизацию между параллельными горутинами.

- **Совместное использование ресурсов между Goroutines**: используйте channels для управления общими ресурсами, такими как фиксированное количество подключений к базе данных между Goroutines.

- **Обработка ошибок**: отправляйте возможные ошибки в центральный центр Goroutine для унифицированной обработки.

- **Потоковая передача данных**. Обеспечьте потоковую передачу данных, например обновлений в реальном времени, по каналам.

- **Пакетная передача данных**: каналы могут эффективно группировать и отправлять данные в пакетном режиме. Это может быть полезно в таких сценариях, как финансовые тикеры, где у вас может быть несколько тиков в секунду, но вы будете обрабатывать данные только время от времени.

- **Мягкое завершение работы**: используйте channel для подачи сигнала Goroutines на корректное завершение или приостановку задач, как на сервере, который должен начинать обработку запросов только после завершения определенной настройки.

**Examples:**

Вот код Java:

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

public class BatchDataTransfer {
    public static void main(String[] args) {
        BlockingQueue<Integer> channel = new ArrayBlockingQueue<>(5);

        // Producer
        new Thread(() -> {
            for (int i = 0; i < 100; i++) {
                try {
                    channel.put(i);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }).start();

        // Consumer
        new Thread(() -> {
            while (true) {
                try {
                    System.out.println(channel.take());
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }).start();
    }
}
```

### What does the range keyword do?

**Definition:**

В Go range — это универсальная конструкция цикла, которая упрощает перебор структур данных, таких как массивы, slices, карты, строки и каналы. Он эффективно обрабатывает различные типы данных и абстрагирует базовые механизмы индексации или итерации.

**How it works:**

#### Основные преимущества

- **Ясность**: делает код более читабельным, поскольку основное внимание уделяется элементам, а не индексам.

- **Безопасность**: циклы диапазона защищают от ошибок выхода индекса за границы и обеспечивают синхронизацию элементов в параллельных контекстах.

- **Эффективность**: устраняется необходимость в ручном управлении индексами.

#### Механика итераций

- **Срез/Массив**: возвращает как текущий элемент, так и его индекс.

- **Карта**: создает пары ключ-значение.

- **Канал**: при использовании в цикле for с channel range извлекает данные из channel, пока он не закроется.

```go
	"fmt"

	go func() {
		defer close(ch)
		for i := 0; i < 5; i++ {
			ch <- i
		}
	}()

	for val := range ch {
		fmt.Println("Channel value:", val)
	}
```

<summary>What is defer and when would you use it?</summary>

### What is defer and when would you use it?

**Definition:** `defer` откладывает вызов функции до возврата из окружающей функции — после `return`, в конце тела или пока горутина паникует.

**How it works:**

#### Вычисление и порядок

- **Аргументы сразу**: значение функции и аргументы вычисляются при выполнении `defer`, а не при самом вызове.
- **LIFO**: отложенные вызовы выполняются в обратном порядке, непосредственно перед возвратом к вызывающему.
- **Именованные результаты**: отложенный функциональный литерал может прочитать и изменить именованные результаты после того, как `return` их задал. Собственные результаты отложенного вызова отбрасываются.
- **Nil-функция**: если отложенное значение функции равно `nil`, паника возникает в момент вызова, а не в момент `defer`.

**When to use:**

#### Освобождение рядом с захватом

- Используйте его, чтобы разблокировать mutex, закрыть файл или тело ответа, либо восстановиться после паники в той же функции, которая получила ресурс.
- Не используйте его для работы, которая должна произойти в произвольный более поздний момент: это обычный поток управления или другая горутина.

**Examples:**

```go
func readFirst(path string) (b []byte, err error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()
	buf := make([]byte, 16)
	_, err = f.Read(buf)
	return buf, err
}
```

### Describe the select statement in Go.

**Definition:** `select` выбирает одну операцию отправки или получения, которая может выполниться. Это мультиплексор коммуникаций, по форме похожий на `switch`, но с операциями над каналами в ветках.

**How it works:**

#### Как выполняется select

- **Операнды один раз**: операнды каналов и отправляемые значения вычисляются ровно один раз, в порядке исходного текста, при входе. Побочные эффекты происходят, даже если ветка не выбрана.
- **Выбор**: если готовы несколько коммуникаций, одна выбирается равномерным псевдослучайным образом. Если не готова ни одна и есть `default`, выполняется он. Иначе `select` блокируется.
- **Nil-каналы**: коммуникация по `nil`-каналу никогда не выполняется. `select` только из `nil`-каналов без `default` блокируется навсегда.
- **Без fallthrough**: ветки не проваливаются друг в друга, а пустой `select {}` блокируется навсегда.

**When to use:**

#### Мультиплексирование ожиданий

- Используйте `select`, когда горутина должна ждать более одного канала, включая отмену или таймаут.
- Одиночные получение или отправка не требуют `select`. `default` делает операцию неблокирующей; он уместен, только если пропуск или повтор — задуманное поведение.

**Examples:**

```go
func take(ctx context.Context, ch <-chan int) (int, error) {
	select {
	case v, ok := <-ch:
		if !ok {
			return 0, errors.New("closed")
		}
		return v, nil
	case <-ctx.Done():
		return 0, ctx.Err()
	}
}
```

### Can you explain what pointers are and how Go handles them?

**Definition:** Тип указателя `*T` — это множество указателей на переменные базового типа `T`. Неинициализированный указатель равен `nil`. Go передаёт каждый аргумент по значению, поэтому функция получает копию указателя, а не копию переменной, на которую он указывает.

**How it works:**

#### Указатели и значения

- **Адрес и разыменование**: `&x` берёт адрес `x`. `*p` обозначает переменную, на которую указывает `p`.
- **Выделение**: `new(T)` выделяет нулевой `T` и возвращает `*T`. Составные литералы тоже дают указатели: `&Point{X: 1}`.
- **Карты, срезы, каналы**: копирование копирует дескриптор, указывающий на общие данные. Копия дескриптора не копирует эти данные.
- **Побег на кучу**: если указатель на локальную переменную переживает функцию, компилятор размещает её в куче, чтобы указатель не повис.
- **Указатели на интерфейс**: указатель на конкретный тип может реализовать интерфейс. Указатель на значение интерфейса почти никогда этого не делает; FAQ советует избегать `*SomeInterface`, кроме редких случаев.

**When to use:**

#### Получатель по значению или по указателю

- Используйте указатель, когда метод должен изменить получателя или когда копировать большое значение неправильно по стоимости.
- Используйте значение, когда метод ничего не меняет и копия дёшева и понятна. Нельзя взять адрес ключа карты или байта строки (`&s[i]` недопустим).

**Examples:**

```go
type Point struct{ X, Y int }

func (p *Point) Move(dx, dy int) {
	p.X += dx
	p.Y += dy
}

func origin() *Point {
	p := Point{}
	return &p
}
```

### Explain Go's interface type and how it differs from other types.

**Definition:** Интерфейсный тип задаёт множество типов. Переменная этого интерфейса может хранить значение любого типа из множества. Тип реализует базовый интерфейс автоматически, если его множество методов включает методы интерфейса; объявления `implements` нет.

**How it works:**

#### Значения интерфейса

- **Список методов**: базовый интерфейс — это список методов. Нулевое значение — `nil`: нет ни динамического типа, ни динамического значения.
- **Неявное соответствие**: тип удовлетворяет каждому интерфейсу, методы которого являются подмножеством его множества методов. Он может удовлетворять многим интерфейсам, а интерфейсы можно объявить позже, в том числе для тестов.
- **Не иерархия классов**: FAQ прямо говорит, что иерархии типов нет. Встраивание и интерфейсы — это не наследование.
- **Ловушка nil**: интерфейс, хранящий типизированный nil-указатель, не равен nil-интерфейсу. Возвращайте явный `nil` error, а не nil-указатель, положенный в переменную `error`.

**When to use:**

#### Принимайте интерфейсы, возвращайте конкретные типы

- Используйте маленький интерфейс на границе API, когда вызывающему нужно подставить другую реализацию, включая тестовый двойник.
- Оставляйте конкретную структуру, когда реализация одна и поведение не является точкой подмены.

**Examples:**

```go
type Stringer interface{ String() string }

type User struct{ Name string }

func (u User) String() string { return u.Name }
```

### What are map and how do you manage them?

**Definition:** Карта — неупорядоченная группа элементов одного типа, индексируемая уникальными ключами другого типа. Тип ключа должен быть сравнимым; функции, карты и срезы ключами быть не могут. Неинициализированная карта равна `nil`.

**How it works:**

#### Создание, чтение, удаление

- **make**: `make(map[K]V)` или `make(map[K]V, hint)` создаёт пустую карту. Подсказка не ограничивает рост. `nil`-карта читается как пустая, но запись элемента вызывает панику.
- **Поиск**: `v := m[k]` возвращает нулевое значение, если ключа нет. `v, ok := m[k]` сообщает, был ли ключ.
- **delete и clear**: `delete(m, k)` удаляет один ключ. `clear(m)` удаляет все элементы. `len(m)` — текущее число элементов.
- **Конкурентность**: FAQ говорит, что карты небезопасны для одновременной записи. Одновременное только чтение допустимо. Запись одновременно с любым другим доступом — гонка данных; среда выполнения может аварийно завершить программу, если обнаружит одновременную запись в карту.

**When to use:**

#### Карта или срез пар

- Используйте карту для поиска по ключу. Используйте срез, когда важен порядок или набор мал и просматривается линейно.
- Если несколько горутин меняют карту, отдайте её во владение одной горутине и шлите обновления в канал либо защитите `sync.Mutex`.

**Examples:**

```go
func counts(words []string) map[string]int {
	m := make(map[string]int)
	for _, w := range words {
		m[w]++
	}
	return m
}
```

### How does Go handle method overloading?

**Definition:** Go не поддерживает перегрузку методов и операторов. Для одного базового типа получателя непустые имена методов должны быть уникальны, а сигнатуры методов должны точно совпадать с интерфейсом.

**How it works:**

#### Что делают вместо этого

- **Разные имена**: `Read` и `ReadAt` — два метода, а не две перегрузки одного имени.
- **Обоснование FAQ**: авторы языка отказались от перегрузки, чтобы множества методов оставались простыми. Два метода с разными типами результата — не один и тот же метод.
- **Дженерики — не перегрузка**: обобщённая функция по-прежнему имеет одно имя и инстанцируется аргументами типа. Она не выбирает сигнатуру из набора перегрузок.

**Examples:**

```go

func (b *Buffer) Write(p []byte) (int, error) {
	b.buf = append(b.buf, p...)
	return len(p), nil
}

func (b *Buffer) WriteString(s string) (int, error) {
	return b.Write([]byte(s))
}
```

### What is type embedding in Go, and when would you use it?

### What is the purpose of the init() function?

<summary>How does Go's garbage collector work?</summary>

### How does Go's garbage collector work?

**Definition:** Сборщик мусора Go — конкурентный, параллельный, неперемещающий и непоколенческий mark-sweep. Он освобождает память кучи, до которой программа больше не может дотянуться. Большинство значений может жить на стеке; компилятор кладёт значение в кучу, когда ссылка на него покидает функцию.

**How it works:**

#### Пометка, очистка и цель кучи

- **Пометка**: сборщик обходит граф от корней и помечает достижимые объекты. Исходный код runtime описывает его как точный по типам, конкурентный с потоками-мутаторами и использующий барьер записи.
- **Очистка**: после пометки непомеченная память кучи снова доступна для выделения. Go не перемещает объекты, чтобы уплотнить кучу.
- **GOGC**: переменная среды задаёт компромисс между CPU сборщика и памятью. Руководство определяет целевой размер кучи как живую кучу плюс `(живая куча + корни GC) * GOGC / 100`. В комментарии runtime доля по умолчанию равна 100.

**Examples:**

```go
func live() *int {
	n := 1
	return &n // n escapes to the heap
}
```

### Can you describe how Go's type assertion works?

**Definition:** Для значения интерфейса `x` (не параметра типа) и типа `T` выражение `x.(T)` утверждает, что `x` не `nil` и что хранимое значение имеет тип `T`. Если `T` — интерфейс, утверждается, что динамический тип реализует `T`.

**When to use:**

- Используйте форму comma-ok, когда ожидается один тип, а неудача — обычный результат.

**Examples:**


### How does Go handle immutable strings?

```go
func shout(s string) string {

	for i, c := range b {

			b[i] = c - 'a' + 'A'
		}
	}
	return string(b)
}
```

- **Mutex**: `sync.Mutex` или `sync.RWMutex` вокруг чтения-изменения-записи. Блокировка должна удерживаться на каждом доступе, который модель памяти ещё не синхронизирует.
- **atomic**: `sync/atomic` покрывает отдельные слова и помощники для указателей и значений. Гонка данных — одновременная запись, пересекающаяся с другим чтением или записью, если не все доступы атомарны.

**When to use:**

#### Канал или mutex

- Передавайте владение по каналу, когда значение переходит от производителя к потребителю и в каждый момент его должна трогать одна горутина.
- Используйте mutex, когда много горутин разделяют одну структуру на месте, а критическая секция короткая.

**Examples:**

```go
type counter struct {
	mu sync.Mutex
	n  int
}

func (c *counter) Add(d int) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n += d
}
```

<summary>How does Go's panic and recover mechanism work?</summary>

### How does Go's panic and recover mechanism work?

**Definition:** `panic` останавливает обычное выполнение горутины и запускает её отложенные вызовы. `recover` останавливает эту панику, только если вызван непосредственно из отложенной функции, и возвращает значение, переданное в `panic`. `recover` в любом другом месте возвращает `nil`.

**How it works:**

#### Паника — не путь ошибки

- **defer во время паники**: отложенные функции всё равно выполняются. Отложенная функция может вызвать `recover`. Если не вызовет, паника продолжается к вызывающему после отложенных вызовов.
- **Повторная паника**: пример regexp в Effective Go делает recover, проверяет конкретный тип и паникует снова, если значение — не ожидаемая ошибка разбора.
- **Библиотеки**: возвращайте `error` для условий, которые вызывающий может обработать. Паникуйте при ошибках программиста и невозможных состояниях. Сервер может сделать recover на границе запроса, чтобы один обработчик не убил процесс; `net/http` делает это для `ServeHTTP`.

**When to use:**

#### возврат error или panic

- Возвращайте ошибку для отсутствующего файла, плохого запроса или неудачного запроса к базе.
- Паникуйте и делайте recover на границе, которой владеете, когда продолжение испортило бы состояние. Не делайте recover в библиотеке, пряча панику от вызывающего.

**Examples:**

```go
func safely(work func()) (err error) {
	defer func() {
		if v := recover(); v != nil {
			err = fmt.Errorf("panic: %v", v)
		}
	}()
	work()
	return nil
}
```

### What is the purpose of the context package in Go?

**Definition:** `context.Context` переносит дедлайн, сигнал отмены и значения области запроса через границы API. Сервер создаёт Context для входящего запроса, а исходящие вызовы принимают этот Context или потомка, полученного через `WithCancel`, `WithDeadline`, `WithTimeout` или `WithValue`.

**How it works:**

#### Отмена распространяется вниз

- **Родитель отменяет детей**: когда Context отменён, отменяется и каждый Context, производный от него. `ctx.Done()` закрывается, когда Context завершён, а `ctx.Err()` объясняет почему.
- **Первый параметр**: документация пакета велит передавать `ctx context.Context` первым параметром и не хранить Context внутри структуры.
- **Значения относятся к запросу**: `WithValue` — для данных, которые едут вместе с запросом, например идентификатора запроса, а не для необязательных параметров.

**When to use:**

#### Любой вызов, который должен отменяться

- Принимайте Context в функциях, которые блокируются на вводе-выводе, ожидании блокировок или работе, которую вызывающий может бросить.
- Не добавляйте Context к чистому вычислению, которое нельзя прервать и у которого нет данных области запроса.

**Examples:**

```go
func fetch(ctx context.Context, url string) error {
	ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return err
	}
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	return nil
}
```

### Explain the difference between concurrency and parallelism in Go, with examples.

**Definition:** Конкурентность — структура программы: независимо выполняемые части, согласованные горутинами и каналами. Параллелизм — это когда эти части действительно выполняются одновременно на разных процессорах. FAQ говорит, что конкурентность даёт параллелизм только когда задачу можно разбить на части, которые выполняются параллельно.

**How it works:**

#### Горутины и GOMAXPROCS

- **Много горутин, один CPU**: при `GOMAXPROCS`, равном 1, горутины всё ещё чередуются, в том числе пока другие блокируются в системных вызовах, но код Go не выполняется на двух CPU сразу.
- **Параллелизм по умолчанию**: FAQ говорит, что `GOMAXPROCS` по умолчанию равен числу доступных ядер, поэтому программа, которая может выполняться параллельно, делает это, пока вы это не измените.
- **Не всякая конкурентная программа ускоряется**: решето простых чисел в спецификации запускает много горутин и не имеет заметного параллелизма. Добавление CPU может замедлить такую программу.

**Examples:**

```go
func fanIn(ctx context.Context, a, b <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for a != nil || b != nil {
			select {
			case v, ok := <-a:
				if !ok {
					a = nil
					continue
				}
				out <- v
			case v, ok := <-b:
				if !ok {
					b = nil
					continue
				}
				out <- v
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

<summary>What is the Go memory model?</summary>

### What is the Go memory model?

**Definition:** Модель памяти Go задаёт, когда чтение переменной в одной горутине гарантированно наблюдает запись в ту же переменную в другой горутине. Совет документа: сериализуйте общее изменение операциями каналов или `sync` и `sync/atomic` и не полагайтесь на хитроумный несинхронизированный код.

**How it works:**

#### Без гонки данных значит последовательно согласованно

- **Гонка данных**: запись одновременно с другим чтением или записью того же места, если не все эти доступы атомарны. Программа без гонок ведёт себя так, будто горутины мультиплексированы на одном процессоре.
- **Happens-before**: отправка в канал происходит раньше, чем завершается соответствующее получение. Unlock мьютекса происходит раньше, чем вернётся последующий Lock этого мьютекса. Без такого ребра чтение может не увидеть запись.
- **Компилятор и CPU**: модель позволяет компилятору и оборудованию переставлять операции. Наблюдать программу с гонкой и ждать конкретного чередования — вне гарантии.

**Examples:**

```go
func publish(msg string) string {
	var ready = make(chan struct{})
	var box string
	go func() {
		box = msg
		close(ready) // happens before the receive below
	}()
	<-ready
	return box
}
```

### Can you manually trigger garbage collection in Go?

**Definition:** Да. `runtime.GC` запускает сборку мусора и блокирует вызывающего, пока эта сборка не завершится. Она может заблокировать и всю программу. Это инструмент для тестов и диагностики, а не обычный путь запроса.

**How it works:**

#### Что делает ручной цикл

- **Полный цикл**: комментарий runtime определяет цикл как завершение очистки, пометку, завершение пометки и очистку. `GC` не возвращается, пока полный цикл не закончится.
- **Не замена GOGC**: обычный ритм задаёт `GOGC` и цель кучи из руководства. Вызов `GC` на горячем пути добавляет участки цикла с остановкой мира.
- **Финализаторы**: `runtime.GC` не обещает, что финализаторы уже выполнились; руководство отмечает, что `GC` ждёт постановки cleanup в очередь, а не их завершения.

**When to use:**

#### Тесты и измерения

- Вызывайте `runtime.GC` в тесте, который должен наблюдать освобождённую память или границу финализатора, которую вы явно проверяете.
- Оставьте боевой ритм сборщику. Настраивайте `GOGC` или лимит памяти из руководства по GC, когда процессу нужен другой компромисс CPU и памяти.

**Examples:**

```go
func collectForTest() {
	runtime.GC()
}
```

### Describe the Go race detector and when you would use it.

**Definition:** Детектор гонок инструментирует программу, чтобы сообщать о гонках данных: две горутины обращаются к одной переменной одновременно, и хотя бы один доступ — запись. Включают его флагом `-race` у `go test`, `go run`, `go build` или `go install`.

- **Требования**: cgo должен быть включён, а на системах не Darwin нужен компилятор C. Поддерживаемые пары `GOOS/GOARCH` перечислены в статье о детекторе; это не каждый порт.

- Запускайте `-race` на тестах и на стендовом бинарнике, когда код разделяет память между горутинами.
- Не оставляйте `-race` на боевом бинарнике, чувствительном к задержке: документированные накладные расходы для этой роли слишком велики.

**Examples:**

```go
// go test -race ./...

	var c counter
	var wg sync.WaitGroup
	for i := 0; i < 8; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			c.Add(1)
		}()
	}
	wg.Wait()
}
```

### Discuss the use of Go routines and thread safety.

**Definition:** Горутина — не поток операционной системы. Планировщик мультиплексирует горутины на потоки. Общие переменные безопасны, только когда каждый конфликтующий доступ синхронизирован. Карты, базовые массивы срезов и обычные поля структур за вас не синхронизируются.

**How it works:**

#### Что runtime блокирует и чего не блокирует

- **Планировщик**: M — поток ОС, G — горутина, P — ресурс, нужный для выполнения кода Go. Блокировка в системном вызове сама по себе не делает данные свободными от гонок.
- **Каналы и мьютексы**: отправка/получение по каналу или `sync.Mutex` создают ребро happens-before, которое требует модель памяти.
- **Обнаружение**: `go test -race` сообщает о несинхронизированном одновременном доступе. Статья о детекторе определяет гонку как два доступа горутин к одной переменной, из которых хотя бы один — запись.

**Examples:**

```go
func worker(jobs <-chan int, wg *sync.WaitGroup) {
	defer wg.Done()
	for n := range jobs {
		_ = n
	}
}
```

### Explain how reflection is used to manipulate objects in Go.

**Definition:** `reflect.ValueOf` оборачивает значение. Если этот Value устанавливаемый, `Set` и типизированные сеттеры заменяют его. Устанавливаемый значит, что Value адресует экспортируемое адресуемое место — обычно `ValueOf(&x).Elem()` или экспортируемое поле адресуемой структуры.

**How it works:**

#### CanSet, затем Set

- **Неадресуемая копия**: `reflect.ValueOf(x)` — копия, и `CanSet` ложен. Взятие указателя и вызов `Elem` адресует `x`.
- **Только экспортируемое**: рефлексия не может установить неэкспортируемое поле структуры, определённой в другом пакете.
- **Проверка Kind**: `SetInt` паникует, если вид — не целочисленный. Проверяйте `Kind` или `CanSet` перед записью.

**Examples:**

```go
func setInt(p any, n int64) error {
	v := reflect.ValueOf(p)
	if v.Kind() != reflect.Pointer || !v.Elem().CanSet() {
		return errors.New("want settable pointer")
	}
	v.Elem().SetInt(n)
	return nil
}
```

<summary>Discuss the benefits and challenges of using channels for IPC in Go.</summary>

### Discuss the benefits and challenges of using channels for IPC in Go.

**Definition:** Канал позволяет конкурентно выполняющимся функциям отправлять и получать значения одного типа элемента. В Go эта коммуникация — между горутинами одного процесса. Это языковой способ передать владение данными, который codewalk про разделяемую память противопоставляет блокировкам вокруг общей структуры.

**How it works:**

#### Что синхронизируют каналы

- **Happens-before**: отправка происходит раньше, чем завершается соответствующее получение, поэтому получатель наблюдает записи, подготовившие значение.
- **Направление**: `chan<- T` может только отправлять, а `<-chan T` — только получать. Спецификация позволяет преобразовать двунаправленный канал в однонаправленный.
- **Не IPC операционной системы**: канал Go не соединяет два процесса ОС. Это делают каналы ОС, сокеты и `os/exec`. Закрытие канала — сигнал получателям, а отправка в закрытый канал вызывает панику.

**When to use:**

#### Передача или mutex

- Используйте канал, когда значение должно перейти к другой горутине или когда `select` должен также ждать отмену.
- Используйте mutex, когда много горутин обновляют одну структуру на месте, а канал добавил бы только копирование.

**Examples:**

```go
func gen(n int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)
		for i := 0; i < n; i++ {
			out <- i
		}
	}()
	return out
}
```

<summary>How would you avoid deadlocks in concurrent programming in Go?</summary>

### How would you avoid deadlocks in concurrent programming in Go?

**Definition:** Взаимная блокировка здесь значит, что горутины ждут друг друга и ни коммуникация, ни блокировка не могут продолжиться. Спецификация говорит, что `select` только по `nil`-каналам без `default` блокируется навсегда, а небуферизованная отправка выполняется, только когда готово получение.

**How it works:**

#### Ожидания, которые не могут завершиться

- **Каждой отправке — получатель**: небуферизованный `ch <- v` без получателя блокирует отправителя. Буферизуйте или обеспечьте получение в другой горутине.
- **Порядок блокировок**: если двум горутинам нужны два `sync.Mutex`, захватывайте их в одном порядке в каждой горутине, чтобы каждое ожидание всё ещё могло быть удовлетворено.
- **Отмена**: включайте `<-ctx.Done()` в `select`, чтобы заблокированное ожидание закончилось, когда вызывающий отменяет работу. Не держите mutex через операцию канала, которая может ждать.

**Examples:**

```go
func sendOrDone(ctx context.Context, ch chan<- int, v int) error {
	select {
	case ch <- v:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

- Не реализуйте его, когда `%v` по полям структуры уже правильный формат.

**Examples:**


### How do you manage database connections in Go?

**Definition:** `database/sql` — обобщённый интерфейс вокруг баз SQL, и его нужно использовать с драйвером. `sql.Open` готовит `*sql.DB`. Этот дескриптор безопасен для одновременного использования несколькими горутинами и держит собственный пул простаивающих соединений. Сам по себе он не создаёт сетевое соединение, пока запрос его не потребует.

**How it works:**

#### Пул, context и время жизни

- **Одно значение DB**: откройте его при старте и закройте, когда процесс завершается. `PingContext` проверяет, что соединение можно получить.
- **Пределы**: `SetMaxOpenConns`, `SetMaxIdleConns` и `SetConnMaxLifetime` ограничивают пул. Оставляйте их нулевыми, только когда значения по умолчанию приемлемы.
- **Отмена**: передавайте `Context` в `QueryContext` и `ExecContext`. Драйверы без поддержки отмены не возвращаются, пока запрос не закончится.

**When to use:**

#### Долгоживущий пул

- Держите один `*sql.DB` на процесс и разделяйте его между запросами.
- Не вызывайте `Open` и `Close` на каждый запрос: это выбрасывает пул, который пакет и должен поддерживать.

**Examples:**

```go
func openDB(driver, dsn string) (*sql.DB, error) {
	db, err := sql.Open(driver, dsn)
	if err != nil {
		return nil, err
	}
	db.SetMaxOpenConns(16)
	return db, nil
}
```

### Explain the difference between iota and const in Go.

**Definition:** `const` объявляет константу. `iota` — предопределённый идентификатор, который внутри объявления константы равен индексу текущего ConstSpec, начиная с нуля. `iota` — не отдельный вид объявления.

**How it works:**

#### Константы и счётчик

- **const**: связывает имена с константными выражениями. Типизированные константы получают объявленный тип. Нетипизированные константные выражения сохраняют произвольную точность, пока их не присвоят переменной, как описывает FAQ.
- **iota**: `c0 = iota`, затем `c1 = iota` дают 0 и 1. В следующем блоке `const` `iota` снова начинается с 0. Несколько использований `iota` в одном ConstSpec имеют одно значение.
- **const без iota**: `const pi = 3.14159` вообще не использует `iota`.

**Examples:**

```go
const (
	_ = iota
	Read
	Write
)
```

- https://go.dev/ref/spec#Constant_declarations

### Discuss the singleton pattern in Go.

**Definition:** `sync.Once` выполняет функцию ровно один раз. Документация говорит, что возврат из `f` синхронизируется-раньше возврата из любого `once.Do(f)`. **How it works:**

#### Once или переменная пакета

- **Do**: одновременные вызывающие `once.Do(f)` ждут, пока `f` не вернётся; `f` выполняет только один.
- **Нельзя копировать**: документация `Once` говорит, что `Once` нельзя копировать после первого использования.
- **init**: используйте значение уровня пакета, когда программа нуждается в нём всегда. Используйте `Once`, когда цену стоит отложить до первого использования.

**When to use:**

#### Один общий ресурс

- Используйте `Once` для ленивого соединения или разбора шаблона, который может запустить любая горутина.
- Передавайте зависимость параметром, когда тесты должны её подменить. Процессный синглтон тогда неподходящая форма.

**Examples:**

```go
var (
	once sync.Once
	db   *sql.DB
)

func DB() *sql.DB {
	once.Do(func() {
		db, _ = sql.Open("example", "")
	})
	return db
}
```

- **В языке нет хранилища на горутину**: данные запроса едут в аргументах и в `context.Context`, поэтому обработчики `net/http` принимают `Request`, а не читают окружающее состояние горутины.
- **Владение**: codewalk про разделяемую память кладёт изменяемую карту в одну горутину и шлёт обновления внутрь. Это выбор устройства, который объясняет модель памяти.
- **Время жизни**: каждому оператору `go` нужен способ закончиться: закрытый канал, `WaitGroup` или отменённый `Context`. Иначе горутина и то, на что она ссылается, остаются достижимыми.

**Examples:**

```go

	for {
		select {
		case <-ctx.Done():
			return
		case j, ok := <-jobs:
			if !ok {
				return
			}
			_ = j
		}
	}
}
```

### Describe TCP/UDP network programming in Go.

**Definition:** Пакет `net` даёт переносимый интерфейс сетевого ввода-вывода, включая TCP/IP и UDP. `Dial` соединяется с именем сети вроде `tcp` или `udp`. `Listen` и `ListenPacket` принимают соединения или пакеты. `net/http` построен на этих типах; используйте `net`, когда вы говорите не на HTTP.

**When to use:**

**Examples:**


### Explain what RPC is and how Go supports it.

### What is a middleware in Go's HTTP server and how do you use it?

**Definition:** Middleware — не ключевое слово языка. Это функция, которая принимает `http.Handler` и возвращает `http.Handler`. Возвращённый обработчик делает свою работу и затем вызывает `next.ServeHTTP`. `http.HandlerFunc` адаптирует функцию к этому интерфейсу, как показывает Effective Go.

**How it works:**

#### Оберните обработчик

- **Порядок**: первая обёртка, которую вы применяете, — внешняя. Она видит запрос раньше внутреннего обработчика.
- **Значения Context**: обёртка может вызвать `r = r.WithContext(ctx)` и передать новый запрос внутрь. Обработчики должны использовать тот `Request`, который им дали.
- **Короткое замыкание**: обёртка может записать статус и вернуться, не вызывая `next`, например когда аутентификация не прошла.

**Examples:**

```go
func method(want string, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.Method != want {
			http.Error(w, "method", http.StatusMethodNotAllowed)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

### How does Go integrate with cloud services?

**Definition:** Go интегрируется с облаком так же, как с любым сетевым сервисом: через `http.Client` или модуль поставщика, который вы получаете `go get`. В стандартной библиотеке нет облачного SDK. Официальные библиотеки поставщиков — сторонние модули со своими версиями в `go.mod`.

**How it works:**

#### HTTP, модули и один бинарник

- **Клиент**: `http.NewRequestWithContext` плюс контекст с таймаутом — переносимый вызов. Закрывайте `resp.Body`.
- **Модули**: `go get` модуля поставщика на семантической версии. `GOPRIVATE` применяется, если путь модуля закрытый.
- **Развёртывание**: `GOOS` и `GOARCH` кросс-компилируют пакет `main`. Результат — бинарник, который запускает хост; язык не встраивает облачную среду выполнения.

**Examples:**

```go
func get(ctx context.Context, url string) error {
	req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
	if err != nil {
		return err
	}
	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	return nil
}
```

### How would you integrate a Go application with a message queue?

**Definition:** В стандартной библиотеке нет клиента очереди сообщений. Интеграция — сторонний модуль или протокол, на котором вы говорите через `net`, если брокер — простой TCP. Что Go даёт — конкурентность вокруг клиента: горутина, которая получает, `Context`, который отменяет, и логика подтверждения, которую вы пишете обычным кодом.

**How it works:**

#### Цикл потребителя

- **Модуль**: `go get` клиента брокера на Go и импортируйте его. Зафиксируйте версию. API принадлежит этому модулю, а не `net/http`.
- **Отмена**: цикл выбирает `ctx.Done()`, чтобы остановка прекратила получение.
- **Хотя бы один раз**: если подтверждение клиента — отдельный вызов, сбой между обработкой и подтверждением доставит снова. Сделайте обработчик безопасным для двойного запуска или используйте транзакционный API клиента, если он его документирует.

**Examples:**

```go
func consume(ctx context.Context, next func(context.Context) error) error {
	for {
		if err := ctx.Err(); err != nil {
			return err
		}
		if err := next(ctx); err != nil {
			return err
		}
	}
}
```

<summary>What options are there for ORM in Go?</summary>

### What options are there for ORM in Go?

**Definition:** `database/sql` — не ORM. Это обобщённый интерфейс SQL плюс драйвер: вы пишете SQL, а `QueryContext` возвращает `*Rows`, которые вы сканируете в переменные. ORM и генераторы запросов — сторонние модули поверх `database/sql` или собственных драйверов.

**How it works:**

#### SQL в стандартной библиотеке

- **Scan**: `rows.Scan(&id, &name)` копирует столбцы в значения Go. Отображение принадлежит вам.
- **Модуль**: ORM добавляют через `go get` и импортируют как любую зависимость. Его поведение — документация этого модуля, а не `database/sql`.
- **Драйверы**: `sql.Open` нужен зарегистрированный драйвер. Пустой импорт пакета драйвера запускает его `init`.

**When to use:**

#### SQL, который видно, или модуль

- Используйте `database/sql`, когда запросы и есть API и вам нужен пул драйвера из стандартной библиотеки.
- Добавляйте модуль ORM, когда команда принимает его правила отображения и версия зафиксирована. Оставляйте `sql` для операторов, которые должны оставаться видимыми.

**Examples:**

```go
func names(ctx context.Context, db *sql.DB) ([]string, error) {
	rows, err := db.QueryContext(ctx, "select name from users")
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	var out []string
	for rows.Next() {
		var name string
		if err := rows.Scan(&name); err != nil {
			return nil, err
		}
		out = append(out, name)
	}
	return out, rows.Err()
}
```

### Discuss how to use Docker with Go applications.

**Definition:** Docker — не инструмент Go. Что даёт Go — бинарник из `go build`. Образ контейнера копирует этот бинарник и запускает его. `CGO_ENABLED=0` собирает без cgo, чтобы бинарник не зависел от библиотеки C машины сборки. Кросс-компилируйте через `GOOS` и `GOARCH`, чтобы совпасть с образом.

**How it works:**

#### Бинарник, который образ может запустить

- **Сборка**: `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app ./cmd/app` даёт бинарник Linux amd64 без cgo.
- **Адрес прослушивания**: привяжите `http.Server` к `0.0.0.0:port` или `:port`, если процесс должен принимать соединения не только с loopback контейнера.
- **Модули в сборке**: сборке образа нужны `go.mod` и `go.sum`, чтобы `go build` разрешал те же версии.

**Examples:**

```go
func listen() error {
	return http.ListenAndServe(":8080", nil)
}
```

<summary>Explain the role of WebAssembly with Go.</summary>

### Explain the role of WebAssembly with Go.

**Definition:** FAQ говорит, что программы Go компилируются заранее в машинный код или, для некоторых реализаций, в JavaScript или WebAssembly. `GOARCH=wasm` — эта архитектура. Заметки команды go о `-buildmode=c-shared` говорят, что на `wasip1` сборка даёт реактор/библиотеку WASI, чьи вызываемые символы — функции, экспортированные через `//go:wasmexport`.

**How it works:**

#### wasm и wasip1

- **Один CPU на порте wasm**: `runtime.GOMAXPROCS` принудительно ставит `n` в 1, когда `GOARCH` — `wasm`, потому что комментарий этого порта говорит, что у WebAssembly ещё нет потоков.
- **js/wasm и wasip1**: `GOOS=js GOARCH=wasm` целится в хост JavaScript. `GOOS=wasip1 GOARCH=wasm` целится в WASI. В команде go это разные значения операционной системы.
- **Не по умолчанию**: обычный `go build` целится в `GOOS`/`GOARCH` хоста. Wasm выбирают, задавая эти переменные.

**When to use:**

#### Хост Wasm, который должен выполнить этот модуль

- Компилируйте в `js/wasm`, когда хост — браузер или другой встраиватель JavaScript, который загружает среду выполнения Go wasm.
- Компилируйте в `wasip1`, когда хост говорит на WASI. Не ждите `GOMAXPROCS` выше 1 на архитектуре wasm; runtime его ограничивает.

**Examples:**

```go
// GOOS=wasip1 GOARCH=wasm go build -o app.wasm .
```

**Sources:**

- https://go.dev/doc/faq
- https://pkg.go.dev/cmd/go
- https://pkg.go.dev/runtime#GOMAXPROCS
</details>
