### Что такое web security, and why is it important?

**Definition:**

**Веб-безопасность** охватывает стратегии и технологии, направленные на защиту систем, подключённых к интернету, включая веб-приложения и сервисы, от разных угроз. Для бизнеса это первостепенное соображение: так сохраняют данные и доверие пользователей.

**How it works:**

Фундаментальные принципы безопасности

- **Конфиденциальность**: чувствительная информация доступна только уполномоченным сторонам.
- **Целостность**: точность и достоверность данных сохраняются.
- **Доступность**: ресурсы и сервисы доступны, когда они нужны.

Компоненты веб-безопасности

Transport Layer Security (TLS)

**TLS** служит основой безопасной связи в интернете и обеспечивает шифрование и целостность данных механизмами вроде симметричного и асимметричного шифрования.

Контроль доступа

- **Аутентификация**: проверяет личность пользователей через учётные данные или многофакторные методы.
- **Авторизация**: определяет доступ пользователя к ресурсам и сервисам по его правам.

Заголовки безопасности

**HTTP Security Headers** — заголовки HTTP-ответа, созданные чтобы усилить безопасность веб-приложения. Они задают строгие политики веб-безопасности, защищают от конкретных атак и помогают обнаруживать и смягчать возможные уязвимости.

- **X-Content-Type-Options**: не даёт угадывать тип содержимого.
- **X-Frame-Options**: защищает от clickjacking.
- **Content-Security-Policy**:  смягчает атаки межсайтового скриптинга и другие атаки внедрения кода.
- **X-XSS-Protection**: включает в браузерах фильтр Cross-site scripting (XSS).

Достоверность и очистка данных

Правильная проверка и очистка входных данных от пользователей критичны, чтобы не допустить атаки внедрения и подмены.

- **Cross-Site Scripting (XSS)**: атаки, при которых в браузере пользователя выполняется вредоносный скрипт.
- **SQL Injection**: использует код работы с базой, чтобы выполнить неразрешённые SQL-команды.

Anti-CSRF-токены

Токены **Cross-Site Request Forgery (CSRF)** смягчают несанкционированные запросы, которые отправляют от имени доверенных аутентифицированных пользователей.

Управление сессиями

Чтобы безопасно поддерживать пользовательские сессии, нужно учитывать практики генерации, срока жизни и хранения токена сессии.

- **Флаги безопасной cookie**: дополнительные флаги вроде «Secure» и «HttpOnly» помогают защититься от некоторых атак, таких как перехват сессии и межсайтовый скриптинг.
- **Перевыпуск сессии**: регулярная смена токенов сессии сужает окно возможностей для атакующего.

**Examples:**

Пример кода: установка HTTP-заголовков безопасности

Вот код на Python:

```python
from flask import Flask

app = Flask(__name__)

# Example: Setting Content-Security-Policy Header
@app.after_request
def add_security_headers(response):
    response.headers.add('Content-Security-Policy', 
                          "default-src 'self'; script-src 'self' 'unsafe-inline';")
    return response

if __name__ == '__main__':
    app.run()
```

### Можете ли вы explain what HTTPS is and how it differs from HTTP?

**Definition:**

**HTTPS** (HyperText Transfer Protocol Secure) — расширение HTTP, которое добавляет протоколы безопасности для более защищённой передачи данных. Это необходимо, чтобы **сохранять приватность** и защищать чувствительные данные при действиях в сети: финансовых операциях, отправке форм и входе пользователей.

**How it works:**

Ключевые свойства

- **Шифрование данных**: использует криптографические протоколы вроде SSL/TLS, чтобы кодировать сообщения.
- **Проверка сертификата**: аутентифицирует серверы и в некоторых случаях клиентов.
- **Целостность данных**: применяет хеш-функции, чтобы подтвердить, что содержимое сообщения не подменили.

Чем HTTP отличается от HTTPS

- **Механизмы безопасности**: HTTP передаёт данные открытым текстом, а HTTPS добавляет протоколы безопасности вроде SSL/TLS.
- **Номер порта**: HTTP обычно использует порт 80, а HTTPS — порт 443.
- **Скорость передачи**: HTTPS может быть чуть медленнее из-за шифрования.
- **Поведение браузера по умолчанию**: современные браузеры могут помечать HTTP-сайты как «Not Secure».
- **SEO и стратегия поисковых систем**: защищённые сайты ранжируются выше.

Рукопожатие SSL/TLS

Когда `Client` подключается к `Server`:

1. **ClientHello**: `Client` начинает обмен и сообщает свои требования и возможности.
2. **ServerHello**: `Server` выбирает лучший cipher suite и сообщает об этом `Client`. Он также отдаёт свой открытый ключ, если используется асимметричное шифрование.
3. **Certificate**: `Server` посылает свой SSL-сертификат вместе с дополнительными сертификатами, включая открытый ключ Certificate Authority (CA) для проверки.
4. **Key Exchange**: `Client` и `Server` вычисляют общий ключ сессии, нужный для симметричного шифрования.
5. **Finished**: обе стороны посылают проверочное сообщение на основе хеша и тем самым подтверждают, что защищённый канал установлен.
6. **Secure Data Transmission**: общий секретный ключ используется для симметричного шифрования.

Обычные термины безопасности в HTTP(S)

- **SSL/TLS**: протоколы, которые отвечают за защищённые соединения.

- **Certificate Authority (CA)**: доверенная сторона, которая выпускает SSL-сертификаты.

- **Cipher Suite**: набор механизмов шифрования данных, аутентификации и обмена ключами для защищённого соединения.

- **Протоколы рукопожатия**: клиент и сервер во время рукопожатия согласуют подходящую конфигурацию безопасности.

- **Public Key Infrastructure (PKI)**: каркас, который управляет использованием и распространением цифровых сертификатов.

**Examples:**

Пример кода: простой HTTP-сервер

Вот код на Python:

```python
from http.server import HTTPServer, BaseHTTPRequestHandler

class SimpleHTTPRequestHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b'Hello, world!')

httpd = HTTPServer(('localhost', 8000), SimpleHTTPRequestHandler)
httpd.serve_forever()
```
Командой `openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365` создают самоподписанный SSL-сертификат.

Пример кода: простой HTTPS-сервер

Вот код на Python:

```python
from http.server import HTTPServer, BaseHTTPRequestHandler
import ssl

class SimpleHTTPRequestHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.end_headers()
        self.wfile.write(b'Hello, secure world!')

httpd = HTTPServer(('localhost', 4443), SimpleHTTPRequestHandler)
httpd.socket = ssl.wrap_socket(httpd.socket, certfile='cert.pem', keyfile='key.pem', server_side=True)
httpd.serve_forever()
```

### Что такое SSL and TLS, and what role do they play in web security?

**Definition:**

**SSL** (Secure Sockets Layer) и **TLS** (Transport Layer Security) — криптографические протоколы, которые создают защищённое шифрованное соединение между клиентом и сервером. Благодаря этому данные, передаваемые по сети, защищены, и их непросто перехватить или подменить. Это особенно важно для чувствительных данных: учётных данных входа, личной информации и финансовых операций.

**How it works:**

Ключевые свойства

- **Аутентификация**: сертификаты проверяют личность сервера и подтверждают, что клиент говорит с нужным сервером, а не с самозванцем.

- **Конфиденциальность**: данные между клиентом и сервером шифруются, и их содержимое скрыто от неуполномоченных сторон.

- **Целостность**: с помощью цифровых подписей SSL/TLS гарантирует, что данные не изменились при передаче. Если обнаружена подмена, соединение разрывается.

- **Forward Secrecy**: каждая сессия SSL/TLS использует свежий уникальный ключ шифрования, поэтому компрометация одного ключа не затронет прошлый или будущий обмен.

- **Совместимость**: SSL и TLS рассчитаны на совместимость назад и вперёд, чтобы старые и новые системы могли общаться безопасно.

- **Защита от известных уязвимостей**: современные версии TLS включают последние практики безопасности и могут смягчать риски вроде перехвата сессии, атак человек-посередине и других.

Механизмы шифрования

SSL/TLS использует разные алгоритмы шифрования. В рукопожатии они нужны для обмена ключами и чтобы установить защищённый канал связи, по категориям:

- **Симметричное шифрование**: один ключ общий у клиента и сервера и служит и для шифрования, и для расшифровки. Обычные алгоритмы: AES и RC4.

- **Асимметричное шифрование**: также криптография с открытым ключом. Используется пара ключей — один открытый, один закрытый. Данные, зашифрованные одним, можно расшифровать только другим. Этот тип обычно применяют для безопасного обмена симметричными ключами и для начальной аутентификации. Обычные алгоритмы: RSA, Diffie-Hellman и Elliptic Curve Cryptography (ECC).

- **Хеш-функции**: обеспечивают целостность данных и создают дайджест сообщения или контрольную сумму. Обычные алгоритмы: варианты SHA (Secure Hash Algorithm), например SHA-256.

Рукопожатие SSL/TLS

Прежде чем начнётся обмен данными, клиент и сервер устанавливают защищённое соединение через **рукопожатие**. Его основные шаги:

1. **Hello Messages**: клиент и сервер обмениваются сообщениями, чтобы начать рукопожатие.

2. **Certificate Exchange**: сервер предъявляет свой сертификат SSL/TLS, в котором есть его открытый ключ, подписанный признанным Certificate Authority (CA).

3. **Key Exchange**: если нужно, безопасный ключ сессии обменивают с помощью асимметричного шифрования.

4. **Symmetric Key Session Creation**: создаётся уникальный ключ сессии (например ключ сессии для симметричного шифра) и безопасно разделяется между клиентом и сервером.

5. **Establish Cipher Suite**: согласуется набор алгоритмов шифрования, хеша и рукопожатия на всю сессию.

6. **Handshake Completion**: обе стороны подтверждают, что рукопожатие завершено.

Эволюция: от SSL к TLS

SSL был основой развития защищённой веб-связи, но его в значительной степени **вывели из употребления** из-за хорошо описанных уязвимостей безопасности.
Это привело к созданию преемника, TLS, у которого было несколько версий, и каждая улучшала предыдущую по безопасности и возможностям.

SSL и TLS в браузере

Чтобы проверить статус SSL/TLS сайта в Google Chrome, например, можно нажать на значок замка и посмотреть сертификат. Более полную картину безопасности сайта даёт нажатие на «Not secure» или на значок замка. Там видны дополнительные детали: защищено ли соединение и есть ли проблемы безопасности.

### Как SSL certificates work, and what is the puRPOse of a Certificate Authority (CA)?

**Definition:**

Разберём назначение и механизмы **SSL-сертификатов** и роль **Certificate Authorities**.

**How it works:**

Secure Sockets Layer и Transport Layer Security

Протоколы **SSL/TLS** дают защищённый канал между двумя машинами и обеспечивают приватность, целостность и аутентификацию.

Главные составные части:

1. **Цифровое рукопожатие**: устанавливает сессию, согласует алгоритм шифрования и порождает ключи сессии.
2. **Key Exchange**: криптография с открытым ключом, чтобы разделить секретный ключ для дальнейшего симметричного шифрования, сочетая скорость и безопасность.
3. **Шифрование**: общий секретный ключ используется для симметричного шифрования данных.
4. **Проверка**: сертификаты дают средство аутентифицировать стороны.

Certificate Authority (CA)

**Certificate Authority** — доверенная сторона, которая проверяет личности субъектов, прежде чем выпустить сертификаты, подтверждающие их подлинность.

Основные функции CA:

1. **Аутентификация**: проверка личности субъектов, которые запрашивают сертификат.
2. **Выпуск**: создание и цифровая подпись сертификатов для проверенных субъектов.
3. **Отзыв**: механизмы признать сертификат недействительным, если он скомпрометирован.

Состав сертификата

Обычный SSL-сертификат состоит из таких разделов:

1. **Сведения об издателе**: данные органа, который выпустил сертификат.
2. **Срок действия**: даты начала и конца, когда сертификат считается действительным.
3. **Сведения о субъекте**: идентифицирующая информация того, кому выдан сертификат, например доменное имя.
4. **Открытый ключ**: ключевой элемент шифрования, который делает связь защищённой.
5. **Подпись**: хеш данных сертификата, подписанный закрытым ключом издающего органа.

Форматы сертификатов

SSL-сертификаты существуют в основном в двух форматах:

1. **Base64-encoded** \( \rightarrow \) удобен для обмена между системами и для чтения человеком.
2. **DER (Distinguished Encoding Rules)** \( \rightarrow \) двоичный формат с более компактным размером, подходящий для машин.

Как получают SSL-сертификаты

SSL-сертификаты получают несколькими способами. Основные:

1. **Самоподписанные сертификаты**: подходят для личной или локальной проверки, где участие CA может быть не нужно. В production их обычно не используют из-за проблем доверия.
2. **Сертификаты публично доверенных CA**: выпускаются устоявшимися CA и широко принимаются браузерами и системами. Они требуют тщательной проверки личности, чтобы владелец сертификата был законным.

### Что такое the difference between encryption and hashing?

**Definition:**

И **шифрование**, и **хеширование** — криптографические методы, которые усиливают безопасность данных. Но цели у них разные, и у этих ролей разные функции и свойства.

**How it works:**

Главные различия и случаи применения

- **Шифрование** защищает данные обратимо, с помощью ключей: понять их можно только с правильным ключом. Это полезно, чтобы хранить данные конфиденциальными.

- **Хеширование**, напротив, одностороннее: оно превращает входные данные в уникальную строку фиксированной длины, **хеш-значение**, которое представляет исходные данные. Это полезно, чтобы проверять целостность данных и аутентифицировать личности, особенно для паролей, где исходные данные не должны быть нужны или известны.

Односторонний процесс (хеширование)

Данные проходят одностороннее преобразование:

- **Вход**: исходные данные, например сообщение или пароль.
- **Хеш-функция**: математический алгоритм, который обрабатывает вход в выход фиксированной длины, известный как хеш-значение.

Случай применения: управление паролями

Вместо паролей открытым текстом безопаснее хранить их хеши. Когда пользователь присылает пароль для сравнения, система хеширует ввод и проверяет, совпадает ли полученный хеш с сохранённым. Это усиливает безопасность данных: даже если сохранённое значение хеша скомпрометировано, исходный пароль остаётся защищён.

Двусторонний процесс (шифрование)

- **Вход**: данные
- **Алгоритм шифрования**: превращает вход в шифротекст.
- **Ключ**: необходим для шифрования. Без правильного ключа почти невозможно расшифровать шифротекст обратно в исходный вид.

**Examples:**

Вычисление зашифрованного значения

Вот код на Python:

```python
from cryptography.fernet import Fernet

# Generate a key to be used for encryption/decryption
key = Fernet.generate_key()

# Initialize the Fernet cipher using the generated key
cipher_suite = Fernet(key)

# Text to encrypt
text = b"Hello, this is a secret message!"

# Encrypt the text using the cipher
cipher_text = cipher_suite.encrypt(text)

print(f"Cipher Text: {cipher_text}")

# Decrypt the text back to its original form
original_text = cipher_suite.decrypt(cipher_text)
print(f"Original Text: {original_text.decode()}")
```

### Определите the concept of a secure session and explain how it is established.

**Definition:**

**Защищённая сессия** — это оберегаемый интерактивный обмен между веб-сервером и пользователем через постоянное шифрованное соединение. Это взаимное доверие устанавливается через **управление ключом сессии**, после чего шифруются и расшифровываются все передачи данных.

**How it works:**

Управление ключом сессии

**Ключ сессии** — криптографическая опора защищённых сессий. Это сравнительно недолговечный симметричный ключ, которым шифруют данные во время сессии. Обе стороны — веб-сервер и браузер пользователя — получают ключ сессии, чтобы поддерживать конфиденциальный обмен.

      - Веб-сервер порождает ключ сессии и остаётся его единственным владельцем.

      - Ключ сессии отправляется в браузер пользователя асимметричным шифрованием (криптография с открытым ключом). Открытым ключом пользователя шифруют ключ сессии.

      - Дальнейший обмен во время сессии заворачивается в ключ сессии.

Порождение ключа

- **Случайность**: безопасность ключа сессии держится на его непредсказуемости. Подходящие криптографические алгоритмы и источники с высокой энтропией, например аппаратные RNG или по-настоящему случайный ввод пользователя, необходимы для случайности ключа. Согласованное хеширование может дать более прямолинейное распределение ключей.

  - **Размер ключа**: большая длина ключа укрепляет безопасность сессии. Ключи в 128 бит, например, обычно считают устойчивыми к обычным атакам.

Установление ключа сессии:

Веб-сервер и пользователь вместе добиваются того, чтобы у каждого **был ключ сессии**. Цель метода — чтобы обе стороны владели ключом и ни в какой момент его не скомпрометировали.

Обмен ключами Diffie-Hellman

Алгоритм Diffie-Hellman позволяет двум сторонам выработать общий секрет, не передавая криптографические ключи напрямую. Каждая сторона создаёт закрытый ключ и вспомогательный открытый ключ, и после ряда обменов обе вычисляют общий секрет. Этот секрет затем работает как ключ сессии.

```plaintext
  Here is the Key Exchange
  
  User:
  Private Key: a
  Public Key: g^a mod p
  
  Server:
  Private Key: b
  Public Key: g^b mod p
  Shared Secret: (g^a)^b mod p = g^(ab) mod p
```

Perfect Forward Secrecy (PFS)

Perfect Forward Secrecy гарантирует, что позднейшие технические изменения или скомпрометированные ключи сессии не раскроют всю сессию и более ранний обмен. Вместо этого для каждой новой сессии берётся заново созданный ключ сессии.

PFS особенно полезен для долгой безопасности: прошлые сессии не будут вскрыты, даже если текущая сессия скомпрометирована.

Дополнительная проверка

Чтобы ещё усилить безопасность и уверенность в установлении сессии, часто добавляют ряд механизмов:

  - **Сертификаты**: проверяют личность веб-сервера и устанавливают доверие.

  - **Системы на токенах**: превращают временные токены в сессии, чтобы данные пользователя были защищены ещё сильнее.

### Что такое some common web security vulnerabilities?

**Definition:**

Понимание обычных уязвимостей веб-безопасности критично, чтобы разрабатывать устойчивые и безопасные веб-приложения. К обычным уязвимостям безопасности относятся:

**How it works:**

Injection

**Описание**: неочищенный ввод пользователя интерпретируется backend-базой как команды, и атакующие могут выполнять произвольные SQL-команды.

**Пример**: пользователь вводит `1; DROP TABLE users--`, и база выполняет непредусмотренные команды.

Смягчение

- **Избегать динамических запросов**: предпочитать параметризованные запросы или инструменты ORM.
- **Очистка ввода**: использовать prepared statements, хранимые процедуры или проверку ввода.

Cross-Site Scripting (XSS)

**Описание**: уязвимость, при которой веб-приложения принимают и показывают содержимое от пользователя (обычно в виде HTML или JavaScript) без экранирования и очистки. Атакующие могут внедрить скрипты, скомпрометировать системы конечных пользователей или украсть данные.

**Пример**: атакующий вводит `<script>malicious_code()</script>` в поле комментария. Когда пользователь смотрит комментарий, скрипт выполняется.

Смягчение

- **Очищать ввод пользователя**: кодировать и экранировать содержимое от пользователя перед отрисовкой.
- **HTTP-заголовки и CSP**: задавать правильные заголовки `Content-Security-Policy`, чтобы ограничить загрузку ресурсов из внешних источников.

Сломанная аутентификация

**Описание**: слабости механизмов, которыми приложение аутентифицирует пользователей. Часто они возникают из плохого управления паролями, небезопасного хранения или незащищённых токенов аутентификации.

**Пример**: учётные данные администратора по умолчанию или слабые, недостаточное управление сессией, или токены **Cross-Site Request Forgery** (CSRF), которые предсказуемы или повторяются.

Смягчение

- **Строгие политики паролей**: требовать сложность и предлагать периодическую смену.
- **Безопасная работа с сессией**: использовать cookie с атрибутами `HTTPOnly` и `Secure` и непредсказуемые идентификаторы сессии.

Ошибки конфигурации безопасности

**Описание**: неточные или неполные настройки сервера, приложения или базы, которые могут дать атакующим несанкционированный доступ или чувствительные данные.

**Пример**: настройки по умолчанию для интерфейсов администратора, подробные сообщения об ошибках со стеком в production или бакеты хранилища, открытые публично вместо приватных.

Смягчение

- **Проверять и наблюдать настройки**: регулярно аудировать конфигурации.
- **Принцип наименьших привилегий**: ограничивать доступ к ресурсам по необходимости.

Insecure Direct Object References (IDOR)

**Описание**: приложение открывает пользователям внутренние объекты реализации, и злоумышленники могут подменять их или читать неразрешённые данные.

**Пример**: атакующий меняет параметр URL, который должен показать его профиль, и открывает чужой профиль.

Смягчение

- **Использовать косвенные ссылки**: применять отображения или уникальные идентификаторы, не связанные напрямую с внутренними ссылками.
- **Access Control Lists (ACL)**: внедрять тонкие механизмы контроля доступа.

Cross-Site Request Forgery (CSRF)

**Описание**: атакующий обманом заставляет жертву выполнить действия на сайте, где жертва аутентифицирована. Это может быть и переход по URL, и отправка формы сайта через другой сайт, без согласия жертвы.

**Пример**: атакующий встраивает скрытую форму во вредоносный сайт, и она отправляет запрос на банковский сайт, где жертва аутентифицирована.

Смягчение

- **Использовать anti-CSRF-токены**: токены, уникальные для аутентифицированных пользователей, или заголовки CORS (Cross-Origin Resource Sharing).

Непроверенные перенаправления и пересылки

**Описание**: сайты со ссылками или кнопками, которые перенаправляют пользователей, атакующие могут подменить и отправить пользователей на вредоносные сайты через уязвимости **URL Redirection** или **Open Redirect**.

**Пример**: у сайта есть вход без логина на сайт партнёра, и атакующий собирает ссылку на затронутый сайт, замаскированную под ссылку на нужный сайт.

Смягчение

- **Белый список или прямое отображение**: проверять ввод пользователя и сверять ссылки с белым списком известных URL или требовать прямые отображения.

### Можете ли вы explain the Cross-Site Scripting (XSS) attack and how to prevent it?

**Definition:**

В контексте веб-приложений **Cross-Site Scripting** (XSS) — это внедрение вредоносных скриптов в иначе безобидные и доверенные сайты или веб-приложения.

**How it works:**

Что делает XSS-атака

Выполняя **произвольный код** в браузере жертвы, XSS-атака может:

- Украсть чувствительную информацию: получить cookie, токены сессии или даже нажатия клавиш.
- Испортить сайты
- Перенаправить пользователей: отправить их на вредоносные сайты.
- Распространять червей: продолжать атаку, заражая других пользователей.

Типы XSS-атак

1. **Stored XSS**: скрипты хранятся в базе или другом источнике данных и затем показываются пользователям на веб-страницах.
2. **Reflected XSS**: внедрённый скрипт отражается от веб-сервера, например в сообщении об ошибке, и затем выполняется в браузере пользователя.
3. **DOM-based XSS**: атака происходит только в клиентском HTML и обходит обычные серверные меры безопасности.

Главные источники уязвимости

1. **Ввод пользователя**: весь ввод пользователя, включая поля форм и параметры запроса в URL, — потенциальные источники XSS.
2. **Данные на клиенте**: данные из GET-запросов, URL документа и якорные элементы (`<a>`) тоже могут быть векторами XSS.

Главные меры защиты

- **Кодирование вывода**: превращать специальные символы в соответствующие HTML-сущности, чтобы они показывались как текст, а не выполнялись.
- **HTTP-заголовки**: использовать Content Security Policy (CSP) и заголовок `X-XSS-Protection`, чтобы усилить защиту.
- **Проверка ввода**: задавать строгие критерии ввода и очищать его, чтобы не допустить внедрение скрипта.
- **Cookie сессии**: ставить атрибуты `HttpOnly` и `Secure`, чтобы защитить cookie.

Смягчение и строгая проверка ввода

Ключевые PHP-функции против XSS:

- **htmlspecialchars()**: превращает специальные символы в HTML-сущности. Второй параметр обязательно использовать: он задаёт механизм кодирования.

  Пример:

  ```php
  $output = htmlspecialchars($_GET['input'], ENT_QUOTES, 'UTF-8');
  ```

- **filter_var()**: в частности с `FILTER_SANITIZE_STRING`.

  Вот код на PHP:

  ```php
  $clean_input = filter_var($_GET['input'], FILTER_SANITIZE_STRING);
  ```

  При этом имейте в виду, что `FILTER_SANITIZE_STRING` может удалять символы Unicode, которые не входят в диапазон 00-7F.

- **ctype**: функции вроде `ctype_alpha()` помогают проверить, что в строке только буквенные символы.

  Пример:

  ```php
  if (ctype_alpha($_GET['username'])) {
      // Username contains only alphabetic characters
  }
  ```

Лучшие практики предотвращения

- **Разбор кода**: регулярно проверять код на возможные уязвимости.
- **Модули безопасности**: рассмотреть подключение сторонних модулей безопасности.
- **Обучение пользователей**: чтобы пользователи знали о рисках и узнавали практики безопасного общения.
- **Изолированные среды**: тестировать или выполнять недоверенный код в защищённых изолированных средах.

**Examples:**

Пример уязвимого кода

Вот код на PHP:

```php
echo $_GET['greeting'];
```

Возможный URL атаки:

```url
example.com?greeting=<script>alert('Hello, world!')</script>
```

### Что такое SQL Injection and how can you defend aGAinst it?

**Definition:**

**SQL Injection** — один из самых опасных и распространённых векторов атаки. Он злонамеренно меняет SQL-операторы через веб-приложения. Такая тактика может привести к краже данных, подмене данных и даже к несанкционированному доступу к системе.

Обычные приёмы атакующих при SQL injection

- **Поиск уязвимых точек ввода**: часто это формы или параметры URL.

- **Вынос или подмена данных**: цель может быть любой: от получения чувствительных данных до вмешательства в систему.

Защита от SQL injection

- **Параметризованные операторы**: использовать параметры-заполнители в SQL-операторах и передавать значения пользователя отдельно.
- **Хранимые процедуры**: собрать SQL-логику в одном месте и вызывать конкретные имена процедур вместо сборки произвольных SQL-запросов.

- **Очистка ввода**: проверять и очищать ввод пользователя, чтобы снизить риск внедрения.

**Examples:**

Пример кода: параметризованный запрос на Python

Вот код на Python:

  ```python
import sqlite3

conn = sqlite3.connect('example.db')
cursor = conn.cursor()

# Unsafe, vulnerable to SQL injection
query = "SELECT * FROM users WHERE username='%s' AND password='%s'" % (username, password)
cursor.execute(query)

# Safe, using parameterized query
query = "SELECT * FROM users WHERE username=? AND password=?"
cursor.execute(query, (username, password))

# Close
conn.close()
  ```

### Опишите what Cross-Site Request Forgery (CSRF) is and how to prevent it.

**Definition:**

**Cross-Site Request Forgery (CSRF)**, часто session riding или атака в один клик, обманом заставляет пользователей выполнить нежелательные действия, пока они аутентифицированы на другом сайте.

**How it works:**

Механизм

- **Жертва**, открывая вредоносный сайт, остаётся аутентифицированной на доверенном сайте в другой вкладке или сессии браузера.

- **Атакующий** загружает изображение, iframe или тег скрипта с запросом к доверенному сайту, и из-за активной сессии жертвы запрос выполняется без согласия пользователя.

Этот прорыв случается, потому что веб-приложения **не проверяют** источник входящих запросов.

Стратегии предотвращения

1. **Same-Origin Policy**: современные браузеры ограничивают, как веб-страница может взаимодействовать с ресурсами других доменов, и смягчают многие сценарии CSRF. Подход в целом эффективен, но у него есть ограничения.

2. **Synchronizer Token Pattern**: веб-приложение встраивает уникальный случайный токен в каждую HTML-форму и/или HTTP-запрос. При отправке сервер проверяет, что токен есть и что он согласован с сессией пользователя. Этот приём, известный как **CSRF-токен**, даёт более крепкую защиту.

3. **Двойные cookie**: помимо cookie сессии пользователя веб-сервер порождает вторую cookie, часто доступную только через HTTP-заголовки. Этот дополнительный слой безопасности бесценен, если основная cookie сессии скомпрометирована.

4. **Подтверждение пользователя**: критические действия только через прямое взаимодействие пользователя, например нажатие кнопки, а не автоматический запрос, отбивают обычные CSRF-эксплойты.

5. **Всегда использовать HTTPS**: HTTPS включает шифрование и цифровые сертификаты и даёт защищённый канал для данных, усиливая защиту от CSRF и многих других векторов атаки.

<summary>Объясните the Same-Origin Policy and its importance in web security.</summary>

### Объясните the Same-Origin Policy and its importance in web security.

**Definition:**

**Same-Origin Policy** (SOP) — основополагающее понятие веб-безопасности, которое защищает от **междоменных атак** и раскрытия данных и делает просмотр безопаснее и приватнее.

**How it works:**

Основной принцип

**SOP** требует, чтобы веб-браузер ограничивал взаимодействие документов из разных origin и тем самым не допускал возможные прорывы безопасности.

Как опознать origin

**Origin** — это сочетание:

- **Протокол**
- **Домен**
- **Порт**

Чтобы две веб-страницы имели общий origin и тем самым не попадали под ограничения SOP, все эти компоненты должны совпасть.

Управление междоменным взаимодействием

Браузеры разрешают контролируемый междоменный доступ такими механизмами:

- **Cross-Origin Resource Sharing (CORS)**: серверы могут указать веб-ресурсы, доступные разным origin, и ослабить строгость SOP.

- **Iframe**: это окна, встроенные в веб-страницу, полезные чтобы встроить сторонний контент, например ленты соцсетей или рекламу. Современные iframe настраиваются и могут разрешать или ограничивать междоменное поведение.

Значение для веб-безопасности

SOP — **краеугольный камень веб-безопасности**, потому что он:

- **Бережёт данные пользователя**: SOP не даёт вредоносным сайтам произвольно читать чувствительную информацию пользователя на законных сайтах в той же сессии браузера.

- **Смягчает Cross-Site Scripting (XSS)**: ограничивая скрипты и другое динамическое содержимое своим origin, SOP пресекает многочисленные векторы XSS.

- **Сдерживает Cross-Site Request Forgery (CSRF)**: SOP помогает устранять несанкционированные межсайтовые запросы, которые могут манипулировать сессией пользователя на другом origin.

- **Предотвращает кражу cookie**: данные вроде токенов сессии в cookie нельзя унести между origin, и аутентификация пользователя крепче.

- **Поддерживает конфиденциальность веб-приложений**: поддерживает конфиденциальность веб-приложений и помогает не допустить утечку информации.

Ограничения SOP

SOP — сильный и фундаментальный инструмент безопасности, но у него есть ограничения, например:

- **Возможное недопонимание**: сайт с множеством поддоменов может запутать пользователей, что именно составляет «тот же origin», и привести к случайному раскрытию данных.
- **Лазейки в старых браузерах**: эффективность SOP различается между браузерами. Ранние версии могут применять её неравномерно и открывать возможные прорывы безопасности.
- **Несовместимость с децентрализованными системами**: некоторые распределённые системы, например на blockchain и с децентрализованным обменом файлами, плохо уживаются с ограничениями SOP, и это мешает их ровной работе.

<summary>Что такое Clickjacking, and what measures can prevent it?</summary>

### Что такое Clickjacking, and what measures can prevent it?

**Definition:**

**Clickjacking**, также атака подмены интерфейса, — угроза веб-безопасности, при которой пользователя **обманом заставляют нажать не на то, что он видит, и это часто ведёт к непреднамеренным действиям**. Обычно проблема возникает из уязвимостей cross-site scripting (XSS) на сайте.

**How it works:**

Обычные приёмы clickjacking

- **Наложения iframe**: атакующие кладут прозрачный позиционированный iframe поверх безобидного элемента, чтобы перехватывать клики.
- **Наложения на CSS**: манипулируя z-index и позицией div, атакующие делают так, что настоящие кнопки оказываются под внешне безобидными элементами.
- **Drag & Drop**: имитирует действия пользователя и обманом заставляет перетащить чувствительную информацию на вредоносную цель.

Механизмы защиты от clickjacking

X-Frame-Options

HTTP-заголовок ответа **`X-Frame-Options`** смягчает clickjacking, управляя встраиванием во фрейм. У него три возможных значения:

1. **DENY**: запрещает любое обрамление, и сайты открываются только отдельно.
2. **SAMEORIGIN**: ограничивает обрамление тем же origin (доменом) и защищает от внешнего встраивания.
3. **ALLOW-FROM uri**: разрешает ограниченное обрамление с конкретного URI и допускает условное встраивание.

Реализация:

- **HTTP-заголовок**:

  ```http
  X-Frame-Options: SAMEORIGIN
  ```

- **Мета-тег**:

  Этот мета-тег следует поместить в секцию `<head>` HTML-страниц.

  ```html
  <meta http-equiv="X-Frame-Options" content="SAMEORIGIN">
  ```

Content Security Policy (CSP)

**CSP** — мощный заголовок, который задаёт разрешённые источники для разных типов содержимого и даёт детальный контроль над тем, что можно загрузить на странице.

- **Директива frame-ancestors**: ограничивает встраивание во фрейм. Значение `'self'` или конкретный домен помогает предотвратить clickjacking.

  ```http
  Content-Security-Policy: frame-ancestors 'self'
  ```

Защита на JavaScript

- **Скрипты frame-busting**: используют JavaScript, чтобы страница не загружалась во фрейме, и тем самым предотвращают clickjacking.

  Например, включите код ниже в секцию `<head>`:

  ```html
  <script>
    if (self !== top) {
      top.location = self.location;
    }
  </script>
  ```

- **Pointer Lock API**: более сложный вариант. Этот API можно использовать, чтобы ограничить движение мыши заданной областью веб-страницы.

   Pointer Lock API может быть не общим решением; однако блокировка не даст iframe двигать связанные элементы во время попыток clickjacking.

  startPointerLock()

Безопасный просмотр с защитой от clickjacking

Когда приложение или сайт применяет крепкие механизмы защиты вроде **X-Frame-Options**, **Content Security Policy** и **тактик на JavaScript**, риск clickjacking существенно снижается, и просмотр для пользователей остаётся безопасным и заслуживающим доверия.

- **Префиксы cookie**: использовать `__Host-` и `__Secure-` для дополнительной безопасности.

<summary>Что такое Man-in-the-Middle (MitM) attack and how can it be prevented?</summary>

### Что такое Man-in-the-Middle (MitM) attack and how can it be prevented?

**Definition:**

Атаки **Man-in-the-Middle (MitM)** происходят, когда злоумышленник перехватывает связь между двумя сторонами. Такой прорыв может привести к краже данных или подделке информации.

**How it works:**

Обычные сценарии MitM

- **Сети Wi-Fi**: незащищённые публичные сети Wi-Fi — главные цели атак MitM.
- **Поддельные сайты**: атакующие создают фальшивые сайты, чтобы захватить учётные данные входа.
- **Почта**: зашифрованные письма можно перехватить, прочитать и изменить.

Меры предотвращения

1. **Цифровые сертификаты**: использовать SSL/TLS на серверах и правильно проверять сертификаты на клиентах.
2. **Шифрование**: применять сквозное шифрование каналов связи.
3. **Public Key Infrastructure (PKI)**: использовать проверенные цифровые сертификаты для надёжной идентификации и целостности данных.
4. **Multi-Factor Authentication (MFA)**: добавлять слои проверки личности помимо паролей.
5. **Строгие политики паролей**: требовать сложные пароли и поощрять регулярное обновление.
6. **Программы осведомлённости**: обучать пользователей замечать подозрительное поведение и возможные признаки MitM.
7. **Безопасные приложения**: использовать аутентифицированное, проверенное и обновлённое ПО. Проводить регулярные аудиты безопасности.

Дополнительные слои с Transport Layer Security (TLS)

- **Certificate Pinning**: привязка конкретного сертификата к приложению, чтобы не допустить несанкционированную подмену.
- **HTTP Strict Transport Security (HSTS)**: указание веб-браузерам общаться с сервером только по HTTPS.

Сетевые механизмы против угроз MitM

- **Аутентификация Ethernet**: IEEE 802.1X даёт контроль доступа к сети и снижает риски MitM.
- **Wi-Fi Protected Access 2 (WPA2)**: усиленные протоколы безопасности по сравнению с WEP и WPA, укрепляют беспроводную безопасность.
- **Intrusion Detection Systems (IDS) и Intrusion Prevention Systems (IPS)**: активное наблюдение за подозрительной сетевой активностью.

**Examples:**

Пример кода: SSL/TLS в Node.js

Вот код на Node.js:

```javascript
const https = require('https');
const fs = require('fs');

const options = {
  key: fs.readFileSync('key.pem'),
  cert: fs.readFileSync('cert.pem')
};

https.createServer(options, (req, res) => {
  // Handle secure requests
}).listen(443);
```

### Опишите the concept of session management in web security.

**Definition:**

**Управление сессиями** — опорный механизм веб-безопасности. Оно поддерживает состояние между веб-страницами и безопасно управляет личностями и правами пользователей. Оно сочетает cookie, токены и данные на сервере, чтобы следить за действиями пользователя в рамках одной сессии.

**How it works:**

Зачем управление сессиями нужно веб-безопасности

- **Защита данных**: чувствительные сведения пользователя меньше раскрыты, и риск несанкционированного доступа снижается.
- **Контроль доступа**: только аутентифицированные пользователи получают доступ к защищённым ресурсам.
- **Приватность пользователя**: ограничение слежения текущей сессией усиливает приватность пользователя.

Обычные механизмы управления сессиями

- **Cookie**: текстовые файлы на устройстве пользователя, в которых есть идентификация сессии.
- **Переписывание URL**: дописывать идентификаторы сессии к URL.
- **Скрытые поля форм**: хранить идентификаторы сессии в веб-формах.
- **HTTP-заголовки**: использовать собственные заголовки для слежения за сессией.
- **Сессии**: хранение на сервере, которое поддерживается между сервером и клиентом через уникальный идентификатор сессии.

Риски плохого управления сессиями

- **Перехват сессии**: неаутентифицированные стороны берут сессию под контроль.
- **Фиксация сессии**: атакующие манипулируют сессией, чтобы получить несанкционированный доступ.
- **Cross-Site Request Forgery (CSRF)**: вредоносные сайты побуждают пользователя к действию на другом сайте, где пользователь аутентифицирован.

Лучшие практики безопасного управления сессиями

- **Соединения, шифрованные SSL/TLS**: разворачивать HTTPS, чтобы защитить данные в пути.
- **Тайм-аут сессий**: завершать неактивные сессии после заданного срока.
- **Случайные идентификаторы сессии**: порождать уникальные, трудно угадываемые идентификаторы сессии.
- **Проверка на сервере**: перепроверять детали сессии на сервере для дополнительной безопасности.
- **Cookie с флагами Secure и HTTPOnly**: cookie должны уходить только по защищённым соединениям и оставаться недоступными для JavaScript.

Обычные веб-уязвимости, связанные с управлением сессиями

- **Предсказание или вывод сессии**: предсказуемые идентификаторы сессии повышают уязвимость к атакам.
- **Неверно настроенные заголовки Cross-Origin Resource Sharing (CORS)**: плохо настроенные заголовки могут позволить неавторизованным сайтам читать данные сессии пользователя.
- **Ошибки конфигурации Transport Layer Security (TLS)**: слабые или устаревшие настройки TLS могут скомпрометировать безопасность сессии.

**Examples:**

```java
sessionCookie.setSecure(true);  // Ensures the cookie is only sent over HTTPS
response.addCookie(sessionCookie);  // Add the cookie to the response
```

В веб-приложении на Java объект `response` используется, чтобы отправить cookie клиенту.

<summary>Что такое the difference between authentication and authorization?</summary>

### Что такое the difference between authentication and authorization?

**Definition:**

**Аутентификация** проверяет, что субъект — тот, за кого себя выдаёт, с помощью одного или нескольких аутентификаторов: пароля, отпечатка или токена. **Авторизация** проверяет, что запрошенное действие или сервис этому субъекту разрешены. Вошедший пользователь часто всё равно не может выполнять все действия, которые система технически умеет.

**How it works:**

OWASP разделяет эти проверки. Аутентификация устанавливает личность. Авторизация затем решает, какие операции этой личности доступны, а часть публичных ресурсов доступна и без входа.

В HTTP-фреймворке аутентификации неудачный или отсутствующий вызов учётных данных даёт `401` (Unauthorized) и заголовок `WWW-Authenticate`. Верные учётные данные, которых всё же недостаточно для ресурса, дают `403` (Forbidden). Сервер может вернуть `404` (Not Found), если не должен раскрывать существование ресурса.

Защита: запрет по умолчанию, наименьшие привилегии и проверка права на каждый запрос на сервере, шлюзе или serverless-функции. Проверки в браузере только для интерфейса. При отказе завершайте работу в безопасном состоянии и не отдавайте в ошибке журналы или отладочные данные.

**When to use:**

Аутентифицируйте, когда нужно знать, кто вызывает. Авторизуйте каждую защищённую операцию после этого, включая намеренно публичное чтение без входа. `401` — когда вызывающему стоит повторить запрос с учётными данными, `403` — когда этот уже известный вызывающий не должен получить ресурс.

**Examples:**

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Access to the staging site"
```

<summary>Объясните basic authentication and its weaknesses.</summary>

### Объясните basic authentication and its weaknesses.

**Definition:**

HTTP-схема **Basic** (RFC 7617) передаёт идентификатор и пароль парой в кодировке base64 в заголовке запроса `Authorization`. Base64 — обратимое кодирование, не шифрование. Сервер вызывает клиента ответом `401` и заголовком `WWW-Authenticate` со схемой и realm.

**How it works:**

Браузер обычно показывает запрос пароля и повторяет запрос с `Authorization: Basic` и закодированными учётными данными. Они уходят и в следующих запросах к этому realm. MDN указывает, что схема небезопасна без HTTPS/TLS: кто прочитает байты, восстановит пароль.

Basic плохо подходит браузерным приложениям, которые меняют данные: агент прикладывает учётные данные независимо от того, какой сайт инициировал запрос, поэтому нужны HTTPS, изменяющие состояние запросы, которые не являются простыми межсайтовыми GET, и CSRF-токены. Без этих мер Basic не должен защищать чувствительную или ценную информацию. Не помещайте идентификатор и пароль в URL: современные браузеры вырезают такую форму до отправки.

**When to use:**

Используйте Basic только для малочувствительного доступа поверх TLS или для вызова прокси (`407`, `Proxy-Authenticate`, `Proxy-Authorization`). Для данных приложения предпочтительны современный аутентификатор, короткоживущие bearer- или sender-constrained токены и серверная авторизация.

**Examples:**

```http
WWW-Authenticate: Basic realm="Access to the staging site"
Authorization: Basic <base64 user-id:password>
```

- [MDN — HTTP authentication](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication)

<summary>Что такое OAuth, and how does it work?</summary>

### Что такое OAuth, and how does it work?

**Definition:**

**OAuth 2.0** позволяет клиентскому приложению обращаться к защищённому ресурсу от имени владельца ресурса и с его разрешения. Сервер авторизации выдаёт access token после аутентификации владельца и получения согласия. Сервер ресурсов принимает этот токен и не обязан понимать все схемы аутентификации владельца.

**How it works:**

Обычные стороны: клиент, владелец ресурса (конечный пользователь, если доступ даёт человек), сервер авторизации и сервер ресурсов. Access token должен быть короткоживущим и ограниченным аудиторией, лучше одним сервером ресурсов. Refresh token получает новые access token и должен быть привязан к отправителю (DPoP или mTLS) либо ротироваться.

Текущая практика — authorization code с PKCE (`response_type=code`) для всех типов клиентов, включая браузер и нативные приложения. Implicit grant (`response_type=token`) устарел по RFC 9700 и убран из OAuth 2.1, потому что кладёт access token во фрагмент URL. Не используйте resource-owner password grant: он раскрывает учётные данные владельца клиенту. Клиент не должен перенаправлять браузер на произвольный URI из query-параметра. Ответы авторизации не передают по незашифрованному соединению; redirect URI со схемой `http` допустим только для native loopback.

**When to use:**

Используйте OAuth, когда клиенту нужен делегированный доступ к API. OpenID Connect — когда клиент должен проверить, кто конечный пользователь. DPoP или mTLS — когда утёкший bearer-токен сам по себе не должен быть пригоден для повтора, особенно для чувствительных или долгоживущих токенов.

**Examples:**

```http
GET /authorize?response_type=code&client_id=app&code_challenge=<S256>&code_challenge_method=S256
```

<summary>Что такое OpenID and how does it relate to web security?</summary>

### Что такое OpenID and how does it relate to web security?

**Definition:**

**OpenID Connect 1.0** — слой идентификации поверх OAuth 2.0. Он позволяет проверяющей стороне подтвердить личность конечного пользователя по аутентификации на сервере авторизации и получить базовые утверждения профиля совместимым способом. ID token — подписанный JWT. Рекомендация OWASP: OpenID Connect для аутентификации и единого входа, OAuth для авторизации к API.

**How it works:**

Клиент (relying party) обращается к серверу авторизации и получает ID token, у которого нужно проверить подпись, издателя и аудиторию. Access token для API по-прежнему приходит с token endpoint, а не по фронт-каналу. В потоках OpenID Connect параметр `nonce` даёт защиту от CSRF; иначе используйте одноразовый `state`, привязанный к агенту пользователя. PKCE для authorization code остаётся обязательным.

Токены — bearer-учётные данные: кто держит токен, тот может его предъявить. Передавайте их только по TLS. Не кладите их в `localStorage` браузера. Предпочтительны безопасные HTTP-only cookie или защищённое хранилище платформы, короткие access token и ротация refresh token. Раз приложение больше не хранит пароли пользователей, защищать нужно токены.

**When to use:**

Выбирайте OpenID Connect, когда продукту нужен вход или SSO через поставщика идентификации. Один OAuth — когда клиент вызывает API по уже выданному разрешению и ID token не нужен.

**Examples:**

```http
GET /authorize?response_type=code&scope=openid&nonce=<transaction-specific>&code_challenge=<S256>&code_challenge_method=S256
```

<summary>Можете ли вы describe Multi-Factor Authentication (MFA) and where it's used?</summary>

### Можете ли вы describe Multi-Factor Authentication (MFA) and where it's used?

**Definition:**

**Многофакторная аутентификация** требует доказательств как минимум из двух разных факторов: знание, владение и биометрия. Два пароля или пароль и PIN — один и тот же фактор, это не MFA. Местоположение и другие сигналы риска могут влиять на решение, но по руководству NIST, на которое ссылается OWASP, они не заменяют фактор.

**How it works:**

OWASP считает MFA самой сильной практической защитой от захвата учётной записи, который начинается со слабого, повторно использованного или украденного пароля, и рекомендует её всем пользователям, с возможностью включить TOTP и с обязательным требованием для администраторов. Факторы должны быть независимы, чтобы одна компрометация не давала оба.

Требуйте MFA при входе и снова для чувствительных действий: смена пароля, смена адреса почты, отключение MFA, повышение сеанса до администратора. Каждый путь входа, включая отдельный API или мобильное приложение, должен держать ту же планку. Одноразовые пароли: короткий срок, одно использование, жёсткий лимит попыток и инвалидация после успеха. Не пишите их в журнал и не храните долго в открытом виде. Дайте безопасный сброс; случайный обход становится слабым фактором.

**When to use:**

Требуйте MFA на каждый интерактивный вход, если пользователь может подключить второй фактор, и всегда для администраторов и для перечисленных чувствительных изменений учётной записи. Предлагайте TOTP; в шпаргалке SMS и телефонные звонки помечены как ограниченные.

**Examples:**

```python
# Distinct factors, not two secrets of the same kind.
know = password
have = totp  # short TTL, single use, attempt limit
```

<summary>Что такое JWT (JSON Web Tokens) and how are they used in authentication?</summary>

### Что такое JWT (JSON Web Tokens) and how are they used in authentication?

**Definition:**

**JSON Web Token** (RFC 7519) — компактный URL-безопасный способ передать утверждения между двумя сторонами. Утверждения — JSON-объект: полезная нагрузка JSON Web Signature или открытый текст JSON Web Encryption, поэтому их можно подписать, защитить целостность с помощью MAC и/или зашифровать. OWASP описывает подписанный JWT как защищённое удостоверение: подпись издателя не даёт клиенту подделать утверждения, например роль администратора.

**How it works:**

Подписанный токен — три части в base64url: защищённый заголовок, утверждения и подпись. Подпись — либо подпись на ключе пары, либо MAC на общем секрете. Зарегистрированные утверждения: `iss`, `sub`, `aud`, `exp`, `nbf`, `iat` и `jti`.

В OpenID Connect ID token — это JWT. В OAuth 2 access token может быть JWT. JWT часто предлагают для сеансов без состояния; OWASP такой приём не одобряет. Сервер ресурсов проверяет целостность и не выбирает алгоритм из заголовка токена, включая `alg` со значением `none`. Для access token API требуйте и проверяйте `iss`, `aud` и `exp`. Если пользователь вышел или idle timeout закончил сеанс раньше `exp`, поместите выданный сервером `jti` (при необходимости вместе с `aud`) в список запрета до истечения токена. Подписи предпочтительнее MAC, когда иначе много сервисов делят ключ, которым можно и выпускать токены.

**When to use:**

Используйте подписанный JWT как ID token или access token, если сервер ресурсов может проверить издателя, аудиторию и срок. Не делайте долгоживущий JWT единственной записью сеанса, если доступ нужно отзывать при выходе или idle timeout; для этого нужна серверная инвалидация.

**Examples:**

```text
# Signed JWT: base64url(header).base64url(claims).base64url(signature)
# Verify iss, aud, and exp with the key you configured — not with alg from the header.
```

<summary>Как you securely store user passwords?</summary>

### Как you securely store user passwords?

**Definition:**

Храните пароли медленным адаптивным хешем, а не обратимым шифрованием и не быстрым хешем вроде SHA-256. Порядок OWASP: Argon2id, затем scrypt, если Argon2id недоступен, bcrypt только в унаследованных системах и PBKDF2-HMAC-SHA-256, когда нужна проверка FIPS 140. У каждого пароля свой salt, чтобы заранее посчитанные таблицы не подходили сразу многим пользователям.

**How it works:**

Минимумы Argon2id в шпаргалке включают 19 МиБ памяти, 2 итерации и параллелизм 1 (этот набор не для Argon2i). Если bcrypt приходится оставить, work factor не ниже 10 и предел пароля 72 байта. PBKDF2-HMAC-SHA-256 — не меньше 600 000 итераций. Pepper вне базы паролей, в хранилище секретов или HSM, мешает, когда унесена только база. Сравнивайте функцией проверки пароля языка или сравнением за постоянное время и не обрезайте пароль молча.

Современный алгоритм можно не скрывать. При повышении work factor пересчитывайте хеш при следующем успешном входе. Передавайте пароли только по TLS, и на странице входа, и на следующих аутентифицированных страницах. Не заставляйте менять пароль по календарю; меняйте учётные данные, когда обнаружена утечка или сменилась технология аутентификатора.

**When to use:**

Для новых приложений — Argon2id. scrypt — где нет Argon2id, PBKDF2 — где обязательна реализация с проверкой FIPS, bcrypt — только пока старое развёртывание ещё не перенесено.

**Examples:**

```java
# Legacy bcrypt only. Prefer Argon2id (19 MiB, t=2, p=1) when the library exists.
String hash = BCrypt.hashpw(password, BCrypt.gensalt(12));
```

<summary>Что такое Single Sign-On (SSO) and what are its benefits?</summary>

### Что такое Single Sign-On (SSO) and what are its benefits?

**Definition:**

**Единый вход** позволяет пользователю один раз аутентифицироваться у поставщика идентификации, после чего проверяющие приложения принимают утверждения об аутентификации и авторизации. Два профиля, которые описывает OWASP: OpenID Connect (слой идентификации на OAuth 2.0 с подписанным ID token) и профиль SAML Web Browser SSO со связываниями Redirect/POST.

**How it works:**

Польза в одном сервисе аутентификации, который может требовать MFA, короткие токены и единую политику учётных записей, вместо хранения своих паролей в каждом приложении. OWASP отмечает, что OpenID Connect снижает риск, связанный с паролями, перенося аутентификацию к поставщику идентификации.

Проверяющая сторона всё равно обязана проверить утверждение. Для SAML используйте TLS 1.2 для конфиденциальности и целостности в пути, требуйте цифровую подпись сертифицированным ключом и элементы данных профиля: ID запроса аутентификации и поставщика услуг, `InResponseTo` в ответе и утверждение, подписанное закрытым ключом поставщика идентификации, с именами клиента, поставщика идентификации и поставщика услуг. Пути SSO на cookie по-прежнему нуждаются в защите от CSRF; API только с токенами эту защиту на cookie-путях не заменяют. Не отдавайте фронтенду тот же внутренний каталог, который используется для незащищённого публичного доступа.

**When to use:**

Используйте SSO, когда несколько приложений должны делить одного поставщика идентификации. Для нового входа в веб и API предпочтителен OpenID Connect. SAML — где существующий корпоративный поставщик уже говорит на этом профиле; проверяйте каждый обязательный элемент до создания локального сеанса.

**Examples:**

```text
# OpenID Connect: authenticate at the IdP, then accept a signed ID token.
# SAML: require InResponseTo and an assertion signed by the IdP.
```

<summary>Объясните role-BASEd access control (RBAC) and how it is implemented.</summary>

### Объясните role-BASEd access control (RBAC) and how it is implemented.

**Definition:**

**Ролевое управление доступом** разрешает или запрещает доступ по ролям пользователя. Права привязаны к роли, пользователь наследует права своих ролей. Связь пользователей и ролей обычно многие-ко-многим, роли могут образовывать иерархию. OWASP отличает это от доступа по атрибутам, который учитывает ещё атрибуты субъекта, объекта и среды, и от доступа по отношениям между пользователем и объектом.

**How it works:**

Проверяйте права на сервере для каждого запроса и по умолчанию запрещайте. На этапе проектирования зафиксируйте, какая роль какую операцию с каким ресурсом может выполнять, и проверьте эту карту тестами. После развёртывания пересматривайте права, чтобы они не расползлись дальше одобренного набора. Не оставляйте решение клиенту.

OWASP для большинства приложений предпочитает решения по атрибутам или отношениям: проверка роли грубая, ей трудно выразить правила уровня объекта, множество ролей создаёт их взрыв, а цепочку `hasAnyRole` легко написать неверно. Роль может остаться одним атрибутом политики. Идентификатор не должен быть единственным контролем: даже трудноугадываемый id требует проверки права на этот конкретный объект.

**When to use:**

Небольшая модель RBAC уместна, когда несколько устойчивых должностных функций правда совпадают с правами. Переходите к атрибутам или отношениям, когда доступ зависит от конкретного объекта, времени, устройства или от того, кто создал запись.

**Examples:**

```python
if not user.has_role("ACCT_MANAGER"):
    return  # deny by default; check the object too, not only the role
```

<summary>Что такое the best practices for handling user session timeouts?</summary>

### Что такое the best practices for handling user session timeouts?

**Definition:**

Таймаут сеанса ограничивает, как долго серверный сеанс остаётся действительным. OWASP требует и **idle timeout** (не было HTTP-запроса с этим id сеанса), и **абсолютный timeout** (от момента, когда приложение создало сеанс, независимо от активности). После любого предела пользователь аутентифицируется снова и получает новый сеанс.

**How it works:**

Оба предела применяет сервер. Если клиент хранит время входа или оставшиеся минуты, это значение можно изменить и растянуть сеанс. Когда сеанс истёк или пользователь вышел, инвалидируйте его на сервере вызовом платформы (`HttpSession.invalidate()`, `Session.Abandon()` или `session_destroy()` / `unset()`) и очистите клиентский токен. Для cookie отправьте пустой id сеанса и дату `Expires` (или `Max-Age`) в прошлом.

Idle timeout также ограничивает, сколько состояния тихого клиента держит сервер, это важно и для доступности, и против захвата учётной записи. Абсолютный timeout ограничивает сеанс, который остаётся активным. Не рассчитывайте, что сеанс кончится, когда закроют браузер.

**Examples:**

```http
Set-Cookie: id=; Expires=Friday, 17-May-03 18:45:00 GMT
```

### Что такое firewall, and how does it contribute to web security?

**Definition:**

**Межсетевой экран** — точка применения политики, которая разрешает или блокирует трафик между сетевыми зонами. В сегментированной веб-архитектуре переход от фронтенда в интернет к зонам приложений или данных означает проход через экран. В шпаргалке Zero Trust экраны, прокси, шлюзы приложений и API тоже названы компонентами, которые применяют решения о доступе, а не только на краю сети.

**How it works:**

Поместите сервисы из интернета во фронтенд-зону: балансировщик, экран прикладного уровня, веб-сервер и кэш. Логику приложения держите в зоне middleware, а базы, каталоги и хранение ключей — в backend. Запишите разрешённые пути: фронтенд может обращаться к своему уровню приложений, а тот — к своей базе. Фронтенд не должен напрямую достигать чужой базы.

Хостовый экран вроде UFW сам не управляет портами, которые публикует Docker. Docker вставляет свои правила, и опубликованный порт может быть доступен даже при правиле запрета. Привязывайте такие порты к `127.0.0.1`, если они должны остаться локальными, или согласуйте экран с правилами Docker. Экран — один слой; авторизация приложения по-прежнему выполняется в серверном коде.

**Examples:**

```bash
# Local only. Publishing 0.0.0.0 bypasses a typical UFW deny.
docker run -p 127.0.0.1:8000:8000 myimage
```

### Определите a Virtual Private Network (VPN) and its significance in enhancing web security.

**Definition:**

В рекомендациях OWASP по удалённому доступу **VPN** — сетевое соединение, которое само по себе не должно разрешать доступ к другим ресурсам. Zero Trust считает VPN с широким доступом в сеть старой моделью. Замена — доступ к конкретным ресурсам, а оставшийся VPN ограничивают и наблюдают. Руководство по TLS добавляет: шлюз VPN и публичный веб-сервер не должны делить один wildcard-сертификат.

**How it works:**

Предпочитайте путь с проверкой личности к конкретному приложению туннелю, который высаживает пользователя во внутреннюю сеть. Если на время миграции VPN ещё нужен, ограничьте его и наблюдайте. Состояние устройства проверяют непрерывно, доступ отзывают, когда устройство перестаёт соответствовать политике. Шлюз VPN может делить wildcard-сертификат с другим шлюзом VPN; он не должен делить его с публичным веб-сервером или внутренним сервером другого уровня доверия.

Функции приватности и VPN также снижают точность проверки местоположения как сигнала риска. Адрес выхода VPN не доказывает, кто пользователь.

**When to use:**

Узкий VPN уместен только пока конкретная система ещё не стоит за проверками на каждый ресурс. Для веб-приложений предпочтителен прокси с проверкой личности, который разрешает пользователя и устройство именно для этого приложения.

**Examples:**

```text
# Do not reuse one wildcard certificate across trust levels.
# A VPN gateway and a public web server need separate certificates.
```

<summary>Что такое Intrusion Detection System (IDS) vs. an Intrusion Prevention System (IPS)?</summary>

### Что такое Intrusion Detection System (IDS) vs. an Intrusion Prevention System (IPS)?

**Definition:**

**Система обнаружения вторжений** записывает подозрительную активность, чтобы люди и инструменты могли её разобрать. В руководстве OWASP по журналированию сетевые и хостовые системы обнаружения (NIDS и HIDS) перечислены среди источников событий безопасности. **Система предотвращения вторжений** стоит на пути трафика: в руководстве по виртуальному патчу IPS назван рядом с WAF как устройство, которое может блокировать совпавшие попытки против известной уязвимости, не меняя уязвимый код.

**How it works:**

Обнаружение питает поток журналов: неудачные аутентификации, нарушения политики и другие события, которые центральное хранилище или SIEM может сопоставить. Предотвращение стоит на пути и может блокировать трафик, который узнаёт правило. Виртуальный патч на IPS или WAF покрывает только трафик, который устройство видит, и варианты, которые узнают его правила. Уязвимость он не устраняет. До блокировки проверьте легитимные сценарии, храните след с id правила и исходом и продолжайте исправление кода или поставщика.

Ни один из ящиков не заменяет серверную авторизацию, параметризованные запросы или установку исправлений.

**When to use:**

Обнаружение — когда нужны видимость и след для разбора. Встроенное предотвращение — когда нужно сократить окно известной проблемы до выкладки исправления кода, и снимите или выведите правило после настоящего исправления.

**Examples:**

```text
# Detective: NIDS/HIDS contribute events to the application log stream.
# Preventive: an IPS or WAF can block a known pattern while the code fix is prepared.
```

### Объясните the concept of a Content Delivery Network (CDN) and its importance in web security.

**Definition:**

Сайты иногда размещают сценарии и стили у третьей стороны, в том числе в **сети доставки содержимого**, а не только на своём origin. Это снижает нагрузку на исходное приложение. **How it works:**

SRI проверяет байты. Оно не решает, следует ли вообще выполнять код этой третьей стороны. Ограничьте метки тем, что нужно, и по возможности размещайте файл у себя, чтобы самим задавать версию. `Integrity-Policy` может требовать метаданные целостности для сценариев или стилей, а не надеяться, что каждый тег их содержит.

**Examples:**

```html

```

<summary>Что такое data encryption best practices for sensitive information?</summary>

### Что такое data encryption best practices for sensitive information?

**Definition:**

**Шифрование хранимых данных** следует модели угроз: от кого вы защищаетесь, решает, шифровать в приложении, в базе (например SQL Server TDE), в файловой системе (BitLocker или LUKS) или в оборудовании. Аппаратное шифрование закрывает физическую кражу и ничего не даёт против того, кто уже выполняет код на сервере. Самое сильное сокращение — не хранить чувствительное значение, особенно данные карты.

**How it works:**

Для симметричного шифрования OWASP предпочитает AES с ключом не короче 128 бит и лучше 256, в режиме с аутентификацией: GCM или CCM. Если их нет — CTR или CBC плюс encrypt-then-MAC. ECB не используют вне очень узких случаев. Свои алгоритмы не изобретают. Для шифрования с открытым ключом берите поддерживаемую гибридную схему вроде HPKE; если нужен RSA — ключ не короче 2048 бит и OAEP (RFC 8017). Открытые ключи RSA и эллиптических кривых не стойки к постквантовым атакам; долгая секретность требует плана вроде ML-KEM (FIPS 203) в гибридной конструкции. Данные по-прежнему шифрует AES.

Ключи генерируйте CSPRNG (`SecureRandom`, `secrets`, `crypto.randomBytes()`, не `Math.random()` и не `rand()`). Храните их в HSM, облачном KMS или менеджере секретов, не в системе контроля версий. Держите ключи отдельно от шифртекста. Ротируйте при компрометации, по криптопериоду, по пределам использования режима или когда алгоритм слабеет. Пароли хешируют, а не шифруют, кроме редкого случая, когда другая система всё ещё требует исходный пароль и нет выдачи в духе OIDC.

**Examples:**

```javascript
# Node.js CSPRNG for a 256-bit data key. Do not use Math.random().
const key = crypto.randomBytes(32);
```

### Объясните data masking and how it can protect sensitive data.

**Definition:**

**Маскирование данных** скрывает чувствительные значения от тех, кто видит экран или журнал, но не нуждается в исходных данных. Мобильная шпаргалка OWASP отдельно называет маскирование чувствительных полей интерфейса, чтобы снизить подглядывание. Шпаргалка журналирования запрещает записывать секреты, полные тела и материал аутентификации. Руководство по HTTP-кэшу велит для чувствительных ответов ставить `Cache-Control: no-store`, чтобы общие кэши их не хранили.

**How it works:**

Маскируйте в интерфейсе поле, которое может прочитать посторонний, и держите полное значение только на серверном пути, которому оно разрешено. В журналах храните факт события и id корреляции, а не пароль, номер карты или тело запроса. В объектном хранилище предпочитайте доступ приложения через IAM публичным объектам и короткоживущие учётные данные вместо долгого ключа доступа.

Маскирование — контроль показа и хранения. Оно не заменяет шифрование при хранении и проверку авторизации. Случайный id объекта, о котором говорит шпаргалка авторизации, тоже не заменяет разрешение на этот объект.

**Examples:**

```http
Cache-Control: no-store
```

<summary>Что такое security headers, and why are they important?</summary>

### Что такое security headers, and why are they important?

**Definition:**

**Заголовки безопасности** — это заголовки ответа HTTP, которые говорят браузеру, как обращаться со страницей. OWASP называет их простой прибавкой против межсайтового скриптинга, кликджекинга и раскрытия сведений. Они относятся к ответам, которые браузер отрисует; JSON API, который не отрисовывают, мало получает от политики кадров или сценариев.

**How it works:**

Задайте `Content-Security-Policy`, чтобы ограничить источники сценариев и стилей, и предпочитайте `frame-ancestors` заголовку `X-Frame-Options`. Если `X-Frame-Options` всё же отправляете, `DENY` запрещает встраивание. Ставьте `X-Content-Type-Options: nosniff` и верный `Content-Type`, для HTML включая `charset=UTF-8`. Явно ставьте `Referrer-Policy: strict-origin-when-cross-origin`. Для чувствительных ответов — `Cache-Control: no-store`. `Strict-Transport-Security` только на ответах HTTPS.

Выключите `X-XSS-Protection` (`0`); шпаргалка предупреждает, что он может создать недостатки, и велит опираться на CSP. Не отправляйте `Expect-CT` и `Public-Key-Pins`. Уберите `X-Powered-By` и бессодержательные значения `Server`, помня, что снятие отпечатка остаётся. `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` и `Cross-Origin-Resource-Policy: same-site` изолируют контексты просмотра. `Permissions-Policy` может отключить камеру, микрофон и геолокацию, если сайту они не нужны. Если отправляете `Access-Control-Allow-Origin`, назовите конкретный origin вместо `*`, если только API намеренно не публичный.

**Examples:**

```http
Content-Security-Policy: default-src 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
X-Frame-Options: DENY
```

<summary>Что такое Content Security Policy (CSP) and how does it improve web security?</summary>

### Что такое Content Security Policy (CSP) and how does it improve web security?

**Definition:**

**Content Security Policy** — это заголовок ответа `Content-Security-Policy` (или элемент `<meta http-equiv>`), который перечисляет, с каких origin и конечных точек сценариев страница может загружать ресурсы. MDN указывает, что это помогает сдерживать межсайтовый скриптинг. Политика — директивы через точку с запятой. Директивы загрузки вроде `default-src`, `script-src` и `style-src` называют разрешённые источники; `default-src` — запасной вариант.

**How it works:**

Если есть `script-src` или `default-src` и в них нет `'unsafe-inline'` или `'unsafe-eval'`, встроенные сценарии и вычисление строк блокируются. Для немногих встроенных сценариев, которые приходится оставить, предпочтительны nonce или хеши (`sha256`, `sha384`, `sha512`). `'strict-dynamic'` распространяет доверие от nonce или хеша на сценарии, которые добавляет доверенный сценарий. `frame-ancestors` перечисляет, кто может встроить страницу. `object-src 'none'` блокирует плагины. `upgrade-insecure-requests` переписывает URL HTTP на HTTPS.

Несколько политик только ужесточают: если одна ставит `connect-src 'none'`, вторая не может это открыть. На время проверки `Content-Security-Policy-Report-Only` сообщает о нарушениях, не блокируя. OWASP велит выключить `X-XSS-Protection` и использовать CSP. Политика только с отчётами исполнение не блокирует.

**Examples:**

```http
Content-Security-Policy: default-src https:; object-src 'none'
```

- [MDN — Content-Security-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)
- [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)

<summary>Можете ли вы explain the role of Subresource Integrity (SRI) in web security?</summary>

### Можете ли вы explain the role of Subresource Integrity (SRI) in web security?

**Definition:**

**Subresource Integrity** позволяет браузеру проверить, что загруженный сценарий или таблица стилей совпадает с криптографическим хешем, который вы указали. MDN описывает это как защиту, когда сторонний узел, например CDN, изменён и иначе отдал бы другие байты. Механизм применяется к `<script>` и к `<link>`, у которого `rel` равен `stylesheet`, `preload` или `modulepreload`.

**How it works:**

Значение `integrity` — список хешей через пробел с префиксами `sha256-`, `sha384-` или `sha512-`. Браузер выбирает самый сильный из присутствующих алгоритмов, хеширует байты и загружает ресурс только при совпадении; иначе загрузка завершается сетевой ошибкой. Несколько хешей одного алгоритма допускают альтернативные легитимные файлы.

Междоменный SRI требует CORS, поэтому тегу нужен `crossorigin="anonymous"`, а узел должен послать `Access-Control-Allow-Origin`. Без `crossorigin` запрос идёт в режиме `no-cors`, и браузеры отказываются применять целостность. `Integrity-Policy: blocked-destinations=(script)` может требовать метаданные целостности. Считайте хеш от файла, который собираетесь отдавать, например OpenSSL `dgst -sha384 -binary` и далее `base64 -A`.

**Examples:**

```bash
cat FILENAME.js | openssl dgst -sha384 -binary | openssl base64 -A
```

**Sources:**

- [MDN — Subresource Integrity](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity)

<summary>Что такое Domain Name System Security Extensions (DNSSEC), and how does it work?</summary>

### Что такое Domain Name System Security Extensions (DNSSEC), and how does it work?

**Definition:**

**DNSSEC** (RFC 4033) добавляет к системе доменных имён аутентификацию происхождения данных и целостность данных. Спецификация вводит расширения, их возможности и ограничения. В ней сказано, что эти расширения не обеспечивают конфиденциальность.

**How it works:**

Резолверы могут удостоверить, что данные DNS пришли из зоны, авторитетной для имени, и что данные не изменены, включая удостоверенный отказ, когда имени или типа нет. Операторы публикуют подписанные записи и цепочку доверия до якоря доверия. Клиенты и резолверы, которые проверяют подписи, отвергают данные, которые не аутентифицированы.

Поскольку DNSSEC не шифрует запросы и ответы, он не скрывает, какие имена искали. Конфиденциальность веб-трафика остаётся задачей TLS. DNSSEC всё же стоит включать, чтобы резолвер замечал несанкционированные изменения записей, которые направляют пользователей на ваш сайт.

**Examples:**

```text
# DNSSEC (RFC 4033): origin authentication and integrity.
# It does not provide confidentiality; use TLS for that.
```

**Sources:**

- [RFC 4033 — DNS Security Introduction and Requirements](https://www.rfc-editor.org/rfc/rfc4033.html)
</details>

<summary>Что такое HTTP Strict Transport Security (HSTS) and how can it be used?</summary>

### Что такое HTTP Strict Transport Security (HSTS) and how can it be used?

**Definition:**

**HTTP Strict Transport Security** — это заголовок ответа `Strict-Transport-Security`. MDN говорит, что он сообщает браузерам обращаться к узлу только по HTTPS, а последующие попытки HTTP повышаются до HTTPS. При следующих соединениях браузер не даст пользователю обойти ошибки сертификата. Узел опознаётся только по доменному имени, не по IP-адресу. Браузеры игнорируют заголовок, если он пришёл по открытому HTTP.

**How it works:**

`max-age` — секунды. `includeSubDomains` покрывает поддомены этого узла, не родителя. `preload` требует `max-age` не меньше `31536000` (один год) и `includeSubDomains`. Шпаргалка заголовков OWASP показывает `max-age=63072000; includeSubDomains; preload` и предупреждает, что долгая политика плюс сломанный сертификат может закрыть пользователей до истечения срока. Отправляйте заголовок только по HTTPS. Первый визит по HTTP всё ещё можно перенаправить; пример MDN использует `301` с `Location` на HTTPS URL, и само перенаправление не должно содержать HSTS. Списки preload закрывают окно до первого ответа HTTPS, и они эксплуатационные, не часть спецификации HSTS. `max-age=0` снимает политику, но только по HTTPS.

**When to use:**

Включайте HSTS на ответах HTTPS после того, как весь узел, включая поддомены, если директива их покрывает, отдаёт действительные сертификаты. Сначала короткий `max-age`. Добавляйте `preload`, только когда выдерживаете минимум в один год и принимаете, что клиенты сохранят политику.

**Examples:**

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

**Sources:**

- [MDN — Strict-Transport-Security](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security)
- [OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)

### Что такое penetration testing, and how does it differ from vulnerability scanning?

**Definition:**

В руководстве OWASP по виртуальному патчу разделены две упреждающие проверки живого приложения: **тесты на проникновение**, которые делают люди, и **автоматические средства оценки веба**. Шпаргалка авторизации добавляет, что модульные и интеграционные тесты ловят простые ошибки контроля доступа и не заменяют отдельный тест безопасности или тест на проникновение. Автоматические тесты пропускают более сложные проблемы.

**How it works:**

Сканирование повторно применяет известные проверки и выдаёт список находок. Тест на проникновение — этичная оценка работающего приложения, включая бизнес-логику и цепочки слабостей, которые сканер не моделирует. Оба способа узнают о недостатке до инцидента. Зафиксируйте находку, решите, уместен ли виртуальный патч, и всё равно исправьте код. Гоняйте сканеры в CI для известных классов; назначайте человеческое тестирование, когда модель угроз или крупный выпуск говорит, что автоматического результата мало.

Чистый скан не доказывает, что логика авторизации верна. Шпаргалка авторизации отсылает к OWASP Web Security Testing Guide для проверки контроля доступа сверх модульных тестов.

**When to use:**

Автоматическую оценку гоняйте постоянно. Тест на проникновение заказывайте для новой или важной системы, после крупных изменений схемы и когда сканер не видит бизнес-правила. Результаты нужны, чтобы расставить исправления, а не как разовый сертификат.

**Examples:**

```text
# Automated scan: known checks in CI.
# Penetration test: people exercise the running app, then you still patch the code.
```

### Как fuzzing used in security testing?

**Definition:**

В руководстве OWASP по журналированию сказано проверять, что журналирование остаётся включённым во время тестов безопасности приложения, **фаззинга**, проникновения и производительности. В этом контексте фаззинг — тест с порождением ввода, который подаёт приложению разнообразные данные, пока вы смотрите на падения, утечки в ошибках и внедрение в журнал. <summary>Можете ли вы explain the concept of threat modeling?</summary>

### Можете ли вы explain the concept of threat modeling?

**Definition:**

**Моделирование угроз** — структурированный повторяемый процесс: система описывается с точки зрения безопасности, находятся применимые угрозы и выбирается ответ. OWASP велит делать это рано, на проектировании, и обновлять модель вместе с системой, а не один раз. Вопросы манифеста: над чем мы работаем? что может пойти не так? что мы с этим сделаем? достаточно ли хорошо мы это сделали?

**How it works:**

Разложите систему диаграммами потоков данных с границами доверия, потоками, хранилищами, процессами и внешними сущностями. Ищите угрозы методом, который подходит вопросу. STRIDE — обычная подсказка для технического проекта: подмена против аутентификации, искажение против целостности, отказ от авторства против учёта, раскрытие информации против конфиденциальности, отказ в обслуживании против доступности и повышение привилегий против авторизации. Другие методы (деревья атак, случаи злоупотребления, LINDDUN, PASTA, OCTAVE, VAST) — для приватности, делового ущерба или риска организации; не складывайте их для вида.

У каждой угрозы есть ответ: смягчить, устранить, передать или принять. Передача сама по себе не снижает вероятность или вред; запишите, кто по-прежнему владеет контролями. **Definition:**

### Что такое the SHAred responsibility models in cloud security?

**Definition:**

**Модель общей ответственности** в облачной шпаргалке OWASP делит обязанности поставщика и заказчика по тому, какую часть стека эксплуатирует поставщик. Физические машины и дата-центр остаются у поставщика. В зависимости от сервиса заказчик может владеть всем от операционной системы вверх или только конфигурацией и кодом.

**How it works:**

IaaS: поставщик держит инфраструктуру; заказчик держит аутентификацию и авторизацию, хранение и доступ к данным, часть сети вроде портов и сетевых ACL и приложение. PaaS: заказчик по-прежнему контролирует аутентификацию и авторизацию приложения, ПО приложения и внешнее хранение данных, а платформа размещает код. Запишите, какая команда обновляет ОС, ротирует ключи и пересматривает IAM. Контроль без владельца — простой заказчика, даже если оборудование ведёт поставщик.

**When to use:**

Выбирайте IaaS, когда нужно контролировать операционную систему и есть кому её сопровождать. Выбирайте PaaS, когда команда должна вести код приложения и доступ к данным, не владея узлом. Выбирайте SaaS, когда продукт уже есть и вы принимаете стек поставщика в обмен на его аттестацию.

### Объясните how encryption is handled in the cloud.

**Definition:**

Шпаргалка криптохранилища перечисляет физический или виртуальный HSM, Amazon KMS, Azure Key Vault и внешние менеджеры секретов. Шпаргалки .NET и Java показывают AES-GCM с ключом 256 бит и nonce в 12 байт, уникальным для каждого шифрования этим ключом. Асимметричные алгоритмы в шпаргалке ключей используют, чтобы считать цифровые подписи и устанавливать ключевой материал. TLS использует оба: наборы AEAD из шпаргалки (AES-GCM или ChaCha20-Poly1305 в TLS 1.3) защищают записи, а открытый ключ сертификата позволяет клиенту аутентифицировать сервер.

Не пишите свои криптографические функции. Шпаргалка Java велит предпочесть поддерживаемую библиотеку или облачную службу ключей. Пароли не шифруют обратимым симметричным шифром; используйте хеш пароля.

**When to use:**

Симметричный AEAD-шифр — для больших данных, когда секретный ключ уже есть. Пара асимметричных ключей — чтобы подписать или согласовать этот секрет. Для паролей — хеш пароля.

**Examples:**

```csharp
// AES-GCM: 32-byte key, 12-byte nonce, a new nonce for every encryption.
var key = new byte[32];
var nonce = new byte[12];
```

<summary>Объясните the significance of rate limiting in API security.</summary>

### Объясните the significance of rate limiting in API security.

**Definition:**

Ограничение частоты ставит предел тому, как быстро клиент может вызывать API. Шпаргалка REST велит возвращать `429 Too Many Requests`, когда запросы приходят слишком часто, и говорит, что ключи API могут снизить влияние отказа в обслуживании, не будучи единственным контролем чувствительных данных. Шпаргалка GraphQL велит ограничивать частоту по IP или по пользователю, чтобы дорогой запрос нельзя было повторять без предела.

**How it works:**

Применяйте предел до дорогой работы. Считайте по устойчивой личности: ключ API, пользователь или арендатор, а не только по адресу, который делят многие люди. При отказе пример из шпаргалки нескольких арендаторов отправляет `429` и значение `Retry-After`. Отзывайте ключ, который нарушает соглашение об использовании.

Предел защищает доступность. Он не аутентифицирует вызывающего и не авторизует объект. Эти проверки оставляйте.

**When to use:**

Ограничивайте частоту публичных и аутентифицированных API, которые делают реальную работу. На вход и на неаутентифицированные вызовы ставьте более жёсткий предел, чем на обычное чтение вошедшего пользователя.

**Examples:**

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

### Как you foster a culture of security within a web development team?

**Definition:**

Приглашайте в просмотр людей, которые эксплуатируют систему. Совмещайте обучение с удобными контролями: MFA, которую можно подключить, ошибки, которые не вываливают секреты, и место, куда сообщить о подозреваемом инциденте.

### Что должна включать web security policy?

**Definition:**

Политика веб-безопасности — записанный набор решений, которым продукт должен соответствовать. Шпаргалка безопасного продукта говорит, что продукты должны выполнять требования безопасности организации и что эти решения должны быть явными. Шпаргалка авторизации добавляет запрет по умолчанию, наименьшие привилегии и серверную проверку на каждый запрос.

**How it works:**

Запишите, кто какую операцию с каким ресурсом может выполнять, и что новые маршруты запрещены, пока правило их не разрешит. Требуйте HTTPS, безопасные cookie и хеширование паролей учётных записей. ### Как change management impact web security?

**Definition:**

Изменение может добавить маршрут, право или образ, которые никто не перепроверил.
