<details>
  <summary>Database overview</summary>

### Database overview

**Definition:** Структурированная система хранения, извлечения и управления данными с определенными шаблонами доступа, правилами целостности и управлением параллелизмом.

**How it works:** Клиент отправляет запрос через драйвер → пул соединений → БД анализирует SQL → планировщик выбирает индексное/последовательное сканирование → исполнитель возвращает строки → журнал транзакций обеспечивает надежность при фиксации.

**When to use:**

OLTP (Postgres) для пользователей/заказов; Redis для кэша; очередь для асинхронности — постоянство полиглотов, когда существует измеренная потребность.

Любое приложение, которое должно сохранять состояние за пределами одного запроса — пользователей, заказов, сеансов, аналитики.

**Pluses and minuses:**

| +                                  | −                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------- |
| Центральный источник истины        | Сложность эксплуатации (резервное копирование, миграция, масштабирование) |
| Запрашиваемые и проверяемые данные | Схема и шаблоны доступа должны быть разработаны заранее                   |
| КИСЛОТА / параметры консистенции   | Неправильный выбор магазина стоит исправить                               |

**Examples:**

```sql
-- Relational: structured, joinable
CREATE TABLE users (
  id         SERIAL PRIMARY KEY,
  email      TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Thoughts:** База данных — это не просто хранилище, это координатор параллелизма. Выбирайте, основываясь на шаблонах доступа, потребностях в согласованности и опыте команды, а не на шумихе.

**Sources:**

[PostgreSQL — Введение](https://www.postgresql.org/docs/current/tutorial.html)

### Database taxonomy

**Definition:**

Базы данных группируются по модели данных и гарантиям согласованности, а не по одной оси «SQL против NoSQL».

| Тип                    | Примеры                                                   | Лучшее для                                                                   |
| ---------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Реляционная (СУБД)** | PostgreSQL, MySQL, SQL-сервер                             | Структурированные данные, объединения, транзакции                            |
| **Документ**           | MongoDB, CouchDB                                          | Гибкие схемы, вложенные документы JSON                                       |
| **Ключ-значение**      | Редис, DynamoDB                                           | Кэширование, сеансы, простой поиск                                           |
| **Семейство столбцов** | Кассандра, HBase                                          | Широкие строки, высокая пропускная способность записи                        |
| **График**             | Нео4дж                                                    | Запросы, ориентированные на взаимоотношения (социальные сети, мошенничество) |
| **Временной ряд**      | TimescaleDB, InfluxDB                                     | Метрики, Интернет вещей, мониторинг                                          |
| **Поиск**              | [Elasticsearch](./9_database_nosql_core.md#elasticsearch) | Полнотекстовый поиск, аналитика журналов                                     |

**When to use:** Начните с одного основного хранилища (обычно PostgreSQL). Добавляйте Redis/Mongo/queue только тогда, когда это оправдано.

**Pluses and minuses:**

| + (настойчивость полиглота)                       | −                                             |
| ------------------------------------------------- | --------------------------------------------- |
| Подходящий инструмент для каждой рабочей нагрузки | Больше операций, синхронизации и режимов сбоя |
| Оптимизация путей чтения и записи                 | Дублирование данных в магазинах               |

**Thoughts:** «NoSQL» означает **Не только SQL** — многие команды используют Postgres + Redis + очередь. Реляционная модель (таблицы, строки, ключи, SQL): [Реляционная база данных](./9_database_sql.md#relational-database). См. [Матрица выбора базы данных](./9_database_nosql_core.md#db-selection-matrix).

<details>
  <summary>ACID</summary>

### ACID

**Definition:** Четыре гарантии транзакций — **Атомарность**, **Последовательность**, **Изоляция**, **Долговечность**.

**How it works:**

| Письмо            | Значение                                                                           |
| ----------------- | ---------------------------------------------------------------------------------- |
| **Атомность**     | Сделка осуществляется по принципу «все или ничего»                                 |
| **Постоянство**   | Ограничения сохраняются, когда они заканчиваются (не CAP «каждая текущая реплика») |
| **Изоляция**      | Параллельные транзакции не видят незафиксированное состояние друг друга            |
| **Долговечность** | Успешный `COMMIT` выдерживает сбой процесса/ОС (сбрасывается WAL)                  |

**When to use:** Финансовые переводы, инвентарь, системы бронирования — везде частичные обновления недопустимы.

**Pluses and minuses:**

| +                                             | −                                                                       |
| --------------------------------------------- | ----------------------------------------------------------------------- |
| Прогнозируемое состояние после сбоев          | Более высокая задержка записи по сравнению с возможной согласованностью |
| Сильная честность в отношении денег/инвентаря | Сложнее масштабировать запись по регионам                               |
| Знакомая ментальная модель для OLTP           | Длинные транзакции блокируют другую работу                              |

**Examples:**

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- ROLLBACK on any error — neither update persists alone
```

**Thoughts:**

- **Согласованность** в ACID = соблюдение ограничений (FK, CHECK), а не согласованность CAP.
- В системах NoSQL часто ослабляются **I** (изоляция) или **D** (надежность) для масштабирования — см. BASE.
- Делайте транзакции короткими; удерживайте блокировки в течение миллисекунд, а не секунд.
- Глаголы SQL: [COMMIT и ROLLBACK](./9_database_sql.md#commit-and-rollback).

**Sources:**

[PostgreSQL — Транзакции](https://www.postgresql.org/docs/current/tutorial-transactions.html)

<details>
  <summary>CAP theorem</summary>

### CAP theorem

**Definition:**

В распределенном хранилище данных вы можете гарантировать не более **двух** свойств в сетевом разделе:

1. **Согласованность** — при каждом чтении возвращается последняя запись (или ошибки).
2. **Доступность** — на каждый запрос возвращается ответ без ошибок.
3. **Допуск на разделы** — система работает, когда узлы не могут общаться.

**How it works:**

| Система                | Под разделом | Компромисс                                        |
| ---------------------- | ------------ | ------------------------------------------------- |
| PostgreSQL (один узел) | Н/Д          | Полная КИСЛОТА                                    |
| MongoDB (по умолчанию) | АП           | Окончательная согласованность реплик              |
| и т. д. / ZooKeeper    | КП           | Согласованность в отношении доступности           |
| Кассандра              | АП           | Настраиваемая согласованность для каждого запроса |

**When to use:** Проектирование слоев данных с несколькими регионами или несколькими узлами — выберите CP (сильная согласованность, может отклонять чтение) или AP (всегда отвечать, может быть устаревшим).

**Pluses and minuses:**

| + (явный компромисс)                    | −                                               |
| --------------------------------------- | ----------------------------------------------- |
| Силы архитектурной честности            | Упрощено для реальных систем                    |
| Руководства по выбору продуктов CP и AP | Разделы редки, но неизбежны в больших масштабах |

**Thoughts:** CAP предполагает, что разделение произошло. Реальный вопрос заключается в поведении **во время** и **после** восстановления. См. ПАСЕЛК.

**Sources:**

[Теорема CAP (Википедия)](https://en.wikipedia.org/wiki/CAP_theorem)

<details>
  <summary>PACELC theorem</summary>

### PACELC theorem

**Definition:** Расширение CAP — **если Раздел**, выберите **A** или **C**; **В противном случае** (обычная работа) выберите **L**atency или **C**consistency.

**When to use:** Объясняем, почему реплики чтения возвращают устаревшие данные даже без разделения сети.

**Pluses and minuses:**

| +                                                  | −                                              |
| -------------------------------------------------- | ---------------------------------------------- |
| Моделирует повседневную задержку и согласованность | Менее известен, чем CAP — объясняют в интервью |
| Объясняет поведение асинхронной репликации         | Не формальное доказательство, такое как CAP    |

**Examples:** Первичная реплика Postgres + асинхронная реплика — нет раздела, но задержка реплики означает, что чтение может быть **конечно согласованным** (меньшая задержка на реплике) или чтение из первичной реплики (более высокая задержка, строгая согласованность).

**Thoughts:** Большинство производственных инцидентов — это «PACELC без P» — задержка реплики, а не расщепление мозга.

**Sources:**

[PACELC (Дэниел Абади)](https://dbmsmusings.blogspot.com/2010/04/problems-with-cap-and-yahoos-little.html)

<details>
  <summary>BASE</summary>

### BASE

**Definition:** Альтернатива строгому ACID для распределенных систем — **Базово доступно**, **Мягкое состояние**, **Возможно согласованное**.

**When to use:** Социальные ленты, счетчики аналитики, корзины покупок в большом масштабе, уровни кэша — там, где допустима краткая несогласованность.

**Pluses and minuses:**

| +                                                   | −                                                   |
| --------------------------------------------------- | --------------------------------------------------- |
| Высокая доступность и пропускная способность записи | Устаревшие чтения, необходимо разрешение конфликтов |
| Легче масштабировать по горизонтали                 | Приложение должно допускать несогласованность окон  |
| Подходит для гибкой эволюции схемы                  | Отладка «неправильных» данных становится сложнее    |

**Examples:**

```js
// Eventually consistent counter — two nodes may diverge briefly
await redis.incr("page:views:home");
// Different readers may see different counts for milliseconds
```

**Thoughts:** BASE — это выбор дизайна, а не функция базы данных. Вы можете выполнять чтение в «BASE-стиле» поверх ACID Postgres через реплики чтения.

**Sources:**

[ACID против BASE](https://www.ibm.com/think/topics/acid-vs-base)

  <summary>Transactions & isolation levels</summary>

### Transactions & isolation levels

**Definition:**

Транзакция группирует операции в одну атомарную единицу. **Уровни изоляции** определяют, что параллельные транзакции могут видеть друг от друга.

| Уровень              | Грязное чтение | Неповторяющееся чтение | Фантомное чтение   |
| -------------------- | -------------- | ---------------------- | ------------------ |
| ПРОЧИТАТЬ НЕПРЕРЫВНО | Возможно       | Возможно               | Возможно           |
| ПРОЧИТАТЬ СОВЕРШЕНО  | Нет            | Возможно               | Возможно           |
| ПОВТОРНОЕ ЧТЕНИЕ     | Нет            | Нет                    | Возможно (PG: нет) |
| СЕРИАЛИЗУЕМЫЙ        | Нет            | Нет                    | Нет                |

**When to use:**

- **READ COMMITTED** — Postgres по умолчанию; хорошо для большинства OLTP.
- **СЕРИАЛИЗИРУЕМЫЙ** — финансовые инварианты, резервирование мест, когда условия гонки имеют значение.

**Pluses and minuses:**

| + (более высокая изоляция) | −                                                       |
| -------------------------- | ------------------------------------------------------- |
| Меньше аномалий            | Больше блокировок, повторных попыток и взаимоблокировок |
| Легче рассуждать           | Снижение пропускной способности под вопросом            |

**Examples:**

```sql
-- Postgres: explicit transaction
BEGIN ISOLATION LEVEL REPEATABLE READ;
  SELECT balance FROM accounts WHERE id = 1;
  UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;
```

**Thoughts:** Postgres использует **MVCC** (управление многоверсионным параллелизмом) — читатели не блокируют записи. Следите за **тупиками** (`deadlock_detected`) и **ошибки сериализации** (повторная попытка с отсрочкой).

**Sources:**

[PostgreSQL — изоляция транзакций](https://www.postgresql.org/docs/current/transaction-iso.html)

  <summary>Normal forms (1NF–3NF, BCNF)</summary>

### Normal forms (1NF–3NF, BCNF)

**Definition:** Нормализация организует отношения так, что каждый факт сохраняется один раз, уменьшая избыточность и аномалии вставки/обновления/удаления. Кодд определил 1NF (1970), затем 2NF/3NF (1971); Бойс-Кодд (BCNF) последовал этому примеру в 1974 году. Неофициальная цель для OLTP: **3NF**.

**How it works:**

**функциональная зависимость** `X → Y` означает значения `X` определять `Y`. Атрибуты **Prime** принадлежат некоторому потенциальному ключу. Каждая форма строже предыдущей.

| Форма    | Неофициальное правило                                                                  | Типичное исправление                                                |
| -------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **1НФ**  | Атомарные ячейки — никаких повторяющихся групп, никаких вложенных таблиц в столбце     | Одно значение на ячейку; дополнительные строки или дочерняя таблица |
| **2НФ**  | 1NF + каждый неключевой столбец зависит от **всего** потенциального ключа              | Разделить частичные зависимости (составной ключ → подмножество)     |
| **3НФ**  | 2NF + неключевые столбцы не зависят от других неключевых столбцов (нет транзитивности) | Двигаться `instructor_office` за пределами курса                    |
| **БКНФ** | Каждое нетривиальное ФД `X → Y` имеет `X` как **суперключ** (более строгий 3NF)        | Разделить перекрывающиеся составные клавиши                         |

Кент (мнемоника интервью): _каждое неключевое поле представляет собой факт о ключе, обо всем ключе и ни о чем, кроме ключа._

обновить один и тот же город во многих строках и пропустить один; не может добавить курс, пока студент не зарегистрируется; удаление последнего студента также удаляет курс.

**When to use:**

Проектирование схемы и «зачем так много таблиц?» интервью. Для большинства приложений остановитесь на 3NF. BCNF при перекрытии ключей по-прежнему допускает противоречивые факты. 4NF+ (независимые многозначные факты) в интервью встречается редко.

OLTP-запись, деньги/инвентарь, общие справочные данные (`users`, `products`).

Чтение моделей, снимки проверок, кэши — см. [Нормализация и денормализация](#normalization-vs-denormalization). Постгрес `ARRAY` / `JSONB` действительны, когда значением является документ, а не замаскированная таблица 1:N.

**Pluses and minuses:**

| +                                                | −                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| Одно место, где можно обновить факты             | Больше соединений и FK во время чтения                            |
| Очистить сущности (пользователь, заказ, артикул) | SQL по-прежнему поддерживает массивы/JSONB, пропускающие 1NF      |
| Целостность через ключи, а не копии              | Чрезмерная нормализация (стиль 6NF) увеличивает количество таблиц |

**Examples:**

```sql
-- UNF: repeating group in one cell
-- orders(id, products)  -- 'Book, Pen'

-- 1NF: atomic, but product_name depends only on product_id (partial of composite key)
-- order_lines(order_id, product_id, product_name, qty)  PK (order_id, product_id)

-- 2NF: product facts in their own table
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL
);
CREATE TABLE order_items (
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),
  qty INT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

-- 3NF: city depends on customer, not on order_id
CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  city TEXT NOT NULL
);
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INT REFERENCES customers(id)
);
```

**Thoughts:**

- 2NF выполняется автоматически, если каждая таблица имеет первичный ключ **из одного столбца** — для частичной зависимости требуется составной ключ.
- BCNF ⊂ 3NF: таблица может быть 3NF (все непростые атрибуты зависят только от ключей), но не BCNF, если **не суперключ** определяет часть ключа. Декомпозиция до BCNF не всегда сохраняет зависимости.
- «Нормализованный» в разговоре обычно означает **3НФ**, а не 6НФ.

**Sources:**

[Нормализация базы данных (Википедия)](https://en.wikipedia.org/wiki/Database_normalization) · [Первая нормальная форма](https://en.wikipedia.org/wiki/First_normal_form) · [BCNF](https://en.wikipedia.org/wiki/Boyce%E2%80%93Codd_normal_form) · Кодд, _Реляционная модель Данные для больших общих банков данных_ (1970 г.)

<details>
  <summary>Normalization vs denormalization</summary>

### Normalization vs denormalization

**Definition:** **Нормализация** разбивает данные на связанные таблицы, чтобы уменьшить избыточность (формы: [1NF–3NF, BCNF](#normal-forms-1nf3nf-bcnf)). **Денормализация** дублирует данные для более быстрого чтения.

**How it works:**

OLTP, часто обновляемые объекты, строгая целостность (пользователи, заказы, платежи).

Аналитика с интенсивным чтением, встроенные документы (снимок заказа при оформлении заказа), таблицы кэша, модели чтения CQRS.

**Pluses and minuses:**

| + (нормализованный)         | − (нормированный)                    |
| --------------------------- | ------------------------------------ |
| Никаких аномалий обновления | Больше присоединений во время чтения |
| Меньший объем памяти        | Сложные запросы для дашбордов        |

| + (денормализованный)                      | − (денормализованный)                                   |
| ------------------------------------------ | ------------------------------------------------------- |
| Быстрее читает, меньше JOINов              | Аномалии обновления — необходимо синхронизировать копии |
| Лучше для отчетов с большим объемом чтения | Больше логики приложения для большей согласованности    |

**Examples:**

```sql
-- 3NF — name lives once in products
CREATE TABLE products (id SERIAL PRIMARY KEY, name TEXT, price NUMERIC(10,2));
CREATE TABLE order_items (
  id SERIAL PRIMARY KEY,
  order_id INT REFERENCES orders(id),
  product_id INT REFERENCES products(id),
  qty INT
);

-- Denormalized snapshot — freeze name/price at purchase (catalog can change later)
CREATE TABLE order_items (
  id SERIAL PRIMARY KEY,
  order_id INT,
  product_id INT,
  product_name TEXT,
  unit_price NUMERIC(10,2),
  qty INT
);
```

**Thoughts:** Целевой 3NF для записи. Денормализуйте **после** измерения медленных запросов, а не заранее. Копии должны обновляться вместе или рассматриваться как неизменяемая история.

**Sources:**

[Используйте Индекс, Люк — Анализ](https://use-the-index-luke.com/sql/anatomy) · [Нормализация базы данных](https://en.wikipedia.org/wiki/Database_normalization)

<details>
  <summary>CRUD</summary>

### CRUD

**Definition:** **Создание, Чтение, Обновление, Удаление** — четыре основные операции сохранения данных, которые реализует каждый API, поддерживаемый данными.

**When to use:** Ресурсы REST, панели администратора, простое управление объектами.

**Pluses and minuses:**

| +                                                 | −                                                      |
| ------------------------------------------------- | ------------------------------------------------------ |
| Универсальный словарь для разных стеков           | Скрывает сложные доменные операции за общими глаголами |
| Четко сопоставляется с HTTP (POST/GET/PUT/DELETE) | Массовые/пакетные операции не совсем подходят          |

**Examples:**

```ts
// Repository pattern — one place for CRUD
type UserRepo = {
  create(data: CreateUserDto): Promise<User>;
  findById(id: string): Promise<User | null>;
  update(id: string, data: UpdateUserDto): Promise<User>;
  delete(id: string): Promise<void>;
};
```

**Thoughts:** Действия домена (`placeOrder`, `refundPayment`) часто охватывают несколько таблиц — не помещайте все в общие CRUD-контроллеры.

**Sources:**

[MDN — методы HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods)

### Migrations & seeds

**Definition:** **Миграции** Изменения схемы версий (вверх/вниз). **Семена** – вводят эталонные или тестовые данные.

**When to use:** Каждый командный проект с общей базой данных. Никогда не изменяйте производственную схему вручную.

**Pluses and minuses:**

| +                                             | −                                                                          |
| --------------------------------------------- | -------------------------------------------------------------------------- |
| Схема в системе контроля версий рядом с кодом | Плохая миграция может привести к блокировке больших таблиц в рабочей среде |
| Воспроизводимые среды                         | Сложность отката при миграции данных                                       |
| Синхронизация команды при изменении схемы     | Требуется дисциплина в CI/CD                                               |

**Examples:**

```prisma
// schema.prisma
model User {
  id        String   @id @default(cuid())
  email     String   @unique
  createdAt DateTime @default(now())
}
```

```bash
npx prisma migrate dev --name init
npx prisma db seed
```

#### Sequelize migration & seed commands

### Sequelize migration & seed commands

```bash
npx sequelize-cli migration:generate --name create-users
npx sequelize-cli db:migrate
npx sequelize-cli db:migrate:undo
npx sequelize-cli seed:generate --name demo-users
npx sequelize-cli db:seed:all
```

Форма файла миграции:

```js
module.exports = {
  async up(queryInterface, Sequelize) {
    await queryInterface.createTable("Users", {
      /* ... */
    });
  },
  async down(queryInterface) {
    await queryInterface.dropTable("Users");
  },
};
```

**Thoughts:**

- Предпочитайте миграцию с обратной совместимостью (добавьте столбец с нулевым значением → заполнение → добавьте NOT NULL).
- Большие изменения таблицы: используйте `CONCURRENTLY` индексы в Postgres, избегайте блокировки `ALTER` в часы пик.
- Семена предназначены для разработки/промежуточного тестирования — никогда не запускайте деструктивные семена в производстве.

**Sources:** [Prisma Migrate](https://www.prisma.io/docs/orm/prisma-migrate)
