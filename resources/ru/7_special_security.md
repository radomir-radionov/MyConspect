### Web application security (principles)

**Definition:**

Практики защиты конфиденциальности, целостности и доступности веб-приложений и пользовательских данных.

| Площадь                | Ключевые практики                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| **Аутентификация**     | Надежные пароли, MFA, OAuth; пароли хэш+соль (bcrypt/argon2); вход с ограничением скорости       |
| **Авторизация**        | РБАК/АБАК; наименьшие привилегии; серверные проверки по каждому запросу                          |
| **Проверка ввода**     | Ввод белого списка; кодировать вывод;параметризованные запросы                                   |
| **Управление сеансом** | Файлы cookie HttpOnly, Secure, SameSite; короткий срок жизни; вращаться при изменении привилегий |
| **Транспорт**          | HTTPS везде; ХСТС                                                                                |
| **Заголовки**          | CSP, Параметры X-Frame, Параметры типа X-Content                                                 |
| **Зависимости**        | Блокировка файлов, аудит(`npm audit`), минимальная глубина                                       |
| **Журналирование**     | Аудит событий аутентификации; никогда не регистрируйте секреты                                   |

**When to use:** Всегда в производстве. Модель угроз перед запуском.

**Pluses and minuses:**

| + (глубокоэшелонированная защита)            | −                                            |
| -------------------------------------------- | -------------------------------------------- |
| Многоуровневые меры по смягчению последствий | Сложность и накладные расходы                |
| Готовность к соблюдению                      | Ложный смысл, если только на стороне клиента |

**Thoughts:**

Безопасность постоянна, а не контрольный список. Транспортное шифрование: [Шифрование](#encryption) · [HTTPS](./6_web_api_http.md#https). Заголовки, специфичные для HTTP: [6_web_api.md](./6_web_api.md).

### Encryption

**Definition:** Шифрование преобразует данные с помощью **шифра** и **ключа**, поэтому посторонние лица не могут их прочитать; только тот, у кого есть соответствующий ключ (или пара), может отменить преобразование. **Криптография** изучает шифры, ключи и целые криптосистемы (хранение + транзит). Хеширование связано с этим, но **не** шифрованием: это односторонний дайджест.

**How it works:**

- Интернет (IP/TCP) **не** шифрует по умолчанию. Конфиденциальность добавляют пользователи и протоколы: **TLS/HTTPS**, почта через TLS, подписанные API, токены. Сам по себе IP никогда не имел встроенного «уровня конфиденциальности».
- Оценивайте алгоритм по **криптографической стойкости** (устойчивости к криптоанализу) и **скорости** (работа в зависимости от размера входных данных, операций на байт, аппаратного обеспечения). Сила без полезной скорости (или наоборот) — неправильный выбор.- **Симметричный** — один и тот же секрет для шифрования и дешифрования (блочные шифры, такие как AES; потоковые шифры). Цезарь/Атбаш/Виженер обучают игрушкам, а не производству. Быстрые, короткие клавиши для заданной силы; ключ **распределение** и **парные секреты N²** — это боль.
- **Асимметричный (открытый ключ)** — **пара** ключей. Открытый ключ шифрует (или проверяет); секретный ключ расшифровывает (или подписывает). РСА, ЕСЦ. Никакого предварительного секрета;медленнее, более длинные клавиши. Типичное использование в Интернете: рукопожатие / перенос **сессионного** ключа, а не больших объемов HTTP-байтов. **SSH** использует ту же идею для входа в систему: закрытый ключ остается у клиента; открытый ключ находится в `authorized_keys` — [DevOps — SSH](./15_devops.md#ssh).
- **Гибрид (настоящий TLS):** стороны аутентифицируют (сертификаты) и **согласовывают** новый **симметричный** сеансовый ключ (современный: **ECDHE**, а не «RSA-шифрование токена сеанса»). Затем AES-GCM (или аналогичный) шифрует сеанс. Ключи умирают вместе с сеансом или при отзыве.
- **Цифровые подписи** инвертируют цель «кто может читать»: **подписи частного** ключа; **открытый** ключ проверяет.Проверить авторство/честность может любой желающий; только владелец закрытого ключа мог подписать. Подписи обычно сначала хешируют документ, а затем подписывают дайджест — они не шифруют весь файл. **Диффи-Хеллмана** — это **ключевое соглашение**, а не схема подписи. **ECDSA** — это алгоритм подписи (используется в TLS и некоторых блокчейнах).- **Криптографические хеши** (MDN: односторонние, с защитой от несанкционированного доступа, устойчивые к коллизиям, фиксированной длины). Небольшие входные изменения → несвязанный дайджест. Столкновения **сложны**, но не невозможны — не претендуйте на «уникальность навсегда». **MD5/SHA-1** не работают в целях безопасности. **SHA-256/512** для целостности; **Argon2id/scrypt/bcrypt/PBKDF2** для **паролей** (медленный + уникальный **соль**).Один только быстрый SHA-256 является неправильным хранилищем паролей ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)).
- **Веб-интерфейс:** TLS, сертификаты X.509, подписи, хеши. Подробности о сертификатах/рукопожатии остаются в [HTTPS](./6_web_api_http.md#https) и [TLS-сертификаты](./6_web_api_http.md#tls-certificates-x509--pki).

**When to use:**

HTTPS-сессии; шифрование хранящегося файла с помощью AES; проверка загрузки с помощью SHA-256; хранение секретов входа в систему с помощью Argon2id; Адресация содержимого Git (см. [Внутренние функции Git](./0_git_core.md#git-internals--dag) — Git по-прежнему использует SHA-1 для объектов; это адресация целостности, а не хеширование паролей).

| Ключи                              | Роль                                                      | Типовые алгоритмы (статус)                                                                       |
| ---------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Нет (дайджест)**                 | Целостность, объекты Git, **не** обратимые                | ША-2/3; избегайте MD5/SHA-1 в целях безопасности. Пароли: Argon2id/bcrypt, а не «хеш=шифрование» |
| **Один (симметричный)**            | Быстрые объемные данные                                   | AES (+режим GCM/CTR); исторические: DES (не работает), RC4 (не использовать)                     |
| **Два (асимметричные)**            | Соглашение о ключах, шифрование небольших данных, подписи | RSA, ECC/ECDH, ECDSA, DSA. ДХ = соглашение                                                       |
| Симметричный против асимметричного | Симметричный                                              | Асимметричный                                                                                    |
| -------------------------          | -----------                                               | ------------                                                                                     |
| Скорость/объемные данные           | Быстро                                                    | Медленный; размер сообщения привязан к размеру ключа                                             |
| Обработка ключей                   | Сначала нужно поделиться секретом                         | Открытый ключ может путешествовать в открытом доступе                                            |
| Количество ключей в масштабе       | Множество парных секретов                                 | Одна пара на вечеринку                                                                           |

#### Common pitfalls

Называя хеши «необратимым шифрованием». Использование MD5/SHA-1 для паролей или сертификатов. Шифрование паролей, чтобы их можно было расшифровать. RSA-шифрование всей полезной нагрузки. Обучение Caesar тому, «как работает HTTPS». Смешивание **хэш-таблиц** (индекс некрипто-ведра — [Хеш-таблица](./7_special_data_structures_advanced.md#hash-table)) с SHA. Предполагая, что DH является подписью.

**Examples:**

Дайджест SHA-256 в безопасном контексте (`SubtleCrypto.digest` — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)). Используйте это для целостности, а не для хранения паролей.

```js
async function sha256Hex(message) {
  const bytes = new TextEncoder().encode(message);
  const buf = await crypto.subtle.digest("SHA-256", bytes);
  return Array.from(new Uint8Array(buf))
    .map((b) => b.toString(16).padStart(2, "0"))
    .join("");
}
```

**Thoughts:** _TLS = рукопожатие с открытым ключом + быстрый симметричный сеанс; хеши подтверждают целостность и (с медленным KDF) защищают пароли — они не расшифровываются._

**Sources:**

[MDN — криптография с симметричным ключом](https://developer.mozilla.org/en-US/docs/Glossary/Symmetric-key_cryptography) · [MDN — криптография с открытым ключом](https://developer.mozilla.org/en-US/docs/Glossary/Public-key_cryptography) · [MDN — Hash функция](https://developer.mozilla.org/en-US/docs/Glossary/Hash_function) · [MDN — SubtleCrypto.digest](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest) · [OWASPХранение паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [Doka — Шифрование](https://doka.guide/tools/encryption/) (концептуальная карта; для статуса алгоритма используйте MDN/OWASP)

<details>
  <summary>XSS (Cross-Site Scripting)</summary>

### XSS (Cross-Site Scripting)

**Definition:** Злоумышленник внедряет скрипт, который запускается в браузере жертвы **в вашем источнике**, чтобы он мог действовать как пользователь (файлы cookie, DOM, запросы).

**How it works:**

Недоверенная строка рассматривается как HTML/JS. Классический **отражённый** XSS: поиск `q=` отражается на странице; полезная нагрузка в URL-адресе выполняется для этого ответа. **Сохраненный** XSS: полезные данные сохраняются (база данных, файл, кеш) и запускаются позже для каждого средства просмотра. **DOM XSS:** клиентский JS записывает в DOM ненадежные данные (`innerHTML`, `document.write`).

| Тип               | Когда он срабатывает                                                              |
| ----------------- | --------------------------------------------------------------------------------- |
| **Отражение**     | Немедленно, в ответе HTTP (часто созданном URL-адресе)                            |
| **Сохранено**     | Позже для многих пользователей — сложнее очистить (необходимо очистить хранилище) |
| **На основе DOM** | Эхо сервера не требуется — ошибочный рендеринг клиента                            |

| смягчение последствий                                   | Почему                                                                                          |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Закодировать вывод для **контекста** (HTML/attr/URL/JS) | `<script>` становится безобидным текстом (`&lt;script&gt;…`)                                    |
| `textContent` / текстовые узлы каркаса                  | Текст React/Svelte экранирован; `innerHTML` / `dangerouslySetInnerHTML` не                      |
| Санировать, если необходимо разрешить HTML              | DOMPurify (или эквивалент) — никогда не «убегайте с помощью `encodeURI`» для HTML               |
| CSP (`script-src` одноразовый номер/хеш)                | Резервное копирование в случае сбоя кодирования — неизвестные скрипты не запускаются            |
| Файлы cookie сеанса HttpOnly                            | XSS не может прочитать файл cookie (все еще может действовать **как** пользователь на странице) |

**When to use:** Поиск по страницам, комментариям, профилям, сообщениям об ошибках, повторяющим ввод, редакторам форматированного текста. Отраженный XSS часто выглядит как поисковый запрос, повторяющий фразу «ничего не найдено для…».

**Examples:**

```js
// Unsafe — parses markup
el.innerHTML = userInput;

// Safer for plain text (not for a <script> element's textContent — that still runs)
el.textContent = userInput;
```

Кодирование HTML превращает разметку в текст, который синтаксический анализатор не будет выполнять:

```
<input>  <script>…</script>
output   &lt;script&gt;…&lt;/script&gt;
```

**Thoughts:**

SQL-инъекция **не** XSS — другой канал (SQL или HTML/JS). `encodeURI` / `encodeURIComponent` кодируйте **URL**, а не HTML. Кодируйте **на выходе** в правильном контексте; также проверьте на сервере. Лабораторные работы: DOM XSS/отраженный XSS на [application.security](https://application.security). Автоматические проверки: [Тестирование безопасности](./7_special_testing_layers.md#security-testing).

_Обрабатывать каждую пользовательскую строку как данные — кодировать для выходного контекста; CSP — резервная сеть._

**Sources:**

[OWASP XSS](https://owasp.org/www-community/attacks/xss/) · [MDN — XSS](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS) · [Doka — веб-безопасность](https://doka.guide/security/web-security/)

  <summary>Stored XSS & XSS-driven keylogging</summary>

### Stored XSS & XSS-driven keylogging

**Definition:** Сохраненный XSS сохраняется в приложении. Распространенным классом полезных данных является **кейлоггер**: скрипт, который записывает нажатия клавиш (и другие события) и отправляет их злоумышленнику.

**How it works:**

1. Злоумышленник публикует контент, который приложение хранит в необработанном виде (комментарий, «твит», профиль).
2. Каждый подписчик/зритель загружает этот HTML; скрипт запускается в источнике сайта.
3. Слушатели включены `keydown` / поля формы собирают учетные данные; при эксфильтрации часто используется запрос, который разрешено сделать странице (например, `img`/`fetch` хосту злоумышленника, если только CSP `connect-src`/`img-src` блокирует его).
4. Очистка требует удаления или очистки сохраненных записей, а не просто исправления кода.

| Плюсы (для злоумышленника)                               | смягчение последствий                                                             |
| -------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Со временем становится популярным у многих пользователей | Кодирование при **сохранении и рендеринге**; считать старые строки БД ненадежными |
| Может самораспространяться через другие ошибки           | CSP + нет `unsafe-inline`; карантин `connect-src`                                 |
| Крадет пароли, введенные в вашем источнике               | HttpOnly файлы cookie; МИД; рассматривать XSS как полную компрометацию аккаунта   |

**When to use:** Любой пользовательский контент, который позже отображается как HTML. Кейлоггинг — это **следствие** XSS, а не отдельный протокол — скрипт запускается как сайт и может прослушивать ключи, а затем отправлять их, если CSP `connect-src` / `img-src` блокирует его.

**Thoughts:**

Очистка — это проблема **данных** (очистка или перекодирование сохраненных строк), а не только исправление кода. Червь может повторно опубликовать себя через другие ошибки. Лабораторная работа: сохраненный XSS на [application.security](https://application.security).

_Сохраненный XSS задерживается и становится жертвой нескольких атак; требуется кодирование + CSP + очистка сохраненного HTML._

**Sources:**

[OWASP XSS](https://owasp.org/www-community/attacks/xss/) · [MDN — CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)

<details>
  <summary>Content-Security-Policy (CSP)</summary>

### Content-Security-Policy (CSP)

**Definition:** Список HTTP-заголовков **доверенных источников** для скриптов, стилей, изображений и подключений — вторая линия защиты в случае сбоя кодирования XSS.

**How it works:** Браузер блокирует загрузки и встроенные скрипты вне политики. `default-src` заполняет неуказанные директивы выборки. `script-src` с **нонсами/хешами** (не `'unsafe-inline'`) это то, что на самом деле останавливает инъекцию `<script>`. `frame-ancestors` является кликджекингом (который может **встроить вас**), а не `frame-src` (что **вы** можете использовать в iframe).

**When to use:** Каждый ответ HTML. Сопряжение с кодировкой вывода — одного CSP недостаточно, если вы разрешите `'unsafe-inline'`.

**Pluses and minuses:**

| +                                                                          | −                                                                             |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Ограничивает использование маяков с украденными клавишами и внедренных CDN | Разбивает встроенные скрипты/стили, пока вы не используете одноразовые номера |
| `frame-ancestors` заменяет устаревший `X-Frame-Options: ALLOW-FROM`        | `<meta>` CSP не может установить `frame-ancestors`                            |

**Examples:**

```http
Content-Security-Policy: default-src 'self' https://*.trusted.com; script-src 'self'; frame-ancestors 'self'
```

Полная таблица директив: [Веб-API — CSP](./6_web_api_security.md#content-security-policy-csp). Каталог заголовков: [securityheaders.com](https://securityheaders.com/).

**Thoughts:** _Источники разрешенного списка; никогда не лечи `'unsafe-inline'` в качестве защиты от XSS._

**Sources:**

[MDN — CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP) · [MDN — Frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)

<details>
  <summary>CSRF (Cross-Site Request Forgery)</summary>

### CSRF (Cross-Site Request Forgery)

**Definition:** Злоумышленник обманом заставляет **уже аутентифицированный** браузер отправить запрос на изменение состояния на ваш сайт. Сеансовые файлы cookie отправляются автоматически; сервер думает, что пользователь намеревался совершить это действие.

**How it works:**

1. У пользователя включен файл cookie сеанса. `app.com`.
2. Посещения пользователей `evil.com`, который запускает POST/GET для `app.com` (форма, образ, `fetch` с файлами cookie, если CORS позволяет).
3. Сервер проверяет подлинность файла cookie, но никогда не проверяет, был ли **этот запрос авторизован пользователем** (токен CSRF/SameSite/Origin).

- **Аутентификация** — кто это? (сессия действительна).
- **Авторизация** — разрешен ли **и предназначен** этот запрос? В CSRF отсутствует вторая проверка мутаций, аутентифицированных с помощью файлов cookie.

| Оборона                                             | Как                                                                                                   |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Токен CSRF в форме/заголовке                        | Секрет, который злоумышленник не может прочитать (синхронизатор или двойная отправка)                 |
| `SameSite=Lax` or `Strict`                          | Файл cookie не отправляется в большинстве межсайтовых POST                                            |
| `HttpOnly`                                          | Не позволяет JS **читать** файлы cookie — **не** останавливает CSRF (браузер все равно отправляет их) |
| `Origin` / `Referer` проверить                      | Отклонить отсутствие или иностранное происхождение                                                    |
| CORS + без подстановочных знаков для учетных данных | CORS сам по себе **не** является защитой от CSRF                                                      |
| Повторная аутентификация/повышение                  | Переводы, смена пароля                                                                                |

**When to use:** Сеансы файлов cookie + HTML-формы (например, «отправить деньги»); API-интерфейсы SPA для файлов cookie. JWT в `Authorization` не прикрепляется браузером автоматически.

**Examples:**

```html
<form action="/send_money/" method="POST">
  <input type="hidden" name="csrf" value="token-generated-by-server" />
  <!-- rest of form -->
</form>
```

```http
Set-Cookie: sid=abc; HttpOnly; Secure; SameSite=Strict
```

AJAX: отправить тот же секрет, что и `X-CSRF-Token`. Полные шаблоны: [Веб-API — CSRF](./6_web_api_security.md#csrf-cross-site-request-forgery). Лабораторная работа: [application.security](https://application.security) CSRF.

**Thoughts:** Никогда не меняйте состояние при GET. `SameSite` это глубокая защита, а не полная замена токенов на конфиденциальных POST. CORS не останавливает файлы cookie CSRF. `HttpOnly` скрывает файл cookie от JS — браузер все равно **отправляет** его.

**Sources:**

[OWASP CSRF](https://owasp.org/www-community/attacks/csrf) · [MDN — SameSite](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie/SameSite)

<details>
  <summary>SQL injection</summary>

### SQL injection

**Definition:** Ненадежные входные данные объединяются в SQL, поэтому злоумышленник меняет **структуру запроса** (чтение, запись или уничтожение данных). Это **инъекция в SQL**, а не XSS.

**How it works:**

Войти или выполнить поиск сборок `SELECT … WHERE email = '${input}'`. Введите лайк `' OR '1'='1` делает предикат всегда истинным. `UNION SELECT` может добавлять дополнительные наборы результатов, если приложение их возвращает. Деструктивные высказывания возможны, если роль БД позволяет это.

| смягчение последствий                                                                          |
| ---------------------------------------------------------------------------------------------- |
| Параметризованные запросы/подготовленные операторы (привязка значений, никогда не объединение) |
| API-интерфейсы ORM, которые связывают параметры (избегайте необработанного строкового SQL)     |
| Пользователь БД с наименьшими привилегиями (приложение не может `DROP DATABASE`)               |
| Никогда не доверяйте «экранированию» на стороне клиента как исправлению SQLi                   |

**When to use:** Любое значение пользователя в запросе — логин, поиск, идентификаторы. Тот же класс существует для NoSQL (внедрение оператора в JSON).

**Examples:** Полный дамп воздействия + пять защит (параметры, ORM, проверка, минимальные привилегии, процедуры): [База данных — SQL-инъекция](./9_database_sql.md#sql-injection). Лабораторная работа: [application.security](https://application.security) SQL-инъекция.

**Thoughts:**

Экранирование на **интерфейсе** не защищает базу данных. Проверка типов/длины в качестве дополнительной защиты; параметризация – это контроль.

_Привязка значений; никогда не объединяйте пользовательский ввод в SQL. SQLi ≠ XSS._

**Sources:**

[OWASP SQL-инъекция](https://owasp.org/www-community/attacks/SQL_Injection)

<a name="clickjacking"></a>

<details>
  <summary>Clickjacking</summary>

### Clickjacking

**Definition:** Исправление пользовательского интерфейса — ложная страница накладывается на **прозрачный iframe** вашего сайта, поэтому клик пользователя попадает в **ваш** аутентифицированный пользовательский интерфейс (например, платите, подписывайтесь).

**How it works:**

1. На злой странице изображена заманчивая кнопка.
2. Прозрачный `<iframe src="https://yoursite.com/…">` находится сверху (в iframe применяются файлы cookie жертвы).
3. Щелчок попадает в реальный элемент управления в iframe.

| Заголовок                                                     | Эффект                                                                      |
| ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `X-Frame-Options: DENY`                                       | Никогда не вставляйте этот документ во фрейм                                |
| `X-Frame-Options: SAMEORIGIN`                                 | Вставлять только в том случае, если все предки имеют такое же происхождение |
| `X-Frame-Options: ALLOW-FROM`                                 | **Устарело** — современные браузеры **игнорируют весь заголовок**           |
| CSP `frame-ancestors 'none'` / `'self'` / перечисленные хосты | Предпочтительная замена; более гибкий, чем XFO                              |

**When to use:** Платежи, удаления, согласие OAuth, лайки/подписки в социальных сетях. Файлы cookie SameSite помогают, когда проверка подлинности основана на файлах cookie, но **не** заменяют элементы управления кадрированием (публичный пользовательский интерфейс без аутентификации все равно может быть создан).

**Examples:**

```http
X-Frame-Options: SAMEORIGIN
Content-Security-Policy: frame-ancestors 'self'
```

`X-Frame-Options` должен быть **HTTP-заголовком**, а не `<meta>`. `SAMEORIGIN` — обычный выбор, когда продукт создает iframe (исторически использовался Twitter/X).

**Thoughts:**

CSP `frame-ancestors` невозможно установить через `<meta http-equiv>`. Разрушающий фреймы JS сам по себе слаб. Лабораторная работа: [application.security](https://application.security) кликджекинг.

_Не разрешать сторонним страницам использовать аутентифицированный пользовательский интерфейс — `frame-ancestors` во-первых, XFO как запасной вариант._

**Sources:**

[javascript.info/clickjacking](https://javascript.info/clickjacking) · [OWASP Clickjacking](https://owasp.org/www-community/attacks/Clickjacking) · [MDN —frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/frame-ancestors)

<details>
  <summary>DoS and DDoS</summary>

### Denial of Service (DoS / DDoS)

**Definition:** Перегрузить службу, чтобы законные пользователи не могли ее использовать (доступность). **DDoS** — это одна и та же идея из многих источников одновременно.

**How it works:**

Заполните HTTP (или другой), чтобы исчерпать ресурсы ЦП, ОЗУ, сокетов или пропускной способности. Одна машина все еще может навредить небольшому происхождению; многие боты (ботнеты) превышают ограничения IP.

| смягчение последствий                         | Лимит                                                                           |
| --------------------------------------------- | ------------------------------------------------------------------------------- |
| Ограничение скорости (пользователь, IP, ключ) | Помогает злоупотреблениям и грубой силе; **слабые и распределенные наводнения** |
| Емкость + CDN/Anycast                         | Собрать или бросить мусор на краю                                               |
| Автомасштабирование/отработка отказа          | Заменить насыщенные экземпляры; изменить IP-адреса, если необходимо             |
| WAF / очистка                                 | Фильтровать известные схемы наводнений                                          |

**When to use:** Публичные API, вход в систему, дорогие конечные точки (поиск, отчеты). См. [Веб-API — 429](./6_web_api_http.md#rate-limiting-429) и [Проектирование системы — ограничение скорости](./0_system_design_data.md#rate-limiting).

**Thoughts:**

100% защиты от DoS не существует. «Отражать DDoS-атаки обратно на злоумышленника» не является практичным и безопасным средством контроля — вместо этого отбрасывайте/фильтруйте на границе.

_Наличие: ограничение скорости + емкость на периферии; Ограничения IP-адресов не работают в отношении ботнета._

**Sources:**

[Отказ в обслуживании OWASP](https://owasp.org/www-community/attacks/Denial_of_Service)

<details>
  <summary>Slowloris</summary>

### Slowloris (slow HTTP DoS)

**Definition:** DoS путем открытия множества соединений и отправки данных запроса **чрезвычайно медленно**, поэтому работники остаются занятыми неполными запросами.

**How it works:**

Сервер не может завершить анализ заголовков/тела; соединение остается открытым. Когда один падает, злоумышленник открывает другой. Серверы потоков/процессов (классический префорк Apache) особенно чувствительны; один клиент может содержать много слотов.

| смягчение последствий                          | Почему                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------- |
| Короткие таймауты чтения / мин байт в секунду  | Закройте незавершенные незавершенные запросы (например, Apache `mod_reqtimeout`) |
| Ограничение количества подключений по IP       | Ограничивает один источник Slowloris                                             |
| Серверы, управляемые событиями/обратный прокси | Меньше заблокированных потоков для каждого медленного клиента                    |
| Ограничения ставок                             | Дополнительный сигнал о подозрительном трафике                                   |

**When to use:** Любой источник, который долго ожидает незавершенного HTTP. Фронтенд не может это исправить — это конфигурация origin/proxy.

**Thoughts:** _Тайм-ауты и ограничения на соединения, а не «больше экранирования XSS»._

**Sources:**

[Qualys — медленные HTTP-атаки](https://blog.qualys.com/vulnerabilities-threat-research/2011/11/02/how-to-protect-against-slow-http-attacks)

<details>
  <summary>Decompression / zip bombs</summary>

### Decompression bombs (data bombs)

**Definition:** Небольшая загрузка (архив, gzip, некоторые изображения), которая **увеличивается в размерах**, когда сервер ее распаковывает – из-за нехватки диска, процессора или оперативной памяти (DoS).

**How it works:**

Вложенные слои zip (хорошо известный **42.zip** имеет размер ~42 КБ и при полной распаковке разворачивается в огромное дерево). Похожий шаблон: бомбы gzip/deflate, XML «миллиард смеха». Тело HTTP выглядит небольшим; обработка огромна.

| Слой        | Контроль                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------- |
| Фронтенд    | Максимальный размер файла + список разрешений MIME (только UX — недостаточно)               |
| Сервер      | Размер шапки в распакованном виде; стрим с жестким лимитом; отказаться от вложенных архивов |
| Изображения | Декодирование с максимальной шириной/высотой/пикселями; не неограниченно раздувать          |

**When to use:** Загрузка аватара, распаковка на сервере, «импорт zip», конвейеры изображений.

**Thoughts:**

Проверки MIME/размера внешнего интерфейса обходятся созданным запросом. Лимиты принадлежат серверу. Фронтенд по-прежнему может ограничивать размер/MIME для UX.

_Привязанный распакованный размер на сервере — никогда не распаковывайте ненадежные архивы без ограничений._

**Sources:**

[OWASP — zip-бомбы/декомпрессия](https://owasp.org/www-community/vulnerabilities/Unrestricted_File_Upload) · [Doka — веб-безопасность](https://doka.guide/security/web-security/)

<details>
  <summary>MITM (Man in the Middle)</summary>

### Man in the Middle (MITM)

**Definition:** Злоумышленник находится на пути (незаконная точка доступа, взломанный маршрутизатор) и **читает или изменяет** трафик между браузером и сервером.

**How it works:**

При открытом Wi-Fi в виде открытого текста **HTTP** отображаются файлы cookie и пароли. Несанкционированная точка доступа может выдавать себя за маршрутизатор. Самодельное «вот мой открытый ключ» через HTTP можно заменить на ключ злоумышленника (классическая история RSA с открытым текстом). **HTTPS** использует TLS с сертификатами **доверенного центра сертификации**; у клиента уже есть корни CA, поэтому ноутбук в кафе не может незаметно подменить удостоверение сервера.Вмешательство нарушает рукопожатие или целостность записи.

| смягчение последствий                            | Почему                                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------- |
| HTTPS повсюду                                    | Конфиденциальность + целостность на проводе                               |
| ХСТС                                             | Останавливает переход на HTTP после первого посещения HTTPS               |
| Не игнорируйте предупреждения сертификатов       | Обход пользователя повторно включает MITM                                 |
| Сертификат Прозрачность/закрепление (редко, опс) | Дополнительные проверки доверия, если центр сертификации скомпрометирован |

**When to use:** Кафе, гостиницы, перехват интернет-провайдеров. См. [Веб-API — HTTPS](./6_web_api_http.md#https) и [сертификаты TLS](./6_web_api_http.md#tls-certificates-x509--pki).

**Thoughts:**

Доверие по-прежнему зависит от центров сертификации (корневой магазин + цепочка). Скомпрометированные или мошеннические центры сертификации — это сбой отраслевого уровня, а не ошибка приложения. RSA — это одно семейство алгоритмов; современный TLS использует согласованные наборы шифров и соглашение об эфемерных ключах, а не «шифрует первое HTTP-приветствие с помощью RSA».

_HTTPS/TLS + HSTS; никогда не просматривайте предупреждения о сертификатах._

**Sources:**

[MDN — HTTPS](https://developer.mozilla.org/en-US/docs/Glossary/HTTPS) · [MDN — TLS](https://developer.mozilla.org/en-US/docs/Glossary/TLS)

<details>
  <summary>IDOR (Insecure Direct Object Reference)</summary>

### IDOR (Insecure Direct Object Reference)

**Definition:** Ошибка авторизации, когда изменение **идентификатора объекта** в URL-адресе, теле или вызове API предоставляет доступ к ресурсу другого пользователя, поскольку сервер проверяет аутентификацию, но **не право собственности**.

**How it works:**

1. Пользователь А аутентифицирован (`GET /api/orders/123` — их приказ).
2. Пользователь А меняет идентификатор на `124` — сервер возвращает заказ пользователя Б.
3. Основная причина: конечная точка проверяет «вошел в систему?» а не "принадлежит ли этот ресурс этому пользователю?"
4. UUID скрывают идентификаторы, но **не исправляют** IDOR — злоумышленник все равно может перечислить или утечь идентификаторы.

| Плюсы (для злоумышленника)                                            | смягчение последствий                                                     |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Легко использовать — изменить один параметр                           | **Авторизуйте доступ к каждому ресурсу** на стороне сервера               |
| Очень часто встречается при аудите API                                | Проверять `resource.ownerId === session.userId` (или RBAC)                |
| Работает с последовательными идентификаторами и идентификаторами UUID | Используйте уровень политики (ABAC) — идентификаторы не являются секретом |

| Интеграционные тесты для межпользовательского доступа (отрицательные случаи) |

| Журналы аудита для проверки подозрительных идентификаторов |

**When to use:** Любой API, возвращающий данные пользователя по идентификатору — заказы, счета, сообщения, файлы, медицинские записи. Особенно опасно в REST, где структура URL раскрывает тип и идентификатор ресурса.

**Examples:**

```js
// ❌ IDOR — only checks auth, not ownership
app.get("/api/orders/:id", async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  res.json(order); // any logged-in user can read any order
});

// ✅ Authorize ownership
app.get("/api/orders/:id", async (req, res) => {
  const order = await db.orders.findById(req.params.id);
  if (!order || order.userId !== req.user.id) return res.status(404).end();
  res.json(order);
});
```

**Thoughts:** Возвращайте **404** (а не 403) для отсутствующих/неавторизованных ресурсов, чтобы избежать утечки информации. Самая распространенная ошибка API в пентестах. Категория OWASP Top 10: Нарушенный контроль доступа.

**Sources:**

[OWASP IDOR](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/05-Authorization_Testing/04-Testing_for_Insecure_Direct_Object_References)
