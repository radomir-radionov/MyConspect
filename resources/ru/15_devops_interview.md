### What is DevOps and how does it enhance software delivery?

**Definition:**

DevOps — совместный и итеративный подход, который объединяет разработку программного обеспечения и IT-эксплуатацию. Эта совместная модель изменила поставку ПО, введя конвейеры Continuous Integration/Continuous Deployment (CI/CD).

**How it works:**

Ключевые положения DevOps

- Автоматизация: упрощает повторяющиеся задачи.
- Кросс-функциональное сотрудничество: развивает командную работу между ролями, которые традиционно были разобщены.
- Непрерывный мониторинг и обратная связь: дают сведения в реальном времени и повышают надёжность и производительность продукта.

**Pluses and minuses:**

Польза DevOps

- Ускоренная разработка ПО: меньше ручного вмешательства и короткие циклы обратной связи ускоряют график выпусков.
- Более высокое качество продукта: упор на всестороннее тестирование вместе с автоматизацией снижает человеческие ошибки.
- Улучшенная безопасность: непрерывная обратная связь и регулярная оценка угроз помогают находить и устранять уязвимости рано в процессе разработки.
- Более высокая конкурентоспособность: компании, которые используют DevOps, быстро реагируют на изменения рынка и опережают конкурентов.
- Экономия затрат: автоматизация и выстроенные процессы снижают накладные расходы и ведут к экономии.
- Устойчивость: автоматизация и мониторинг в DevOps дают стабильность системы и быстрое восстановление после сбоев, обеспечивая высокую доступность.
- Удовлетворённость клиентов: быстрые исправления ошибок и новые возможности делают опыт пользователя лучше.

### Can you describe the key principles of DevOps?

**Definition:**

DevOps — набор практик, которые упрощают и соединяют разработку программного обеспечения (Dev) и IT-эксплуатацию (Ops), чтобы поставка ПО была быстрее и надёжнее.

**How it works:**

Основные принципы

1. Ориентация на клиента: непрерывная обратная связь и короткие циклы разработки дают быстрые обновления, которые ведёт клиент.
2. Ответственность от начала до конца: команда DevOps отвечает за весь процесс поставки ПО, от разработки до постоянного мониторинга и сопровождения.
3. Гибкость: команды умеют адаптироваться и быстро отвечать на изменения требований и деловой среды.
4. Непрерывное улучшение: DevOps развивает культуру постоянного обучения и совершенствования и ищет постоянную оптимизацию в командах и процессах.
5. Возможности самообслуживания: команда вкладывается в то, чтобы участники были самостоятельными и имели готовый доступ к нужным инструментам и платформам.
6. Автоматизированное обеспечение качества: автоматические тесты дают быструю обратную связь о качестве ПО на всём пути разработки и поставки.
7. Безопасность как код: безопасность встроена во все стороны разработки и поставки ПО; политики и код автоматизируют протоколы безопасности.
8. Сотрудничество и общение: регулярное общение и активное сотрудничество между командами, отделами и функциями — ключ к успеху.

Золотое правило DevOps

Главное положение DevOps — ломать барьеры, которые есть в традиционных средах разработки. Когда сотрудничество охватывает роли, команды и функции, каждый участник становится заинтересованной стороной производственного процесса. Это общее владение ведёт к лучшим решениям и в итоге к более качественным выпускам ПО.

### How do continuous integration and continuous deployment (CI/CD) relate to DevOps?

**Definition:**

Continuous Integration (CI) и Continuous Deployment (CD) — основополагающие практики DevOps. Их слаженная оркестрация делает циклы разработки, тестирования и развёртывания тесно связанными, быстрыми и надёжными.

Конвейер CI/CD использует средства автоматизации, контроль версий и репозитории кода, чтобы собирать, тестировать и разворачивать ПО гибко и эффективно.

**How it works:**

Ключевая польза

- Совместный рабочий процесс: участники вносят небольшие и частые изменения кода.
- Быстрая обратная связь: автоматические тесты и проверки качества кода дают мгновенный отклик.
- Упрощённое развёртывание: автоматизация снижает вероятность человеческих ошибок.
- След аудита: контроль версий и журналы обеспечивают прослеживаемость.
- Участие заинтересованных сторон: бизнес-команды, тестировщики и разработчики видят процесс и могут им управлять.
- Адаптивное управление: менеджеры гибче меняют приоритеты и требования.

Учебные алгоритмы

- Триггер сборки: этот триггер конвейера запускает новую сборку при коммите кода.
- Этап модульных тестов: этот этап проверяет, что отдельные компоненты работают как ожидается.
- Этап интеграционных тестов: он проверяет взаимодействие и совместимость компонентов.
- Этап сканирования безопасности: этот этап использует инструменты статического анализа, чтобы находить уязвимости.
- Этап развёртывания в staging: подтверждённые изменения кода разворачивают в промежуточную среду.
- Этап приёмочных тестов: эти тесты выполняет команда QA в промежуточной среде, чтобы убедиться, что продукт ведёт себя как ожидается.
- Этап тестирования UI: этот этап проверяет пользовательский интерфейс ПО.
- Этап выпуска: одобренные изменения кода разворачивают в производственную среду.
- Механизм отката: автоматическая или полуавтоматическая система возвращает производственную среду к прежнему состоянию, если после развёртывания возникают проблемы.

**Examples:**

Учебный пример кода: Node.js и Jenkinsfile

Вот код на Node.js:

```javascript
// server.js
const http = require('http');
const port = 3000;
const server = http.createServer((req, res) => {
    res.statusCode = 200;
    res.setHeader('Content-Type', 'text/plain');
    res.end('Hello, World!\n');
});
server.listen(port, () => {
    console.log(`Server running at http://localhost:${port}/`);
});
```

Ниже Jenkinsfile:

```groovy
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'npm install'
            }
        }
        stage('Test') {
            steps {
                sh 'npm test'
            }
        }
        stage('Deploy to Staging') {
            when {
                branch 'dev'
            }
            steps {
                sh 'docker build -t myapp .'
                // The code below assumes the staging environment is already set up.
                sh 'docker run -d --name myapp-staging -p 3000:3000 myapp'
            }
        }
        stage('Deploy to Production') {
            when {
                branch 'main'
            }
            steps {
                sh 'docker build -t myapp .'
                // The code below assumes the production environment is already set up.
                sh 'docker run -d --name myapp-production -p 8080:8080 myapp'
            }
        }
    }
}
```

### What are the benefits of DevOps in software development and operations?

**Definition:**

DevOps (Development + Operations) — совместный подход, который переплетает разработку программного обеспечения с IT-эксплуатацией. Он ведёт весь цикл разработки ПО, от написания кода до развёртывания в производство, связно, автоматически и эффективно.

**Pluses and minuses:**

Ключевая польза DevOps

- Гибкость: DevOps развивает быструю и итеративную разработку ПО, даёт быструю адаптацию к нуждам рынка и сокращает время выхода на рынок.
- Надёжность и стабильность: практики вроде автоматического тестирования и одинакового развёртывания снижают частоту сбоев и дают стабильные, предсказуемые выпуски.
- Непрерывная поставка: DevOps делает выпуски ПО лёгкими и непрерывными, и команды быстро отвечают на отзывы клиентов или изменения рынка.
- Mean Time To Recover (MTTR): за счёт практик написания кода и автоматических механизмов восстановления DevOps заметно сокращает время на исправление возможных проблем.
- Сотрудничество и общение: DevOps ломает барьеры и даёт согласованное взаимодействие и обмен знаниями между отделами.
- Встроенная безопасность: методология включает проверки безопасности по всему процессу разработки, находит проблемы рано и снижает риски безопасности.
- Приспособляемость: DevOps не привязан к одной экосистеме: он поддерживает разные инструменты и технологии и к ним адаптируется.
- Эффективность: автоматизация упрощает множество ручных задач и экономит время и ресурсы.
- Обеспечение качества: автоматическое тестирование и непрерывный мониторинг держат высокий стандарт качества ПО.
- Управление жизненным циклом: DevOps ведёт полный жизненный цикл ПО и обеспечивает сквозные лучшие практики и эффективность.
- Оптимизация ресурсов: упор на меньшие и более частые развёртывания ведёт к лучшему управлению ресурсами.
- Инновации и обратная связь: отзывы пользователей в реальном времени эффективно включают в работу, что поддерживает постоянное улучшение и инновации.

### Can you explain the concept of “Infrastructure as Code” (IaC)?

**Definition:**

Infrastructure as Code (IaC) — практика DevOps, при которой вычислительную инфраструктуру управляют и подготавливают автоматически, эффективно и одинаково, с помощью шаблонов под контролем версий.

Инструменты IaC, такие как Terraform и Ansible, описывают элементы инфраструктуры, например серверы и сети, в декларативном или императивном стиле для эффективного управления.

Это даёт несколько преимуществ:

- Снижение риска: автоматические процессы уменьшают вероятность человеческой ошибки.
- Одинаковость сред: каждая среда, от разработки до производства, поднимается надёжно и одинаково.
- Гибкость: быстрое развёртывание, масштабирование и изменения сокращают время выхода на рынок.
- Экономия: распределение ресурсов оптимизируют, чтобы экономить время и деньги.

IaC охватывает не только подготовку инфраструктуры, но и включает:

- Следы аудита: фиксируют изменения конфигурации.
- Соответствие требованиям: проверяет инфраструктуру по заранее заданным политикам безопасности и соответствия.
- Continuous Integration/Continuous Deployment (CI/CD): стыкуется с CI/CD, чтобы автоматизировать выпуск ПО.

**How it works:**

Инструменты IaC

Несколько инструментов дают IaC, у каждого свои возможности и синтаксис:

- Terraform: объявляет инфраструктуру в готовых модулях и абстрагирует ресурсы через провайдеры.
- Ansible: выполняет задачи на удалённых хостах, работает без агента и общается по SSH.
- AWS CloudFormation: решение только для AWS, которое описывает ресурсы в JSON или YAML.

Лучшие практики IaC

- Версионирование: хранить код в системе контроля версий для прослеживаемости.
- Модульность: разбивать код инфраструктуры на управляемые и переиспользуемые модули.
- Документация: держать ясную и актуальную документацию.
- Тестирование: внедрять автоматические тесты, чтобы проверять изменения инфраструктуры.
- Контроль изменений: следовать формальным процессам управления изменениями при правках инфраструктуры.
- Сотрудничество: внедрять контроль безопасности и доступа.

Парадигмы IaC

- Императивная: прямо задаёт действия, которые нужны, чтобы достичь определённого состояния. Удобна для быстрых разовых задач или поиска неисправностей.
- Декларативная: описывает желаемое состояние и даёт инструменту IaC самому определить действия, чтобы свести текущее состояние к желаемому. Это основной подход для устойчивого, сопровождаемого и одинакового управления инфраструктурой.

Типичные задачи IaC

Подготовка инфраструктуры

- Задача: быстро поднять новую инфраструктуру.
- Пример: развернуть серверы в облаке.

Управление конфигурацией

- Задача: эффективно настраивать уже существующие системы.
- Пример: установить пакеты и поднять веб-серверы.

Оркестрация

- Задача: согласовать несколько систем.
- Пример: развернуть многоуровневое приложение с балансировщиком нагрузки, веб-серверами и базой данных.

Управление жизненным циклом

- Задача: вести жизненный цикл компонентов инфраструктуры, от создания до вывода из эксплуатации.
- Пример: остановить устаревшие ресурсы.

IaC и облачные вычисления

- On-Premise: для традиционных физических серверов и дата-центров инструменты IaC управляют этими ресурсами так же, как облачными средами.
- Публичное облако: платформы вроде AWS, Azure или GCP сами поддерживают IaC. Инструменты этих платформ, такие как AWS CloudFormation или Azure Resource Manager, дают преимущества, специфичные для облака.

IaC и Kubernetes

- Управление ресурсами: инструменты вроде kubectl и Helm дают IaC для Kubernetes, управляя ресурсами вроде pod, service и deployment.
- Конфигурация: объекты Kubernetes, описанные в файлах YAML, помогают поддерживать конфигурации.

<summary>What is meant by “Shift Left” in DevOps?</summary>

### What is meant by “Shift Left” in DevOps?

**Definition:**

Shift Left в DevOps — практика проводить разные процессы разработки и тестирование рано в жизненном цикле ПО. Это даёт быстрое обнаружение проблем и снижает стоимость исправления.

**How it works:**

Ключевая польза

- Раннее обнаружение проблем: дефекты, найденные на начальном этапе, можно быстро устранить.
- Экономия денег и времени: исправлять изъяны рано — небольшая финансовая и временная нагрузка.
- Лучшая синхронизация разработки и QA: меньше расхождений между разработкой и обеспечением качества.

Приёмы, согласованные с методологией Shift Left

- Test-Driven Development (TDD): его ввело Extreme Programming (XP); TDD требует написать тест до кода, который этот тест должен проверять.
- Continuous Integration (CI): интеграции кода выполняют с перерывами, часто несколько раз в день, и это снижает риск осложнений при полномасштабных развёртываниях.
- Автоматическое развёртывание и тестирование: это также ключ к Continuous Deployment (CD); автоматические процессы ускоряют циклы выпуска и рано отмечают любые отклонения.

Shift Right как дополнение

Shift Right по сути отличается от левого аналога, но не обязательно ему противоречит. Он его дополняет: после того как приложение или возможность работает, по ним собирают данные. Эта информация затем направляет следующие итерации или решения.

**Examples:**

Пример кода: Shift Left с Test-Driven Development

Вот код на Java:

```java
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }

    public static void main(String[] args) {
        Calculator calc = new Calculator();
        System.out.println(calc.add(5, 10));  // Output: 15
    }
}
```

### How does version control support DevOps practices?

**Definition:**

Инструменты контроля версий, такие как Git, играют ключевую роль в DevOps: они дают слаженное сотрудничество разработчиков, тестировщиков и команд эксплуатации. Вот как контроль версий поддерживает DevOps.

**How it works:**

Ключевая польза

Контроль версий даёт командам несколько преимуществ:

- Сотрудничество: команды работают синхронно с центральным репозиторием кода и избегают дублирования и рассинхронизированных файлов.
- Отслеживание изменений: каждую правку документируют, что даёт тщательный аудит и откаты к устойчивому состоянию.
- Качество кода: процессы ревью кода гарантируют, что сливают только одобренные изменения, и кодовая база в целом становится лучше.
- Согласование задач: команды связывают изменения кода с конкретными задачами или проблемами, дают контекст и повышают прозрачность.
- Управление выпусками: инструменты интеграции согласуют изменения между разными командами и автоматизируют разные задачи выпуска.

Рабочие процессы DevOps

- Continuous Integration (CI): платформы контроля версий запускают автоматическое тестирование и сборку при изменениях кода и рано находят проблемы.
- Continuous Deployment (CD): одобренные изменения автоматически разворачивают в производство или промежуточные среды контролируемым образом, снижая человеческие ошибки.
- Стратегии ветвления: подобранные стратегии, такие как Git-Flow или Trunk-based Development, упрощают совместные рабочие процессы.
- Автоматические ревью кода: инструменты вроде линтеров и статических анализаторов повышают качество кода и следят за соблюдением лучших практик.
- Синхронизация сред: команды могут использовать infrastructure as code (IaC), чтобы среды разработки и производства шли в ногу с изменениями кода.

Распространённые заблуждения и лучшие практики

### What are the common metrics used to measure DevOps success?

**Definition:**

Успех DevOps можно измерять разными количественными и качественными показателями, которые показывают слаженное сотрудничество, гибкую разработку и устойчивые конвейеры поставки.

**How it works:**

Ключевые метрики

- Частота развёртываний: упор на более высокую частоту ради коротких циклов обратной связи и гибкости.
- Время выполнения изменений: меньшее время выполнения означает более быстрые циклы от кода до производства.
- Доля неудачных изменений: следить за неудачными изменениями после развёртывания, чтобы оценивать стабильность и надёжность.
- Mean Time to Recovery (MTTR): более низкий MTTR означает более быстрое разрешение инцидентов.
- Time to Restore Service (TTRS): время на восстановление после инцидента. Это особенно важно для Service Level Objectives (SLOs)/SLOs.
- Строгая автоматизация: отслеживать процент автоматизации в тестировании, continuous integration (CI) и infrastructure as code (IaC), чтобы повышать эффективность.
- Доля ускользнувших дефектов: измеряет действенность тестирования и процессов качества.
- Масштабируемость инфраструктуры: по мере роста бизнеса инфраструктура должна успевать за ним.
- Непрерывный мониторинг (или сопровождение): регулярно смотреть на ПО и проверять, что всё работает как должно.
- Динамическое масштабирование: как и масштабируемость инфраструктуры, ПО должно расти вместе с клиентской базой.
- Метрики успеха клиентов: смотреть на сбои приложения, обращения клиентов и другое, чтобы видеть, насколько приложение служит клиентам после развёртывания.

<summary>How does DevOps differ from the Agile methodology?</summary>

### How does DevOps differ from the Agile methodology?

**Definition:**

Методологии DevOps и Agile обе созданы, чтобы улучшать разработку ПО. При этом Agile в первую очередь смотрит на итеративную природу разработки, а DevOps идёт дальше процесса разработки и обеспечивает эффективную сборку, тестирование и развёртывание кода.

**How it works:**

Ключевые области внимания

- Agile делает упор на постоянные выпуски с постепенными улучшениями и включает тесные команды, сотрудничество с клиентом и адаптацию к изменениям.
- DevOps сосредоточен на автоматизации процессов сборки, тестирования и развёртывания, чтобы выпуски были частыми, надёжными и часто автоматическими. Он упрощает сотрудничество разработки, эксплуатации и других IT-команд.

Межотдельское сотрудничество

- Agile: в первую очередь координация внутри команды, особенно между разработкой и управлением продуктом.
- DevOps: идёт дальше координации внутри команды и усиливает упор на сотрудничество разных внутренних команд, таких как разработка, безопасность и IT-эксплуатация.

Автоматизация

- Agile: автоматизация полезна, но не является основным требованием. Главная цель — короткие итеративные циклы разработки, которым ручное вмешательство может быть не нужно.
- DevOps: автоматизация — сердце методологии. Она необходима для конвейеров continuous integration, delivery и deployment (CI/CD), чтобы отдельные изменения кода тщательно тестировали и бесшовно разворачивали в производство.

Непрерывность развёртывания

- Agile: регулярные небольшие выпуски возможностей поощряют, но решение о развёртывании остаётся за владельцем продукта.
- DevOps: команды разработки и эксплуатации работают в тесной связке и проводят несколько автоматических развёртываний каждый день.

Качество кода

- Agile: поощряет чистый код, но это не главный двигатель.
- DevOps: ставит устойчивое качество кода на первое место и проводит автоматические стандарты инструментами на всех фазах конвейера.

Интеграция ролей

- Agile: поддерживает разделение по ролям, таким как владелец продукта, Scrum-мастер и команда разработки.
- DevOps: в отличие от Agile, который задаёт конкретные роли, DevOps поощряет более цельный подход с кросс-функциональными командами, где каждый участник делит ответственность за конечный продукт.

**Definition:**

Stdout и агент на узле хватает большинству сервисов. Sidecar добавляйте, только если процесс пишет в файлы и не может писать в stdout. Прямая отправка из приложения — когда вы уже стандартизировали один telemetry SDK.

### Explain the use of a tool like Jenkins or GitLab CI in the CI/CD pipeline.

**Definition:**

Jenkins и GitLab CI превращают коммит в упорядоченный набор задач: сборка, тесты, затем выкат. Описание pipeline лежит в репозитории, поэтому шаги ревьюят как код.

**How it works:**

- Declarative Pipeline в Jenkins — это `Jenkinsfile`. `agent` выделяет executor и workspace и забирает репозиторий. `stages` идут по порядку (`Build`, `Test`, `Deploy`). При `skipStagesAfterUnstable` упавшая стадия останавливает следующие. `post` выполняет очистку независимо от результата.
- GitLab CI использует `.gitlab-ci.yml` в корне репозитория. Стадии идут последовательно; задачи одной стадии — параллельно. Каждую задачу выполняет runner. Pipeline создаётся на push, merge request, по расписанию или вручную.
- Оба инструмента могут собрать образ Docker и передать артефакт следующей стадии. Оркестратор они не заменяют, а вызывают.

**When to use:**

GitLab CI — когда репозиторий уже на GitLab и нужны runner, pipeline на merge request и environments в одном продукте. Jenkins — когда нужен свой automation server и плагины к инструментам, с которыми GitLab CI напрямую не говорит.

**Examples:**

```groovy
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'make'
            }
        }
        stage('Test') {
            steps {
                sh 'make check'
                junit 'reports/**/*.xml'
            }
        }
        stage('Deploy') {
            steps {
                sh 'make publish'
            }
        }
    }
}
```

```yaml
stages:
  - build
  - test
  - deploy

build_job:
  stage: build
  script:
    - make build

test_job:
  stage: test
  script:
    - make test
```

### Can you describe the CI/CD pipeline and its stages?

**Definition:**

```yaml
  script:
    - make test

deploy_prod:
  stage: deploy
  script:
    - make deploy
  environment: production
```

### How do you manage branching strategies for CI/CD?

**Definition:**

Стратегия ветвления решает, какие ref Git запускают pipeline и какой ref можно выкатывать. Короткие ветки в Git дёшевы: ветка — указатель, а слияние — three-way merge.

**How it works:**

- **Topic branches.** Короткая ветка на одно изменение. CI идёт по ветке или по merge request. После ревью и зелёного pipeline ветку вливают и удаляют.
- **Долгие ветки.** Стабильная ветка (`master` или `main`) хранит выпущенный код. Ветка `develop` или `next` собирает topic branches, прежде чем они перейдут в стабильную.
- Конфигурация pipeline смотрит на ветку. GitLab может запустить pipeline на push или merge request. Задачи выката в production ограничены стабильной веткой.

**When to use:**

Topic branches плюс защищённая стабильная ветка подходят большинству продуктовых команд. Долгая `develop` нужна, когда несколько функций надо собрать до релиза. Trunk-based development (короткие ветки, частое слияние в main) подходит, когда pipeline быстрый, а незавершённое прячут feature flags.

<summary>What is blue-green deployment?</summary>

### What is blue-green deployment?

**Definition:**

Blue-green держит две production-среды. Одна (blue) обслуживает трафик. Другая (green) получает новый релиз. После проверок маршрутизатор отправляет пользователей на green. Прежняя среда остаётся, чтобы быстро переключиться назад.

**How it works:**

1. Новую версию выкатывают в простаивающую среду. Артефакт того же вида, что у живой среды (например тот же образ контейнера с новым тегом).
2. Smoke-тесты идут в простаивающую среду, пока пользователи ходят в живую.
3. Балансировщик, селектор Service или DNS переключают на новую среду.
4. Старую среду держат, пока не ясно, что возвращаться не придётся.

Rolling update в Kubernetes — другой механизм: Deployment постепенно меняет Pod внутри пары ReplicaSet. Blue-green держит полную вторую копию и переключает трафик один раз.

**When to use:**

Blue-green — когда можно оплатить две полные среды и нужен мгновенный возврат. Rolling update — когда среда одна и Pod заменяются постепенно.

**Sources:**

- [Kubernetes — Rolling update](https://kubernetes.io/docs/tasks/run-application/update-deployment-rolling/)
- [AWS — Blue/green deployments on ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-bluegreen.html)

<summary>How does a canary release differ from blue-green deployment?</summary>

### How does a canary release differ from blue-green deployment?

**Definition:**

Canary отправляет небольшую долю настоящего трафика на новую версию и смотрит ошибки и задержку, прежде чем сдвинуть остальное. Blue-green переключает всех пользователей сразу после проверок простаивающей среды без пользовательского трафика.

**How it works:**

- Blue-green: 0%, затем 100%. Откат — вернуть маршрутизатор на старую среду.
- Canary: 1–5% (или выбранное подмножество), затем больше, затем 100%. Откат — вес новой версии снова ноль, пока старая ещё работает.
- В Kubernetes можно держать два Deployment и сдвинуть селектор Service или отдать разделение трафика mesh. Data plane Istio умеет направлять долю HTTP, gRPC, WebSocket и TCP по правилам маршрутизации.
- Rolling update Deployment заменяет Pod по readiness. Это постепенная замена, а не взвешенный canary по пользователям сам по себе.

**When to use:**

Canary — когда ошибка дорога и новую версию можно измерить на живом трафике. Blue-green — когда нужен один переключатель и полная простаивающая копия для проверки заранее.

**Sources:**

- [Istio — What is Istio?](https://istio.io/latest/docs/overview/what-is-istio/)

<summary>What challenges might you face in implementing CI/CD and how would you overcome them?</summary>

### What challenges might you face in implementing CI/CD and how would you overcome them?

**Definition:**

CI/CD ломается, когда pipeline медленный, нестабильный или результату не доверяют настолько, чтобы из него выкатывать. Лечение — меньший детерминированный pipeline, а не новые ручные ворота.

**How it works:**

- **Медленная обратная связь.** Разделите тесты на быструю и медленную стадии. Задачи одной стадии гоняйте параллельно — GitLab так и делает.
- **Нестабильные тесты.** Красная задача, которая иногда зелёная, учит людей перезапускать вслепую. Изолируйте такой тест, почините гонку и оставляйте падение pipeline только на настоящих регрессиях.

- **Страх выката.** Начните с continuous delivery (артефакт готов, человек продвигает) и переходите к continuous deployment, когда стадии тестов доверяют. Оставьте путь отката: предыдущий тег образа или прежнее состояние Terraform.

### How do you roll back a deployment in a CI/CD process?

**Definition:**

- **База.** Откатывайте только changeset, у которого есть rollback (в Liquibase это `rollback` у changeset). Не выдумывайте обратное разрушительной миграции данных.

### What is Terraform and how is it used in IaC?

**Definition:**

Terraform — инструмент infrastructure as code. Вы описываете вычисления, хранилища, DNS и другие ресурсы в файлах конфигурации. Terraform строит план разницы и применяет его, чтобы реальная инфраструктура совпала с конфигурацией.

**How it works:**

1. **Пишете** блоки resource. У ресурса есть тип и имя, например `aws_instance.app_server`.
2. **Initialize** (`terraform init`), чтобы Terraform скачал провайдеры и модули.
3. **Plan** показывает создания, обновления и удаления.
4. **Apply** выполняет эти действия. Второй apply с той же конфигурацией сообщает: «No changes. Your infrastructure matches the configuration.»
5. **State** помнит, что Terraform создал. Модули группируют ресурсы, чтобы корневой модуль вызывал дочерний (`module.website`).

**Examples:**

```hcl
resource "aws_instance" "app_server" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = var.instance_type

  tags = {
    Name = var.instance_name
  }
}
```

- [Terraform — Apply](https://developer.hashicorp.com/terraform/tutorials/cli/apply)

<summary>Can you describe the functionality of AWS CloudFormation?</summary>

### Can you describe the functionality of AWS CloudFormation?

**Definition:**

AWS CloudFormation описывает и создаёт ресурсы AWS из шаблона. Шаблон — JSON или YAML. Stack — набор ресурсов, который CloudFormation создаёт из этого шаблона.

**How it works:**

- У шаблона есть секция `Resources` (без неё стек бесполезен) и необязательные `Parameters`, `Mappings`, `Conditions` и `Outputs`. YAML опирается на отступы, JSON — на скобки. Оба описывают один и тот же стек.
- Стек создаётся из шаблона. CloudFormation вызывает API AWS и учитывает ресурсы как одну единицу.
- Чтобы изменить стек, правьте шаблон и создайте change set. Change set перечисляет, что будет добавлено, изменено или заменено. Его запуск обновляет только затронутые ресурсы. Если обновление падает, CloudFormation откатывает стек к последнему рабочему состоянию.
- Change set не доказывает, что обновление пройдёт. Он не проверяет квоты аккаунта и права IAM.

**Examples:**

```yaml
AWSTemplateFormatVersion: 2010-09-09
Resources:
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !Ref LatestAmiId
      InstanceType: !Ref InstanceType
```

<summary>Explain the differences between declarative and imperative approaches in IaC.</summary>

### Explain the differences between declarative and imperative approaches in IaC.

**Definition:**

Декларативный IaC называет желаемые ресурсы. Инструмент сам считает действия. Императивный IaC называет действия по порядку: создать это, затем настроить то.

**How it works:**

- **Декларативный.** Конфигурация Terraform и шаблон CloudFormation перечисляют ресурсы и свойства. `terraform plan` и change set CloudFormation показывают разницу с текущей инфраструктурой. Повторное применение того же файла ничего не делает, если не было дрейфа.
- **Императивный.** Shell-скрипт или процедурный инструмент выполняет команды: `aws ec2 run-instances`, затем вторая команда ставит тег. Второй запуск может создать второй инстанс, если скрипт сам не проверяет, что он уже есть.
- Манифесты Kubernetes тоже декларативны: `kubectl apply` задаёт желаемый Pod или Deployment, а control plane сходится к нему.

**When to use:**

Декларативные шаблоны — для всего, что надо воспроизвести или отревьюить (сети, кластеры, базы). Короткий императивный скрипт — для разовой миграции, которую декларативная модель не выражает; результат потом возвращают в шаблон.

<summary>What is a “stack” in the context of IaC, as seen in tools like Terraform?</summary>

### What is a “stack” in the context of IaC, as seen in tools like Terraform?

**Definition:**

Stack — одна развёрнутая копия шаблона: ресурсы, параметры и выходы, которые живут вместе и обновляются как единица. CloudFormation называет эту единицу stack. Ближайшее в Terraform — корневой модуль плюс его state; это чаще workspace или файл state, а не слово stack.

**How it works:**

- В CloudFormation вы отдаёте шаблон и получаете стек. Обновления идут через change set этого стека. Откат восстанавливает этот стек, а не соседний.
- В Terraform один каталог конфигурации (корневой модуль) и один файл state учитывают один набор ресурсов. Дочерние модули (`module.website.aws_s3_bucket.this`) — части этого набора, а не отдельные стеки, пока вы специально не разделите state.
- Команды часто держат один state на среду (dev, prod), чтобы изменение dev не строило план по ресурсам production.

**When to use:**

Делите стеки или файлы state по жизненному циклу и радиусу поражения: сеть в одном, приложение в другом. Ресурсы, которые надо создавать и уничтожать вместе, держите в одном стеке.

### How do you handle configuration drift?

**Definition:**

Дрейф конфигурации — реальный ресурс, который больше не совпадает с кодом, который должен его описывать. Кто-то поменял security group в консоли или процесс поправил тег, а шаблон не обновили.

**How it works:**

- Terraform сравнивает инфраструктуру с конфигурацией на plan и apply. В учебнике по дрейфу `terraform apply -refresh-only` сообщает об объектах, изменённых вне Terraform, и может записать эти изменения в state, не трогая облако. Это фиксирует дрейф, а не откатывает его.
- Чтобы убрать дрейф, верните нужное значение в конфигурацию и выполните `terraform apply`, либо примите правку из консоли в конфигурации и примените её, чтобы код и state совпали.
- Change set CloudFormation показывает разницу между присланным шаблоном и стеком. Обнаружьте дрейф стека, затем обновите шаблон и выполните change set, если должен победить шаблон.
- Дрейф предотвращают, ограничивая запись из консоли и выкатывая только из pipeline.

<summary>Describe idempotence in the context of IaC and its importance.</summary>

### Describe idempotence in the context of IaC and its importance.

**Definition:**

Идемпотентная операция оставляет систему в желаемом состоянии, запустите вы её один раз или снова. Второй `terraform apply` неизменённой конфигурации сообщает, что изменений нет, и не создаёт дубликаты ресурсов.

**How it works:**

- Terraform хранит идентификаторы в state. Следующий apply обновляет эти ресурсы или оставляет их; он не вызывает «создать» вслепую.
- CloudFormation обновляет стек на месте. Повторная отправка того же шаблона не создаёт вторую копию ресурсов стека.
- `kubectl apply` в Kubernetes сводит Deployment к манифесту. Повтор того же манифеста не добавляет второй объект с тем же именем.
- Shell-скрипт, который всегда вызывает `run-instances`, не идемпотентен. Поэтому декларативные инструменты важны для pipeline, которые повторяют шаг.

<summary>What is the significance of using modules in IaC tools?</summary>

### What is the significance of using modules in IaC tools?

**Definition:**

Модуль — переиспользуемая группа ресурсов со входами и выходами. Вызывающий передаёт переменные и не копирует блоки ресурсов.

**How it works:**

- В Terraform корневой модуль вызывает дочерний. В документации `module.website` создаёт S3 bucket с провайдером, заданным в корне. Модуль версионируют, и каждая среда указывает на ref.

### Explain the concept of “test-driven development (TDD)” within DevOps.

**Definition:**

TDD пишет падающий автотест на поведение, затем код, который этот тест проходит, затем подчищает дизайн. В DevOps эти тесты живут в стадии тестов CI, и та же проверка сторожит каждый следующий коммит.

**How it works:**

1. Добавьте тест, который описывает поведение и падает, потому что поведения ещё нет.
2. Меняйте приложение, пока тест не проходит локально.
3. Запушьте ветку. Стадия тестов pipeline гоняет этот тест вместе с остальным набором. Выкат не идёт, если тест упал.
4. Рефакторьте, пока стадия зелёная.

TDD — способ писать тесты, которые pipeline и так требует. Это не отдельная среда.

**When to use:**

TDD — для логики с ясными входами и выходами (цены, парсеры, обработчики API). Для спайка или эксперимента с UI тест можно написать после того, как поведение понятно, и затем закрепить его в той же стадии тестов.

<summary>What is Application Performance Monitoring (APM)?</summary>

### What is Application Performance Monitoring (APM)?

**Definition:**

Мониторинг производительности приложения — телеметрия работающего сервиса: сколько длятся запросы, как часто они падают и какой downstream-вызов был медленным. Ею смотрят эффект выката, а не только то, что процесс жив.

**How it works:**

- Prometheus снимает числовые временные ряды по HTTP (модель pull). Ряд — имя метрики плюс метки, сохранённые с временем образца. PromQL запрашивает эти ряды. Prometheus рассчитан оставаться доступным во время сбоя; он плохо подходит, если нужна полная запись каждого запроса для биллинга.
- OpenTelemetry порождает и экспортирует трейсы, метрики и логи. Это не backend. Трейс показывает один запрос через сервисы; метрики — агрегаты, которые хранят системы вроде Prometheus.
- Grafana (или другой потребитель API) рисует ряды, которые сохранил Prometheus. Alertmanager обрабатывает алерты, которые зажёг сервер Prometheus.

**When to use:**

Начните с метрик в духе RED на HTTP-сервисе (rate, errors, duration) через Prometheus. Трейсы OpenTelemetry добавляйте, когда одной метрики не хватает, чтобы увидеть, какой hop медленный.

**Definition:**

**Examples:**

<summary>How would you set up an alerting system for your applications?</summary>

### How would you set up an alerting system for your applications?

**Definition:**

Алерт зажигается, когда выражение PromQL остаётся истинным заданное время, затем Alertmanager группирует его и направляет получателю. Страница должна быть действенной: человек или runbook могут что-то сделать.

**How it works:**

1. Инструментируйте приложение или exporter, чтобы Prometheus мог его снимать. Метрика `up` равна 0, когда scrape не удался.
2. Укажите Prometheus на файл правил и на Alertmanager (`alerting.alertmanagers` в `prometheus.yml`).
3. Напишите правило с `expr`, `for` и annotations. `for: 5m` не будит из-за одного пропущенного scrape.
4. В Alertmanager маршрутизируйте по метке вроде `severity` и группируйте связанные алерты, чтобы один сбой был одним уведомлением.

**Examples:**

```yaml
groups:
  - name: example
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 5m
        labels:
          severity: page
        annotations:
          summary: "Instance {{ $labels.instance }} down"
```

### How do serverless architectures fit into DevOps?

**Definition:**

### What is Kubernetes and what problem does it solve?

**Definition:**

Kubernetes — переносимая расширяемая open-source платформа для управления контейнерными workload и сервисами. Она решает запуск многих контейнеров на многих машинах: планирование, перезапуск, выкат изменений и стабильное сетевое имя.

- Масштаб — это число реплик. `kubectl autoscale deployment/my-nginx --min=1 --max=3` создаёт HorizontalPodAutoscaler, если есть источник метрик.

<summary>How does a container differ from a virtual machine?</summary>

### How does a container differ from a virtual machine?

**Definition:**

Виртуальная машина — операционная система со своим ядром. Контейнер — изолированный процесс плюс нужные ему файлы, и он делит ядро хоста. Docker использует контейнеры, чтобы один образ шёл на ноутбуке, в CI и в облаке без установки зависимостей приложения на хост.

**How it works:**

- ВМ включает драйверы, программы и приложения. Поднимать ВМ только чтобы изолировать один процесс — большой overhead.
- Контейнеры самодостаточны, изолированы друг от друга, удаляются независимо и переносимы. Несколько контейнеров на одной машине делят одно ядро, поэтому на меньшей инфраструктуре работает больше процессов.
- Облачные ВМ часто несут container runtime. Одна ВМ тогда запускает много контейнеров вместо одного приложения на машину.
- Kubernetes планирует контейнеры внутри Pod на этих узлах. Pod — объект Kubernetes; контейнер по-прежнему процесс.

**When to use:**

Контейнеры — чтобы упаковать приложение. ВМ — когда нужно отдельное ядро, другая ОС или жёсткая граница изоляции, которую требует модель угроз. На практике ВМ — узел, а контейнеры — workload на нём.

### What is the purpose of a Kubernetes pod?

**Definition:**

Pod — наименьшая единица, которую вы создаёте и которой управляете в Kubernetes. Это один или несколько контейнеров, которые делят хранилище и сеть и планируются вместе.

**How it works:**

- Обычный случай — один контейнер на Pod. Kubernetes управляет Pod, а не отдельными контейнерами. Deployment создаёт эти Pod из шаблона, когда нужны реплики.
- Pod из нескольких контейнеров — для тесно связанных помощников, которым нужны сетевой namespace и тома Pod (в документации по логам пример — sidecar для логов). Не кладите несвязанные приложения в один Pod, чтобы получить больше копий; поднимите число реплик.
- Pod также может запускать init-контейнеры на старте. Ephemeral-контейнеры можно внедрить, чтобы отладить работающий Pod.
- На каждом узле нужен container runtime, чтобы там могли идти Pod.
- Pod смертны. Service и контроллер (Deployment) дают стабильное имя и замену, когда Pod умирает.

**Examples:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.14.2
```

### Explain the role of service discovery in container orchestration.

**Definition:**

Service discovery позволяет клиенту найти workload после того, как Pod перепланировали и их IP сменились. В Kubernetes стабильное имя — это Service, и его публикует DNS.

**How it works:**

- Service выбирает Pod селектором меток и имеет cluster IP и порт. IP остаётся у Service, пока IP Pod приходят и уходят.
- С кластерным DNS (CoreDNS) Service с именем `my-service` в namespace `my-ns` — это `my-service` внутри этого namespace и `my-service.my-ns` снаружи. Эти имена резолвятся в cluster IP.
- Именованные порты получают SRV-записи. Порт с именем `http` и протоколом TCP можно найти запросом `_http._tcp.my-service.my-ns`.
- Service типа `ExternalName` резолвятся только через этот DNS.
- Docker Swarm даёт service имя в сети swarm; task за `--replicas` делят этот service. Клиенты используют имя service, а не IP task.

<summary>How can you scale containers using Docker Swarm or Kubernetes?</summary>

### How can you scale containers using Docker Swarm or Kubernetes?

**Definition:**

Масштабирование задаёт, сколько копий контейнера должно работать. Swarm называет их репликами service. Kubernetes задаёт реплики на Deployment, либо HorizontalPodAutoscaler меняет это число по метрикам.

**How it works:**

- **Swarm.** `docker service create --name my_web --replicas 3 nginx` просит три task. Manager раскладывает их по узлам. `docker service scale my_web=5` меняет желаемое число. Task остаётся на узле, которому его назначили. Global service запускает один task на каждом узле вместо фиксированного числа.
- **Kubernetes.** Задайте `spec.replicas` у Deployment. `kubectl autoscale deployment/my-nginx --min=1 --max=3` создаёт HPA. Автомасштабу нужен источник метрик; команда метрики не выдумывает.
- Сначала масштабируйте реплики без состояния. База не становится безопасной от того, что вы подняли число реплик; ей нужна своя схема репликации.

**Examples:**

```console
docker service create --name my_web --replicas 3 nginx
docker service scale my_web=5
```

```shell
kubectl autoscale deployment/my-nginx --min=1 --max=3
```

**When to use:**

Парьтесь на инцидентах в production, на незнакомом коде pipeline и на изменениях, чувствительных к безопасности. Одиночная работа плюс ревью pull request достаточна для понятной правки.

### What is meant by “systems thinking” in the context of DevOps?

**Definition:**

Системное мышление смотрит на путь от коммита до работающего сервиса, включая передачи, очереди и обратную связь, а не оптимизирует локальный шаг одной команды. Более быстрая сборка не помогает, если выкаты неделю ждут ручного окна.

**How it works:**

- Проведите одно изменение через Git, стадии pipeline, выкат и сигнал production (ряды Prometheus, логи). Ограничение — самый медленный или самый рискованный шаг на этом пути.
- Улучшайте ограничение: параллельные задачи стадии, меньший тест или откат, которому не нужно совещание.
- Смотрите систему при отказе. Prometheus устроен так, чтобы его можно было запросить во время сбоя: каждый сервер хранит данные локально.
- Локальные победы, которые сдвигают боль дальше (пропуск тестов, правки в консоли, которые дрейфуют от Terraform), улучшениями не являются. Дрейф и красная стадия тестов — сигналы системы.

<summary>How can DevOps practices reduce technical debt?</summary>

### How can DevOps practices reduce technical debt?

**Definition:**

Технический долг — короткий путь, который делает следующее изменение дороже. DevOps уменьшает его, делая shortcut видимым в системе контроля версий и в pipeline, и выплачивая его маленькими слияниями, а не проектом переписывания.

**How it works:**

- **Уникальные серверы.** Правки в консоли дрейфуют от Terraform или CloudFormation. Обнаружение дрейфа и повторное применение конфигурации убирает разовые серверы.
- **Непроверенные пути.** Недостающий тест становится задачей стадии тестов. Следующее изменение не может тихо вернуть баг.
- **Большие партии.** Topic branches, которые сливают часто, держат diff маленьким, и уборка едет вместе с функцией.
- **Образы и манифесты.** Сборка из Dockerfile и Deployment лучше, чем ручной патч долго живущей ВМ.
- Долг, который выбрали сознательно, остаётся в бэклоге с триггером («когда в следующий раз тронем биллинг»). Pipeline не отменяет продуктовое решение.

### What are microservices and how do they influence DevOps?

**Definition:**

Микросервисы делят приложение на отдельно выкатываемые процессы, у каждого свой pipeline и релиз. Для DevOps это много pipeline, много дашбордов и сеть между сервисами вместо одного вызова функции.

- Больше сервисов — больше поверхность дежурства. Начинайте с границы, у которой свои данные и своя причина выкатываться.

### Can you outline the benefits and challenges of a microservices architecture?

**Definition:**

**How it works:**

Что платформа реально даёт:

- Независимый выкат: rolling update одного Deployment не пересобирает каждый другой сервис.
- Масштаб по потребности: `kubectl autoscale` или число реплик Swarm применяется к загруженному сервису.
- Изолированные зависимости: каждый образ несёт свой runtime — это модель упаковки Docker.

Что надо запланировать:

- Нужны IP Service и имя DNS, потому что IP Pod меняются.
- Частичный отказ: у вызывающего нужны таймауты, а у mesh или клиента — видимая доля ошибок. Istio умеет добавить retry и fault injection; это явные правила, а не умолчание, которое прячет баги.
- Данные больше не одна транзакция. Изменение схемы — changelog Liquibase базы этого сервиса, согласованный с выкатом приложения.
- Много pipeline. GitLab или Jenkins должны оставаться зелёными по каждому сервису, иначе независимый релиз теряется.

**When to use:**

Выделяйте сервис, когда команде нужно выкатывать его в другом ритме. Держите одну единицу выката, пока одна команда выпускает один продукт.

<summary>How does feature flagging work and why is it useful in DevOps?</summary>

### How does feature flagging work and why is it useful in DevOps?

**Definition:**

Feature flag — проверка во время выполнения, которая включает или выключает путь кода без нового выката. Она отделяет «коммит в main» от «пользователи видят поведение», и поэтому можно сливать маленькими кусками и выпускать, когда готово.

**How it works:**

- Приложение спрашивает провайдера флага о булевом значении или варианте, с ключом пользователя, арендатора или среды. Путь по умолчанию остаётся старым поведением.
- Pipeline выкатывает образ с выключенным флагом. Когда Deployment здоров, флаг включают для подмножества (canary пользователей) и смотрят ряды Prometheus этого пути.
- Выключение флага — откат, когда новый путь ведёт себя плохо и новый rolling update не нужен.
- Определения флагов храните вне образа. Флаг, оставленный включённым навсегда, — недоделанная уборка; удалите ветку в коде, когда флаг полностью включён.
- OpenFeature задаёт API оценки флага, не привязанный к вендору, чтобы приложение не было зашито на одного поставщика флагов.

**When to use:**

Флаг — для изменения поведения, которое может понадобиться быстро спрятать, или для коммита в trunk, который ещё не готов всем пользователям. Флаг не заменяет миграцию схемы, которую нельзя переключить.

### What is a service mesh and how does it fit into a DevOps environment?

**Definition:**

Service mesh — отдельный слой для трафика между сервисами: маршрутизация, mutual TLS и телеметрия без переписывания каждого сервиса. Istio — такой слой. Он ложится на уже существующее распределённое приложение.

**How it works:**

- Control plane (`istiod`) настраивает data plane. В режиме sidecar прокси Envoy рядом с каждым workload обрабатывает его трафик. В режиме ambient это делает прокси ztunnel на уровне узла.
- Istio может требовать mutual TLS между сервисами (`ISTIO_MUTUAL` на DestinationRule), делить трафик для canary и отдавать метрики, логи и трейсы трафика mesh.
- Deployment приложения остаётся источником образа. Mesh не собирает и не выкатывает этот образ; это делают pipeline CI и Kubernetes. Argo CD или pipeline синхронизирует манифесты; политики Istio — тоже манифесты.
- Mesh добавляют, когда сервисов уже много и нужны единообразные mTLS или взвешенная маршрутизация. Это дополнительные прокси и конфиг, которые надо эксплуатировать.

**When to use:**

Mesh — для безопасности между сервисами и политики трафика, которую не хотите кодировать в каждом клиенте. Пропустите его, если сервисов немного и они зовут друг друга обычными Service Kubernetes.

### Describe the concept of immutable infrastructure.

**Definition:**

Неизменяемая инфраструктура заменяет работающий экземпляр, а не меняет его на месте. Вы отправляете новый образ или новую ревизию шаблона. Вы не заходите по SSH и не ставите пакеты на долго живущую машину.

**How it works:**

- Образ Docker собирается из Dockerfile и опознаётся по содержимому. Pipeline выкатывает новый digest. Старый контейнер останавливают; его не обновляют пакетным менеджером внутри работающего процесса.
- В Kubernetes rolling update Deployment создаёт новые Pod из обновлённого шаблона и завершает старые.
- Для облачных ресурсов вы меняете конфигурацию Terraform или шаблон CloudFormation и применяете. Замена ресурса — запланированное действие в plan или change set, а не ручная правка, которая становится дрейфом.
- Логи и state живут вне экземпляра (backend логов, удалённый объект state Terraform), потому что экземпляр одноразовый.
- Откат — выкат предыдущего digest или шаблона, а не разворот истории shell на машине.

**When to use:**

Неизменяемые релизы — для узлов приложений и контейнеров. Базы и другие системы записи по-прежнему нуждаются в осторожных изменениях схемы на месте (changelog Liquibase), потому что том с данными нельзя выбросить пустым.

### How do you apply DevOps practices to database management?

**Definition:**

DevOps для базы значит, что изменения схемы ревьюят, версионируют и применяет тот же pipeline, что и приложение, а не разовая SQL-сессия на production.

**How it works:**

- Храните changelog в Git. Liquibase учитывает changeset и применяет только те, что ещё не выполнялись. `liquibase update --changelog-file=changelog.sql` выкатывает ожидающие changeset.
- Pipeline выполняет эту команду на тестовой базе в стадии тестов, затем на production в стадии выката, с учётными данными из Vault или переменных CI.
- Образ приложения и changelog, которого он ждёт, едут вместе. Rolling update Deployment сам данные не мигрирует.
- Разрушительные изменения люди всё равно ревьюят. `diff` и `diff-changelog` могут показать дрейф между базами, но сам Liquibase пишет, что diff плохо подходит для больших данных и для тестовых строк, которые нельзя копировать в production.

<summary>What are the considerations for database version control?</summary>

### What are the considerations for database version control?

**Definition:**

В систему контроля версий кладут изменение, а не дамп всей базы. Liquibase делает это changelog из changeset. У каждого changeset есть автор и id, и когда он выполнился, это записано, чтобы не применить его дважды.

**How it works:**

- Один файл changelog (SQL, XML, YAML или JSON) лежит рядом с сервисом, который владеет схемой. Его ревьюят в merge request как код приложения.
- Changeset упорядочены. Liquibase хранит, какие уже выполнялись. Правка changeset, который уже шёл в production, историю не переписывает: Liquibase сравнит контрольную сумму и выдаст ошибку. Добавляйте новый changeset.
- Включайте `--rollback`, когда изменение можно обратить (`drop table` для create). Исправления данных и разрушительные drop часто нельзя безопасно откатить; скажите это в ревью.
- Не коммитьте пароли и данные production. Параметры соединения приходят из переменных CI.
- `generate-changelog` может снять снимок существующей базы, когда вы принимаете инструмент. После этого новые изменения — написанные changeset, а не повторные дампы. Вывод diff может пропустить различия, которые всё равно корректны, например строки, вставленные в другом порядке.

**Examples:**

```sql
--liquibase formatted sql

--changeset app:person_table
create table person (
  id int primary key,
  name varchar(50) not null
);
--rollback drop table person;
```

### Can you discuss the tools and strategies for database CI/CD?

**Definition:**

Pipeline базы применяет отревьюенный changelog к одноразовой базе в CI, затем тот же changelog — к production при релизе. Команда `update` в Liquibase — шаг применения.

**How it works:**

- **Pull request.** Выполните `liquibase update` на пустой или уже мигрированной тестовой базе, чтобы плохой changeset уронил стадию тестов. В GitLab эта задача идёт до выката.
- **Артефакт.** Changelog едет с коммитом, в котором код приложения ждёт новую схему. Expand-contract, когда нельзя менять оба сразу: добавьте nullable-колонку, выкатите приложение, заполните данные, затем в позднем changeset ужесточите ограничение.
- **Production.** Задача выката использует узкие учётные данные базы. Общая административная оболочка не используется.
- **Дрейф.** `diff` сравнивает две базы. Им находят изменение в обход инструмента и превращают его в changeset. Не давайте diff копировать тестовые данные в production: Liquibase пишет, что diff данных для этого плохо подходит.

**Examples:**

```bash
liquibase update --changelog-file=changelog.sql
```

### How does database schema change management fit into DevOps?

**Definition:**

Управление изменениями схемы — упорядоченный отревьюенный набор changeset, который переводит базу с одной ревизии на следующую. Он стоит в стадии выката рядом с образом приложения, потому что код и схема должны совпасть.

**How it works:**

- Changeset — одна единица: создать таблицу, добавить колонку или поправить данные, с id и автором. Liquibase применяет ожидающие по порядку и записывает их.
- Обратно совместимые изменения выходят первыми (новая колонка, новая таблица). Затем выкат приложения. Drop или переименование ждут, пока ни одна работающая версия не читает старую форму. Так rolling update не связывают с разрушительной миграцией: старые Pod ещё работают во время выката.
- Упавшее обновление останавливает pipeline. Файл не «дощёлкивают» наполовину.
- Неизменяемые серверы приложения не означают неизменяемую базу. Схему мигрируют; том с данными не заменяют пустым.

- [Liquibase — SQL format](https://docs.liquibase.com/secure/user-guide-5-1/sql-changelog-example)
- [Kubernetes — Rolling update](https://kubernetes.io/docs/tasks/run-application/update-deployment-rolling/)

<summary>What is the significance of database release automation?</summary>

### What is the significance of database release automation?

**Definition:**

Автоматизация выпуска базы применяет changelog вместе с релизом приложения, чтобы production не оказался другим набором SQL, чем тот, который уже прошёл CI. `update` в Liquibase повторяем: changeset, которые уже выполнялись, пропускаются.

**How it works:**

- Задача выката выполняет `liquibase update` с changelog этого коммита, затем выкатывает приложение на образ этого коммита.
- Автоматизация убирает пропущенные ручные шаги и делает релиз идемпотентным, если задачу повторяют.
- Откат явный. Changeset может нести `--rollback`. `rollback-one-changeset` откатывает один changeset, когда переданы автор, id и путь; это не волшебная отмена любого изменения данных.
- Смысл для DevOps тот же, что у Terraform: желаемое изменение в Git, инструмент сводит цель, и второй запуск не изобретает вторую копию изменения.

**Examples:**

```bash
liquibase update --changelog-file=changelog.sql
```

- [Liquibase — rollback-one-changeset](https://docs.liquibase.com/secure/reference-guide-5-1/init-update-and-rollback-commands/rollback-one-changeset)
