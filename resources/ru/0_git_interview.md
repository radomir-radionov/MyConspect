### What is Git and why is it used?

**Definition:**

Git — децентрализованная система контроля версий (DVCS), которой разработчики в первую очередь пользуются, чтобы вести исходный код в самых разных проектах. Она повышает качество кода, облегчает совместную работу и даёт надёжный механизм резервного копирования.

**How it works:**

Commit. Коммит — сохранённое состояние проекта. Это снимок всех файлов проекта в данный момент времени. У каждого коммита есть сообщение.

Branch. Ветка — независимая линия разработки. Она позволяет работать над функцией или исправлением, изолировать это от остальной кодовой базы, пока работа не готова, а затем влить обратно.

Master — ветка по умолчанию, которая есть во всех репозиториях Git. Можно создать много других веток.

Merge. Слияние в Git означает, что независимые разработки двух веток объединяют в одну ветку.

После слияния две ветки, из которых шло слияние, совпадают со слитой веткой.

Remote и Origin. Remote — общий репозиторий на сервере или в доступной памяти, через который все участники команды обмениваются изменениями.

Origin — источник объектов коммитов (хранилище всех закоммиченных версий).

Командная строка и визуальные инструменты. Для повседневных задач и CLI, и GUI сильны, но важно понимать внутреннюю механику Git, чтобы разбирать неполадки и вести сложные задачи.

**Pluses and minuses:**

- История и путешествие во времени: Git хранит каждую версию проекта, поэтому можно откатить изменения или посмотреть код в любой точке.
- Безопасность и целостность: у каждого файла в Git свой хеш SHA-1, поэтому несанкционированные изменения легко заметить.
- Совместная работа: Git позволяет нескольким разработчикам работать над проектом одновременно без конфликта.
- Ревью кода: Git упрощает просмотр кода до того, как он попадёт в основную кодовую базу.

**Thoughts:**

- Делайте коммиты часто.
- Пишите ясные и короткие сообщения коммитов.
- Часто отправляйте код в удалённый репозиторий, особенно перед перерывом или в конце задачи.

### How does Git differ from other version control systems (VCS)?

**Definition:**

Git даёт множество преимуществ перед традиционными системами контроля версий (VCS): распределённую и эффективную модель версионирования.

**How it works:**

- Распределённая модель: децентрализованная природа Git наделяет каждый набор файлов полной историей репозитория и позволяет полноценно работать без сети. Это отличается от централизованных систем, которым нужно постоянное сетевое соединение и один центральный сервер со всеми данными проекта.
- Быстрые операции: Git известен быстрыми и эффективными операциями. В отличие от старых VCS, которые часто работали медленно или требовали существенного общения с сервером, Git использует локальные операции и за счёт этого впечатляюще быстр.
- Целостность данных: Git обеспечивает криптографическую целостность каждого фрагмента данных и защищает от порчи файлов, потери и несанкционированных правок. Отсутствие этой возможности в некоторых традиционных VCS создаёт риск для целостности данных.
- Упрощённое ветвление: сегменты или ветки в старых VCS часто использовали для параллельной разработки, а ветки Git легковесные и рассчитаны на частое и быстрое использование.
- Настраиваемые рабочие процессы: Git допускает разные процессы благодаря распределённой природе и возможности менять историю коммитов до того, как изменения увидят другие.
- Область подготовки (index): перед коммитом разработчики пользуются «staging area», чтобы выборочно включить в коммит конкретные изменения, а не каждый изменённый файл.
- Мощный набор основных команд: устойчивый набор незаменимых команд Git покрывает широкий круг возможностей контроля версий — от просмотра истории ревизий до совместного ведения кода функций.
- Снимки против отслеживания файлов: снимки Git записывают текущее состояние всего репозитория, тогда как некоторые традиционные VCS, такие как CVS и Subversion, в основном отслеживают изменения файлов.
- Атомарные коммиты: каждое изменение отдельно и исключительно от других, что даёт точный контроль над синхронизацией данных.
- Готовность к современному ландшафту: Git мелодично встраивается в современные подходы разработки вроде Continuous Integration/Continuous Deployment (CI/CD).
- Кроссплатформенность: на Windows, macOS и Linux Git работает одинаково.

**Pluses and minuses:**

- Риск единой точки отказа: если центральный сервер скомпрометирован, под угрозой данные всего проекта.
- Ограничения нумерации версий: пользователя может ограничивать монотонно растущий номер версии, и детализация страдает.
- Долгосрочные риски целостности: без криптографической проверки файлы можно изменить незаметно.
- Осложнения при потере данных: если центральный сервер или репозиторий скомпрометирован или повреждён, потеря данных тяжёлая.
- Ограниченная работа офлайн: пользователям мешает необходимость устойчивого сетевого соединения.
- Устаревшие ветки: в централизованных репозиториях бывают устаревшие ветки, и это мешает совместной работе.

**Thoughts:**

- Простота и гибкость: в отличие от некоторых традиционных VCS, Git задуман и как удобный для пользователя, и как способный на сложные задачи.
- Эффективность и производительность: быстрые и упрощённые процессы Git ведут к оптимальной эффективности.

### What is the difference between Git and GitHub?

**Definition:**

Git и GitHub часто путают из-за похожих имён. При этом они служат разным целям: контроль версий и хостинг разработки.

Git — распределённая система контроля версий, которая ведёт код и отслеживает его изменения. Это в основном локальное решение: разработчики координируются напрямую.

GitHub, со своей стороны, — веб-платформа, которая даёт хостинг репозиториям Git. Она предлагает возможности за пределами ядра Git.

**How it works:**

- Локальное ведение: разработчики могут работать со своими репозиториями без центрального сервера.
- Скорость: операции вроде коммита, ветвления и слияния быстрые и удобны для локальной разработки.
- Область подготовки: изменения сначала попадают в staging, и только потом в коммит, так контроль точнее.
- Отслеживание содержимого: Git ориентирован на содержимое, а не на файлы, и отслеживание получается эффективным.
- Удалённые репозитории: можно синхронизировать локальные репозитории с удалёнными и так работать вместе.
- Хостинг кода: разработчики могут хранить код и управлять им откуда угодно, не только со своей машины.
- Инструменты совместной работы: GitHub даёт средства для ведения проекта, учёта задач и работы команды.
- Ревью кода: несколько человек могут смотреть предлагаемые изменения и обсуждать их до слияния в основную кодовую базу.
- Контроль доступа: у разных пользователей могут быть разные уровни доступа к репозиторию или организации.

### What is a repository in Git?

**Definition:**

Репозиторий Git — место, где хранятся все файлы под контролем версий и их история. Это ядро совместных процессов и контроля версий.

У каждого репозитория Git две основные части: рабочее дерево и скрытый каталог `.git`, где Git держит все метаданные репозитория.

**How it works:**

- Распределённость: у каждого участника проекта своя копия репозитория, включая полную историю и возможность отслеживать версии. Это даёт работу офлайн и служит резервной копией проекта.
- Эффективное хранение: Git оптимизирует хранение такими приёмами, как хеширование файлов и дельта-сжатие, с упором на минимальную избыточность и устранение избыточности данных.
- Целостность содержимого: все файлы в репозитории Git, как и их версии, получают контрольную сумму и проверяются при каждой операции Git ради целостности данных.
- Учёт работы: Git позволяет отслеживать изменения проекта во времени и помогает человеку или команде понять, как проект развивался, кто внёс конкретные изменения и зачем.

Каталог `.git` — центр управления репозиторием Git: в нём всё, что нужно Git, чтобы вести репозиторий и его историю. Туда входит:

- База объектов, где лежат все данные о коммитах, деревьях и blob.
- Каталог ссылок, который хранит указатели на конкретные коммиты (например, ветки и теги).
- Файлы конфигурации с настройками и атрибутами репозитория.

Рабочее дерево — каталог, куда извлечены отслеживаемые файлы для просмотра и правки. Изменения файлов в рабочем дереве можно подготовить и закоммитить в репозиторий, чтобы зафиксировать их.

Неотслеживаемые файлы, то есть файлы, которые ещё не готовили и не коммитили, соседствуют с рабочим деревом и лежат вне управления Git.

### Explain the concept of a commit in Git.

**Definition:**

В Git коммит — снимок проекта в конкретный момент времени. Каждый коммит записывает сделанные изменения, автора и уникальный идентификатор. Коммиты организованы в ориентированный ациклический граф (DAG), и это совпадает с моделью ветвления.

**How it works:**

- Tree: состояние файловой системы проекта на момент коммита. Объект tree — запись расположения и содержимого каждого файла в репозитории.
- Родительский коммит (или несколько): указывает коммит или коммиты, от которых произошёл текущий. У начального коммита родителя нет.
- Метаданные: подробности вроде автора коммита, даты и сообщения, которое суммирует изменения.

В обычном репозитории Git есть рабочий каталог, область подготовки и история коммитов. Каждая часть отслеживает состояние проекта на своём этапе.

- Рабочий каталог: текущий живой набор файлов и каталогов. Это та версия проекта, с которой вы работаете и которую меняете.
- Область подготовки (её ещё называют «index»): буферная зона. Файлы здесь помечены для включения в следующий коммит. Вы решаете, какое содержимое переходит из рабочего каталога в область подготовки.
- История коммитов (в каталоге Git): линия времени коммитов в виде версионированного архива. Там же лежит полное содержимое проекта в соответствующих точках коммитов.

Обычный git-flow идёт по жизненному циклу, в который входят три дерева выше.

- Создание коммитов: вы начинаете с изменений в рабочем каталоге. Когда готовы их записать, добавляете конкретные файлы из рабочего каталога в область подготовки. Когда нужные изменения в области подготовки, следующая команда захватывает её содержимое и создаёт новый коммит в истории.
- Просмотр истории: история коммитов Git упорядочена по времени, обычно от самого свежего коммита назад. Каждый коммит влияет на то, как проект выглядит в данный момент времени.

Историю коммитов можно смотреть командами вроде `git log`. Эта команда даёт структурированный список коммитов: автор, дата коммита и связанное сообщение.

**When to use:**

- Возврат кода: проект можно сбросить к более раннему коммиту и тем самым обратить изменения.
- Совместная работа: коммиты помогают команде понимать, какие изменения сделаны и когда.
- Ревью кода: до включения изменений в основную ветку коммиты дают команде структурированный способ смотреть код друг друга. Так новый код соответствует стандартам репозитория.

**Examples:**

Пример кода: создание коммита и просмотр.

Вот команда консоли Git, чтобы создать «Meaingful Commit» с сообщением, а затем посмотреть коммит.

```bash
# To make a commit with a message
git commit -m "Meaningful Commit"

# To view the commit history
git log
```

### What is the difference between a working directory, staging area, and repository in Git?

**Definition:**

Git отличает трёхъярусная архитектура из таких слоёв:

- Рабочий каталог
- Область подготовки
- Репозиторий

У каждого слоя своя роль в архитектуре Git.

**How it works:**

Рабочий каталог — ваша площадка. Это место для экспериментов: здесь правят файлы, сливают разные версии и даже создают новые.

Область подготовки (её ещё называют Index) — своего рода середина. Здесь можно точно настроить, какие изменения войдут в следующий коммит. Здесь два типа файлов:

- MDS: файлы, изменённые с прошлого коммита
- SML: файлы, которые изменили и подготовили к следующему коммиту

Когда изменения в области подготовки вас устраивают, вы их «stage». Staging в этом смысле — пометка тех частей проекта, которые нужно сохранить в следующем коммите. Заметьте, что этот шаг полностью необязателен.

Репозиторий — последний ярус, он занят сохранением работы. Думайте о нём как о локальном репозитории, сейфе для всех коммитов. Он помнит все изменения и коммиты, так что их можно достать и после крупных обновлений.

Репозиторий также разложен на три явных «дерева» — рабочий каталог, область подготовки и последнее, HEAD. HEAD указывает на самый свежий коммит. Эти три дерева поначалу могут путать. На деле они понятны: это текущее состояние проекта, изменения, которые вы собираетесь закоммитить, и коммиты, которые вы подтвердили сохранить на будущее.

### Define branching in Git and its importance.

**Definition:**

Ветвление в Git позволяет независимо разрабатывать отдельные функции или участки кодовой базы. Это важная стратегия контроля версий, особенно в совместных проектах.

**How it works:**

- Master/Trunk/Branch: основная ветка, которая служит источником проекта.
- Ветки функций: дополнительные ветки под конкретные функции или задачи, часто ответвлённые от Master.
- Слияние: процесс переноса изменений из одной ветки в другую. Например, вливание готовых веток функций в Master.
- Разрешение конфликтов: разрешение пересекающихся изменений кодовой базы в разных ветках.

**Pluses and minuses:**

1. Изоляция кода: каждая ветка функции — изолированная среда для одной функции. Это не мешает основной кодовой базе.
2. Совместная разработка: несколько разработчиков могут работать с одной кодовой базой одновременно, и конфликтов меньше.
3. Снижение риска: изменения держат отдельно, пока их тщательно не проверят. Если экспериментальная функция работает не так или приносит ошибки, более стабильная ветка Master не пострадает.
4. Область подготовки: отдельное место для интеграции и проверки, прежде чем код развернут или влит в ветку Master.
5. Переключатели функций: упрощает выборочный вывод новых функций на проверку.
6. Ревью кода: помогает проверять качество кода до слияния, и ветка Master остаётся стабильной.
7. Ведение задач: стыкуется с инструментами и методиками управления проектом и даёт способ оформлять задачи так, чтобы они были под контролем версий.
8. Управление релизами: помогает изолировать и проверять изменения, намеченные к конкретным релизам.

<summary>What is a HEAD in Git?</summary>

### What is a HEAD in Git?

**Definition:**

В Git понятия рабочего каталога, области подготовки (или index) и репозитория (или истории коммитов) все ведёт `HEAD`.

**How it works:**

- Точка отсчёта: `HEAD` определяет текущий снимок или коммит в дереве истории. Любые действия в рабочем каталоге или области подготовки опираются на этот коммит.
- Связка уровней: он связывает самый свежий коммит ветки и с областью подготовки, и с рабочим каталогом. Каждый коммит — ровно то, на что указывает `HEAD`.

**Examples:**

Пример кода: работа с `HEAD`.

Вот наглядное представление того, как работает Git.

Вот код на `python`:

```bash
# Check out the "first-branch" branch
git checkout first-branch

# Make some modifications and stage them
git add modified-file-1.txt

# Commit the staged changes
git commit -m "Modified file 1 in first branch"

# Verify the new `HEAD` after the commit
git log --oneline --decorate
```

Команда `git log` в коде выше включает параметр `--decorate` и показывает самый свежий коммит и связанные с ним ссылки.

<summary>What does the clone operation in Git do?</summary>

### What does the clone operation in Git do?

**Definition:**

Клонирование в Git создаёт локальную копию репозитория и тем самым даёт контроль версий и совместную работу. Оно устанавливает связь с указанным remote и разрешает операции fetch и push.

**How it works:**

- Процесс из двух частей: клонирование включает копирование репозитория и настройку локального окружения.
- Полная история версий: клонированный репозиторий обычно включает все коммиты и версии файлов.
- Связь с remote: с назначенным remote строится отношение для синхронизации данных.
- Локальный репозиторий: хранилище на машине пользователя, где лежат все данные проекта и версий.
- Удалённый репозиторий: внешнее общее хранилище, часто на сервере, доступное для совместной работы.
- Рабочий каталог: место в файловой системе пользователя, где правят файлы и отслеживают изменения для коммитов.
- Копирование: процесс clone воспроизводит весь проект, со всеми ветками и коммитами, на машине пользователя. Получается полная самостоятельная история.
- Настройка: локальное окружение настраивают так, чтобы оно синхронизировалось с конкретным удалённым репозиторием. По умолчанию репозиторий, из которого сделан clone (origin), становится основным remote, но при необходимости можно добавить другие remote.
- Целостность: Git обеспечивает целостность скопированных данных, таких как коммиты и снимки файлов, во время клонирования.
- Ограничения выборочной истории: обычно clone получает всю историю репозитория, но ограниченное клонирование тоже возможно, особенно на больших репозиториях. Техника вроде shallow cloning или указание определённого коммита для клонирования тоже применяется.

После успешного clone локальный репозиторий настроен на взаимодействие с назначенным удалённым репозиторием, обычно на централизованном сервере вроде Github или Bitbucket.

Для GitHub клонирование часто идёт в режиме HTTPS. Когда удалённая сторона обновляется, локальный репозиторий можно синхронизировать обычными командами Git (например, fetch, pull, push).

Технически клональность не привязана к конкретному URL remote: важнее согласовать истории. Например, после клонирования с GitHub по HTTPS remote можно перенастроить на SSH.

1. Получение данных: команда clone связывается с удалённым репозиторием, забирает его историю и файлы и сохраняет этот снимок локально.
2. Создание репозитория: выполнение `git clone` поднимает новый репозиторий на данных, полученных с целевого remote, и тем самым создаёт и рабочий каталог, и связанный каталог `.git`, где лежит вся управляющая структура Git.
3. Настройка связи: операция clone сама устанавливает соединение с remote и по умолчанию называет его « origin». Если remote несколько или нужно другое имя, настройку можно поправить.
4. Извлечение: clone завершает создание и связывание локального репозитория, который пользователи затем могут «извлечь» в рабочие каталоги для правок.
5. Проверка статуса: успешность clone можно подтвердить, посмотрев текущие remote через `git remote -v`: там должен быть origin.

**Examples:**

Clone: запустить процесс клонирования.

```bash
git clone <remote-repo-url>
```

Remote: проверить настройку origin.

```bash
git remote -v
```

<summary>How does Git store information?</summary>

### How does Git store information?

**Definition:**

Git использует файловую систему, чтобы хранить данные, но хранение не исключительно файловое. Три главные части структуры данных Git — репозиторий, index/область подготовки и локальная рабочая копия.

**How it works:**

1. Локальная рабочая копия: здесь вы напрямую работаете с файлами.
2. Область подготовки (Index): своего рода «зона ожидания» для изменений, которые нужно включить в следующий коммит.
3. Локальный репозиторий: здесь Git ведёт полную историю и хранит разные версии файлов.

В репозитории такие ключевые части:

- База объектов: постоянно хранит снимки файлов и каталогов как объекты, которые дальше делятся на:
  - Объекты blob для содержимого отдельных файлов.
  - Объекты tree, которые повторяют иерархию файловой системы.
  - Объекты commit, связанные с конкретным состоянием в истории проекта.
  - Объекты tag, которые помечают конкретные коммиты, часто для релизов.
- Index/Stage: динамическое рабочее пространство, которое отражает ожидаемое состояние следующего коммита.
- Head Pointer: ссылка на последний коммит текущей рабочей ветки
- Branches: человекочитаемые имена, которые ссылаются на конкретные коммиты и дают независимые линии разработки.

1. Blobs: хеш SHA-1 считается по содержимому файла.
2. Trees: хеш SHA-1 объединяет содержимое файла и каталога внутри — изменения в любом файле или подкаталоге приводят к новому хешу.
3. Commits: хеш SHA-1 включает дерево структуры каталогов проекта вместе с родительским коммитом (или несколькими), сообщением коммита и сведениями об авторе.

Git допускает для объектов механизм «lazy write». Это значит, что файл объекта записывается при создании и остаётся неизменным, пока не изменится содержимое, которое он представляет. Когда изменение происходит, объект обновляется и его SHA-1 пересчитывается. Эту особенность называют «immutable storage».

Вот иллюстрация, чтобы было понятнее:

- Допустим, содержимое файла изменилось, и обновлённый файл добавлен в область подготовки.
- Новая версия файла сохраняется как объект Blob, и связанный объект Tree тоже обновляется.
- При следующем коммите создаётся новый объект Commit, который ссылается на обновлённый объект Tree.
- Одновременно ветка, на которой вы работаете, сдвигается вперёд и начинает ссылаться на этот новый коммит.

Такой порядок обеспечивает целостность истории проекта. Любое изменение содержимого, структуры каталогов или деталей коммита меняет хеш SHA-1 связанных объектов, и изменение сразу видно.

**Definition:**

`git status` — важная команда для отслеживания изменений в репозитории Git. Она даёт существенные подробности: состояния файлов, текущую рабочую ветку, неотслеживаемые файлы и другое.

### What does the git add command do?

**Definition:**

`git add` — первый шаг, когда нужно отследить изменения существующих файлов или добавить новые файлы в репозиторий Git. Команда готовит изменения к следующему коммиту: переносит изменённые или новые файлы в область подготовки.

Когда вызывают `git add`, происходят три главных действия:

1. Выбор файлов: вы выбираете, какие конкретные изменения файлов включить в предстоящий коммит.
2. Сравнение файлов: Git разбирает выбранные файлы и находит точные изменения по строкам или блокам.
3. Обновление области подготовки: выбранные изменения файлов готовятся и раскладываются по категориям. Когда вы готовы, действием коммита все изменения из области подготовки переходят в репозиторий.

**How it works:**

Область подготовки служит мостом между рабочим каталогом и репозиторием (историей).

- Рабочий каталог: содержит активные файлы, которые вы сейчас правите.
- Область подготовки (Index): своего рода «Sandbox», где изменения выборочно группируют для точных коммитов.
- Репозиторий: историческая запись всех коммитов и их состояний.

- Добавить все изменения: заново подготовить изменённые файлы к текущему состоянию: `git add .`
- Добавить интерактивно: выбрать изменения из изменённых файлов вручную: `git add -p`
- Конфликты слияния: после разбора конфликтов подготовить файлы к коммиту: `git add`

**Examples:**

Пример кода: подготовка и история Git.

Вот код на Python:

```python
# File: my_file.py  (in the working directory)

# Current content
print("This line is part of the initial version.")

# Post staging changes (not committed yet)
print("This line will be part of the next commit.")
```

В нашем примере на Python считайте файлом «file.py». Сначала в файле одна строка — это была начальная версия. Затем добавляется «This line will be part of the next commit.» (ещё не закоммичено), так что эти изменения оказываются между `git add` и `git commit`.

<summary>How do you create a commit in Git?</summary>

### How do you create a commit in Git?

**Definition:**

Посмотрим на процесс создания коммита в Git.

**How it works:**

Перед коммитом пользователю стоит просмотреть изменения в рабочем каталоге и в области подготовки.

Неотслеживаемые файлы: это новые файлы, которые Git ещё не отслеживает. Чтобы начать их отслеживать и затем включить в коммит, их нужно подготовить командой `git add`.

Отслеживаемые файлы: файлы, которые уже коммитили или добавляли в область подготовки, можно включить в следующий коммит.

- Конкретные файлы: напрямую добавить отдельные файлы или группу файлов по именам или путям.
- По шаблону: использовать подстановки или именованные наборы файлов, чтобы добавить сразу несколько.
- Интерактивно: открыть приглашение, где изменения можно просмотреть и выбрать для подготовки.

`git rm` и `git mv`. Эти команды соответственно удаляют и переименовывают файлы. Изменения затем готовят и коммитят так же, как новые добавления.

`git reset`. Убрать из области подготовки файлы, которые добавили по ошибке.

`git checkout`. Убрать изменения в рабочем каталоге и вернуть их к состоянию коммита `HEAD`.

`git commit`. Этой командой сохраняют изменения в локальный репозиторий после того, как их подготовили.

`-m`. Однострочное сообщение, которое описывает коммит.

`-a`. Подготовить все изменённые файлы и закоммитить их.

Эта команда пропускает шаг подготовки и по сути совмещает `git add` и `git commit`. Она полностью обходит область подготовки, поэтому пользоваться ею стоит осторожно, чтобы в коммит попали только задуманные изменения.

Если `-a` без `-m`, Git откроет текстовый редактор по умолчанию, чтобы вы написали сообщение коммита в отдельном файле.

Некоторые файлы коммитить не нужно, например:

- Временные файлы: сюда могут входить артефакты сборки или временные файлы редактора.
- Конфиденциальная информация: такая как пароли или закрытые ключи.

Для таких исключений шаблоны или имена файлов задают в файле `.gitignore`.

Чтобы исключать файлы глобально, создайте или поправьте глобальный файл `.gitignore`.

Затем при необходимости добавьте файл `.gitignore` в корневой каталог локального репозитория.

```bash
git add file1.txt path/to/file2.txt
```

```bash
git add *.txt
```

```bash
git add -i
```

```bash
git reset file1.txt
```

```bash
git checkout file1.txt
```

```bash

```

```bash
git commit -am "Update feature xyz"
```

```bash
git config --global core.excludesfile ~/.gitignore_global
```

```bash
touch .gitignore
```

- Не отслеживайте, не готовьте и не коммитьте конфиденциальную информацию.
- Держите `.gitignore` актуальным, особенно в совместных проектах.

<summary>What information is contained in a commit object in Git?</summary>

### What information is contained in a commit object in Git?

**Definition:**

Объект коммита в Git заключает в себе насыщенные текстовые данные, которые помогают отслеживать изменения в репозитории и управлять ими.

**How it works:**

- Author и Committer: эти записи метаданных содержат имя и адрес электронной почты человека, а также метку времени.
- Сообщения коммита: они дают краткое, но ёмкое понимание изменений, внесённых коммитом, и помогают сохранять ясность и контекст.
- Родительские коммиты: это указатель на один или несколько родительских коммитов. У коммита слияния родителей может быть больше одного.
- `HEAD` большинства веток указывает на самый свежий коммит, и именно эта `reference` продвигается, когда появляются более новые коммиты. Сам `HEAD` указывает на самый свежий коммит, но действует косвенно, через ссылку ветки.
- Объект Tree: каждый коммит связан с объектом tree, который представляет состояние содержимого репозитория на момент коммита. Объект tree, в свою очередь, держит ссылки на различные blob и поддеревья.
- Вот краткая сводка. Blob в Git — это файл, а tree — набор файлов, и он может включать другие tree.
- Коммит, следовательно, создаётся с объектом, ссылающимся на tree: он фиксирует и сданную версию файлов (через объект tree), и снимок метаданных (через свой уникальный ключ SHA).
- Внутри этого tree также различные поддеревья и blob, к которым tree прилипает.

Когда ветка или ссылка больше не указывает на коммит, Git всё равно сохраняет эти висячие коммиты. Через `git reflog` их потенциально можно восстановить.

Продвинутые процессы Git часто требуют целостности и подлинности данных, особенно в распределённых командах и проектах с открытым кодом. Git применяет GitPG, чтобы подписывать коммиты, проверять подлинность объектов коммитов и отмечать возможную подмену или подделку прежних коммитов.

<summary>How does git push differ from git fetch?</summary>

### How does git push differ from git fetch?

**Definition:**

git push обновляет ссылки на удалённом репозитории из локального и отправляет объекты, которых на удалённой стороне ещё нет. git fetch скачивает ссылки и объекты, нужные для их истории, и обновляет ветки удалённого слежения. Fetch не двигает текущую ветку.

**How it works:**

Простой git push берёт upstream текущей ветки или origin, если upstream не задан. Какие ссылки уйдут, решают refspec, remote.<name>.push или push.default (по умолчанию simple: текущая ветка уходит в одноимённую). git fetch без имени remote использует upstream текущей ветки или origin. Имена записываются в .git/FETCH_HEAD и при обычном refspec обновляют refs/remotes/<remote>/*. Ни одна из команд не меняет рабочее дерево другой стороны.

**When to use:**

Fetch — когда нужно только увидеть удалённые коммиты. Push — когда удалённые ссылки должны сдвинуться на коммиты, которые уже есть локально.

**Examples:**

```bash
git fetch origin
git push origin main
git push --set-upstream origin main
```

- [git-fetch](https://git-scm.com/docs/git-fetch)

### Explain the purpose of the git pull command.

**Definition:**

git pull скачивает изменения с remote и встраивает выбранную ветку в текущую.

**How it works:**

Выбор хранят pull.rebase, pull.ff и pull.squash. Конфликт можно отменить через git merge --abort или git rebase --abort.

**When to use:**

Pull — когда текущая ветка должна сразу принять удалённые коммиты. Один fetch — когда их сначала нужно посмотреть.

### What is a merge conflict in Git and how do you resolve it?

**Definition:**

Конфликт слияния — это фрагмент, который изменили обе стороны, поэтому Git не выбирает сторону сам. Он оставляет маркеры конфликта в рабочем дереве и останавливает слияние.

**How it works:**

HEAD остаётся на месте. MERGE_HEAD указывает на другую ветку. Чистые пути обновляются в индексе и в рабочем дереве. Для конфликтного пути индекс хранит до трёх стадий: стадия 1 — общий предок, стадия 2 — HEAD, стадия 3 — MERGE_HEAD (git ls-files -u). В рабочем файле результат с маркерами <<<<<<<, ======= и >>>>>>>. Часть до ======= обычно ваша сторона. Отредактируйте файл, уберите маркеры, выполните git add для пути, затем git merge --continue или git commit. git merge --abort отменяет слияние.

**Examples:**

```bash
git merge topic
git ls-files -u
git add path/to/file
git merge --continue
```

### What is a fast-forward merge in Git?

**Definition:**

Fast-forward бывает, когда кончик текущей ветки является предком вливаемого коммита. Git переводит HEAD и индекс на этот коммит и не создаёт merge-коммит.

**How it works:**

Так часто проходит git pull, если на ветке нет своих коммитов. Для обычного слияния веток --ff — поведение по умолчанию. --no-ff создаёт merge-коммит, даже если fast-forward возможен. --ff-only делает fast-forward или завершается с ненулевым кодом. --no-commit не останавливает fast-forward, потому что merge-коммита, перед которым можно остановиться, нет.

**Examples:**

```bash
git merge topic
git merge --ff-only topic
git merge --no-ff topic
```

### Define a three-way merge.

### How do you rebase a branch in Git?

**Definition:**

git rebase переносит цепочку коммитов на новую точку старта. Исходные коммиты проигрываются заново как новые коммиты.

**How it works:**

Получается новая цепочка (A', B', C'), и topic указывает на новый кончик. Конфликт останавливает rebase. git rebase --continue продолжает после исправления и индексации. git rebase --skip отбрасывает текущий коммит. git rebase --abort возвращает ветку к состоянию до rebase.

**When to use:**

Перебазируйте ветку, пока эти коммиты никто не забрал. После публикации предпочтительнее merge, чтобы чужие клоны не восстанавливались после переписанной истории.

**Examples:**

```bash
git switch topic
git rebase master
git rebase --continue
git rebase --abort
```

<summary>Explain the pros and cons of rebasing vs. merging.</summary>

### Explain the pros and cons of rebasing vs. merging.

**Definition:**

Merge соединяет две истории merge-коммитом, если это не fast-forward. Rebase проигрывает ваши коммиты поверх другого кончика и записывает новые объекты коммитов.

**How it works:**

gitworkflows предпочитает merge: одно слияние переносит все коммиты ветки и сохраняет запись о том, как ветки соединились. Rebase переписывает коммиты; через git rebase -i так же меняют порядок и объединяют их до публикации. Руководство rebase отсылает к разделу восстановления после upstream rebase, если переписаны уже опубликованные коммиты.

**When to use:**

Опубликованную работу сливайте. Rebase — только для ещё локальных коммитов, когда нужна линейная серия.

**Pluses and minuses:**

- Merge сохраняет обоих родителей и за один шаг переносит сколько угодно коммитов. Fast-forward даже не добавляет merge-коммит.
- Rebase даёт прямую линию новых коммитов и до публикации умеет сжимать их и менять порядок.
- Rebase меняет идентификаторы коммитов. Тот, кто уже забрал старые коммиты, должен согласовать переписанную историю.
- История merge показывает соединение, и граф долгой ветки может быть труднее читать.

**Examples:**

```bash
git merge topic
git rebase master
git rebase -i HEAD~5
```

### What are Git tags and how are they different from branches?

### What is semantic versioning in the context of Git tagging?

**Definition:**

Git не разбирает номера версий. Имя тега вроде v1.2.0 — только ссылка в refs/tags/. Любая схема major.minor.patch — соглашение проекта в момент создания тега.

**How it works:**

git tag -a v1.2.0 -m "..." сохраняет имя и сообщение в объекте тега. git tag --list 'v-*' показывает имена, которые совпали с шаблоном оболочки. git tag не проверяет, что более новый тег имеет больший номер. Слияние аннотированного тега, который лежит не на своём месте в refs/tags/, создаёт merge-коммит даже при возможном fast-forward; git merge v1.2.3^0 или git merge --ff-only v1.2.3 встраивает помеченный коммит без этого лишнего merge-коммита.

**How it works:**

### Explain the purpose of a git hook.

**Definition:**

**When to use:**

### What is the difference between git pull and git fetch followed by git merge?

**Definition:**

Pull сам выбирает upstream, если refspec не передан, и затем встраивает. **When to use:**

Fetch, затем merge — когда входящие коммиты нужно сначала посмотреть. Pull — когда встраивание должно идти сразу и вас устраивает умолчание «только fast-forward».

### How do you handle large binary files in Git without using Git LFS?

**Definition:**

Оставьте их неотслеживаемыми или примите, что каждая закоммиченная версия — целый blob. Частичный клон скачивает эти blob только когда команда их требует.

**How it works:**

gitignore не даёт неотслеживаемому бинарному файлу попасть в коммиты. Отслеживаемые бинарные файлы остаются в истории; git rm --cached не даёт следующему коммиту записать путь и оставляет файл в рабочем дереве. git clone --filter=blob:limit=<size> пропускает blob не меньше этого размера, пока они не нужны. --filter=blob:none так же пропускает содержимое всех blob. Исторические blob он не уменьшает.

**Examples:**

```bash
printf '%s\n' '*.zip' >> .gitignore
git clone --filter=blob:limit=1m <repository>
```

### Explain the impact of case sensitivity in Git and how to manage it across different operating systems.

**Definition:**

core.ignoreCase говорит Git считать имена, которые различаются только регистром, одним путём на файловых системах, которые так устроены: APFS, HFS+, FAT и NTFS.

**How it works:**

По умолчанию значение false, но git clone и git init проверяют файловую систему и ставят core.ignoreCase true, когда это уместно. Если список каталога вернул makefile, а Git ждал Makefile, Git сохраняет имя, которое уже запомнил. Руководство говорит, что Git полагается на соответствие этой переменной операционной системе и что её изменение может дать неожиданный результат. core.precomposeUnicode — родственная настройка macOS: при true Git отменяет Unicode-декомпозицию имён, которую делает macOS. Это важно, когда один репозиторий открывают и на macOS, и на Linux или Windows.

**When to use:**

Оставьте значение, которое определили clone или init. Не переключайте core.ignoreCase, чтобы замаскировать два отслеживаемых имени, которые различаются только регистром.

**Examples:**

```bash
git config core.ignoreCase
git config core.precomposeUnicode true
```

```bash
git switch -c maint-1.2 v1.2.0

git merge maint-1.2
```
