### Что такое Redis and what do you use it for?

**Definition:**

**Redis** (Remote Dictionary Server) — это **хранилище ключ-значение в памяти**, известное своей **производительностью** и **универсальностью**. Его разработал в 2009 году Salvatore Sanfilippo, и он остаётся влиятельным инструментом современного управления данными и кеширования.

**How it works:**

**Ключевые возможности**

- **Структуры данных**: Redis выходит за рамки простого хранения ключ-значение и поддерживает разные структуры данных, включая **strings, lists, sets, sorted sets** и **hashes**.
- **Persistence**: Есть оба варианта — сохранение на диск и чистое хранение в памяти. Эта гибкость подходит задачам, где требования к долговечности и скорости различаются.
- **Replication**: Redis позволяет создавать несколько реплик, обеспечивая высокую доступность и избыточность данных.
- **Clustering**: Redis можно развернуть в кластерном режиме, чтобы распределять данные по нескольким узлам и обеспечивать масштабируемость.
- **Pub/Sub Messaging**: Поддерживается шаблон обмена сообщениями publish-subscribe.
- **Atomic Operations**: Большинство операций с данными атомарны, что даёт надёжный ход работы.

**Базовые структуры**

1. **Strings**: Пары ключ-значение, которые могут хранить текст, целые числа или двоичные данные.
2. **Lists**: Упорядоченные коллекции строк с операциями на обоих концах.
3. **Sets**: Коллекции уникальных неупорядоченных строк со встроенными операциями вроде union, intersection и difference.
4. **Sorted Sets**: Как sets, но у каждого элемента есть ключ (или score), по которому их можно сортировать.
5. **Hashes**: Пары ключ-значение, по сути карта внутри ключа Redis.

**Внутренняя архитектура**

- **Event Loops**: Для производительности используется событийное программирование на эффективной кодовой базе на C.
- **Caching Strategy**: Для истечения кеша Redis применяет алгоритм LRU (Least Recently Used), но допускает и более тонкие стратегии.

**Сохранение данных**

Redis предлагает такие варианты **persistence**:

1. **RDB Snapshots**: Периодически сохраняет образ набора данных на диск.
2. **AOF (Append-Only File)**: Журналирует каждую операцию записи, обеспечивая долговечность и позволяя восстановить данные после падения сервера.

Имеет смысл сохранять и данные в памяти, и исторические данные на диск или на внешний сервер для избыточности.

**Встроенная репликация**

В Redis можно иметь несколько реплик (или slaves) основного сервера Redis (или master). Такая схема даёт **избыточность данных** и может **ускорить чтение**, позволяя клиентам читать с любой доступной реплики.

**Шардирование и кластеризация**

Чтобы **масштабироваться горизонтально**, Redis может использовать два подхода:

1. **Sharding**: Распределяет данные по нескольким экземплярам Redis на стороне клиента или сервера, но ответственность за управление шардами лежит на пользователе.
2. **Redis Cluster**: Встроенное решение, которое автоматически делит данные по узлам и при этом обеспечивает отказоустойчивость и согласованность данных.

Для надёжности и масштабируемости в современных приложениях выгодно поднять кластер Redis.

**Поддержка многопоточности**

Традиционно Redis напрямую не поддерживает многопоточность. Однако **работы по добавлению** нативной поддержки этой возможности **уже идут**.

**Лучшие практики**

- **Data Segregation**: Используйте отдельные базы и экземпляры для разных типов данных или ролей.
- **Error Handling**: Применяйте механизмы, которые обнаруживают проблемы связи или сервера и восстанавливаются после них.
- **Backup Strategies**: Регулярно делайте резервные копии сохранённых данных и следите, чтобы задачи бэкапа выполнялись стабильно.

**Соображения безопасности**

- **VPCs and Firewalls**: Ограничьте доступ к Redis конкретными IP через правила файрвола или VPC.
- **TLS Encryption**: Используйте SSL/TLS, чтобы шифровать данные при передаче.
- **Access Control**: Настройте аутентификацию, чтобы отказывать неавторизованным пользователям в доступе к Redis.

**Типичные ловушки**

- **Single Point of Failure**: Запуск Redis вне кластера может оставить вас уязвимыми к полной потере данных.
- **Persistence Lag**: В некоторых схемах Redis может слегка запаздывать с записью данных на диск.
- **Memory Overload**: Без внимательного наблюдения Redis может потребить слишком много памяти и привести к проблемам производительности или падению системы.

**When to use:**

**Типичные сценарии**

1. **Caching Layer**: Redis хорошо работает как кеш благодаря хранению в памяти и быстрому чтению и служит источником данных для веб-серверов, баз данных и не только.
2. **Session Store**: Его используют для сессий пользователей в веб-приложениях, чтобы доступ был быстрым, а обновления — в реальном времени.
3. **Queues**: Списки Redis и блокирующие операции делают его частым выбором для очередей сообщений и систем управления задачами.
4. **Real-Time Leaderboards and Counters**: Структура sorted set помогает вести упорядоченные списки в реальном времени — для таблиц лидеров и рейтингов.
5. **Pub/Sub Communication**: Redis может обеспечить связь в реальном времени между компонентами архитектуры через шаблон publish-subscribe.
6. **Geospatial Data**: Есть функции для геоданных, поэтому он подходит приложениям с сервисами на основе местоположения.
7. **Analytics**: Структуры данных и атомарные операции помогают в аналитике и обработке данных в реальном времени.

### Как Redis store data?

**Definition:**

**Redis**, хранилище данных в памяти, обеспечивает **очень быстрые** чтение и запись, раскладывая данные по типам, и у каждого типа свои возможности.

Модели данных Redis — это пары $key \rightarrow value$, устроенные в памяти как набор возможных типов данных:

- **String**: Бинарно-безопасные строки, где каждый символ хранится восемью битами.
- **List**: Коллекция упорядоченных строк. Оптимизирована для быстрых вставок и удалений.
- **Set**: Коллекция неупорядоченных различных строк.
- **Sorted Set**: Похож на set, но у каждого элемента есть уникальный score для сортировки.
- **Hash**: Структура вроде карты с полями и значениями, и то и другое — строки.
- **HyperLogLog**: Структура для приблизительной оценки числа уникальных элементов в множестве.
- **Streams**: Коллекция только для добавления из пар `key-value`.
- **Bitmaps**: Особый тип для манипуляций с битами.

**How it works:**

**Управление памятью**

Redis применяет стратегии, чтобы эффективно управлять памятью:

- **Key and Encapsulation Metadata**: Каждый ключ занимает минимум места, только под своё представление. Значение, связанное с ключом, ослабляет роль инкапсуляции.
- **Memory Optimizations**: Используются алгоритмы, которые уменьшают избыточность данных, например общее использование сегментов у ключей с похожим содержимым.

**Механизмы сохранения**

Redis даёт два основных механизма сохранения данных:

- **RDB (Redis Database)**: Периодические снимки набора данных.
- **AOF (Append-Only File)**: Журналирует каждую операцию записи и позволяет полностью восстановить набор данных.

Система может использовать любой из этих способов или оба сразу ради сохранности данных.

**Соответствие функциональным базам**

**Redis** даёт операционное присутствие в реальном времени и в памяти, но через сохранение на диск повторяет функции традиционных баз для отказоустойчивости и восстановления данных.

**Производительность и масштабируемость**

Сохранение данных на диск добавляет накладные расходы, которые ухудшают и **время записи**, и само число записей, которое база может выдержать.

Redis вместо этого сосредоточен на оптимизации операций в памяти ради **низких задержек** и высокой пропускной способности записи. Такой подход особенно выгоден там, где нужна высокая интерактивность или где долговечность вторична по отношению к скорости.

Redis также даёт разумный уровень надёжности через настраиваемую долговечность и держит баланс между высокой скоростью и сохранностью данных.

### Какие data types можно хранить в Redis?

**Definition:**

**Redis** как сервер структур данных оптимизирован под разные типы данных и даёт разнообразные варианты хранения.

**How it works:**

**Основные типы данных**

**Strings**

- Подходят для простых ключей и кеширования данных.
- Примеры: `username` или JSON-строка

**Lists**

- Подходят для данных, у которых есть порядок и которые могут допускать дубликаты.
- Пример: очередь задач.

**Sets**

- Эффективны для уникальных неупорядоченных наборов.
- Пример: уникальные посетители сайта.

**Sorted Sets**

- Похожи на **Sets**, но у каждого участника изначально есть score, что упрощает свой порядок и поиск.
- Пример: таблица лидеров, где score — это ранг пользователя.

**Hashes**

- Дают структуру вроде карты из пар ключ-значение, удобную для хранения и чтения сгруппированных данных.
- Пример: данные пользователя, такие как username, email и status.

**HyperLogLogs**

- Позволяют оценить число уникальных элементов в множестве.
- Пример: подсчёт уникальных IP-адресов в журнале доступа веб-сервера.

**Bitmaps**

- Лучше всего там, где задачу удобно моделировать битовыми массивами, часто для учёта активности пользователя во времени.
- Пример: отслеживание вовлечённости пользователя по конкретным дням.

**Geospatial Indexing**

- Позволяет сопоставлять места участникам так, чтобы выполнять операции по географическому расстоянию.
- Пример: поиск ближайших мест.

**Вторичные типы данных**

**Streams**

- Доступны с Redis 5.0, **Streams** — это коллекции только для добавления.
- Примечательны тем, что дают уникальные ручные подтверждения.
- Пример: журналы данных с настраиваемой детальной политикой хранения.

**Modules**

- **Redis Modules** сильно расширяют базовые возможности Redis и добавляют множество новых типов данных со специальными функциями.
- Примеры:
- RediSearch: даёт мощный полнотекстовый поиск.
- ReJSON: упрощает работу с JSON и по сути добавляет в Redis развитый тип данных JSON.

**Временные операции**

- Redis даёт структуры данных, а именно time series и вероятностные модели, для конкретных расчётов и оценок, чувствительных ко времени.
- Пример:
- Time Series заточен под операции с данными, привязанными к меткам времени.
- Вероятностные структуры данных, как следует из названия, дают оценки, иногда ценой абсолютной точности.

**За пределами типов данных**

Redis даёт гибкую систему, которая позволяет настраивать функции и поведение данных. Механизмы **Lua Scripting** и **Pub/Sub**, например, расширяют возможности Redis и открывают путь к устойчивому собственному поведению, не отходя от его основных типов данных.

### Что такое Redis key and how should you structure it for best performance?

**Definition:**

В Redis **ключ** служит основным идентификатором для хранения данных. Эффективное устройство ключа важно для высокой производительности.

**How it works:**

**Соглашения об именах ключей**

- **Keyspace Segmentation**: Разделяйте ключи логически, например по пользователю. Это ускоряет операции вроде `DEL` или `KEYS` на подмножестве.
- **Consistent Naming**: Используйте единый формат, например "RESOURCE:ID".

**Длина и сложность ключа**

- **Minimize**: Короткие и простые ключи уменьшают память и время поиска.
- **Avoid Repetition**: Единый префикс уменьшает избыточность, но чрезмерное повторение может быть вредным.

**Кодирование данных**

- Redis различает **прямое** (явное) и **косвенное** (неявное) кодирование. Явное кодирование предпочтительнее для производительности и ясности.

**Прямое кодирование**

- **String Numbers**: Предпочитайте хранить числовые строки, чтобы оптимизировать целые значения в определённом диапазоне.
- **Zip List**: Автоматически кодирует короткие списки или множества с определёнными типами значений (целые или строки).
- **Introspection**: Используйте `OBJECT ENCODING`, если не уверены в стратегии кодирования.

**Косвенное (RAW) кодирование**

- **Always RAW**: Гарантированно использует память — подходит для более крупных или непримитивных типов.

**Эволюция и удаление ключей**

- **Evolution**: Когда обновить ключи нельзя, добавляйте идентификаторы версии к новым ключам.
- **Deletion**: Следите за очисткой, чтобы не оставлять осиротевшие или устаревшие ключи.

**Examples:**

**Пример кода: соглашения об именах ключей**

Вот код на Python:

```python
def get_user_key(user_id, data_type):
    return f"USER:{user_id}:{data_type}"

def get_resource_key(resource_id):
    return f"RESOURCE:{resource_id}"

def delete_user_data(user_id):
    for key in r.keys(get_user_key(user_id, "*")):
        r.delete(key)
```

### Как you set an expiration on Redis keys?

**Definition:**

Установка времени истечения у **ключей Redis** — мощная возможность, которая помогает управлять ключами. Есть несколько механизмов под разные типы ключей. Разберём эти варианты.

**How it works:**

**Настройка истечения по умолчанию**

**Redis** позволяет задать время истечения ключей по умолчанию. Например, чтобы задать истечение по умолчанию в 60 секунд:

**Redis CLI**

```sh
CONFIG SET  lazyfree-lazy-eviction-limit 30
config set -1
```

**Истечение отдельных ключей**

**Ключи Redis** можно настроить так, чтобы они истекали через заданный срок.

**Использование команд**

- **Задать ключ с истечением**: Используйте команды `EXPIRE` или `SETEX` для управления истечением по ключу.

Синтаксис:

```
redis> SET key value EX seconds
redis> SETEX key seconds value
redis> EXPIRE key seconds
```

Пример:

```sh
redis> SET mykey redis
OK
redis> EXPIRE mykey 10  # Expires in 10 seconds
(integer) 1
```

- **Постоянное истечение через PSETEX**: Чтобы задать ключу и значение, и истечение одним шагом.

Синтаксис:

```
redis> PSETEX key milliseconds value
```

Пример:

```sh
redis> PSETEX mykey 10000 redis  # Expires in 10 seconds (10000ms)
OK
```

**Запрос сведений об истечении**

- **Time to Live (TTL)**: Проверить, сколько времени жизни осталось у ключа.

Синтаксис:

```sh
redis> TTL mykey
```

Пример:

```sh
redis> TTL mykey
(integer) 5
```

- **Persist/Remove Expiry**: Продлить или снять истечение ключа.

Синтаксис:

```sh
redis> PERSIST mykey
redis> PERSIST mykey  # To remove the key
```

**Точная настройка истечения ключей**

Для выборочного или массового истечения Redis даёт специальные методы.

- **Scan, Delete, and Expire**: Используйте эти команды вместе с алгоритмом scan для обширного управления ключами.

Команды:

- SCAN
- DEL
- UNLINK (introduced in Redis 4.0)
- EXPIRE
- PEXPIRE

- **Expiration Report**: Получить ключи с определённым оставшимся временем жизни; это часто используют вместе с командой `TTL`.

Команда: `PTTL key`

- **Batch Expiry with Sorted Sets**: Используйте sorted sets, чтобы создать отдельные наборы ключей с разным временем истечения. Затем обрабатывайте каждую категорию пакетами.

- **Multiple-Step Approach with LUA Scripting**: Этот метод идёт в несколько шагов, чтобы выполнение было упорядоченным. Он особенно полезен, когда для нужного результата нужно несколько шагов, например при сложных операциях.

### Что делают команды `SET` и `GET` в Redis?

**Definition:**

`SET` и `GET` в **Redis** — базовые команды ключ-значение, у каждой своя роль, и они дополняют друг друга.

**How it works:**

**Основные функции**

- **`SET`**: Сохраняет значение, либо перезаписывая существующую пару ключ-значение, либо создавая новую.
- **`GET`**: Возвращает значение, связанное с данным ключом. Если ключа нет, `GET` возвращает null.

**Дополнительные указания `SET` и `GET`**

**`SET`**

- **Options**:

  - `EX` или `PX`: Задаёт истечение в секундах (`EX`) или миллисекундах (`PX`), после чего пара ключ-значение удаляется автоматически.
  - `NX` или `XX`: Определяет, выполнится ли команда только если ключа ещё нет (`NX`) или только если ключ уже есть (`XX`).

- **Multi-SET Variants**:

  - `MSET`: Задаёт несколько пар ключ-значение одновременно.
  - `MSETNX`: Задаёт несколько пар ключ-значение, только если ни одного из ключей ещё нет.

- **Memory Usage Control**:

  - `SET foo "Hello" EX 3600`: Задаёт ключ с истечением, который будет удалён через час.

**`GET`**

- **Data Transformation**:

  - Если значение по ключу **является целым числом**, `GET` автоматически преобразует его в целочисленный тип данных перед возвратом.
  - Если нужно вернуть значение как строку, используйте команду `GET foo`.

- **Multi-Key Operations**:

  - `MGET`: Возвращает значения нескольких ключей одной операцией.

- **Performance Considerations**:

  - Кандидаты в большой ключ `{KEY}` могут быть получены через `GET` или `MGET` не полностью из-за их возможного влияния на производительность Redis.
  - Обычно лучше читать каждый ключ после того, как уже решено, какие ключи читать.

- **Consistency and Atomicity**:

  - Команды `GET` и `SET` атомарны. После того как `SET` произошёл, следующий `GET` вернёт значение в состоянии после выполнения `SET`.

**Практики по сценариям**

- **Security Sensitive Data**:
  - Избегайте `GET` в средах с чувствительными данными: он может раскрыть пары ключ-значение.

- **Memory Efficiency**:
  - Для операций с несколькими ключами предпочитайте `MSET`: часто это экономнее по памяти, чем `GET` или `MGET`.

- **Concurrent Operations**:
  - Используйте опции вроде `NX` и `XX` вместе с `SET` для безопасных параллельных вставок или обновлений, когда заранее известно, есть ключ или нет.

- **Expiry Management**:
  - Пользуйтесь истечением по времени, чтобы пары ключ-значение удалялись сами, без дополнительной уборки.

- **Performance Optimization**:
  - Учитывайте стоимость преобразования данных, особенно когда ключи часто хранят целые числа.

### Как Redis handle data persistence?

**Definition:**

**Redis** в целом ставит скорость **данных в памяти** выше, а методы persistence использует для лучшей надёжности и восстановления.

**How it works:**

**Варианты persistence**

1. **RDB (Snapshots)**:
   - Сохраняет снимки на момент времени.
   - Способ настройки часто **совмещают** с AOF ради полной долговечности.

    ```conf
    save 900 1         # Save every 15 minutes only if 1+ key changed
    save 300 10        # Save every 5 minutes only if 10+ keys changed
    ```

2. **AOF (Append-Only File)**:

   - Журналирует каждую операцию записи, это подходит для **полной долговечности**.
   - Можно настроить **sync** после каждой команды или периодически.

    ```conf
    appendonly yes          # Enable the AOF
    appendfsync everysec    # Sync AOF log every second
    ```

**Понимание RDB и AOF**

- **RDB Advantages**:
  - Упрощает восстановление. При перезапуске быстрее грузится из бинарного дампа.
  - Эффективен для наборов данных, которые меняются редко.

- **AOF Advantages**:
  - Лучше всего, когда нужно сохранить каждую запись. Подходит для соответствия требованиям и целостности данных. Может слегка влиять на производительность.

**Совместное использование для лучшей производительности**

- Применение **и** RDB, **и** AOF даёт лучшее от обоих:
  - Быстрое восстановление через RDB.
  - Уверенность, что записи сохранены, через AOF.

Такая схема довольно обычна в production: она даёт и резервную копию, и гарантии полной целостности данных.

**Лучшая практика**

- Когда используются и RDB, и AOF, важно тонко настроить их параметры, чтобы сбалансировать целостность данных, производительность и механизм восстановления, который они дают.
- Периодически проверяйте и подтверждайте стратегию сохранения данных.

<summary>Объясните the difference between RDB and AOF persistence strategies in Redis.</summary>

### Объясните the difference between RDB and AOF persistence strategies in Redis.

**Definition:**

В Redis **RDB** и **AOF** — две стратегии persistence, направленные на долговечность данных. **RDB** даёт **резервные копии на момент времени**, а **AOF** сосредоточен на **журнале команд**.

**How it works:**

**RDB Persistence**

RDB, или Redis DataBase, рассчитан на **периодические резервные копии**. Он снимает снимки данных через заданные интервалы и сохраняет их на диск, чтобы после неожиданных событий восстановление было быстрым.

- **Backup Frequency**: Задаётся параметром конфигурации. Обычно сохранение ставят после определённого числа операций записи.
- **Performance and Storage**: RDB производительнее и экономнее по памяти, потому что может накопить несколько операций записи перед сохранением.
- **Recovery**: При восстановлении возможна потеря данных до последней точки резервной копии.

**AOF Persistence**

AOF, или Append-Only File, стремится дать полную **историю команд** Redis, чтобы было проще воспроизвести команды и восстановить набор данных до конкретного момента времени.

- **Backup Frequency**: В реальном времени. Каждая операция записи дописывается в файл AOF, так что перезапуск сервера не приводит к потере данных.
- **Recovery**: Потеря данных минимальна, потому что даже отключившиеся клиенты могут заново синхронизировать свои изменения из журнала AOF, когда подключатся снова.

**Совместное persistence**

Redis позволяет выбрать либо RDB, либо AOF, и также поддерживает **одновременное persistence**. Когда включены и RDB, и AOF, Redis может использовать файл AOF, чтобы восстановить набор данных дальше последнего снимка RDB.

Несмотря на преимущества, использование обеих стратегий может потребовать дополнительных усилий на наблюдение и управление компонентами persistence.

### Как бы вы implement a simple counter in Redis?

**Definition:**

Чтобы реализовать **простой счётчик** в Redis, можно использовать команды **`INCR`** или **`HINCRBY`** — в зависимости от того, это отдельный счётчик или счётчик на основе hashmap.

**How it works:**

**Отдельный счётчик**

Для одного ключа можно использовать `INCR`, чтобы увеличивать значение и получать его.

**Команды Redis**

```plaintext
> SET myCounter 0                # Initialize the counter
OK
> INCR myCounter                # Increment the counter
(integer) 1
> GET myCounter                    # Retrieve the counter value
"1"
```

**Счётчик на основе hashmap**

Если нужно несколько счётчиков, можно использовать **hashmap** Redis вместе с командой `HINCRBY`.

**Команды Redis**

```plaintext
> HSET myHash key1 0            # Initialize the counters within the hashmap
(integer) 1
> HINCRBY myHash key1 5        # Increment counter 'key1' by 5
(integer) 5
> HGET myHash key1             # Get value of counter 'key1'
"5"
```

**Examples:**

**Пример кода: отдельный счётчик**

Вот код на Python:

```python
import redis

# Connect to Redis
r = redis.StrictRedis(host='localhost', port=6379, db=0)

# Set up the counter
r.set('myCounter', 0)

# Increment and retrieve the counter
r.incr('myCounter')
print(r.get('myCounter'))
```

```python
import redis

r = redis.StrictRedis(host='localhost', port=6379, db=0)
```

<summary>Что такое hashes in Redis and how do you use them?</summary>

### Что такое hashes in Redis and how do you use them?

**Definition:**

**Redis** даёт мощную структуру данных под названием **hash** — по сути это отображение строк на строковые значения.

Хранясь как **неупорядоченная** коллекция, hashes исключительно эффективны для задач с частыми операциями **по отдельному полю**, например когда нужно обновить или прочитать конкретные значения, а не весь набор данных.

**How it works:**

**Зачем использовать Hashes?**

- **Simplicity**: Hashes дают практичный способ организовать связанные данные.
- **Memory Efficiency**: Удобны для небольших наборов данных или полей, которые часто меняются.
- **Performance**: Особенно заметны в приложениях, которым нужны тонкие операции по полям и у которых внутри ключа много полей.

**Сценарии Redis**

- **User Profiles**: Hashes собирают разные атрибуты пользователя, такие как name, email и date of birth.
- **Caching**: Вместо того чтобы хранить число просмотров статьи каждого пользователя отдельным ключом списка, hash дополнительно делит счётчик по пользователям.

**Ключевые функции**

- **HSET** задаёт поле и значение (создаёт, если его нет).
- **HGET** возвращает значение конкретного поля.
- **HGETALL** получает все поля и значения.
- **HDEL** удаляет конкретное поле.
- **HEXISTS** проверяет, существует ли поле.

**Examples:**

**Пример кода: hash в Redis**

Вот код на Python:

```python
import redis

# Connect to Redis
client = redis.StrictRedis(host='localhost', port=6379, db=0)

# User Attributes
user_key = 'user:123' # user_123 is a unique identifier for a user
user_attributes = {
    'name': 'John Doe',
    'email': 'john.doe@email.com',
    'age': '30'
}

# Store user attributes as a hash
client.hset(user_key, mapping=user_attributes)

# Retrieve user's name
name = client.hget(user_key, 'name')
print(f"User Name: {name.decode()}")  # Decoding from bytes back to string

# Check if a user is already registered
new_user_attributes = {
    'name': 'Jane Smith',
    'email': 'jane.smith@email.com'
}
is_new_user = bool(client.hsetnx(user_key, mapping=new_user_attributes))

if is_new_user:
    print("Welcome! A new user has been registered.")

# Fetch all user attributes
all_attributes = client.hgetall(user_key)
print("All User Attributes:")
for field, value in all_attributes.items():
    print(f"{field.decode()}: {value.decode()}")

# Delete User's age
deleted = client.hdel(user_key, 'age')
print(f"Age field deleted: {bool(deleted)}")

# Check if age field exists
has_age = bool(client.hexists(user_key, 'age'))
print(f"Age field exists: {has_age}")
```

<summary>Как you handle atomic operations in Redis?</summary>

### Как you handle atomic operations in Redis?

**Definition:**

**Redis** в первую очередь применяет **атомарность одной операции** на уровне команд или скриптов. Это уменьшает гонки и делает управление данными безопаснее.

Чтобы обеспечить атомарность многошаговых процессов, Redis поддерживает **Transactional Commands** и механизм **WATCH-EXEC** как дополнительные уровни согласованности.

**How it works:**

**Механизмы многошаговой атомарности**

1. **WATCH-EXEC**: Защищает транзакционную целостность конкретных ключей, наблюдая за ними. Следующий многошаговый блок EXEC обрабатывает действия только если наблюдаемые ключи не изменились.

2. **MULTI-EXEC**: Заключает набор команд, которые выполняются атомарно, либо все вместе, либо никакие. Это защищает от частичного выполнения заключённых команд.

**Главные выводы**

- Redis обеспечивает атомарность на разных уровнях, но может применять её по-разному в зависимости от команды.
- Пара WATCH-EXEC защищает целостность конкретных ключей внутри транзакции.
- Хотя степень атомарности различается, отдельные команды Redis эффективно закрывают конкретные нужды изменения данных.

**Examples:**

**Пример кода: WATCH-EXEC**

Вот код на Python:

```python
import redis

r = redis.StrictRedis()

# Initialize the watched key
r.set('watched', 100)

# Begin watch and multi-step execution
pipe = r.pipeline()
while True:
    try:
        pipe.watch('watched')
        value = pipe.get('watched')
        new_value = int(value) + 1
        # If the value was altered externally, retry
        if pipe.execute():
            break
        pipe.multi()
        pipe.set('watched', new_value)
    except redis.WatchError:
        continue
```

### Что такое lists in Redis and what are some common operations you can perform on them?

**Definition:**

**Redis** даёт самостоятельную структуру данных **list**, известную как **Redis List**, которая эффективна для работы с упорядоченными коллекциями.

Списки в Redis:

- **Динамические** по размеру: растут или сжимаются, когда элементы добавляют или удаляют.
- **Индексированные**: элементы списка доступны по индексу с нуля.

**How it works:**

**Ключевые операции**

**Добавление элементов**

- **LEFT PUSH (LPUSH)**: Добавляет элемент в голову списка.
- **RIGHT PUSH (RPUSH)**: Добавляет элемент в хвост списка.

**Удаление элементов**

- **LEFT POP (LPOP)**: Удаляет и возвращает элемент в голове списка.
- **RIGHT POP (RPOP)**: Удаляет и возвращает элемент в хвосте списка.

**Операции по диапазону**

- **RANGE**: Даёт диапазон элементов по позициям индекса.
- **TRIM**: Обрезает список так, чтобы в нём остался только заданный диапазон элементов.

**Сведения о списке**

- **LENGTH**: Возвращает текущий размер списка.
- **INDEX SEARCH**: Найти индекс первого элемента, совпадающего со значением.
- **ELEMENT SEARCH**: Найти элементы, совпадающие с шаблоном (например, через RPOP).

**Обновление списка**

- **INSERT**: Вставляет элемент до или после опорного элемента.
- **UPDATE AT**: Обновляет значение элемента по конкретному индексу.

**Операции между списками**

- **POP-AND-PUSH**: Переносит элемент из хвоста одного списка в голову другого.
- **BLOCKING POP**: Получает элемент из списка в блокирующем режиме; полезно для распределённых очередей сообщений.

**When to use:**

**Сценарии использования**

1. **Message Queues**: Упрощают операции очереди, например добавление сообщений в конец и обработку с начала списка.

2. **Collaborative List Management**: Позволяют участникам добавлять, удалять и обновлять элементы по мере надобности, похоже на Google Sheets в режиме реального времени.

3. **Activity Streams**: Ведут потоки активности пользователей или других данных в реальном времени.

4. **Search Engine Indexing**: Реализуют поисковый движок небольшого масштаба, где недавние запросы и проиндексированные термины можно держать в списках.

5. **Leaderboards**: Ведут очки игры или соревнования, где список поддерживается в порядке убывания очков.

6. **Partitioned Data**: Делят миллионы записей на меньшие куски, держа их в отдельных списках, и тем самым ускоряют выборку данных.

<summary>Можете ли вы describe the Pub/Sub model and how it's implemented in Redis?</summary>

### Можете ли вы describe the Pub/Sub model and how it's implemented in Redis?

**Definition:**

**Redis**, хотя его в первую очередь знают как **хранилище ключ-значение**, даёт гибкую функциональность **Publish-Subscribe** (Pub/Sub).

**How it works:**

**Обзор парадигмы**

В модели Pub/Sub издатели создают сообщения, а подписчики их получают и обрабатывают. Redis реализует этот шаблон через подход **на основе каналов**: каждое сообщение помечено именем канала, который служит очередью прямого получения для подписчиков.

Здесь издатель не шлёт сообщения конкретным подписчикам, как во многих других системах сообщений. Вместо этого подписчики **выражают интерес к темам**, или «каналам», и получают только сообщения, относящиеся к этим темам.

**Ключевые понятия**

- **Publisher**: Создаёт сообщения и отправляет их в связанные каналы.
- **Subscriber**: Регистрирует интерес к конкретным каналам и получает новые сообщения из этих каналов.

**Модель Redis PUB/SUB**

В модели Redis:

- Связью управляют три основных компонента:
  - **publications-container**, который хранит сообщения, связанные с каналами.
  - **subscription registry**, который хранит отношения канал-подписчик.
  - **management interface**, который организует каналы и подписчиков. Старые «заброшенные» каналы могут отбрасываться автоматически.

- Издатели и подписчики взаимодействуют с Redis через назначенные **наборы команд**.

**Наборы команд**

- **Publishers**: Используют команду `PUBLISH`, чтобы отправлять сообщения в конкретные каналы.
- **Subscribers**: Используют команды `SUBSCRIBE`, `UNSUBSCRIBE` и `PATTERN MATCHING`, чтобы управлять подписками на каналы и получением сообщений.

**Управление каналами**

- Подписчики через `SUBSCRIBE` добавляют интересующие каналы в реестр подписок.
- Через `UNSUBSCRIBE` или иным способом они могут отказаться от отдельных подписок.

Когда у **канала не остаётся подписчиков**, Redis удаляет его из реестра подписок.

**Рассылка сообщений**

Когда канал получает новое сообщение:

- Для **совпавших подписчиков канала**:
  - Redis отдаёт сообщение сразу.
- Для **последующих подписчиков**:
  - Redis доставляет сообщение, когда все текущие сообщения обработаны. Это сохраняет порядок сообщений.

**Подтемы**

**Subscription Lifecycle**: Последовательные состояния, которые проходят, когда подписчик взаимодействует с Redis.

**Message Exchange**: Шаги, которыми Redis передаёт сообщения от издателей к подписчикам.

**Channel Cleaning**: Механизм, которым Redis управляет неиспользуемыми — или «холодными» — каналами ради эффективности и гигиены системы.

**Examples:**

**Пример кода: Pub/Sub в Redis**

Вот код на Python:

```python
import redis
import time
from multiprocessing import Process

def publisher():
    publisher = redis.StrictRedis(host='localhost', port=6379, db=0)
    
    while True:
        publisher.publish('news', 'New News!')
        time.sleep(1)

def subscriber():
    subscriber = redis.StrictRedis(host='localhost', port=6379, db=0)
    pubsub = subscriber.pubsub()
    pubsub.subscribe('news')
    
    for message in pubsub.listen():
        print("Received:", message['data'])

# Start publisher and subscriber on separate processes
Process(target=publisher).start()
Process(target=subscriber).start()
```

### Что такое pipelining in Redis and when would you use it?

**Definition:**

**Pipelining** в **Redis** позволяет **отправить несколько команд одним сетевым запросом** и тем самым повышает производительность.

Сокращая круговые походы между клиентами и сервером, pipelining даёт лучшую эффективность, особенно там, где важны задержка или число запросов.

**How it works:**

**Ключевые компоненты**

- **Queue**: Команды, ожидающие ответа
- **TCP Connection**: Среда передачи данных
- **Client**: Инициатор команд в пайплайне
- **Server**: Экземпляр Redis, совместимый с pipelining.

**Преимущества**

- **Performance**: Меньше накладных расходов на круговые походы ускоряет общее выполнение.
- **Network Efficiency**: Реже взаимодействия по сети.
- **Atomicity**: Последовательности в пайплайне атомарны; либо выполняются все команды, либо ни одна.
- **Synchronization**: Pipelining сохраняет порядок команд.

**Недостатки**

- **Complexity**: Обрабатывать события не по порядку или незавершённые пайплайны сложнее.
- **Consistency**: Запоздалый или сбойный pipelining может повлиять на согласованность данных.

**When to use:**

Pipelining полезен в таких сценариях:

**Операции с большим объёмом данных**

Когда нужно выполнить много команд в Redis и выжать максимум эффективности.

**Управление задержкой**

Особенно в распределённых системах, где сетевая задержка может быть узким местом, pipelining даёт способ справляться с такими задержками.

**Кеширование**

В первую очередь, когда Redis используется как хранилище кеша, pipelining помогает поднять производительность и ускорить чтение данных.

**Examples:**

**Пример кода: базовый pipelining**

Вот код на Python:

```python
import redis

# Connect to Redis
r = redis.StrictRedis(host='localhost', port=6379, db=0)

# Initialize a pipeline
pipe = r.pipeline()

# Queue up commands
pipe.set('key1', 'value1').get('key1')

# Execute the pipeline
result_set, result_get = pipe.execute()
print(result_set, result_get)
```

<summary>Что такое Redis transaction and how do you create one?</summary>

### Что такое Redis transaction and how do you create one?

**Definition:**

Транзакция Redis выполняет группу команд как один изолированный шаг. Её открывают командой `MULTI`, команды ставят в очередь и запускают через `EXEC`.

**How it works:**

- `MULTI` отвечает `OK`. Следующие команды ставятся в очередь и отвечают `QUEUED`, а не выполняются сразу.
- `EXEC` выполняет очередь по порядку и возвращает по одному ответу на команду. Другой клиент не обслуживается посреди этого выполнения.
- `DISCARD` сбрасывает очередь. Если клиент отключился до `EXEC`, ни одна команда из очереди не выполняется.
- `WATCH key` — оптимистическая блокировка. Если наблюдаемый ключ изменился до `EXEC`, транзакция прерывается.

**When to use:**

Берите `MULTI`/`EXEC`, когда несколько команд нельзя перемежать с другими клиентами, например два счётчика надо увеличить вместе. `WATCH` нужен, если запись зависит от только что прочитанного значения. `EVAL` нужен, когда сервер должен выбрать ветку до записи.

**Examples:**

```redis
MULTI
INCR foo
INCR bar
EXEC
```

- [`MULTI`](https://redis.io/docs/latest/commands/multi/)

<summary>Объясните the concept of a stream in Redis.</summary>

### Объясните the concept of a stream in Redis.

**Definition:**

Поток (stream) — журнал только на добавление. У каждой записи есть id и список пар поле-значение в том порядке, в котором их добавили.

**How it works:**

- `XADD` — команда, которая дописывает запись. `*` просит Redis сгенерировать id.
- `XADD key MAXLEN ~ 1000 * field value` обрезает поток примерно до 1000 записей. `~` — приблизительная обрезка, она дешевле точного предела.
- `XREAD COUNT 100 BLOCK 300 STREAMS key $` ждёт до 300 миллисекунд новые записи. `$` значит «только записи, добавленные после этого вызова».
- `XREADGROUP GROUP group consumer ... STREAMS key >` читает записи, ещё не выданные этой группе потребителей. `>` означает ещё не доставленные записи.

**When to use:**

Поток нужен, когда воркеры делят сохраняемый журнал и подтверждают записи. Pub/Sub не хранит сообщение для подписчика, который был offline. Список — более простая очередь без id потока и групп потребителей.

**Examples:**

```redis
XADD race:italy * rider Castilla
XREAD COUNT 100 BLOCK 300 STREAMS race:france $
```

### Можете ли вы explain Redis's role as a message broker?

**Definition:**

Redis передаёт сообщения двумя описанными способами: Pub/Sub доставляет тем, кто подписан сейчас, а поток хранит журнал, который потребители читают позже.

**How it works:**

- `SUBSCRIBE channel [channel ...]` слушает сообщения на этих каналах.
- Опубликованное сообщение уходит текущим подписчикам. Оно не сохраняется как ключ для того, кто подключится потом.
- Поток хранит записи. `XADD` дописывает, а `XREADGROUP` даёт группе потребителей работу, которую ещё не выдавали.
- Список плюс `BLPOP` — более простая очередь: pop удаляет элемент, и упавший воркер может его потерять, если не переложить элемент через `BLMOVE`.

**When to use:**

Pub/Sub — для живой рассылки, когда пропуск сообщения допустим. Поток — когда воркер должен догнать журнал после offline. `BLMOVE` — когда очередь на списке должна парковать взятую в работу задачу во втором списке.

**Examples:**

```redis
SUBSCRIBE orders
XADD race:italy * rider Castilla
```

<summary>Что такое the limitations of Redis transactions?</summary>

### Что такое the limitations of Redis transactions?

**Definition:**

Транзакция изолирует команды только на время выполнения `EXEC`. Если команда падает во время выполнения, Redis не откатывает пакет.

**How it works:**

- Команды лежат в очереди до `EXEC`. Затем они сериализуются, и другой клиент не выполняется посреди пакета.
- Отката нет. На странице транзакций сказано, что откаты ударили бы по простоте и производительности Redis.
- Обрыв соединения до `EXEC` ничего не выполняет. После принятого `EXEC` команды выполняются. Сбой всё же может оставить частичную транзакцию в AOF; Redis тогда отказывается стартовать, а `redis-check-aof` может вырезать эту частичную транзакцию.
- `WATCH` прерывает транзакцию, если наблюдаемый ключ изменился. Это check-and-set, а не блокировка на всё время, пока команды лежали в очереди.
- То же правило без отката действует для скриптов Lua.

**When to use:**

Не считайте `MULTI`/`EXEC` транзакцией базы, которая отменяет уже выполненные команды пакета. Проверяйте каждый ответ `EXEC` или принимайте решение в скрипте Lua до записи.

**Examples:**

```redis
SET foo 1
MULTI
INCR foo
DISCARD
GET foo
```

**Sources:**

- [Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)
- [`DISCARD`](https://redis.io/docs/latest/commands/discard/)

### Как you create and manage indices in Redis?

**Definition:**

Redis не держит вторичный индекс внутри ключа, как таблица SQL. Индекс — это другой ключ, обычно множество или сортированное множество, либо загруженный поисковый модуль.

**How it works:**

- Запись лежит в своём ключе. Id добавляют в индексное множество через `SADD`.

- `MODULE LIST` показывает модуль `search`, если он загружен. Команды запроса тогда принадлежат модулю, а не базовым типам ключей.

**When to use:**

Множество — для точных тегов. Сортированное множество — когда индекс должен быть упорядочен. Поисковый модуль — когда поиска через `SINTER` и `ZRANGE` мало.

**Examples:**

### Обсудите Redis's role in session caching.

**Definition:**

Кеш сессий хранит данные сессии в Redis и удаляет их, когда истекает TTL, поэтому любой сервер приложения с id сессии может её прочитать.

**How it works:**

- Сессию пишут через `SET`. В скриптах фиксированного окна rate limit в документации `EXPIRE key seconds` ограничивает жизнь ключа; та же команда ограничивает сессию.
- Когда TTL доходит до нуля, следующее чтение — промах, и приложение считает сессию завершённой.
- Id сессии в cookie — суффикс ключа Redis. Запись пользователя, которая должна пережить выход, остаётся в долговременной базе.
- Репликация позволяет другому узлу Redis отдать сессию после failover. Persistence (`appendonly`) решает, сохранятся ли сессии после рестарта.

**When to use:**

Redis подходит, когда много процессов приложения делят короткоживущее состояние сессии. Долгоживущие данные аккаунта остаются в основной базе, а TTL убирает простаивающие сессии.

**Examples:**

```redis
SET session:abc "user-id=7"
EXPIRE session:abc 3600
```

### Можно ли Redis be used as a Primary dataBASE? Why or why not?

**Definition:**

Redis может быть системой записи для данных, которые помещаются в память, если включены persistence и репликация. Это по-прежнему сервер структур данных в памяти: рабочая копия в RAM, а диск — журнал восстановления.

**How it works:**

- RDB — снимок на момент времени. AOF дописывает команды записи и проигрывает их при старте. `appendonly yes` включает AOF.
- `appendfsync always` делает fsync на каждый дописанный пакет (медленно и надёжнее всего). `everysec` делает fsync раз в секунду и может потерять около секунды. `appendfsync no` не вызывает fsync.
- Если есть и AOF, и RDB, восстановление идёт по включённой схеме persistence. Сбой во время `EXEC` может оставить частичную транзакцию в AOF, пока её не поправит `redis-check-aof`.
- SQL-соединений нет. Согласованность нескольких ключей — это то, что вы кодируете через `MULTI`/`EXEC` или `EVAL`, и эти пути не откатываются.

**When to use:**

Redis как основное хранилище подходит для сессий, таблиц лидеров, очередей и других значений, которые моделируются его типами и помещаются в RAM. Дисковая база нужна, когда набор больше памяти или нужны произвольные реляционные запросы.

**Examples:**

```redis
CONFIG SET appendonly yes
```

### Как you configure Redis for optimal performance?

<summary>Как you scale Redis?</summary>

### Как you scale Redis?

**Definition:**

Redis масштабируют, давая одному primary больше памяти, добавляя реплики для чтения или шардируя через Redis Cluster. Cluster делит пространство ключей на 16384 хеш-слота.

**How it works:**

- Реплика обслуживает чтение. Запись по-прежнему принимает primary.
- Cluster не использует consistent hashing. Слот — это CRC16 ключа по модулю 16384. Каждый primary владеет частью этих слотов.
- Перенос слотов на новый узел или с узла, который нужно убрать, не требует остановки кластера.
- `redis-cli --cluster add-node <new> <existing>` присоединяет узел. `--cluster-slave` присоединяет его как реплику primary, у которого реплик меньше.

**When to use:**

Один primary плюс реплики достаточны, когда запись и набор данных помещаются в один процесс. Cluster нужен, когда слоты надо разделить между несколькими primary.

**Examples:**

```redis
redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000 --cluster-slave
```

### Объясните how Redis Sentinel works.

<summary>Что такое Redis Cluster and how does it improve Redis' Scalability and availability?</summary>

### Что такое Redis Cluster and how does it improve Redis' Scalability and availability?

**Definition:**

Redis Cluster шардирует ключи по primary и держит реплики, чтобы заменить упавший primary. Ёмкость растёт переносом хеш-слотов без остановки кластера.

**How it works:**

- Хеш-слотов 16384. Слот ключа — CRC16(key) по модулю 16384.
- Пример из документации: узел A владеет 0–5500, узел B — 5501–11000, узел C — 11001–16383.
- Добавление узла D — это перенос части слотов с A, B и C на D. Удаление A — перенос слотов A на B и C, затем вывод пустого узла.
- `CLUSTER NODES` показывает id, роль и диапазон слотов каждого узла. `CLUSTER FAILOVER` на реплике принудительно делает ручной failover её primary. `FORCE` не советуется с primary. `TAKEOVER` забирает роль без обычных проверок.

**When to use:**

Cluster нужен, когда один primary не вмещает рабочий набор или запись. Sentinel — когда нужен только failover, а данные остаются на одном primary.

**Examples:**

```redis
CLUSTER NODES
CLUSTER FAILOVER
```

**Sources:**

- [Scale with Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)

### Какие стратегии can you use to optimize memory usage in Redis?

**Definition:**

Память — это размер ключей плюс накладные расходы. Redis может вытеснять ключи, крупные значения можно дробить, а цену одного ключа можно посмотреть.

<summary>Можете ли вы explain the eviction policies in Redis?</summary>

### Можете ли вы explain the eviction policies in Redis?

**Definition:**

Когда занятая память превышает `maxmemory`, Redis вытесняет ключи по `maxmemory-policy` или отказывает в записи.

**How it works:**

- `noeviction`: ничего не вытесняется. Команды, которые добавили бы данные, возвращают ошибку. В наборе с репликами это относится к primary. Чтение существующих данных работает.
- `allkeys-lru` вытесняет наименее недавно использованные ключи. `allkeys-lfu` — наименее часто использованные. `allkeys-lrm` — наименее недавно изменённые. `allkeys-random` — случайные.
- `volatile-lru`, `volatile-lfu`, `volatile-lrm` и `volatile-random` делают то же среди ключей с TTL. `volatile-ttl` вытесняет ключ с наименьшим оставшимся TTL.
- Если ни у одного ключа нет TTL, любая политика `volatile-*` ведёт себя как `noeviction`.
- Руководство по вытеснению по умолчанию советует `allkeys-lru`, когда небольшая доля ключей гораздо горячее остальных.

**When to use:**

`allkeys-lru` — для обычного кеша. `allkeys-lrm` — когда чтение стабильных данных надо сохранить, а неизменённые ключи можно убрать. `volatile-ttl` — когда приложение само помечает жертв коротким TTL. `noeviction` — когда терять ключ нельзя.

**Examples:**

```redis
maxmemory 2mb
maxmemory-policy allkeys-lru
```

### Что такое the max memory setting in Redis?

**Definition:**

`maxmemory` — настроенный потолок памяти, которую Redis тратит на набор данных. Выше потолка поведение задаёт `maxmemory-policy`.

**How it works:**

- Пример кеша в руководстве по конфигурации: `maxmemory 2mb` и `maxmemory-policy allkeys-lru`.
- Руководство по администрированию велит вычесть из свободной RAM накладные расходы Redis, буферы и фрагментацию. Если кажется, что свободно 10 GB, оно предлагает попробовать 8 или 9 GB.
- `INFO memory` сообщает `mem_not_counted_for_evict` — память буферов, которую надо оставить вне бюджета данных.
- При `noeviction` переход за предел не удаляет ключи. Запись, которой нужна ещё память, завершается ошибкой; чтение продолжается.
- Страница вытеснения отдельно говорит, что запас свободной RAM не обязателен именно для политики `noeviction`. Предел всё равно задают, чтобы Redis вернул ошибку, а не умер, когда на хосте почти не осталось памяти.

**When to use:**

`maxmemory` ставят на каждом кеше и на каждом хосте, где ОС иначе позволит Redis расти до падения машины. В контейнере предел ставят ниже лимита контейнера.

**Examples:**

```redis
CONFIG SET maxmemory 2mb
CONFIG SET maxmemory-policy noeviction
```

<summary>Как Redis handle backups?</summary>

### Как Redis handle backups?

**Definition:**

Резервная копия — это копия снимка RDB или файлов AOF, снятая пока Redis обслуживает трафик или после явного сохранения.

**How it works:**

- Снимок RDB делает fork. Дочерний процесс пишет временный RDB и затем заменяет старый файл. `save 60 1000` в руководстве по persistence значит: сбросить данные, если за 60 секунд изменилось хотя бы 1000 ключей.
- `BGSAVE` запрашивает снимок в фоне. `SAVE` делает снимок на переднем плане; в заметках по обновлению `redis-cli SAVE` обновляет `dump.rdb`.
- При AOF файлы называются вроде `appendonly.aof.*` в каталоге append-only. `CONFIG SET appendonly yes` включает AOF на работающем сервере.
- Готовый `dump.rdb` или каталог AOF копируют на хранилище вне хоста Redis. Заметки Redis 2.0 в руководстве по persistence велят скопировать последний `dump.rdb` в безопасное место перед рискованным изменением.

**When to use:**

`BGSAVE` или автоматические правила `save` дают снимок на момент времени, который можно унести с машины. AOF нужен, когда важны и записи после последнего снимка. Проверяйте, что копия действительно загружается.

**Examples:**

```redis
BGSAVE
SAVE
```

<summary>Какие security features предлагает Redis?</summary>

### Какие security features предлагает Redis?

**Definition:**

Безопасность Redis — это изоляция сети, protected mode, аутентификация, TLS и ACL, которые ограничивают команды и ключи. Сам по себе Redis небезопасно выставлять в открытую сеть.

**How it works:**

- Страница безопасности описывает protected mode, аутентификацию, TLS и запрет отдельных команд.

<summary>Как you handle reconnection logic when the Redis server becomes unavailable?</summary>

### Как you handle reconnection logic when the Redis server becomes unavailable?

**Definition:**

`node-redis` по умолчанию переподключается. Команды, отправленные пока сокет лежит, ставятся в очередь и уходят, когда соединение вернётся, из-за чего запись может выполниться дважды.

**How it works:**

- Руководство по production говорит, что неидемпотентная команда может изменить данные и остаться в очереди offline. После переподключения клиент посылает её снова.
- `disableOfflineQueue: true` ставят на клиенте, который не должен повторять команды. Невыполненные команды отбрасываются, а не копятся.
- Отдельное соединение с выключенной очередью используют, когда повторять небезопасно только часть команд.
- Обработчик `error` оставляют. После failover Sentinel снова спрашивают `SENTINEL get-master-addr-by-name` или берут клиент, который следит за Sentinel.

**When to use:**

Очередь по умолчанию оставляют для идемпотентного чтения, если короткий обрыв должен быть незаметен. Её выключают для увеличений, pop из списка и любой записи, которую нельзя безопасно выполнить дважды.

**Examples:**

```javascript
const client = createClient({
  disableOfflineQueue: true
});
```

### Обсудите how Redis can be used in conjunction with a dataBASE.

**Definition:**

**When to use:**

Redis — для данных, которые горячие, общие и либо восстановимы, либо короткоживущие. База — для данных, которые надо запрашивать произвольно и сохранить, если Redis пуст.


<summary>Что такое the trade-offs of using Redis vs. traditional dataBASEs?</summary>

### Что такое the trade-offs of using Redis vs. traditional dataBASEs?

**Definition:**

Redis держит рабочий набор в памяти и даёт конкретные типы данных и атомарные команды. Традиционная база держит данные на диске и отвечает на декларативные запросы.

**How it works:**

- Команды Redis вроде `INCR`, `ZADD` и `XADD` работают с одним ключом (или с пакетом скрипта / `MULTI`) без планировщика SQL.
- Долговечность необязательна: RDB может потерять записи после последнего снимка; `appendfsync everysec` может потерять около секунды; `appendfsync always` делает fsync на каждый пакет дописывания и гораздо медленнее.

- Предел ёмкости — память, если вы не вытесняете. `noeviction` возвращает ошибку вместо удаления ключей. Дисковая база растёт вместе с диском.
- Репликация и Sentinel или Cluster добавляют доступность. Они следуют правилам Redis про отставание и хеш-слоты, а не многострочным транзакциям.

**When to use:**

Redis выбирают, когда доступ — это ключ и операция над типом, а набор помещается в RAM. Традиционную базу выбирают, когда нужны долговечные таблицы больше памяти и произвольные запросы.

**Examples:**

```redis

```

### Redis Persistence and Durability

<details>
<summary>Какие mechanisms Redis предоставляет для durability?</summary>

### Какие mechanisms Redis предоставляет для durability?

**Definition:**

Долговечность необязательна и складывается из снимков RDB, файла только на добавление и репликации на другой узел.

**How it works:**

- RDB: Redis делает fork, дочерний процесс пишет временный файл, и этот файл заменяет прежний `dump.rdb`.
- AOF: `appendonly yes` журналирует каждую команду записи и проигрывает журнал при старте.
- `appendfsync` выбирает, как часто журнал сбрасывается через fsync: `always`, `everysec` или `no`.
- `REPLICAOF host port` копирует набор на реплику. Реплика не является устойчивой дисковой копией primary, если сама реплика тоже не пишет persistence.
- `MULTI`/`EXEC` пишется в AOF одним вызовом `write(2)`. Жёсткий сбой всё же может оставить частичную транзакцию; `redis-check-aof` удаляет её, чтобы сервер смог стартовать.

**When to use:**

AOF включают, когда потеря последнего снимка слишком велика. Репликацию добавляют, когда нужен ещё и другой хост. Persistence выключают только у чистого кеша, который можно собрать заново.

**Examples:**

```redis
CONFIG SET appendonly yes
```

**Sources:**

- [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- [Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)
- [Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)

<details>
<summary>Как you control when Redis writes data to disk?</summary>

### Как you control when Redis writes data to disk?

**Definition:**

Запись на диск задают правила RDB `save` и `appendfsync` для AOF. Снимок можно запросить и явно через `BGSAVE` или `SAVE`.

**How it works:**

- `save 60 1000` пишет RDB, если за 60 секунд изменилось хотя бы 1000 ключей. Дочерний процесс пишет файл после fork.
- `appendfsync always` делает fsync каждый раз, когда команды дописываются. Страница называет это очень медленным и очень надёжным. fsync происходит один раз на пакет команд от клиентов или конвейера, до отправки ответов.
- `appendfsync everysec` делает fsync раз в секунду. Это описано как достаточно быстрое, и можно потерять одну секунду данных.
- `appendfsync no` никогда не вызывает fsync.
- `CONFIG SET appendonly yes` включает AOF на работающем сервере.

**When to use:**

`everysec` — когда потеря секунды допустима. `always` — когда эта секунда недопустима и можно заплатить задержкой. Точки `save` для RDB — когда нужен компактный снимок, а не журнал команд.

**Examples:**

```redis
CONFIG SET appendonly yes
```

**Sources:**

- [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- [`CONFIG SET`](https://redis.io/docs/latest/commands/config-set/)
- [`BGSAVE`](https://redis.io/docs/latest/commands/bgsave/)

<details>
<summary>Сравните the pros and cons of RDB and AOF.</summary>

### Сравните the pros and cons of RDB and AOF.

**Definition:**

RDB — компактный снимок на момент времени, который пишет дочерний процесс после fork. AOF — журнал команд записи, который проигрывается при старте.

**How it works:**

- Плюсы RDB: один двоичный файл, и fork позволяет родителю обслуживать клиентов, пока дочерний процесс пишет. Теряются все записи после последнего успешного снимка.
- Плюсы AOF: `appendfsync always` сохраняет каждый дописанный пакет, а `everysec` ограничивает потерю примерно одной секундой. Файл — журнал команд, поэтому Redis его переписывает (в руководстве по persistence для создания AOF указан `BGREWRITEAOF`).
- Цена AOF: больше дискового ввода-вывода, особенно с `always`. Сбой может оставить неполный пакет `MULTI`/`EXEC`; Redis завершается при старте, пока `redis-check-aof` его не удалит.
- Позиция руководства: одних снимков мало для долговечности. Можно включить оба. `CONFIG SET appendonly yes` запускает AOF без рестарта.

**When to use:**

RDB предпочтителен, когда скорость рестарта и небольшие копии важнее последних секунд записи. AOF, обычно `everysec`, — когда эти записи должны пережить сбой. Оба включают, когда нужен и быстрый снимок, и более плотный журнал.

**Examples:**

```redis
SAVE
CONFIG SET appendonly yes
```

- [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- [`SAVE`](https://redis.io/docs/latest/commands/save/)
- [Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)

### Как you force a Redis data dump to disk?

**Definition:**

`SAVE` пишет снимок RDB на переднем плане. `BGSAVE` пишет его в дочернем процессе, и сервер может продолжать обслуживание.

**How it works:**

- В заметках по обновлению запускают `redis-cli SAVE`, чтобы создать или обновить `dump.rdb` в каталоге данных.
- Снимок делает fork: дочерний процесс пишет временный RDB и заменяет старый файл, когда заканчивает.
- Если вместо этого нужен AOF, `CONFIG SET appendonly yes` его запускает. Руководство по persistence также использует `BGREWRITEAOF`, когда вы создаёте append-only файл.
- `SAVE` на переднем плане блокирует обработку команд, пока дамп не закончится. Его берут, когда такая пауза допустима, например перед управляемой остановкой.

**Examples:**

```redis
SAVE
BGSAVE
```

<summary>Какие стратегии are involved in ensuring data durability in Redis?</summary>

### Какие стратегии are involved in ensuring data durability in Redis?

**Definition:**

Долговечность — это выбор, сколько данных можно потерять: интервал снимков, политика fsync для AOF, реплика и копия файлов вне хоста.

**How it works:**

- RDB настраивают правилами `save` или вызывают `BGSAVE` перед рискованной операцией. `dump.rdb` копируют в другое место; руководство по persistence велит положить эту копию в безопасное место.
- AOF включают через `appendonly yes`. Выбирают `appendfsync always` или `everysec`. `no` не вызывает fsync.
- Перед рестартом дожидаются, пока перезапись AOF простаивает: `INFO persistence`, где `aof_rewrite_in_progress` и `aof_rewrite_scheduled` равны `0`, а `aof_last_bgrewrite_status` — ok. Эта проверка есть в руководстве по persistence.
- Реплицируют через `REPLICAOF`, чтобы набор был на втором хосте. На этом хосте тоже включают persistence, если реплика должна пережить сбой сама.
- Если Redis не стартует, потому что транзакция в AOF оборвана, запускают `redis-check-aof`, как описано на странице транзакций.

**When to use:**

Политику fsync подбирают под допустимую потерю. RDB или AOF уносят с машины. Реплика на том же диске не спасает от отказа этого диска.

**Examples:**

```redis
CONFIG SET appendonly yes
INFO persistence
```

### Как you troubleshoot latency issues in Redis?

**Definition:**

Разбор задержки начинают с `LATENCY DOCTOR` и `SLOWLOG GET`, затем смотрят память и fork, на которые указывает вывод doctor.

**How it works:**

- `SLOWLOG GET` показывает команды, которые были медленными, например `KEYS` на большом пространстве ключей.
- Тот же отчёт говорит, что удаление, истечение или вытеснение большого объекта блокирует Redis. Такой объект делят.
- Перезапись RDB или AOF делает fork. На инстансе с тяжёлой записью copy-on-write может поднять память почти до удвоенного обычного размера и застопорить хост.
- Руководство по администрированию также отключает Transparent Huge Pages и ставит `vm.overcommit_memory = 1`, чтобы фоновые сохранения не боролись с ядром.

**Examples:**

```redis

SLOWLOG GET 16
CONFIG SET slowlog-log-slower-than 1000
```

### Что такое some best practices for error handling in Redis clients?

**Definition:**

<summary>Как you recover a Redis instance from a failure?</summary>

### Как you recover a Redis instance from a failure?

**Definition:**

Восстановление — это либо рестарт с RDB и AOF, либо повышение реплики. Оборванную транзакцию в AOF чинят до того, как сервер согласится стартовать.

**How it works:**

- При старте Redis загружает `dump.rdb` и, если включён `appendonly`, проигрывает AOF.
- Если сбой разрезал группу `MULTI`/`EXEC` в AOF, Redis завершается с ошибкой. `redis-check-aof` удаляет эту частичную транзакцию, чтобы сервер смог стартовать. Это описано на странице транзакций.
- `REPLICAOF NO ONE` на реплике повышает её, когда primary исчез и failover делают вручную.
- С Sentinel клиенты вызывают `SENTINEL get-master-addr-by-name` и берут адрес, который Sentinel уже повысил.
- В Cluster реплика забирает слоты primary. `CLUSTER FAILOVER` на реплике делает это вручную.

**When to use:**

Повышенная реплика предпочтительна, когда хост мёртв, а реплика достаточно догнала журнал. Рестарт с AOF предпочтителен, когда диск того же хоста цел.

**Examples:**

```redis
REPLICAOF NO ONE
SENTINEL get-master-addr-by-name mymaster
```

### Что такое meant by "hot" keys in Redis and how do you deal with them?

**Definition:**

Горячий ключ — это ключ, на который приходится несоразмерная доля команд. Так как выполнение команд сосредоточено на нём, он ограничивает пропускную способность и виден как задержка.

**How it works:**

- `SLOWLOG GET` показывает команды, которые выполнялись слишком долго. Горячий ключ часто оказывается там, когда значение огромное (заметки по разбору проблем велят смотреть чтения вроде `HGETALL`) или когда все клиенты бьют в один ключ.
- `LATENCY DOCTOR` указывает на большие объекты, которые блокируют Redis при удалении, истечении или вытеснении. Значение делят на меньшие ключи.
- `MEMORY USAGE key` оценивает размер именно этого ключа.
- Чтение горячего ключа можно перенести на реплику (`REPLICAOF`, реплика по умолчанию только для чтения). Запись всё равно попадает на primary, поэтому реплики не лечат ключ, горячий на запись.
- В Cluster один ключ — один слот: CRC16(key) по модулю 16384. Весь трафик этого ключа остаётся на одном узле.

**When to use:**

Крупное значение делят и, если нагрузка позволяет, разносят запись по нескольким ключам. Реплику используют только для чтения.

**Examples:**

```redis
MEMORY USAGE hot:key
SLOWLOG GET 16
```

<summary>Как Redis be used for rate limiting?</summary>

### Как Redis be used for rate limiting?

**Definition:**

Ограничитель частоты считает запросы в Redis по ключу вроде id пользователя и окна времени и отклоняет вызов, когда счёт превышает предел.

**How it works:**

- Фиксированное окно в документации использует `INCR`. Если результат `1`, ставится `EXPIRE`. Если счёт выше предела, запрос отклоняют. Скрипт Lua делает `INCR`, `EXPIRE` и проверку `PTTL` в одном `EVAL`, чтобы шаги не перемежались.
- Вариант на списках на странице `INCR` использует `LLEN`, затем `RPUSH` плюс `EXPIRE` внутри `MULTI`/`EXEC`, если ключа ещё нет, или `RPUSHX`, если он уже есть.
- Скользящее окно в руководстве по rate limit хранит каждое попадание в сортированном множестве: `ZREMRANGEBYSCORE` убирает старые счета, `ZCARD` считает оставшиеся, `ZADD` записывает новое попадание.
- `INCREX` с `UBOUND` и `EX` описан как атомарное увеличение, которое ещё и ограничивает счётчик.

**When to use:**

Фиксированное окно — когда хватает счётчика на минуту. Окно на сортированном множестве — когда предел должен скользить по времени. Проверку кладут в `EVAL`, чтобы `INCR` и `EXPIRE` не разошлись между клиентами.

**Examples:**

```redis
INCR rate_limit:user:42
EXPIRE rate_limit:user:42 60
```

**Sources:**

- [`INCR`](https://redis.io/docs/latest/commands/incr/)
- [Scripting with Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)

<summary>Что бы вы be an ideal use case for Redis queues?</summary>

### Что бы вы be an ideal use case for Redis queues?

**Definition:**

Очередь Redis — это список или поток задач, которые воркеры забирают по одной. Идеальная задача короткая, её можно повторить, и ей не нужна SQL-транзакция вместе с остальными бизнес-данными.

**How it works:**

- `BLPOP` ждёт, пока производитель добавит элемент через `LPUSH` или `RPUSH`. Ждущий клиент не блокирует сервер.
- `BLMOVE source destination LEFT|RIGHT LEFT|RIGHT timeout` снимает задачу из рабочего списка и кладёт в список обработки, поэтому сбой не ограничивается удалением задачи.
- Поток — более сильный журнал: `XADD` дописывает, `XREADGROUP` выдаёт одному потребителю, и запись остаётся, пока группа с ней не закончит.
- Pub/Sub — плохая очередь: отключённые подписчики пропускают сообщение.

**When to use:**

Список с `BLMOVE` — для простой рабочей очереди. Поток — когда нужны группы потребителей и сохраняемый журнал. Pub/Sub не используют, если воркер может быть offline.

**Examples:**

```redis
BLMOVE jobs processing LEFT RIGHT 30
```

### Как бы вы use Redis for full-page cache?

### Как you handle Redis persistence in cloud environments?

**Definition:**

### Как you add or remove nodes in a Redis Cluster?

**Definition:**

Узел добавляют, затем переносят на него хеш-слоты. Узел удаляют только после того, как его слоты живут где-то ещё. На время переноса кластер продолжает обслуживание.

**How it works:**

- Слотов 16384. Добавление узла D — перенос части слотов с текущих primary на D. Удаление узла A — перенос слотов A на оставшиеся узлы и вывод A, когда он пуст.

- `CLUSTER SETSLOT` — команда, которой в документации описан перенос одного слота с узла-источника на узел-назначение.

**When to use:**

Реплику добавляют через `--cluster-slave`, когда нужна ёмкость для failover. Primary добавляют и переносят слоты, когда нужны память или запись. Перед удалением узел опустошают.

**Examples:**

```redis
redis-cli --cluster add-node 127.0.0.1:7006 127.0.0.1:7000

```

<summary>Объясните how failover works in a Redis Cluster.</summary>

### Объясните how failover works in a Redis Cluster.

**Definition:**

Если primary падает, одна из его реплик повышается и забирает хеш-слоты этого primary. Клиенты затем ходят за этими слотами на новый primary.

**How it works:**

- В тесте отказа из руководства по масштабированию останавливают primary и затем смотрят `CLUSTER NODES`: реплика старого primary указана как master для этого диапазона слотов.
- На время переключения клиенты видят ошибки по слотам, которые переезжают. В том же тесте есть всплеск ошибок чтения и записи, после чего команды снова проходят.
- `CLUSTER FAILOVER` на реплике принудительно делает ручной failover её primary. `FORCE` не советуется с primary. `TAKEOVER` забирает роль без обычных проверок.
- Реплика без своих слотов не отдаёт эти ключи, пока её не повысят. `CLUSTER NODES` показывает новую роль и диапазон слотов.

**When to use:**

Хотя бы одна реплика на primary нужна, если смерть узла должна повышать реплику сама. `CLUSTER FAILOVER` используют, когда primary переносят намеренно, например перед обновлением.

**Examples:**

```redis
CLUSTER FAILOVER
CLUSTER NODES
```

**Sources:**

### Обсудите the challenges of running a Redis Cluster in production.

**Definition:**

Cluster разносит слоты по узлам, поэтому операции, которые предполагают одно пространство ключей, и отказы одного узла становятся обычной эксплуатацией.

**How it works:**

- Слот ключа — CRC16(key) по модулю 16384. Команда, которая трогает ключи в разных слотах, — многоключевая операция, и кластер должен уметь её направить; заметки о блокирующих командах говорят, что в кластере поведение может отличаться, и отсылают к странице многоключевых операций.
- Решардинг кластер не останавливает, но тест failover показывает окно клиентских ошибок, пока primary лежит.
- Горячий ключ остаётся в одном слоте и на одном узле. Реплики не принимают его запись.
- Память на fork по-прежнему нужна каждому primary, который пишет RDB или AOF. Каждый узел считают с copy-on-write, а не только сумму данных.
- `KEYS` по-прежнему O(N). В кластере шаблон, который попадает в один слот, может ограничить поиск этим слотом; широкий шаблон — нет.

**When to use:**

Cluster берут, когда шардировать необходимо. Связанные ключи держат в одном слоте, только если клиент и команды под это написаны. Реплики нужны, чтобы отказ узла повышал реплику, а не терял эти слоты.

**Examples:**


<summary>Как you SHArd data in a Redis Cluster?</summary>

### Как you SHArd data in a Redis Cluster?

**Definition:**

Redis Cluster шардирует по хеш-слотам. Каждый ключ принадлежит одному из 16384 слотов, и каждый primary владеет частью этих слотов.

**How it works:**

- Слот — CRC16 ключа по модулю 16384. Это не consistent hashing.
- Пример из руководства по масштабированию: узел A держит слоты 0–5500, B — 5501–11000, C — 11001–16383.
- Владение меняют переносом слотов. Новый узел получает часть слотов. Удаляемый узел отдаёт свои слоты. Кластер останавливать не нужно.
- `CLUSTER NODES` печатает диапазон, который обслуживает каждый primary, например `0-5959`.
- Один ключ нельзя разрезать по узлам. Горячий ключ — это горячий слот.

**When to use:**

Кластеру отдают размещение ключей, когда доступ распределён. Слоты переносят, когда узкое место — память или CPU одного узла. Один занятый ключ горизонтально не масштабируется.

**Examples:**

```redis
CLUSTER NODES
```

Идиоматичный Redis использует тип под способ доступа, TTL или `maxmemory`, когда данные — кеш, и скрипт или `MULTI`, когда несколько команд должны остаться вместе.

**How it works:**

- Счётчики: `INCR`. Уникальные элементы: `SADD`. Ранжированные элементы: `ZADD` и `ZRANGE`. Биты: `SETBIT`. Журналы: `XADD`.
- Приблизительные уникальные: `PFADD` / `PFCOUNT`, а не огромное множество.
- Очереди: `BLMOVE` или поток с `XREADGROUP`, не Pub/Sub, когда воркер не должен пропустить задачу.
- Клиент один на процесс (`createClient` / `connect`). Пакет склеивают конвейером или `MULTI`, а не круговым путём на каждый `SET`.
- Обходят ключи через `SCAN`, не через `KEYS`, в коде приложения.

**Examples:**

```redis
INCR page:views
SADD article:9:tags redis
SCAN 0 MATCH session:* COUNT 100
```

### Как common design patterns apply to Redis usage?

**Definition:**

Обычные шаблоны — кеш рядом с базой, счётчик, очередь и pub/sub для сигналов. Каждый из них ложится на документированную команду, а не на таблицу.

**How it works:**

- Cache-aside: читают Redis, при промахе читают базу и делают `SET` плюс `EXPIRE`. `allkeys-lru` выбирают, когда кеш должен ограничивать память, а не TTL.
- Rate limit: `INCR` и `EXPIRE`, лучше внутри `EVAL`.
- Очередь: `BLPOP` или `BLMOVE`. Журнал работ: `XADD` и `XREADGROUP`.
- Рассылка, которая может терять сообщения: `SUBSCRIBE`.
- Оптимистическое обновление: `WATCH`, затем `MULTI` / `SET` / `EXEC`, как в примере транзакций Node.js. Если `EXEC` прервался, чтение повторяют.

**When to use:**

Шаблон выбирают по допустимому сбою: кеш может промахнуться, очередь не должна, Pub/Sub может потерять сообщение.

**Examples:**

```redis
WATCH shellpath
MULTI
SET shellpath /usr/syscmds/:/usr/mycmds/
EXEC
```

### Как you test software that relies on Redis?

**Definition:**

Тестовый процесс направляют на Redis, который можно очистить, выполняют настоящие команды и проверяют и успешный ответ, и те ошибки, которые Redis действительно возвращает.

**When to use:**

Интеграционные тесты гоняют против Redis для команд, TTL и `MULTI`. Чистые модульные тесты оставляют на своих функциях, подставляя клиент, которым вы управляете, и всё равно держат один тест на настоящий сервер.

<summary>Объясните how to use Redis with asynchronous programming models.</summary>

### Объясните how to use Redis with asynchronous programming models.

**Definition:**

Клиент Node.js асинхронный: `connect`, `set` и `get` возвращают promise, а сокет переподключается, не блокируя цикл событий на круговом пути к Redis.

**How it works:**

- `await client.connect()` вызывают до команд. `error` обрабатывают, чтобы отказ сокета не всплыл только как необработанное исключение.
- `client.multi().set(...).exec()` возвращает promise. Пример транзакций ждёт этот promise и обрабатывает отказ, когда `WATCH` прерывает пакет.
- Пока соединения нет, команды стоят в очереди, если `disableOfflineQueue` не true. Команды из очереди завершаются позже, и это может удивить async-вызывающего, который уже пошёл дальше.
- Блокирующие команды сервера вроде `BLPOP` блокируют это соединение, не сервер Redis. Воркеру дают отдельное соединение, чтобы путь запроса его не делил.

**When to use:**

На пути запроса каждую команду ждут через await. `BLPOP` ставят на своё соединение. Очередь offline выключают для записей, которые async-поток не должен выполнить дважды.

**Examples:**

```javascript
await client.connect();
const value = await client.get('foo');
await client.multi().set('shellpath', newPath).exec();
```

<summary>Обсудите the pros and cons of using Redis as a caching layer.</summary>

### Обсудите the pros and cons of using Redis as a caching layer.

**Definition:**

Кеш Redis избегает более медленного чтения базы для горячих ключей. Он может отдать устаревшие данные, вытеснить ключ, который ещё нужен, или отказать в записи, когда память кончилась.

**How it works:**

- Плюсы: `GET` / `SET` идут из памяти. `EXPIRE` ограничивает устаревание. `allkeys-lru` вытесняет холодные ключи без TTL на каждом. `INFO stats` отдаёт `keyspace_hits` и `keyspace_misses`.
- Минусы: попадание может быть устаревшим, пока вы не удалите ключ или не кончится TTL. Политики `volatile-*` ничего не делают, если вы забыли TTL; тогда они ведут себя как `noeviction`.
- `noeviction` превращает кеш в ошибки, как только достигнут `maxmemory`. Чтение ключей, которые ещё на месте, работает.
- Вытеснение или истечение очень большой закешированной страницы блокирует сервер. На это указывает `LATENCY DOCTOR`.
- Persistence и репликация для кеша, который можно собрать заново, необязательны. Они стоят памяти на fork и отставания.

**When to use:**

Redis как кеш используют, когда промах — правильное поведение и значение можно собрать заново. Не используйте его как единственную копию, если AOF или RDB не выбраны явно.

**Examples:**

```redis
maxmemory 2mb
maxmemory-policy allkeys-lru
```

- [`INFO`](https://redis.io/docs/latest/commands/info/)

<summary>Как you monitor key events in Redis?</summary>

### Как you monitor key events in Redis?

**Definition:**

Уведомления пространства ключей публикуют сообщения Pub/Sub, когда ключ меняется. По умолчанию они выключены, потому что тратят CPU.

**How it works:**

- Их включают через `CONFIG SET notify-keyspace-events` или той же директивой в `redis.conf`. Пустая строка их выключает.
- `K` публикует события keyspace (`__keyspace@<db>__`). `E` публикует события keyevent (`__keyevent@<db>__`). Нужен хотя бы один из `K` или `E`, иначе ничего не доставляется.
- `A` — псевдоним `g$lshztdxea`. Строка `KEA` включает большинство событий. `x` — истечение, `e` — вытеснение. `m`, `n`, `o` и `c` в `A` не входят.
- `PSUBSCRIBE __key*__:*` их получает. В документации перед этой подпиской стоит `config set notify-keyspace-events KEA`.
- Уведомления — не журнал долговечности. Отключённый подписчик пропускает события. Поток — журнал, если события надо сохранить.

**When to use:**

`KEA` включают, когда приложение должно реагировать на удаления и истечения. Функцию оставляют выключенной, когда никто не подписан. Поток используют, если само событие надо сохранить.

**Examples:**

```redis
CONFIG SET notify-keyspace-events KEA
PSUBSCRIBE __key*__:*
```

### Как you CAPture and analyze Redis logs?

**Definition:**

У Redis две разные записи: вывод doctor и info и slow log в памяти. Slow log — не текстовый файл, который читают через tail.

**How it works:**

**Examples:**

```redis
SLOWLOG GET 32
INFO persistence
LATENCY DOCTOR
```

<summary>Что можно диагностировать по Redis slow query logs?</summary>

### Что можно диагностировать по Redis slow query logs?

**Definition:**

Slow log перечисляет команды, которые выполнялись дольше `slowlog-log-slower-than`. Он показывает, на что Redis потратил время сам, а не время в сети до начала команды.

**How it works:**

- `SLOWLOG GET n` — команда, которой заметки по разбору проблем ищут медленные команды вроде `KEYS`.
- `LATENCY DOCTOR` связывает оба источника: если монитор latency видит всплески, а slow log пуст, порог выше всплесков. В примере совет — `CONFIG SET slowlog-log-slower-than 1000`.
- Медленный `KEYS` имеет сложность O(N) по числу ключей. Страница команды говорит, что на большой базе он может испортить производительность, и он для отладки, не для кода приложения.
- Крупные удаления тоже блокируют сервер. Текст doctor просит дробить большие объекты, когда задержка — это delete, expire или eviction.
- `ACL CAT dangerous` включает `slowlog`, поэтому урезанный пользователь приложения может не иметь права его читать.

**When to use:**

Slow log читают, когда `LATENCY DOCTOR` упоминает команды. Если doctor видит всплески, а slow log нет, сначала снижают порог и только потом делают вывод, что виновата сеть.

**Examples:**

```redis
SLOWLOG GET 10
CONFIG SET slowlog-log-slower-than 1000
```

**Sources:**

- [`SLOWLOG GET`](https://redis.io/docs/latest/commands/slowlog-get/)
- [`LATENCY DOCTOR`](https://redis.io/docs/latest/commands/latency-doctor/)
- [`KEYS`](https://redis.io/docs/latest/commands/keys/)

<summary>Как monitoring differ in a Redis Cluster environment?</summary>

### Как monitoring differ in a Redis Cluster environment?

**Definition:**

Каждый узел кластера — процесс Redis со своей памятью, своим slow log и своим persistence. Один `INFO` не описывает остальные узлы.

**How it works:**

- `CLUSTER NODES` — карта: id узла, `master` или `slave` и диапазон слотов вроде `0-5959` или `11423-16383`.
- `INFO`, `SLOWLOG GET`, `LATENCY DOCTOR` и `MEMORY USAGE` запускают на узле, который владеет ключом. Слот горячего ключа не переезжает от того, что вы посмотрели другой узел.
- Во время failover руководство по масштабированию показывает период клиентских ошибок, затем реплику как master для старого диапазона. Смену роли смотрят в `CLUSTER NODES`.
- `BGSAVE` и `INFO persistence` относятся к одному процессу. Один узел может переписывать AOF, пока другой простаивает.
- `SCAN` на одном узле видит ключи этого узла. Это не список ключей всего кластера.

**When to use:**

Снимают метрики с каждого узла. Тревогу ставят на primary с нулём реплик и на `maxmemory` любого одного узла, а не на среднее по кластеру.

**Examples:**

```redis
CLUSTER NODES
INFO memory
```

<summary>Как Redis maintain high availability?</summary>

### Как Redis maintain high availability?

**Definition:**

Высокая доступность — это реплика, которая может стать primary. Sentinel делает это для одного primary. Cluster делает это для диапазона слотов.

**How it works:**

- `REPLICAOF host port` создаёт реплику. По умолчанию она только для чтения (`replica-read-only`).
- Sentinel следит за этим primary. После failover `SENTINEL get-master-addr-by-name` возвращает новый хост и порт.
- В Cluster реплику повышают, и она владеет слотами упавшего primary. `CLUSTER NODES` показывает нового master. `CLUSTER FAILOVER` форсирует переключение.
- Файлы на диске сами по себе сервис не держат. AOF и RDB позволяют подняться перезапущенному процессу; живая реплика позволяет клиентам продолжить.

**When to use:**

Реплику добавляют до того, как называть схему высокодоступной. Sentinel — когда primary один. Cluster — когда primary уже шардированы.

**Examples:**

```redis
REPLICAOF 127.0.0.1 6799
SENTINEL get-master-addr-by-name mymaster
```

<summary>Обсудите the pros and cons of using Redis Sentinel vs. Redis Cluster.</summary>

### Обсудите the pros and cons of using Redis Sentinel vs. Redis Cluster.

**Definition:**

Sentinel делает failover одного primary и его реплик. Cluster шардирует 16384 хеш-слота по многим primary и делает failover диапазона каждого primary.

**How it works:**

- Sentinel: клиенты вызывают `SENTINEL get-master-addr-by-name`. Набор данных не делится. Каждый ключ остаётся на этом одном primary. Ёмкость — RAM этого primary.
- Cluster: слот — CRC16(key) по модулю 16384. Узел добавляют и слоты переносят без остановки. Реплика повышается только для слотов своего primary.
- Sentinel — неверный инструмент, когда одна машина не вмещает данные. Cluster — лишняя машинерия, когда хватает одного primary.
- Многоключевые и блокирующие команды в кластере ведут себя особо. Схема Sentinel с одним primary эти команды не шардирует.
- Обоим всё ещё нужен persistence, если повышенная реплика не должна опираться только на память.

**When to use:**

Sentinel выбирают для высокой доступности одного набора. Cluster — когда нужны память или запись больше, чем у одного primary.

**Examples:**

```redis
SENTINEL get-master-addr-by-name mymaster
CLUSTER NODES
```

**Sources:**

- [Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)
- [Scale with Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)
- [Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

<details>
<summary>Как you ensure data consistency across Redis replicas?</summary>

### Как you ensure data consistency across Redis replicas?

**Definition:**

Реплики копируют primary. Они не второй источник записи и не обязаны показать запись в тот же миг, когда primary её подтвердил.

**How it works:**

- `REPLICAOF host port` запускает репликацию. `replica-read-only` включён по умолчанию с Redis 2.6, поэтому клиенты не пишут в реплику и не расходятся с primary.
- Запись идёт на primary. Чтение с реплики может отставать от этого primary.
- `REPLICAOF NO ONE` останавливает репликацию и делает узел независимым primary. После этого узлы могут разойтись, если оба принимают запись.
- Для обновления одного ключа, которое нельзя перемежать на primary, используют `MULTI`/`EXEC` или `EVAL`. Это не делает реплику синхронной.
- AOF на primary ограничивает, что потеряет сбой до того, как реплика успеет скопировать. `appendfsync always` — самый строгий fsync; `everysec` может потерять около секунды.

**When to use:**

Читают с primary, когда следующая строка кода зависит от только что сделанной записи. Реплики используют для чтения, которое терпит отставание. `replica-read-only` оставляют включённым.

**Examples:**

```redis
REPLICAOF 127.0.0.1 6799
```

<summary>Что такое some strategies for Redis failover management?</summary>

### Что такое some strategies for Redis failover management?

**Definition:**

Управление failover — это кто повышает реплику, как клиенты узнают новый адрес и как не получить двух primary.

**How it works:**

- Sentinel: повышение отдаётся Sentinel, а результат узнают через `SENTINEL get-master-addr-by-name`. Всех клиентов не направляют на один зашитый хост.
- Ручная реплика: `REPLICAOF NO ONE` на выбранной реплике и остановка записи на старый primary, если он вернётся.
- Cluster: `CLUSTER FAILOVER` на реплике, которую надо повысить. `FORCE` не советуется с primary. `TAKEOVER` пропускает обычные проверки. Затем сверяют `CLUSTER NODES`.
- Тест отказа кластера показывает, что клиенты получают ошибки, пока идёт повышение, а затем команды проходят. Повторы приложения относятся к этому окну.
- Перед плановым failover делают `BGSAVE` или убеждаются, что перезапись AOF простаивает, чтобы у старого узла остался файл.

**When to use:**

Sentinel или Cluster — для незапланированного отказа. `CLUSTER FAILOVER` или `REPLICAOF NO ONE` — для планового переноса. Повторы клиентов ограничивают, чтобы они не обрушились на новый primary.

**Examples:**

```redis
CLUSTER FAILOVER
SENTINEL get-master-addr-by-name mymaster
```

**Sources:**

- [Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)
- [`CLUSTER FAILOVER`](https://redis.io/docs/latest/commands/cluster-failover/)
- [`REPLICAOF`](https://redis.io/docs/latest/commands/replicaof/)
- [Scale with Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)

### Как the Redis ecosystem evolved over the years?

**Definition:**

Redis вырос из сервера структур данных в памяти в сервер с репликацией, persistence, Sentinel, Cluster, модулями, потоками и ACL. Это возможности, которые описывает текущая документация, а не догадка о невыпущенной работе.

**How it works:**

- Репликация и `replica-read-only`: реплика только для чтения по умолчанию с Redis 2.6. Команда — `REPLICAOF`.
- У транзакций появился `WATCH` как оптимистическая блокировка. Страница транзакций относит эту дополнительную гарантию к версии 2.2.
- `MODULE LIST` есть с Redis 4.0.0. Текущая установка Stack может загрузить `search`, `timeseries`, `bf`, `ReJSON` и `vectorset`.
- Потоки используют `XADD` и `XREADGROUP`. Cluster шардирует 16384 слота. ACL используют `ACL SETUSER`.
- К вытеснению добавились политики LFU и, на текущей странице вытеснения, LRM рядом с LRU.

**Examples:**

```redis
MODULE LIST
ACL SETUSER alice on >p1pp0 ~cached:* +get
```

### Обсудите the impact of in-memory data grid solutions compared to Redis.

**Definition:**

Redis — сервер структур данных в памяти с необязательными persistence, репликацией и шардированием по слотам. Data grid обычно добавляет распределённые вычисления и другую модель согласованности поверх похожей идеи «сначала память».

**How it works:**

- Ёмкость Redis для одного ключа — один процесс или один слот кластера: CRC16(key) по модулю 16384. Масштаб наружу — перенос слотов, в документации это онлайн-решардинг.
- Инструменты согласованности — `MULTI`/`EXEC` и `EVAL`. Транзакцию Redis не откатывает. Реплика может отставать; `replica-read-only` не даёт ей стать вторым источником записи.
- Долговечность — RDB и AOF, не дисковая таблица. `appendfsync everysec` может потерять около секунды.
- Модули (`MODULE LIST`) расширяют типы. Они не превращают Redis в сетку, которая гоняет код приложения на каждом узле.
- Redis выбирают, когда нужный API — ключи, множества, потоки и Lua. Grid — другой продукт, когда нужна модель вычислений, которую Redis не документирует.

**When to use:**

Grid сравнивают с Redis по трём документированным пределам: нет отката, есть отставание реплики и один слот на ключ. Если нагрузке эти пределы подходят, Redis — более простая система в эксплуатации.

**Examples:**

```redis
EVAL "return 'Hello, scripting!'" 0
```

- [Scale with Redis Cluster](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)
- [Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)
- [Replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)
- [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### Какие new features вы ожидаете в будущих версиях Redis?

**Definition:**

Ожидать стоит только то, что Redis уже задокументировал и выпустил. Имена невыпущенных команд — ненадёжный ответ на собеседовании.

**How it works:**

- В текущей документации уже есть модули (`MODULE LIST` с 4.0.0), потоки (`XADD`, `XREADGROUP`), слоты Cluster, ACL (`ACL SETUSER`) и политики вытеснения вплоть до LFU и LRM.

**When to use:**

На собеседовании перечисляют возможности, которые можно показать командой и URL документации. Про следующую версию говорят, что её смотрят в заметках о выпуске, а не называют команду, которой ещё нет.

<summary>Как Redis modules expand its CAPabilities?</summary>

### Как Redis modules expand its CAPabilities?

**Definition:**

Модуль загружается в сервер и добавляет команды и типы, которых нет в ядре. `MODULE LIST` показывает, что загружено на самом деле.

**How it works:**

- Modules API — способ, которым разделяемая библиотека регистрирует команды. `RedisModule_PublishMessage` — одна документированная точка: она публикует как `PUBLISH` и есть с Redis 6.0.0.
- Модули могут реализовать блокирующие команды. Как `BLPOP`, они блокируют вызвавшего клиента, а не весь сервер.
- Пример `MODULE LIST` для Stack включает `search`, `timeseries`, `bf`, `ReJSON` и `vectorset`. Пустой список значит, что конфигурация их не загрузила.
- Категории `ACL`, кроме `+@all`, не включают команды модулей, поэтому модуль может открыть команды, которые ваш ACL не рассматривал.
- Базовые типы (строки, списки, множества, хеши, потоки) доступны без модуля.

**When to use:**

Модуль загружают для JSON, поиска, временных рядов или фильтра Блума, когда базовый тип не может представить данные. Его не загружают вместо `INCR` или `ZADD`.

**Examples:**

```redis
MODULE LIST
```

**Sources:**

- [Modules API](https://redis.io/docs/latest/develop/reference/modules/)
- [`MODULE LIST`](https://redis.io/docs/latest/commands/module-list/)

### Обсудите the role of Redis in the NoSQL movement.

**Definition:**

Redis — хранилище NoSQL, потому что это не реляционная таблица: это ключ, сопоставленный типу, с командами для этого типа, и рабочая копия живёт в памяти.

**How it works:**

- Типы включают строки, списки, множества, сортированные множества, хеши, битовые карты, HyperLogLog, геоиндексы и потоки. Тип выбирают вместо нормализации в таблицы.
- SQL join нет. Вторичный поиск — другой ключ (`SADD` / `SINTER` или `ZADD` / `ZRANGE`) или поисковый модуль.
- Атомарность — на команду, на пакет `MULTI`/`EXEC` или на один скрипт `EVAL`. Пакет не откатывается.
- Долговечность необязательна (RDB, AOF). Многие кеши NoSQL работают с вытеснением (`allkeys-lru`), а не хранят каждый ключ.
- Cluster масштабируется хеш-слотом, а не распределённым планировщиком SQL.

**When to use:**

Redis используют, когда приложение уже знает ключ и операцию над типом. Реляционную базу используют, когда вопросы — это произвольные соединения строк, которые заранее не индексировали.

**Examples:**

```redis
ZADD board 10 alice
SINTER skill:redis skill:python
```

<summary>Как you inspect and debug the contents of a running Redis server?</summary>

### Как you inspect and debug the contents of a running Redis server?

**Definition:**

Работающий сервер смотрят командами чтения и пошаговым обходом. На большой базе не выгружают все ключи через `KEYS`.

**How it works:**

- `INFO` (и `INFO memory`, `INFO stats`, `INFO persistence`) показывает память, попадания, промахи и состояние перезаписи AOF.
- `SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]` проходит имена ключей небольшими порциями. `TYPE` есть с Redis 6.0.0. Цикл идёт, пока курсор не вернётся к `0`.
- `MEMORY USAGE key` оценивает один ключ. `SLOWLOG GET` и `LATENCY DOCTOR` показывают медленные команды.
- `CLUSTER NODES` показывает роли кластера. `MODULE LIST` показывает загруженные модули.
- Страница `KEYS` говорит, что команда для отладки и особых операций, и просит крайнюю осторожность в production, потому что она может испортить производительность.

**When to use:**

`SCAN` и `MEMORY USAGE` используют, пока сервер принимает трафик. `KEYS` оставляют для маленького инстанса или для момента, когда остановка уже допустима.

**Examples:**

```redis
SCAN 0 MATCH user:* COUNT 100 TYPE string
INFO memory
MEMORY USAGE user:1
```

**Sources:**

- [`SCAN`](https://redis.io/docs/latest/commands/scan/)
- [`INFO`](https://redis.io/docs/latest/commands/info/)
- [`MEMORY USAGE`](https://redis.io/docs/latest/commands/memory-usage/)
- [`KEYS`](https://redis.io/docs/latest/commands/keys/)
- [`LATENCY DOCTOR`](https://redis.io/docs/latest/commands/latency-doctor/)

<summary>Что такое the implications of using the `KEYS` command in production?</summary>

### Что такое the implications of using the `KEYS` command in production?

**Definition:**

`KEYS pattern` возвращает каждое подходящее имя ключа и имеет сложность O(N) по числу ключей. На большой базе это может остановить Redis.

**How it works:**

- Страница команды говорит: крайняя осторожность в production; на больших базах команда может испортить производительность; она предназначена для отладки и особых операций вроде смены раскладки пространства ключей; не используйте `KEYS` в обычном коде приложения.
- Если нужно подмножество имён, та же страница советует `SCAN` или множества.
- `KEYS` входит в категорию ACL `dangerous` вместе с `FLUSHALL` и `DEBUG`. `ACL CAT dangerous` её перечисляет.
- В Redis Cluster шаблон, который может совпасть только с одним слотом (хеш-тег вроде `{a}`), обходит этот слот. Шаблон, который может совпасть с любым слотом, обходит больше, чем один слот.
- `SCAN cursor MATCH pattern COUNT count` — пошаговая замена. `COUNT` — подсказка, не гарантия, и курсор читают, пока он не станет `0`.

**When to use:**

`KEYS` запрещают пользователям ACL приложения. Её разрешают человеку на маленькой базе или в окно обслуживания. В коде используют `SCAN`.

**Examples:**

```redis
SCAN 0 MATCH user:* COUNT 100
```

**Sources:**

- [`KEYS`](https://redis.io/docs/latest/commands/keys/)
- [`SCAN`](https://redis.io/docs/latest/commands/scan/)
- [ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

<summary>Как you identify memory leaks in a Redis instance?</summary>

### Как you identify memory leaks in a Redis instance?

**Definition:**

Память Redis растёт из-за ключей, фрагментации, буферов клиентов и fork. Поиск утечки разделяет это через `INFO memory`, `MEMORY DOCTOR` и `MEMORY USAGE`.

**How it works:**

- `INFO memory` включает `mem_not_counted_for_evict` — память буферов, которую страница вытеснения велит вычесть, когда задаёте `maxmemory`.
- `MEMORY DOCTOR` — отчёт, который руководство по администрированию называет для разбора памяти, рядом с `LATENCY DOCTOR`.
- `MEMORY USAGE key [SAMPLES count]` оценивает один ключ. Число образцов по умолчанию — 5. Ключ, который остался после TTL, должен был исчезнуть; если `volatile-*` не срабатывает, вы забыли истечения, и политика ведёт себя как `noeviction`.
- `BGSAVE` или перезапись AOF при тяжёлой записи может занять примерно до двух обычных объёмов памяти (copy-on-write). Этот всплеск — не утечка, если он спадает после выхода дочернего процесса.
- `SCAN` находит шаблоны имён, которые приложение продолжает создавать. `maxmemory` с `allkeys-lru` — потолок для кеша; без потолка рост идёт, пока не откажет хост.

**When to use:**

Сравнивают `INFO memory` во время fork и после него. Если занятость остаётся высокой, самые большие ключи смотрят через `MEMORY USAGE` и проверяют, не забыл ли код `EXPIRE` и не пишет ли ключи, которые никогда не удаляет.

**Examples:**

```redis
INFO memory
MEMORY DOCTOR
MEMORY USAGE session:abc
```

**Sources:**

- [`INFO`](https://redis.io/docs/latest/commands/info/)
- [`MEMORY DOCTOR`](https://redis.io/docs/latest/commands/memory-doctor/)
- [`MEMORY USAGE`](https://redis.io/docs/latest/commands/memory-usage/)
- [Administration](https://redis.io/docs/latest/operate/oss_and_stack/management/admin/)
- [Eviction](https://redis.io/docs/latest/develop/reference/eviction/)
