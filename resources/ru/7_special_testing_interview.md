### Что такое software testing, and why is it important?

**Definition:**

Тестирование программного обеспечения — это все процедуры, которые ведут, направляют и оценивают разработку систем и приложений. Оно обеспечивает качество и разрабатываемого ПО, и задействованных процессов.

**How it works:**

#### Важность тестирования программного обеспечения

- Обнаружение ошибок: находит дефекты, расхождения или отклонения от ожидаемого поведения.
- Снижение риска: уменьшает вероятность или последствия сбоя ПО.
- Обеспечение качества: продукт соответствует ожиданиям пользователей и бизнес-требованиям.
- Удовлетворённость клиента: даёт надёжный, удобный опыт.
- Экономия: раннее обнаружение дефектов важно, потому что исправлять ошибки со временем становится дороже.
- Улучшение процесса: тестирование даёт ценные данные, чтобы оттачивать процессы разработки.

#### Положительные петли обратной связи

- Побуждение исправлять дефекты
- Рост уверенности
- Учёба на ошибках
- Непрерывное улучшение

#### Области тестирования

1. Модульное тестирование: проверка отдельных компонентов или модулей в изоляции.
2. Интеграционное тестирование: разные части системы работают вместе гладко.
3. Системное тестирование: продукт проверяется целиком, обычно в среде, близкой к промышленной.
4. Приёмочное тестирование: система соответствует конкретным бизнес-требованиям; это последняя проверка перед выпуском.
5. Тестирование производительности: как система ведёт себя при разной нагрузке.
6. Тестирование безопасности: уязвимости, которые могут привести к взлому или компрометации данных.
7. Тестирование удобства: насколько система удобна пользователю.

#### Распространённые заблуждения о тестировании

1. Неверное понимание роли: тестирование часто видят как эпитет для Bug Tracking, хотя оно глубже уходит в управление рисками, анализ требований и работу с обратной связью клиентов.
2. Стоимость настройки тестов: начальная настройка может казаться дорогой. В неё стоит вложиться, чтобы не платить больше из-за падения системы или проблем с удержанием клиентов.
3. Заблуждение об обнаружении дефектов: утверждение о нуле дефектов после тестирования нереалистично. Важная оговорка: “Мы не можем гарантировать отсутствие всех дефектов, но неустанно работаем, чтобы свести эти случаи к минимуму.”
4. Ловушка статического анализа: автоматические проверки и ревью кода дают много данных, но не заменяют динамическое тестирование, которое воспроизводит и смотрит живые выполнения.
5. Отказ от ручного тестирования: автоматическое тестирование сильно, но человеческий интеллект исследовательских тестов даёт преимущество в поиске неожиданных аномалий.
6. Ограничение спринтом или временем: тестирование — непрерывный процесс, устойчиво встроенный в разработку и вложенный в каждую спроектированную единицу.

#### Владение навыками

1. Test-Driven Development (TDD): тесты пишут ещё до кода, и это задаёт ясный путь разработки, поднимает качество кода и снижает число дефектов.
2. Синтез Agile и DevOps: слаженное взаимодействие разработки, тестирования и развёртывания возможно в таких цельных средах.
3. Основы знания предметной области: такая экспертиза помогает тщательно намечать сценарии и сертифицировать системы.

### Определите the difference between verification and validation in software testing.

**Definition:**

Определим верификацию и валидацию в контексте тестирования ПО и различим их.

**How it works:**

#### Основные различия

- Верификация: подтверждает, что ПО соответствует своим спецификациям и требованиям.

Она отвечает на вопрос “Are we building the product right?”
Примеры: ревью кода, инспекции и разборы.
- Валидация: гарантирует, что ПО отвечает действительным нуждам пользователя.

Она отвечает на вопрос “Are we building the right product?”
Примеры: пользовательское приёмочное тестирование, альфа- и бета-тестирование.

### Объясните the software development life cycle and the role testing plays in each phase.

**Definition:**

Жизненный цикл разработки ПО (SDLC) состоит из нескольких отдельных фаз, которые закладывают основу успешного проекта.

**How it works:**

#### Ключевые фазы

1. Анализ требований и планирование:

Консультации со стейкхолдерами: работа со стейкхолдерами, чтобы полностью понять их нужды и ожидания и задать ясные цели проекта.
Роль тестирования: проверка требований приёмами вроде оценки прототипа и анализа сценариев использования.
2. Проектирование и архитектурное планирование:

Создание документов: сюда входят Software Requirement Specification (SRS) и документ высокоуровневого проектирования.
Роль тестирования: ревью проекта и структурное тестирование проверяют, что проект системы соответствует заданным требованиям.
3. Реализация и кодирование:

Основная функциональность: здесь пишут код под проверенные и утверждённые требования.
Модульное тестирование: небольшие независимые единицы кода проверяют, что они ведут себя как ожидается, и дают надёжные кирпичи для большей системы.
4. Системное тестирование: интегрированную систему проверяют целиком, чтобы все возможности работали согласованно.

Разбиение фазы: перед выпуском это часто делят на альфа- и бета-тестирование.
Стресс-тестирование: опыты в крайних условиях помогают оценить пределы системы.
5. Развёртывание и сопровождение:

Проверка развёртывания: после развёртывания тесты убеждаются, что система правильно работает в живой среде.
Регулярные проверки: сопровождение включает периодические проверки и обновления, чтобы ПО оставалось оптимизированным и защищённым.

#### Пример кода: модульное тестирование

Вот код на Python:

```python
def add(a, b):
    return a + b

def subtract(a, b):
    return a - b

# Unit Tests
assert add(1, 2) == 3
assert subtract(5, 2) == 3
```

#### Пример кода: интеграционное тестирование

Вот код на Python:

```python
def add_and_subtract(a, b):
    return add(a, b), subtract(a, b)

# Integration Test
result = add_and_subtract(5, 3)
assert result == (8, 2)
```

### Что такое the different levels of software testing?

**Definition:**

Посмотрим на разные уровни тестирования ПО по жизненному циклу разработки.

**How it works:**

#### Модульное тестирование

- Что это? Сосредоточено на проверке отдельных функций и методов.
- Когда делается? Во время кодирования.
- Уровень тестирования: изолированный.
- Роль в пирамиде тестирования: образует основание.
- Инструменты: JUnit, NUnit, PyTest.
- Главная польза: раннее обнаружение ошибок.

#### Компонентное тестирование

- Что это? Проверяет компоненты ПО, часто заданные на высоком уровне.
- Когда делается? После модульного тестирования и до интеграционного.
- Уровень тестирования: ограниченный контекст.
- Роль в пирамиде тестирования: фундамент.
- Главная польза: единицы кода работают вместе так, как ожидается в заданных сценариях.

#### Интеграционное тестирование

- Что это? Сосредоточено на объединённых единицах приложения.
- Когда делается? После компонентного тестирования и до системного.
- Уровень тестирования: умеренный контекст.
- Роль в пирамиде тестирования: фокус.
- Инструменты: Apache JMeter, LoadRunner.
- Главная польза: находит проблемы в интерфейсах между модулями ПО.

#### Системное тестирование

- Что это? Оценивает полную интегрированную систему.
- Когда делается? После интеграционного тестирования.
- Уровень тестирования: всесторонний.
- Роль в пирамиде тестирования: основной.
- Главная польза: сверяет требования к системе с поставленными функциями.

#### Приёмочное тестирование

- Что это? Проверяет, соответствует ли система заданным требованиям заказчика.
- Когда делается? После системного тестирования.
- Уровень тестирования: внешний.
- Роль в пирамиде тестирования: вершина.
- Главная польза: система приемлема для конечных пользователей.

#### Альфа- и бета-тестирование

- Когда делается? После приёмочного тестирования; часто включает фазы уже после запуска продукта.

#### Альфа-тестирование

- Для чего: проверяет систему в контролируемой внутренней среде.
- Роль в пирамиде тестирования: первый источник обратной связи пользователей.

#### Бета-тестирование

- Для чего: проверяет систему в живой среде реального времени и часто получает отзывы от избранной группы внешних пользователей.
- Роль в пирамиде тестирования: ранний источник обратной связи пользователей.

### Опишите the difference between static and dynamic testing.

**Definition:**

Статическое и динамическое тестирование дополняют друг друга и вместе дают всестороннюю проверку кода. Статическое тестирование изучает ПО, не выполняя его, а динамическое проверяет ПО в рабочей среде. Разберём эти два подхода подробнее.

**How it works:**

#### Основной фокус

- Статическое тестирование: анализирует код или документацию и находит проблемы, не выполняя программу.
- Динамическое тестирование: включает выполнение кода, чтобы выявить и оценить поведение программы.

#### Время

- Статическое тестирование: обычно раньше в цикле разработки и помогает найти проблемы у корня.
- Динамическое тестирование: обычно позже в цикле, после интеграции кода, чтобы оценить функции системы и взаимодействие с пользователем.

#### Инструменты и приёмы

#### Статическое тестирование

- Ручные ревью: эксперты вручную смотрят код и документацию.
- Автоматические инструменты: программы анализируют код или документацию на возможные проблемы. Примеры: линтеры, интеграции в IDE и проверка орфографии в документации.

#### Динамическое тестирование

- ** Unit Testing**: оценивает самые мелкие единицы кода, такие как отдельные функции или методы, в изоляции.
- Интеграционное тестирование: модули или компоненты работают вместе так, как ожидается.
- ** System Testing**: оценивает полный интегрированный продукт и то, что он соответствует заранее заданным требованиям.
- Приёмочное тестирование: система соответствует набору бизнес-требований и/или ожиданий пользователей. Часто конечные пользователи сами выполняют систему.

#### Покрытие кода

- Статическое тестирование: даёт некоторое покрытие строк, чтобы код был правильным и полным, но не гарантирует выполнение.
- Динамическое тестирование: даёт всестороннее выполнение и то, что код запускается как задумано в разных сценариях.

#### Цели тестирования

- Статическое тестирование: в первую очередь ищет нарушения в коде, ошибки проектирования и проблемы документации.
- Динамическое тестирование: стремится подтвердить функции системы и взаимодействие с пользователем в реальной или смоделированной среде.

### Что такое test case, and what elements should it contain?

**Definition:**

Тест-кейс — это одна процедура поиска проблем и ошибок.

Каждый тест-кейс должен включать конкретные атрибуты, чтобы быть действенным инструментом проверки в процессе тестирования ПО:

- ID: уникальный идентификатор, возможно сгенерированный автоматической системой.
- Title: описательное краткое название тест-кейса.
- Description: подробный рассказ о цели тест-кейса, предварительных шагах и ожидаемых результатах.
- Steps to Reproduce: процедурное руководство, чтобы воспроизвести среду теста и вызвать ожидаемый результат.
- Expected Outcome: ясно заданный желаемый или оптимальный результат теста либо состояние после теста.
- Actual Outcome: записанные результаты выполнения для сравнения с ожидаемым результатом.
- Comments: место для дополнительной информации о тест-кейсе или его отдельных действиях.
- Assigned To: кто из тестировщиков или какая группа отвечает за выполнение тест-кейса.
- Last Updated: метка времени последнего изменения тест-кейса, включая правки любого из его элементов.

**How it works:**

#### Пример кода: атрибуты тест-кейса

Вот код на Java:

```java
import java.util.List;
import java.time.LocalDateTime;

public class TestCase {
    private int id;
    private String title;
    private String description;
    private List<String> stepsToReproduce;
    private String expectedOutcome;
    private String actualOutcome;
    private String comments;
    private String assignedTo;
    private LocalDateTime lastUpdated;

    // Constructor, getters and setters
}
```

### Объясните the concept of coverage in testing and the main types of coverage (e.g., line, branch, path, statement).

**Definition:**

Тестирование покрытия оценивает, в какой мере куски кода выполняются. Эта оценка помогает найти области кода, которые не протестированы.

**How it works:**

Ключевые метрики покрытия:

- Покрытие строк: доля исполняемых строк кода, которые задействует набор тестов.
- Покрытие ветвей: доля точек решения в коде, где оба возможных исхода проверены хотя бы один раз.
- Покрытие путей: идеальный случай, когда каждый возможный путь через программу выполнен хотя бы один раз. Полное покрытие путей для больших программ может быть непрактичным.
- Покрытие операторов: самый простой вид покрытия — выполнен ли каждый оператор программы хотя бы один раз во время тестирования.

### Что такое the difference between white-box, black-box, and grey-box testing?

**Definition:**

Тестирование белым, чёрным и серым ящиком служит разным целям, и их часто применяют вместе.

**How it works:**

#### Тестирование чёрным ящиком

В тестировании чёрным ящиком тестировщик не знаком с внутренним устройством системы. Тесты строят по спецификациям или требованиям системы, чтобы выполнялись и функциональные, и нефункциональные требования.

Такое тестирование часто делают на ранних стадиях разработки.

#### Тестирование белым ящиком

Тестирование белым ящиком требует глубокого понимания внутренних структур системы или ПО под тестом.

Это структурный метод: проверяются все или большинство путей и операций внутри ПО.

Этот метод также называют clear box testing и glass box testing, и он уместнее на поздних стадиях жизненного цикла разработки.

#### Тестирование серым ящиком

В тестировании серым ящиком у тестировщика есть доступ к некоторым внутренним структурам или алгоритмам ПО под тестом.

Такое тестирование ищет баланс между покрытием тестами и функциональностью системы. Оно соединяет пользу белого и чёрного ящика.

Тестирование серым ящиком считают самым практичным для реальных сценариев, особенно при проверке веб-приложений, API или распределённых систем.

### Что такое regression testing, and why is it performed?

**Definition:**

Регрессионное тестирование — специальный механизм, который проверяет, что недавние изменения кода не вредят уже существующей функциональности системы.

**How it works:**

#### Основные цели

1. Гарантия стабильности: изменения не вносят новые дефекты и проблемы.
2. Проверка согласованности: неизменённые возможности сохраняют задуманное поведение.
3. Предотвращение деградации ПО: найти места, где изменения ломают устоявшиеся возможности.

#### Обычные поводы для регрессионного тестирования

- Исправление дефекта: после починки ошибки проверяют другие области, чтобы не появились новые неисправности.
- Развитие возможностей: новую функциональность добавляют и при этом удостоверяются, что существующие возможности работают без изменений.
- Рефакторинг кода: прежняя функциональность сохраняется после структурных или архитектурных правок.

#### Методы регрессионного тестирования

#### Полный

Исчерпывающая проверка всех функций приложения. Метод тщательный, но занимает много времени и для больших систем часто непрактичен.

#### Выборочный

Нацелен на конкретные возможности или компоненты, которые, как известно, взаимодействуют с только что изменёнными участками кода. Подход эффективнее, но нужно тщательно определить подходящие сценарии тестов.

#### Регрессия на модульных тестах

Опирается на непрерывное и автоматическое выполнение модульных тестов. Так регрессии обнаруживаются сразу во время разработки, и их можно быстро исправить.

Выборочный подход распространён в индустрии, потому что полная проверка часто невыполнима или без нужды отнимает время.

#### Инструменты автоматизации

Для автоматизации регрессионного тестирования есть разные инструменты, среди них:

- Jenkins: сервер непрерывной интеграции, который может планировать и выполнять тестовые задания через заданные интервалы.
- JUnit: популярный фреймворк модульного тестирования для Java, часто вместе со средствами сборки вроде Maven.
- Selenium: фреймворк тестирования веб-приложений, который автоматизирует взаимодействие с браузерами.
- GitLab CI/CD: встроенная в GitLab система непрерывной интеграции и непрерывного развёртывания, которая позволяет автоматически выполнять тесты.

<summary>Объясните unit testing and which tools you might use for it.</summary>

### Объясните unit testing and which tools you might use for it.

**Definition:**

Модульное тестирование проверяет отдельные компоненты или модули системы, чтобы они работали как ожидается. Его обычно делают в процессе разработки, и оно помогает рано находить и чинить дефекты.

**How it works:**

#### Основные принципы

- Изоляция: каждая единица должна быть независима от системы, чтобы её можно было проверить отдельно.
- Повторяемость: тесты должны быть согласованы от прогона к прогону.
- Скорость: один тест должен выполняться быстро, чтобы гонять их часто.
- Согласованность между платформами: тесты должны давать согласованные результаты независимо от платформы.

#### Инструменты и фреймворки

- JUnit: для тестирования на Java.
- NUnit: для разработчиков .NET и C#.
- JUnit Jupiter API: последняя версия JUnit, спроектированная на возможностях Java 8.
- TestNG: Java-фреймворк, который поддерживает несколько уровней тестов.
- RSpec: инструмент тестирования в стиле BDD для Ruby.
- Google Test: тестовый фреймворк, подходящий для проектов на C++.
- Mocha и Jasmine: для разработчиков на JavaScript.
- PyTest и Unittest: для тестирования на Python.

#### Пример кода: JUnit 5 для Java

Вот код на Java:

```java
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;
import org.junit.jupiter.api.Test;

class MathFunctionsTest {
    MathFunctions mathFunctions = new MathFunctions();

    @Test
    void testAdd() {
        assertEquals(4, mathFunctions.add(2, 2));
    }

    @Test
    void testIsPrime() {
        assertTrue(mathFunctions.isPrime(7));
    }
}
```

#### Инструменты автоматизации

- Maven для Java: это инструмент автоматизации сборки. Помимо зависимостей и пакетов, он может запускать тесты.
- Gradle для Java, Groovy и Kotlin: инструмент сборки с предметно-ориентированным языком для настройки автоматизации проекта.
- JUnit Platform Launcher: движок выполнения тестов, его используют со системами сборки, чтобы гонять тесты на JUnit 5.
- Jenkins: часто используется для Continous Integration/Continous Deployment (CI/CD) и может автоматизировать выполнение тестов.
- GitHub Actions: инструмент CI/CD от GitHub, сосредоточенный на автоматизации рабочих процессов, например тестирования.

#### Утверждения и тест-кейсы

- Assert: даёт методы, чтобы проверять разные условия. Например, assertEquals(expected, actual) проверяет, равны ли два значения.
- Тест-кейсы: методы, начинающиеся с @Test, помечают тестовые методы.

#### Использование аннотаций

- @BeforeAll и @AfterAll: методы с этими аннотациями выполняются один раз, до и после всех тестовых методов соответственно.
- @BeforeEach и @AfterEach: методы с этими аннотациями выполняются до и после каждого тестового метода и дают чистую среду теста.

#### Интеграция со средствами разработки

- Инструменты IDE: многие современные среды, такие как IntelliJ IDEA или Eclipse, поддерживают модульное тестирование прямо в интерфейсе.
- Системы управления версиями: инструменты вроде Git можно связать с модульным тестированием для проверок до коммита и после него.
- Автоматические системы сборки: системы вроде Jenkins и TeamCity можно настроить так, чтобы они запускали автоматическое тестирование.

#### Ловушки, которых стоит избегать

- Недостаточное покрытие: тесты могут не закрывать все требования, и дефекты останутся незамеченными.
- Чрезмерная опора на внешние системы: внешние зависимости могут отказать, и появятся ложные срабатывания.
- Жёстко связанные тесты: это усложняет рефакторинг, потому что даже несвязанные изменения могут сломать тесты.
- Избыточность тестов: повторять сценарии неэффективно и может вести к несогласованности.

#### Польза модульного тестирования

- Раннее обнаружение дефектов: проблемы находят рано в разработке, и цена исправления ниже.
- Более высокое качество кода: разбиение кода на маленькие тестируемые единицы способствует более чистому и поддерживаемому коду.
- Уверенность при рефакторинге: можно спокойнее менять существующий код.
- Лучшая документация: набор тестов может служить живой документацией и описывать поведение единиц.

### Что такое integration testing and what are its types?

**Definition:**

Интеграционное тестирование оценивает совместную работу компонентов ПО, чтобы найти проблемы на стыках и убедиться, что они работают вместе без швов.

Проверяя группы компонентов как единицу, интеграционное тестирование стремится:

- Найти дефекты во взаимодействии компонентов.
- Проверить, что сообщения и запросы передаются правильно.
- Оценить системы на правильное выделение ресурсов и управление ими.

**How it works:**

#### Виды интеграционного тестирования

#### Стратегии сверху вниз

Преимущества:

- Архитектурные проблемы легче найти и исправить на раннем этапе.
- Удобно следить за общим ходом проекта.

Недостатки:

- Управлять этим может быть сложно, особенно в больших системах.

#### Тестирование сверху вниз

Также известная как “Big Bang Integration Testing”, эта стратегия сначала проверяет верхние слои приложения.

Она включает:

1. Опору на заглушки, которые имитируют модули нижнего уровня (это временные заместители настоящих нижних модулей).
2. Последовательное подключение модулей нижнего уровня и планомерное сокращение числа заглушек.

#### Тестирование снизу вверх

Эта стратегия, известная как “Incremental Integration Testing”, идёт наоборот и сначала проверяет нижние слои:

1. Собрать начальные базы тестов из модулей снизу.
2. Использовать драйверы как временных заместителей компонентов более высокого уровня.
3. Постепенно интегрировать модули вверх.

#### Тестирование от середины

Стратегия “Sandwich” или “Middleware” интегрирует модули слой за слоем, начиная с ядра и расширяясь наружу.

- Даёт сбалансированный взгляд.
- Сначала убеждается, что ядро надёжно.

#### Гибридные подходы

На практике интеграционное тестирование часто применяет несколько методик, чтобы покрытие было как можно полнее:

- Федеративный: начинается с вертикальных срезов приложения, затем идут вертикальные и горизонтальные интеграции.
- Концентрический: идёт изнутри наружу или снаружи внутрь и сосредоточен на конкретных зонах или областях приложения.

#### Пример кода: тестирование сверху вниз и снизу вверх

Вот код на Java:

```java
// Top-Down Testing
public class SalesReportServiceTest {
    // Test dependency to CashierService
}

// Bottom-Up Testing
public class CashierServiceTest {
    // Test core functionality
}
```

### Что такое system testing, and how does it differ from other types of testing?

**Definition:**

Системное тестирование проверяет, что интегрированная система соответствует требованиям к проекту.

Оно отличается от других видов, таких как модульное, интеграционное и приёмочное, фокусом, охватом тестирования и средой теста.

**How it works:**

#### Системное тестирование и модульное тестирование

#### Фокус

- Модульное тестирование: проверяет отдельные “единицы” или компоненты в изоляции.
- Системное тестирование: оценивает всю систему целиком, так, как ею будут пользоваться в настоящей среде.

#### Охват тестирования

- Модульное тестирование: режим узкого охвата.

Чтобы изолировать функциональность для теста, могут применяться mock-объекты и заглушки.
Такое тестирование обычно автоматическое, и его делают разработчики.
- Системное тестирование: режим широкого охвата.

Во время тестирования никакие компоненты не изолируют.
Обычно это сквозные, ручные и ориентированные на заказчика тесты.

- Модульное тестирование: опирается на контролируемую и смоделированную среду.
- Системное тестирование: использует среду реального мира.

#### Фокус

- Интеграционное тестирование: оценивает, соответствуют ли ожиданиям взаимодействие и совместные функции компонентов системы.
- Системное тестирование: вся система ведёт себя согласно заданным требованиям.

- Интеграционное тестирование: режим среднего охвата.

Больше сосредоточено на взаимодействии компонентов внутри системы, чем на более широких функциях системы.
- Системное тестирование: режим широкого охвата.

#### Среда теста

- Интеграционное тестирование: использует частично контролируемую среду, где компоненты интегрированы.
- Системное тестирование: проводится в среде, mirrorring реальное использование приложения.

#### Фокус

- Приёмочное тестирование: обычно это тестирование, которое стейкхолдеры делают для одобрения системы.
- Системное тестирование: в первую очередь обеспечение качества продукта и соответствие конкретным требованиям.

#### Охват тестирования

- Приёмочное тестирование: режим среднего охвата, часто с тест-кейсами, которые создают бизнес-пользователи.
- Системное тестирование: режим широкого охвата, всестороннее поведение системы.

### Определите acceptance testing and describe its types.

**Definition:**

Приёмочное тестирование (AT) проверяет, достигает ли система своих бизнес-целей. Это последний шаг проверки перед тем, как продукт выпустят конечным пользователям или заказчикам.

**How it works:**

#### Виды приёмочного тестирования

1. Альфа-тестирование:

Охват: выполняет внутренняя команда, прежде чем продукт станет доступен нескольким внешним заказчикам.
Цель: найти критические проблемы и уточнить возможности по прямой обратной связи пользователей.
Обычно в: ПО, игровых консолях и развёртывании приложений в частных организациях.
2. Бета-тестирование:

Охват: выполняет избранная группа внешних пользователей или заказчиков.
Цель: вскрыть последние проблемы или сбои и понять опыт и принятие пользователей.
Обычно в: ПО, веб-приложениях и более широких потребительских продуктах.
3. Приёмка по контракту:

Охват: обычно происходит в точке договорённости между двумя или более сторонами.
Цель: разработанный продукт или услуга соответствует заданным требованиям контракта.
Обычно в: государственных проектах, крупных клиентских работах и юридических соглашениях.
4. Приёмка по регулированию:

Охват: нужна, чтобы продукт соответствовал конкретным отраслевым или региональным нормам.
Цель: продукт удовлетворяет заданным регуляторным условиям или стандартам безопасности.
Обычно в: отраслях вроде здравоохранения, финансов, авиации и фармацевтики.
5. Пользовательское приёмочное тестирование (UAT):

Охват: проводят стейкхолдеры, часто конечные пользователи или представители заказчика.
Цель: система работает согласно их заданным требованиям и нуждам.
Обычно в: всех отраслях, особенно там, где сильно опираются на нужды и вклад пользователей.
6. Операционное тестирование:

Охват: операционные аспекты и способность системы выполнять задачи.
Цель: операционная готовность системы, часто в условиях реального мира.
Обычно в: критически важных системах, обороне, экстренном реагировании и крупных промышленных системах.
7. Приёмка по регулированию:

Охват: продукт соответствует отраслевым или региональным нормам.
Цель: соблюдение конкретных норм или стандартов безопасности.
Обычно в: секторах вроде здравоохранения, финансов, авиации и фармацевтики.

### Когда would you choose not to automate test cases?

**Definition:**

Хотя автоматическое тестирование в целом выгодно, есть конкретные сценарии, где ручное тестирование уместнее. Такие случаи обычно отличают высокая начальная стоимость настройки, малая потребность повторять тест или польза человеческой интуиции и приспособляемости.

**How it works:**

#### Когда выбрать ручное тестирование

- Повторяющиеся разовые сценарии: если тест-кейс сложный и вряд ли будет повторён, ручное тестирование может быть эффективнее.
- Чувствительность данных: случаи с чувствительными данными, особенно в регулируемых отраслях, часто лучше проверять вручную.
- Исследовательское тестирование: этот метод больше про то, чтобы органично обнаруживать поведение ПО, а не подтверждать заранее заданное. По определению его трудно автоматизировать, и он часто выигрывает от человеческого взгляда.
- Локальная проверка: некоторые сценарии, вроде мелких изменений или разбора конкретной ошибки, эффективнее проверить вручную.
- Начальная стоимость автоматизации тестов: для проектов с малым объёмом или там, где настройка автоматического тестирования относительно дорога, ручное тестирование может быть более прямым вариантом.

#### Совмещённый подход: лучшее от обоих

Смешанные подходы к тестированию становятся всё популярнее в индустрии. Соединяя сильные стороны ручного и автоматического тестирования, команды получают полное покрытие и быструю обратную связь.

- Автоматизация снизу вверх после ручного тестирования: тестировщики сначала понимают систему, её область и нужды тестов, а потом автоматизируют отдельные участки.
- Исследовательское тестирование с помощью автоматизации: автоматические инструменты направляют и упорядочивают исследовательское тестирование и могут дать более полное покрытие.
- Тестирование на основе риска с инструментами: тест-кейсы расставляют по риску и автоматизируют сценарии высокого риска, чтобы критические функции проверялись постоянно.

### Что такое data-driven testing, and how can it be implemented?

**Definition:**

Тестирование, управляемое данными, — техника скриптов, которая использует файлы данных, чтобы хранить тестовые данные и ожидаемые результаты, нужные для выполнения тестовых скриптов. Один и тот же скрипт выполняется по разу на строку.

**How it works:**

#### Две реализации

- `test.each` в Jest принимает строки. В заголовке `%i` подставляет значения.
- `@pytest.mark.parametrize("test_input,expected", [("3+5", 8), ("2+4", 6), ("6*9", 42)])` в pytest запускает `test_eval` три раза. В документации `6*9` падает, потому что `eval('6*9')` равен 54, а не 42.

**When to use:**

Применяйте, когда много пар «вход и ожидание» делят одну процедуру. Пишите отдельные тесты, когда шаги различаются.

**Examples:**

```python
import pytest

@pytest.mark.parametrize("test_input,expected", [("3+5", 8), ("2+4", 6), ("6*9", 42)])
def test_eval(test_input, expected):
    assert eval(test_input) == expected
```

Тестирование производительности определяет эффективность производительности компонента или системы: как она использует время, ресурсы и ёмкость, выполняя свои функции. Функциональное тестирование спрашивает, верен ли результат. Тестирование производительности спрашивает, укладывается ли эта работа во временные и ресурсные пределы. ### Что такое the key performance testing metrics?

**Definition:**

HTTP-метрики k6 — `http_req_duration` (задержка) и `http_req_failed` (доля ошибок). Порог проваливает прогон, когда его выражение ложно в конце.

**Examples:**

```javascript
import http from 'k6/http';

export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<200'],
  },
};

export default function () {
  http.get('https://quickpizza.grafana.com');
}
```

### Объясните how to set up a performance test.

**Definition:**

Руководство k6 говорит сначала решить образец трафика, выбрать тип теста, затем расписать эту нагрузку в `options`. Проверки затем утверждают статус, заголовки и полезную нагрузку.

**How it works:**

#### Последовательность

- Назовите цель: надёжность при ожидаемом трафике или пределы при необычном трафике.
- Выберите smoke, load, stress, spike, breakpoint или soak.
- Положите нагрузку в сценарий (`constant-arrival-rate`, `ramping-vus` или другой executor).
- Вызовите API и сделайте `check` ответа. Добавьте пороги, чтобы процесс падал, когда задержка или ошибки не дотягивают до планки.

**Examples:**

```javascript
import { check } from 'k6';
import http from 'k6/http';

export const options = {
  scenarios: {
    my_scenario1: {
      executor: 'constant-arrival-rate',
      duration: '30s',
      preAllocatedVUs: 50,
      rate: 50,
      timeUnit: '1s',
    },
  },
};

export default function () {
  const payload = JSON.stringify({ name: 'lorem', surname: 'ipsum' });
  const headers = { 'Content-Type': 'application/json' };
  const res = http.post('https://quickpizza.grafana.com/api/post', payload, { headers });
  check(res, {
    'Post status is 200': (r) => res.status === 200,
    'Post Content-Type header': (r) => res.headers['Content-Type'] === 'application/json',
    'Post response name': (r) => res.status === 200 && res.json().name === 'lorem',
  });
}
```

### Объясните SQL injection and how you test for it.

**Definition:**

Шпаргалка OWASP по предотвращению SQL-инъекций говорит, что атакующий может внедрить SQL, когда приложение строит запрос, склеивая пользовательский ввод. Документированная строка атаки — `tom' or '1'='1`.

**How it works:**

#### Тест и защита

- Найдите запросы, построенные как `"... WHERE user_name = " + request.getParameter("customerName")`.
- Отправьте `tom' or '1'='1` как этот параметр. Если оператор склеен, текст становится частью SQL.
- Безопасный образец на той же странице — `PreparedStatement` с `?` и `setString`. База тогда ищет имя пользователя, которое буквально равно этой строке.
- Проверка по списку разрешённых — вариант, когда связанная переменная незаконна, например имя таблицы. Экранирование всего ввода перечислено как настоятельно не рекомендуемое.

**Examples:**

```java
String query = "SELECT account_balance FROM user_data WHERE user_name = ? ";
PreparedStatement pstmt = connection.prepareStatement(query);
pstmt.setString(1, custname);
ResultSet results = pstmt.executeQuery();
```

Мобильный проект — когда раскладка, цели касания или user agent меняют поведение. Проект рабочего стола — когда не меняют.

```ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({

});
```

### Что такое responsive testing, and how is it conducted?

**Definition:**

```ts
import { test, expect } from '@playwright/test';

test.use({ viewport: { width: 1600, height: 1200 } });

test('my test', async ({ page }) => {

});
```

### Опишите different types of test automation frameworks (e.g., data-driven, keyword-driven, hybrid, modular).

**Definition:**

Глоссарий ISTQB определяет две техники скриптов: тестирование, управляемое данными, хранит входы и ожидаемые результаты в данных, а тестирование по ключевым словам хранит ключевые слова высокого уровня в скрипте и низкоуровневые реализации во вспомогательных файлах. Модульный и гибридный — это то, как эти идеи сочетаются в наборе.

**How it works:**

#### Четыре формы

- Управляемый данными: один скрипт, много строк. `test.each` в Jest и `@pytest.mark.parametrize` в pytest — уже приведённые реализации.
- По ключевым словам: скрипт перечисляет фразы; другой файл их выполняет.
- Модульный: объекты страниц Playwright держат локаторы и действия в одном классе на страницу.
- Гибридный: объект страницы (модульный), метод которого вызывается по разу на строку `test.each` (управляемый данными).

**When to use:**

Управляемый данными — когда меняются только данные. Ключевые слова — когда не-разработчики должны переставлять шаги. Объекты страниц — когда одни и те же экраны повторяются.

**Examples:**

`test.each([[1, 1, 2], [1, 2, 3]])('.add(%i, %i)', (a, b, expected) => { expect(a + b).toBe(expected); })` — управляемый данными. Класс `PlaywrightDevPage`, которым пользуется этот тест, — модульная часть.

### Что такое API testing, and why is it important?

**Definition:**

Тестирование API проверяет сообщения между приложениями, не водя весь UI. Pact описывает эти сообщения как HTTP-запрос и ответ или сообщение в очереди. k6 и Postman отправляют HTTP-вызовы напрямую.

Клиенту магазина нужен один запрос списка товаров, один чтобы создать заказ и один чтобы войти клиенту. Postman — место, где эти три вызова отправляют и ответы осматривают.

### Как you approach testing RESTful APIs?

**Definition:**

Отправьте HTTP-запрос с параметрами, заголовками и авторизацией, которых требует API, затем проверьте ответ. Postman — интерактивный клиент. k6 — скриптовый клиент с проверками.

**How it works:**

#### Что документы показывают утверждать

- Postman: соберите запрос (параметры, заголовки, тело), отправьте его и осмотрите ответ. Переменные и окружения переиспользуют значения. Vault хранит секреты.
- Пример k6 постит JSON с `Content-Type: application/json` и проверяет статус 200, этот заголовок и поле в теле JSON.
- Авторизация — отдельная тема Postman, когда API требует личность или доступ.

```javascript
const payload = JSON.stringify({ name: 'lorem', surname: 'ipsum' });
const headers = { 'Content-Type': 'application/json' };
const res = http.post('https://quickpizza.grafana.com/api/post', payload, { headers });

  'Post status is 200': (r) => res.status === 200,
  'Post Content-Type header': (r) => res.headers['Content-Type'] === 'application/json',
});
```

**Examples:**

### Что такое contract testing, and which tools support this type of API testing?

**Definition:**

**How it works:**

#### Как это делает Pact

- Потребительский тест порождает контракт из вызовов, которые он реально делает. Pact называет это consumer-driven и «contract by example», а не полной схемой каждого возможного состояния.

Применяйте, когда два сервиса должны продолжать соглашаться, особенно при многих потребителях. Одному приложению без удалённого соучастника контрактный тест не нужен.

**Examples:**

Веб-клиент, который читает только `name` и `price`, порождает контракт для этой пары. Сборка поставщика падает, если он перестаёт их возвращать. Неиспользуемое поле может измениться без падения Pact.
