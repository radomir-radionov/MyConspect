### Что такое Docker, and how is it different from virtual machines?

**Definition:**

Docker - это платформа контейнеризации, которая упрощает развертывание приложений, обеспечивая равномерную работу программного обеспечения и его зависимостей в любой инфраструктуре, от ноутбуков до серверов и облака.

Использование Docker позволяет объединять код и зависимости в образ контейнера, который затем можно запускать в любой Docker-совместимой среде. Этот подход является значительным улучшением по сравнению с традиционными виртуальными машинами, которые менее эффективны и имеют более высокие накладные расходы.

**How it works:**

Ключевые компоненты Docker

- **Docker Daemon**: постоянный фоновый процесс, который управляет и выполняет контейнеры.
- **Docker Engine**: CLI и API для взаимодействия с демоном.
- **Docker Registry**: репозиторий для Docker-образов.

Строительные блоки

- **Dockerfile**: текстовый документ, содержащий команды, которые собирают образ контейнера.
- **Изображение**: автономный исполняемый пакет, содержащий все необходимое для запуска программного обеспечения.
- **Container**: экземпляр образа во время выполнения.

Виртуальные машины и контейнеры Docker

Виртуальные машины

Преимущества:

- **Изоляция**: виртуальные машины работают с отдельными операционными системами, обеспечивая строгую изоляцию приложений.

Неэффективность

- **Ресурсные накладные расходы**: для каждой виртуальной машины требуется операционная система, потребляющая оперативную память, хранилище и процессор. Запуск нескольких виртуальных машин может привести к избыточному использованию ресурсов.
- **Время медленной загрузки**: при загрузке виртуальной машины запускается целая ОС, что замедляет развертывание.

Контейнеры

Эффективность:

- **Оптимизация ресурсов**: поскольку контейнеры совместно используют ядро ОС хоста, они исключительно легкие, требуют минимального объема оперативной памяти и хранилища.
- **Быстрое развертывание**: контейнеры запускаются почти мгновенно, ускоряя как разработку, так и производство.

Предупреждения по изоляции:

- **Application-Level Isolation**: в то время как Docker обеспечивает отделение контейнеров от хоста и других контейнеров, он полагается на ОС хоста для базовых ресурсов.

Основные уникальные особенности Docker

- **Слоистая файловая система**: Docker-образы состоят из слоев, каждый из которых представляет собой набор изменений файлов. Эта структура помогает минимизировать размер образа и оптимизировать сборки.

- **Контейнерная оркестрация**: такие технологии, как Kubernetes и Docker Swarm, позволяют управлять кластерами контейнеров, предоставляя такие функции, как балансировка нагрузки, масштабирование и автоматизированные развертывания и откаты.

- **Интероперабельность**: Docker-контейнеры портативны и стабильно работают в различных средах. Кроме того, Docker дополняет множество других инструментов и платформ, включая Jenkins для конвейеров CI/CD и AWS для облачных сервисов.

**Examples:**

Пример кода: Dockerfile

Вот Docker-файл:

```dockerfile
FROM python:3.8

WORKDIR /app

COPY requirements.txt requirements.txt

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]
```

### Можете ли вы explain what a Docker image is?

**Definition:**

Образ Docker - это легкий, автономный и исполняемый программный пакет, который включает в себя все необходимое для запуска части программного обеспечения, включая код, среду выполнения, библиотеки, переменные среды и файлы конфигурации.

Он обеспечивает согласованность между средами, гарантируя, что каждый экземпляр образа идентичен, что является ключевым принципом философии Docker build-once-run-here.

**How it works:**

Изображение и контейнер

- **Изображение**: статический пакет, который включает в себя все, что требуется приложению для запуска.
- **Контейнер**: Операционный экземпляр образа, выполняющийся как процесс на хост-машине.

Многоуровневая файловая система

Docker-образы содержат множество слоев, каждый из которых представляет собой отдельную модификацию файловой системы. Слои доступны только для чтения, а конечный слой контейнера - для чтения/записи, что обеспечивает эффективность и гибкость.

Основные составляющие

- **Операционная система**: традиционные образы имеют полную или индивидуальную ОС, адаптированную к потребностям приложения. Однако последние разработки, такие как образы «distroless», сосредоточены исключительно на зависимостях приложений.
- **Код приложения**: Ваш код и файлы, которые указываются при сборке образа.

Реестры образов

Образы хранятся в реестрах образов Docker, таких как Docker Hub, который обеспечивает центральное расположение для управления и совместного использования образов. Вы можете загружать существующие образы, изменять их и загружать измененные версии, что позволяет командам эффективно сотрудничать.

Как создать имидж

- **Dockerfile**: описывает шаги и действия, необходимые для настройки образа, от выбора базовой ОС до копирования кода приложения.
- **Команда сборки**: команда сборки Docker использует Dockerfile в качестве чертежа для создания образа.

Преимущества образов Docker

- **Переносимость**: Docker-образы обеспечивают согласованное поведение в различных средах, от разработки до производства.
- **Воспроизводимость**: если вы используете один и тот же образ, вы можете ожидать того же поведения приложения.
- **Эффективность**: многоуровневая файловая система уменьшает избыточность и ускоряет развертывание.
- **Безопасность**: четкие слои позволяют осуществлять детальный контроль безопасности.

Рекомендации для Dockerfiles

По возможности используйте официальный базовый образ.
Стремитесь к минимальным слоям для лучшей эффективности.
Регулярно обновляйте базовый образ для обеспечения безопасности и обновления функций.
Уменьшите количество установленных пакетов, чтобы свести к минимуму риски безопасности.

**Examples:**

Пример кода: Dockerfile

Вот Docker-файл:

```dockerfile
# Use a base image
FROM ubuntu:latest

# Set the working directory
WORKDIR /app

# Copy the current directory contents into the container at /app
COPY . /app

# Specify the command to run on container start
CMD ["/bin/bash"]
```

### Как a Docker container differ from a Docker image?

**Definition:**

Docker-образы служат шаблонами для контейнеров, в то время как Docker-контейнеры выполняют экземпляры этих образов.

**How it works:**

Ключевые отличия

- **Состояние**: контейнеры инкапсулируют как код приложения, так и его среду выполнения в стабильное и согласованное состояние. Напротив, образы пассивны и не меняются после создания.

- **Изменяемое и неизменяемое**: контейнеры, как и любой запущенный процесс, могут изменять свое состояние. Напротив, образы неизменны и не меняются после построения.

- **Использование диска**: контейнеры имеют как записываемые слои (например, журналы или файлы конфигурации), так и слои, доступные только для чтения (слои образа), что со временем может привести к увеличению использования диска. Однако использование Docker многоуровневого хранилища ограничивает этот рост.

С другой стороны, образы доступны только для чтения, то есть каждый экземпляр, основанный на одном и том же образе, не занимает дополнительное дисковое пространство.

Docker Image vs Container

Практическая демонстрация

Создание образа - используйте команду docker build для создания образа.
```shell
docker build -t myapp .
```

Создание контейнеров — запустите собранный образ через docker run, чтобы создать контейнер.
Просмотр контейнеров - команды docker container ls или docker ps отображают активные контейнеры.

Изменение контейнеров — например, содержимое контейнера можно изменить, войдя в него через docker exec.

```shell
docker exec -it mycontainer /bin/bash
```

Остановка и удаление контейнеров - это можно сделать с помощью команд docker stop и docker rm или в сочетании с флагом -f.
Очистка образов - удалите все неиспользуемые образы, чтобы сэкономить место для хранения.
```shell
docker image prune -a
```

**Examples:**

Code:

Dockerfile - определяет образ:

```dockerfile
# Set the base image
FROM python:3.8

# Set the working directory
WORKDIR /app

# Copy the current directory contents into the container at /app
COPY . /app

# Install any needed packages specified in requirements.txt
RUN pip install --trusted-host pypi.python.org -r requirements.txt

# Make port 80 available to the world outside this container
EXPOSE 80

# Define environment variable
ENV NAME World

# Run app.py when the container launches
CMD ["python", "app.py"]
```

```shell
# Run a single command within a new container
docker run myapp python my_script.py
# Run a container in detached mode and enter it to explore the environment
docker run -d -it --name mycontainer myapp /bin/bash
```

```shell
docker stop mycontainer
docker rm mycontainer
```

### Что такое the Docker Hub, and what is it used for?

**Definition:**

Docker Hub - это публичный облачный реестр для Docker-образов. Это центральный центр, где вы можете находить образы контейнеров Docker, управлять ими и обмениваться ими. По сути, это система контроля версий для Docker-контейнеров.

**How it works:**

Основные функции

- **Хранение образов**: как централизованное хранилище, Hub хранит ваши Docker-образы, делая их легкодоступными.

- **Управление версиями**: он сохраняет записи различных версий ваших образов, позволяя вам при необходимости вернуться к предыдущим итерациям.

- **Совместная работа**: это платформа для совместной работы, где над проектом могут работать несколько разработчиков, каждый из которых вносит свой вклад и использует один и тот же образ.

- **Ссылка на GitHub**: Docker Hub интегрируется с популярной платформой для размещения кода GitHub, позволяя автоматически создавать образы с использованием предопределенных контекстов сборки.

- **Автоматизация**: с помощью автоматических сборок вы можете быть уверены, что ваши образы обновлены и построены в соответствии с последними спецификациями.

- **Веб-перехватчики**: они позволяют запускать внешние действия, такие как конвейеры CI/CD, при возникновении определенных событий, расширяя возможности автоматизации вашего рабочего процесса.

- **Сканирование безопасности**: Docker Hub включает функции безопасности для защиты ваших приложений в контейнерах. Он может сканировать ваши образы на наличие уязвимостей и проблем безопасности.

Стоимость и ценообразование

- **Бесплатный уровень**: предлагает один частный репозиторий и неограниченное количество общедоступных репозиториев.
- **Профессиональный и командный уровни**: оба оснащены расширенными функциями. Уровень группы обеспечивает возможности совместной работы для организаций.

Основные преимущества и ограничения

Преимущества:

Централизованное распределение контейнеров

Возможности для безопасности

Интеграция с инструментами CI/CD

Поддержка нескольких архитектур

Ограничения:

Ограниченные частные репозитории в бесплатном плане

Могут потребоваться дополнительные меры безопасности для чувствительных рабочих нагрузок

**When to use:**

Варианты использования

- **Публичные репозитории**: они идеально подходят для совместного использования ваших приложений с открытым исходным кодом с сообществом. Docker Hub является домом для множества публичных репозиториев, каждый из которых расширяет функциональность Docker.

- **Частные репозитории**: для ситуаций, требующих конфиденциальности или обеспечения соответствия в регулируемых средах, Docker Hub позволяет поддерживать частные репозитории.

### Объясните the Dockerfile and its significance in Docker.

**Definition:**

Одной из определяющих особенностей Docker является использование Dockerfiles для автоматизации создания образов контейнеров. Dockerfile - это текстовый документ, содержащий все команды, которые пользователь может вызвать в командной строке для сборки образа.

**How it works:**

Основные команды

- **FROM**: Устанавливает базовый образ для последующих этапов сборки.
- **RUN**: Выполняет команды внутри образа, а затем фиксирует изменения.
- **EXPOSE**: информирует Docker о том, что контейнер прослушивает на определенном порту.
- **ENV**: Устанавливает переменные среды.
- **ADD/COPY**: добавляет файлы из контекста сборки в образ.
- **CMD/ENTRYPOINT**: Определяет, какую команду запускать при запуске контейнера.

Многоступенчатые сборки

- **FROM**: позволяет выполнять несколько этапов сборки в одном Docker-файле.
- **COPY --from=source**: Позволяет копировать с другого этапа сборки, полезно для извлечения артефактов сборки.

Сохранённые образы

Docker использует кэширование для ускорения процессов сборки. Если слой изменяется, Docker перестраивает его и все, что от него зависит. Часто это приводит к случайным провалам кэша, что делает сборки медленнее, чем ожидалось.

Для оптимизации разместите команды, которые часто меняются (например, копирование файлов или установка пакетов), ближе к концу файла.

Docker Build Доступ к удаленному репозиторию Docker Cloud. Контекст сборки - это абсолютный путь или URL-адрес каталога, содержащего Dockerfile.

Советы по написанию эффективных Dockerfiles

- **Используйте конкретные базовые образы**: начните с самого легкого, подходящего образы, чтобы сохранить компактность сборки.
- **Комбинировать команды**: Связывание команд с && (где это возможно) уменьшает количество слоев, повышая эффективность.
- **Удаление ненужных файлов**: удаляйте файлы, которые не требуются вашему приложению, особенно временные файлы сборки или кэшированные ресурсы.

**Examples:**

Пример кода: Dockerfile для веб-сервера Node.js

Вот Docker-файл:

```dockerfile
# Use a specific version of Node.js as the base
FROM node:14-alpine

# Set the working directory in the container
WORKDIR /app

# Copy package.json and package-lock.json first to leverage caching when the
# dependencies haven't changed
COPY package*.json ./

# Install NPM dependencies
RUN npm install --only=production

# Copy the rest of the application files
COPY . .

# Expose port 3000
EXPOSE 3000

# Start the Node.js application
CMD ["node", "app.js"]
```

### Как Docker use layers to build images?

**Definition:**

Docker следует подходу многоуровневой файловой системы, используя файловые системы Union, такие как AUFS, OverlayFS и Device Mapper, для стекирования слоёв образа.

Эта структура повышает модульность, эффективность хранения и скорость создания образов. Он также предлагает доступные только для чтения слои для обеспечения согласованности и целостности образов.

**How it works:**

Файловые системы Union

Файловые системы Union позволяют складывать несколько каталогов или файловых систем, представляя их согласованно как единое целое. В то время как несколько таких систем используются, AUFS и OverlayFS особенно популярны.

- **AUFS**: долгое время являясь лидером, AUFS предлагает универсальную совместимость, но не является частью ядра Linux.
- **OverlayFS**: теперь интегрирована в ядро Linux, OverlayFS легкая и обеспечивает обратную совместимость с ext4 и XFS.

Слои образа в Docker

При укладке слоёв образа Docker это похоже на файловую систему со слоями только для чтения, наложенными на записываемый слой, слой контейнера. Эта настройка обеспечивает разделение и постоянство:

- **Базовый уровень образов **: это основа, часто включающая операционную систему и основные утилиты. Это в основном доступно только для чтения, чтобы обеспечить единообразие.

- **Промежуточные слои**: они взаимозаменяемы и инкапсулируют дискретные модификации. Следовательно, они также в основном доступны только для чтения.

- **Верхний или контейнерный слой**: этот слой записывает изменения, сделанные в контейнере в режиме реального времени, и является изменяемым.

Наложения кода

Code:

Каждый слой определяется инструкцией Dockerfile.
Базовый образ ubuntu:latest, а код приложения хранится в файле app.py.

**Examples:**

```dockerfile
# Layer 1: Start from base image
FROM ubuntu:latest

# Layer 2: Set the working directory
WORKDIR /app

# Layer 3: Copy the application code
COPY app.py /app

# Placeholder for Dockerfile
# ...
```

<summary>В чём разница между командами `COPY` и `ADD` в Dockerfile?</summary>

### В чём разница между командами `COPY` и `ADD` в Dockerfile?

**Definition:**

Давайте рассмотрим тонкие различия между командами COPY и ADD в Dockerfile.

**How it works:**

Цель

- **COPY**: предназначен для простого копирования файлов и каталогов. Это предпочтительный выбор для большинства вариантов использования.
- **ADD**: предлагает дополнительные функции, такие как поддержка URI. Однако, поскольку он более мощный, часто рекомендуется придерживаться COPY, если вам специально не нужны дополнительные возможности.

Ключевые отличия

- **Извлечение URI и TAR**: только ADD позволяет использовать URI (включая URL-адреса HTTP), а также автоматически извлекать локальные ресурсы .tar. Для простой передачи файлов COPY является подходящим выбором.
- **Соображения о кэше**: в отличие от COPY, которое уважает кэш сборки образов, ADD обходит кэш для любых ресурсов, которые даже незначительно отличаются от их записей в кэше. Это может привести к замедлению сборки.
- **Последствия для безопасности**: поскольку ADD позволяет загружать файлы во время сборки, это создаёт потенциальную угрозу безопасности. В сценариях, когда URL-адрес не контролируется, а файл не тщательно проверяется, предпочтительнее COPY.
- **Владение файлами**: Хотя как COPY, так и ADD сохраняют право собственности на файлы и разрешения во время процесса сборки, могут быть отклонения для конкретной ОС. Последовательное поведение часто является критическим фактором, что делает COPY более безопасным выбором.
- **Простота и прозрачность**: использование исключительно COPY, когда это возможно, обеспечивает ясность и упрощает управление Dockerfile. Например, другому разработчику или системе CI/CD легче понять простую команду COPY, чем выяснить сложные детали команды ADD, которая включает в себя извлечение файлов на основе URL-адресов или извлечение TAR.

Передовой опыт

- **Избегайте веб-передач**: избегайте извлечения ресурсов из недоверенных URL-адресов в Dockerfiles. Безопаснее копировать эти ресурсы в контекст сборки, обеспечивая безопасность и воспроизводимость.

- **Управление кэшем**: поскольку ADD может обходить кэширование для ресурсов, которые даже минимально отличаются от их кэшированных версий, это может непреднамеренно привести к замедлению процессов сборки. Чтобы избежать этого, предпочитайте детерминированное, удобное для кэширования поведение COPY, когда это возможно.

### В practice, how do you reduce the size of Docker images?

**Definition:**

Сокращение размеров образов Docker имеет решающее значение для эффективного развертывания ресурсов. Это можно достичь с помощью различных стратегий.

**How it works:**

Многоступенчатые сборки

Многоступенчатые сборки позволяют использовать несколько этапов Dockerfile, разделяя различные аспекты вашего процесса сборки. Это обеспечивает более чистое разделение между библиотеками времени сборки и времени выполнения, что в конечном итоге приводит к уменьшению размеров образов.

Флаг --from в инструкциях COPY и RUN здесь является ключевым, так как он позволяет выбирать артефакты из предыдущего этапа сборки.

Файл .dockerignore

Подобно .gitignore, файл .dockerignore исключает файлы и папки из контекста сборки Docker. Это может значительно уменьшить размер вашего контекста сборки, что приведет к более компактным образам.

Вот пример файла .dockerignore:

node_modules
npm-debug.log

Использование меньших базовых образов

Выбор минималистичного базового образа может привести к значительно меньшему размеру контейнеров. Для node.js вы можете выбрать более лёгкий базовый образ, такое как node:alpine, особенно для использования в производстве. Версия alpine особенно легкая, так как она построена на дистрибутиве Alpine Linux.

Вот образы разных размеров:

node:current-slim (около 200 МБ)
node:alpine (около 90МБ)
узел:текущий (около 900 МБ)

Команды однократного выполнения

Использование команд RUN и многострочных COPY в одном слое Dockerfile может привести к раздутию образа. Чтобы этого избежать, используйте одну команду RUN, которая объединяет несколько операций. Такой подход снижает создание дополнительных слоев, что приводит к уменьшению размера образов.

Убедитесь, что вы всегда объединяете такие команды в одной инструкции RUN, разделяя их логическими операторами, такими как &&, и очищайте временные файлы или кэши, чтобы слой оставался минимальным.

Менеджеры пакетов и кэширование

При использовании менеджеров пакетов, таких как npm и pip, в ваших образах важно использовать флаг --production.

Для pip вы можете достичь того же с помощью:

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

Эта практика значительно уменьшает размер образа, включая только необходимые зависимости во время выполнения.

Используйте глобальные шаблоны для COPY

При использовании команды COPY в вашем Dockerfile лучше внедрить синтаксис .dockerignore, чтобы гарантировать, что копируются только необходимые файлы.

**Examples:**

Вот Dockerfile с многоступенчатой сборкой.

```dockerfile
# Use an official Node.js runtime as the base image
FROM node:current-slim AS build

# Set the working directory in the container
WORKDIR /app

# Copy the package.json and package-lock.json files to the workspace
COPY package*.json ./

# Install app dependencies
RUN npm install

# Copy the entire project into the container
COPY . .

# Build the app
RUN npm run build

# Use a smaller base image for the final stage
FROM node:alpine AS runtime

# Set the working directory in the container
WORKDIR /app

# Copy built files and dependency manifest
COPY --from=build /app/package*.json ./
COPY --from=build /app/dist ./dist

# Install production dependencies
RUN npm install --only=production

# Specify the command to start the app
CMD ["node", "dist/main.js"]
```

Вот пример:

```text
RUN apt-get update && apt-get install -y nginx && apt-get clean
```

Для npm выполнение следующей команды предотвращает установку зависимостей для разработки:

```text
RUN npm install --only=production
```

Вот пример:

```text
COPY ["*.json", "*.sh", "config/", "./"]
```

<summary>Объясните the use and significance of the `Docker-compose` tool.</summary>

### Объясните the use and significance of the `Docker-compose` tool.

**Definition:**

Docker Compose, инструмент командной строки, облегчает работу с многоконтейнерными приложениями Docker, используя файл YAML для определения их архитектуры и способов взаимодействия между ними. Это чрезвычайно полезно для настройки многоконтейнерных сред и позволяет запускать все соответствующие компоненты одной командой. Например, веб-приложению может понадобиться база данных на сервере, очередь сообщений и другие компоненты. Хотя вы можете запускать эти компоненты по отдельности, использование docker-compose делает это бесшовной операцией с одной командой.

**How it works:**

Основные преимущества

- **Упрощённое управление несколькими контейнерами**: С одной предустановленной конфигурацией запускайте и управляйте многоконтейнерными приложениями без усилий.
- **Оптимизированный процесс совместного использования окружений**: Согласованные настройки между командами и окружениями упрощают тестирование, подготовку и разработку.
- **Автоматическое взаимодействие между контейнерами**: Определяет сетевые конфигурации, такие как совместное использование томов и связывание сервисов, без дополнительных команд.
- **Параллельный запуск служб**: Эффективно запускает службы параллельно, ускоряя загрузку.

Основные компоненты

- **Сервисы**: Контейнеры, которые создаются на основе одного и того же образа, определённые в файле compose. Каждый из них является независимым компонентом (например, веб-сервер, база данных).
- **Тома**: Для постоянных данных, независимых от времени жизни контейнера. Полезны, например, для баз данных.
- **Сети**: Виртуальные сети для изоляции различных приложений или сервисов, поддержания их раздельного функционирования или помощи в коммуникации.

Пример конфигурации YAML

- **Сервисы**: упомянуты компоненты web и db. Они определяют образ, который будет использоваться, настройки порта, тома для сохранения данных и структуру зависимостей (например, как web зависит от db).

- **Тома**: В сервисе базы данных указан том для постоянного хранения.

- **Сети**: Веб- и базы данных являются частью сетей бэкенда, определённых внизу. Это обеспечивает стабильную работу сети, даже когда сервисы связываются друг с другом или контейнеры перезапускаются.

**Examples:**

Вот конфигурация YAML:

```yaml
version: '3.3'

services:
  web:
    image: nginx:latest
    ports:
      - "8080:80"
    volumes:
      - "/path/to/html:/usr/share/nginx/html"
    depends_on:
      - db

  db:
    image: postgres:latest
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password
      POSTGRES_DB: dbname
    volumes:
      - /my/own/datadir:/var/lib/postgresql/data
```

<summary>Опишите the different types of networks in Docker.</summary>

### Опишите the different types of networks in Docker.

**Definition:**

Сетевая подсистема Docker подключаемая. Драйверы, которые идут с движком: `bridge`, `host`, `overlay`, `ipvlan`, `macvlan` и `none`. Можно поставить и сетевой плагин.

**How it works:**

- `bridge` — умолчание. Контейнеры на одном мосту одного хоста видят друг друга. Снаружи к ним попадают через опубликованные порты. Без `--driver` команда `docker network create` создаёт bridge.
- `host` убирает сетевой namespace между контейнером и хостом. Контейнер пользуется стеком хоста.
- `overlay` соединяет демоны, чтобы сервисы Swarm и контейнеры говорили между узлами без маршрутов ОС между этими узлами.
- `ipvlan` даёт контроль адресов IPv4 и IPv6. VLAN-драйвер добавляет метки второго уровня и маршрутизацию L3 для underlay.
- `macvlan` выдаёт MAC, и контейнер выглядит физическим устройством. Демон маршрутизирует по MAC. Документация советует его старым приложениям, которые ждут место в физической сети.
- `none` изолирует контейнер от хоста и от других контейнеров. Для сервисов Swarm он недоступен.

**When to use:**

- `bridge` — контейнеры на одной машине.
- `overlay` — Swarm на нескольких хостах.
- `host` — когда общий стек хоста приемлем.
- `none` — контейнеру сеть не нужна.

**Examples:**

```console
docker network create -d overlay --attachable my-attachable-overlay
```

`--attachable` пускает на этот overlay и обычные контейнеры, не только сервисы Swarm.

### Можете ли вы explain how Docker’s default bridge network differs from a user-defined bridge network?

**Definition:**

- На пользовательском bridge контейнеры резолвят друг друга по имени или алиасу. На bridge по умолчанию они видят друг друга по IP, если не использовать устаревший `--link`.

**When to use:**

- Пользовательский bridge — для любого приложения из нескольких контейнеров.

<summary>Как resource constraints be applied to containers in Docker?</summary>

### Как resource constraints be applied to containers in Docker?

**Definition:**

По умолчанию контейнер берёт столько памяти и CPU, сколько позволит планировщик ядра. Флаги `docker run` ставят лимиты cgroup. `deploy.resources` в Compose задаёт limits и reservations сервиса.

**How it works:**

- `-m` / `--memory` — жёсткий максимум. Минимальное значение, которое можно поставить, — `6m`.
- `--memory-swap` — сумма памяти и swap, и он имеет смысл только вместе с `--memory`. Одинаковые значения отключают swap. Незаданный `--memory-swap` при заданном `--memory` разрешает swap того же размера, если на хосте есть swap. `-1` — swap без лимита, вплоть до хоста.
- `--memory-reservation` — мягкий лимит и должен быть ниже `--memory`. `--memory-swappiness` — от 0 до 100. `0` выключает swap анонимных страниц. Умолчание — значение хоста.
- `--cpus=0.5` ограничивает контейнер половиной CPU. Это то же, что `--cpu-period=100000` и `--cpu-quota=50000`. `--cpu-shares` (умолчание 1024) — вес, и он действует, только когда CPU занят.
- `--oom-kill-disable` не ставят без `--memory`. OOM killer ядра не даёт одному контейнеру уронить хост. Docker снижает OOM-приоритет демона, чтобы убили скорее контейнер, чем демон.
- `deploy.resources.limits` в Compose задаёт `cpus` и `memory` для той же идеи на одном хосте.

**Examples:**

```console
docker run -it --cpus=".5" --memory="300m" ubuntu /bin/bash
```

**Sources:**

- [Docker — Resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)
- [Docker — Compose deploy](https://docs.docker.com/reference/compose-file/deploy/)

### Что такое Docker security profiles, and how do they work?

**Definition:**

Seccomp — возможность ядра Linux, которой Docker ограничивает системные вызовы внутри контейнера. Профиль по умолчанию — список разрешённых вызовов. Документация не советует его менять без причины.

**How it works:**

- У профиля по умолчанию `defaultAction` равен `SCMP_ACT_ERRNO` (доступ запрещён), а отдельные вызовы переведены в `SCMP_ACT_ALLOW`. Он отключает порядка 44 вызовов из 300+.

**When to use:**

- Профиль по умолчанию оставляют включённым.
- Свой профиль — только если приложению нужен вызов, который умолчание блокирует, и вы можете его назвать.
- `unconfined` — короткая диагностика, не настройка production.

**Examples:**

```console
docker run --rm -it --security-opt seccomp=/path/to/seccomp/profile.json hello-world
```

### Что такое the puRPOse of a Docker Healthcheck?

**Definition:**

`HEALTHCHECK` говорит демону, как проверить, что процесс в контейнере ещё делает полезную работу. Живого PID недостаточно: веб-сервер может зависнуть и остаться процессом 1.

**How it works:**

- Первые 4096 байт stdout и stderr сохраняются и видны в `docker inspect`. Смена статуса порождает событие `health_status`.

**Examples:**

```dockerfile
HEALTHCHECK --interval=5m --timeout=3s \
```

### Опишите how you would handle sensitive data with Docker.

**Definition:**

Пароли, ключи и сертификаты не кладут в образ и Dockerfile. Для сервисов Swarm секреты Docker хранят эти данные в шифрованном виде и монтируют только в сервисы, которым выдали доступ.

**How it works:**

- Секрет уходит менеджеру по mutual TLS и лежит в шифрованном журнале Raft. Журнал реплицируется на других менеджеров.

- Секрет есть только у менеджеров и у узлов, где крутится задача с доступом. Когда задача останавливается, секрет размонтируют и стирают из памяти узла.
- Секреты — для сервисов Swarm, не для одиночных контейнеров. Документация предлагает один реплику (`scale` 1), если секрет нужен без переделки контейнера в многорепличный сервис.
- Лимит размера в документации — 500 КБ. Несекретные файлы можно отдать конфигами: они монтируются обычными файлами, не RAM-диском.
- `docker secret rm` не удалит секрет, который ещё использует запущенный сервис.

**When to use:**

- Секреты Swarm — пароли и TLS-ключи, которые сервису нужны в runtime.
- Config — для несекретных файлов.

### Что такое Docker Swarm, and when would you use it?

**Definition:**

Swarm mode — оркестратор внутри Docker Engine. Его включают командой `docker swarm init`. Сервисы планируются по узлам, которые вошли в swarm.

**How it works:**

- Менеджер принимает `docker service` и `docker stack`. `docker stack deploy` читает файл Compose и создаёт сервисы. Гид деплоя предупреждает, что команда ждёт старый формат Compose file version 3, а не последнюю спецификацию Compose.
- Образы должны лежать в реестре, откуда узлы могут их скачать. Гид использует Docker Hub или локальный сервис реестра.
- Routing mesh публикует порт сервиса на каждом узле и ведёт трафик к задаче.
- Секреты и overlay — возможности Swarm. `none` не является сетевым драйвером Swarm.
- Локальный пробный swarm покидают командой `docker swarm leave --force`.

**When to use:**

- Несколько хостов Docker должны крутить одно приложение, и вы остаётесь внутри Docker Engine.
- Одному хосту Swarm не нужен. `docker compose up` запускает стек на одном движке. Гид говорит, что Compose не раскладывает контейнеры по узлам swarm.

**Examples:**

```console
docker swarm init
docker stack deploy --compose-file compose.yaml stackdemo
```

### Можете ли вы explain the difference between Docker Swarm and Kubernetes?

**Definition:**

- Секреты Swarm — возможность Docker для сервисов swarm. У Kubernetes свой объект Secret. Одно хранилище другим не является.
- Swarm выбирают, когда кластер должен остаться на CLI Docker. Kubernetes — когда платформа, куда вы деплоите, уже кластер Kubernetes.

### Что такое Docker stack?

**Definition:**

Стек — группа сервисов, вместе выложенных из файла Compose на swarm. `docker stack deploy` создаёт сервисы и сеть, чьи имена получают префикс имени стека.

**How it works:**

- Файл в гиде — `compose.yaml` с картой `services`. Команда — `docker stack deploy --compose-file compose.yaml stackdemo`. Последний аргумент — имя стека.
- Деплой в гиде печатает `Ignoring unsupported options: build`. Образ сначала собирают и пушат в реестр. Узлы Swarm его скачивают. Они не собирают образ из контекста вашего ноутбука.
- `docker stack services STACK` показывает сервисы и число реплик. `docker stack rm STACK` удаляет сервисы и сеть стека.
- `docker compose up` — не деплой стека. На движке в swarm mode он всё равно сажает все контейнеры на текущий узел.

**Sources:**

- [Docker — Deploy a stack to a swarm](https://docs.docker.com/engine/swarm/stack-deploy/)

<summary>Как you deploy an application stack in Docker Swarm?</summary>

### Как you deploy an application stack in Docker Swarm?

**Definition:**

Включают swarm mode, пушат образы в реестр и с менеджера запускают `docker stack deploy`.

**How it works:**

1. `docker swarm init` на менеджере. Остальные движки входят в этот swarm.
2. Образы кладут в реестр. Пример гида тегирует веб-образ `127.0.0.1:5000/stackdemo` и выполняет `docker compose push`.
3. С менеджера: `docker stack deploy --compose-file compose.yaml stackdemo`.
4. `docker stack services stackdemo` должен показать реплики вроде `1/1`, когда узлы скачают образы.
5. Опубликованный порт доступен на любом узле через routing mesh.
6. `docker stack rm stackdemo` стек снимает.

**Examples:**

```console
docker stack deploy --compose-file compose.yaml stackdemo
```

**Sources:**

- [Docker — Deploy a stack to a swarm](https://docs.docker.com/engine/swarm/stack-deploy/)

### Как Docker manage service replication and load balancing?

**Definition:**

Сервис Swarm держит заданное число задач. Routing mesh отправляет трафик, пришедший на опубликованный порт, этим задачам.

**How it works:**

- `deploy.mode` в Compose для долгого сервиса — `replicated` (умолчание, заданное число задач) или `global` (одна задача на узел). Задачи-jobs используют `replicated-job` или `global-job` и завершаются, когда работа кончилась.
- `docker stack services` печатает `REPLICAS` как запущено/желаемо, например `1/1`.
- В гиде стека порт `8000` веб-сервиса отвечает на каждом узле. Запрос на адрес другого узла уходит в сервис. Это routing mesh.
- `deploy.resources.limits` ограничивает CPU и память этих задач. Limits движок не даёт превысить. Reservations — то, что планировщик должен суметь выдать.

**Examples:**

```yaml
services:
  web:
    image: 127.0.0.1:5000/stackdemo
    ports:
      - "8000:8000"
    deploy:
      mode: replicated
      replicas: 3
```

### Можете ли вы describe how you would execute a command inside a running container?

**Definition:**

`docker exec` запускает новый процесс внутри работающего контейнера. PID 1 контейнера должен быть жив. Процесс exec не перезапускается, если перезапускается контейнер.

**How it works:**

- Команда должна быть исполняемым файлом. `docker exec -it my_container sh -c "echo a && echo b"` работает. Вся цепочка в кавычках как один исполняемый файл — нет.
- `-i` держит STDIN открытым. `-t` выделяет TTY. `-d` запускает в фоне. `-w` задаёт рабочий каталог. `-e` задаёт переменную только этому процессу.
- `-u` задаёт пользователя. `--privileged` расширяет привилегии. Справка exec отсылает этот флаг к `docker run --privileged`.
- `docker exec` падает, если контейнер на паузе. Сначала его снимают с паузы.
- Рабочий каталог по умолчанию — тот, что задали при создании контейнера.

**Examples:**

```console
docker exec -it mycontainer sh
```

**Sources:**

- Вывод healthcheck отдельно. `docker inspect` хранит первые 4096 байт stdout и stderr команды проверки.

<summary>Объясните the importance of minimizing the number of layers in a Dockerfile.</summary>

### Объясните the importance of minimizing the number of layers in a Dockerfile.

**Definition:**

Каждая инструкция, которая меняет файловую систему, добавляет слой. Лишние слои увеличивают размер и записи кэша. Команды склеивают ради меньшего образа и меньшего числа устаревших слоёв, а не ради одной строки любой ценой.

**How it works:**

- `RUN`, `COPY` и `ADD` создают слои. `ENV` и метаданные тоже влияют на образ, но размер обычно раздувают файлы, оставшиеся в `RUN`.
- `RUN`, который ставит пакеты и удаляет кэш пакетов следующей инструкцией, оставляет кэш в предыдущем слое. Удаляют его в том же `RUN`.
- Порядок всё ещё важен для кэша сборки. Файлы, которые часто меняются, копируют поздним `COPY`, чтобы ранние слои остались в кэше.
- Многостадийная сборка вообще не отдаёт слой компилятора. Финальная стадия копирует только артефакт. Это уменьшает размер сильнее, чем склейка двух `RUN`.

**Examples:**

```dockerfile
RUN apt-get update && apt-get install -y curl \
  && rm -rf /var/lib/apt/lists/*
```

**Sources:**

- [Docker — Dockerfile reference](https://docs.docker.com/reference/dockerfile/)
- [Docker — Building best practices](https://docs.docker.com/build/building/best-practices/)

**When to use:**

- Любая сборка, в каталоге которой есть зависимости, логи или секреты.
- Без файла можно обойтись, только если в каталоге контекста и так лежат лишь файлы, которые копирует Dockerfile.

### Почему is it advised to run only one process per container?

**Definition:**

Жизненный цикл контейнера следует за PID 1. `docker stop`, healthcheck и логи определены для этого процесса. Несколько несвязанных серверов в одном контейнере прячут, кто именно упал.

**How it works:**

- `HEALTHCHECK` проверяет одну команду. Если соседний процесс в том же контейнере умер, команда проверки всё ещё может выйти с кодом 0.
- `docker logs` показывает stdout и stderr PID 1. Второй процесс, пишущий в файл, невидим, пока его не перенаправят.
- `docker exec` и политика перезапуска действуют на контейнер, не на лишний демон рядом с PID 1.
- Масштаб — это больше контейнеров. `replicas` Swarm и сервисы Compose — единица масштаба, не лишние процессы в одном контейнере.
- Общий сетевой namespace — исключение. Предпочтительнее два контейнера на одном пользовательском bridge.

### Как следует you handle logging in Docker containers?

<summary>Как бы вы diagnose high CPU or memory usage in a container?</summary>

### Как бы вы diagnose high CPU or memory usage in a container?

**Definition:**

Сравнивают, сколько контейнеру разрешено, с тем, сколько он берёт. Лимиты приходят из `docker run` (`--memory`, `--cpus`) или из `deploy.resources.limits` в Compose. Потребление смотрят, пока он работает.

**How it works:**

- `docker inspect` показывает HostConfig, включая память и CPU, которые вы передали.
- `docker stats` печатает живой процент CPU и строку памяти по каждому запущенному контейнеру.
- Если ядро убивает контейнер по OOM, кончилась память хоста или контейнер упёрся в лимит. Гид по ресурсам не велит отключать OOM killer без `--memory`. Запись об убийстве в состоянии `docker inspect` значит, что лимит или хост были малы.
- `--cpus` троттлит. Контейнер продолжает работать, но не может взять больше этой доли.
- Чинка — починить приложение или поднять лимит. Лимит без RAM на хосте роняет другие процессы. Гид говорит, что OOM-оценка демона снижена, чтобы скорее убили контейнер, чем демон.

**Examples:**

```console
docker stats
docker run -it --cpus=".5" --memory="300m" ubuntu /bin/bash
```

**Sources:**

- [Docker — Resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)
- [Docker — docker container stats](https://docs.docker.com/reference/cli/docker/container/stats/)

<summary>Какие шаги вы предпримете, если container постоянно падает сразу после запуска?</summary>

### Какие шаги вы предпримете, если container постоянно падает сразу после запуска?

**Definition:**

Смотрят, почему вышел PID 1, затем статус здоровья, если проверка задана. Контейнер перезапускается или остаётся exited, потому что этот процесс остановился.

**How it works:**

- `docker ps -a` включает вышедшие контейнеры. `docker logs CONTAINER` показывает STDOUT и STDERR упавшего процесса.
- `docker inspect` показывает `State.ExitCode` и, если есть `HEALTHCHECK`, журнал здоровья. Код `1` команды проверки помечает контейнер unhealthy после `--retries` неудач (по умолчанию 3).
- Контейнер на паузе не упал. `docker exec` падает, пока паузу не снимут. Справка exec показывает эту ошибку.
- Если процесс не может занять порт или разрешить имя, смотрят сеть. На пользовательском bridge другой контейнер доступен по имени. На bridge по умолчанию — нет.
- Нет нужного файла или плохая команда в `CMD` — процесс выходит сразу. `CMD` в Dockerfile и есть PID 1.

**Examples:**

```console
docker logs CONTAINER
docker inspect CONTAINER
```

<summary>В what scenarios would you prune Docker objects, and how?</summary>

### В what scenarios would you prune Docker objects, and how?

**Definition:**

`docker system prune` удаляет неиспользуемые данные: остановленные контейнеры, сети без контейнера, висячие образы и неиспользуемый кэш сборки. Его запускают, когда диск забит остатками сборок, а не чтобы снести ещё нужный том.

**How it works:**

- Без флагов команда спрашивает подтверждение. `-f` / `--force` пропускает вопрос.
- Тома остаются, пока не передан `--volumes`. Документация так делает, чтобы том без контейнера не удалился случайно. `--volumes` чистит анонимные тома, которыми не пользуется контейнер.
- `-a` / `--all` удаляет и неиспользуемые образы, а не только висячие. Образ без контейнера подходит.
- `--filter until=24h` оставляет объекты новее этого срока. `--filter label=foo` выбирает по метке. Разные ключи фильтра — это И. Повтор одного ключа — ИЛИ.
- Кэш сборки, включая BuildKit `RUN --mount=type=cache`, всегда подходит для `docker system prune`. `docker builder prune` чистит только кэш сборки.
- `docker volume prune` удаляет неиспользуемые тома и оставляет том, на который ещё ссылается контейнер. Гид по томам говорит, что удаление контейнера том не удаляет.

**Examples:**

```console
docker system prune
```

- [Docker — Volumes](https://docs.docker.com/engine/storage/volumes/)

<summary>Какие типичные проблемы возникают при работе с Docker в CI/CD pipeline?</summary>

### Какие типичные проблемы возникают при работе с Docker в CI/CD pipeline?

**Definition:**

CI собирает образ и пушит его. Типичные сбои — размер контекста, кэш, двигающиеся теги и swarm, который не может скачать то, что вы только что собрали.

**How it works:**

- Контекст сборки — всё, что не исключил `.dockerignore`. Секреты и `node_modules` в этом каталоге замедляют сборку и могут попасть в слой.
- `docker stack deploy` игнорирует `build`. Пайплайн должен запушить образ. Узлы его скачивают. Тег, который есть только на runner CI, swarm не видит.
- `latest` — двигающийся тег. Фиксируйте версию или деплойте дайджест, напечатанный после push.
- `docker system prune` на общем runner удаляет неиспользуемые образы и кэш сборки. Следующая задача собирает больше. `--volumes` не передают на runner, где ещё лежат нужные данные.
- Кэш слоёв помогает, только если инструкции выше изменения те же. Ранний `COPY` всего исходника сбрасывает каждый следующий шаг.

**Sources:**

- [Docker — Deploy a stack to a swarm](https://docs.docker.com/engine/swarm/stack-deploy/)
- [Docker — docker system prune](https://docs.docker.com/reference/cli/docker/system/prune/)
- [Docker — Building best practices](https://docs.docker.com/build/building/best-practices/)

<summary>Как you define a multi-container application with `Docker-compose`?</summary>

### Как you define a multi-container application with `Docker-compose`?

**Definition:**

Файл Compose перечисляет сервисы. `docker compose up` создаёт контейнеры и сеть по умолчанию на одном движке. `compose.yaml` из гида стека — такой файл.

**How it works:**

- Каждый ключ под `services` — сервис. `image` выбирает образ. `build` собирает из Dockerfile. `ports` публикует порт. Веб-сервис гида ходит на хост `redis`, потому что Compose сажает оба на одну сеть, а DNS использует имя сервиса.
- `docker compose up -d` их запускает. `docker compose ps` показывает список. `docker compose down --volumes` останавливает и удаляет тома этого проекта.
- На движке, который ещё и в swarm mode, `docker compose up` всё равно запускает каждый контейнер на текущем узле. Предупреждение гида говорит взять `docker stack deploy`, чтобы разложить по swarm, и эта команда не понимает `build`.
- `deploy.resources` в спецификации Compose задаёт лимиты CPU и памяти. `docker stack deploy` использует старый файл Compose v3, не каждый ключ текущей спецификации.

**Examples:**

```yaml
services:
  web:
    image: 127.0.0.1:5000/stackdemo
    build: .
    ports:
      - "8000:8000"
  redis:
    image: redis:alpine
```

**Sources:**

- [Docker — Deploy a stack to a swarm](https://docs.docker.com/engine/swarm/stack-deploy/)
- [Docker — Compose deploy](https://docs.docker.com/reference/compose-file/deploy/)

### Какие соображения must be made when deploying Docker containers in a production environment?

**Definition:**

Production — это реестр, закреплённые образы, лимиты ресурсов, логи в stdout, секреты вне образа и healthcheck. У `docker run` на ноутбуке этого по умолчанию нет.

**How it works:**

- Образ пушат. Узлы Swarm его скачивают. На локальную сборку не рассчитывают.
- Ставят `--memory` и `--cpus` или `deploy.resources.limits` в Compose. Минимальный лимит памяти — `6m`.
- Профиль seccomp по умолчанию оставляют. `seccomp=unconfined` в production не передают.
- Секреты монтируют секретами Swarm (`/run/secrets/<name>`), а не паролями `ENV` в Dockerfile.
- Добавляют `HEALTHCHECK`. Логи идут в stdout. Висячие образы на хосте чистят, когда кончается диск, и тома не чистят, если эти данные ещё нужны.
- Несколько реплик нуждаются в overlay и routing mesh или в другом балансировщике, который ведёте вы.

<summary>Когда would you use a bind mount over a volume?</summary>

### Когда would you use a bind mount over a volume?

**Definition:**

Том — каталог, которым управляет Docker. Bind mount — выбранный вами путь на хосте, смонтированный в контейнер. Гид по томам говорит, что тома — обычный выбор для постоянных данных, а bind mount — когда хост и контейнер должны видеть одни и те же файлы.

**How it works:**

- Тома проще бэкапить и переносить, они работают в контейнерах Linux и Windows и могут быть общими для нескольких контейнеров. Они не следуют раскладке каталогов хоста.
- Bind mount зависит от пути и ОС хоста. Его берут, когда исходники правят на хосте или когда программа вне Docker должна читать этот каталог.
- Непустой том, смонтированный на каталог, прячет файлы, которые были в образе по этому пути. Пустой том получает копию этих файлов, если не задан `volume-nocopy`.
- У томов распространение `rprivate`. Перенастроить его нельзя.

**When to use:**

- Том — базы и данные приложения.
- Bind mount — локальное дерево исходников или файл хоста, которым нужно делиться.

**Sources:**

- [Docker — Volumes](https://docs.docker.com/engine/storage/volumes/)
</details>

<summary>Как you create a Docker volume, and what is its lifecycle?</summary>

### Как you create a Docker volume, and what is its lifecycle?

**Definition:**

`docker volume create` создаёт именованный том. Docker может создать том и при старте контейнера или сервиса. Том остаётся после удаления контейнера.

**How it works:**

- Том — каталог на хосте под управлением Docker, смонтированный в контейнер. Это не записываемый слой контейнера. Запись в записываемый слой медленнее из-за union filesystem драйвера хранения.
- Уничтожение контейнера уничтожает записываемый слой, не том. Том без контейнера остаётся, пока его не почистят.
- `docker volume prune` удаляет неиспользуемые тома. `docker system prune` их не трогает, пока не передан `--volumes`, и этот флаг чистит анонимные тома.
- Анонимный том получает случайное имя. Именованный — тот, который вы передали в `docker volume create`.
- Монтирование непустого тома прячет существующие файлы по этому пути контейнера. Монтирование пустого тома копирует файлы образа в том, если не задан `volume-nocopy`.

**Examples:**

```console
docker volume create app-data
```

**Sources:**

- [Docker — Volumes](https://docs.docker.com/engine/storage/volumes/)
- [Docker — docker system prune](https://docs.docker.com/reference/cli/docker/system/prune/)
</details>

<summary>Какие стратегии would you use for data persistence in Docker clusters?</summary>

### Какие стратегии would you use for data persistence in Docker clusters?

**Definition:**

Записываемый слой контейнера локален для этой задачи и умирает вместе с ней. Данные кластера должны жить на томе, который сможет смонтировать сменная задача, или в базе, которая уже реплицируется.

**How it works:**

- Именованные тома переживают контейнер на одном узле. Задача Swarm, переехавшая на другой узел, этот локальный том не видит. Задачу привязывают к узлу с данными или берут драйвер тома на общем хранилище.
- Гид по томам предпочитает тома bind mount для данных, которыми должен управлять Docker, и bind mount, когда нужен конкретный путь хоста.
- Пароли в слой образа тома не кладут. Секреты Swarm монтируются в `/run/secrets/<name>` и снимаются с узла, когда задача останавливается. Это не база.
- `docker system prune --volumes` удаляет неиспользуемые анонимные тома. Эту команду не запускают по дискам, где лежат данные кластера.
- У проекта Compose на одном узле `docker compose down --volumes` удаляет тома проекта. Флаг не ставят, если данные должны остаться.

**Sources:**

- [Docker — Volumes](https://docs.docker.com/engine/storage/volumes/)
- [Docker — Secrets](https://docs.docker.com/engine/swarm/secrets/)
- [Docker — Deploy a stack to a swarm](https://docs.docker.com/engine/swarm/stack-deploy/)
