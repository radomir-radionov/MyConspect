### XML Fundamentals

<details>
<summary>What is XML and what does it stand for?</summary>

### What is XML and what does it stand for?

**Definition:**

XML расшифровывается как Extensible Markup Language. Это текстовый формат для деревьев именованных элементов, чтобы две системы могли обмениваться документом, структура которого явна в тегах.

**How it works:**

- У элемента есть имя, необязательные атрибуты и содержимое: текст, дочерние элементы или оба.
- У документа один корневой элемент. Он корректно оформлен (well-formed), когда теги правильно вложены и закрыты, и действителен (valid), когда ещё и совпадает с DTD или схемой.
- Пространства имён не дают одному локальному имени столкнуться, когда словари смешиваются.
- Его используют для обмена данными, конфигурации и разметки документов. XPath выбирает узлы, XSLT их преобразует, XQuery запрашивает, XML Schema описывает.
- Он описывает структуру. Сам по себе он не показывает страницу и не запускает скрипт. Эту работу делает HTML с фиксированным словарём.
- Формат многословнее JSON. Он окупается, когда нужны смешанное содержимое, пространства имён или строгая схема.

**Examples:**

```xml
<order id="17"><sku>A1</sku><qty>2</qty></order>
```

Теги говорят, чем является каждое значение. Читателю не нужно гадать, что второе поле — количество.
</details>

<details>
<summary>What are the key features and benefits of XML?</summary>

### What are the key features and benefits of XML?

**Definition:**

XML — самоописывающее дерево в простом тексте. Теги едут вместе с данными, поэтому получатель видит структуру без отдельной схемы «сбоку».

**How it works:**

- Элементы вкладываются, поэтому значение может содержать структуру, а не только плоский список полей.
- Это текст, обычно Unicode, поэтому он пересекает платформы и языки без бинарной раскладки.
- Имена элементов придумываете вы (он расширяемый), а позже их можно ограничить схемой.
- Комментарии и инструкции обработки могут ехать в документе, не становясь данными.
- Схема даёт проверку: типы, какие дети обязательны и сколько их.
- Пространства имён позволяют смешивать словари. Версионирование — это в основном «добавить необязательный элемент» или новое пространство имён, чтобы старые читатели пропускали неизвестное, если их так написали.
- Выгода — совместимость и стандартный набор инструментов. Цена — размер и необходимость экранировать `<` и `&`.

**Examples:**

Поставщик добавляет `<note>` внутрь `<item>`, не ломая читателя, который смотрит только на `<sku>` и `<qty>`, если схема говорит, что заметка необязательна.
</details>

<summary>Explain the difference between XML and HTML.</summary>

### Explain the difference between XML and HTML.

**Definition:**

XML — набор средств для определения языков разметки. HTML — один язык разметки, нацеленный на документы в браузере, со словарём, который браузер уже понимает.

**How it works:**

- Назначение HTML — показ и взаимодействие: заголовки, формы, скрипты. Назначение XML — нести структуру, которую вы назвали.
- Теги HTML фиксированы (`p`, `a`). Теги XML ваши (`sku`, `qty`).
- XML обязан быть корректно оформлен: один корень, закрытые теги, атрибуты в кавычках. Парсеры HTML чинят много сломанной разметки. XHTML — это HTML, записанный по более строгим правилам XML.
- Атрибуты и элементы XML — данные. Атрибуты HTML часто питают отрисовку и поведение (`href`, `onclick`).
- Документы HTML интерактивны, потому что браузер запускает скрипт и применяет CSS. Документ XML ничего не делает, пока программа его не истолкует.
- Оба могут выглядеть похожими тегами. Путаница значит либо браузер, который не нарисует ваш `<order>`, либо строгий парсер, который отвергнет незакрытый `<p>`.

**Examples:**

```html
<p>Qty: 2</p>
```

это HTML, который браузер показывает. `<qty>2</qty>` — XML, который читает программа. Браузер не знает, что `qty` — число. Ваша схема может знать.
</details>

<details>
<summary>What is an XML document and what are its main components?</summary>

### What is an XML document and what are its main components?

**Definition:**

Документ XML — одно дерево: необязательное объявление, необязательные комментарии и инструкции обработки и ровно один корневой элемент, который содержит остальное.

**How it works:**

- Пролог может начинаться с `<?xml version="1.0" encoding="UTF-8"?>`. Это не элемент.
- Корневой элемент оборачивает каждый другой элемент. Два элемента верхнего уровня — не корректно оформленный документ.
- Внутри корня бывают элементы, текст, атрибуты на этих элементах, комментарии и инструкции обработки.
- Well-formed значит грамматику самого XML: парные теги, атрибуты в кавычках, допустимые символы.
- Valid значит, что DTD или схема дополнительно принимает это дерево. Корректно оформленный документ всё ещё может быть недействительным.
- Ссылки на сущности вроде `&amp;` раскрываются в символы до того, как вы видите текстовое значение.

**Examples:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<catalog>
  <book id="b1">XML</book>
</catalog>
```

`catalog` — корень. `book` — ребёнок. `id` — атрибут. Объявление — метаданные для парсера, а не узел дерева элементов в том же смысле.
</details>

<details>
<summary>Describe the structure of an XML element.</summary>

### Describe the structure of an XML element.

**Definition:**

Элемент — это открывающий тег, содержимое и закрывающий тег с тем же именем. На открывающем теге могут быть атрибуты. Содержимое — текст, дочерние элементы или пустота.

**How it works:**

- `<book id="b1">Guide</book>`: имя `book`, атрибут `id`, текстовое содержимое `Guide`.
- Имена чувствительны к регистру. `<Book>` и `<book>` — разные.
- Теги должны вкладываться. Внутренний элемент закрывают до внешнего. Перекрытие не разрешено.
- Значения атрибутов в кавычках. Имя атрибута встречается на теге не больше одного раза.
- Пустой элемент можно записать `<flag></flag>` или `<flag/>`. У обоих нет детей. Атрибуты допустимы в обеих формах.
- Символьные данные, которым нужен сырой `<`, могут лежать в секции CDATA. Иначе `<` и `&` экранируют.

**Examples:**

```xml
<book id="b1">
  <title>Guide</title>
</book>
```

`book` содержит один дочерний элемент, а не текст `Guide` напрямую. JSON-объект с `"title": "Guide"` — другое дерево с теми же фактами.
</details>

<details>
<summary>What is the purpose of XML attributes?</summary>

### What is the purpose of XML attributes?

**Definition:**

Атрибуты вешают на элемент небольшие именованные значения, обычно метаданные об этом элементе, а не собственную структуру.

**How it works:**

- Они стоят в открывающем теге: `id="b1"`, `lang="en"`. Значение всегда текст и всегда в кавычках.
- Данное имя встречается один раз. Если нужно много значений или вложенные значения, используйте дочерние элементы.
- Они подходят идентификаторам, типам и флагам: компактно, без порядка и без повтора.
- Элементы подходят содержимому, у которого свои дети, повтор или смешанный текст. Атрибут не может содержать элемент.
- Пробелы в атрибуте нормализуют жёстче, чем в тексте элемента. Длинная проза принадлежит элементу.
- Атрибут это или ребёнок — выбор проекта вашего словаря, а не правило, которое XML навязывает сверх синтаксиса.

**Examples:**

```xml
<book id="b1" lang="en">
  <title>Guide</title>
</book>
```

`id` и `lang` описывают книгу. Название — содержимое, поэтому это элемент, и позже у него могут появиться свои дети.
</details>

<summary>Explain the concept of XML namespaces.</summary>

### Explain the concept of XML namespaces.

**Definition:**

Пространство имён не даёт именам элементов и атрибутов столкнуться, привязывая локальное имя к URI, который вы выбираете. Два имени `id` в разных пространствах — разные имена.

**How it works:**

- Префикс связывают через `xmlns:ord="http://example.com/order"` и пишут `ord:id`.
- `xmlns="..."` задаёт пространство имён по умолчанию для этого элемента и его детей. Элементы без префикса используют его. Атрибуты без префикса — нет. Они остаются вне пространства имён, пока их не пометили.
- URI — идентификатор, а не документ, который парсер обязан скачать.
- Без пространств имён составной документ не отличит ваш `title` от `title` другого словаря.
- Проверка схемой и XPath нуждаются в тех же URI. Префикс может меняться. Совпасть должен URI.
- Пространства по умолчанию — частый источник ошибок: ребёнок выглядит без префикса и всё равно в пространстве по умолчанию.

**Examples:**

```xml
<root xmlns:a="http://example.com/a" xmlns:b="http://example.com/b">
  <a:item id="1"/>
  <b:item id="2"/>
</root>
```

Оба локальных имени — `item`. Это не один и тот же элемент. Уберите префиксы — одна схема их не различит.
</details>

<summary>What is the difference between well-formed and valid XML?</summary>

### What is the difference between well-formed and valid XML?

**Definition:**

Корректно оформленный XML подчиняется синтаксическим правилам XML. Действительный XML корректно оформлен и ещё удовлетворяет DTD или схеме, которую вы назвали.

**How it works:**

- Well-formed: один корень, у каждого открывающего тега есть закрывающий, элементы правильно вложены, значения атрибутов в кавычках, имена законны, а `&` и `<` в тексте экранированы.
- Парсер отвергает вход, который не well-formed. Документа, который вам отдать, нет.
- Действительность добавляет словарь: какие элементы могут появиться, в каком порядке, сколько раз, какие атрибуты обязательны и как должен выглядеть текст (дата, целое).
- Документ может быть well-formed и недействительным: `<qty>lots</qty>` — нормальный синтаксис и провал схемы, которая говорит, что `qty` — целое.
- Корректность оформления проверяет каждый XML-парсер. Действительность проверяют, только когда просят проверку DTD или схемы.
- Не пропускайте well-formed и не «будьте либеральны». XML-парсеры строги нарочно.

**Examples:**

`<a><b></a></b>` не является well-formed (теги перекрещены). `<qty>lots</qty>` внутри одного корня — well-formed. Против схемы, где `qty` имеет тип `xs:integer`, это недействительно.
</details>

<details>
<summary>What is the role of XML declaration in an XML document?</summary>

### What is the role of XML declaration in an XML document?

**Definition:**

Объявление XML говорит парсеру, какую версию XML и какую кодировку символов используют байты. Оно необязательно и не является элементом.

**How it works:**

- Форма: `<?xml version="1.0" encoding="UTF-8" standalone="yes"?>`. Если вы его включаете, оно должно быть самым началом файла. Перед ним нет комментария и пробелов.
- `version` — `1.0` или `1.1`. 1.0 — то, что почти всё ещё использует.
- `encoding` называет, как превратить байты в символы. Если объявление опущено, парсер откатывается к правилам UTF-8 или UTF-16 из спецификации.
- `standalone="yes"` утверждает, что документ не зависит от внешних объявлений DTD для своего содержимого. Это подсказка такой обработке, а не переключатель безопасности.
- Неверное объявление кодировки портит документ или заставляет парсер упасть. Байты и подпись должны совпасть.
- Оно похоже на инструкцию обработки. Считайте его прологом, а не данными приложения.

**Examples:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<note>café</note>
```

Файл в UTF-8, поэтому `é` — байты UTF-8 этого символа. Подпись `encoding="UTF-16"` заставляет корректный парсер отвергнуть его.
</details>

<summary>Describe the concept of XML entities and their usage.</summary>

### Describe the concept of XML entities and their usage.

**Definition:**

Сущность — именованный заместитель. Когда парсер видит ссылку, он подставляет значение сущности. Встроенные сущности существуют, чтобы символы разметки могли появиться как текст.

**How it works:**

- Предопределённые сущности: `&lt;` `<`, `&gt;` `>`, `&amp;` `&`, `&apos;` `'`, `&quot;` `"`. В тексте нужны `&amp;` и `&lt;`, иначе парсер думает, что началась разметка.
- Ссылка на символ числовая: `&#233;` или `&#xE9;` — это `é`. Объявление ей не нужно.
- DTD может объявить общую сущность: `<!ENTITY city "Paris">`, используется как `&city;` в содержимом.
- Параметрические сущности (`%name;`) — для использования внутри самого DTD, чтобы переиспользовать куски объявлений.
- Внешние сущности указывают на другой файл или URL. Это проблема XXE: парсер, который их раскрывает, можно обманом заставить читать локальные файлы или звать внутренние хосты. Отключайте раскрытие внешних сущностей, если вы полностью не контролируете DTD.
- Сущности раскрываются до того, как приложение видит текст. Это не теги.

**Examples:**

```xml
<note>Tom &amp; Jerry &#x2014; a title</note>
```

Текстовое значение — `Tom & Jerry — a title`. Сырой `&` нельзя было записать без экранирования.
</details>

### What are the rules for naming XML elements and attributes?

**Definition:**

Имена элементов и атрибутов следуют одному правилу Name. Они чувствительны к регистру и не могут содержать пробелы или начинаться с цифры или знака препинания, который уже использует разметка.

**How it works:**

- Имя может начинаться с буквы, подчёркивания или двоеточия. Дальше допустимы также цифры, дефисы и точки. Двоеточия грамматика разрешает, но они заняты префиксами пространств имён. Не ставьте двоеточие в имя, которое вы придумываете, если это не настоящий префикс.
- `item`, `_id` и `sku-2` законны. `2sku`, `sku code` и `sku<` — нет.
- `<Item>` и `<item>` — два разных элемента. То же для атрибутов.
- Отдельного более строгого правила для атрибутов нет. `id` как атрибут не особенный для грамматики XML (некоторые приложения особо относятся к `xml:id`).
- Имена, которые начинаются с `xml` в любом регистре, зарезервированы спецификацией (`xml:lang`, `xml:space`).
- Предпочитайте короткие устойчивые имена без двоеточий. Какие имена разрешены в вашем словаре, говорит схема, а не грамматика имён.

**Examples:**

```xml
<sku-code region="eu">A1</sku-code>   <!-- legal -->
<!-- <2sku region=eu> is illegal: name starts with a digit, attribute is unquoted -->
```

### Explain the difference between XML elements and attributes.

**Definition:**

Элементы строят дерево и могут содержать текст и другие элементы. Атрибуты — неупорядоченные строки имя-значение на одном элементе, и они не могут повторяться или вкладываться.

**How it works:**

- Элемент может появиться много раз как сосед (`<sku>` дважды). Имя атрибута может появиться на этом теге только один раз.
- Элемент может держать детей и смешанное содержимое. Значение атрибута — плоский текст.
- Порядок элементов в документе значим. Порядок атрибутов — нет. Парсеры могут отдать их в любом порядке.
- Атрибуты подходят идентификаторам, языку и единицам измерения. Элементы — спискам, длинному тексту и всему, что позже может обрасти структурой.
- Некоторым API атрибуты чуть неудобнее расширять. Добавить ребёнка обычно совместимое изменение. Превратить атрибут в элемент — нет.
- Ни один не «более действителен». Действительность — то, что говорит ваша схема. Разрез — про форму.

**Examples:**

```xml
<book id="b1">
  <author>Ada</author>
  <author>Edsger</author>
</book>
```

Двум авторам нужны элементы. `author="Ada"` нельзя повторить на том же `book`, и позже у него не вырастет ребёнок `<born>`.
</details>

<summary>What is the purpose of XML comments and how are they represented?</summary>

### What is the purpose of XML comments and how are they represented?

**Definition:**

Комментарий — заметка для людей, читающих исходник. Парсер не считает его данными, и обычное приложение никогда не видит его как элемент или как текстовое содержимое.

**How it works:**

- Синтаксис: `<!-- words -->`. Он может стоять там, где разрешена прочая разметка: в прологе, после корня и между элементами.
- Внутри не должно быть `--`. Эта последовательность — часть грамматики комментария, поэтому двойной дефис заканчивает его рано или делает документ не well-formed.
- Комментарии — не место для секретов. Они всё ещё в файле, который вы отдаёте, и часть конвейеров их сохраняет.
- Не заворачивайте настоящие данные в комментарий в надежде, что потребитель их прочитает. Данные принадлежат элементам.
- Комментарий не может стоять внутри тега и не меняет проверку окружающих элементов, кроме того, что его пропускают.

**Examples:**

```xml
<qty>2</qty> <!-- warehouse count, not the order qty -->
```

Текст приложения для `qty` — `2`. Заметка — для человека, который правит файл.
</details>

<summary>Describe the concept of XML processing instructions.</summary>

### Describe the concept of XML processing instructions.

**Definition:**

Инструкция обработки — заметка, адресованная конкретной программе, а не модели данных XML из элементов и текста. Парсер пропускает имя цели и остальной текст дальше.

**How it works:**

- Форма: `<?target instructions?>`. Цель — имя. То, что следует, решает эта программа, и это не атрибуты в смысле XML, даже когда выглядит как `key="value"`.
- `xml-stylesheet` — обычная: `<?xml-stylesheet type="text/xsl" href="style.xsl"?>` говорит браузеру или процессору, какое преобразование применить.
- Объявление XML `<?xml ...?>` выглядит похоже, но это пролог, а не инструкция приложения. Не придумывайте цель с именем `xml`.
- Цели чувствительны к регистру. Неизвестные цели игнорируют программы, которые не являются адресатом.
- Они не замена элементам. Данные, которые нужно запрашивать, принадлежат дереву. Инструкция обработки — боковой канал для инструмента.
- CDATA, ссылки на символы и объявление решают другие задачи (сырой текст, символ, кодировка). Это не инструкции обработки.

**Examples:**

```xml
<?xml-stylesheet type="text/xsl" href="order.xsl"?>
<order id="17"/>
```

Браузер, который слушает инструкцию, применяет `order.xsl`. Программа, которая только читает `order`, может проигнорировать инструкцию и всё равно увидеть элемент.

<summary>What is the difference between an empty element and a self-closing element in XML?</summary>

### What is the difference between an empty element and a self-closing element in XML?

**Definition:**

В XML это два способа записать одно и то же: элемент без содержимого. `<flag></flag>` и `<flag/>` дают один и тот же элемент в модели данных.

**How it works:**

- Тег пустого элемента `<flag/>` — синтаксис. Парная форма `<flag></flag>` тоже пуста, когда между тегами ничего нет.
- Обе могут нести атрибуты: `<flag on="true"/>` и `<flag on="true"></flag>` совпадают.
- Ни одна форма не может содержать детей. Если есть текст или ребёнок, нужны открывающий и закрывающий теги. Самозакрывающийся тег не может «ещё и» держать содержимое.
- Парсерам разрешено сообщить любое написание. Не ветвите код по тому, какая форма была в файле. Ветвите по тому, есть ли у элемента дети.
- HTML другой. Часть элементов HTML пустые по определению (`br`, `img`), и HTML5 не пользуется правилами XML. XHTML, будучи XML, считает `<br/>` и `<br></br>` одним и тем же пустым элементом.
- XML разметки Android следует правилу XML: самозакрывающаяся форма и парная пустая форма эквивалентны.

**Examples:**

```xml
<img src="a.png"/>
<img src="a.png"></img>
```

XML-парсер в обоих случаях строит один элемент с именем `img` и одним атрибутом. `<img src="a.png">caption</img>` — третий случай: он не пустой, поэтому самозакрывающаяся форма его не выразит.

<summary>Explain the concept of XML CDATA sections and their usage.</summary>

### Explain the concept of XML CDATA sections and their usage.

**Definition:**

Секция CDATA — это участок символьных данных, в котором < и & остаются обычными символами. Как разметка узнаётся только закрывающее `]]>`.

**How it works:**

- Спецификация XML говорит, что секции CDATA могут стоять везде, где допустимы символьные данные. Они экранируют куски текста, которые иначе прочитались бы как разметка.
- Они начинаются с `<![CDATA[` и заканчиваются `]]>`. Вкладывать их нельзя. Внутри левые угловые скобки и амперсанды не нужно и нельзя экранировать через `&lt;` и `&amp;`.
- В примере спецификации `<greeting>Hello, world!</greeting>` внутри секции CDATA — это символьные данные, а не элемент.
- Введение в XML на MDN — другой инструмент для тех же символов вне CDATA: пять предопределённых сущностей, включая `&lt;` и `&amp;`. Их берут, когда текст короткий или когда в данных встречается само `]]>`, потому что эта последовательность закроет секцию.
- Секция CDATA — не комментарий, не инструкция обработки и не способ спрятать разметку от разборщика, который раскрывает секцию в символьные данные.

**Examples:**

```xml
<script><![CDATA[ if (a < b && c > d) { run(); } ]]></script>
```

**Sources:**

- https://www.w3.org/TR/xml/#sec-cdata-sect
- https://developer.mozilla.org/en-US/docs/Web/XML/Guides/XML_introduction
</details>

<summary>What is the purpose of the XML prolog and what does it contain?</summary>

### What is the purpose of the XML prolog and what does it contain?

**Definition:**

Пролог — необязательное начало XML-документа перед корневым элементом. XML 1.0 говорит, что документы следует начинать с XML-декларации, которая указывает используемую версию XML.

**How it works:**

- Продукция — необязательная XML-декларация, затем прочая разметка (комментарии и инструкции обработки), затем необязательное объявление типа документа и ещё прочая разметка.
- XML-декларация — это `<?xml`, обязательная версия, необязательная кодировка и необязательное объявление standalone, и закрывается `?>`. Форма у MDN: `<?xml version="1.0" encoding="UTF-8"?>`.
- Объявление типа документа, если оно есть, стоит до первого элемента. Именно оно делает документ кандидатом на действительность: документ действителен, только если объявление есть и документ ему соответствует.
- Документ из одного корневого элемента без декларации всё равно правильно сформирован. `<?xml version="1.0"?><greeting>Hello, world!</greeting>` и `<greeting>Hello, world!</greeting>` в примерах спецификации — оба законченных правильно сформированных документа. Второй не действителен, потому что у него нет объявления типа документа.

**Examples:**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<greeting>Hello, world!</greeting>
```

- https://www.w3.org/TR/xml/#sec-prolog-dtd
- https://developer.mozilla.org/en-US/docs/Web/XML/Guides/XML_introduction

### Describe the concept of XML character references and their usage.

**Definition:**

Ссылка на символ называет один символ его кодовой позицией в ISO/IEC 10646. Десятичная форма — `&#` цифры `;`. Шестнадцатеричная — `&#x` шестнадцатеричные цифры `;`.

**How it works:**

- Указанный символ должен соответствовать продукции Char. Это ограничение правильной сформированности.
- `&#x` берёт шестнадцатеричную кодовую позицию. `&#` берёт десятичную. Обе формы кончаются на `;`.
- Числовые ссылки на символы раскрываются при распознавании и должны считаться символьными данными. Спецификация говорит, что `&#60;` и `&#38;` могут экранировать `<` и `&` в символьных данных.
- Это не ссылки на сущности. Ссылка на сущность — `&` имя `;` и подставляет именованную сущность. Пять предопределённых сущностей — `amp`, `lt`, `gt`, `apos` и `quot`. Процессоры должны узнавать их независимо от объявления.
- Ссылку на символ используют для символа, который нельзя набрать, или когда `<` или `&` нужно записать как символьные данные без секции CDATA.

**Examples:**

```xml
<price>&#8364;10</price>
<compare>&#60; and &#38;</compare>
```

**Sources:**

- https://www.w3.org/TR/xml/#sec-references
- https://www.w3.org/TR/xml/#sec-predefined-ent
</details>

<summary>What is the difference between an XML document and an XML fragment?</summary>

### What is the difference between an XML document and an XML fragment?

**Definition:**

XML-документ соответствует продукции document: необязательный пролог, ровно один корневой элемент и необязательная прочая разметка после него. Фрагмент — кусок этого дерева, а не документ сам по себе.

**How it works:**

- Правильная сформированность требует один или несколько элементов и ровно один корень, внутри которого вложены все остальные. Два соседних элемента без родителя — не документ.
- `Document` у MDN — объект, который возвращает `DOMParser.parseFromString()`, когда разбирает полную строку XML или HTML. `XMLSerializer` превращает дерево DOM обратно в исходный текст.
- `DocumentFragment` — минимальный объект документа без родителя. Он хранит отрезок узлов и не входит в активное дерево документа. Изменения фрагмента не меняют документ, пока фрагмент не вставлен.
- Вставка фрагмента через `append()` или `appendChild()` переносит его детей в документ и оставляет фрагмент пустым.
- Не отдавайте фрагмент разборщику, которому нужен один корень, и не ждите документ. Сначала оберните его одним корневым элементом.

**When to use:**

Разбирайте документ, когда есть один корень и нужен `Document`. Собирайте `DocumentFragment`, когда несколько узлов нужно собрать до присоединения к живому дереву.

- https://developer.mozilla.org/en-US/docs/Web/API/DOMParser

### Explain the concept of XML whitespace handling.

**Definition:**

Пробельные символы в XML — это один или несколько пробелов (`#x20`), табуляций (`#x9`), возвратов каретки (`#xD`) или переводов строки (`#xA`). XML-процессор обязан передать приложению каждый символ, который не является разметкой.

**How it works:**

- Редакторы ставят пробелы, чтобы разложить теги. Эти пробелы часто не должны входить в выдаваемый текст. Поэзия и исходный код — примеры спецификации значимых пробелов, которые нужно сохранить.
- Проверяющий процессор обязан также сообщить приложению, какие из этих символов — пробелы в содержимом элемента. SAX показывает это разделение: проверяющий разборщик сообщает игнорируемые пробелы через `ignorableWhitespace`, а не только через `characters`.
- `xml:space` на элементе сообщает намерение. В действительном документе атрибут надо объявить перечислением `default`, `preserve` или обоих. `default` значит, что обычная обработка приложения приемлема. `preserve` значит сохранить все пробелы. Значение действует на потомков, пока другой `xml:space` его не перекроет. Любое иное значение — ошибка.
- Сначала обрабатываются концы строк: литеральные символы `#xD` удаляются или заменяются на `#xA` до другой обработки. Ссылка на символ — способ, которым `#xD` всё ещё может соответствовать продукции пробела внутри значения сущности.

### What is XML Schema and its purpose?

**Definition:**

Язык определения схемы XML описывает структуру XML-документов и ограничивает их содержимое, включая документы, которые используют пространства имён XML. Сама схема — словарь XML и использует пространства имён.

**How it works:**

- XSD 1.1 Part 1 существенно пересобирает и расширяет то, что может сказать DTD. Он зависит от Part 2, Datatypes.
- Документ может быть правильно сформирован и всё равно не пройти схему. Действительность относительно DTD — это понятие XML 1.0 (объявление типа документа плюс соответствие). Проверка схемой — более поздняя и более богатая проверка.
- Среди компонентов — объявления элементов, объявления атрибутов, определения простых типов и определения сложных типов. Объявление элемента связывает имя с типом, необязательным значением по умолчанию и ограничениями тождества.
- `targetNamespace` на элементе `schema` называет пространство имён, которое схема определяет. Пример самой спецификации структур: `<schema targetNamespace="http://www.example.com/XMLSchema/1.0/mySchema">`.

**When to use:**

Используйте схему, когда потребители должны отвергать документы, которые правильно сформированы, но имеют неверную форму. DTD оставляйте там, где тип документа уже им описан.

### Explain the difference between XML DTD and XML Schema.

**Definition:**

DTD — язык ограничений из объявления типа документа в XML 1.0. XML Schema — отдельный словарь XML, который описывает структуру и типы данных и расширяет то, что могут выразить DTD.

**How it works:**

- XML 1.0 говорит, что документ действителен, если у него есть связанное объявление типа документа и он соответствует ограничениям в нём. Объявление должно стоять до первого элемента.
- Спецификация схемы говорит, что язык схемы существенно пересобирает и значительно расширяет возможности DTD и что сам он представлен в XML и использует пространства имён. DTD в этом смысле не является экземпляром XML-документа.
- Схема связывает элемент с простым или сложным типом. Простой тип ограничивает строки и значения, которые они кодируют, для атрибутов и для элементов только с текстом. Типы атрибутов DTD — более узкий набор (CDATA, ID, IDREF и остальные из спецификации XML).
- Пространства имён — забота схемы, которую DTD не моделирует как URI пространства имён. Спецификация структур отдельно говорит о документах, которые пользуются средством пространств имён XML.

**When to use:**

Для новых словарей, которым нужны типы, пространства имён и ограничения шире DTD, предпочитайте XML Schema. DTD оставляйте, когда существующие документы проверяются так и вы ещё не готовы к переносу.

- https://www.w3.org/TR/xml/#sec-prolog-dtd
- https://www.w3.org/TR/xmlschema11-1/#intro-purpose

### What are the key components of an XML Schema document?

**Definition:**

XML Schema — это набор компонентов схемы. Те, которые на собеседовании называют первыми, — объявления элементов, объявления атрибутов, определения простых типов и определения сложных типов.

**How it works:**

- Объявление элемента связывает имя с простым или сложным типом, необязательным значением по умолчанию или фиксированным значением и, возможно, пустым набором ограничений тождества. - Другие компоненты той же спецификации — группы моделей, группы атрибутов, нотации и ограничения тождества. В маленькой схеме не нужен каждый компонент. Нужен тип для каждого элемента, который вы хотите проверять.

### Describe the concept of XML Schema data types.

**Definition:**

Типы данных XML Schema — это простые типы, которые определяет Part 2, и ограничения, которые вы строите из них. Простой тип ограничивает строку и значение, которое эта строка кодирует.

### Explain the concept of XML Schema complex types and their usage.

**Definition:**

Определение сложного типа — это набор объявлений атрибутов и тип содержимого. Оно применяется к атрибутам и детям элемента.

**How it works:**

- Тип содержимого может требовать, чтобы дети были пустыми, или были строкой определённого простого типа, или содержали элементы по модели содержимого.
- Сложный тип, который разрешает содержимое элементов или атрибутов сверх того, что разрешает другой тип, — это расширение. Ограничение сужает базовый тип. Спецификация структур отмечает, что пустое ограничение и пустое расширение приняли бы одни и те же входы, но синтаксис всё равно требует записать каждый производный тип как одно или другое.
- Сложный тип нужен, когда у элемента есть дочерние элементы или атрибуты, которые вы хотите проверять. Элемент только с текстом и без атрибутов может остаться простым типом.
- Ограничения тождества и принадлежность к группе подстановки висят на объявлении элемента, а не на идее «сложного типа» самой по себе. Тип описывает форму. Объявление прикрепляет форму к имени.

**When to use:**

Используйте сложный тип для любого элемента, чьё содержимое богаче одного простого значения. Расширяйте базу, когда добавляете атрибуты или детей. Ограничивайте базу, когда каждый действительный экземпляр нового типа уже должен был быть действителен для базы.

**Sources:**

- https://www.w3.org/TR/xmlschema11-1/#intro-purpose
</details>

<summary>What is the difference between XML Schema simple types and complex types?</summary>

### What is the difference between XML Schema simple types and complex types?

**Definition:**

Простой тип ограничивает строку и значение, которое она кодирует. Сложный тип объявляет атрибуты и тип содержимого для детей элемента.

**How it works:**

- Спецификация структур говорит, что простой тип применяется к значениям атрибутов и к элементам без элементов-детей. Каждый простой тип — ограничение своего базового типа. Встроенные простые типы приходят из спецификации типов данных.
- Сложный тип — набор объявлений атрибутов и тип содержимого. Содержимое может быть пустым, строкой простого типа или элементами.
- Если у элемента есть дочерние элементы или атрибуты, которые надо проверять, ему нужен сложный тип. Если это только текст, достаточно простого типа.
- Порождение различается. Простые типы ограничивают базу. Сложные типы записывают как расширение или ограничение другого типа.

**When to use:**

Простой тип — для листового значения, например целого или даты. Сложный тип — как только у элемента появляется структура.

**Sources:**

- https://www.w3.org/TR/xmlschema11-1/#intro-purpose

<summary>Describe the concept of XML Schema facets and their usage.</summary>

### Describe the concept of XML Schema facets and their usage.

**Definition:**

Фасет — ограничение, которое сужает пространство значений простого типа относительно базового типа. Спецификация структур называет фасет enumeration одним из случаев: значение должно быть одним из перечисленного набора.

**How it works:**

- Каждый пользовательский простой тип — ограничение базы. Фасеты — это то, как ограничение записано. Без них ограничение не говорило бы, что изменилось.
- Enumeration — фасет, который спецификация структур называет явно: фактическое значение сверяют со списком, и тип данных может быть конкретнее простой строки.
- Та же спецификация отмечает, что фиксированные значения и значения по умолчанию у элементов и атрибутов тоже привязаны к отображению типа данных, а не остаются непроверенным текстом.
- Фасеты применяются к простым типам. Они не заменяют модель содержимого сложного типа. Модель содержимого говорит, какие дети появляются. Фасет говорит, какие значения может принимать лист.

**When to use:**

Ставьте фасет на простой тип, когда базовый тип слишком широк: замкнутый набор кодов, ограниченное число или шаблон, которому должна соответствовать лексическая форма. Сложный тип используйте, когда ограничение касается дочерних элементов.

**Sources:**

- https://www.w3.org/TR/xmlschema11-1/#intro-purpose
</details>

### What is the purpose of XML Schema namespace declarations?

**Definition:**

Объявления пространств имён в схеме отделяют собственный словарь схемы от словаря, который она определяет, и называют целевое пространство имён элементов экземпляра.

**How it works:**

- Пространства имён в XML уточняют имена элементов и атрибутов, связывая их с пространством имён, которое задано ссылкой URI. Пространство имён по умолчанию объявляют через `xmlns`. Имя с префиксом использует префикс, привязанный к URI.
- Язык схемы сам является словарём XML и использует пространства имён. В примере спецификации структур на `schema` стоит `targetNamespace`, называющий определяемое пространство имён: в том примере это `http://www.example.com/XMLSchema/1.0/mySchema`.
- Элементы экземпляра в целевом пространстве имён — те, которые схема проверяет. Элементы в другом пространстве имён — другой словарь, поэтому один документ может смешивать несколько схем.
- Префикс локален. Сравнивают URI пространства имён, а не строку префикса. Два префикса, привязанные к одному URI, — одно пространство имён.

### Explain the concept of XML Schema substitution groups.

**Definition:**

Группа подстановки позволяет одному элементу стоять там, где ожидается другой элемент — голова. Спецификация структур записывает это в объявлении элемента как принадлежность к группам подстановки.

**How it works:**

- У объявления элемента есть набор принадлежностей к группам подстановки: другие объявления элементов, которые оно может заменять. Есть также исключения группы подстановки и запрещённые подстановки, которые могут блокировать расширение, ограничение или подстановку.
- Голова — объявление элемента. Члены — другие объявления элементов, которые называют эту голову. В экземпляре член может появиться там, где модель содержимого просила голову, с учётом этих исключений.
- Это свойство объявлений элементов, данное вместе с ними. Это не расширение сложного типа. Расширение добавляет содержимое типу. Подстановка меняет, какое имя элемента использовано.
- Свойство `abstract` у объявления элемента, тоже в этом компоненте, может заставить экземпляр использовать член, а не саму голову.

**When to use:**

Используйте группу подстановки, когда несколько имён элементов делят одну роль в модели содержимого и схема должна разрешить любое из этих имён. Выбор внутри сложного типа используйте, когда альтернативы локальны и их не нужно переиспользовать как глобальные элементы.

**Sources:**

- https://www.w3.org/TR/xmlschema11-1/#intro-purpose

### What is XML parsing and why is it important?

**Definition:**

Разбор XML читает текстовый документ и сообщает его структуру: элементы, атрибуты и символьные данные по правилам правильной сформированности. Без разборщика приложение угадывало бы теги.

**How it works:**

- У правильно сформированного документа ровно один корень и правильно вложенные элементы. Разборщик отвергает текст, который нарушает эти ограничения, вместо того чтобы отдать приложению полусобранное дерево.
- Ссылки на символы и предопределённые сущности раскрывает процессор. Разметку вроде комментариев и инструкций обработки он отделяет от символьных данных.
- Обычны две формы API. Древесный API строит документ, по которому можно ходить потом. `DOMParser.parseFromString()` возвращает `Document`. Событийный API сообщает начало и конец элементов по мере чтения. SAX `ContentHandler` — эта форма: разборщик вызывает `startElement` и `endElement`.
- Разбор делает возможными следующие шаги: XPath, проверка схемой и преобразование предполагают, что процессор уже распознал разметку.

- https://developer.mozilla.org/en-US/docs/Web/API/DOMParser

<summary>Explain the difference between DOM and SAX parsing.</summary>

### Explain the difference between DOM and SAX parsing.

**Definition:**

Разбор DOM строит дерево и возвращает его. Разбор SAX сообщает события по мере чтения и дерево не хранит.

**How it works:**

- В браузере `DOMParser.parseFromString()` разбирает строку XML в `Document`. Дальше вы обходите `childNodes` или запрашиваете дерево. После возврата вызова весь документ в памяти.
- SAX `ContentHandler` — другой контракт. Приложение регистрирует обработчик через `setContentHandler`. Разборщик вызывает `startDocument`, `startElement`, `characters`, `endElement` и `endDocument` в порядке документа. Содержимое элемента сообщается между парными событиями начала и конца.
- DOM можно пересматривать и менять. SAX — один проход. Если родитель нужен после того, как вы увидели следующего соседа, SAX уже ушёл дальше, если вы сами его не сохранили.
- SAX может отвергнуть работу или пропустить её до конца документа. Фатальная ошибка может остановить разбор так, что `endDocument` не будет вызван.

**When to use:**

Используйте DOM или `DOMParser`, когда документ достаточно мал, чтобы его держать, и вы будете запрашивать его больше одного раза. Используйте SAX, когда документ велик и решение можно принять по мере прихода каждого элемента.

**Sources:**

- https://developer.mozilla.org/en-US/docs/Web/API/DOMParser
- https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/org/xml/sax/ContentHandler.html

<summary>What are the advantages and disadvantages of using DOM parsing?</summary>

### What are the advantages and disadvantages of using DOM parsing?

**Definition:**

Разбор DOM даёт `Document`, который можно обходить и менять. Цена в том, что дерево лежит в памяти для всего документа.

**How it works:**

- `DOMParser.parseFromString()` возвращает `Document`. `XMLSerializer` может превратить это дерево обратно в текст XML. Java `DocumentBuilder.parse` делает ту же работу из файла, потока, URI или SAX `InputSource`, а `newDocument()` строит пустое дерево.
- Плюсы: произвольный доступ, второй запрос без повторного чтения файла и прямые правки. XPath на MDN определён как способ адресовать части такого дерева.
- Минусы: память растёт вместе с документом. Результат нельзя выдать, пока разбор не закончится. Потоковый обработчик вроде SAX `ContentHandler` или StAX `XMLStreamReader` не держит неиспользуемых соседей.
- MDN отмечает, что `DocumentFragment` — более лёгкое место собрать узлы перед присоединением. Он не снимает цену разбора огромного источника в `Document`.

**When to use:**

Используйте DOM, когда документ будут запрашивать или править и он помещается в память. Потоковый разборщик предпочтителен, когда нужен один проход по большому файлу.

### Describe the concept of XML XPath and its usage.

**Definition:**

XPath — язык путей XML. MDN говорит, что он использует не-XML синтаксис, чтобы адресовать части XML-документа и проверять, соответствует ли узел образцу.

**How it works:**

- Пути похожи на URL: шаги по дереву. Не-XML синтаксис намеренный, чтобы путь мог стоять в URI или в значении атрибута.
- XPath в основном используют в XSLT. MDN также описывает его как способ ходить по DOM XML-подобного документа, включая HTML и SVG, через `XPathExpression`, а не только через `getElementById`, `querySelectorAll` и `childNodes`.
- Оси описывают отношения между узлами. Функции считают над узлами, которые путь выбрал. MDN держит эти два списка как справочник.
- Путь документ не преобразует. Он выбирает. Преобразование — задача XSLT, а запрос к набору документов — задача XQuery.

**Examples:**

Путь вроде `/catalog/book[@id='b1']/title` указывает на дочерний `title` того `book`, у которого атрибут `id` равен `b1`, начиная от корня документа.

**Sources:**

- https://developer.mozilla.org/en-US/docs/Web/XML/XPath
</details>

<summary>What is the purpose of XML XSLT and how does it work?</summary>

### What is the purpose of XML XSLT and how does it work?

**Definition:**

XSLT — язык преобразования XML-документов в другие XML-документы. XSLT 3.0 рассчитан на использование вместе с XPath 3.0 и делит с XPath модель данных.

**How it works:**

- Таблица стилей сопоставляет узлы и пишет дерево результата. XPath, а не второй язык запросов XML, — это то, как шаблон адресует источник.
- Главное изменение XSLT 3.0 относительно 2.0 — потоковый режим: преобразование, которому не нужно держать в памяти весь источник или весь результат. Другая цель — модульность, чтобы большую таблицу стилей можно было собрать из независимо разработанных компонентов.
- Сама таблица стилей — XML. Источник — XML. Результат часто тоже XML, но заявленная основная цель языка — преобразовывать XML в другой XML.
- У SAX среди известных реализаций `ContentHandler` есть `TransformerHandler`: это событийный способ, которым процессор может получить источник. DOM заранее строить не обязательно, если процессор работает потоком.

**When to use:**

Используйте XSLT, когда задача — декларативное отображение одной формы XML в другую. Код приложения используйте, когда отображение зависит от состояния, которое XSLT только затуманит.

### Explain the concept of XML DOM traversal and manipulation.

**Definition:**

Обход DOM проходит по дереву узлов, которое построил разборщик. Изменение вставляет, перемещает или заменяет эти узлы, а затем может сериализовать дерево обратно в XML.

**How it works:**

- `DOMParser.parseFromString()` создаёт `Document`. Дальше `childNodes`, `getElementById` и `querySelectorAll` обходят элементы. MDN также указывает на XPath как на более сильную адресацию в то же дерево.
- `DocumentFragment` — обычное место собрать поддерево в стороне. `append`, `prepend` и `replaceChildren` меняют его детей. Присоединение фрагмента к живому родителю переносит узлы и оставляет фрагмент пустым.
- `XMLSerializer` делает обратное разбору: дерево DOM становится исходным текстом XML или HTML.
- Java `DocumentBuilder.newDocument()` создаёт пустой `Document`, который можно наполнить, а `parse` наполняет его из байтов. Правки относятся к дереву, а не к исходному файлу, пока вы не запишете сериализацию.
- Обход видит логическое дерево. Порядок атрибутов в открывающем теге в XML не значим, поэтому не рассчитывайте, что порядок атрибутов переживёт разбор и запись.

### What is the difference between XML pull parsing and push parsing?

**Definition:**

При выталкивающем разборе ваш код вызывают, когда разборщик готов. При вытягивающем разборе разборщик ждёт, пока ваш код попросит следующее событие.

**How it works:**

- SAX — выталкивающий. Вы реализуете `ContentHandler`, и разборщик вызывает `startElement`, `characters` и `endElement` в порядке документа. Между событиями разборщик не поставить на паузу, кроме как бросив исключение из обратного вызова.
- StAX `XMLStreamReader` — вытягивающий. Он начинается с `START_DOCUMENT`. Вы вызываете `hasNext()` и `next()`, затем читаете текущее событие через `getEventType()`, `getLocalName()` или `getText()`.
- Вытягивающий код может вставлять другую работу между событиями и может остановиться, не заводя объект обработчика. Выталкивающий код держит цикл разбора внутри разборщика, и это просто, когда вы только реагируете.
- Оба — один проход. Ни один не строит дерево DOM, которое возвращает `DocumentBuilder.parse`.

**When to use:**

Используйте вытягивание (`XMLStreamReader`), когда циклом должно управлять приложение. Используйте выталкивание (SAX), когда обработчик уже совпадает с событиями и циклом должен управлять разборщик.

**Sources:**

- https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/org/xml/sax/ContentHandler.html
- https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/javax/xml/stream/XMLStreamReader.html

<summary>Describe the concept of XML streaming and its benefits.</summary>

### Describe the concept of XML streaming and its benefits.

**Definition:**

Потоковая обработка читает или пишет XML, не держа весь документ деревом. Выигрыш — ограниченная память и более ранний результат.

**How it works:**

- `XMLStreamReader` задан как доступ только вперёд и только для чтения и как самый низкоуровневый эффективный способ читать XML. Вы идёте через `next()` и не получаете `Document`.
- SAX потоковый в другую сторону: события приходят по порядку, а символьные данные могут быть разбиты на несколько вызовов `characters`. Документ вы всё равно не держите.
- XSLT 3.0 добавил потоковый режим, чтобы ни источник, ни результат не нужно было целиком держать в памяти. Та же идея на уровне таблицы стилей.
- Разбор DOM потоковым не бывает. `DOMParser` и `DocumentBuilder.parse` возвращают управление только когда дерево уже есть.
- Поток теряет произвольный доступ. Если позднее решение требует более раннего соседа, которого вы не сохранили, вернуться по `XMLStreamReader` нельзя.

**When to use:**

Поток используйте, когда документы велики или когда результат можно выдать, как только один элемент закончен. DOM стройте, когда потом нужно запрашивать произвольные узлы.

**Sources:**

- https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/javax/xml/stream/XMLStreamReader.html
- https://www.w3.org/TR/xslt-30/#intro

<summary>What is the purpose of XML SAX events and how are they handled?</summary>

### What is the purpose of XML SAX events and how are they handled?

**Definition:**

События SAX — это обратные вызовы, которые разборщик делает, распознавая разметку. Приложение обрабатывает их, реализуя `ContentHandler` и регистрируя его через `setContentHandler`.

**How it works:**

- `startDocument` вызывается один раз, до остальных событий, кроме того что `setDocumentLocator` может прийти раньше. `endDocument` вызывается после успешного разбора. Фатальная ошибка может пропустить `endDocument`.
- `startElement` сообщает URI пространства имён, локальное имя, уточнённое имя и атрибуты. `endElement` использует те же имена. Содержимое элемента, включая детей, сообщается между этими двумя вызовами, даже если элемент пуст.
- `characters` сообщает кусок символьных данных. Разборщик может разбить один участок текста на несколько вызовов. Приложение должно читать только `ch[start]` на `length` символов. Проверяющие разборщики сообщают игнорируемые пробелы через `ignorableWhitespace`.
- `processingInstruction` сообщает цель и данные. Разборщик SAX не должен использовать этот метод для XML-декларации. Для версии, кодировки и standalone есть отдельный обратный вызов `declaration`.
- `startPrefixMapping` и `endPrefixMapping` сообщают область пространства имён. `skippedEntity` сообщает сущность, которую разборщик не раскрыл.

**Sources:**

- https://docs.oracle.com/en/java/javase/21/docs/api/java.xml/org/xml/sax/ContentHandler.html
</details>

### Explain the concept of XML StAX (Streaming API for XML) and its usage.

**Definition:**

StAX — потоковый API с вытягиванием. `XMLStreamReader` даёт доступ только вперёд и только для чтения: приложение двигает курсор методами `next()` и `hasNext()`.

**How it works:**

- Экземпляр начинается с `START_DOCUMENT`. `getEventType()` — текущее событие. `next()` загружает следующее. На `END_DOCUMENT` допустимый вызов — `close()`.
- События включают XML-декларацию, DTD, открывающий тег, символьные данные, пробелы, закрывающий тег, комментарий и инструкцию обработки. На `START_ELEMENT` можно вызвать `getLocalName()`, методы `getAttribute` и `getElementText()`. На символьных данных вызывают `getText`.
- Вызов метода в неверном состоянии бросает `IllegalStateException`. Класс документирует, какие методы допустимы для каждого типа события.
- Во время события DTD `getProperty("javax.xml.stream.notations")` и `getProperty("javax.xml.stream.entities")` отдают нотации и объявления сущностей. Эти свойства определены так, что возвращают null, если сведений нет, и они только для события DTD.
- Это не SAX. Вас никто не вызывает. Вы опрашиваете.

**When to use:**

Используйте `XMLStreamReader`, чтобы читать большой документ одним проходом вперёд, когда цикл должен быть в вашем коде.

### Explain the concept of XML SAX (Simple API for XML) and its usage.

**Definition:**

SAX — событийный API. Разборщик читает документ и вызывает `ContentHandler` для каждого логического куска, вместо того чтобы вернуть дерево.

**How it works:**

- Требования спецификации покрывают путь от XML Schema к Java, включая привязки по умолчанию и настраиваемую схему привязки, и обратное направление, от Java к XML Schema.
- Архитектура использует аннотации отображения и каркас привязки. Демаршалинг и маршалинг — два направления во время выполнения. Проверка может идти как часть этих шагов, и спецификация также позволяет отключить проверку схемой.
- Выигрыш в том, что код приложения видит поля и объекты, а не события `startElement` или сырой `Document`. Отображением управляет схема, а не написанные вручную разборщики.

- Текущая спецификация — Jakarta XML Binding 4.0. Пакет — `jakarta.xml.bind`, а не прежний `javax.xml.bind`, которого Java SE больше не поставляет.

**When to use:**

Используйте привязку, когда схема стабильна и нужны объекты Java. Используйте SAX или StAX, когда граф объектов строить нельзя.

### What is the purpose of XML XQuery and how does it differ from XPath?

**Definition:**

XQuery — язык запросов к источникам данных XML. XPath адресует части документа. XQuery использует модель XPath и добавляет язык, который запрашивает несколько источников и строит результат.

**How it works:**

- Рекомендация XQuery 3.1 говорит, что язык запросов, который разумно использует структуру XML, может запрашивать структурированные и полуструктурированные документы, реляционные данные и хранилища объектов, независимо от того, хранятся ли данные как XML или только видны как XML.
- XPath, по MDN, — не-XML синтаксис путей, чтобы указывать на узлы и проверять образцы. Сам по себе он не описывает запрос в стиле FLWOR и не описывает построенный документ-результат. XSLT — язык преобразований, который встраивает XPath.
- XQuery 3.1 также покрывает JSON: карты и массивы в модели данных для приложений, которые смешивают JSON с XML и HTML.
- Путь нужен, когда документ уже в руках и нужен узел. Запрос нужен, когда вопрос охватывает много документов или должен вернуть новую структуру.

**When to use:**

Выбирайте XPath внутри XSLT, DOM или поиска по одному документу. Выбирайте XQuery, когда задача — запрос к коллекции.

### Explain the concept of XML Namespaces and their usage in XML technologies.

**Definition:**

Пространство имён XML уточняет имя элемента или атрибута, связывая его со ссылкой URI, чтобы два словаря могли делить документ без столкновения.

**How it works:**

- Рекомендация Namespaces говорит, что это простой способ уточнять имена. Пространство имён по умолчанию использует `xmlns="uri"` и действует на элементы без префикса в области видимости. Префикс привязывают через `xmlns:prefix="uri"` и используют как `prefix:local`.
- Область — элемент, где стоит объявление, и его потомки, пока объявление не перекроют. Атрибуты не входят в пространство имён по умолчанию; атрибут без префикса не имеет пространства имён.
- Имена, начинающиеся с `xml`, зарезервированы самим XML. `xml:space` и `xml:lang` относятся к этому зарезервированному словарю. Не выдумывайте свои имена `xml:`.
- Схема использует пространства имён дважды: документ схемы лежит в словаре схемы, а `targetNamespace` называет определяемый словарь. XPath и DOM показывают URI пространства имён отдельно от префикса. SAX `startElement` передаёт `uri`, `localName` и `qName` именно поэтому. Канонический XML должен выбрать одну физическую форму этих объявлений, потому что префиксы не входят в логическое имя.

### What is XML Signature and its role in XML security?

**Definition:**

XML Signature — синтаксис и правила обработки W3C для цифровой подписи, которую несут в XML. Рекомендация говорит, что подписи дают целостность, аутентификацию сообщения и/или аутентификацию подписавшего для данных любого типа, лежат ли данные внутри XML подписи или в другом месте.

- XML Encryption — тот другой сервис. Подпись не скрывает данные, которые покрывает.

### What is the purpose of XML Canonicalization and its usage?

**Definition:**

Канонический XML даёт одно физическое представление XML-документа, чтобы логически эквивалентные документы, которым XML разрешает различаться синтаксисом, сравнивались как равные. Версия 1.1 — пересмотр 1.0 для атрибутов пространств имён, которые наследуют подмножества документа.

**How it works:**

- XML 1.0 допускает различия, которые не меняют логический документ: порядок атрибутов, некоторые пробелы и то, как записаны пространства имён. Подпись по сырым байтам не сошлась бы после безобидной перезаписи.
- Если у двух документов одна каноническая форма, они логически эквивалентны в том контексте приложения, который описывает спецификация, кроме нескольких необычных случаев, которые она ограничивает. Обратное не всегда верно: разные канонические формы всё ещё могут быть эквивалентны по правилам приложения, которые спецификация не пытается охватить.
- Canonical XML 1.1 определён для XML 1.0 и модели данных XPath 1.0. Для XML 1.1 он не определён. Он меняет наследование атрибутов пространства имён XML на подмножествах, включая отказ наследовать `xml:id`, и заданным образом обрабатывает пути URI в `xml:base`.
- XML Signature 1.1 требует Canonical XML 1.1 как алгоритм канонизации. Обычно его встречают именно там: перед хешированием подписанного XML.

### Explain the concept of XML Catalogs and their benefits.

**Definition:**

Каталог XML — локальная карта от внешних идентификаторов в документе к ресурсам, которые процессор должен реально открыть. Разборщик спрашивает распознаватель сущностей; каталог — таблица, в которую этот распознаватель смотрит.

**How it works:**

- Каталог не меняет правильную сформированность и не меняет схему. Он меняет только то, откуда читают байты внешней сущности.

**When to use:**

Используйте каталог или другой `EntityResolver`, когда документы ссылаются на DTD или схемы, которые можно поставить рядом с приложением. Оставляйте распознаватель по умолчанию только когда удалённая копия — именно та, которой вы намерены доверять.

<summary>What are some best practices for designing XML schemas?</summary>

### What are some best practices for designing XML schemas?

**Definition:**

Проектируйте схему как набор именованных типов и глобальных элементов в целевом пространстве имён: простые типы ограничивайте ровно настолько, насколько требуют значения, а сложные типы оставляйте для структуры.

**How it works:**

- Поместите словарь в `targetNamespace`. Сам документ схемы живёт в пространстве имён схемы, поэтому они не сталкиваются. На этом разделении построена спецификация структур.
- Для листа предпочитайте простой тип, ограниченный от встроенной базы. Добавляйте фасеты вроде enumeration, когда набор значений замкнут. Сложный тип используйте, когда есть дети или атрибуты.
- Объявления элементов держите глобальными, когда на них должны ссылаться другие схемы или группы подстановки. Локальное объявление используйте, когда имя имеет смысл только внутри одного родителя.
- Меняйте пространство имён или расположение схемы, когда модель содержимого меняется так, что старые читатели не должны молча её принять. Изменённый тип в том же пространстве имён без истории версий делает старые и новые документы похожими, а падают они по-разному.
- Проверяйте схемой. Одной правильной сформированности недостаточно. `DocumentBuilder` можно настроить на проверку, и он может показать `Schema`, которую использует.

### Explain the concept of XML modularity and its benefits.

**Definition:**

Модульность XML — это разбиение словаря или таблицы стилей на части, которые собираются вместе, вместо одного документа, который определяет всё.

**How it works:**

- Пространства имён — правило сборки словарей. У каждого модуля свой URI пространства имён. Документ смешивает их префиксами. Рекомендация Namespaces существует, чтобы эти имена оставались уточнёнными.
- Компоненты схемы могут быть глобальными, поэтому другой документ схемы может сослаться на элемент или тип, а не копировать его. Группы подстановки — один механизм переиспользования на объявлениях элементов.
- XSLT 3.0 прямо называет модульность целью проекта: большие таблицы стилей из независимо разработанных компонентов. Потоковость — другая цель; модульность делает большое преобразование поддерживаемым.
- Внешние сущности и каталоги — физическая сторона. Грамматика может жить в своём файле, а `EntityResolver` может загрузить вашу копию. Это переиспользование текста, и оно слабее переиспользования компонентов схемы, потому что включённый текст сам не является пространством имён.

**When to use:**

Делите по пространству имён и по глобальным компонентам схемы, когда словарём владеет больше одной команды. Делите таблицу стилей XSLT, когда независимые преобразования нужно сочетать.

### What is the purpose of XML versioning and how is it achieved?

**Definition:**

Версионирование говорит читателю, какую грамматику использует документ, чтобы изменение грамматики было видно, а не принималось за действительный старый документ.

**How it works:**

- Версия в XML-декларации — это версия XML, например `1.0`, а не версия вашего словаря. Не перегружайте её как версию приложения.
- `targetNamespace` схемы — устойчивое имя словаря. Ломающее изменение принадлежит новому URI пространства имён, чтобы старые и новые элементы не проходили проверку типами друг друга.
- Внутри одного пространства имён совместимое расширение может добавить необязательное содержимое. Расширение сложного типа в спецификации структур — механизм, который добавляет атрибуты или детей. Старые читатели, которые игнорируют неизвестные необязательные части, всё ещё читают ядро. Читателям со строгой проверкой нужна новая схема.
- Документ может также нести атрибут версии приложения в вашем собственном пространстве имён. Это соглашение поверх пространства имён, полезное, когда пространство имён остаётся тем же и появляются только необязательные поля.

**When to use:**

Меняйте URI пространства имён, когда меняется обязательная модель содержимого. Расширяйте сложный тип и сохраняйте пространство имён, когда вы только добавляете необязательные сведения.

### Describe the concept of XML internationalization and localization.

**Definition:**

Интернационализация — это пометка, на каком естественном языке содержимое документа, и кодирование этого содержимого в Unicode. Локализация — поставка содержимого для конкретного языка.

**How it works:**

- XML 1.0 определяет для этого `xml:lang`. Атрибут задаёт язык содержимого элемента и значений его атрибутов. Значения — языковые метки IETF BCP 47, и пустая строка допустима. В действительном документе атрибут надо объявить, если он используется.
- Объявление относится к элементу и в модели обработки спецификации идентифицирует язык этого содержимого. Ребёнок может задать другой `xml:lang`.
- Кодировка в XML-декларации, например `UTF-8` в примере MDN, — это то, как байты отображаются в символы. Ссылки на символы адресуют кодовую позицию в ISO/IEC 10646, когда символ не набран напрямую.
- Имена элементов, говорит спецификация, должны быть словами, и в именах разрешены почти все символы. Это отдельный выбор от `xml:lang`: язык тегов и язык содержимого не обязаны совпадать.
- Локализация не требует отдельной схемы на каждый язык, если структура одна и та же. Она требует другие символьные данные, помеченные `xml:lang`.

**Examples:**

```xml
<p xml:lang="en">The quick brown fox</p>
<p xml:lang="ru">Быстрая бурая лиса</p>
```

### Explain the concept of XML security and its key considerations.

**Definition:**

Безопасность XML — это набор механизмов W3C, которые подписывают XML, шифруют XML и приводят подписанные байты к канонической форме, плюс обычные правила XML, которые не дают разборщику принять данные за разметку.

**How it works:**

- Целостность и аутентификация подписавшего — это XML Signature: подпись над данными внутри документа или снаружи. Конфиденциальность — XML Encryption: элемент шифрования, который содержит шифрданные или ссылается на них; это может быть один элемент или содержимое элемента.
- Canonical XML 1.1 даёт последовательность байтов, которую эти подписи хешируют, чтобы порядок атрибутов и синтаксис пространств имён не меняли подписанное значение. XML Signature 1.1 требует эту канонизацию.
- Работа разборщика отдельно. Символьные данные должны экранировать `<` и `&` или использовать секцию CDATA, у которой особая последовательность только `]]>`. Внешние сущности разрешаются через `EntityResolver`. Направляйте этот распознаватель на локальные копии, которым доверяете, а не на то, что документ просит забрать из сети.
- XKMS распространяет и регистрирует открытые ключи, которые используют эти шаги подписи и шифрования. Ключ не внутри алгоритма; его нужно связать со стороной.
- Ничто из этого не заменяет TLS на проводе. Они защищают XML-документ как документ, в том числе после хранения или пересылки.

### What is XML Signature and how does it ensure data integrity?

**Definition:**

XML Signature — структура XML, проверка которой проходит, только если подписанные данные всё ещё совпадают с подписанным дайджестом. Рекомендация определяет это как сервис целостности вместе с аутентификацией сообщения и аутентификацией подписавшего.

**How it works:**

- Данные могут быть внутри того же XML или в другом месте. Правила обработки подписи выбирают байты, канонизируют XML, когда данные — это XML, хешируют их и проверяют это значение подписью.
- Canonical XML 1.1 делает последовательность байтов устойчивой. Без него смена порядка атрибутов меняла бы хеш, хотя логический документ не изменился. С ним настоящее изменение текста меняет каноническую форму, и дайджест больше не совпадает.
- XML Signature 1.1 требует Canonical XML 1.1 и называет алгоритмы хеша, которые входят в соответствие. Хеш и есть проверка целостности. Слабый хеш её подрывает, поэтому рекомендация добавила дополнительные алгоритмы хеша.
- Проверка использует открытый ключ. Она не расшифровывает нагрузку. Скрытие нагрузки — это XML Encryption.

**Sources:**

- https://www.w3.org/TR/xmldsig-core1/#sec-Overview
- https://www.w3.org/TR/xml-c14n11/#sec-Intro

### Explain the concept of XML Encryption and its role in data confidentiality.

**Definition:**

Роль XML Encryption — конфиденциальность: данные шифруют, и результат представляют как XML. Рекомендация говорит, что результат — элемент XML Encryption, который содержит шифрданные или ссылается на них.

**How it works:**

- Вход может быть потоком октетов или XML: целым документом, одним элементом или содержимым элемента. Шифрование содержимого элемента оставляет окружающие теги видимыми и скрывает то, что было внутри.
- Получатель расшифровывает по сведениям о ключе, связанным с этим элементом шифрования. Без этого ключа шифртекст бесполезен.
- Конфиденциальность здесь про документ, а не про сеанс TLS, который его вёз. Хранимое сообщение остаётся конфиденциальным, только если применено это шифрование или равносильное.
- Сервис целостности оно не даёт. Шифртекст всё ещё можно подменить. Сочетайте его с XML Signature, когда нужно ещё и заметить изменение и опознать подписавшего.

### What is the purpose of XML Digital Signatures and how are they created?

**Definition:**

Назначение — целостность, аутентификация сообщения и аутентификация подписавшего для любых данных, внутри документа подписи или снаружи. Создание следует правилам обработки XML Signature: выбрать данные, канонизировать XML, хешировать и подписать.

**How it works:**

- Элемент подписи записывает, что подписано, какие алгоритмы канонизации и хеша использованы и значение подписи. Версия 1.1 требует Canonical XML 1.1, чтобы хешируемые байты не зависели от незначащего синтаксиса.
- Алгоритмы хеша — часть подписи. Рекомендация 1.1 расширила набор, который реализации должны поддерживать, включая дополнительные хеши и Elliptic Curve DSA, потому что дайджест — это то, что проверка потом пересчитывает.
- Закрытый ключ создаёт значение подписи. Проверяющие используют открытый ключ. Описание цифровой подписи у NIST — та же операция: закрытый ключ подписывает, открытый проверяет, и результат — не конфиденциальность.
- Создание подписи не шифрует данные, на которые она ссылается. Если данные надо скрыть, примените XML Encryption отдельным шагом и подпишите тот результат, который нужно защитить.

### Describe the concept of XML Key Management and its importance.

**Definition:**

Управление ключами XML (XKMS) задаёт протоколы распространения и регистрации открытых ключей для использования с XML Signature и XML Encryption. У него две части: X-KISS, сервис сведений о ключах, и X-KRSS, сервис регистрации ключей.

**How it works:**

- Подпись полезна лишь настолько, насколько крепка связь открытого ключа и подписавшего. XKMS — это то, как клиент просит сервис найти и проверить эти сведения о ключе, вместо того чтобы принимать каждое решение о доверии локально.
- X-KRSS — сторона регистрации: владелец регистрирует открытый ключ в сервисе. X-KISS — сторона запроса: проверяющий спрашивает, что ключ означает.
- Рекомендация прямо говорит, что эти протоколы подходят для использования вместе с рекомендациями XML Signature и XML Encryption. Они не заменяют правила обработки тех рекомендаций.
- Важность следует из этого разделения. Алгоритмы шифрования и подписи не называют человека. Управление ключами называет. Без зарегистрированного и находимого открытого ключа проверяющий не может решить, чью подпись он только что проверил.

**Sources:**

- https://www.w3.org/TR/xkms2/#sec-Introduction

### What is the role of XML in web services and service-oriented architectures (SOA)?

**Definition:**

В сервис-ориентированной системе XML — формат сообщения, который несёт самоописываемый запрос или ответ между сервисами. SOAP 1.2 определяет это сообщение как конструкцию XML, которая может идти по разным нижележащим протоколам.

**How it works:**

- Каркас сообщений SOAP расширяем и децентрализован. Конверт — XML, поэтому посредники видят структуру, маршрутизируют по заголовкам и оставляют нагрузку в её собственном пространстве имён.
- Нагрузку можно описать схемой: объявления элементов и сложные типы говорят, что содержит действительное тело. Проверка на границе отвергает правильно сформированное сообщение, которое не совпало с контрактом.
- XML Signature и XML Encryption применяются к сообщению как к документу, и это важно, когда сообщение хранят или оно проходит узел, который не является исходным сеансом TLS.
- XKMS — спутник для открытых ключей, которые эти сервисы используют. Архитектура такая: схема для контракта, SOAP для конверта, подпись и шифрование для документа, пространства имён, чтобы словарь каждого сервиса оставался отдельным.
- Более поздний HTTP API может слать JSON. Это не меняет роль XML в слое сервисов на SOAP: типизированное сообщение с пространствами имён.

- https://www.w3.org/TR/xmlschema11-1/#intro-purpose
- https://www.w3.org/TR/xml-names/#ns-decl

### Explain the concept of XML-based protocols such as SOAP and REST.

**Definition:**

SOAP 1.2 — протокол на XML: лёгкий каркас сообщений, чьё сообщение — конструкция XML, которой обмениваются поверх нижележащего протокола. REST — не протокол на XML. MDN определяет REST как ограничения архитектуры для распределённых систем и отмечает, что HTTP API часто называют REST, даже когда они не выполняют каждое ограничение.

**How it works:**

- Сообщение SOAP — это XML. Пространства имён отделяют конверт от нагрузки. Каркас расширяем, и одну и ту же конструкцию сообщения можно везти больше чем одним транспортом. Part 1 — каркас сообщений, а не программный API.
- Взаимодействие REST передаёт представление ресурса обычными операциями клиента и сервера. Представление может быть XML, а может быть чем-то другим. Ничто в ограничениях REST не требует конверта XML, описания WSDL или заголовка SOAP.
- Выбор SOAP означает выбор XML как сообщения и, обычно, схемы как контракта, плюс XML Signature или XML Encryption, когда защищать нужно сам документ.
- Выбор HTTP API в стиле REST означает выбор ресурса и метода HTTP. Если представление — XML, правила XML всё равно действуют: один корень, пространства имён, если смешиваются словари, и схема, если вы проверяете. Протоколом остаётся HTTP.

**When to use:**

Используйте SOAP, когда контракт — XML-сообщение, которое должно пройти посредников без изменения. Используйте HTTP с XML или не-XML представлением, когда клиент вызывает ресурсы обычными веб-средствами: в этом смысле MDN говорит, что новички могут считать REST API HTTP-сервисом.

**Sources:**

- https://www.w3.org/TR/soap12-part1/#intro
- https://developer.mozilla.org/en-US/docs/Glossary/REST
</details>
