<details>
  <summary>What is a data contract?</summary>

### What is a data contract?

**Definition:** **Контракт данных** — это согласованная форма и семантика данных, которыми обмениваются системы: запрос/ответ API, полезные данные событий, схема базы данных.

**How it works:**

- Типы общих ресурсов внешнего и внутреннего интерфейса (OpenAPI → Генератор кода TypeScript, общий пакет).
- Правила управления версиями: аддитивные изменения безопасны; удаление/переименование полей нарушается.
- Проверка времени выполнения (Zod) на границах, где типы стираются.

**When to use:** DTO REST API · Схемы событий Kafka · Схема GraphQL как контракт.

**Thoughts:** _Контракт = обе стороны знают, что отправлять и чего ожидать — типы и документы обеспечивают это._

**See also:** [REST, принципы и контракт](./6_web_api_rest.md#rest-principles-and-contract) · [5_ts.md](./5_ts.md)

</details>

<details>
  <summary>Why does scalability matter?</summary>

### Why does scalability matter?

**Definition:** Масштабируемость — это способность справляться с ростом (больше пользователей, данных, трафика или функций) без пропорциональных затрат или снижения качества.

**Why it matters:**

- Скачки трафика (запуск, маркетинг) могут привести к перегрузке немасштабируемых систем.
- Рост данных влияет на производительность запросов без индексации/секционирования.
- Для роста команды необходима модульная архитектура для распараллеливания работы.

**Interview framing:** Различайте **вертикальное** (больший сервер) и **горизонтальное** (больше экземпляров + балансировщик нагрузки). Упомяните кеширование, CDN, асинхронные очереди, реплики чтения БД.

**Thoughts:** _Масштабируйтесь, когда у вас есть доказательства необходимости, — но проектируйте так, чтобы вас не заблокировали, когда наступит рост._

**See also:** [0_system_design.md — Балансировка нагрузки, кеширование](./0_system_design_interview.md#interview-practice)

</details>

  <summary>Why is typing important in a team?</summary>

### Why is typing important in a team?

**Definition:** Статические типы (TypeScript) действуют как документация, проверяемая компьютером, и обеспечивают безопасность рефакторинга за пределами модуля.

| Выгода                   | Влияние команды                                                    |
| ------------------------ | ------------------------------------------------------------------ |
| Безопасный рефакторинг   | Переименовать поле → компилятор находит все варианты использования |
| Очистить API             | Сигнатуры функций заменяют племенные знания                        |
| Меньше ошибок интеграции | Типы совместного использования внешнего и внутреннего интерфейса   |
| Ускоренная адаптация     | Автозаполнение IDE объясняет кодовую базу                          |

**Thoughts:** _Типы масштабируют общение — это критично, когда к коду прикасается более одного человека._

**See also:** [5_ts.md — Почему TypeScript в больших проектах](./5_ts_interview.md#interview-practice)

<details>
  <summary>How do you choose tools for a project?</summary>

### How do you choose tools for a project?

**Definition:** При выборе инструмента учитываются требования, навыки команды, экосистема и затраты на обслуживание.

**Framework:**

1. **Требования** — SEO? В реальном времени? Мобильный? Размер команды?
2. **Знакомство с командой** — самая быстрая доставка с известным стеком
3. **Экосистема** — найм, библиотеки, сообщество, поддержка LTS.
4. **Операционные затраты** — хостинг, мониторинг, сложность CI
5. **Стоимость выхода** — насколько сложно впоследствии мигрировать

**Examples:**

| Нужна                            | Разумный выбор                           |
| -------------------------------- | ---------------------------------------- |
| SEO маркетинговый сайт           | Next.js или Nuxt SSR/SSG                 |
| Внутреннее администрирование SPA | Vite + React или Vue                     |
| Типизированная граница API       | OpenAPI + орвал + Зод                    |
| Простое глобальное состояние     | Поддержите Redux, если команда маленькая |

**Thoughts:** _Лучший инструмент = соответствует ограничениям и команде — не самое модное имя в Твиттере._

</details>

<details>
  <summary>When does MVP beat architecture?</summary>

### When does MVP beat architecture?

**Definition:** **MVP** (минимально жизнеспособный продукт) подтверждает гипотезу с помощью наименьшей сборки, обеспечивающей обучение — архитектура может подождать, пока идея не будет доказана.

**MVP wins when:**

- Соответствие рынку неизвестно — скорость обучения > идеальный код
- Ресурсы ограничены — один разработчик, короткая взлетно-посадочная полоса.
- Набор функций носит исследовательский характер — требования радикально изменятся.

**Invest in architecture when:**

- Продукт валидирован и масштабируется
- Многим разработчикам нужны четкие границы модулей.
- Применяются соглашения об уровне обслуживания, безопасности и бесперебойной работы.
- Ставка **[AI-first](./0_ai.md#ai-first-approach)** — интерактивный пользовательский интерфейс без цикла модели + оценок — это демо, а не MVP.

**Thoughts:** _MVP = подтвердить; архитектура = устойчивость — не занимайтесь золотом, пока не знаете, что строить._

</details>

<details>
  <summary>Working code vs good code?</summary>

### Working code vs good code?

**Definition:** **Рабочий код** проходит тесты и поставляется с функциями. **Хороший код** также легко читается, поддерживается, тестируется и может быть изменен следующим разработчиком.

| Рабочий код                       | Хороший код                                                |
|  ---------------------------------  |  ----------------------------------------------------------  |
| Решает сегодняшнюю задачу         | Решает задачу сегодняшнего дня + изменения завтрашнего дня |
| Может скрыть сложность            | Названия и структура раскрывают намерения                  |
| Скопируйте и вставьте ОК один раз | СУХОЙ, где дублирование вредно |
| Никаких тестов | Тесты критических путей |
| Плотная связь                     | Четкие границы (слои, модули)                              |

**Interview answer:** _ «Рабочий код реализует функцию; хороший код позволяет команде без страха реализовать следующие десять функций»._

**Principles:** SOLID, небольшие функции, осмысленные имена, проверки на границах, удаление мертвого кода.

**Thoughts:** _Хороший код — это работающий код, который ваш товарищ по команде может с уверенностью изменить._

**See also:** [SOLID](./7_special_engineering.md#9-oop-and-solid)

</details>

<details>
  <summary>What technical documentation do you actually write?</summary>

### What technical documentation do you actually write?

**Definition:** Документы, которые товарищ по команде может использовать без Slack: **README** (запускать локально), **ADR** (почему мы выбрали X), **Контракт API** (OpenAPI), **runbooks** (как развертывать/откатывать), **встроенные типы** (TS как документы).

**How it works:** Напишите решение и команду. Предпочитайте 20-строчный ADR вики-роману. Codegen (orval) предохраняет документацию API от гниения. Обновите Runbook в том же PR, что и изменение конвейера.

| Плюсы                                                     | Минусы                                                    |
| --------------------------------------------------------- | --------------------------------------------------------- |
| Скорость адаптации и инцидентов                           | Документы гниют, если не быть рядом с изменениями         |
| ADR прекращают повторное судебное разбирательство решений | Чрезмерное документирование MVP приводит к потере времени |

**When to use:** Новый прием в первый день. Откат в 3 часа ночи. Интервью: «Я пишу ADR для необратимых решений и сохраняю OpenAPI в качестве контракта».

**Thoughts:** Документы живут рядом с кодом, который они описывают.

</details>
